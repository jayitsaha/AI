Understanding ZenML
▼

What is it? ZenML is an open-source MLOps framework that turns plain Python functions into a reproducible, versioned ML workflow. You write a handful of functions, decorate them with @step, wire them together in a function decorated with @pipeline, and ZenML automatically tracks every input/output as a typed, versioned artifact, records full lineage in a metadata store, skips re-running anything that hasn't changed (caching), and lets you point the exact same code at wildly different infrastructure by swapping a stack.

Analogy: Think of the pipeline as a recipe card and the stack as the kitchen. The recipe ("ingest → train → evaluate → deploy") never changes. On your laptop, the "kitchen" is a home stove — a local orchestrator and a folder on disk. In production, the "kitchen" becomes an industrial line — Kubernetes, S3, a container registry. Same recipe, different kitchen, and ZenML is the head chef who also keeps a logbook of every dish ever cooked (metadata store) and never re-cooks a dish that's still fresh in the fridge (caching).

💡 If you remember one thing

ZenML separates what your ML workflow does (pipeline code: steps + data dependencies) from where it runs (the stack: orchestrator, artifact store, registry, deployer). Every step's inputs/outputs are content-addressed artifacts, so a step only re-executes when its code, parameters, or upstream artifacts actually change.

2
How ZenML Works Internally
▼

Steps & Typed Artifacts

Each @step is a plain Python function with type-annotated inputs and outputs (e.g. -> pd.DataFrame). When a step runs, ZenML doesn't just return the value — it materializes it: serializes it with a type-specific materializer, writes it to the artifact store (local disk, S3, GCS, Azure Blob…), and stamps it with a unique artifact ID. The metadata store (a SQL database — SQLite locally, MySQL/Postgres in production) then records which run produced which artifact, from which step, with which parameters, at what time.

Building the DAG

The @pipeline function is executed once in a "compile" pass — not to compute anything, but to trace which step's output feeds which step's input. That trace becomes a directed acyclic graph (DAG) of steps, which is what actually gets submitted to the orchestrator for execution in topological order.

The Caching Mechanism

Before running a step, ZenML computes a cache key from three ingredients: a hash of the step's source code, a hash of its parameters, and the IDs of its upstream input artifacts. If an identical key was seen in a previous run, ZenML skips execution entirely and re-links the existing artifact — instant, "free" re-use. Crucially, because the upstream artifact ID feeds into the key, changing an early step invalidates the cache for every step downstream of it, even if their own code never changed.

Stack Components

A Stack bundles the infrastructure a pipeline runs on: an Orchestrator (local, Kubeflow, Airflow, Vertex AI…), an Artifact Store, a Container Registry, an Experiment Tracker (MLflow, W&B), and a Model Deployer (KServe, Seldon, local). Running zenml stack set production swaps all five at once — the pipeline's Python code never has to know or care which one is active.

🔑 Design Decision — Why decouple stack from code?

Coupling infrastructure choices into pipeline code means every environment (dev → staging → prod) needs its own script. By making the Stack a swappable, externally-configured bundle, the identical pipeline definition can be promoted across environments untouched — only the active stack changes.

3
Why It Works — The Formalism
▼

The Pipeline as a DAG

Formally, a pipeline is a graph \(G=(V,E)\) where each vertex \(v \in V\) is a step and each edge \((u,v) \in E\) means step \(v\) consumes an artifact produced by step \(u\). Because a step can only consume artifacts already produced, \(G\) is guaranteed acyclic, so a valid execution order always exists via topological sort.

The Cache Key Function

Each step \(s\) has a deterministic cache key built from its source code, parameters, and upstream artifact IDs:

$$ \text{key}(s) = H\Big(\text{code}(s)\;\|\;\text{params}(s)\;\|\;\bigoplus_{a\,\in\,\text{inputs}(s)}\text{id}(a)\Big) $$

where \(H\) is a hash function and \(\|\) denotes concatenation. Because the artifact ID of a step's own output is itself derived from key(s) (content-addressed storage), a change anywhere upstream propagates forward: \(\text{id}(a)\) changes \(\Rightarrow\) \(\text{key}(s)\) changes for every downstream \(s\) \(\Rightarrow\) the cache misses all the way down, even for steps whose own code is untouched.

⚠️ Common Pitfall

Caching assumes a step is a pure function of its declared inputs. If a step secretly reads a file, an environment variable, or an unseeded random number that isn't part of its declared parameters or inputs, the cache key won't capture that dependency — ZenML will happily replay a stale cached artifact even though the "real" output should differ. Always declare everything a step depends on as an explicit parameter or input.

Key Takeaways
▼

When to use ZenML:

  • You need the same pipeline to run identically on a laptop and on a cloud cluster
  • Teams need audit-ready lineage: which model was deployed, from which data, with which code
  • Re-running expensive steps (large training jobs) on every small change is wasteful — caching saves real compute
  • You want to swap orchestrators/artifact stores/deployers without rewriting pipeline logic

When NOT to use it:

  • A single quick exploratory notebook with no need for reproducibility or handoff
  • Extremely simple one-off scripts where the orchestration overhead isn't justified
💡 Hierarchy

Step (one typed function) ⊂ Pipeline (a DAG of steps + artifact dependencies) ⊂ Stack (the infrastructure the pipeline is executed on). ZenML sits above raw orchestrators like Airflow/Kubeflow — it generates the DAG and lineage layer, then hands execution off to whichever orchestrator the active stack points to.

Code Trace
▼
from zenml import step, pipeline
@step
def ingest_data() -> pd.DataFrame:
return pd.read_csv("data.csv")
@step
def train(df: pd.DataFrame) -> ClassifierMixin:
model = RandomForestClassifier()
model.fit(df.drop("y", axis=1), df["y"])
return model
@step
def evaluate(model, df: pd.DataFrame, threshold: float) -> dict:
acc = model.score(df.drop("y", axis=1), df["y"])
return {"accuracy": acc, "threshold": threshold}
@step
def deploy(model, metrics: dict) -> Endpoint:
if metrics["accuracy"] > metrics["threshold"]:
return model_deployer.deploy(model)
@pipeline
def training_pipeline(threshold: float = 0.9):
df = ingest_data()
model = train(df)
metrics = evaluate(model, df, threshold)
deploy(model, metrics)
# Run 1: default threshold (all steps cache MISS)
training_pipeline(threshold=0.9)
# Run 2: only threshold changed -> ingest/train cache HIT
training_pipeline(threshold=0.95)
$ zenml stack set production # swap infra, zero code change
