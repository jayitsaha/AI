Understanding Artifact Management
▼

What is it? An ML training run produces a chain of "artifacts" — the dataset it read, the code and config it ran, and the model checkpoints it wrote. Artifact management is the discipline (and storage system) that keeps every one of these files immutable, uniquely identified, deduplicated, and linked together so you can always answer "which exact dataset produced this exact model?"

Analogy: Think of Git for files that are gigabytes, not lines of text. Just like Git names every commit by the SHA-1 hash of its content, a content-addressable artifact store names every dataset shard, model weight file, and checkpoint by the cryptographic hash of its bytes. Upload the same file twice — from two different laptops, weeks apart — and the store recognizes it is byte-identical and stores it exactly once, while still letting both uploads point to it.

💡 If you remember one thing

An artifact's identity is its content: \(\text{id} = H(\text{bytes})\). Two artifacts with identical bytes always collapse to the same id, giving you free deduplication, tamper-evidence, and a stable key for building a lineage graph — dataset \(\to\) run \(\to\) model \(\to\) checkpoint.

How It Works Internally
▼

The Problem With Naming Files By Path

Naive pipelines store artifacts under human paths like models/run42/checkpoint_final.pt. That path is mutable — someone can overwrite it — and it says nothing about what's actually inside. Two teams can end up with files at identical paths but different bytes, or identical bytes at different paths wasting storage. Neither failure is detectable from the path alone.

The Content-Addressable Fix

Every time an artifact (dataset shard, model weights, checkpoint) is written, the store hashes its full byte content with a cryptographic digest (SHA-256 in production systems; this demo uses a fast illustrative hash) and uses that digest as the permanent object key: store/objects/<hash>. Metadata (path, run id, timestamp, tags like "best") lives separately and points at the hash — the object itself never changes once written.

Deduplication Is a Side Effect, Not a Feature

Before writing bytes, the store checks: "does an object with this hash already exist?" If yes, it just adds a new reference (pointer) and skips the write entirely. This is why re-uploading an unchanged dataset, or two experiments that happen to converge on the same weights, costs zero extra bytes on disk — the hash check is O(1) via a lookup table, no byte-by-byte diff needed.

Lineage as a DAG

Every run records which input hashes it consumed and which output hashes it produced. Stitching these edges together across many runs yields a directed acyclic graph (DAG): dataset versions feed into training runs, runs emit checkpoints across epochs, and one checkpoint gets promoted to "model". Because nodes are immutable hashes, the DAG never has to worry about a node silently changing under it — reproducibility is structural, not just a policy.

🔑 Key Property

Content-addressing gives referential transparency for data: if you have the hash, you have a cryptographic guarantee of exactly which bytes you'll get — regardless of who wrote them, when, or from where. This is what makes an experiment truly reproducible.

Why It Works — The Math
▼

Collision Probability (Birthday Bound)

For a hash function producing \(b\) bits of output, storing \(n\) distinct artifacts, the probability that two different artifacts accidentally collide to the same hash is approximately:

$$P(\text{collision}) \approx \frac{n^2}{2^{b+1}}$$

With SHA-256 (\(b=256\)) and even \(n = 10^{12}\) artifacts, \(P(\text{collision}) \approx 10^{24}/2^{257} \approx 10^{-53}\) — astronomically smaller than the odds of a cosmic ray flipping a bit in your RAM. This is why content-addressable stores treat "same hash" as "same content" without a byte-level comparison.

Deduplication Ratio

Let \(L\) be the logical size (sum of sizes of every reference, counting duplicates) and \(P\) the physical size (sum of sizes of unique hash objects actually on disk). The storage savings from deduplication is:

$$\text{Dedup ratio} = 1 - \frac{P}{L} \qquad \text{Space amplification} = \frac{L}{P}$$

A repo where every training run re-references the same 250 GB dataset 40 times has \(L = 10\text{TB}\), \(P = 250\text{GB}\) — a 40× space amplification avoided, i.e. a 97.5% dedup ratio.

Garbage Collection Condition

An object with hash \(h\) is safe to reclaim iff it has zero incoming references from any live metadata pointer (tag, run record, or DAG edge):

$$\text{reclaim}(h) \iff \text{refcount}(h) = |\{e \in E : e.\text{target} = h\}| = 0$$
⚠️ Common Pitfall

Hashing must cover full byte content, not just a filename or a quick sample. Tools that hash only file size + mtime ("looks the same") will silently treat a corrupted or re-shuffled dataset as identical to the original — breaking the tamper-evidence guarantee that makes the whole system trustworthy.

Key Takeaways
▼

When to use content-addressable artifact management:

  • You need exact reproducibility — "which data trained this exact model checkpoint?"
  • Storage costs matter and the same large files (datasets, base checkpoints) get reused across many runs
  • You need tamper-evidence / auditability for compliance (e.g. model cards, regulated ML)
  • Multiple teams or pipelines write overlapping data and you want automatic dedup without coordination

When it's overkill:

  • Single-user prototyping with tiny, throwaway artifacts — the hashing overhead isn't worth it
  • Extremely latency-sensitive online feature stores where content rarely repeats (little dedup benefit)
💡 Hierarchy

Path-based storage (mutable, no identity) ⊂ versioned storage (immutable per-path snapshots, e.g. S3 versioning) ⊂ content-addressable storage (immutable, deduplicated, hash-identified — e.g. Git LFS, DVC, LakeFS, MLflow artifact store, Weights & Biases Artifacts). Each layer adds a stronger identity and integrity guarantee.

Code Trace

import hashlib, json, shutil, pathlib
class ContentStore:
def __init__(self, root):
self.objects = pathlib.Path(root) / "objects"
self.refs = {} # hash -> set(referrers)
def put(self, filepath, referrer):
h = hashlib.sha256(open(filepath,"rb").read()).hexdigest()
dest = self.objects / h
if not dest.exists(): # miss: new content
shutil.copy(filepath, dest)
else: # hit: dedup, no write
pass
self.refs.setdefault(h, set()).add(referrer)
return h
def gc(self, live_referrers):
for h, refs in list(self.refs.items()):
if not (refs & live_referrers):
(self.objects / h).unlink() # reclaim
del self.refs[h]
# --- lineage DAG edge on every run ---
store = ContentStore("./artifact_store")
dataset_hash = store.put("images_v1.tar", referrer="dataset:v1")
for epoch, ckpt_path in enumerate(train(dataset_hash)):
ckpt_hash = store.put(ckpt_path, referrer=f"run:A/epoch:{epoch}")
lineage.add_edge(dataset_hash, ckpt_hash, kind="produced_by")
best = min(checkpoints, key=lambda c: c.val_loss)
promote(best.hash, tag="model:v1") # pointer update, zero copy
