Understanding Apache Airflow
▼

What is it? Apache Airflow is an open-source platform to programmatically author, schedule, and monitor workflows. It allows you to define workflows as Directed Acyclic Graphs (DAGs) of tasks in Python code. This "configuration as code" approach makes workflows more maintainable, versionable, testable, and collaborative.

Analogy: Imagine a master conductor orchestrating a complex orchestra. The musical score is the DAG, defining the sequence of pieces and when each instrument (operator) should play. Some musicians (tasks) perform their part directly. Other specialized musicians (sensors) wait for a specific cue from outside the orchestra — perhaps a light signal or a timed event — before they play their part, allowing the rest of the orchestra to continue in parallel. The conductor (scheduler) ensures everyone starts on time and keeps track of who has played and who is waiting.

💡 If you remember one thing

Airflow's power comes from defining complex data pipelines as code (DAGs), enabling robust scheduling, monitoring, and distributed execution. It tells *what* to run, *when* to run it, and *where* to run it, but typically delegates the heavy computational lifting to external systems.

2
How It Works Internally
▼

Core Components

An Airflow deployment typically consists of several components:

  • Scheduler: Monitors all DAGs and tasks, triggers task runs when their dependencies are met, and manages retries. It's the "heart" of Airflow.
  • Webserver: Provides the user interface (UI) to visualize DAGs, monitor their progress, manage connections, and view logs.
  • Worker(s): Executes the actual tasks. These can be local processes, Docker containers, or Kubernetes pods.
  • Database: Stores the state of all tasks, DAGs, connections, variables, and other metadata. This is critical for Airflow's persistence and distributed nature.

DAGs as Code: Operators & Sensors

A DAG (Directed Acyclic Graph) is a collection of tasks with dependencies, defining a workflow. "Directed" means tasks flow in one direction, "Acyclic" means no loops (a task cannot depend on itself or a downstream task). DAGs are defined in Python scripts, allowing for dynamic generation and version control.

  • Operators: These are the atomic units of work in Airflow. Each operator defines a single task. Examples include BashOperator (runs a bash command), PythonOperator (calls a Python function), S3ToRedshiftOperator (moves data from S3 to Redshift).
  • Sensors: A special type of operator that waits for a certain condition to be met. Unlike regular operators that perform an action and then exit, sensors continually poll a condition until it becomes true. Examples: FileSensor (waits for a file to appear), S3KeySensor (waits for a key in S3), SqlSensor (waits for a SQL query to return a specific result). Sensors are crucial for interacting with external systems.

Design Decision: Why not just cron scripts?

While cron can schedule simple scripts, Airflow offers significant advantages for complex data pipelines: built-in dependency management, robust retry mechanisms, backfilling (running past schedules), a rich UI for monitoring, distributed execution, and extensibility. A cron job for a multi-step ETL process would require custom logic for all these features, which Airflow provides out-of-the-box.

🔑 Key Property

Airflow decouples DAG definition (Python code) from task execution logic (operators) and workflow state (database). This separation enables scalability, resilience, and visibility into complex data pipelines.

3
The Scheduling & Execution Model
▼

`schedule_interval` and `execution_date`

DAGs are scheduled using a schedule_interval, which can be a cron expression (e.g., '0 0 * * *' for daily at midnight) or a timedelta (e.g., timedelta(days=1)). A crucial concept is the execution_date (now called logical_date in Airflow 2.2+). This date represents the *start* of the data interval that the DAG run is processing. A DAG configured to run daily at midnight will trigger *after* midnight, with an execution_date of the previous day's midnight. This ensures that all data for the interval is available before processing begins.

$$\text{DAG Run Start Time} = \text{execution\_date} + \text{schedule\_interval}$$ $$\text{Data Interval} = [\text{execution\_date}, \text{execution\_date} + \text{schedule\_interval})$$

For example, a daily DAG scheduled at midnight (0 0 * * *) will have its first run triggered at 2023-01-02 00:00:00 with an execution_date of 2023-01-01 00:00:00. This run processes data from Jan 1st.

Task Instances and Dependencies

Each time a DAG runs, it creates a DAG Run. Within a DAG Run, each task defined in the DAG becomes a Task Instance. The scheduler continuously evaluates the state of these task instances. A task instance will only be marked as "ready to run" if all its upstream dependencies are met (e.g., they have succeeded).

$$\text{Task } T_B \text{ is ready if } \forall T_A \in \text{Upstream}(T_B): \text{State}(T_A) = \text{Success}$$

Dependencies are defined using bitshift operators in Python: task_a >> task_b means task_b depends on task_a. This creates a directed edge in the DAG.

Idempotency and Retries

A key principle in robust data pipelines is idempotency: a task should produce the same result if run multiple times with the same inputs. This is vital for Airflow's retries mechanism, where tasks can be automatically re-attempted if they fail. The retry_delay parameter specifies the wait time between retries.

$$\text{Task}(Input) = \text{Output} \quad \forall \text{runs}$$

Airflow also supports backfilling (running a DAG for past execution_dates) and catching up (running missed schedules). These features are only safe if tasks are idempotent.

⚠️ Common Pitfall

Misunderstanding execution_date (logical_date) is a frequent source of errors. Always remember it refers to the start of the data interval, not the time the DAG actually triggers. Also, be wary of mutable default arguments in Python functions used by PythonOperator, as they can lead to unexpected behavior across task runs.

Key Takeaways
▼

When to use Airflow:

  • Complex ETL/ELT pipelines: Orchestrating data ingestion, transformation, and loading across various systems.
  • Long-running batch jobs: Automating daily, weekly, or monthly data processing tasks.
  • Data quality checks: Running validation tasks as part of a pipeline.
  • Machine Learning pipelines: Orchestrating data preparation, model training, evaluation, and deployment steps.
  • When you need robust monitoring & alerting: Airflow's UI and extensibility provide excellent visibility into workflow health.

When NOT to use:

  • Real-time / low-latency processing: Airflow is batch-oriented; its scheduling overhead makes it unsuitable for immediate responses.
  • Stream processing: Tools like Apache Flink or Spark Streaming are designed for continuous data streams.
  • Very short-lived tasks: The overhead of Airflow's scheduler and worker setup can outweigh the task execution time for tasks that run in milliseconds.
  • Simple cron-like scripts: For trivial, single-step tasks without complex dependencies, cron or simple systemd timers might be sufficient.
💡 Airflow's Role

Airflow is an orchestrator, not a compute engine. It excels at coordinating tasks across diverse systems (databases, cloud services, custom scripts) by telling them *when* to execute. It doesn't perform the actual data manipulation or heavy computation itself, but rather triggers other tools to do so.

Code Trace (Simple ETL DAG)
▼
from __future__ import annotations
import pendulum
from airflow.models.dag import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.python import PythonOperator
from airflow.sensors.filesystem import FileSensor
def _process_data_func():
print("Processing raw data...")
def _transform_data_func():
print("Transforming processed data...")
def _load_to_db_func():
print("Loading data to database...")
def _notify_success_func():
print("Workflow completed successfully!")
with DAG(
dag_id="etl_pipeline_example",
start_date=pendulum.datetime(2023, 1, 1, tz="UTC"),
schedule=None, # Manual trigger for simplicity
catchup=False,
tags=["etl", "sensor"],
) as dag:
start_task = PythonOperator(
task_id="start_workflow",
python_callable=lambda: print("Starting ETL workflow...")
)
download_data = BashOperator(
task_id="download_raw_data",
bash_command="echo 'Downloading data...'"
)
process_data = PythonOperator(
task_id="process_downloaded_data",
python_callable=_process_data_func
)
check_file_sensor = FileSensor(
task_id="wait_for_external_file",
filepath="/tmp/external_trigger.txt",
poke_interval=5, # Check every 5 seconds
timeout=600 # Fail after 10 minutes
)
transform_data = PythonOperator(
task_id="transform_processed_data",
python_callable=_transform_data_func
)
load_to_db = PythonOperator(
task_id="load_to_database",
python_callable=_load_to_db_func
)
notify_success = PythonOperator(
task_id="notify_workflow_completion",
python_callable=_notify_success_func
)
# Define dependencies
start_task >> [download_data, check_file_sensor]
download_data >> process_data
check_file_sensor >> transform_data
[process_data, transform_data] >> load_to_db
load_to_db >> notify_success
