Understanding Python Concurrency
▼

What is this? Python gives you three ways to do multiple things "at once": threading (OS-level threads sharing memory), multiprocessing (OS-level processes, each with its own memory), and asyncio (cooperative coroutines on a single OS thread). They are NOT interchangeable — they excel at different problems.

The killer constraint: CPython (the standard Python interpreter) has a Global Interpreter Lock (GIL) — a mutex that allows only ONE thread to execute Python bytecode at a time. This makes threading safe for object access but prevents true CPU parallelism in Python threads.

Analogy: Imagine a busy kitchen. threading = multiple cooks (OS threads) sharing the same kitchen — one cook can prep while another waits for the oven, but only one can use the stove (GIL) at a time. multiprocessing = multiple separate kitchens — no sharing, no lock, true parallelism, but setup (spawn) costs more. asyncio = one cook who is very efficient — while bread is rising (I/O wait), they peel vegetables; but they can only physically do one thing at a time.

If you remember one thing

I/O-bound work: threading and asyncio both work well (the GIL is released during I/O system calls). CPU-bound work: only multiprocessing achieves true parallelism in Python — the GIL prevents threading from helping.

threading

OS threads, shared memory, GIL-limited. Best: I/O-bound tasks, GUI responsiveness.

multiprocessing

OS processes, separate memory, no GIL. Best: CPU-bound parallelism, data isolation.

asyncio

Single thread, event loop, cooperative. Best: high-concurrency I/O (servers, web clients).

2
How Each Model Works Internally
▼

threading — OS Threads + GIL

When you call threading.Thread(target=fn).start(), the OS creates a real kernel-level thread. Each thread has its own call stack and registers but shares the process's heap (including all Python objects). The GIL is a C-level mutex (_PyRuntimeState.ceval.gil) in CPython. The key rules:

  • GIL is released on I/O system calls — when a thread calls read(), recv(), sleep(), etc., it drops the GIL before entering the kernel and re-acquires it on return. While sleeping, other threads can run.
  • GIL is released every N opcodes — CPython 3.2+ uses a timeout mechanism: after ~5ms of holding the GIL, the thread signals a switch request. The OS scheduler picks another thread.
  • CPU-bound threads fight for the GIL — they never voluntarily release it (no I/O), so the OS must preempt them via signal. This causes "GIL thrashing": constant lock/unlock with no real speedup, sometimes slower than sequential due to overhead.
GIL Acquisition Protocol

When Thread-A holds the GIL and Thread-B wants it: (1) Thread-B sets a flag gil_drop_request = 1. (2) Thread-A detects this at the next eval breaker check (every opcode in CPython 3.12+). (3) Thread-A drops the GIL and signals Thread-B. (4) Thread-B races to acquire — if another thread wins, Thread-B sleeps on a condition variable. This protocol adds ~microsecond overhead per switch.

multiprocessing — Fork/Spawn, Separate Interpreters

Each multiprocessing.Process is a full OS process with its own Python interpreter, its own GIL, its own heap. On Unix: fork copies the parent's memory (copy-on-write); on Windows and macOS 3.8+ default: spawn starts a fresh interpreter. Communication via Queues (built on OS pipes + pickle serialization) or shared memory (multiprocessing.shared_memory). No shared mutable state by default — this is a feature, not a bug.

asyncio — Event Loop + Coroutines

asyncio is a cooperative multitasking scheduler. One OS thread runs the event loop. Coroutines (async def functions) are Python generator-based objects. await expr suspends the current coroutine and returns control to the event loop. The loop checks: (1) are any I/O file descriptors ready? (via select/epoll/kqueue); (2) have any scheduled callbacks' timers fired? The first ready item runs. There is no preemption — a coroutine runs until it explicitly yields via await.

Common Pitfall

Calling a blocking function (e.g., time.sleep(), requests.get(), heavy computation) inside an async def without await blocks the entire event loop — all other coroutines freeze until it returns. Always use await asyncio.sleep(), aiohttp, and loop.run_in_executor() for CPU/blocking work.

3
Performance Models & The GIL
▼

Amdahl's Law for Python Concurrency

Let \(f\) be the fraction of work that is parallelizable and \(n\) be the number of parallel workers (processes). The theoretical speedup is bounded by Amdahl's Law:

$$S(n) = \frac{1}{(1-f) + \frac{f}{n}}$$

For threading on CPU-bound work, the GIL enforces \(f \approx 0\) at the Python level (even if \(n > 1\)), so \(S(n) \approx 1\) — no speedup. For multiprocessing on CPU-bound work, \(f\) can approach 1 (ignoring IPC), giving \(S(n) \approx n\) with enough cores.

asyncio I/O Concurrency Model

asyncio achieves I/O concurrency on a single thread via event demultiplexing. For \(k\) concurrent I/O tasks each with wait time \(T_{io}\), the wall time is:

$$T_{\text{wall}} = T_{io} + k \cdot T_{\text{switch}}$$

where \(T_{\text{switch}}\) is the coroutine switch overhead (typically \(\sim 1\)\(\mu\)s). For I/O waits of 100–1000ms, this is negligible, giving near-linear concurrency gain. Compare with \(k\) sequential requests: \(T_{\text{wall,seq}} = k \cdot T_{io}\).

GIL Check Interval (CPython implementation detail)

In CPython \(\geq\) 3.2, the GIL switch uses a 5ms timeout. Thread-A holds GIL, Thread-B waits. After 5ms, Thread-B sends a signal (SIGINT-like wakeup). Thread-A checks the eval breaker flag on the next bytecode instruction boundary and drops the GIL. This gives roughly:

$$T_{\text{GIL\_switch}} \approx 5\text{ms} + T_{\text{OS\_sched}}$$

For CPU-bound threads, each switch costs ~5–15ms of serialization latency with no computation benefit. With 2 CPU threads, you get the same CPU throughput as 1 thread but with added context-switch overhead — sometimes making it slower.

Memory Model

threading: shared heap — \(O(1)\) data sharing, but requires locks for mutation. multiprocessing: separate heaps — \(O(k \cdot S)\) memory for \(k\) workers with state size \(S\); data sharing via pickle serialization costs \(O(S)\) per transfer. asyncio: single heap — no locking needed (single-threaded), \(O(1)\) sharing.

Speedup Summary Table

Model I/O-bound speedup CPU-bound speedup Overhead
threading \(\approx k\times\) (GIL released) \(\approx 1\times\) (GIL blocks) ~1ms thread spawn, low memory
multiprocessing \(\approx k\times\) \(\approx k\times\) (true parallel) 50–200ms spawn, \(k\times\) memory

When to Use Which — Decision Guide
▼

Use threading when:

  • Work is I/O-bound: network requests, file reads, database queries, sleep
  • You need shared state (e.g., a shared cache) — multiprocessing would require costly IPC
  • Spawning processes is too expensive (startup time, memory)
  • Integrating with C extensions that release the GIL (NumPy, Pillow, some CFFI code)

Use multiprocessing when:

  • Work is CPU-bound: number crunching, image processing, ML training on CPU
  • You want true parallelism regardless of GIL
  • Data isolation is desirable (no accidental shared-state bugs)
  • Use ProcessPoolExecutor for simplicity; Pool.map() for data-parallel batch jobs

Use asyncio when:

  • High-concurrency I/O: web servers (FastAPI, aiohttp), async database clients, WebSocket handlers
  • You control the full call stack (can use async/await throughout)
  • Thousands of concurrent connections with minimal overhead (no thread-per-connection)
  • Structured concurrency: asyncio.gather(), asyncio.TaskGroup (3.11+)
Decision Rule

CPU-bound → multiprocessing (or C extension releasing GIL)
I/O-bound, high concurrency, async-native codebase → asyncio
I/O-bound, legacy sync code, need shared memory → threading
Mixed: asyncio + run_in_executor hands CPU work to a thread/process pool

Python 3.13+ Free-Threaded Mode

CPython 3.13 introduced an experimental free-threaded build (compile with --disable-gil) where the GIL is optional. This changes threading from I/O-only to potentially CPU-parallel. As of 2025, this is marked experimental; most C extensions still assume the GIL exists. Check sys.flags.nogil at runtime.

Code Comparison
▼
import time, threading, multiprocessing, asyncio
# ── I/O-bound task (releases GIL via time.sleep) ──
def io_task(name):
time.sleep(0.2) # GIL released here → other threads run
return f"{name} done"
# ── CPU-bound task (holds GIL for duration) ──
def cpu_task(name):
total = sum(i*i for i in range(1_000_000)) # holds GIL
return f"{name} = {total}"
# ── threading: good for I/O ──
from concurrent.futures import ThreadPoolExecutor
with ThreadPoolExecutor(max_workers=4) as ex:
futs = [ex.submit(io_task, f"T{i}") for i in range(4)]
results = [f.result() for f in futs] # wall ≈ 200ms
# ── multiprocessing: good for CPU ──
from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor(max_workers=4) as ex:
futs = [ex.submit(cpu_task, f"P{i}") for i in range(4)]
results = [f.result() for f in futs] # wall ≈ 250ms (true parallel)
# ── asyncio: good for high-concurrency I/O ──
async def async_io(name):
await asyncio.sleep(0.2) # cooperative yield — event loop runs others
return f"{name} done"
async def main():
tasks = [async_io(f"C{i}") for i in range(4)]
results = await asyncio.gather(*tasks) # wall ≈ 200ms
return results
asyncio.run(main())
# ── asyncio + CPU offload to process pool ──
async def mixed_main():
loop = asyncio.get_running_loop()
with ProcessPoolExecutor() as pool:
# CPU work in subprocess, doesn't block event loop
cpu_future = loop.run_in_executor(pool, cpu_task, "P0")
io_result = await async_io("C0") # runs concurrently
cpu_result = await cpu_future
return io_result, cpu_result
