Understanding Tokenization
▼

What is it? Neural networks only understand numbers, not letters. Tokenization is the step that chops raw text into discrete pieces — tokens — and maps each one to an integer ID from a fixed vocabulary. Everything downstream (embeddings, attention, the softmax over the vocabulary) is built on top of these IDs.

Analogy: Think of a fixed catalog of LEGO bricks. Whole-word tokenization gives you one giant brick per word — great when the word is in the catalog, but if it isn't, you're stuck with a generic "unknown" brick and the model loses all information about that word. Character-level tokenization gives you only 1×1 studs — you can always build anything, but a sentence takes hundreds of tiny bricks. Subword tokenization (like Byte-Pair Encoding) is the practical middle ground: common words stay as single big bricks, rare or unfamiliar words get broken into a handful of meaningful smaller pieces you already own.

One-sentence summary: Tokenization trades off vocabulary size, sequence length, and out-of-vocabulary (OOV) risk to turn arbitrary text into a bounded set of integer IDs a model can embed and predict over.

💡 If you remember one thing

Subword tokenization exists because word-level vocabularies can never cover every word (infinite OOV risk) and character-level vocabularies make sequences painfully long. Byte-Pair Encoding merges frequent character pairs bottom-up so common words stay whole while rare words gracefully fall back to smaller, still-meaningful pieces — with zero true OOV tokens.

How It Works Internally
▼

Word-level

Split text on whitespace/punctuation with a regex, then look each word up in a vocabulary dictionary built once from a training corpus (typically the top 20k–100k most frequent words). Anything not seen during training — misspellings, new slang, morphological variants like "jumped" when only "jump" was seen — maps to a single <UNK> id, permanently destroying information about that word.

Character-level

Split into individual Unicode characters (or raw bytes). The vocabulary is tiny — often under 300 symbols — so OOV is essentially impossible. The cost: sequence length explodes (a 6-letter word becomes 6 tokens instead of 1), the model must learn spelling and word structure from scratch, and self-attention's \(O(n^2)\) cost grows quickly with sequence length.

Subword — Byte-Pair Encoding (BPE)

BPE starts every word as a sequence of characters and repeats a simple loop: count every adjacent symbol pair across the training corpus, merge the single most frequent pair into a new symbol, and record that merge as a rule. After a fixed number of merges (e.g. 30k for GPT-2), the ordered list of merge rules is the tokenizer. At inference, the same merges are re-applied greedily to new text — so frequent whole words end up as one token (because every pair inside them got merged early), while rare words stop partway through and are represented as 2–4 meaningful pieces instead of one <UNK>.

🔑 Design Decision: Why Frequency-Ranked Merges?

Merging by frequency (not fixed-length chunks) means the vocabulary is corpus-driven: extremely common substrings ("the", "ing", "tion") get merged first and become atomic tokens, while rare or novel strings simply merge less and fall back toward raw characters/bytes. Because merges are ordered and deterministic, the exact same rule set works identically on text the tokenizer has never seen — that's what gives BPE (and its cousins WordPiece and Unigram LM) an OOV rate of effectively zero.

3
Why It Works — The Math
▼

Why Word-Level OOV Never Goes Away

Word frequencies roughly follow Zipf's law: the word of rank \(r\) has probability \(p(r) \propto 1/r\). For a corpus with \(N\) distinct words, the fraction of probability mass covered by a vocabulary of the top \(V\) words is:

$$\text{coverage}(V) = \frac{\sum_{r=1}^{V} 1/r}{\sum_{r=1}^{N} 1/r} = \frac{H_V}{H_N}$$

where \(H_k\) is the \(k\)-th harmonic number, which grows only as \(\ln k\). Because \(H_V\) grows logarithmically, doubling the vocabulary size \(V\) yields ever-smaller gains in coverage — you need exponentially larger vocabularies to keep chasing down the OOV rate. Word-level tokenizers can shrink OOV, but never eliminate it.

Compute/Memory Cost of Vocabulary Size

The embedding table and output (softmax) projection both scale as \(O(V \cdot d)\) parameters, where \(d\) is the model's hidden dimension. Meanwhile average sequence length scales roughly as \(O(1/\bar{t})\), where \(\bar{t}\) is the mean tokens-per-word for a given vocabulary — bigger vocabularies encode text in fewer tokens. This is the central tension every tokenizer designer balances:

$$\underbrace{O(V\cdot d)}_{\text{embedding + softmax cost}} \quad\text{vs.}\quad \underbrace{O(n^2)}_{\text{attention cost, } n \propto 1/\bar t}$$

Why BPE's OOV Rate Is Exactly Zero

BPE's base vocabulary is the full alphabet of atomic symbols (bytes or characters) actually observed during training, and merges only ever combine symbols that are themselves already in the vocabulary. By induction, every string decomposable into those atomic symbols — which, for byte-level BPE, is every possible string — has a valid tokenization: worst case, it falls all the way back to single bytes. No <UNK> token is structurally required.

⚠️ Common Misconception

"A bigger subword vocabulary is always better." Not for free: a larger \(V\) inflates the embedding/softmax matrices by \(O(V\cdot d)\) and can make short, frequent strings (especially digits: "2024" vs "20"+"24" vs "2"+"0"+"2"+"4") fragment inconsistently across contexts, which is a well-known source of arithmetic errors in LLMs.

When to use which:

  • Subword (BPE / WordPiece / Unigram) is the default for essentially every modern LLM — best balance of vocab size, sequence length, and zero OOV.
  • Character/byte-level shines for noisy text, code, or multilingual settings with many scripts where a shared subword vocabulary struggles.
  • Pure word-level is mostly legacy — still useful for quick prototyping or when the vocabulary is genuinely closed (e.g. a fixed set of product SKUs).
💡 Hierarchy

Character-level (max robustness, max length) ↔ Subword (the tunable middle, controlled by merge count) ↔ Word-level (max compression, max OOV risk). Subword tokenization is literally a dial between the other two extremes.

Code Trace — BPE From Scratch
▼
from collections import Counter
# 1. Represent every word as a list of characters + end marker
def get_vocab(corpus_words):
vocab = Counter()
for w, freq in corpus_words.items():
symbols = tuple(w) + ("</w>",)
vocab[symbols] += freq
return vocab
# 2. Count all adjacent symbol pairs, weighted by word frequency
def get_pair_counts(vocab):
pairs = Counter()
for symbols, freq in vocab.items():
for a, b in zip(symbols, symbols[1:]):
pairs[(a, b)] += freq
return pairs
# 3. Merge the single most frequent pair everywhere it appears
def merge_pair(pair, vocab):
a, b = pair
new_vocab = {}
for symbols, freq in vocab.items():
merged, i = [], 0
while i < len(symbols):
if i < len(symbols)-1 and symbols[i:i+2] == pair:
merged.append(a + b); i += 2
else:
merged.append(symbols[i]); i += 1
new_vocab[tuple(merged)] = freq
return new_vocab
# 4. Train: repeat for num_merges iterations, recording each rule
def train_bpe(corpus_words, num_merges):
vocab = get_vocab(corpus_words)
merges = []
for _ in range(num_merges):
pairs = get_pair_counts(vocab)
if not pairs: break
best = max(pairs, key=pairs.get) # most frequent pair
vocab = merge_pair(best, vocab)
merges.append(best) # order matters at inference!
return merges
# 5. Encode new text by re-applying merges in the learned order
def bpe_encode(word, merges):
symbols = list(word) + ["</w>"]
for a, b in merges:
symbols = merge_pair((a, b), {tuple(symbols): 1})
symbols = list(next(iter(symbols)))
return symbols # -> e.g. ["fox", "es</w>"]
