NCCL vs GLOO: GPU & CPU Communication Backends

How distributed training moves gradients — topology-aware GPU collectives vs portable CPU collectives

1
Understanding NCCL & GLOO
▼

What are they? When you train a model across many GPUs (or machines), every worker computes a partial gradient, and all workers must combine those gradients into one agreed-upon value before the next step — an operation called AllReduce. A "communication backend" is the library that actually moves the bytes between workers to make that happen. NCCL (NVIDIA Collective Communications Library) is a GPU-native backend that talks directly over NVLink, PCIe and InfiniBand. GLOO is a CPU-oriented backend (from Meta) that works over ordinary TCP/Ethernet and runs anywhere — including machines with no GPUs at all.

Analogy: Imagine a group project where teammates sit in the same room (fast, direct hand-offs — NVLink), teammates in different rooms of the same building (a shared hallway — PCIe/InfiniBand), and remote teammates who only have email (slow, universal — TCP/Ethernet). NCCL is optimized to exploit every "same room" and "same building" shortcut it can detect. GLOO only assumes "email" is available, so it works everywhere but never uses the fast hallway.

💡 If you remember one thing

NCCL is topology-aware: it inspects the physical GPU interconnect graph (NVLink / NVSwitch / PCIe / InfiniBand) and builds a ring or tree that hugs the fastest links. GLOO makes no such assumption — it moves data through host memory over standard sockets, trading peak bandwidth for universal portability.

2
How They Work Internally
▼

The Ring AllReduce (the default building block)

Both backends can express AllReduce as a ring: arrange the \(N\) workers in a logical circle. In the reduce-scatter phase, each worker sends a \(1/N\) chunk of its buffer to its neighbor while receiving and accumulating a chunk from the other side — after \(N-1\) steps every worker holds one fully-reduced chunk. The all-gather phase then circulates those finished chunks around the ring so everyone ends up with the complete result. Total data moved per worker is \(2\frac{N-1}{N}S\) for a buffer of size \(S\) — independent of \(N\) for large \(N\), which is why ring AllReduce is bandwidth-optimal.

NCCL: Topology Detection + Rings/Trees over Real Hardware

NCCL builds a graph of the actual hardware at init time: NVLink/NVSwitch edges within a node (hundreds of GB/s), PCIe edges from GPU to host, and InfiniBand/RoCE edges between nodes (using GPUDirect RDMA to skip the CPU entirely when possible). It then constructs one or more rings — or, for large clusters, a double binary tree — that route traffic preferentially over the fastest edges, and pipelines multiple rings in parallel to saturate NVSwitch bandwidth. The tree algorithm trades a constant bandwidth term for \(O(\log N)\) latency instead of the ring's \(O(N)\), which matters once you scale to hundreds of GPUs.

GLOO: Host-Staged Rings over Sockets

GLOO has no concept of NVLink or RDMA by default. Tensors are first copied GPU→host over PCIe, the CPU processes run a ring (or tree) AllReduce over plain TCP sockets, and results are copied host→GPU again. This makes GLOO slower for GPU-to-GPU traffic but gives it two big advantages: it works identically on CPU-only clusters, and it works on hardware NCCL doesn't support (non-NVIDIA GPUs, Windows, single-machine CPU debugging).

🔑 Key Property

Both implement the same collective-communication algorithms (ring, tree, all-gather, broadcast). The difference is entirely about which transport carries the bytes — GPUDirect/NVLink/RDMA for NCCL vs host-memory/TCP for GLOO — which is why swapping backend="nccl" for backend="gloo" in torch.distributed.init_process_group changes performance drastically but not correctness.

3
Why It Works — The Cost Model
▼

The classic latency-bandwidth (\(\alpha\)-\(\beta\)) model predicts collective runtime from three numbers: per-message latency \(\alpha\), inverse bandwidth \(\beta = 1/B\), and the number of hops the algorithm requires.

$$T_{ring}(N,S) = \underbrace{2(N-1)\,\alpha}_{\text{latency term}} \;+\; \underbrace{2\frac{N-1}{N}\cdot\frac{S}{B}}_{\text{bandwidth term}}$$
$$T_{tree}(N,S) = \underbrace{2\log_2 N\,\alpha}_{\text{latency term}} \;+\; \underbrace{2\cdot\frac{S}{B}}_{\text{bandwidth term (const.)}}$$

The effective (algorithmic) bandwidth actually delivered is simply \(BW_{eff} = S / T\). Notice the ring's latency term grows linearly in \(N\) while its bandwidth term is nearly flat — so ring is bandwidth-optimal but latency-hungry at scale. The tree flips this trade: constant bandwidth term, logarithmic latency — better for many small messages across many nodes. This is precisely why NCCL switches algorithms automatically based on message size and cluster size, and why GLOO (with its much larger \(\alpha\) from kernel-level TCP overhead, ~10-20 µs per hop vs ~1-2 µs for NVLink/RDMA) is dominated by the latency term far more severely.

⚠️ Common Pitfall

People assume "GLOO is just slower NCCL." It is actually slower for a specific, structural reason: GPUDirect RDMA lets NCCL move bytes GPU-to-GPU/NIC without ever touching host memory or the kernel's network stack, eliminating both a copy and a context switch. GLOO's socket path pays for both on every hop — that overhead, not raw wire bandwidth, is usually the dominant cost at typical gradient-tensor sizes.

5
Key Takeaways
▼

Use NCCL when:

  • Training on NVIDIA GPUs, single-node or multi-node
  • NVLink/NVSwitch and/or InfiniBand (with GPUDirect RDMA) are present
  • You need maximum AllReduce throughput for large gradient tensors

Use GLOO when:

  • CPU-only training or inference (no GPUs, or GPUs without NCCL support)
  • Local debugging of distributed code on a laptop / single machine
  • Windows, or clusters without RDMA-capable networking
  • Point-to-point CPU tensor exchange (e.g., parameter-server style code, RPC)
💡 Practical Rule

In PyTorch, mixed setups are common: backend="nccl" for GPU collectives and a second GLOO process group for any CPU-tensor communication in the same job. Never mix message tensors of the wrong device type into a backend that can't natively move them — NCCL collectives require CUDA tensors; GLOO handles both CPU and (more slowly) CUDA tensors.

Code Trace
▼
import torch, torch.distributed as dist
# Pick the backend based on hardware / OS
backend = "nccl" if torch.cuda.is_available() else "gloo"
dist.init_process_group(backend=backend, init_method="env://")
rank, world_size = dist.get_rank(), dist.get_world_size()
torch.cuda.set_device(rank % torch.cuda.device_count())
# A gradient tensor produced by local backward()
grad = torch.randn(64_000_000 // 4, device="cuda") # ~64MB fp32
# NCCL: stays on GPU, uses NVLink/IB rings under the hood
dist.all_reduce(grad, op=dist.ReduceOp.SUM) # in-place
grad /= world_size
# Separate GLOO group for CPU-side metadata exchange
gloo_group = dist.new_group(backend="gloo")
meta = torch.tensor([rank], dtype=torch.int64) # CPU tensor
dist.all_gather(meta_list, meta, group=gloo_group)
