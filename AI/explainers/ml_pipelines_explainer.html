1
Understanding ML Pipelines
▼

What is it? An ML pipeline is a directed acyclic graph (DAG) of steps — ingest data, validate it, preprocess, train a model, evaluate it, register it, and deploy it — where each step depends on artifacts produced by earlier steps. A scheduler/orchestrator decides which steps are runnable right now, dispatches them to workers, retries failures, and reuses (caches) results when nothing upstream has changed.

Analogy: Think of a factory assembly line with quality-control gates. A part can't reach "paint" until it passes "weld inspection." If a station jams, the line supervisor retries that station a few times before escalating. If yesterday's batch used identical raw material and settings, the supervisor skips re-running an already-passed inspection and reuses its stamp — that's caching. Three well-known "supervisors" exist: Airflow (a general-purpose task scheduler that happens to run ML jobs), Kubeflow Pipelines (a Kubernetes-native supervisor purpose-built for containerized ML components with artifact lineage), and MLflow Pipelines (renamed MLflow Recipes — an opinionated, fixed template for the classic train/evaluate/register recipe).

💡 If you remember one thing

All three tools solve the same core problem — run a DAG of steps, respecting dependencies, with retries and caching — but they differ in what a step is (arbitrary Python function vs. a container vs. a fixed recipe stage) and where it runs (any executor vs. a Kubernetes pod vs. a local/Spark process).

2
How the Scheduler Works Internally
▼

The DAG and Readiness

Every pipeline is a graph \(G = (V, E)\) where \(V\) is the set of steps and \(E\) the dependency edges. A step \(v\) becomes ready the instant every parent has finished successfully — the scheduler continuously recomputes the ready set and dispatches new work as soon as it appears, which is exactly what lets independent branches (like a fast baseline model and a slow deep model both waiting on "preprocess") run in parallel instead of one after another.

Fan-out and Fan-in

When two or more steps share the same parent, the scheduler fans out — dispatching both concurrently to separate workers/pods. When a step has two or more parents, it fans in: it only becomes ready once the last of its parents finishes, so the effective wait is the maximum, not the sum, of the parent runtimes.

Retries, Backoff, and Failure

Real steps fail transiently — a flaky network call, a schema hiccup, an out-of-memory container. Orchestrators wrap each step with a retry policy: on failure, wait \(\text{wait}_k\), then re-attempt, up to \(k_{max}\) tries, before marking the step (and everything downstream) as failed.

Caching

If a step's declared inputs (code + data + parameters, usually content-hashed) are unchanged since the last successful run, the scheduler can skip execution entirely and reuse the cached output artifact — turning a full re-run into a fast incremental one.

🔑 Key Property

The scheduler's job is purely graph-theoretic — topological ordering, readiness, retries, caching — and is identical in spirit across Airflow, Kubeflow, and MLflow Pipelines. What differs is the execution substrate each one dispatches work to.

3
Formalizing the Scheduler
▼

Readiness Function

At any time \(t\), a task \(v\) is dispatchable when all of its predecessors are done:

$$\text{ready}(v) = \mathbb{1}\left[\forall\, u : (u \to v) \in E,\ \ \text{status}(u) = \texttt{done}\right]$$

Critical Path (Makespan)

With unlimited parallel workers, total pipeline latency is not the sum of every step's duration — it's the longest path through the DAG, computed by dynamic programming over finish times:

$$\text{finish}(v) = \text{duration}(v) + \max_{u \to v \in E} \text{finish}(u), \qquad \text{makespan} = \max_{v \in V} \text{finish}(v)$$

This is exactly what the interactive walkthrough below computes live — parallel branches (fan-out) overlap in time, so the true end-to-end runtime is shorter than the naive sequential sum.

Retry Backoff

$$\text{wait}_k = \min\!\left(\text{base} \cdot 2^{k}, \ \text{cap}\right)$$

Exponential backoff with a cap prevents a flaky dependency from being hammered with retries while still recovering quickly from one-off blips.

Cache Hit Ratio

$$\text{hit\_ratio} = \frac{|\{v \in V : \text{cached}(v)\}|}{|V|}$$
⚠️ Common Pitfall

Caching is only correct if the cache key captures everything that affects the output — code hash, data hash, and parameters. Miss one (e.g. an untracked environment variable or a mutable "latest" data pointer) and you silently serve a stale artifact — a classic source of "it worked in the notebook" bugs.

5
Key Takeaways
▼

When to reach for each tool:

  • Airflow — you need a general-purpose, battle-tested scheduler for heterogeneous jobs (ETL, ML, reporting, alerting) and are fine writing your own operators/containers for ML-specific concerns like artifact lineage.
  • Kubeflow Pipelines — your org is Kubernetes-native, steps are naturally containerized, and you want first-class artifact/metadata lineage, GPU scheduling, and a UI built for ML experiments (built on Argo Workflows under the hood).
  • MLflow Pipelines (Recipes) — you want the classic ingest/split/transform/train/evaluate/register recipe with minimal boilerplate, tight integration with MLflow Tracking and the Model Registry, and don't need arbitrary DAG topology.

💡 Hierarchy of specialization

Airflow (general DAG scheduler) ⊃ Kubeflow (DAG scheduler specialized for containerized, K8s-native ML) ⊃ MLflow Pipelines (a single, opinionated DAG template specialized for the train→evaluate→register recipe). Generality trades off against batteries-included ML ergonomics.

# Airflow — general task orchestration, explicit retries
with DAG("ml_pipeline", schedule="@daily") as dag:
ingest = PythonOperator(task_id="ingest", python_callable=run_ingest,
retries=3, retry_delay=timedelta(minutes=2))
validate = PythonOperator(task_id="validate", python_callable=run_validate, retries=3)
preprocess = PythonOperator(task_id="preprocess", python_callable=run_preprocess)
baseline = PythonOperator(task_id="baseline", python_callable=run_baseline)
train = PythonOperator(task_id="train", python_callable=run_train)
evaluate = PythonOperator(task_id="evaluate", python_callable=run_evaluate)
register = PythonOperator(task_id="register", python_callable=run_register)
deploy = KubernetesPodOperator(task_id="deploy", image="serving:latest")

# Kubeflow Pipelines — containerized components + K8s-native artifacts
@dsl.pipeline(name="ml-pipeline")
def ml_pipeline():
ingest_op = ingest_component()
validate_op = validate_component(data=ingest_op.outputs["dataset"])
prep_op = preprocess_component(data=validate_op.outputs["clean"])
base_op = baseline_component(data=validate_op.outputs["clean"])
train_op = train_component(data=prep_op.outputs["features"]).set_gpu_limit(1)
eval_op = evaluate_component(model=train_op.outputs["model"],
baseline=base_op.outputs["model"])
with dsl.If(eval_op.outputs["passed"] == True):
register_component(model=train_op.outputs["model"])
