Understanding PyMC
▼

What is it? PyMC (formerly PyMC3) is a Python probabilistic programming language: you declare a generative model — priors, deterministic relationships, and a likelihood tying parameters to observed data — and PyMC handles the hard part: drawing samples from the posterior distribution of the unknowns given the data. You never derive gradients or write a sampler by hand; PyMC builds a computational graph (via PyTensor) with automatic differentiation and hands it to a sampler, almost always the No-U-Turn Sampler (NUTS), a self-tuning variant of Hamiltonian Monte Carlo (HMC).

Analogy: Writing a PyMC model is like filling out a Mad Libs template for how your data was generated: "a coin has some unknown bias \(p\), drawn from a mild prior belief; each flip is a Binomial draw from that \(p\); here are the flips we actually observed." PyMC reads that story backwards — using Bayes' rule — to tell you what values of \(p\) are consistent with what you saw, and how confident you should be.

💡 If you remember one thing

PyMC turns Bayes' rule into executable code: $$p(\theta \mid D) \;\propto\; p(D \mid \theta)\, p(\theta)$$ You write p(\theta) (the prior) and p(D\mid\theta) (the likelihood) as a few lines of declarative code; pm.sample() returns Monte Carlo draws from the posterior \(p(\theta\mid D)\) on the right, computed via gradient-guided Hamiltonian dynamics — no closed form required.

How PyMC Works Internally
▼

The Model as a Computational Graph

Inside a with pm.Model() as model: block, every pm.Beta(...), pm.Normal(...), or pm.Binomial(..., observed=...) call registers a random variable (RV) node in a PyTensor graph. Free RVs (priors) contribute logp(value) to a running total; observed RVs contribute logp(observed_data) evaluated at fixed data. Summing every node's log-probability gives the model's total unnormalized log-posterior, model.logp() — a single scalar function of all the free parameters, differentiable end-to-end.

Inference: pm.sample() and NUTS

Calling pm.sample() triggers a two-phase process. In the tuning phase (default 1000 draws, discarded), NUTS adapts its step size \(\epsilon\) to hit a target acceptance rate (default 0.8) and estimates a mass matrix from the emerging posterior geometry. In the sampling phase, each draw runs a Hamiltonian trajectory: sample a random momentum, integrate the parameter + momentum system with the leapfrog method, and accept/reject via a Metropolis correction that makes the whole procedure exact. NUTS automatically decides how many leapfrog steps to take by growing the trajectory until it starts to double back on itself (the "No-U-Turn" criterion) — you never hand-tune a fixed number of steps.

Design Decision: Why Gradient-Guided Sampling?

Plain Metropolis-Hastings proposes randomly and rejects a lot in high dimensions — a "drunkard's walk" that explores the posterior painfully slowly. HMC/NUTS instead treats \(-\log p(\theta\mid D)\) as a potential energy surface and simulates a frictionless particle sliding across it, using the gradient to always move toward higher-probability regions while momentum lets it coast past local structure. This is why PyMC can fit models with hundreds of correlated parameters that plain MCMC could never touch.

🔑 Key Property

Every PyMC posterior is stored in an InferenceData object (via ArviZ) shaped (chain, draw, ...). Running multiple independent chains from different starting points is what lets PyMC/ArviZ diagnose convergence — via R-hat — and effective sample size, rather than trusting a single, possibly-stuck chain.

3
Why It Works — The Math
▼

Bayes' Rule for the Coin Example

Let \(p\in(0,1)\) be the coin's true heads-probability, with prior \(p \sim \text{Beta}(\alpha_0,\beta_0)\), and let \(k\) heads occur in \(n\) flips: \(k \mid p \sim \text{Binomial}(n,p)\). Bayes' rule gives:

$$p(p \mid k) \;\propto\; \underbrace{p^{k}(1-p)^{n-k}}_{\text{likelihood}} \cdot \underbrace{p^{\alpha_0-1}(1-p)^{\beta_0-1}}_{\text{prior}} \;=\; p^{\alpha_0+k-1}(1-p)^{\beta_0+n-k-1}$$

which is itself a \(\text{Beta}(\alpha_0+k,\ \beta_0+n-k)\) density — the Beta prior is conjugate to the Binomial likelihood. PyMC does not need to know this closed form; it will find the same answer numerically via HMC, which is what makes it general enough to handle models with no conjugacy at all.

Hamiltonian Dynamics in Unconstrained Space

PyMC transforms the bounded parameter \(p\) to an unconstrained \(\theta = \operatorname{logit}(p)\) so gradients behave well everywhere. Writing the potential energy as \(U(\theta) = -\log p(\theta \mid D)\) and introducing an auxiliary momentum \(r \sim \mathcal{N}(0,1)\), the Hamiltonian \(H(\theta,r) = U(\theta) + \tfrac12 r^2\) is simulated with the leapfrog integrator:

$$r \leftarrow r - \tfrac{\epsilon}{2}\nabla U(\theta), \qquad \theta \leftarrow \theta + \epsilon r, \qquad r \leftarrow r - \tfrac{\epsilon}{2}\nabla U(\theta)$$

For this model, the unconstrained log-posterior reduces to \(\log f(\theta) = a\log\sigma(\theta) + b\log(1-\sigma(\theta))\) with \(a=\alpha_0+k,\ b=\beta_0+n-k,\ \sigma(\theta)=\text{sigmoid}(\theta)\), giving a clean analytic gradient \(\nabla U(\theta) = (a+b)\,\sigma(\theta) - a\) — exactly what the live simulation below uses.

Convergence: R-hat and Effective Sample Size

With \(m\) chains of \(n\) post-warmup draws each, the Gelman-Rubin diagnostic compares within-chain variance \(W\) to between-chain variance \(B\):

$$\hat R = \sqrt{\frac{\frac{n-1}{n}W + \frac{1}{n}B}{W}}$$

\(\hat R \approx 1.00\) means the chains agree with each other and have mixed well; \(\hat R > 1.01\) is a red flag that they have not converged to the same distribution.

⚠️ Common Pitfall

A divergence in PyMC means the leapfrog integrator's discretized energy blew up relative to the true Hamiltonian — usually because the posterior has extreme curvature (e.g. a "funnel" in hierarchical models). Divergences signal that samples may be biased, not just noisy — the fix is reparameterization (non-centered parameterization) or raising target_accept, not just running longer.

Key Takeaways
▼

When to reach for PyMC:

  • You need calibrated uncertainty (credible intervals), not just a point estimate
  • The model has no closed-form posterior — hierarchical models, mixtures, custom likelihoods
  • You want to bake in domain knowledge as priors rather than starting from nothing
  • You need to combine multiple data sources / partial pooling across groups

Watch out for:

  • Divergences and low target_accept — a geometry problem, not a "sample more" problem
  • \(\hat R > 1.01\) or low effective sample size (ESS) — chains haven't mixed; run longer or reparameterize
  • Overly informative priors silently dominating small datasets — always run prior predictive checks
  • Posterior predictive checks (PPC) that don't cover the observed data — a sign of model misspecification
💡 Hierarchy of Bayesian inference methods

Conjugate closed-form (exact, only for special model pairs) → grid approximation (exact but exponential in dimensions) → Metropolis-Hastings (general, slow random walk) → HMC / NUTS (general, gradient-guided, PyMC's default) → Variational Inference / ADVI (fast, approximate, can understate uncertainty). PyMC lets you swap the last two with one keyword argument.

Code Trace
▼
import pymc as pm
import arviz as az
with pm.Model() as coin_model:
# Prior: p ~ Beta(2, 2) -- weakly informative, centered at 0.5
p = pm.Beta("p", alpha=2, beta=2)
# Likelihood: k heads out of n flips, k is observed
obs = pm.Binomial("obs", n=20, p=p, observed=14)
# Inference: PyMC selects NUTS automatically for continuous p
trace = pm.sample(1000, tune=1000, chains=4,
target_accept=0.9, random_seed=42)
# Posterior analysis
print(az.summary(trace, hdi_prob=0.94))
az.plot_trace(trace)
az.plot_posterior(trace, hdi_prob=0.94)
ppc = pm.sample_posterior_predictive(trace, model=coin_model)
