Understanding Mixed Precision
▼

What is it? Mixed precision training and inference involves using different numerical formats (e.g., 32-bit floating point, 16-bit floating point, 8-bit integers) for different parts of a neural network computation. The goal is to maximize performance (speed, memory footprint) without significantly compromising model accuracy.

Analogy: Imagine you're building a house. You wouldn't use a laser precision ruler for every measurement. For laying out the foundation, you might need a highly accurate laser (FP32). For cutting framing lumber, a tape measure (FP16/BF16) is usually good enough. For rough estimates like where to put a pile of dirt, a quick glance (INT8/INT4) is fine. Using the right tool for the right job saves time and money, but using a low-precision tool for a critical task can lead to disaster.

💡 If you remember one thing

Precision refers to the number of significant digits a number can hold, while range refers to how large or small a number can be. Different formats offer different trade-offs, impacting how values are stored, how arithmetic is performed, and ultimately, a model's performance and accuracy.

How Different Formats Work Internally
▼

Floating Point Formats (FP32, FP16, BF16)

These formats adhere to the IEEE 754 standard (or similar) and represent numbers using a sign bit, an exponent (determining the magnitude/range), and a mantissa (determining the precision/significant digits). The total number of bits is fixed, so there's a trade-off:

  • FP32 (Single Precision): The standard. 1 sign bit, 8 exponent bits, 23 mantissa bits. Offers a wide range (approx. \(10^{-38}\) to \(10^{38}\)) and good precision (~7-8 decimal digits).
  • FP16 (Half Precision): 1 sign bit, 5 exponent bits, 10 mantissa bits. Its narrow exponent range (approx. \(10^{-5}\) to \(6.5 \times 10^4\)) makes it prone to underflow (values becoming zero) and overflow (values becoming infinity). However, its 10-bit mantissa offers decent precision for its bit count.
  • BF16 (Bfloat16): 1 sign bit, 8 exponent bits, 7 mantissa bits. Crucially, it reuses FP32's 8-bit exponent, giving it the same wide range as FP32. The cost is a much smaller mantissa, leading to coarser precision (~2-3 decimal digits). This makes it less prone to under/overflow but more susceptible to rounding errors.

Integer Formats (INT8, INT4)

Integer formats represent whole numbers without a fractional component. They have a fixed, linear range determined by the number of bits. For ML, signed integers (e.g., 2's complement) are common:

  • INT8 (8-bit Integer): Typically signed, ranging from \(-128\) to \(+127\). Offers 256 discrete values. Used extensively for quantized inference.
  • INT4 (4-bit Integer): Typically signed, ranging from \(-8\) to \(+7\). Offers only 16 discrete values. Used for extreme quantization to push memory/speed limits, often with significant accuracy trade-offs.

To use integers for weights and activations (which are usually floats), a process called quantization is used, mapping a range of floating-point values to a fixed set of integer values. This introduces quantization error.

🔑 Key Property

The exponent bits primarily dictate the range (how large or small a number can be before over/underflowing). The mantissa bits primarily dictate the precision (how many significant digits, affecting rounding error). Integers have neither, relying on a fixed, linear mapping.

3
Why It Works — The Math of Representation
▼

Floating Point Representation

IEEE 754 floating-point numbers are represented in a normalized form:

$$V = (-1)^S \times M \times 2^E$$

where \(S\) is the sign bit (0 for positive, 1 for negative), \(M\) is the mantissa (or significand), and \(E\) is the exponent. The mantissa is typically represented as \(1.f\) where \(f\) is the fractional part stored in the mantissa bits. The exponent is stored with a bias to allow for negative exponents.

The number of bits dedicated to \(S\), \(E\), and \(M\) determines the format's characteristics:

  • FP32: 1 bit for \(S\), 8 bits for \(E\), 23 bits for \(M\). Bias is 127.
  • FP16: 1 bit for \(S\), 5 bits for \(E\), 10 bits for \(M\). Bias is 15.
  • BF16: 1 bit for \(S\), 8 bits for \(E\), 7 bits for \(M\). Bias is 127.

A smaller exponent field (like FP16's 5 bits) means a smaller maximum exponent and a larger minimum (more negative) exponent, leading to a narrower overall range. A smaller mantissa field (like BF16's 7 bits) means fewer significant digits, leading to more rounding error.

Linear Quantization for Integers

For integer formats (INT8, INT4), a floating-point value \(x\) is mapped to an integer \(x_q\) using a scale factor \(S_q\) and a zero-point \(Z\). This is often done linearly:

$$x_q = \text{round}\left( \frac{x}{S_q} + Z \right)$$

And to convert back to float:

$$x = S_q \times (x_q - Z)$$

The range of quantized values \([x_{q, \text{min}}, x_{q, \text{max}}]\) is fixed (e.g., \([-128, 127]\) for INT8). Any float outside the corresponding effective range \([S_q \times (x_{q, \text{min}} - Z), S_q \times (x_{q, \text{max}} - Z)]\) will be clipped to the min/max integer value, introducing error. The scale \(S_q\) and zero-point \(Z\) are chosen to minimize this error over a given distribution of float values.

⚠️ Key Trade-off

There is no free lunch: reducing the number of bits for a numerical format always means sacrificing either range (how large/small values can be) or precision (how accurately values are represented), or both. The choice of format depends on which type of error is more tolerable for a given task and hardware.

Key Takeaways
▼

When to use each format:

  • FP32: For model development, sensitive operations (e.g., softmax, loss calculation), and when maximum accuracy is paramount. Always used for master weights in mixed-precision training.
  • FP16: For training on GPUs with Tensor Cores (e.g., NVIDIA V100/A100/H100) to gain speed and memory efficiency. Requires loss scaling to prevent gradient underflow.
  • BF16: Increasingly the default for large model pretraining (e.g., LLMs) on modern hardware (TPUs, newer GPUs) due to its wide range (like FP32) which largely negates the need for loss scaling, simplifying training.
  • INT8: The workhorse for high-performance inference deployment, especially on edge devices and CPUs. Requires careful quantization of weights and activations, often with calibration data.
  • INT4: For extreme memory and latency reduction in inference, often for very large models. Involves significant quantization error and can lead to accuracy drops if not managed carefully.

Common pitfalls:

  • FP16: Underflow of small gradients to zero, leading to stalled training. Overflow to infinity for large activations.
  • BF16: Increased rounding errors due to lower mantissa precision, which can accumulate in very deep networks or long sequences.
  • INT8/INT4: Quantization error and clipping for values outside the representable range. Requires careful calibration and can be sensitive to data distribution.
💡 Rule of Thumb

Use the highest precision (FP32) unless you have a compelling reason (speed, memory) to go lower. When going lower, understand the specific limitations of the chosen format (range for FP16, precision for BF16, quantization for INTs) and apply the appropriate mitigation strategies (loss scaling, quantization-aware training).

Code Trace — PyTorch Mixed Precision & Quantization
▼
import torch
import torch.nn as nn
import torch.optim as optim
from torch.cuda.amp import autocast, GradScaler # For FP16/BF16 training
from torch.quantization import quantize_dynamic # For INT8 inference
# 1. Mixed Precision Training (FP16/BF16)
model = nn.Linear(10, 2).cuda() # FP32 master weights on GPU
optimizer = optim.Adam(model.parameters(), lr=0.001)
scaler = GradScaler() # For FP16: handles loss scaling to prevent underflow
# Example training step with FP16:
data = torch.randn(16, 10).cuda()
labels = torch.randint(0, 2, (16,)).cuda()
optimizer.zero_grad()
with autocast(dtype=torch.float16): # Context manager for FP16 ops
output = model(data) # Forward pass in FP16
loss = nn.CrossEntropyLoss()(output, labels)
scaler.scale(loss).backward() # Scale loss, then backprop (grads are scaled)
scaler.step(optimizer) # Unscale grads & apply optimizer step
scaler.update() # Update loss scale factor dynamically
# For BF16, GradScaler is often not needed as range matches FP32:
# with autocast(dtype=torch.bfloat16):
# output = model(data); loss = nn.CrossEntropyLoss()(output, labels)
# loss.backward(); optimizer.step()
# 2. Post-Training Dynamic Quantization (INT8)
model_fp32 = nn.Linear(10, 2).eval() # Load FP32 model in eval mode
# Quantize weights to INT8, activations dynamically to INT8 at runtime
model_int8 = quantize_dynamic(model_fp32, {nn.Linear}, dtype=torch.qint8)
# Example inference with INT8 model:
input_fp32 = torch.randn(1, 10)
output_int8 = model_int8(input_fp32) # Inference runs with INT8 ops
