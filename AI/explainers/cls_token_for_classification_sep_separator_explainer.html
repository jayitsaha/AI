How one placeholder token learns to summarize a sequence, and one separator learns to mark its boundaries

Understanding [CLS] and [SEP]
▼

What is it? BERT never sees raw sentences — it sees a fixed vocabulary of subword tokens, plus two artificial ones it invents no meaning for at all: [CLS] ("classification") and [SEP] ("separator"). [CLS] is glued to the front of every input; [SEP] is glued after every sentence. Neither corresponds to a real word — they are empty placeholders whose entire meaning is learned purely from training.

Analogy: Imagine handing a group of coworkers a stack of documents to summarize together in a meeting. You staple a blank cover sheet ([CLS]) to the front — by the end of the meeting, everyone has written a one-line summary on it, even though it started blank. And between each document you insert a bright red divider tab ([SEP]) so nobody accidentally reads two documents as one continuous ramble. The cover sheet becomes the summary; the divider tabs mark where one document ends and the next begins.

💡 If you remember one thing

[CLS]'s final hidden state \(h_{[CLS]}\) is used as a whole-sequence summary vector for classification tasks; [SEP] tells self-attention (via position + segment embeddings) exactly where each sentence starts and stops. Both are ordinary tokens with learned embeddings — there is no special hardcoded mechanism, only training signal.

How It Works Internally
▼

Building the Input Sequence

Given a sentence pair \((A, B)\), BERT's tokenizer (WordPiece) first splits each sentence into subword pieces — rare words get chopped into fragments prefixed with ## (e.g. "unforgettable" → un, ##forget, ##table). The model then assembles: \(\text{[CLS]}, a_1, \dots, a_m, \text{[SEP]}, b_1, \dots, b_n, \text{[SEP]}\). Note [SEP] appears twice — once after \(A\), once after \(B\) — and single-sentence tasks just drop the \(B\) half and keep one trailing [SEP].

Three Embeddings, Summed

Every position gets three learned embeddings added together before entering the transformer stack:

  • Token embedding — identity of the token (including [CLS]/[SEP], which have their own rows in the embedding matrix)
  • Position embedding — where it sits (0, 1, 2, …)
  • Segment (token-type) embedding — which sentence it belongs to: 0 for everything up to and including the first [SEP], 1 for everything after

This is precisely how [SEP] "marks a boundary": it is not special-cased in attention at all — it just sits at the segment-0/segment-1 transition and gets segment id 0 (last token of A) while every following token gets segment id 1. The model learns, from millions of examples of Next-Sentence-Prediction and downstream fine-tuning, to treat the region around [SEP] as a boundary signal.

Design Decision: Why Prepend a Dedicated Token Instead of Averaging?

An alternative pooling strategy would be mean- or max-pooling over all token hidden states. BERT's authors instead reserved a token whose hidden state is trained end-to-end (via a linear + tanh "pooler" head) specifically to aggregate sequence-level information, because self-attention lets [CLS] selectively attend to whichever tokens matter for the task — a learned, task-adaptive pool rather than a fixed uniform average.

🔑 Key Property

[CLS] and [SEP] carry no intrinsic meaning — their embedding rows start randomly initialized exactly like any word. All of their usefulness is emergent: it comes entirely from the pretraining objectives (Masked LM + Next Sentence Prediction) and fine-tuning gradients that flow back into those specific embedding rows and into every attention head that reads from them.

Why It Works — The Math
▼

Input Representation

For token at position \(i\) with token id \(t_i\), segment id \(s_i \in \{0,1\}\):

$$E_i = E_{\text{tok}}(t_i) + E_{\text{pos}}(i) + E_{\text{seg}}(s_i)$$

This \(E_i\) is what actually enters the first transformer layer — nothing in the architecture "knows" that token 0 is [CLS] except that its token embedding row was trained to be useful there.

Self-Attention Makes [CLS] a Summary

At each layer, \(\text{[CLS]}\)'s query vector \(q_{\text{CLS}} = W_Q h_{\text{CLS}}\) attends over every key in the sequence:

$$\alpha_{\text{CLS}, j} = \frac{\exp(q_{\text{CLS}}\cdot k_j / \sqrt{d_k})}{\sum_{l} \exp(q_{\text{CLS}}\cdot k_l / \sqrt{d_k})}, \qquad h_{\text{CLS}}' = \sum_j \alpha_{\text{CLS},j}\, v_j$$

Because \(\text{[CLS]}\) has no fixed syntactic role, its attention pattern is free to specialize per-head and per-layer to whatever aggregation the loss demands — some heads pull from segment A, others from segment B, others focus on [SEP] itself as a "no-op" resting place for attention mass.

Classification Head

After \(L\) layers, only the final [CLS] hidden state is used downstream:

$$p = \text{softmax}(W_c \cdot \tanh(W_p\, h_{\text{CLS}}^{(L)} + b_p) + b_c)$$

where \(W_p\) is BERT's "pooler" dense layer and \(W_c, b_c\) is the task-specific classification head trained (or fine-tuned) for the downstream problem.

⚠️ Common Pitfall

Using raw [CLS] embeddings from a base (non-fine-tuned) BERT as sentence embeddings for similarity search performs surprisingly poorly — anisotropy in the embedding space makes untrained [CLS] vectors cluster together regardless of meaning. Models like Sentence-BERT fine-tune specifically to fix this with contrastive objectives.

Key Takeaways
▼

What to remember:

  • [CLS] is always token position 0; its final-layer hidden state is fed to a classification/regression head for sequence-level tasks (sentiment, NLI, similarity scoring)
  • [SEP] ends every segment; combined with segment (token-type) embeddings, it is how BERT packs two sentences into one forward pass for tasks like Next Sentence Prediction, QA (question + passage), and NLI (premise + hypothesis)
  • Both tokens have ordinary learned embeddings — no architectural code path treats them specially; all their behavior is emergent from pretraining
  • For single-sentence tasks (e.g. single-text sentiment), only one [SEP] is used, at the very end

Common failure modes:

  • Forgetting [SEP] between concatenated segments silently merges two sentences into one — the model has no other cue where one ends and the next begins
  • Using un-fine-tuned [CLS] embeddings directly for semantic similarity (see pitfall above)
  • Truncating sequences without preserving the trailing [SEP] — some tokenizer pipelines silently drop it if max-length truncation is naive
💡 Bigger Picture

This "special token as programmable interface" pattern generalizes far beyond BERT: GPT uses a similar trick with an appended prompt token for classification, ViT prepends a [CLS] patch token for image classification, and modern LLMs use <|endoftext|>-style separators for exactly the same reason [SEP] exists here — giving attention an explicit, learnable boundary marker.
