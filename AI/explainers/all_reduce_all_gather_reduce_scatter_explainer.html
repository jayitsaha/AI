How GPUs synchronize gradients and shard parameters in distributed training

Understanding Collective Communication
▼

What is it? When a neural network trains across many GPUs, each device only sees a slice of the work — a slice of the data, a slice of the gradients, or a slice of the parameters. Collective operations are the standard patterns that let all devices exchange and combine that information without anyone acting as a single overloaded bottleneck.

Analogy: Imagine four cooks, each holding one ingredient for a shared recipe. All-Gather is everyone photocopying their ingredient list and mailing it to the other three, so all four end up holding the complete list. Reduce-Scatter is four accountants each holding a partial receipt for every expense category; they pass slips around until each accountant ends up the sole owner of the final total for one category. All-Reduce is doing the accounting step first, then photocopying the finished totals to everyone — first Reduce-Scatter, then All-Gather.

💡 If you remember one thing

$$\text{All-Reduce} = \text{Reduce-Scatter} + \text{All-Gather}$$ Reduce-Scatter combines the data and hands each device one finished piece; All-Gather then broadcasts every finished piece to everyone. Chaining them turns a scatter of partial data into a fully synchronized copy on every device.

How the Ring Algorithm Works Internally
▼

The Naive Approach — and Why It Fails

The obvious way to synchronize \(N\) devices is to have every device send its entire buffer of size \(S\) to every other device (or route everything through one root). Per-device traffic scales as \(O((N-1)\cdot S)\) — as the cluster grows, so does the burden on every link, and one root can become a serialized bottleneck.

The Ring Algorithm

Modern collective libraries (NCCL, Gloo) arrange the \(N\) devices into a logical ring and split the buffer into \(N\) equal chunks. Two phases run, each taking exactly \(N-1\) synchronized steps:

  • Reduce-Scatter phase: at each step, every device forwards one chunk to its ring neighbor, which adds it to its own running total for that chunk. After \(N-1\) steps, each device holds the fully-reduced (summed) value for exactly one distinct chunk — no device has the full result yet.
  • All-Gather phase: the same ring topology now just relays the (already finished) chunks around \(N-1\) more steps, so every device ends up holding all \(N\) finished chunks — the complete, fully-reduced buffer.
🔑 Design decision: why a ring, not a star?

In a ring, every device only ever talks to its two neighbors, and every link carries the same amount of traffic regardless of \(N\). This makes the ring bandwidth-optimal: per-device traffic is \(O(S)\), independent of cluster size, versus \(O(N \cdot S)\) for a naive star/root pattern. The trade-off is latency — a ring needs \(2(N-1)\) sequential steps, which hurts on very large \(N\) with tiny messages. That is why large clusters often use hybrid tree/ring or recursive-doubling schemes instead of a pure ring.

3
Why It Works — The Communication-Volume Math
▼

Let \(S\) be the total buffer size and \(N\) the number of devices, so each ring chunk has size \(S/N\). Each phase (Reduce-Scatter or All-Gather) takes \(N-1\) steps, and at each step a device sends exactly one chunk:

$$\text{bytes sent per device (one phase)} = (N-1)\cdot \frac{S}{N} = \frac{N-1}{N}\,S$$

Since All-Reduce chains both phases back-to-back, its total per-device traffic doubles:

$$\text{bytes sent per device (All-Reduce)} = 2\cdot\frac{N-1}{N}\,S$$

As \(N\to\infty\), \(\frac{N-1}{N}\to 1\) — the ring algorithm's per-device cost converges to a constant (\(S\) for one phase, \(2S\) for All-Reduce), completely independent of how many devices participate. Compare that to the naive approach's \((N-1)\cdot S\), which grows linearly with \(N\) — a naive 64-GPU job moves roughly 64× more data per device than the ring version.

⚠️ Common misconception

"All-Reduce is a single atomic primitive optimized as one unit." In most production libraries it is literally implemented as Reduce-Scatter immediately followed by All-Gather — two separate ring passes glued together. Profilers that show two distinct communication bursts per All-Reduce call are not being inefficient; that is the algorithm working as designed.

Key Takeaways
▼

When to use which collective:

  • All-Gather — reconstructing a full tensor from shards: gathering sharded embedding tables, or re-materializing full parameters in FSDP/ZeRO-3 right before a forward/backward pass.
  • Reduce-Scatter — combining contributions while immediately re-sharding the result: summing gradients in ZeRO-2/ZeRO-3 and FSDP, where each device only needs to keep the shard of the gradient it is responsible for.
  • All-Reduce — the classic data-parallel gradient sync (PyTorch DDP, Horovod): every device needs the identical, fully-summed gradient, so Reduce-Scatter and All-Gather are chained automatically.

When NOT to reach for a pure ring implementation:

  • Very small messages on very large device counts — the \(2(N-1)\) sequential steps become latency-bound; tree or recursive-doubling algorithms (used automatically by NCCL for small buffers) win instead.
  • Single-device or single-node training — there is nothing to communicate; skip collectives entirely.
💡 The one identity to internalize

All-Reduce is not a separate algorithm to memorize — it is Reduce-Scatter's output fed straight into an All-Gather. Once you can reason about those two primitives, All-Reduce (and its cost) falls out for free.

Code Trace — Ring All-Reduce
▼
def ring_all_reduce(tensor, rank, world_size):
chunks = list(tensor.chunk(world_size)) # split buffer into N chunks
send_to, recv_from = (rank + 1) % world_size, (rank - 1) % world_size
# ---- Phase 1: Reduce-Scatter (N-1 steps) ----
for step in range(world_size - 1):
send_idx = (rank - step) % world_size
dist.send(chunks[send_idx], dst=send_to)
recv_buf = torch.empty_like(chunks[send_idx])
dist.recv(recv_buf, src=recv_from)
chunks[send_idx] += recv_buf # accumulate into own copy
# ---- Phase 2: All-Gather (N-1 steps) ----
for step in range(world_size - 1):
send_idx = (rank - step + 1) % world_size
dist.send(chunks[send_idx], dst=send_to)
recv_idx = (rank - step) % world_size
dist.recv(chunks[recv_idx], src=recv_from) # overwrite: already final
return torch.cat(chunks) # identical full buffer on every rank
