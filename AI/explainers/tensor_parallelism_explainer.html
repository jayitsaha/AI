Megatron-LM's strategy for scaling large transformer layers beyond single-GPU memory limits

1
Understanding Tensor Parallelism
▼

What is it? Tensor parallelism (TP) is a technique to distribute the computation of a single layer's large tensors (like weight matrices or activation states) across multiple devices. Instead of duplicating the entire layer on each GPU (as in data parallelism) or splitting the model layer-by-layer (as in pipeline parallelism), TP slices the tensors themselves, allowing individual layers to exceed the memory capacity of a single GPU.

Why is it needed? As transformer models grow to billions or even trillions of parameters (e.g., GPT-3, Megatron-LM), the weight matrices in dense layers (like MLPs and attention projections) become enormous. Even with a single batch, these weights, plus their activations and gradients, can easily exhaust a GPU's memory. TP enables these colossal layers to fit into memory by distributing their components across a cluster of GPUs.

Analogy: Imagine a giant spreadsheet too wide for a single screen. Instead of scrolling back and forth (like pipeline parallelism) or having many people work on separate copies of the whole sheet (like data parallelism), you connect multiple monitors side-by-side. Each monitor shows a contiguous part of the spreadsheet, and when you perform an operation, it's done across all monitors in a coordinated way. Tensor parallelism applies this concept to matrix operations.

💡 If you remember one thing

Tensor parallelism splits individual layers' weights and activations across devices, primarily to reduce the memory footprint of these large tensors. It's often combined with data and pipeline parallelism for maximum scalability on very large models.

2
How It Works Internally: Megatron-LM's Approach
▼

Megatron-LM introduced a common pattern for tensor parallelism in transformer blocks, specifically for the linear layers in the Multi-Layer Perceptron (MLP) and Attention mechanisms. The key idea is to alternate between two types of matrix splitting:

1. Column Parallel Linear Layers (Output Dimension Split)

Consider a linear layer \(Y = XW\), where \(X\) is the input activation (\(B \times H\)) and \(W\) is the weight matrix (\(H \times O\)). In column parallelism, the weight matrix \(W\) is split column-wise into \(P\) chunks: \(W = [W_0 \mid W_1 \mid \dots \mid W_{P-1}]\). Each device \(k\) stores \(W_k\), which has dimensions \(H \times (O/P)\).

The input activation \(X\) is replicated across all \(P\) devices. Each device \(k\) then locally computes its part of the output: \(Y_k = XW_k\). The resulting \(Y_k\) has dimensions \(B \times (O/P)\). The full output \(Y\) is conceptually the concatenation of these \(Y_k\)s: \(Y = [Y_0 \mid Y_1 \mid \dots \mid Y_{P-1}]\). This operation is used for layers like the first linear layer in an MLP (e.g., \(W_{fc1}\)) or the query, key, and value projection matrices in self-attention.

2. Row Parallel Linear Layers (Input Dimension Split)

For a subsequent linear layer, say \(Z = YB\), where \(Y\) is the input activation (\(B \times H'\)) and \(B\) is the weight matrix (\(H' \times O'\)). In row parallelism, the weight matrix \(B\) is split row-wise into \(P\) chunks: \(B = [B_0^T \mid B_1^T \mid \dots \mid B_{P-1}^T]^T\). Each device \(k\) stores \(B_k\), which has dimensions \((H'/P) \times O'\).

The input \(Y\) for this layer must be distributed such that each device \(k\) holds \(Y_k\), corresponding to the row-split of \(B\). This is often the output from a previous column-parallel layer. Each device \(k\) computes a partial sum: \(Z_k = Y_k B_k\). To get the final, full output \(Z\), these partial sums must be aggregated across all devices using an AllReduce collective communication operation: \(Z = \sum_{k=0}^{P-1} Z_k\). This pattern is used for layers like the second linear layer in an MLP (e.g., \(W_{fc2}\)) or the output projection matrix in self-attention.

🔑 Key Property

The alternation of column-parallel and row-parallel operations within a transformer block (e.g., MLP: Column Parallel \(X \to A\), then Row Parallel \(Y \to B\)) ensures that the input to each operation is correctly distributed, and the communication overhead is minimized by performing an AllReduce only once per block.

3
Why It Works — The Math
▼

Let's consider a simplified MLP block: an input \(X\) of shape \((B, H)\) goes through a linear layer with weight \(A\) of shape \((H, 4H)\), followed by a GELU activation, and then another linear layer with weight \(B\) of shape \((4H, H)\), producing output \(Z\) of shape \((B, H)\). The full operation is \(Z = \text{GELU}(X A) B\).

1. Column Parallel: \(Y = X A\)

To parallelize \(Y = X A\) across \(P\) devices, we split the weight matrix \(A\) along its output dimension (columns). Each device \(k\) receives a slice \(A_k\) of shape \((H, 4H/P)\). The input \(X\) is replicated on all devices.

$$A = [A_0 \mid A_1 \mid \dots \mid A_{P-1}]$$ $$Y = X A = X [A_0 \mid A_1 \mid \dots \mid A_{P-1}] = [X A_0 \mid X A_1 \mid \dots \mid X A_{P-1}]$$

Each device \(k\) computes its local output \(Y_k = X A_k\). This \(Y_k\) has shape \((B, 4H/P)\). The concatenation of these local outputs forms the full intermediate activation \(Y\). No communication is needed at this stage for the forward pass, as each device holds its part of \(Y\).

2. Element-wise Activation: \(\text{GELU}(Y)\)

The GELU activation is applied element-wise. Since each device \(k\) already holds its partition \(Y_k\), it can locally compute \(\text{GELU}(Y_k)\) without any communication. Let \(Y'_{k} = \text{GELU}(Y_k)\).

3. Row Parallel: \(Z = Y' B\)

Now, we want to compute \(Z = Y' B\). The input \(Y'\) is logically partitioned as \(Y' = [Y'_0 \mid Y'_1 \mid \dots \mid Y'_{P-1}]\). To parallelize this, we split the weight matrix \(B\) along its input dimension (rows). Each device \(k\) receives a slice \(B_k\) of shape \((4H/P, H)\).

$$B = \begin{pmatrix} B_0 \\ B_1 \\ \vdots \\ B_{P-1} \end{pmatrix}$$ $$Z = Y' B = [Y'_0 \mid Y'_1 \mid \dots \mid Y'_{P-1}] \begin{pmatrix} B_0 \\ B_1 \\ \vdots \\ B_{P-1} \end{pmatrix} = \sum_{k=0}^{P-1} Y'_k B_k$$

Each device \(k\) computes its local partial sum \(Z_k = Y'_k B_k\). This \(Z_k\) has shape \((B, H)\). To obtain the final, correct output \(Z\), an AllReduce operation is performed across all devices, summing up these partial results: \(Z = \text{AllReduce}(\sum Z_k)\). After the AllReduce, each device holds the complete output tensor \(Z\).

$$Z_{\text{final}} = \text{AllReduce}(Z_0, Z_1, \dots, Z_{P-1})$$
⚠️ Communication is Key

The efficiency of tensor parallelism heavily relies on fast inter-device communication. The AllReduce operation in row-parallel layers (and potential AllGather for replicating inputs) is the primary source of overhead. For large \(P\), this can become a bottleneck, especially on networks with high latency or low bandwidth.

5
Key Takeaways
▼

When to use Tensor Parallelism:

  • Training extremely large models (100B+ parameters) where a single layer's weights exceed GPU memory.
  • For dense linear layers (MLP, attention projections) that involve large matrix multiplications.
  • When combined with other parallelism strategies (data and pipeline parallelism) to scale training across hundreds or thousands of GPUs.

Benefits:

  • Memory Reduction: The primary benefit is distributing large weight matrices, activations, and gradients, allowing models to fit into aggregate memory that no single GPU could hold.
  • Potential Speedup: On hardware optimized for distributed computation and with efficient interconnects (e.g., NVLink, InfiniBand), TP can leverage multiple Tensor Cores concurrently for faster matrix multiplications.

Limitations & Considerations:

  • Communication Overhead: TP introduces significant communication (AllGather, AllReduce) between devices within the same tensor parallel group. This can become a bottleneck if inter-device bandwidth is limited.
  • Implementation Complexity: Requires careful partitioning of tensors and explicit collective communication operations, making model implementation more complex than pure data parallelism.
  • Not Universal: Only certain operations (like matrix multiplication) benefit directly. Element-wise operations (e.g., GELU, ReLU) are naturally local.
💡 Hierarchy of Parallelism

Data Parallelism (DP) splits the batch across devices. Pipeline Parallelism (PP) splits the model layer-by-layer across devices. Tensor Parallelism (TP) splits individual layers' tensors across devices. For the largest models, all three are often combined (e.g., 3D Parallelism in Megatron-LM).

import torch
import torch.nn as nn
import torch.distributed as dist
# Assume P devices, world_size = P
# rank = current device's ID (0 to P-1)
# group = tensor parallel group
class ColumnParallelLinear(nn.Module):
def __init__(self, in_features, out_features, bias=True):
super().__init__()
self.out_features_per_partition = out_features // dist.get_world_size(group)
self.weight = nn.Parameter(torch.empty(in_features, self.out_features_per_partition))
# Initialize weight (e.g., Xavier uniform)
if bias:
self.bias = nn.Parameter(torch.empty(self.out_features_per_partition))
def forward(self, input_):
# Input 'input_' is replicated across all devices.
# Local matrix multiplication (X @ W_k)
output_parallel = torch.matmul(input_, self.weight)
if self.bias is not None:
output_parallel = output_parallel + self.bias
# No explicit AllGather here, subsequent layers will work on partitions
return output_parallel # Each device returns its Y_k
class RowParallelLinear(nn.Module):
def __init__(self, in_features, out_features, bias=True):
super().__init__()
self.in_features_per_partition = in_features // dist.get_world_size(group)
self.weight = nn.Parameter(torch.empty(self.in_features_per_partition, out_features))
# Initialize weight
self.bias = bias # Bias is applied after AllReduce
self.out_features = out_features
def forward(self, input_):
# Input 'input_' is a partition (e.g., Y_k from ColumnParallelLinear)
# Local matrix multiplication (Y_k @ B_k)
output_parallel = torch.matmul(input_, self.weight)
# AllReduce to sum partial outputs across devices
output_ = dist.all_reduce(output_parallel, op=dist.ReduceOp.SUM, group=group, async_op=False)
# Bias is added after the AllReduce, as it's a global operation
if self.bias:
# Need a global bias here, or handle it differently for simplicity
# For simplicity, assume bias is managed externally or added to a replicated tensor
pass
return output_ # Each device returns the full Z
# Example MLP Block using these layers
class TP_MLP(nn.Module):
def __init__(self, hidden_size, intermediate_size):
super().__init__()
self.dense_h_to_4h = ColumnParallelLinear(hidden_size, intermediate_size)
self.activation = nn.GELU()
self.dense_4h_to_h = RowParallelLinear(intermediate_size, hidden_size)
def forward(self, hidden_states):
# hidden_states (X) is replicated on all devices
intermediate_parallel = self.dense_h_to_4h(hidden_states) # Y_k
intermediate_activated = self.activation(intermediate_parallel) # GELU(Y_k)
output = self.dense_4h_to_h(intermediate_activated) # AllReduce(Z_k) -> Z
return output
