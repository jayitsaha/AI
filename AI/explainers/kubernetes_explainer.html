Understanding Kubernetes Fundamentals
▼

What is it? Kubernetes (often abbreviated K8s) is an open-source system for automating deployment, scaling, and management of containerized applications. It groups containers into logical units for easy management and discovery. Think of it as an operating system for your cluster, abstracting away the underlying machines and letting you focus on your applications.

Analogy: Imagine you're managing a large, busy restaurant. Instead of manually hiring, training, and assigning every chef (container) to specific stoves (machines) and making sure they're always cooking enough food (handling traffic), you hire a smart manager (Kubernetes). This manager automatically assigns chefs, brings in more chefs if demand increases (scaling), replaces sick chefs, and ensures customers always get their orders (service discovery and load balancing). You just tell the manager what kind of food you want and how many portions, and K8s handles the rest.

💡 If you remember one thing

Kubernetes manages the lifecycle of containerized applications by orchestrating underlying infrastructure. Its core strength lies in declarative configuration: you describe the desired state of your application, and K8s continuously works to make the actual state match it.

2
Key Abstractions and Components
▼

The Kubernetes Control Plane

At the heart of every K8s cluster is the Control Plane. This is where decisions are made. Key components include:

  • API Server: The front end of the Kubernetes control plane. All communication (internal and external) goes through it.
  • etcd: A highly available key-value store that holds all cluster data (desired state, actual state, configurations).
  • Scheduler: Watches for newly created Pods with no assigned node, and selects a node for them to run on.
  • Controller Manager: Runs controller processes. For example, a Deployment controller watches Deployment objects and creates/updates ReplicaSets, which then create/update Pods.

Worker Nodes and Their Agents

Worker nodes are where your applications actually run. Each worker node has:

  • Kubelet: An agent that runs on each node in the cluster. It ensures containers are running in a Pod.
  • Kube-proxy: A network proxy that maintains network rules on nodes, allowing network communication to Pods from inside or outside the cluster.
  • Container Runtime: The software responsible for running containers (e.g., Docker, containerd, CRI-O).

The Core Workloads: Pods, Deployments, Services

These are the user-facing abstractions you interact with:

  • Pod: The smallest deployable unit in Kubernetes. A Pod is a group of one or more containers, with shared storage and network resources, and a specification for how to run the containers. Pods are ephemeral.
  • Deployment: Manages a set of identical Pods. It ensures that a specified number of Pod replicas are running at any given time. Deployments automate rolling updates and rollbacks.
  • Service: An abstract way to expose an application running on a set of Pods as a network service. Services provide a stable IP address and DNS name, and load-balance traffic across the Pods they target.
🔑 Key Property

Kubernetes resources are defined declaratively, typically in YAML files. You declare what you want (e.g., "I want 3 replicas of this Nginx container"), and Kubernetes' control plane works to achieve and maintain that state, continuously reconciling any deviations.

Scaling and Resource Management (HPA, GPU)
▼

Horizontal Pod Autoscaling (HPA)

HPA automatically scales the number of Pod replicas in a Deployment (or ReplicaSet, StatefulSet) based on observed CPU utilization, memory usage, or custom metrics. This ensures applications can handle varying loads efficiently.

The HPA controller periodically queries resource metrics (e.g., from Metrics Server). If the average CPU utilization across all Pods in a Deployment exceeds a target percentage, the HPA calculates the new desired replica count \(N_{new}\) using the formula:

$$N_{new} = \lceil N_{current} \cdot \frac{Current\ Metric\ Value}{Target\ Metric\ Value} \rceil$$

For example, if current CPU utilization is 80% and the target is 50%, \(N_{new} = \lceil N_{current} \cdot (80/50) \rceil = \lceil N_{current} \cdot 1.6 \rceil\). The HPA then updates the Deployment's replica count, triggering the Deployment controller to create or terminate Pods.

GPU Scheduling and Resource Requests

For workloads requiring specialized hardware like GPUs, Kubernetes allows Pods to request specific resources. This is crucial for ML training, inference, and high-performance computing.

A Pod's resource request for a GPU is specified in its manifest:

resources:
  limits:
    nvidia.com/gpu: 1 # request 1 GPU

The Kubernetes Scheduler plays a vital role here. When a Pod with a GPU request is created, the Scheduler:

  1. Filters out nodes that do not have available GPUs (or don't have GPUs at all).
  2. Scores the remaining nodes based on various factors (e.g., resource availability, anti-affinity rules).
  3. Assigns the Pod to the highest-scoring suitable node.

If no node can satisfy the GPU request, the Pod remains in a Pending state until a suitable node becomes available. This ensures that GPU-intensive workloads only run on nodes equipped to handle them, preventing resource contention and maximizing hardware utilization.

🔑 Key Property

Resource requests are a contract: Kubernetes guarantees that a Pod will receive at least the requested resources. Resource limits, however, define the maximum amount of a resource a Pod can consume, preventing noisy neighbors from hogging all resources.

Key Takeaways
▼

Kubernetes is essential for:

  • Scalability: Easily scale applications up or down based on demand (manual or HPA).
  • High Availability: Automatically replaces failed Pods, ensuring continuous service.
  • Resource Management: Efficiently allocates resources (CPU, Memory, GPU) across a cluster.
  • Portability: Run applications consistently across different cloud providers or on-premises.
  • Simplified Operations: Automates many tasks that would otherwise require manual intervention.

When to be cautious:

  • Complexity: Kubernetes has a steep learning curve and introduces operational overhead for small projects.
  • Resource Overhead: The control plane and agent processes consume resources, which might be significant for very small clusters.
  • Stateful Applications: Managing persistent storage and stateful applications can be more challenging than stateless ones.
💡 Modern Cloud Native Standard

Kubernetes has become the de-facto standard for container orchestration. Understanding its core objects (Pods, Deployments, Services) and controllers (HPA, Scheduler) is fundamental for anyone working with cloud-native applications, especially for ML workloads leveraging specialized hardware like GPUs.
