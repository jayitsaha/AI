Understanding MLflow
▼

What is it? MLflow is an open-source platform for managing the end-to-end machine learning lifecycle. It is built from four loosely-coupled components that you can adopt independently or together: Tracking (log parameters, metrics and artifacts for every run), Projects (package code so anyone can reproduce a run from a clean environment), Models (a standard packaging format so a trained model can be deployed to many serving tools without rewriting it), and the Model Registry (a versioned, governed store that tracks which model version is in Staging vs. Production).

Analogy: Think of a science lab notebook (Tracking) that records every experiment's inputs and results, a shipping container standard (Projects) so the experiment runs identically on any machine, a universal power adapter (Models) so the trained artifact plugs into any serving system, and a librarian's card catalog (Registry) that stamps "approved for production" on exactly one version at a time while archiving the rest.

💡 If you remember one thing

MLflow does not train your model — it wraps the training loop so that every run is logged, every environment is reproducible, every artifact is portable, and the promotion from experiment to production is governed instead of ad-hoc. The four components form a pipeline: Projects packages the code → Tracking records what happened when it ran → Models packages the resulting artifact → Registry governs which version serves traffic.

2
How MLflow Works Internally
▼

Tracking: Runs, Experiments and the Backend Store

An Experiment is a named bucket of Runs. Each run is created with mlflow.start_run() and gets a unique run ID. Inside the run you call mlflow.log_param(key, value) for hyperparameters (immutable, one value per key), mlflow.log_metric(key, value, step) for time-series values like loss or accuracy per epoch (mutable — you can log the same key repeatedly with increasing step), and mlflow.log_artifact(path) for files (plots, checkpoints, the model itself). All of this is written to a backend store (a local folder, or a SQL database such as Postgres in production) and an artifact store (local disk or S3 / GCS / Azure Blob).

Projects: Reproducibility as a Contract

A Project is any directory (or Git repo) containing an MLproject YAML file. It declares an environment (a conda.yaml, a Docker image, or a virtualenv requirements file) and one or more named entry points with typed parameters. Running mlflow run . -P lr=0.01 recreates the exact environment before executing the entry point — the same command works on a laptop, a CI runner, or a Databricks cluster.

Models: One Save Format, Many Flavors

When you call mlflow.sklearn.log_model(model, "model") (or the pytorch / xgboost / transformers equivalents), MLflow writes an MLmodel YAML file plus the serialized weights into the artifact store. The MLmodel file lists one or more flavors — the generic python_function flavor (so any tool can call predict() without knowing it is sklearn underneath) and the native flavor (so sklearn-specific code can load it back as a real RandomForestClassifier). This dual representation is what lets the exact same saved artifact be served by mlflow models serve, deployed to a Kubernetes pod, converted to ONNX, or loaded straight into a batch-scoring notebook.

Registry: Governance on Top of Storage

The Model Registry sits above the artifact store. mlflow.register_model(model_uri, name) takes an existing logged model and creates (or increments) a registered model version. Each version carries a stage — None → Staging → Production → Archived — that a human or a CI job transitions explicitly via MlflowClient.transition_model_version_stage(). Exactly the governance step that ad-hoc "just copy the .pkl to prod" workflows lack.

🔑 Key Property

Every MLflow component talks to the same backend/artifact store through a thin client. That is why a run logged from a Jupyter notebook, a registered model created from that run, and a production deployment reading that registered model version are all just different views onto one consistent record — there is no separate "deployment config" to keep in sync by hand.

The Math Behind This Demo
▼

The interactive walkthrough below simulates a real hyperparameter sweep of 5 runs training a small feed-forward classifier, so every number you see is computed live from these formulas — not hard-coded.

Simulated Validation Accuracy per Epoch

Each run has a learning rate \(\ell\). There is a sweet spot around \(\ell=0.01\): rates far from it in log-space reach a lower accuracy ceiling, modeled as a Gaussian bump in \(\log_{10}\ell\):

$$a_{max}(\ell) = 0.97 - 0.03\big(\log_{10}\ell - \log_{10}(0.01)\big)^2$$

Convergence speed scales with the learning rate, \(k(\ell) = 40\ell\), and the accuracy after \(e\) epochs follows an exponential-saturation curve plus a small run-seeded jitter term \(\eta(e)\):

$$\text{acc}(e) = a_{max}(\ell)\cdot\big(1 - e^{-k(\ell)\cdot e}\big) + \eta(e)$$

Model Size from the Architecture

Each run also picks a hidden-layer width \(h\) for a network mapping 784 inputs (a flattened 28×28 image) to 10 output classes. The parameter count — which drives the artifact size shown in the Models step — is exact arithmetic, not a guess:

$$P(h) = \underbrace{(784h + h)}_{\text{input}\to\text{hidden, + bias}} + \underbrace{(10h + 10)}_{\text{hidden}\to\text{output, + bias}} = 794h + 10$$

Promotion Score for the Registry

Deciding which Staging candidate gets promoted to Production is not "pick the highest accuracy" alone — a tiny accuracy gain from a 16× larger model is rarely worth the latency and serving cost. The demo scores each candidate with a small complexity penalty on the log parameter count:

$$S = \text{acc}_{final} - 0.004 \cdot \log_{10} P(h)$$

The version with the highest \(S\) among Staging candidates is the one the walkthrough promotes to Production — computed live, so if you re-derive the numbers by hand you will get the same winner.

⚠️ Common Pitfall

Teams often promote the run with the single best training-set metric without checking that a registered, versioned model even exists for it — meaning the "production" artifact silently drifts from what was validated. The Registry's stage transitions exist precisely to force that check to happen explicitly, in one auditable place.

Key Takeaways
▼

When to reach for each component:

  • Tracking — anytime you run more than one experiment and want to compare them later instead of trusting your memory or a spreadsheet
  • Projects — when a run needs to be reproduced by a teammate, a CI job, or a scheduled retraining pipeline on a different machine
  • Models — when the same trained artifact needs to be consumed by more than one serving path (batch scoring, a REST endpoint, an edge device)
  • Registry — the moment more than one person can push to "production" and you need an explicit, auditable gate

When it may be overkill:

  • A single throwaway notebook experiment with no comparison need — plain logging is fine
  • A team already standardized on a different tracking system (Weights & Biases, Neptune, SageMaker Experiments) — don't run two in parallel without a reason
  • Registry governance for a model that never leaves a research notebook
💡 Hierarchy

Tracking (what happened) feeds Models (what was produced), which is versioned by the Registry (what is allowed to serve), while Projects (how to rerun it) wraps the whole thing so the pipeline is reproducible end to end, not just recorded after the fact.

import mlflow
from mlflow.tracking import MlflowClient
# --- 1. Tracking: run the sweep, log everything ---
mlflow.set_experiment("mnist-mlp-sweep")
for lr, hidden in [(0.001,16),(0.003,32),(0.01,64),(0.03,128),(0.1,256)]:
with mlflow.start_run() as run:
mlflow.log_param("learning_rate", lr)
mlflow.log_param("hidden_units", hidden)
model = train(lr=lr, hidden=hidden)
for epoch, acc in enumerate(model.history, start=1):
mlflow.log_metric("val_accuracy", acc, step=epoch)
# --- 2. Projects: MLproject makes this reproducible ---
# $ cat MLproject
# name: mnist-mlp-sweep
# conda_env: conda.yaml
# entry_points:
# train:
# parameters: {lr: {type: float, default: 0.01}}
# command: "python train.py --lr {lr}"
# $ mlflow run . -P lr=0.01
# --- 3. Models: log the best run with multiple flavors ---
mlflow.sklearn.log_model(
sk_model=model,
artifact_path="model",
registered_model_name=None,
) # writes MLmodel with python_function + sklearn flavors
# --- 4. Registry: register + govern the best run ---
best_run_id = "runC" # highest promotion score S
mv = mlflow.register_model(f"runs:/{best_run_id}/model", "mnist-mlp")
client = MlflowClient()
client.transition_model_version_stage(
name="mnist-mlp", version=mv.version, stage="Staging")
client.transition_model_version_stage(
name="mnist-mlp", version=mv.version, stage="Production",
archive_existing_versions=True)
# --- 5. Serve the production version ---
model = mlflow.pyfunc.load_model("models:/mnist-mlp/Production")
