Lambda Architecture: Batch + Streaming

Merging an accurate-but-slow batch layer with a fast-but-approximate speed layer into one query surface
Foundational Data Engineering Streaming Systems Eventually Exact
1
Understanding Lambda Architecture
▼

What is it? Lambda Architecture, coined by Nathan Marz around 2011, is a data-processing pattern for answering arbitrary queries over data that never stops arriving. It splits work across three layers: a batch layer that periodically recomputes exact "views" from the entire immutable history, a speed layer that incrementally processes only the events since the last batch run to fill the latency gap, and a serving layer that merges both views to answer a query with one number.

Analogy: Think of a newspaper (the batch layer) and a live news ticker (the speed layer). The newspaper is thorough, fact-checked, and correct — but it only comes out once a day. The ticker is instant, but sometimes reports a number that later gets revised once the full story is confirmed. Reading "today's news" (the serving layer) means combining yesterday's newspaper with today's ticker, and every morning the ticker's guesses get quietly replaced by the newspaper's verified account.

💡 If you remember one thing

Every query is answered by merging two views: $$\text{Answer}(q) = q(V_{batch}) \oplus q(V_{speed})$$ where \(V_{batch}\) is exact but stale (recomputed from all history) and \(V_{speed}\) is fresh but approximate (computed only from the delta since the last batch run). As the batch layer catches up, it silently overwrites and corrects the speed layer's guesswork.

2
How Lambda Architecture Works Internally
▼

The Batch Layer: Slow but Always Right

New events are appended, immutably and forever, to a master dataset (a durable, append-only log — think HDFS, S3, or Kafka with infinite retention). Periodically — every few minutes to every few hours — a batch engine (historically MapReduce, now more often Spark or Flink batch mode) recomputes batch views from scratch, over the entire dataset. Because it always recomputes from raw, immutable facts, the batch layer is self-healing: any bug in yesterday's logic is corrected the moment the code is fixed and the job reruns. The cost is latency — a full recompute can take minutes to hours.

The Speed Layer: Fast but Approximate

The speed layer only has to cover the gap the batch layer hasn't reached yet — the events that arrived since the last batch view was materialized. A stream processor (Storm, Flink streaming, Kafka Streams) updates real-time views incrementally, per-event, in milliseconds. To hit that latency it often trades correctness for speed: approximate algorithms (HyperLogLog for distinct counts, Count-Min Sketch for frequencies), best-effort deduplication, or simply not yet having reconciled out-of-order and retried events.

The Serving Layer: One Answer, Two Sources

A query never touches the batch or speed layer directly. The serving layer merges the two: it takes whatever the batch layer has already computed (the reliable historical base) and adds the speed layer's live estimate of everything since (the reliable base's "in-progress" continuation). When the next batch cycle finishes, the serving layer swaps in the new exact batch view and tells the speed layer to discard the window it just covered and start counting from zero again.

🔑 Key Property — Self-Healing

The speed layer's error never accumulates indefinitely. Every batch cycle resets it to zero by replacing the approximate window with an exact recomputation. The system oscillates between "small approximation error" (just after a batch run) and "larger approximation error" (right before the next one) — a repeating sawtooth, not a runaway drift.

3
Why It Works — The Math
▼

Defining the Two Views

Let \(D_{[0,t]}\) be all events observed up to time \(t\), and let \(t_b\) be the timestamp of the most recent completed batch run. The batch view is a deterministic function of everything up to that boundary:

$$V_{batch}(t) = f\big(D_{[0,\,t_b]}\big) \qquad \text{(exact, recomputed from scratch)}$$

The speed layer only ever has to summarize the small delta since the boundary, using an incremental, approximate estimator \(\hat f\):

$$V_{speed}(t) = \hat f\big(D_{(t_b,\,t]}\big) \qquad \text{(approximate, updated per-event)}$$

The serving layer's answer to any query \(q\) is simply:

$$\text{Answer}(q, t) = q\big(V_{batch}(t)\big) \oplus q\big(V_{speed}(t)\big)$$

where \(\oplus\) is a merge operator appropriate to the query — sum for counts, union for sets, max for extremes.

Where the Approximation Error Comes From

A concrete, real example: if the speed layer estimates distinct counts with a HyperLogLog sketch using \(m\) registers, its relative standard error is bounded by the well-known result

$$\text{RSE} \approx \frac{1.04}{\sqrt{m}}$$

More generally, as the delta window \((t_b, t]\) grows — the longer it has been since the last batch run — more unreconciled, out-of-order, or approximately-deduplicated events pile up, so error grows with the size of the uncorrected window. The moment the next batch run completes, \(t_b\) jumps forward, the window resets to empty, and error snaps back to zero.

⚠️ Common Pitfall

Lambda Architecture requires maintaining the same business logic in two different systems — one batch engine, one stream engine — that must agree on what \(f\) and \(\hat f\) compute. If the two implementations drift apart (different edge-case handling, different bugs), the merged answer becomes inconsistent in ways that are hard to detect. This "dual codebase" cost is the single biggest criticism of the pattern, and is exactly what the alternative Kappa Architecture (one stream engine, replaying the durable log for reprocessing instead of a separate batch engine) was designed to eliminate.

Key Takeaways
▼

When to use Lambda Architecture:

  • You need both a low-latency approximate answer right now and an eventually-exact answer for auditing or billing
  • Raw data is immutable and append-only, so full historical recomputation is always possible
  • Your team can genuinely maintain two processing codebases (batch + streaming) without them drifting apart
  • Classic case: a real-time analytics dashboard that reconciles against a nightly (or hourly) exact batch job

When NOT to use it:

  • You cannot afford to keep two implementations of the same business logic in sync — consider Kappa Architecture instead (a single stream engine that replays the durable log for reprocessing, no separate batch engine)
  • Strong, immediate consistency is a hard requirement — approximate speed-layer answers, even briefly, are unacceptable
  • Data volume is small enough that a single stream or batch job alone is fast enough — the extra layer adds pure complexity
💡 Hierarchy

Batch-only (correct, high latency) vs Streaming-only (low latency, no self-healing) vs Lambda (both, at the cost of two codebases) vs Kappa (low latency and self-healing via log replay, one codebase — but requires the stream engine to reprocess efficiently at full historical scale).

# ── BATCH LAYER: runs periodically (e.g. every hour) ──
def batch_job(master_dataset):
# Recompute EVERYTHING from the raw immutable log — always correct
batch_views = full_recompute(master_dataset)
serving_db.write(batch_views, layer="batch")
return batch_views.boundary_timestamp
# ── SPEED LAYER: runs continuously, per-event ──
def speed_job(event_stream, last_batch_boundary):
running_view = ApproxCounter() # e.g. HyperLogLog, Count-Min Sketch
for event in event_stream.since(last_batch_boundary):
running_view.update(event) # O(1) incremental update
serving_db.write(running_view, layer="speed")
return running_view
# ── SERVING LAYER: answers ad-hoc queries ──
def query(q, serving_db):
batch_result = q(serving_db.batch_views)
speed_result = q(serving_db.speed_views)
return merge(batch_result, speed_result) # sum / union / max
# ── SELF-HEALING: fires when a batch cycle completes ──
def on_batch_complete(new_boundary):
serving_db.batch_views = batch_job(master_dataset)
serving_db.speed_views.reset(since=new_boundary) # discard stale approx
