Mapping raw sensors directly toward driving decisions — versus the classic modular pipeline

1
Understanding End-to-End Driving
▼

What is it? The classic self-driving stack is modular: cameras/LiDAR feed a perception module (detect cars, pedestrians, lanes), whose output feeds a prediction module (forecast where other agents will move), whose output feeds a planning module (compute a safe ego trajectory), whose output feeds a control module (steering/throttle/brake commands). Each stage is built and trained separately against its own hand-picked proxy metric — detection mAP, tracking IDF1, trajectory ADE — none of which is the thing we actually care about: safe, comfortable, efficient driving. End-to-end learning instead learns a single differentiable function (or a jointly-optimized set of modules) that maps raw sensor input directly toward the control or planning objective, trained so that every parameter is pushed by gradients that trace back to actual driving performance.

Analogy: The modular pipeline is like a relay race where each runner (module) is graded individually on their own stopwatch split, not on whether the team wins the race. A runner can post a great split and still hand off the baton badly. End-to-end learning grades the whole team on whether they win — every runner's training signal comes from the final outcome.

💡 If you remember one thing

A modular pipeline optimizes each stage against a local proxy loss and hopes the composition is good; end-to-end learning optimizes (some or all) stages jointly against the actual driving objective. Formally, a policy \(\pi_\theta\) maps observations to actions: $$a_t = \pi_\theta(o_t), \qquad o_t = \text{camera/LiDAR at time } t$$ trained to imitate expert driving or to directly minimize a planning cost.

How It Works Internally
▼

The Problem with the Modular Pipeline

Each interface between modules is a hand-designed, lossy bottleneck: perception outputs a list of bounding boxes, prediction outputs a handful of trajectory hypotheses, planning outputs a discretized path. Information that doesn't fit the interface (e.g. a pedestrian's subtle body language, uncertainty about an occluded lane) is thrown away before the next module ever sees it. Because each module is trained against its own proxy loss, a "locally optimal" detector or predictor can still be globally harmful — e.g. a detector tuned for high recall on cars may produce noisy boxes that confuse the planner, even though its mAP score looks great in isolation.

NVIDIA PilotNet: The Original End-to-End Baseline

PilotNet (Bojarski et al., 2016) is the canonical minimal end-to-end system: a single convolutional network takes a raw front-camera image and outputs one number — the steering angle. It has 5 convolutional layers followed by 3 fully-connected layers, trained with behavior cloning: minimize the mean-squared error between the network's predicted steering angle and the angle a human driver actually applied at that instant. No explicit lane detector, no object list, no planner — the network implicitly discovers useful internal representations (later shown via saliency maps to correlate with lane edges and other vehicles) purely because they help predict steering.

Design Decision: Full Black Box vs Planning-Oriented Joint Training

Modern differentiable stacks (e.g. UniAD, 2023) take a middle path: they keep interpretable intermediate modules — a bird's-eye-view (BEV) feature encoder, multi-object tracking, online mapping, motion forecasting, occupancy prediction — but make every one of them differentiable and train them jointly, with the planning loss as the primary signal. Gradients from the planning head flow backward through occupancy, motion, mapping, and tracking, so each upstream module is shaped by "does this help the car plan well," not just "does this match my isolated proxy label." This is called planning-oriented end-to-end design: it keeps the interpretability of module outputs while removing the misalignment between per-module objectives and the true driving objective.

🔑 Key Property

Full black-box end-to-end (PilotNet-style) maximizes optimization alignment but sacrifices interpretability and unit-testability. Planning-oriented joint training (UniAD-style) keeps interpretable intermediates and aligns their gradients with the planning objective — it is a differentiable modular pipeline, not a modular-vs-end-to-end binary choice.

3
Why It's Hard — Imitation Learning & Distribution Shift
▼

Behavior Cloning as Supervised Learning

Given a dataset of expert demonstrations \(\mathcal{D} = \{(o_i, a_i)\}_{i=1}^N\) (observation, expert action pairs logged from human driving), behavior cloning fits:

$$\theta^\star = \arg\min_\theta \; \frac{1}{N}\sum_{i=1}^{N} L\big(\pi_\theta(o_i), a_i\big)$$

This is ordinary supervised regression (PilotNet uses MSE on steering angle). It works well when the network only ever needs to act at states drawn from the same distribution as the training data.

The Core Failure Mode: Covariate / Distribution Shift

The expert's demonstrations were collected under the expert's own driving policy, so they only cover the state distribution \(d_{\pi^\star}(o)\) that a good driver visits. Once the learned policy \(\pi_\theta\) drives itself, its small per-step errors push it into states the expert rarely visited — the policy is now evaluated under its own induced distribution \(d_{\pi_\theta}(o) \neq d_{\pi^\star}(o)\), where it has little training signal and often no idea how to recover.

$$\mathbb{E}\big[\text{trajectory deviation at horizon } T\big] = O(\epsilon T^2) \quad \text{(compounding error, Ross \& Bagnell)}$$

where \(\epsilon\) is the per-step probability of a mistake. Errors compound quadratically because a mistake pushes the car into an off-distribution state, which makes the next action even more likely to be wrong — a positive feedback loop that pure behavior cloning has no mechanism to break. DAgger (Dataset Aggregation) addresses this by iteratively rolling out the current policy, querying the expert for the correct action at the states the policy actually visits (including its own mistakes), and retraining on the aggregated dataset — closing the gap between train-time and test-time state distributions.

Causal Confusion

A second, subtler failure: behavior cloning only matches correlations in the demonstration data, not causation. A well-known example is a network that learns to predict "brake" almost perfectly from its own past braking/indicator signals (a nuisance correlate of the true cause) rather than from the actual causal trigger (a pedestrian or lead-car brake light) — it gets excellent open-loop accuracy yet fails in closed loop because the spurious cue isn't available, or is misleading, once the policy is actually driving.

⚠️ Common Pitfall

A model can achieve near-zero open-loop imitation loss and still crash in closed-loop deployment. Low training loss on logged expert actions says nothing about behavior under compounding error or spurious-cue reliance — you must evaluate the actual rollout, not just the single-step prediction.

Key Takeaways
▼

When end-to-end / joint training helps:

  • Large fleets of demonstration data are available, so the policy sees a wide state distribution
  • Hand-crafted module interfaces are known to bottleneck information (e.g. discretized detections losing subtle cues)
  • You can align every module's gradient with the true driving objective (planning-oriented training) rather than isolated proxy losses
  • The deployment domain is close enough to the training distribution that distribution shift is manageable, or DAgger-style online correction is available

When the modular pipeline is still preferred:

  • Safety certification and regulatory audits require inspectable, unit-testable intermediate outputs
  • You need to diagnose why a failure happened (was it perception, prediction, or planning?) — a black box gives no such breakdown
  • Formal verification or rule-based safety layers must wrap the planner's output
  • Training data is scarce or narrow, so joint end-to-end optimization would overfit / hallucinate shortcuts (causal confusion)

Open-loop vs closed-loop evaluation:

  • Open-loop: compare the policy's predicted action to the logged human action on a fixed dataset — cheap, reproducible, but blind to compounding error and gameable by trivial policies (e.g. "always go straight" scores well on mostly-straight roads)
  • Closed-loop: feed the policy's own actions back into the simulation/environment and measure collision rate, route completion, comfort — the real test of driving competence, but expensive and less reproducible
  • Open-loop and closed-loop rankings frequently disagree — always validate with closed-loop rollouts before trusting an open-loop leaderboard
💡 Hierarchy

Modular pipeline (independent proxy losses) ⊂ Planning-oriented end-to-end (interpretable modules, jointly optimized gradients) ⊂ Full black-box end-to-end (single differentiable function, pixels to control). Each step trades interpretability for tighter alignment with the true driving objective.
