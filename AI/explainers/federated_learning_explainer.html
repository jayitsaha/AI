Understanding Federated Learning
▼

What is it? Federated Learning (FL) is a distributed machine learning paradigm that enables training a shared global model across multiple decentralized edge devices (clients) holding local data samples, without explicitly exchanging their data. Instead, clients download the current global model, train it locally on their private data, and then send only model updates (e.g., gradients or new weights) back to a central server for aggregation.

Analogy: Imagine a group of chefs (clients) each with their own secret spice blend (private data). A master chef (server) wants to create a "universal" dish. Instead of sharing their secret spices, each chef takes the master's base recipe, adapts it slightly using their own spices, and then sends back only the *changes* they made to the recipe. The master chef then combines all these changes to refine the universal recipe, never seeing any individual chef's secret spices. This process repeats until the universal recipe is perfected.

💡 If you remember one thing

Federated Learning trains a single global model by orchestrating local training on private client data. The raw data never leaves the client device; only model updates are communicated. This provides strong privacy guarantees and enables learning from vast, distributed datasets.

How It Works Internally
▼

The Federated Learning Round

Federated learning operates in synchronous "rounds" orchestrated by a central server. Each round typically involves these steps:

  1. Initialization: The server initializes a global model \(w^0\).
  2. Selection: The server selects a subset of available clients \(S_t\) for the current round \(t\).
  3. Broadcast: The server sends the current global model \(w^t\) to all selected clients.
  4. Local Training: Each client \(k \in S_t\) trains the received model \(w^t\) on its local dataset \(D_k\). This typically involves several steps of Stochastic Gradient Descent (SGD) to produce an updated local model \(w_k^{t+1}\).
  5. Upload: Clients send their updated local models (or the difference \(w_k^{t+1} - w^t\)) back to the server.
  6. Aggregation: The server aggregates the received updates from all clients in \(S_t\) to compute a new global model \(w^{t+1}\). The most common aggregation method is Federated Averaging (FedAvg).
  7. Repeat: Steps 2-6 are repeated for many rounds until the global model converges or a maximum number of rounds is reached.

Federated Averaging (FedAvg)

Proposed by McMahan et al. (2017), FedAvg is the most widely used aggregation algorithm. After clients train their local models \(w_k^{t+1}\), the server computes the new global model \(w^{t+1}\) as a weighted average of the client models:

$$w^{t+1} = \sum_{k=1}^{K} \frac{n_k}{N} w_k^{t+1}$$

where \(n_k\) is the number of data samples on client \(k\), \(N = \sum_{k=1}^{K} n_k\) is the total number of samples across all clients, and \(K\) is the total number of clients (or the number of participating clients in the current round). This weighting ensures that clients with more data contribute proportionally more to the global model.

Challenges: Non-IID Data and Client Drift

A major challenge in FL is that client data distributions are typically non-IID (non-independent and identically distributed). For example, a mobile phone might mostly contain photos of its owner, or a hospital might specialize in a certain type of patient data. When clients train on highly non-IID data, their local models \(w_k^{t+1}\) can diverge significantly from the global objective, leading to "client drift." This drift can slow down convergence or even cause the global model to oscillate or converge to a suboptimal solution.

🔑 Key Property

The core idea of FL is "bringing the code to the data, not the data to the code." This fundamental shift enables privacy by design, but introduces new algorithmic and systems challenges, particularly around communication efficiency and handling heterogeneous client data.

Why It Works — The Math & FedProx
▼

Global Objective & Local Optimization

The overarching goal in federated learning is to minimize a global loss function \(F(w)\), which is typically a weighted average of the local loss functions \(F_k(w)\) across all clients:

$$F(w) = \sum_{k=1}^K \frac{n_k}{N} F_k(w) = \sum_{k=1}^K \frac{n_k}{N} \left( \frac{1}{n_k} \sum_{(x,y) \in D_k} \ell(w; x, y) \right)$$

where \(\ell(w; x, y)\) is the loss of the model \(w\) on a single data point \((x,y)\). FedAvg achieves this by having each client optimize its local loss \(F_k(w)\) and then averaging the resulting models. However, on non-IID data, optimizing \(F_k(w)\) locally can lead to \(w_k^{t+1}\) values that are far from the global optimum.

FedProx: Mitigating Client Drift with a Proximal Term

To address client drift, FedProx (Li et al., 2020) modifies the local optimization objective for each client \(k\) in round \(t\). Instead of minimizing just \(F_k(w)\), clients minimize a regularized version that penalizes divergence from the current global model \(w^t\):

$$\min_{w} \left( F_k(w) + \frac{\mu}{2} \|w - w^t\|^2 \right)$$

Here, \(\mu \ge 0\) is the proximal term coefficient. The term \(\frac{\mu}{2} \|w - w^t\|^2\) acts as a regularization, encouraging the local model \(w\) to stay "close" to the global model \(w^t\) that it received from the server. A larger \(\mu\) enforces stronger regularization, pulling local models closer to \(w^t\) and reducing drift, but potentially slowing down local learning. When \(\mu = 0\), FedProx reduces to standard FedAvg.

Communication Efficiency

Communication is often the bottleneck in FL, especially with many clients or large models. Techniques to improve efficiency include:

  • Sparsification: Sending only a subset of the most important weights or gradients.
  • Quantization: Reducing the precision of model updates (e.g., from 32-bit floats to 8-bit integers).
  • Compression: Using various encoding schemes to reduce message size.

These methods aim to reduce the total number of bits transmitted per round without significantly degrading model performance.

⚠️ Common Pitfall

While FL offers strong privacy, it's not foolproof. Sophisticated attacks (e.g., gradient inversion, membership inference) can sometimes reconstruct client data or infer sensitive information from shared model updates. Differential Privacy (DP) mechanisms are often combined with FL to provide stronger, mathematically provable privacy guarantees, usually at the cost of some model utility.

Key Takeaways
▼

When to use Federated Learning:

  • Privacy-sensitive data: When data cannot be centralized due to regulations (GDPR, HIPAA) or proprietary concerns.
  • Distributed data: When data naturally resides on edge devices (smartphones, IoT devices, hospitals) and is too large or costly to move.
  • Learning from diverse sources: To build a robust global model that generalizes across various client populations.
  • Communication constraints: When bandwidth is limited, FL's focus on sending small model updates (instead of raw data) is advantageous.

When NOT to use / Challenges:

  • IID data: If data is already IID and can be centralized, traditional distributed training is often simpler and faster.
  • High communication frequency: If many communication rounds are needed, even small updates can add up.
  • Highly heterogeneous models: If clients require vastly different model architectures, standard aggregation becomes difficult.
  • Client reliability: Dealing with unreliable clients (dropping out, sending malicious updates) adds complexity.
💡 Big Picture

Federated Learning is not a single algorithm, but a paradigm. FedAvg and FedProx are just two examples of aggregation and local optimization strategies. The field is actively researching new methods to improve convergence, robustness, and privacy under increasingly complex real-world constraints.

import torch
import torch.nn as nn
import torch.optim as optim
# Assume 'model_global' is the server's current model
# 'client_datasets' is a list of DataLoaders, one for each client
# 'config' contains learning_rate, local_epochs, mu, etc.
def client_update(model, dataloader, global_weights_t, mu):
model.train()
optimizer = optim.SGD(model.parameters(), lr=config.learning_rate)
# Store initial global weights for proximal term
global_model_param_list = [p.data.clone() for p in global_weights_t]
for epoch in range(config.local_epochs):
for batch_idx, (data, target) in enumerate(dataloader):
optimizer.zero_grad()
output = model(data)
loss = nn.CrossEntropyLoss()(output, target)
# FedProx proximal term
if mu > 0:
proximal_term = 0.0
for local_param, global_param in zip(model.parameters(), global_model_param_list):
proximal_term += torch.norm(local_param - global_param, 2) ** 2
loss += (mu / 2.0) * proximal_term
loss.backward()
optimizer.step()
return model.state_dict() # Return updated local model weights
def server_aggregate(global_model, client_models_states, client_data_sizes):
global_weights = global_model.state_dict()
total_data_size = sum(client_data_sizes)
# Initialize new global weights to zeros
new_global_weights = {key: torch.zeros_like(global_weights[key]) for key in global_weights}
# Weighted average of client models
for client_state, client_n_k in zip(client_models_states, client_data_sizes):
for key in new_global_weights:
new_global_weights[key] += client_state[key] * (client_n_k / total_data_size)
global_model.load_state_dict(new_global_weights) # Update global model
return global_model
# --- Federated Training Loop ---
for round_t in range(config.num_rounds):
# Server selects clients (e.g., all clients for simplicity)
selected_clients_indices = list(range(len(client_datasets)))
client_models_states = []
client_n_ks = []
# Get current global weights for proximal term and client model initialization
global_weights_t = [p.data.clone() for p in model_global.parameters()]
for client_idx in selected_clients_indices:
local_model = type(model_global)() # Instantiate a fresh local model
local_model.load_state_dict(model_global.state_dict()) # Initialize with global weights
updated_local_state = client_update(
local_model, client_datasets[client_idx], global_weights_t, config.mu
)
client_models_states.append(updated_local_state)
client_n_ks.append(len(client_datasets[client_idx].dataset))
model_global = server_aggregate(model_global, client_models_states, client_n_ks)
