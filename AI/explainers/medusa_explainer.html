Medusa: Parallel Decoding Heads

Accelerating LLM inference by predicting multiple future tokens in parallel
Intermediate Deep Learning Inference Optimization ~2-4x speedup
1
Understanding Medusa
▼

What is it? Medusa is an inference acceleration technique for large language models (LLMs). Instead of generating one token at a time sequentially, it attaches multiple small "decoding heads" to the main LLM's hidden states. These heads predict tokens at different future positions (e.g., +1, +2, +3 tokens ahead) in parallel. This allows for a "tree-style" or "speculative" decoding process where several tokens are proposed and verified by the main LLM in a single batch forward pass, significantly speeding up text generation.

Analogy: Imagine a master author (the main LLM) writing a novel. Normally, they write one word, then the next, and so on. With Medusa, the master author has a team of junior editors (the Medusa heads). After the master writes a word, the junior editors immediately suggest the next few words, and even the words after that, all at once. The master then quickly reviews all these suggestions in a single glance, accepting the good ones and discarding the bad. This way, the master can write many words in the time it would normally take to write just one, without sacrificing quality.

💡 If you remember one thing

Medusa leverages auxiliary, lightweight prediction heads (MLPs) to propose multiple future tokens in parallel from a single main model hidden state. These proposed sequences are then efficiently verified by the main LLM in a single batch, effectively converting sequential token generation into a parallel process to reduce inference latency.

2
How Medusa Works Internally
▼

The Core Mechanism: Parallel Prediction & Speculative Verification

Medusa enhances standard LLM inference by adding a "drafting" step. Here's the typical flow:

  1. Main LLM Generation: The large language model performs a forward pass on the current input sequence to generate the next token, let's call it \(t_0\). It also produces its hidden states for this position.
  2. Parallel Medusa Predictions: Instead of immediately feeding \(t_0\) back into the main LLM, the Medusa heads come into play. These are small, independently trained Multi-Layer Perceptrons (MLPs) attached to the main LLM's hidden states. Each head \(h_k\) is trained to predict the token at position \(k\) steps ahead (e.g., \(t_1, t_2, t_3\)) *conditioned on the hidden state that produced \(t_0\)*. This is the key parallel step.
  3. Candidate Tree Construction: The generated \(t_0\) and the parallel predictions from Medusa heads (e.g., \(h_1 \to t_1', h_2 \to t_2', h_3 \to t_3'\)) form a "tree" of candidate sequences. For instance, paths like \((t_0, t_1', t_2')\) or \((t_0, t_1', t_2', t_3')\) are constructed.
  4. Batch Verification by Main LLM: All these candidate sequences (or a subset, depending on the tree structure) are then concatenated and fed into the main LLM in a single batch. The main LLM performs a forward pass to re-evaluate the probabilities of each token in the proposed sequences. This is the "speculative verification" step.
  5. Acceptance & Rejection: Each proposed token \(t_k'\) in a candidate sequence is compared against the main LLM's own probability distribution for that position. If the main LLM "agrees" (e.g., its probability for \(t_k'\) is high enough, often a simple equality check is used), the token is accepted. If not, the sequence is truncated at that point, and the remaining tokens in that branch are rejected.
  6. Commit & Iterate: All accepted tokens form the new suffix of the generated sequence. The process then repeats from step 1 with the extended context.

Design Decision: Why Small Heads and Not Just a Deeper Main Model?

The Medusa heads are intentionally small (e.g., single-layer MLPs). They are fast to compute and add minimal overhead. If the main LLM itself were to predict multiple tokens ahead, it would require multiple sequential forward passes, negating the speedup. The small heads are essentially "drafting models" that are cheap to run. Their role is to generate plausible candidates that the powerful main LLM can then verify quickly in parallel, rather than doing the heavy lifting of prediction themselves.

🔑 Key Property

Medusa's efficiency comes from decoupling the *proposal* of future tokens (cheap Medusa heads) from their *verification* (expensive main LLM). The verification is amortized over multiple proposed tokens by batching, turning sequential generation into a more parallel process without altering the main model's final output distribution.

Why It Works — The Math
▼

Probabilistic Formulation of Medusa Heads

A standard LLM generates tokens sequentially, predicting \(t_{i+1}\) based on the context up to \(t_i\):

$$P_{\text{main}}(t_{i+1} | t_0, \dots, t_i)$$

Medusa heads, on the other hand, are trained to predict tokens at future positions \(k\) steps ahead, using the hidden state \(h_i\) from the main model after processing \(t_i\):

$$P_{\text{head}_k}(t_{i+k} | h_i)$$

During inference, the Medusa heads are used to construct a draft sequence \(t_0, t_1', \dots, t_N'\), where \(t_0\) is from the main model and \(t_k'\) are from head \(h_k\). The core idea is that even though \(t_k'\) is predicted based only on \(h_i\) (and not on \(t_0, \dots, t_{i+k-1}\)), it often provides a good enough guess to be verified.

Speculative Decoding (Verification) Algorithm

The true power of Medusa comes from its integration with speculative decoding. Given a draft sequence \(x_0, x_1, \dots, x_N\) (where \(x_0\) is the main LLM's prediction and \(x_1, \dots, x_N\) are from Medusa heads), the main LLM verifies it. For each proposed token \(x_k\), the main model calculates its probability given the prefix:

$$P_{\text{main}}(x_k | x_0, \dots, x_{k-1})$$

Let \(P_{\text{draft}}(x_k | x_0, \dots, x_{k-1})\) be the probability assigned by the Medusa heads (or combined draft distribution) to \(x_k\). A token \(x_k\) is accepted if it passes a statistical test. A common (and simple) acceptance rule is to accept \(x_k\) if \(P_{\text{main}}(x_k | x_0, \dots, x_{k-1}) \ge P_{\text{draft}}(x_k | x_0, \dots, x_{k-1})\). This ensures that the generated sequence maintains the exact distribution of the original main LLM, just faster.

If a token \(x_k\) is rejected, the process stops at \(x_{k-1}\), and a new token is sampled from \(P_{\text{main}}(t | x_0, \dots, x_{k-1})\). This ensures that the final output sequence is always sampled exactly from the main LLM's distribution, making it a "lossless" acceleration.

⚠️ Common Pitfall

The effectiveness of Medusa heavily relies on the quality of the Medusa head predictions. If the heads frequently propose incorrect tokens, the verification step will often lead to rejections, forcing the process to backtrack and nullifying the speedup. Careful training of the Medusa heads to align with the main model's probabilities is crucial.

Key Takeaways
▼

When to use Medusa:

  • When LLM inference speed is a critical bottleneck, especially for real-time applications or long generations.
  • For models that are already well-trained, as Medusa heads can be fine-tuned on top without retraining the entire LLM.
  • In scenarios where the underlying hardware (e.g., GPUs with Tensor Cores) benefits significantly from batched matrix multiplications.

When NOT to use:

  • For very small models where the overhead of additional heads and speculative decoding logic might negate the benefits.
  • If the quality of Medusa head predictions is consistently poor, leading to frequent rejections and no effective speedup.
  • In highly constrained environments where every parameter counts, as Medusa adds a small number of extra parameters.
💡 Big Picture

Medusa is a powerful example of how architectural modifications and clever algorithmic design (speculative decoding) can dramatically improve the efficiency of large, computationally intensive models without sacrificing output quality. It highlights the importance of parallelization in modern deep learning systems.

Code Trace (PyTorch-like Pseudocode)
▼
import torch.nn as nn
import torch
class MedusaHead(nn.Module):
def __init__(self, hidden_size, vocab_size):
super().__init__()
self.mlp = nn.Sequential(
nn.Linear(hidden_size, hidden_size),
nn.ReLU(),
nn.Linear(hidden_size, vocab_size)
)
def forward(self, hidden_state):
return self.mlp(hidden_state) # logits for next token
class MedusaModel(nn.Module):
def __init__(self, main_llm, num_heads, hidden_size, vocab_size):
super().__init__()
self.main_llm = main_llm
self.medusa_heads = nn.ModuleList([
MedusaHead(hidden_size, vocab_size) for _ in range(num_heads)
])
self.num_heads = num_heads
def train_step(self, input_ids, labels):
# Normal LLM forward pass to get hidden states and main logits
main_output = self.main_llm(input_ids)
main_logits = main_output.logits # P_main(t_0 | context)
hidden_state = main_output.hidden_states[-1] # last layer hidden state
# Medusa heads predict future tokens in parallel
head_logits = [head(hidden_state) for head in self.medusa_heads] # P_head_k(t_k | h_0)
# Compute loss for main LLM and Medusa heads
main_loss = F.cross_entropy(main_logits, labels[:, 0])
medusa_losses = [F.cross_entropy(hl, labels[:, k+1]) for k, hl in enumerate(head_logits)]
total_loss = main_loss + sum(medusa_losses)
total_loss.backward()
# optimizer.step() etc.
def generate(self, input_ids, max_new_tokens, threshold=0.7):
generated_tokens = []
current_input = input_ids
for _ in range(max_new_tokens):
# 1. Main LLM generates t_0 and hidden state
with torch.no_grad():
main_output = self.main_llm(current_input)
main_logits = main_output.logits[:, -1, :]
t0 = torch.argmax(main_logits, dim=-1) # Greedy for simplicity
hidden_state = main_output.hidden_states[-1][:, -1, :]
# 2. Medusa heads predict t_1', t_2', ... in parallel
draft_logits = [head(hidden_state) for head in self.medusa_heads]
draft_tokens = [torch.argmax(dl, dim=-1) for dl in draft_logits]
# 3. Form candidate sequence (simple linear for demo)
candidate_seq = torch.cat([t0.unsqueeze(0)] + [dt.unsqueeze(0) for dt in draft_tokens], dim=0)
# 4. Batch verification by main LLM
# This requires feeding (current_input + candidate_seq) into main_llm
# For simplicity, assume we get probabilities P_main(t_k | prefix)
verified_probs = self.main_llm.get_probs(current_input, candidate_seq) # conceptual API
draft_probs = [F.softmax(dl, dim=-1)[0, dt] for dl, dt in zip(draft_logits, draft_tokens)]
draft_probs = [F.softmax(main_logits, dim=-1)[0, t0]] + draft_probs
accepted_count = 0
for k in range(len(candidate_seq)):
if verified_probs[k] >= draft_probs[k] * threshold:
accepted_count += 1
else:
break # Reject remaining tokens in this branch
# 5. Commit accepted tokens
if accepted_count > 0:
new_tokens = candidate_seq[:accepted_count]
generated_tokens.extend(new_tokens.tolist())
current_input = torch.cat([current_input, new_tokens.unsqueeze(0)], dim=1)
else: # Fallback: if t0 itself is rejected (rare), resample from main_logits
resampled_t0 = torch.multinomial(F.softmax(main_logits, dim=-1), num_samples=1)
generated_tokens.append(resampled_t0.item())
current_input = torch.cat([current_input, resampled_t0], dim=1)
return generated_tokens
