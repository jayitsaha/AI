Why yesterday's model and yesterday's features lose to a stream that never stops

1
Understanding Real-Time Recommendation
▼

What is it? A classic recommender pipeline retrains on yesterday's logs in a nightly batch job, computes item/user features from that same snapshot, and serves the resulting model unchanged for the next 24 hours. A real-time recommender instead keeps two things alive continuously: feature freshness (item and user signals recomputed the instant new events arrive) and online learning (model weights nudged by every new labeled interaction via streaming gradient steps). Both close the gap between "what is happening right now" and "what the model believes."

Analogy: A batch recommender is like a newspaper — accurate as of last night's print run, but blind to anything that happened this morning. A real-time recommender is a live news ticker: every click, view, or purchase updates the picture within milliseconds, so a video that goes viral at 9am can be surfaced by 9:02am instead of waiting for tomorrow's paper.

💡 If you remember one thing

Two independent clocks matter: how fresh the input features are, and how fresh the model weights are. A system can have a perfectly fresh feature store feeding a stale model, or fresh weights reading stale features — both leak accuracy. Real-time recommendation means keeping both clocks close to zero: $$\text{staleness}(t) = t - t_{\text{last update}}$$

How It Works Internally
▼

The Batch Baseline and Its Blind Spot

A nightly Spark/Hive job aggregates the previous day's logs, computes features like item popularity, category CTR, and user embeddings, and trains a ranking model \(w_{batch}\) via full-batch or mini-batch gradient descent over millions of examples. Both the features and \(w_{batch}\) are then frozen and served all day through an offline feature store and a static model artifact — accurate at midnight, increasingly wrong by evening.

Feature Freshness: A Streaming Feature Store

A real-time feature pipeline (Kafka/Flink/Kinesis + a low-latency key-value store) consumes the event stream and updates per-item statistics incrementally — e.g. an exponential moving average of the click rate — the instant an event lands. But even streaming features go stale between events: freshness itself decays, so serving must discount an old live value back toward a safe prior the longer it has been since the last update.

Online Learning: One Gradient Step per Event

Instead of waiting for the nightly retrain, an online learner treats every labeled interaction (impression → click/no-click) as a single training example and takes one stochastic gradient descent (SGD) step immediately. Weights drift continuously toward the current data distribution rather than jumping once a day. In practice the online model is usually warm-started from the last batch model, so it inherits stable priors and only has to correct for what changed since training.

🔑 Key Design Decision

Freshness and learning are orthogonal knobs. You can serve fresh features into a stale model (better than nothing, but weights don't know the new regime exists) or serve stale features into freshly-updated weights (weights are current but starved of the signal that would let them act on it). Real gains come from freshening both in lockstep.

Why It Works — The Math
▼

Freshness Decay

Model a feature's "trustworthiness" as an exponentially decaying confidence since its last real update at \(t_{\text{last}}\):

$$\text{freshness}(t) = e^{-\lambda (t - t_{\text{last}})}, \qquad \lambda > 0 \text{ (decay rate)}$$

At serving time, blend the live streamed value \(x_{\text{live}}\) with a stale prior/batch value \(x_{\text{batch}}\) using this confidence as a mixing weight:

$$\hat{x}(t) = \text{freshness}(t)\cdot x_{\text{live}} + \big(1-\text{freshness}(t)\big)\cdot x_{\text{batch}}$$

Right after an event, \(\text{freshness}\approx 1\) and the estimate trusts the live signal fully; as time passes with no new events, it decays smoothly back to the safe batch prior — this guards against acting on a value that is itself now out of date.

Online SGD Update

For a logistic click model \(\hat p = \sigma(w^\top x)\) with \(\sigma(z) = 1/(1+e^{-z})\), each new labeled event \((x_i, y_i)\) triggers one gradient step on the cross-entropy loss \(\mathcal{L}(w) = -[y_i\log \hat p_i + (1-y_i)\log(1-\hat p_i)]\):

$$w \leftarrow w - \eta\,(\sigma(w^\top x_i) - y_i)\, x_i$$

Because \((\sigma(w^\top x_i)-y_i)\) is exactly the prediction error, this update nudges \(w\) toward reducing that single example's loss — no need to wait for a full epoch over the whole dataset.

Regret: The Formal Goal of Online Learning

$$R_T = \sum_{i=1}^{T} \mathcal{L}_i(w_i) \;-\; \min_{w} \sum_{i=1}^{T} \mathcal{L}_i(w)$$

Online learning aims to keep cumulative regret \(R_T\) sublinear in \(T\) — i.e. the running average loss of the online sequence of weights approaches that of the best fixed weight vector in hindsight, without ever seeing the future.

⚠️ Common Pitfall

A single noisy or adversarial event can swing \(w\) too far with an aggressive learning rate \(\eta\) — this is the online-learning analogue of overfitting, sometimes called "one-example whiplash." It also creates feedback loops: if the model instantly promotes whatever gets an early click, it can manufacture its own popularity signal. Production systems clip gradients, use per-feature adaptive rates (e.g. FTRL, Adagrad), and often hold out a fraction of traffic for unbiased evaluation.

Key Takeaways
▼

When real-time features + online learning pay off:

  • Fast-moving inventory: news, live commerce, trending video/audio, breaking events
  • Cold items with almost no historical signal — a handful of live events beat a frozen prior
  • Short session windows where next-item relevance shifts within minutes (session-based recs)
  • High-value moments where a few hours of staleness is directly measurable in lost engagement/revenue

When batch is good enough (or even safer):

  • Stable catalogs where item relevance barely changes day to day
  • Low event volume — online SGD on sparse, noisy signals can thrash more than it helps
  • Strict auditability/reproducibility requirements — a frozen nightly model is easier to test, roll back, and explain
  • Feedback-loop risk is high and there is no safeguard against the model reinforcing its own early predictions
💡 Hierarchy

Batch (features + weights frozen for a day) ⊂ Fresh features, static model (real-time feature store, nightly retrain) ⊂ Fully online (streaming features + per-event SGD). Most production systems land in the middle: a hybrid that blends a stable batch model with a lightweight online correction layer, exactly the freshness-weighted blend from Card 3.

import math
# --- streaming feature store: updated the instant an event lands ---
def on_event(event, feature_store, alpha=0.4):
est = feature_store.get(event.item_id, prior=0.2)
est += alpha * (event.clicked - est) # exponential moving average
feature_store.set(event.item_id, est, ts=event.t)
# --- freshness-aware read at serving time ---
def get_feature(item_id, now, feature_store, batch_snapshot, lam=0.18):
live_val, last_ts = feature_store.get_with_ts(item_id)
freshness = math.exp(-lam * (now - last_ts))
return freshness * live_val + (1 - freshness) * batch_snapshot[item_id]
# --- online learner: one SGD step per incoming labeled event ---
def sigmoid(z): return 1 / (1 + math.exp(-z))

p = sigmoid(w[0]*x + w[1])
grad = (p - event.clicked)
w[0] -= eta * grad * x
w[1] -= eta * grad
return w
