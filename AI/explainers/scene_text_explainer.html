Understanding the Concept
▾

What is this? Scene text recognition (STR) is the job of reading text that appears "in the wild" — on street signs, product packaging, license plates, storefronts — rather than in clean scanned documents. It is a two-stage pipeline: first a detector finds where the text is in the photo (drawing a box or polygon around it), then a recognizer reads what the characters inside that box actually say.

Analogy: Think of a tourist reading a foreign menu. First their eyes dart around the page to find blocks of text amid the decorations (detection). Then, for each block found, they focus in and sound out the letters one at a time (recognition). Scene text systems like PaddleOCR and EasyOCR automate exactly this two-step process, except the "eyes" are a segmentation network and the "sounding out" is a sequence model trained with a loss called CTC.

One-sentence summary: A detector (e.g. DBNet) segments text regions in an image, then a rectifier crops/unwarps each region into a horizontal strip that a recognizer (CNN + BiLSTM + CTC, or an attention decoder) converts into a character string.

If you remember one thing

Scene text is two different problems glued together — "where is text?" (a segmentation/detection problem) and "what does it say?" (a variable-length sequence labelling problem) — and the interface between them, the rectified crop, is where most real-world failures happen.

How It Works Internally
▾

Why this exists — historical context

Classical OCR (Tesseract-era, pre-2015) assumed clean, axis-aligned, high-contrast scanned documents with a fixed font and uniform lighting. It relied on connected-component analysis and template matching. Photos taken "in the wild" broke every one of those assumptions: text is rotated, curved, occluded, low-resolution, and sits on cluttered backgrounds. Deep detectors (EAST 2017, PSENet 2019, DBNet — Liao et al., AAAI 2020) and deep recognizers (CRNN — Shi et al., 2015; attention-based ASTER, 2018) replaced hand-crafted rules with learned segmentation and sequence models, which is what PaddleOCR (Baidu, 2020) and EasyOCR (JaidedAI, built on CRAFT + CRNN) package into production pipelines today.

The pipeline, stage by stage

  • Detection (DBNet / CRAFT): a fully-convolutional backbone (ResNet + FPN) predicts a per-pixel probability map \(P\) of "this pixel is inside text." A threshold map \(T\) is learned jointly, and a differentiable binarization step turns \(P\) into a sharp binary mask \(\hat B\) whose connected components are shrunk text polygons — these are dilated back out (Vatti clipping) to recover tight quadrilaterals or polygons around each text instance.
  • Perspective rectification: because scene text is rotated or on a curved surface, each detected polygon is warped with a perspective/thin-plate-spline transform into a canonical horizontal strip of fixed height (e.g. 32px) before recognition — this single step accounts for a large fraction of real-world recognition errors when it goes wrong.
  • Feature extraction (CNN): the rectified strip is passed through a convolutional stack (VGG-style in CRNN, MobileNetV3 in PaddleOCR-mobile) that collapses the height dimension, producing a sequence of \(T\) feature columns — one "time step" per horizontal slice of the strip.
  • Sequence modeling (BiLSTM): a bidirectional LSTM (or transformer encoder in newer models) contextualizes each column with its neighbors so the model can use surrounding-character context (e.g. distinguishing "l" from "I" using stroke width of nearby glyphs).
  • CTC decoding: a linear + softmax head produces a probability distribution over the character vocabulary (plus a special "blank" symbol) at every time step; Connectionist Temporal Classification collapses this per-timestep sequence into the final variable-length string without ever needing character-level box supervision.
Design decision — why CTC and not per-character boxes?

Annotating a bounding box for every individual character in every training image is prohibitively expensive. CTC only needs the transcript ("CAFE") and the crop, no character-level alignment — the loss marginalizes over every valid alignment automatically. This is the same trick used in speech recognition, where you don't know exactly which audio frame corresponds to which phoneme.

Why It Works — The CTC Alignment Trick
▾

The core guarantee CTC provides: given any per-timestep softmax output over a fixed vocabulary plus a blank symbol, there exists a well-defined, differentiable way to score how likely that output is to represent a target string of any shorter length — without knowing which timestep corresponds to which character.

Key invariant — the collapse function \(\mathcal{B}\)

Define \(\mathcal{B}\) on a raw per-timestep path \(\pi\) (length \(T\), the number of feature columns) by: (1) merge consecutive repeated symbols into one, then (2) remove all blank symbols. So \(\mathcal{B}(\text{"\_CC\_AFF\_E\_"}) = \text{"CAFE"}\). Many different raw paths \(\pi\) collapse to the same label string \(y\) — CTC sums the probability of every such path, so the network is free to place each character at any timestep and repeat it for as long as needed (e.g. a wide "F" occupying two feature columns).

This is why CTC-based recognizers are robust to characters of varying width — a slim "I" might occupy one feature column while a wide "W" occupies three, and the model just repeats the "W" prediction across those columns; the collapse function removes the redundancy automatically. The blank symbol is what lets the model separate two adjacent occurrences of the same letter (e.g. "LL" in "HELLO") — without it, repeated-then-merged would wrongly turn "LL" into "L".

The Math — Differentiable Binarization & CTC
▾

Differentiable binarization (detection)

DBNet predicts a probability map \(P\) and a threshold map \(T\), then instead of a hard, non-differentiable step function it uses a sigmoid-shaped approximation so the whole pipeline can be trained end-to-end with gradient descent:

$$\hat{B}_{i,j} = \frac{1}{1 + e^{-k\,(P_{i,j} - T_{i,j})}}$$

As the sharpness \(k\) (typically 50) grows, \(\hat B\) approaches a true binary mask, but because it stays smooth everywhere, \(\partial \hat B / \partial P\) is well-defined and gradients can flow back into the segmentation backbone during training.

CTC: path probability

Let the recognizer emit a matrix \(y \in \mathbb{R}^{T\times|V|}\) of softmax probabilities over a vocabulary \(V\) (characters + blank) across \(T\) timesteps. The probability of one specific raw alignment path \(\pi = (\pi_1,\dots,\pi_T)\) is the product of the per-timestep probabilities of picking that symbol:

$$p(\pi \mid x) = \prod_{t=1}^{T} y^t_{\pi_t}$$

The probability of the actual target label \(\ell\) (e.g. "CAFE") is the sum over every path that collapses to it:

$$p(\ell \mid x) = \sum_{\pi \,:\, \mathcal{B}(\pi)=\ell} p(\pi \mid x)$$

Enumerating all paths directly is exponential in \(T\), so CTC uses a forward-backward dynamic program over an extended label sequence \(\ell'\) (target with blanks inserted between and around every character). Define the forward variable \(\alpha_t(s)\) = total probability of all length-\(t\) prefixes that are consistent with the first \(s\) symbols of \(\ell'\):

$$\alpha_t(s) = \left(\alpha_{t-1}(s) + \alpha_{t-1}(s-1) + [\ell'_s \ne \ell'_{s-2}]\,\alpha_{t-1}(s-2)\right) \cdot y^t_{\ell'_s}$$

The final loss is the negative log-likelihood of the target sequence, computed in \(O(T\cdot|\ell'|)\) time instead of exponential time:

$$\mathcal{L}_{CTC} = -\log p(\ell \mid x) = -\log \sum_{s} \alpha_T(s)$$

Gradients \(\partial \mathcal{L}_{CTC}/\partial y^t_k\) are obtained by combining the forward pass \(\alpha\) with an analogous backward pass \(\beta\), giving every timestep credit proportional to how much it contributed across all valid alignments — this is exactly what lets the network learn where to place each character without ever being told explicitly.

Common misconception

"CTC decoding always finds the single most probable label sequence." In practice, greedy/argmax decoding (take the arg-max symbol at every timestep, then collapse) is only an approximation — the true most-probable label can require summing over multiple competing paths, which is why production systems often use beam search over the CTC lattice, not plain greedy decoding, when accuracy matters more than latency.

Takeaways

Scene text is a detect → rectify → recognize pipeline. The detector (DBNet/CRAFT) solves "where," using a smooth, differentiable approximation of binary segmentation so the whole network trains end-to-end. The recognizer (CRNN or attention) solves "what," using CTC to sidestep the need for character-level box labels by summing over every alignment that could have produced the target string. Most real-world failures live at the seam — imperfect rectification of curved/rotated text — which is why curved-text benchmarks (Total-Text, CTW1500) remain an active research area, and why attention-based decoders (which can look back at any position, not just left-to-right) are gradually displacing pure CTC in state-of-the-art systems.
