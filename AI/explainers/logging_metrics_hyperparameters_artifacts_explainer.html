Understanding Experiment Tracking
▼

What is it? Every training run produces three kinds of information worth keeping: the hyperparameters you chose (learning rate, batch size, dropout...), the metrics that unfold over time (loss, accuracy, per step or per epoch), and the artifacts it produces (saved model weights, plots, sample predictions). Experiment tracking is the discipline — and the tooling (MLflow, Weights & Biases, Comet, Neptune) — of recording all three automatically, so that any run can be inspected, reproduced, or compared months later.

Analogy: Think of a chemistry lab notebook. A careful scientist writes down the exact reagents and quantities before the reaction starts (hyperparameters), records the temperature every few minutes as the reaction proceeds (metrics), and staples in the resulting spectrograph printout at the end (artifact). Without that notebook, "the reaction that worked" is just a rumor. Experiment tracking is that notebook, kept automatically by code instead of by hand.

💡 If you remember one thing

Hyperparameters are logged once per run (they never change), metrics are logged repeatedly as a time series keyed by step, and artifacts are logged as files attached to the run. Together they let you answer: "which configuration produced the best model, and can I get that exact model back?" Formally, picking a winner is just $$\text{run}^\star=\underset{i}{\operatorname{arg\,max}}\; m_i(T)$$ where \(m_i(T)\) is a chosen metric for run \(i\) at final step \(T\).

How It Works Internally
▼

Three Logging Primitives

Every tracking library exposes roughly the same three calls, backed by a tracking server (a database + a file/object store):

  • log_param(key, value) — writes an immutable key-value pair to the run's metadata row. Called once, right after the config is parsed.
  • log_metric(key, value, step) — appends a row (run_id, key, step, value, timestamp) to an append-only metrics table. Called every training step or epoch — this is what produces the loss/accuracy curves.
  • log_artifact(path) — copies a file (checkpoint, plot, config dump) into an artifact store, keyed by run_id, and records a pointer to it.

Why Three Separate Storage Shapes?

Hyperparameters are low-cardinality and queried for filtering ("show me all runs with lr > 0.01") — a flat key-value table with indexes is enough. Metrics are high-cardinality time series (thousands of points per run) — they need a schema optimized for range scans over step. Artifacts are large binary blobs — they belong in object storage (S3, GCS, or a local disk cache), not a relational database. Using one data shape for all three would be either too slow for metrics or too wasteful for artifacts.

🔑 Key Property

Every run gets a unique, immutable run_id. Everything logged — params, every metric point, every artifact — is tagged with that id. This is what makes a run reconstructable: given only the id, you can pull back the exact config, the full training curve, and the exact binary weights that were produced.

3
Why It Works — Comparing Runs Rigorously
▼

A Run as a Point in Hyperparameter × Metric Space

Let each run \(i\) have a hyperparameter vector \(\theta_i = (\text{lr}_i, \text{batch}_i, \text{dropout}_i, \dots)\) and a logged metric trajectory \(m_i(t)\) for \(t = 0, \dots, T\). Experiment tracking turns a messy pile of training scripts into a clean table:

$$\mathcal{D} = \big\{\, (\theta_i,\; \{m_i(t)\}_{t=0}^{T},\; A_i) \;\big\}_{i=1}^{N}$$

where \(A_i\) is the set of artifacts for run \(i\). Once every run is a row in \(\mathcal{D}\), model selection becomes a simple query rather than a manual spreadsheet exercise:

$$\theta^\star = \theta_{i^\star}, \qquad i^\star = \underset{i \in \{1,\dots,N\}}{\operatorname{arg\,max}}\; m_i(T)$$

Because every \(\theta_i\) is logged with full precision and every \(m_i(t)\) is timestamped, this argmax is reproducible: two people running the same query against \(\mathcal{D}\) get the same \(\theta^\star\) — unlike eyeballing a shared spreadsheet of "run5_final_v2.csv".

Visual Search: Parallel Coordinates & Scatter

With \(k\) hyperparameters, the search space is \(k\)-dimensional and can't be plotted directly once \(k>3\). A parallel-coordinates plot sidesteps this: draw one vertical axis per hyperparameter (plus one for the metric), normalize each axis to \([0,1]\), and draw each run as a polyline connecting its values. Runs that consistently sit on the "good" side of every axis reveal a pattern (e.g., "every top run uses Adam and dropout ≥ 0.3") that a table of numbers would hide.

⚠️ Common Pitfall

Logging the final metric only (no time series) hides instability. A run with lr = 0.1 can spike mid-training and still land on a plausible final accuracy — without the full curve logged per step, you cannot tell "stable convergence" apart from "got lucky right before you stopped."

Key Takeaways
▼

When to reach for full experiment tracking:

  • Any hyperparameter sweep or ablation with more than a couple of runs
  • Collaborative projects, where "which run made this checkpoint?" must have a definite answer
  • Long training jobs where you need to detect divergence early from live curves
  • Regulated or production settings requiring lineage from a deployed model back to its training config and data

When it is overkill:

  • A single quick notebook experiment you will never revisit
  • Extremely tight prototyping loops where the tracking overhead outweighs the benefit — though most modern loggers add only milliseconds per call
💡 Tool Landscape

MLflow (self-hosted, framework-agnostic) · Weights & Biases (hosted, rich dashboards) · TensorBoard (lightweight, metrics-only, no artifact store) · Comet / Neptune (hosted alternatives). All three primitives — log_param, log_metric, log_artifact — appear under different names in every one of them.

import mlflow
for cfg in sweep_configs: # 4 hyperparameter configurations
with mlflow.start_run(run_name=cfg["name"]) as run:
# 1) Log hyperparameters ONCE, immediately
mlflow.log_param("lr", cfg["lr"])
mlflow.log_param("batch_size", cfg["batch"])
mlflow.log_param("dropout", cfg["dropout"])
mlflow.log_param("optimizer", cfg["optimizer"])
model = build_model(cfg)
for step in range(N_STEPS):
train_loss, val_loss, val_acc = train_one_step(model, cfg)
# 2) Log metrics EVERY step, keyed by step
mlflow.log_metric("val_loss", val_loss, step=step)
mlflow.log_metric("val_acc", val_acc, step=step)
# 3) Log artifacts once training is done
torch.save(model.state_dict(), "model.pt")
mlflow.log_artifact("model.pt")
mlflow.log_artifact("confusion_matrix.png")
mlflow.log_artifact("training_curves.png")
# 4) Query the tracking server to find the winner
best = mlflow.search_runs(order_by=["metrics.val_acc DESC"]).iloc[0]
print(best["run_id"], best["params.lr"], best["metrics.val_acc"])
