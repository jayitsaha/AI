Blue-Green Deployment & Canary Releases

Two strategies for shipping a new ML model to production without breaking it for everyone at once
Advanced MLOps Model Serving Zero-downtime rollout
1
Understanding the Two Strategies
▼

What is it? Both are strategies for shipping a new version of a service — or, in ML, a newly trained model — to production without breaking things for real users. Blue-green deployment keeps two identical, fully-scaled environments running: "blue" (the current live model) and "green" (the new model). Traffic is switched from blue to green in one atomic step once green passes its checks, and switched straight back if anything looks wrong. Canary release is more cautious: instead of an all-or-nothing switch, a small slice of real traffic — say 1% — is routed to the new model while the rest keeps hitting the old one. If live metrics stay healthy the slice is grown, 5% then 25% then 100%, and an automated gate pauses or rolls back the instant an error-rate or latency threshold is breached.

Analogy: Blue-green is like flipping a light switch between two identical rooms — the whole house is lit by one room or the other, never both, so if the new room's wiring is faulty, every occupant is instantly in the dark until you flip the switch back. Canary release is like slowly opening a door and letting a few people walk into the new room first: if they start coughing (the canary in the coal mine), you shut the door before the rest of the crowd ever goes in.

💡 If you remember one thing

Blue-green makes rollback instantaneous by keeping a full standby environment warm; canary makes a bad release survivable by only ever exposing a small, bounded fraction of traffic to it before an automated metric gate decides whether to promote or roll back.

2
How the Rollout Machinery Works Internally
▼

Blue-Green: Two Full Environments, One Switch

A load balancer, service mesh (Istio/Envoy), or DNS record holds a routing rule pointing 100% of traffic at "blue." The new model is deployed as "green" — a completely separate, fully-scaled fleet with its own feature pipeline, so it never competes with blue for resources. Green is smoke-tested with synthetic and shadow traffic while serving zero real users. Cutover is a single config change: the router's weight flips from {blue:100, green:0} to {blue:0, green:100} in one atomic write. Blue is kept warm (not torn down) for a rollback window — if error rate or latency regresses, the weight flips back to {blue:100, green:0} just as instantly.

Canary: Gradual Exposure With Automated Gates

The canary pool runs the new model alongside the untouched stable fleet. A controller (Argo Rollouts, Flagger, or a custom sidecar) advances traffic through a fixed schedule — 1% → 5% → 25% → 50% → 100% — pausing at each rung for a fixed "bake time." At every rung it queries live metrics: error rate, p95/p99 latency, and often ML-specific signals like prediction distribution drift or business KPIs (click-through, conversion). Each metric is checked against a gate (a hard threshold or a statistical test versus the stable baseline). If all gates pass, traffic advances to the next rung; if any gate fails, the controller automatically routes back to 0% canary traffic — no human has to notice and react.

🔑 Design Decision: Why Gradual Ramp Instead of a Straight A/B Split?

A/B testing holds a fixed split (e.g. 50/50) for the whole experiment to measure a business metric with statistical rigor. Canary release is a safety mechanism, not an experiment — the split is deliberately asymmetric and grows over time specifically to bound the blast radius while confidence in the new model increases. It borrows A/B's statistics for the gate decision, but its goal is risk containment, not measurement.

For ML specifically, both strategies must also keep the feature store and preprocessing code in lock-step between old and new: a model trained on features computed one way will silently misbehave if green/canary reads stale or differently-versioned features at serving time — this is a common source of canary "false positives" that have nothing to do with the model itself.

3
Why It Works — The Statistics of the Gate
▼

The promote/rollback decision at each canary rung is a live hypothesis test: is the canary's error rate meaningfully worse than the stable baseline, or is the difference just noise from a small sample? Let \(x_c\) errors occur out of \(n_c\) canary requests, and \(x_b\) errors out of \(n_b\) baseline requests, with observed rates \(\hat p_c = x_c/n_c\) and \(\hat p_b = x_b/n_b\).

Two-Proportion Z-Test

Under the null hypothesis that canary and baseline have the same true error rate, the pooled rate and test statistic are:

$$\hat p = \frac{x_c + x_b}{n_c + n_b}, \qquad z = \frac{\hat p_c - \hat p_b}{\sqrt{\hat p (1-\hat p)\left(\dfrac{1}{n_c} + \dfrac{1}{n_b}\right)}}$$

Reject the null (i.e. trigger rollback) when \(z\) exceeds a critical value such as \(z_{0.99} \approx 2.33\) for a one-sided 99% test — meaning the canary's error rate is significantly higher, not just randomly higher.

Numerical Trace (the spike you will see in Step 8)

At the 25% ramp, baseline serves \(n_b = 9{,}000\) req/min at \(\hat p_b = 0.0035\) (35 errors) while canary serves \(n_c = 3{,}000\) req/min at \(\hat p_c = 0.048\) (144 errors):

$$\hat p = \frac{144+32}{3000+9000} = 0.0147, \qquad z = \frac{0.048 - 0.0035}{\sqrt{0.0147(0.9853)\left(\frac{1}{3000}+\frac{1}{9000}\right)}} \approx 17.6$$

\(z \approx 17.6 \gg 2.33\) — this is an overwhelmingly significant regression, not noise. The gate fires and traffic is pulled back within a single monitoring tick.

How Much Traffic Do You Need in the Canary?

Sizing the first rung matters: too little traffic and a real regression hides in noise; too much and you have needlessly widened the blast radius. A standard power calculation for detecting a difference \(\Delta = p_c - p_b\) with significance \(\alpha\) and power \(1-\beta\) gives the required per-arm sample size:

$$n \approx \frac{\left(z_{\alpha/2} + z_{\beta}\right)^2\big[p_b(1-p_b) + p_c(1-p_c)\big]}{\Delta^2}$$

This is why real canary schedules start at 1% (bounding exposure) rather than jumping straight to 25% — the ramp itself is a sample-size schedule, buying statistical power gradually as confidence is earned.

⚠️ Common Pitfall

A gate that only checks the mean error rate can miss a regression concentrated in a thin slice of traffic (e.g. one country, one device type, one rare input feature value). Production canary systems segment gates by cohort, not just globally — a model can pass the aggregate gate while quietly failing 100% of requests from a minority segment.

Key Takeaways
▼

Use blue-green when:

  • You need the simplest possible rollback story — one config flip, seconds to revert
  • You can afford to run two full-scale environments simultaneously (2x infra cost during the window)
  • The change is monolithic and hard to partially expose (e.g. a schema migration alongside the model)

Use canary when:

  • You want to bound the blast radius of an undetected regression to a small percentage of users
  • You have reliable real-time metrics (error rate, latency, business KPIs) to gate on automatically
  • The model may have subtle, data-dependent failure modes that only show up under real production traffic and cannot be fully caught by offline evaluation

ML-specific nuance: a model can look statistically fine yet be silently wrong (e.g. confidently mis-ranking a content type) — pair canary error-rate gates with model-specific signals like prediction-distribution drift, calibration, and shadow-mode comparison against the incumbent before ever serving live traffic.

💡 They Compose

Many production systems run both: canary the new model up to 100% traffic for safety, and keep the previous version's environment blue-green-warm for a while afterward, so a delayed issue (e.g. surfaced only after a weekly batch job) still has an instant full rollback path.

Code Trace

# --- Istio VirtualService: traffic weight is the single source of truth ---
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata: { name: model-router }
spec:
http:
- route:
- destination: { host: model-stable }
weight: 100 # <- flips to 0 on blue-green cutover
- destination: { host: model-candidate }
weight: 0 # <- ramps 1 -> 5 -> 25 -> 100 for canary
# --- Python: the controller loop that drives the gate decision ---
RAMP = [1, 5, 25, 50, 100]
GATE = {"max_err_rate": 0.02, "max_p95_ms": 250}
def z_test(err_c, n_c, err_b, n_b):
p_pool = (err_c * n_c + err_b * n_b) / (n_c + n_b)
se = (p_pool * (1 - p_pool) * (1 / n_c + 1 / n_b)) ** 0.5
return (err_c - err_b) / se if se > 0 else 0.0
def advance_canary(metrics_stable, metrics_canary, rung_idx):
z = z_test(metrics_canary.err, metrics_canary.n,
metrics_stable.err, metrics_stable.n)
gate_ok = (metrics_canary.err <= GATE["max_err_rate"]
and metrics_canary.p95_ms <= GATE["max_p95_ms"]
and z < 2.33)
if not gate_ok:
set_weights(stable=100, candidate=0) # instant auto-rollback
return "ROLLED_BACK"
if rung_idx + 1 == len(RAMP):
return "FULLY_PROMOTED"
next_pct = RAMP[rung_idx + 1]
set_weights(stable=100 - next_pct, candidate=next_pct)
return "HOLD_AND_BAKE"
