Search Space Design: Cell-Based vs. Macro-Based

Two paradigms for defining neural network architectures for automated search (NAS)
Intermediate Deep Learning Neural Architecture Search O(N) vs O(N_cell)
1
Understanding Search Space Design
▼

What is it? When performing Neural Architecture Search (NAS), we need to define the set of all possible neural network architectures that our algorithm can explore. This "set of possibilities" is called the search space. The way this search space is designed fundamentally impacts the complexity of the search, the quality of the resulting architectures, and their transferability.

The two dominant paradigms for search space design are macro-based and cell-based.

Analogy: Imagine you're an architect designing a new building.

  • Macro-based is like designing every single floor plan uniquely, from the ground up, for a 100-story building. You have immense freedom, but the number of choices is astronomical.
  • Cell-based is like designing one "standard floor" layout (a "cell") and then specifying that your 100-story building will consist of 98 copies of this standard floor, with a unique ground floor and roof. You have less freedom for the overall structure, but the design task is massively simplified, and the core "floor plan" can be reused across different buildings.

💡 If you remember one thing

Macro-based search spaces allow maximum flexibility but lead to extremely large, computationally intractable search problems. Cell-based search spaces constrain the problem by enforcing modularity and repetition, drastically reducing complexity at the cost of some structural flexibility.

2
How Each Design Works Internally
▼

Macro-Based Search Spaces

In a macro-based search space, the entire neural network is treated as a single, large computational graph. Each layer or block in the network can be chosen from a predefined set of operations (e.g., convolutional layers with different kernel sizes, pooling layers, skip connections, recurrent cells). The connections between these layers can also be part of the search (e.g., sequential, multi-branch, dense connections).

  • High Flexibility: Allows for discovery of highly novel and unconventional architectures.
  • Large Search Space: The number of possible architectures grows exponentially with the number of layers and choices per layer, quickly becoming astronomically large.
  • Computational Cost: Evaluating each candidate architecture is expensive, making exhaustive search impossible and even advanced search algorithms struggle.

Cell-Based Search Spaces

Cell-based search spaces introduce a hierarchical design. Instead of searching for the entire network structure, the search focuses on finding an optimal "building block" called a cell. This cell is a small, directed acyclic graph (DAG) of operations with a few input nodes and one or more output nodes. The full neural network is then constructed by stacking multiple copies of this learned cell in a predefined macro-structure.

  • Reduced Search Space: By searching only for the cell structure, the complexity is significantly reduced. If a network has \(L\) layers composed of \(K\) identical cells, the search is for one cell, not \(L\) distinct layers.
  • Modularity & Transferability: The learned cells often exhibit good modularity and can be transferred to different datasets or tasks, even forming larger networks.
  • Predefined Macro-Structure: The overall network structure (how cells are stacked, reduction layers, etc.) is typically fixed or part of a much simpler macro-search.

Design Decision: Why Cell-Based Architectures Became Dominant

The success of early macro-based NAS (e.g., NASNet) demonstrated the power of automated architecture discovery but came with an exorbitant computational cost (thousands of GPU days). Cell-based approaches, pioneered by works like NASNet-A and DARTS, dramatically reduced this cost by exploiting the observation that successful deep learning architectures often exhibit repetitive, modular patterns. This made NAS feasible for a wider range of researchers and applications.

🔑 Key Property

The core idea of cell-based design is that a complex network can be effectively represented as a repetition of simpler, optimized motifs. This allows the search algorithm to focus its efforts on a smaller, more manageable sub-problem (the cell), leading to faster convergence and more transferable results.

3
Why It Works — Search Space Complexity
▼

Calculating Search Space Size

The effectiveness of cell-based design hinges on its ability to drastically reduce the size of the architecture search space. Let's quantify this for simplified sequential networks.

For a macro-based search space, if a network has \(N_L\) layers and each layer can choose from \(N_{ops}\) distinct operations, the total number of possible architectures is:

$$|S_{macro}| = N_{ops}^{N_L}$$

This is a simple multiplicative model. If we introduce skip connections or more complex DAG structures, the complexity grows even faster (e.g., for \(N_L\) layers, there are \(2^{N_L(N_L-1)/2}\) ways to connect them in a DAG, multiplied by operation choices).

For a cell-based search space, we first define a cell with \(N_C\) internal nodes (operations) and \(N_{ops}\) choices for each node. The number of possible unique cells is:

$$|S_{cell}| = N_{ops}^{N_C}$$

Once an optimal cell is found, the full network is constructed by stacking \(N_{stacks}\) copies of this identical cell. The overall search space for the entire network architecture is then effectively just the size of the cell search space:

$$|S_{network}| = |S_{cell}| = N_{ops}^{N_C}$$

The key insight is that the number of operations in a cell \(N_C\) is typically much smaller than the total number of layers in a macro network \(N_L\). For example, if \(N_{ops}=5\), a macro network of \(N_L=10\) layers has \(5^{10} \approx 9.7 \times 10^6\) architectures. A cell with \(N_C=3\) internal nodes has \(5^3 = 125\) architectures. This is a reduction of 5 orders of magnitude in search complexity.

⚠️ Common Pitfall

While cell-based search dramatically reduces complexity, it also introduces a strong inductive bias: the assumption that a good architecture can be formed by repeating a single motif. If the optimal architecture for a given task genuinely requires highly heterogeneous layers or complex, non-repeating global structures, a cell-based approach might fail to find it or perform sub-optimally. This is where macro-based search, despite its cost, retains its theoretical appeal.

Key Takeaways
▼

When to use Macro-Based Search Spaces:

  • When exploring truly novel or highly unconventional architectures, especially for smaller models or specific research questions where flexibility is paramount.
  • If computational resources are virtually unlimited, allowing for extensive exploration of a vast space.
  • For tasks where the optimal architecture is unlikely to follow a repetitive, modular pattern.

When to use Cell-Based Search Spaces:

  • For large-scale models (e.g., deep convolutional networks for image recognition, large language models) where full macro-search is computationally prohibitive.
  • When seeking architectures that are efficient and transferable across different datasets or downstream tasks.
  • When computational budget for NAS is limited, as it offers a much more tractable search problem.
  • This is the dominant approach in modern NAS for vision and often used in NLP.

Hybrid Approaches: It's common to combine elements of both: for example, performing a macro-search over how to stack different types of cells (e.g., "normal" cells and "reduction" cells) or allowing for global skip connections between distant cells, while keeping the internal cell structure fixed or independently searched.

💡 Big Picture

The choice between macro- and cell-based search space design reflects a fundamental trade-off in automated machine learning: between exploration breadth (macro) and search efficiency/transferability (cell). Modern NAS largely favors cell-based designs due to their practical advantages in terms of computational cost and empirical success on large-scale tasks.

op_name = OPS[op_idx]
# Instantiate the chosen operation (e.g., torch.nn.Conv2d)
layer = instantiate_op(op_name, input_channels, output_channels)

# --- Cell-Based Architecture Definition ---
class NasCell(nn.Module):
def __init__(self, choices_in_cell, input_channels):
super().__init__()
self.ops = nn.ModuleList()
for op_idx in choices_in_cell:
op_name = OPS[op_idx]
self.ops.append(instantiate_op(op_name, input_channels, input_channels))
# For simplicity, assume sequential internal connections.
# Real cells often have complex DAGs.
def forward(self, x):
for op in self.ops:
x = op(x)
return x
def build_cell_architecture(cell_choices, num_cells, input_channels):
model_cells = []
for _ in range(num_cells):
model_cells.append(NasCell(cell_choices, input_channels))
return Sequential(*model_cells)
