Understanding Qwen-VL & Qwen2-VL
▼

What is it? Qwen-VL and Qwen2-VL are Alibaba's open multimodal large language models that let an LLM "see" images and video. The interesting engineering story isn't the LLM itself — it's how the image gets turned into tokens the LLM can read, and how those tokens know where they sit in space and time.

Analogy: Imagine describing a photo to someone over the phone by reading out a fixed list of exactly 256 index cards, no matter if the photo is a tiny icon or a giant panorama — that's Qwen-VL's approach. Qwen2-VL instead says "let me use as many or as few cards as the photo actually needs," and it writes a coordinate (row, column, time) on every card so the listener can reconstruct the layout perfectly — that's naive dynamic resolution plus M-RoPE.

💡 If you remember one thing

Qwen-VL compresses every image into a fixed 256 tokens via a position-aware cross-attention adapter. Qwen2-VL instead keeps a variable number of tokens proportional to the image's native resolution (naive dynamic resolution), and replaces 1D RoPE with M-RoPE — a rotary position embedding decomposed into temporal \(t\), height \(h\), and width \(w\) components — so the LLM can reason about 2D/3D structure directly.

2
How It Works Internally
▼

Qwen-VL: the position-aware adapter (2023)

Qwen-VL's vision encoder (an OpenCLIP ViT-bigG) always resizes the input image to a fixed size (e.g. 448×448), producing a fixed grid of patch features. A single-layer cross-attention adapter with 256 learnable query embeddings then compresses this patch sequence — whatever its length — down to exactly 256 output tokens. To stop this compression from destroying spatial layout, 2D absolute positional encodings are added to the patch keys before the cross-attention, so the queries can still attend selectively by location. This keeps the LLM's input length constant and cheap, but it is wasteful for simple images and lossy for dense, high-resolution ones — detail gets squeezed into the same 256 slots regardless of how much content is actually there.

Qwen2-VL: naive dynamic resolution (2024)

Qwen2-VL removes the fixed-resize step entirely. It patchifies the image at its native resolution (rounded to a multiple of 28 pixels) using 14×14 patches, so a wide image yields a wide patch grid and a tall image yields a tall one — aspect ratio is preserved and no content is cropped or squashed. To keep sequence length manageable, a lightweight MLP then merges each adjacent 2×2 block of patch embeddings into one visual token, cutting the token count 4× before the tokens reach the LLM. The result: a 224×224 image and a 1024×768 image now produce genuinely different numbers of visual tokens — the token budget scales with actual visual content, not a fixed constant.

Why M-RoPE was needed

Once the number and 2D layout of visual tokens became variable, plain 1D RoPE (one scalar position per token, incremented left-to-right) could no longer express "this token is two rows below and three columns right of that one," nor extend cleanly to video frames. Qwen2-VL's Multimodal Rotary Position Embedding (M-RoPE) decomposes each token's position into three components \((t, h, w)\) — temporal, height, width — and splits the rotary frequency channels into three groups, one per axis. Text tokens simply set \(t=h=w\), which collapses M-RoPE exactly back to ordinary 1D RoPE, preserving full backward compatibility.

🔑 Design Decision: why not just keep the fixed adapter?

A fixed 256-token bottleneck caps how much visual detail can ever reach the LLM, independent of image complexity. Naive dynamic resolution trades a fixed, predictable sequence length for a resolution-proportional one — better fidelity on dense images, fewer wasted tokens on simple ones — but it requires a positional scheme (M-RoPE) that can describe an irregular, resolution-dependent 2D/3D grid instead of a fixed 16×16 layout.

3
Why It Works — The Math
▼

From 1D RoPE to M-RoPE

Standard RoPE rotates each 2D sub-plane \(i\) of a query/key vector by an angle proportional to its absolute position \(m\):

$$q'_{(i)} = R(m\theta_i)\, q_{(i)}, \qquad \theta_i = 10000^{-2i/d}$$

Because rotation matrices compose as \(R(m\theta)^\top R(n\theta) = R((n-m)\theta)\), the attention dot product \(\langle q'_m, k'_n\rangle\) depends only on the relative offset \(n-m\) — this relative-position property is why RoPE works so well.

M-RoPE's partition

M-RoPE replaces the scalar position \(m\) with a triple \(p=(t,h,w)\), and partitions the \(d/2\) frequency indices into three disjoint groups \(I_t, I_h, I_w\):

$$\text{angle}(i, p) = \begin{cases} t\cdot\theta_i & i \in I_t \\ h\cdot\theta_i & i \in I_h \\ w\cdot\theta_i & i \in I_w \end{cases}$$

For a text token, \(t=h=w\), so every group rotates by the same angle and M-RoPE reduces exactly to 1D RoPE. For an image token, \(t\) stays constant across the whole image (or increments per video frame), while \(h\) and \(w\) sweep over the patch grid — giving the model a genuine 2D relative-position signal along each axis independently.

Assigning positions across a mixed sequence

Let \(p_0\) be the 1D position of the last text token before an image block. Image token at grid row \(r\), column \(c\) (0-indexed) gets:

$$t = p_0+1, \qquad h = p_0+1+r, \qquad w = p_0+1+c$$

After the image block, the next text token resumes at a single scalar position equal to one plus the maximum coordinate used anywhere in the image block, and then \(t=h=w\) again increments together like ordinary 1D RoPE:

$$p_{\text{next}} = 1 + \max\big(t,\ \max_r h,\ \max_c w\big)$$
⚠️ Common Pitfall

It's tempting to think M-RoPE triples the number of position "slots" used. It doesn't — the same rotary channels are reused, just split into three groups that each track one axis. The total rotary dimensionality is unchanged; only how position numbers are computed and applied changes. Also, naive dynamic resolution means token count is a function of pixel resolution — extremely high-resolution images can still blow up the LLM's context length, which is why the 2×2 merge step and resolution capping both matter in practice.

Key Takeaways
▼

When naive dynamic resolution + M-RoPE shine:

  • High-resolution documents, charts, and UI screenshots where fine detail matters
  • Images with extreme or unusual aspect ratios (panoramas, tall receipts)
  • Video, where the same \(h,w\) scheme extends naturally by incrementing \(t\) per frame
  • Mixed text+image sequences that must stay position-consistent with pure-text pretraining

When the fixed-adapter approach (Qwen-VL-style) is still fine:

  • Latency/memory-constrained serving where a hard cap on visual tokens is required
  • Simple, low-detail images (icons, thumbnails) where 256 tokens is already plenty
  • Systems that cannot easily support a variable-length vision segment in the context window
💡 Hierarchy

1D RoPE (text only) ⊂ Fixed adapter + 2D abs. pos. (Qwen-VL, constant 256 tokens) ⊂ Naive dynamic resolution + M-RoPE (Qwen2-VL, variable tokens with native \((t,h,w)\) positions). Each step relaxes an assumption: first that position must be 1D, then that visual token count must be fixed.

Code Trace
▼
PATCH, MERGE = 14, 2
# 1. Naive dynamic resolution: patchify at native size
def patch_grid(img_w, img_h, patch=PATCH):
gw = round(img_w / patch) # patches across width
gh = round(img_h / patch) # patches down height
return gw, gh
# 2. Spatial merge: 2x2 adjacent patches -> 1 visual token
def merged_grid(gw, gh, merge=MERGE):
return gw // merge, gh // merge # (tok_w, tok_h)
tok_w, tok_h = merged_grid(*patch_grid(img_w, img_h))
num_visual_tokens = tok_w * tok_h
# 3. M-RoPE: assign (t, h, w) position ids
def mrope_positions(p0, tok_w, tok_h):
t0 = p0 + 1 # constant temporal id
positions = []
for r in range(tok_h):
for c in range(tok_w):
t, h, w = t0, t0 + r, t0 + c
positions.append((t, h, w))
next_text_pos = 1 + max(max(t, h, w) for t, h, w in positions)
return positions, next_text_pos
# 4. Text tokens: t == h == w -> identical to 1D RoPE
def text_positions(start, n):
return [(p, p, p) for p in range(start, start + n)]
