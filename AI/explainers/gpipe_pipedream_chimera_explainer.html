GPipe, PipeDream & Chimera

Three schedules for pipelining micro-batches across GPUs — same idea, three different bubble/memory/staleness trade-offs

1
Understanding Pipeline-Parallel Training
▼

What is it? When a model is too big for one GPU, you can split its layers across several GPUs — that's model parallelism. But naively running layer group 1 on GPU0, then layer group 2 on GPU1, and so on means only one GPU is ever busy at a time: everyone else waits for its turn. Pipeline parallelism fixes this by chopping a mini-batch into many small micro-batches and streaming them through the stages like items on an assembly line, so several GPUs overlap and stay busy at once.

Analogy: Picture a car factory with 4 stations (chassis, engine, paint, wheels). With one car, three stations are always idle waiting their turn. Send a continuous stream of cars down the line instead, and every station stays busy — except right at the start (line is still filling up) and right at the end (line is draining out). That start/end idle time is the pipeline bubble. GPipe, PipeDream and Chimera are three different ways of scheduling that assembly line.

💡 If you remember one thing

The pipeline bubble fraction is $$\text{bubble} = \frac{p-1}{m+p-1}$$ for both GPipe and PipeDream, where \(p\) is the number of pipeline stages and \(m\) is the number of micro-batches. Chimera changes the topology (bidirectional pipelines) to cut that bubble roughly in half — the three schedules differ mainly in memory footprint and weight-consistency guarantees, not in the underlying bubble formula.

2
How It Works Internally
▼

GPipe — all-forward, then all-backward

GPipe (Huang et al., 2019) splits a batch of size \(B\) into \(m\) micro-batches and pushes all \(m\) of them forward through the \(p\) stages before running any backward pass. This is simple and fully synchronous — there is exactly one weight version in play for the whole step, so there's no staleness to reason about. The cost: activations for every in-flight micro-batch must stay alive until its backward runs, which means storing up to \(m\) sets of activations. GPipe's answer is activation checkpointing (recomputation): keep only the activation at each stage boundary, and recompute the rest during the backward pass — trading roughly one extra forward pass of compute for a large cut in memory.

PipeDream — One-Forward-One-Backward (1F1B)

PipeDream (Narayanan et al., 2019) doesn't wait for all \(m\) forwards. After a short warm-up, each stage alternates one forward, one backward, so at most \(p\) micro-batches are ever "in flight" (forwarded but not yet backpropagated) — activation memory drops from \(O(m)\) to \(O(p)\), letting you scale to far more micro-batches or bigger models. Because a stage's weights could in principle change between a micro-batch's forward and its later backward, PipeDream adds weight stashing: it snapshots the exact weight version used at forward time and reuses that same version at backward time, guaranteeing the gradient is mathematically consistent — at the cost of holding a handful of extra weight copies per stage.

Chimera — bidirectional pipelines

Chimera (Li & Hoefler, 2021) notices that even 1F1B still has an unavoidable bubble at the very start and end of the pipeline. Its fix: run two pipelines over the same GPUs, one flowing stage 0→p-1 ("down") and one flowing stage p-1→0 ("up"), interleaved in time. While the down-pipeline is still filling up (bubbly), the up-pipeline is already in its productive steady state on those same GPUs, and vice versa — the two bubbles cancel each other out. Net effect: roughly half the bubble time of GPipe/PipeDream, at the cost of about 2× the weight memory (each GPU now holds a stage's weights for both directions).

🔑 Key Property

GPipe and PipeDream have identical total wall-clock time and bubble fraction — 1F1B only changes the order of work, not the amount. Its win is purely about peak activation memory. Chimera is the only one of the three that actually changes the bubble fraction, by changing the pipeline's shape from a single line to two interleaved lines.

3
Why It Works — The Math
▼

Let \(p\) be the number of pipeline stages, \(m\) the number of micro-batches, and \(t_f, t_b\) the forward/backward time per stage. A single-direction pipeline (GPipe or PipeDream 1F1B) needs \((p-1)\) extra stage-times to fill and \((p-1)\) more to drain around \(m\) steady-state steps:

$$T = (m + p - 1)(t_f + t_b)$$

If the pipeline had zero bubble, the wall-clock time would just be the useful work each GPU does, \(T_{ideal} = m(t_f+t_b)\). So the fraction of time spent idle is:

$$\text{bubble} = \frac{T - T_{ideal}}{T} = \frac{p-1}{m+p-1}$$

This is exactly the same for GPipe and PipeDream — the schedule order (all-then-all vs. interleaved) changes memory, not this ratio. Chimera splits the \(m\) micro-batches across two opposite-direction pipelines sharing the same \(p\) GPUs; because one direction's fill/drain overlaps with the other's steady state, the effective bubble roughly halves for the same \(p\) and \(m\):

$$\text{bubble}_{\text{chimera}} \approx \tfrac{1}{2}\cdot\frac{p-1}{m+p-1}$$
⚠️ Common Pitfall

As \(m \to \infty\), bubble → 0 for all three schedules — the fill/drain cost gets amortized away. But you can't grow \(m\) forever: more micro-batches means a smaller per-micro-batch size, which can hurt batch-statistics-sensitive layers, and for GPipe it grows activation memory linearly (mitigated only by recomputation's extra compute). The real differentiator at large \(m\) is memory and staleness guarantees, not the bubble.

Key Takeaways
▼

When to use which:

  • GPipe — simplest to implement and debug, fully synchronous, no staleness. Fine when memory allows (pair with activation recomputation) or as a correctness baseline.
  • PipeDream 1F1B — the default in most modern frameworks (Megatron-LM, DeepSpeed): identical bubble to GPipe but dramatically less activation memory, so you can afford bigger models or more micro-batches.
  • Chimera — worth the extra ~2× weight memory when you want to shave the last bit of bubble time, especially when \(m\) is small relative to \(p\) (few micro-batches per stage, where the bubble fraction is otherwise painfully large).
💡 Hierarchy

GPipe (sync, \(O(m)\) activation memory) → PipeDream 1F1B (same bubble, \(O(p)\) activation memory) → Chimera (bidirectional, ~half the bubble, ~2× weight memory). Each step trades a different resource for a different win — none of them is strictly better than the others in every dimension.

Code Trace — Scheduling Logic
▼
# GPipe schedule: all-forward, then all-backward
for i in range(m):
forward(stage, microbatch[i]) # fill phase
for i in range(m):
backward(stage, microbatch[i]) # drain phase
# PipeDream 1F1B schedule, per stage s (0 = first stage)
warmup = min(m, p - 1 - s)
for i in range(warmup):
forward(s, i) # warm-up: fill the window
for i in range(m - warmup):
forward(s, warmup + i) # steady state:
backward(s, i) # one forward, one backward
for i in range(m - warmup, m):
backward(s, i) # cool-down: drain remaining grads
# PipeDream weight stashing
W_stash[s][mb_id] = copy(W[s]) # snapshot BEFORE forward(s, mb_id)
grad = backward(s, mb_id, using=W_stash[s][mb_id]) # match version
# Chimera: two mirrored 1F1B pipelines sharing the same p GPUs
down = build_1f1b(stages=range(p), m_down) # stage 0 -> p-1
up = build_1f1b(stages=range(p)[::-1], m_up) # stage p-1 -> 0
schedule_greedy_interleave(down, up) # fill each other's bubbles
