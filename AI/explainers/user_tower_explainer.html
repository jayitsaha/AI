1
Understanding the User Tower
▼

What is it? In two-tower retrieval (used at scale by YouTube, Pinterest, Instagram, and most large recsys), a user tower is a neural network that consumes everything you know about a user right now — their identity, demographics, recent activity, and current context — and compresses it into a single dense vector, the user embedding. A separate, independently-trained item tower does the same for every catalog item. Retrieval then becomes nearest-neighbor search: find the items whose embeddings have the highest dot product (or cosine similarity) with the user's embedding.

Analogy: Think of the user tower as a translator that takes a messy paragraph describing someone — "user #4471, female, 25-34, in India, just watched running shoes and a yoga mat, browsing on mobile in the evening" — and rewrites it as a single coordinate in a 6-dimensional "taste space." Items live in that same space. Whatever coordinate is closest to the user's is what gets recommended.

💡 If you remember one thing

The user tower's whole job is fusion + compression: take features of wildly different shapes (a single ID, a handful of categoricals, a variable-length history, a few context flags), turn each into a fixed-size vector, concatenate them, and push the result through an MLP to a single normalized embedding $$\mathbf{u} = \frac{f_\theta(\mathbf{x}_{\text{user}})}{\lVert f_\theta(\mathbf{x}_{\text{user}}) \rVert_2}$$ that can be compared to item embeddings with one dot product.

How the User Tower Works Internally
▼

Four Kinds of Raw Signal

A production user tower typically ingests four feature families, each requiring a different encoding strategy before they can be combined:

  • Sparse identity — the user ID itself, looked up in a learned embedding table \(E_{\text{id}} \in \mathbb{R}^{N \times d}\). This lets the model memorize idiosyncratic taste that no other feature captures.
  • Categorical demographics — age bucket, gender, country. Each categorical gets its own small embedding table; the looked-up vectors are concatenated.
  • Sequential behavior history — the last \(k\) items the user engaged with. Because \(k\) varies per user, a variable-length sequence of item embeddings must be pooled into one fixed-size vector — commonly via mean pooling or, better, attention pooling, where the pooling weights depend on how relevant each historical item is to the user's identity.
  • Context — time of day, device type, surface — features that change every request and let the same user get different embeddings in different situations.

Fusion Then Encoding

All four fixed-size vectors are concatenated into one wide vector \(\mathbf{x} = [\mathbf{e}_{\text{id}}; \mathbf{e}_{\text{demo}}; \mathbf{e}_{\text{hist}}; \mathbf{e}_{\text{ctx}}]\), then passed through 2-3 dense layers with non-linearities (ReLU) that let the network learn interactions between feature families — e.g. "mobile evening browsing" interacting differently with "25-34 demographic" than with "45-54."

Design Decision: Why L2-Normalize the Output?

The final layer's raw output is L2-normalized to unit length. This turns the retrieval dot product into cosine similarity, bounding scores to \([-1, 1]\) regardless of how large the raw activations get — critical for training stability with contrastive losses (like sampled softmax) and for making approximate nearest-neighbor (ANN) search well-behaved at serving time.

🔑 Key Property

The user tower and item tower never see each other's raw features — they only meet through the dot product of their output embeddings. This is what makes two-tower models serve at massive scale: item embeddings are pre-computed offline and indexed in an ANN structure (e.g. HNSW), so at request time you only run the (cheap) user tower once and do a fast approximate search.

3
Why It Works — The Math
▼

Attention Pooling Over History

Given history item embeddings \(\mathbf{h}_1, \dots, \mathbf{h}_k\) and a query vector \(\mathbf{q}\) (often the user-ID embedding itself), attention pooling computes a relevance score for each item, turns scores into weights with softmax, and pools:

$$s_i = \mathbf{q}^\top \mathbf{h}_i, \qquad \alpha_i = \frac{e^{s_i}}{\sum_{j=1}^k e^{s_j}}, \qquad \mathbf{e}_{\text{hist}} = \sum_{i=1}^k \alpha_i \, \mathbf{h}_i$$

Unlike mean pooling (\(\alpha_i = 1/k\) for all \(i\)), attention pooling lets the model up-weight the historical items most relevant to this user, which is exactly what models like Deep Interest Network (DIN) exploit.

The MLP Forward Pass

The concatenated feature vector \(\mathbf{x} \in \mathbb{R}^{d_0}\) is transformed layer by layer:

$$\mathbf{z}^{(l)} = \text{ReLU}\!\left(W^{(l)} \mathbf{z}^{(l-1)} + \mathbf{b}^{(l)}\right), \qquad \mathbf{z}^{(0)} = \mathbf{x}$$

The final layer applies a linear projection without a non-linearity, then L2-normalizes:

$$\mathbf{u} = \frac{W^{(L)}\mathbf{z}^{(L-1)} + \mathbf{b}^{(L)}}{\lVert W^{(L)}\mathbf{z}^{(L-1)} + \mathbf{b}^{(L)} \rVert_2}$$

At serving time, retrieval scores an item embedding \(\mathbf{v}\) (also unit-norm, from the item tower) via a single dot product:

$$\text{score}(u, v) = \mathbf{u}^\top \mathbf{v} = \cos(\mathbf{u}, \mathbf{v}) \in [-1, 1]$$
⚠️ Common Pitfall

If the user and item towers are trained with a contrastive loss (e.g. in-batch sampled softmax) but the batch's negative items are not representative of the true item distribution, the model learns a popularity-biased embedding space — it gets very good at ranking popular items and poor at surfacing long-tail ones. Correcting for sampling bias (e.g. logQ correction) is essential in production.

Key Takeaways
▼

What the user tower buys you:

  • A fixed-size representation from variable-size, heterogeneous inputs (ID + categoricals + sequence + context)
  • Decoupling from the item tower: user embeddings can be computed at request time cheaply, item embeddings pre-computed offline and ANN-indexed
  • A single learned similarity metric (cosine) that generalizes across the entire catalog, instead of hand-tuned scoring rules

Design levers that matter in practice:

  • Pooling strategy for history — mean pooling is cheap but attention pooling captures "what matters right now"
  • Embedding dimensionality — must match the item tower's output dimension exactly, since they share the same space
  • Normalization — L2-normalizing both towers turns retrieval into cosine similarity and stabilizes contrastive training
  • Freshness — context features let the same user ID produce different embeddings across sessions
💡 Symmetry with the Item Tower

Everything shown here for the user tower has a mirror image on the item side: item ID embedding, item metadata (category, price bucket), item content features (e.g. text/image embeddings), all fused through an item-side MLP to the same-dimensional output space. The two towers are trained jointly but scored independently — that's the entire trick that makes two-tower retrieval scale to billions of items.

import numpy as np
# --- 1. Sparse identity: lookup in learned embedding table ---
id_emb = E_id[user_id] # shape (4,)
# --- 2. Categorical demographics: lookup + concat ---
demo_emb = np.concatenate([
E_age[age_bucket], E_gender[gender], E_country[country]
]) # shape (8,)
# --- 3. Sequential history: attention pooling ---
H = np.stack([E_item[i] for i in history_ids]) # shape (k, 4)
scores = H @ id_emb # query = id_emb
weights = softmax(scores)
hist_emb = weights @ H # shape (4,)
# --- 4. Context: lookup + concat ---
ctx_emb = np.concatenate([E_time[hour_bucket], E_device[device]]) # (4,)
# --- 5. Fuse: concatenate everything ---
x = np.concatenate([id_emb, demo_emb, hist_emb, ctx_emb]) # (20,)
# --- 6. MLP tower ---
z1 = relu(W1 @ x + b1) # (16,)
z2 = relu(W2 @ z1 + b2) # (8,)
raw = W3 @ z2 + b3 # (6,)
user_emb = raw / np.linalg.norm(raw) # unit vector
# --- 7. Retrieval: score against item tower output ---
score = user_emb @ item_emb # cosine similarity
