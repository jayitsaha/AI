Understanding ML Model Deployment
▼

What is it? Model deployment is the process of making a trained machine learning model available for use by other applications or end-users. It involves integrating the model into a larger system, ensuring it can receive input data, make predictions, and return results reliably and efficiently. This isn't just about putting a model on a server; it's about building a robust system around it, including infrastructure, monitoring, and update mechanisms.

Analogy: Think of it like launching a new restaurant. You've perfected your recipes (trained model), but that's not enough. You need a kitchen (serving infrastructure), staff to take orders and serve food (API/inference logic), a system for new menu items (model updates), and a plan if a new dish is unpopular or causes problems (rollback strategy). Without proper deployment, even the best recipe stays in the chef's notebook.

💡 If you remember one thing

Deployment is the bridge between ML research and real-world impact. A model is only valuable if it's reliably accessible, performant, and maintainable in a production environment. It's a continuous process, not a one-time event.

2
Core Components & Strategies
▼

Serving Infrastructure

Models are typically served via an API endpoint. Common infrastructure choices include:

  • REST API / gRPC services: Standard web service patterns, often containerized (Docker) and orchestrated (Kubernetes). Flexible, scalable, but requires managing servers.
  • Serverless functions (e.g., AWS Lambda, Google Cloud Functions): Pay-per-invocation, scales automatically, less operational overhead. Best for infrequent or bursty inference.
  • Edge devices: Deploying models directly to user devices (mobile, IoT) for low-latency, offline capabilities, and data privacy.
  • Specialized ML serving platforms (e.g., TensorFlow Serving, TorchServe, Seldon Core): Optimized for model loading, versioning, and high-throughput inference.

Batch vs. Online Inference

The choice depends on latency requirements and data availability:

  • Online (Real-time) Inference: Predictions are made one-by-one or in small mini-batches as requests arrive. Requires low-latency infrastructure and is typical for user-facing applications (e.g., recommendation systems, fraud detection).
  • Batch Inference: Predictions are made on large datasets at scheduled intervals (e.g., hourly, daily). Results are stored and later consumed. Suitable for tasks where immediate predictions aren't critical (e.g., monthly reports, large-scale content moderation).

Model Update Strategies

Replacing an old model with a new one without disrupting service is crucial:

  • Direct/Rolling Update: Replace instances of the old model with the new one directly. Simple but carries risk if the new model has issues.
  • Canary Deployment: Route a small percentage of live traffic (e.g., 5-10%) to the new model (the "canary"), while the majority still uses the old. Monitor performance; if good, gradually increase traffic to the new model.
  • Blue/Green Deployment: Maintain two identical production environments ("blue" for old, "green" for new). Deploy the new model to the "green" environment, test it thoroughly, then switch all traffic to "green" instantly via a load balancer. The "blue" environment is kept as a quick rollback option.
  • A/B Testing: Similar to canary, but traffic is split based on user segments or features, often for comparing business metrics or user experience rather than just model stability.

Rollback Strategy

The plan for reverting to a previous, stable state if a new deployment fails:

  • Automated Rollback: Triggered by monitoring alerts (e.g., sudden increase in error rates, latency, or drop in accuracy).
  • Manual Rollback: Initiated by an operator.
  • Effective rollback requires keeping previous model versions, their artifacts, and a clear understanding of traffic routing.
🔑 Key Property

Successful deployment requires a robust CI/CD pipeline, comprehensive monitoring, and well-defined update and rollback procedures. It's a continuous feedback loop where models are deployed, monitored, and iteratively improved.

3
Metrics & Decision Principles
▼

Performance Metrics for Online Serving

When serving models in real-time, key system metrics are paramount:

  • Latency (\(L\)): Time taken from request to response. Often measured as p50, p90, p99 (50th, 90th, 99th percentile) to capture tail latencies. $$L = \text{Time}(\text{Response}) - \text{Time}(\text{Request})$$
  • Throughput (\(T\)): Number of requests processed per unit of time (e.g., requests per second, RPS). $$T = \frac{\text{Total Requests}}{\text{Total Time}}$$
  • Error Rate (\(E\)): Percentage of requests that result in an error (e.g., HTTP 5xx, model prediction failure). $$E = \frac{\text{Error Requests}}{\text{Total Requests}}$$
  • Resource Utilization (\(U\)): CPU, GPU, memory usage. High utilization can indicate a bottleneck.

Monitoring & Observability

Beyond system health, ML-specific monitoring is critical:

  • Data Drift: Changes in the distribution of input features over time, potentially degrading model performance. Measured using statistical divergence metrics like Kullback-Leibler (KL) divergence or Jensen-Shannon (JS) divergence: $$D_{KL}(P \parallel Q) = \sum_i P(i) \log \frac{P(i)}{Q(i)}$$ where \(P\) is current data distribution and \(Q\) is training data distribution.
  • Concept Drift: Changes in the relationship between input features and the target variable. Harder to detect directly, often inferred from model performance metrics.
  • Model Performance: Monitoring business metrics (e.g., click-through rate, conversion, revenue) and ML metrics (e.g., accuracy, precision, recall, F1-score) on live data (if ground truth is available or can be approximated).

Rollback Decision Criteria

When to trigger a rollback? Define clear thresholds:

  • If \(L_{new} > (1 + \delta_L) L_{old}\) (latency increases by \(\delta_L\)).
  • If \(E_{new} > (1 + \delta_E) E_{old}\) (error rate increases by \(\delta_E\)).
  • If \(P_{new} < (1 - \delta_P) P_{old}\) (model performance metric drops by \(\delta_P\)).
  • If \(D_{KL}(P_{new} \parallel Q_{train}) > \tau\) (data drift exceeds threshold \(\tau\)).

These thresholds should be set based on business requirements and empirical observation during testing.

⚠️ Common Pitfall

Ignoring comprehensive monitoring is a recipe for disaster. A model deployed without robust observability for both system health and ML-specific metrics (drift, performance) is a ticking time bomb. You can't fix what you can't see.

Key Takeaways
▼

When to use different deployment strategies:

  • Direct/Rolling Update: For non-critical internal models, or when downtime is acceptable. Simplest to implement.
  • Canary Deployment: Ideal for high-traffic, user-facing models where risk must be minimized. Allows early detection of issues with minimal user impact.
  • Blue/Green Deployment: Great for zero-downtime, rapid rollbacks. Best for applications that can afford the duplicated infrastructure cost.
  • Batch Inference: For offline tasks, periodic reports, or pre-computing predictions where real-time latency is not a concern.
  • Online Inference: For real-time user interactions, fraud detection, recommendation engines, where immediate predictions are required.

When NOT to use:

  • Direct Deploy for Critical Systems: Too risky, can lead to widespread outages.
  • Canary/Blue-Green without Monitoring: These strategies only work if you can effectively monitor for issues. Without it, they offer a false sense of security.
  • Over-engineering for Simple Models: For trivial models or internal tools, a simpler deployment might suffice to avoid unnecessary complexity.
💡 MLOps Philosophy

Deployment is not the end of the ML lifecycle, but a critical part of a continuous loop: Train → Deploy → Monitor → Retrain. Automation, version control for models and infrastructure, and robust observability are the pillars of effective MLOps.
