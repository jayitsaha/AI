HPO Tools: Optuna, Ray Tune & W&B Sweeps

Define-by-run search spaces, pruning, distributed schedulers, and sweep dashboards — the three workhorses of modern hyperparameter optimisation.
Advanced Classical ML MLOps Interview: Important Optuna · Ray Tune · W&B
1
Understanding the Concept

Training a machine-learning model requires choosing dozens of settings before training begins — learning rate, depth, regularisation strength. These are hyperparameters: knobs that humans set, not values the model learns. HPO tools automate the search for the best combination.

💡 Real-World Analogy
Imagine tuning a racing car. You have hundreds of adjustable parts (tyre pressure, downforce, fuel mix). A rookie tries random combos; an expert prunes bad setups after one lap without finishing the full race. Optuna, Ray Tune, and W&B Sweeps are your expert crew chiefs — they propose, observe, prune, and track.
🔑 Key Property
All three tools implement a suggest → evaluate → feedback loop. What differs is where the intelligence lives: Optuna packs it in a single process with define-by-run APIs; Ray Tune spreads evaluation across a cluster with async schedulers; W&B Sweeps centralise configuration + logging on a cloud dashboard.
2
How Each Tool Works Internally

Optuna — Define-by-Run + Pruning

A Study is a named optimisation session. Each function call to study.optimize(objective, n_trials) spawns Trials. Inside the objective you sample hyperparameters on demand via the trial object:

lr = trial.suggest_float("lr", 1e-5, 1e-2, log=True) # log-uniform
n = trial.suggest_int("n_layers", 1, 4) # integer
act = trial.suggest_categorical("act", ["relu","gelu"]) # categorical

This is define-by-run: the search space is not declared upfront — it is constructed dynamically during each trial. Optuna uses a Tree-structured Parzen Estimator (TPE) by default. TPE models \(p(x \mid y < y^*)\) and \(p(x \mid y \geq y^*)\) separately and proposes \(x^* = \arg\max_x \frac{p(x \mid y < y^*)}{p(x \mid y \geq y^*)}\) — i.e., configurations more likely to be below the percentile threshold \(y^*\).

Pruning is mid-trial early stopping. After each epoch you call trial.report(val_loss, step=epoch). If the internal pruner (Median, HyperBand, etc.) decides the trial is hopeless, trial.should_prune() returns True and you raise TrialPruned.

for epoch in range(100):
train(); val_loss = evaluate()
trial.report(val_loss, step=epoch) # feed intermediate value
if trial.should_prune(): # scheduler decides
raise optuna.exceptions.TrialPruned()

Ray Tune — Distributed Schedulers

Ray Tune wraps any training function in a ray.tune.Tuner. Configurations are sampled from a search space dict, dispatched as Ray remote tasks, and governed by a Scheduler (e.g., ASHA — Asynchronous Successive Halving) and a Searcher (e.g., Optuna, HyperOpt). Workers report metrics via train.report({"val_acc": acc}). ASHA eliminates bottom-performing trials after each rung \(r\), doubling resources to survivors — all asynchronously across workers.

$$\text{ASHA eliminates trial } i \text{ at rung } r \text{ if } f_i(r) < Q_\eta\!\left(\{f_j(r)\}_j\right)$$

where \(Q_\eta\) is the bottom \(1/\eta\) quantile and \(\eta\) is the reduction factor (typically 3–4).

W&B Sweeps — Cloud Dashboard

A sweep.yaml defines the search strategy (bayes, grid, random), hyperparameter ranges, and the metric to optimise. A sweep controller process (on W&B servers) assigns configurations to agents (your training machines). Each agent calls wandb.init() and the controller streams the next config. All runs are logged centrally; the dashboard shows parallel coordinate plots, parameter importance, and correlation matrices in real time.

The Math Behind It

TPE (Optuna Default)

Let \(\mathcal{D} = \{(x_i, y_i)\}_{i=1}^{n}\) be past trials. Fix percentile \(\gamma \in (0,1)\) and threshold \(y^* = Q_\gamma(\mathbf{y})\). TPE fits two density models:

$$\ell(x) = p(x \mid y < y^*), \quad g(x) = p(x \mid y \geq y^*)$$

The expected improvement surrogate simplifies to:

$$\text{EI}(x) \propto \frac{\ell(x)}{g(x)}$$

The next config is \(x^* = \arg\max_x \, \ell(x) / g(x)\), approximated via \(N\) candidates drawn from \(\ell\). Each density is a mixture of truncated Gaussians (or histograms for categoricals).

ASHA (Ray Tune)

Successive Halving at rung \(r \in \{r_0, r_0\eta, r_0\eta^2, \ldots\}\) promotes the top \(1/\eta\) fraction of trials: if trial \(i\) reaches rung \(r\) and ranks in the bottom \(1 - 1/\eta\), it is stopped. ASHA removes synchronisation barriers — a trial can be promoted as soon as \(\eta\) peers reach the same rung, even if others are still running.

$$\text{Promote } i \text{ at rung } r \iff f_i(r) \geq Q_{1/\eta}\!\left(\{f_j(r) : j \text{ reached } r\}\right)$$
⚠️ Common Misconception
Pruning is not the same as early stopping during a single run. Pruning is an inter-trial decision — it stops a trial to free resources for more promising configs. Within-trial early stopping (e.g., patience) operates independently and should still be used alongside pruning.

Key Takeaways & When to Use Each
🎯 Decision Guide
  • Use Optuna when you want zero-infrastructure Bayesian HPO on one machine with dynamic search spaces and built-in pruning callbacks (PyTorch, Keras, XGBoost, LightGBM).
  • Use Ray Tune when you have a multi-GPU or multi-node cluster and need population-based training, async scheduling, or integration with Ray Serve / RLlib.
  • Use W&B Sweeps when your team needs shared visibility, reproducibility, and rich visual analysis; best used alongside any training framework via the wandb callback.
  • Combine them: Optuna as searcher inside Ray Tune + W&B for logging is a common production stack.
