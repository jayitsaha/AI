LakeFS: Git-like Data Versioning for Data Lakes

Bringing atomic commits, branching, and merging to petabyte-scale object storage
Intermediate Data Engineering Version Control O(1) commit, O(1) branch
1
Understanding LakeFS
▼

What is it? LakeFS is an open-source tool that brings Git-like version control capabilities to data lakes (e.g., S3, ADLS, GCS). It allows data engineers and scientists to perform atomic commits, create isolated branches, merge changes, and revert to previous states of their data, all without copying data or impacting production workflows. This enables more reliable, collaborative, and experimental data pipelines.

Analogy: Imagine your entire data lake (terabytes of raw data, processed tables, ML features) is a single massive Git repository. You can branch off to experiment with a new ETL pipeline, add new features to your ML training set, or fix a bug in a data transformation, all in isolation. If your changes break something, you can simply revert. When ready, you merge your changes back to the "main" production data, knowing it's an atomic operation that won't corrupt anything mid-way. LakeFS provides this power without duplicating your petabytes of data.

💡 If you remember one thing

LakeFS provides Git-like semantics (commits, branches, merges, reverts) on top of object storage, enabling isolated data experimentation and atomic, reliable data delivery. It achieves this with zero-copy operations by managing metadata pointers to objects, not duplicating the actual data.

2
How It Works Internally
▼

The Challenge: Data Lakes vs. Git Repos

Traditional Git works by storing snapshots of text files. Data lakes are different: they contain massive, binary, often immutable objects (Parquet, ORC, CSV, images). Copying terabytes of data for every branch is prohibitively expensive and slow. Updating files in place is risky and breaks version history.

The LakeFS Solution: Metadata as the Source of Truth

LakeFS sits as a thin layer between your data applications (Spark, Flink, Pandas, etc.) and your object storage. Instead of manipulating files directly, applications interact with LakeFS endpoints (e.g., `s3:////`). LakeFS then translates these requests into reads and writes on the underlying object storage, but critically, it maintains its own metadata layer:

  1. Objects are immutable: When you "modify" a file, LakeFS actually writes a *new* object to a dedicated internal storage prefix (e.g., `s3:///data/`). The old object remains untouched.
  2. Commits are snapshots: A commit is a snapshot of the repository's state at a given point in time. It's a pointer to a manifest (a list of all paths and their corresponding immutable object IDs).
  3. Branches are pointers: A branch is simply a named pointer to a specific commit. Creating a branch is an O(1) metadata operation: just create a new pointer to an existing commit.
  4. Reads are resolved: When you read `s3://my-repo/feature-branch/data.parquet`, LakeFS looks up `feature-branch`'s head commit, finds the manifest for that commit, and resolves `data.parquet` to its physical object ID in storage, then redirects your read.

This architecture ensures that branches are truly zero-copy, commits are atomic, and reverts are instantaneous, as they only involve changing metadata pointers.

Design Decision: Why Not Just Use Object Storage Versioning?

Native object storage versioning (e.g., S3 Versioning) keeps multiple versions of an object, but it's per-object, not repository-wide. It lacks Git's critical features:

  • Atomic commits: No way to group multiple file changes into a single, consistent snapshot.
  • Branching/Merging: No concept of isolated development branches or merging changes back.
  • Data isolation: No way to query a consistent view of the data lake at a specific point in time across many objects.

LakeFS provides these missing features by layering a Git-like graph structure on top of object storage's immutability.

🔑 Key Property

LakeFS achieves zero-copy branching and atomic commits by treating all data objects as immutable. Any "change" to a file results in a new object being written, and commits/branches are simply metadata pointers to these immutable objects and their manifests.

3
Why It Works — The Core Concepts
▼

The Commit Graph: Directed Acyclic Graph (DAG)

At its heart, LakeFS builds a commit graph, similar to Git. Each commit is identified by a unique ID (a hash) and points to its parent commit(s). This forms a DAG, representing the full history of changes. A branch is merely a mutable pointer to a specific commit in this DAG.

$$\text{Commit}_C = \{ \text{ID: } c_h, \text{Parent: } p_h, \text{Timestamp}, \text{Message}, \text{Manifest: } M_h \}$$

Where \(M_h\) is a hash of a manifest file, which lists all object paths and their corresponding physical storage addresses (hashes of content). This means a commit effectively points to a frozen snapshot of the entire data lake's state.

Branching: Just a Pointer Move

When you create a new branch, say `feature-branch` from `main`, LakeFS simply creates a new named reference pointing to the same commit that `main` currently points to. No data is copied:

The new commit's manifest points to a mix of existing (unchanged) physical objects and new physical objects (for modified/added files) from both branches. Again, no data is duplicated unless a file's content actually changes.

⚠️ Data Consistency at Scale

The core challenge is ensuring atomicity and consistency. Without LakeFS, a multi-file update might leave the data lake in an inconsistent state if it fails halfway. LakeFS commits are atomic: either all changes are visible in a new snapshot, or none are. This guarantees data readers always see a complete, consistent view.

Key Takeaways
▼

When to use LakeFS:

  • You need isolated development environments for data (e.g., multiple data scientists working on the same datasets).
  • Your ETL/ML pipelines require atomicity and consistency for data delivery (e.g., ensuring a new version of a table is fully available or not at all).
  • You want to easily revert bad data changes without complex recovery procedures.
  • You need to reproduce past data states for debugging or auditing.
  • You're building CI/CD for data, where data validation and testing occur on isolated, versioned datasets.

When NOT to use (or consider alternatives):

  • Your data lake is very small or static, and simple object storage versioning suffices.
  • You only need basic data lineage, not full Git-like branching/merging.
  • You're primarily concerned with schema evolution rather than data content versioning (though LakeFS complements schema management tools).
  • You have extremely high-frequency, low-latency transactional workloads that require row-level locking (LakeFS operates at a file/object level).
💡 Big Picture

LakeFS transforms a raw, unversioned data lake into a robust, collaborative data platform. By applying Git's battle-tested workflow to data, it unlocks new levels of experimentation, reliability, and automation in data engineering and machine learning.

import lakefs_client
from lakefs_client.models import CommitCreation, BranchCreation, Merge
# --- 1. Configure LakeFS client ---
configuration = lakefs_client.Configuration(host="http://localhost:8000/api/v1")
configuration.username = "AKIAIOSFODNN7EXAMPLE"
configuration.password = "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
client = lakefs_client.ApiClient(configuration)
repo_api = lakefs_client.RepositoriesApi(client)
branches_api = lakefs_client.BranchesApi(client)
objects_api = lakefs_client.ObjectsApi(client)
repo_name = "my-data-lake"
# --- 2. Create a branch ---
# This is an O(1) metadata operation, no data copied
branches_api.create_branch(repo_name, BranchCreation(name="feature-A", source="main"))
print("Created branch 'feature-A' from 'main'")
# --- 3. Write/modify data on the branch ---
# Data is written to internal object storage, not directly to 'main'
objects_api.upload_object(repo_name, "feature-A", "data/customers.csv", content="id,name\n1,Alice\n2,Bob")
objects_api.upload_object(repo_name, "feature-A", "reports/new_report.csv", content="report_data")
print("Uploaded objects to 'feature-A'")
# --- 4. Commit changes to the branch ---
# Creates an atomic snapshot, updates branch pointer
commit_resp = branches_api.commit(
repo_name, "feature-A", CommitCreation(message="Add new report, update customers")
)
print(f"Committed to 'feature-A': {commit_resp.id}")
# --- 5. Read data from a specific branch/commit ---
# LakeFS resolves the correct object from the commit's manifest
content_main = objects_api.get_object(repo_name, "main", "data/customers.csv")
content_feature = objects_api.get_object(repo_name, "feature-A", "data/customers.csv")
print(f"Customers on main: {content_main.read().decode()}")
print(f"Customers on feature-A: {content_feature.read().decode()}")
# --- 6. Merge feature branch into main ---
# Creates a new commit on 'main', updating its pointer atomically
merge_resp = branches_api.merge_into_branch(
repo_name, source_branch="feature-A", destination_branch="main", merge=Merge(message="Merge feature-A")
)
print(f"Merged 'feature-A' to 'main': {merge_resp.reference}")
