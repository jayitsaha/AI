Understanding Two-Tower Feature Design
▼

What is it? A two-tower model has two independent neural networks — a user tower \(f_\theta\) and an item tower \(g_\phi\) — that each map their own raw features into a shared \(d\)-dimensional embedding space. A match score is the inner product \(s(u,i) = f_\theta(x_u) \cdot g_\phi(x_i)\). The entire feature-engineering discipline of two-tower retrieval boils down to one rule: every feature must belong to exactly one tower — it must be computable from the user alone, or the item alone, never both.

Analogy: Think of a matchmaking service that pre-prints a "personality card" for every client and a separate "profile card" for every listing, then matches them later by comparing cards. The cards must be produced independently — you can't ask "how did this specific client feel about this specific listing last time?" while printing either card, because that question needs both people in the room. That fact — printed independently, compared later — is exactly what makes it possible to print a million profile cards once and reuse them for every client that walks in.

💡 If you remember one thing

Feature engineering for two-tower models isn't just "pick good features" — it's "partition the world into user-only and item-only signals," because the model architecture itself, $$s(u,i) = \mathbf{e}_u \cdot \mathbf{e}_i, \quad \mathbf{e}_u = f_\theta(x_u), \; \mathbf{e}_i = g_\phi(x_i)$$ mathematically cannot consume any feature that depends on both \(u\) and \(i\) at once.

2
How Each Tower's Features Are Built
▼

User Tower — features known before you pick an item

The user tower ingests everything describable about the user and the current request without reference to any specific candidate item: a learned user-ID embedding, pooled/aggregated engagement history (e.g. mean or attention-pooled embeddings of recently clicked items), demographic or account attributes, and request-time context (time of day, device, location, session length). All of these change per-request but never per-candidate — they are the same for every item being scored in that request.

Item Tower — features that never look at the user

The item tower ingests only what describes the item itself: an item-ID embedding, categorical/taxonomy features (category, brand, price bucket), and content-derived features (text/title embeddings, image embeddings, aggregate popularity stats). Crucially these features are static per item (or slowly changing), which is what lets them be computed once, offline, for the entire catalog.

🔑 Key Property

Because neither tower ever reads the other side's ID, the item tower's output is identical regardless of which user is asking. That single property is what turns retrieval into an offline-indexable, sub-linear approximate nearest neighbor (ANN) search problem instead of an \(O(|\text{catalog}|)\) scan per request.

3
Why It Works — The Math of Decomposability
▼

The factorization requirement

A ranking model with cross features (e.g. a wide-and-deep or GBDT ranker) can learn an arbitrary joint function \(s(u,i) = h_\psi(x_u, x_i)\) — powerful, but it must be evaluated for every candidate item at serving time, which is only feasible over a few hundred pre-filtered candidates. Two-tower retrieval trades some of that expressiveness for scale by forcing:

$$s(u,i) = f_\theta(x_u)^\top g_\phi(x_i) = \sum_{k=1}^{d} e_{u,k}\, e_{i,k}$$

This factorized form is exactly what Maximum Inner Product Search (MIPS) / ANN libraries (FAISS, ScaNN, HNSW) require: an index built once over \(\{g_\phi(x_i)\}_{i \in \text{catalog}}\), queried with a single vector \(f_\theta(x_u)\) at request time in \(O(\log N)\) or better.

Why a cross feature breaks it

Suppose you add a feature \(c(u,i)\) — say, "number of times user \(u\) previously clicked item \(i\)" — into the user tower's input. Now \(f_\theta\) depends on \(i\): \(f_\theta(x_u, i)\). The score becomes \(h(u,i) = f_\theta(x_u, i)^\top g_\phi(x_i)\), which can no longer be written as (a fixed user vector) · (a fixed item vector), because the "user vector" itself changes per candidate item:

$$s(u,i) \neq f_\theta(x_u)^\top g_\phi(x_i) \quad\text{once } f_\theta \text{ depends on } i \;(\text{or } g_\phi \text{ on } u)$$

You would then need to re-run the user tower once per candidate item — exactly the \(O(N)\) cost two-tower retrieval was built to avoid. Cross features are not banned because they're low-quality signal (they're often the highest-quality signal) — they're banned because the serving architecture cannot amortize them. They belong in the downstream re-ranker, which only scores a short retrieved list.

⚠️ Common Pitfall

A subtle version of this mistake: putting a query-time item popularity computed against this user's session into the item tower, or a user segment computed from their interaction with this specific item into the user tower. If a feature's value would change depending on which item/user is being paired with it, it is a cross feature — no matter which tower you technically place it in.

Key Takeaways
▼

User-tower feature checklist:

  • User-ID / account embedding (learned lookup table)
  • Pooled interaction history (mean, sum, or attention pooling over recent item embeddings)
  • Request-time context: time of day, device, surface, geo, session signals
  • Demographic / declared preferences — anything true regardless of the candidate item

Item-tower feature checklist:

  • Item-ID embedding
  • Categorical taxonomy: category, brand, price tier
  • Content embeddings: title/description text, image, audio
  • Item-only aggregate stats: global popularity, recency, average rating — anything true regardless of who's asking

Never in either tower: co-occurrence counts, this-user-this-item click/purchase history, session-specific item affinity, or any feature whose value is a function of the pair \((u,i)\). Route those to the re-ranking stage instead.

💡 The trade-off in one line

Two-tower retrieval sacrifices cross-feature expressiveness for sub-linear serving over millions of items; the downstream re-ranker gets the cross features back over a shortlist of a few hundred candidates from the tower's ANN search.

class UserTower(nn.Module):
def forward(self, user_id, history_ids, ctx):
id_emb = self.user_id_emb(user_id) # [B, d_id]
hist_emb = self.item_id_emb(history_ids).mean(dim=1) # pooled, [B, d_id]
ctx_feat = ctx # [B, d_ctx] time/device/etc.
x = torch.cat([id_emb, hist_emb, ctx_feat], dim=-1)
return F.normalize(self.mlp(x), dim=-1) # e_u, no item info anywhere
class ItemTower(nn.Module):
def forward(self, item_id, category, content_emb):
id_emb = self.item_id_emb(item_id)
cat_emb = self.category_emb(category)
x = torch.cat([id_emb, cat_emb, content_emb], dim=-1)
return F.normalize(self.mlp(x), dim=-1) # e_i, no user info anywhere
# Serving: build the ANN index OFFLINE, once, over the whole catalog
item_embs = item_tower(all_item_ids, all_categories, all_content_embs)
ann_index = faiss.IndexFlatIP(d)
ann_index.add(item_embs.numpy())
# Serving: at request time, ONLY the user tower runs live
e_u = user_tower(user_id, history_ids, ctx)
top_k_scores, top_k_items = ann_index.search(e_u.numpy(), k=200)
