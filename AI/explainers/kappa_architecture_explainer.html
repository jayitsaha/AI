1
Understanding Kappa Architecture
▼

What is it? Kappa architecture is a way of building data pipelines with exactly one processing path: events land in an immutable, append-only log (Kafka is the canonical example), and a single stream-processing job reads that log to produce every view the business needs. There is no separate "batch layer" running nightly jobs on historical data and no "speed layer" giving approximate real-time answers that a batch job later corrects — there is only the log and the code that reads it.

Analogy: Think of a bank ledger. Every transaction is written once, in order, and never erased. If you discover your interest-calculation formula had a bug, you do not build a second machine that recomputes historical balances differently from the live teller system. You fix the formula and re-run it over the same ledger from the beginning. The ledger IS the source of truth; "batch" is simply "replay the ledger with today's logic."

💡 If you remember one thing

In Kappa architecture, batch processing is just stream processing replayed from an earlier offset. Reprocessing does not mean "run a different system" — it means "start a new version of the same stream job at offset 0 (or the oldest retained offset) and let it catch up to the tail."

2
How It Works Internally
▼

The Problem It Replaced: Lambda Architecture

Nathan Marz's Lambda architecture (2011) ran the same logic twice: a batch layer periodically recomputed exact views over the full historical dataset (correct, but hours stale), and a speed layer processed only the newest events for a low-latency, approximate view that the batch layer would later overwrite. A serving layer merged both. This worked, but it meant maintaining two codebases — one in Spark/Hadoop, one in Storm/Flink — that had to compute the same aggregation logic and inevitably drifted apart, producing subtly different numbers between the "fast but approximate" and "slow but correct" answers.

The Kappa Idea (Jay Kreps, 2014)

Kreps observed that if your log retains enough history and your stream engine is fast enough, the batch layer is redundant: a batch computation is nothing more than a stream computation run over a bounded, already-closed range of the log. So delete the batch layer entirely. Keep one continuous stream job as the only codebase. When business logic changes or a bug is found, you do not patch the running job in place — you deploy a new, independently versioned job that subscribes to the same topic from its earliest available offset, writes to a new output table, and catches up to the live tail while the old job keeps serving traffic. Once the new job's lag reaches zero, you atomically switch reads over to it and decommission the old version.

🔑 Key Property

Because the "batch" recomputation and the "live" computation are executed by the same code path against the same log, Kappa architecture eliminates the entire class of batch/speed-layer inconsistency bugs — there is nothing left to disagree with itself.

Design Decision: Why Replay Instead of a Batch Layer?

Alternatives considered: (a) keep Lambda's dual layers and invest in code-sharing libraries — reduces duplication but not the operational burden of two runtime systems; (b) snapshot state periodically and only replay the delta — faster reprocessing but adds a second mechanism (snapshotting) that itself needs to be correct. Kappa's answer is deliberately the simplest one: make the log retention window long enough (or tiered to cheap storage) that a full replay is always possible, and accept the cost of re-reading history in exchange for a single, provably consistent codebase.

Why It Works — The Formal Model
▼

Model the log as an ordered, unbounded sequence of events with monotonically increasing offsets. Let \(\text{tail}(t)\) be the newest committed offset at time \(t\), growing at ingestion rate \(\lambda\) (events/sec). A consumer (stream job) sits at position \(\text{off}_c(t)\). Its lag is:

$$\text{Lag}_c(t) = \text{tail}(t) - \text{off}_c(t)$$

A brand-new job version starts at \(\text{off}_c(0) = \max(0,\ \text{tail} - \lambda \cdot T_{retention})\) — offset 0 if everything is retained, otherwise the oldest surviving offset. If the replaying job reads at a bounded multiple \(k\) of the live ingestion rate (bounded so it does not starve other consumers or the broker), its time-to-catch-up is:

$$\text{ETA} = \frac{\text{Lag}_c(t)}{\lambda \cdot k - \lambda} \approx \frac{\text{Lag}_c(t)}{\lambda (k-1)} \quad (k>1)$$

Reprocessing is only physically possible while the desired start offset still exists in the log:

$$\text{replayable} \iff \text{off}_{start} \ge \text{tail}(t) - \lambda \cdot T_{retention}$$

This is Kappa's one hard constraint: the retention window \(T_{retention}\) (time-based or size-based) bounds exactly how far back "batch" can ever reach through the raw log alone.

⚠️ Common Pitfall

Kappa's "you can always reprocess" promise silently breaks once a desired replay start falls outside \(T_{retention}\) — the raw bytes are physically deleted (or compacted away). Teams work around this with tiered/infinite retention (e.g., Kafka tiered storage to object storage) or by periodically landing raw events into a cheap columnar store (S3/Iceberg) that a stream engine can still treat as a bounded "replay source" — without this, unlimited historical reprocessing is not actually free.

Key Takeaways
▼

When to use Kappa:

  • Your stream engine (Flink, Kafka Streams, ksqlDB) can express every view you need — including historical recomputation — with acceptable latency
  • You can afford a retention window long enough for realistic reprocessing needs, or you tier cold data to cheap storage
  • You want one codebase and one operational surface instead of two

When NOT to use:

  • You need enormous one-off historical joins or ML feature backfills that batch engines (Spark) handle far more cheaply than a stream engine replaying at bounded speed
  • Retention costs are prohibitive and you have no tiered/cold-storage replay path
  • Your workloads are dominated by ad-hoc batch analytics, not continuous live views
💡 The One-Line Contrast

Lambda = batch layer + speed layer + a merge/serving layer reconciling two answers. Kappa = one log + one versioned stream job. Kappa is what you get when you delete the batch layer because the log itself, replayed, already is the batch layer.

StreamsBuilder b1 = new StreamsBuilder();
b1.stream("events-topic")
.groupByKey()
.aggregate(() -> 0L, (k, v, agg) -> agg + v.amount)
.toTable("view-v1"); // materialized view, app id = job-v1
// A bug is found in the aggregation logic -> fix it, ship v2
// v2 topology: SAME source topic, reset to earliest retained offset
Properties propsV2 = baseProps();
propsV2.put(APPLICATION_ID_CONFIG, "job-v2");
propsV2.put(AUTO_OFFSET_RESET_CONFIG, "earliest"); // replay from start!
StreamsBuilder b2 = new StreamsBuilder();
b2.stream("events-topic")
.groupByKey()
.aggregate(() -> 0L, (k, v, agg) -> agg + v.correctedAmount)
.toTable("view-v2"); // NEW output, does not touch view-v1
// job-v2 runs alongside job-v1, consuming at k x normal rate
// until lag(job-v2) == 0, i.e. it has caught up to the live tail
while (lagOf("job-v2") > 0) { sleep(pollInterval); }
// Atomic cutover: point reads at the new view, retire the old job
servingLayer.repoint("view-v1", "view-v2");
jobRegistry.decommission("job-v1");
