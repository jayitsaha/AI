1
Understanding Data Sources
▼

What is this? Before any model can be trained, data must be collected from the real world. Data sources are the origin points — APIs that serve structured JSON, websites whose HTML can be parsed, relational databases holding transactional records, and data lakes storing raw files at petabyte scale. Knowing when to use each (and how to ingest reliably from each) is the first job of a data engineer.

Analogy: Think of building a reservoir (the training dataset). You can fill it from four sources: a municipal water pipe with metered flow (API — controlled, rate-limited JSON), rainwater collected from rooftops (web scraping — unstructured, must be filtered), a natural spring underground (databases — structured, deep, requires pumping), and a wide river delta (data lake — massive volume, various formats). The ingestion pipeline is the plumbing that connects all four to one reservoir.

💡 If you remember one thing

Every training dataset starts as raw bytes from one or more of these four source types. The source's structure, volume, velocity, and legal constraints determine the ingestion strategy — not the other way around.

The Four Source Types at a Glance

API Paginated JSON/XML over HTTP — rate-limited, authenticated, versioned. Best for real-time or operational data from third-party services.

Scraping BeautifulSoup (HTML parsing) or Scrapy (full crawl framework) — extracts structure from unstructured web pages. Ethics and robots.txt apply.

Database SQL queries (OLTP/OLAP) — structured, relational, transactional. Requires CDC (Change Data Capture) or snapshot reads to avoid production load.

Data Lake Raw files (CSV, Parquet, JSON, images) in object storage (S3, GCS, ADLS). Schema-on-read, petabyte-scale, columnar formats for ML efficiency.

2
How Each Source Type Works Internally
▼

REST & GraphQL APIs

A REST API exposes resources as HTTP endpoints. Pagination comes in three forms: offset-based (?page=2&per_page=100), cursor-based (?cursor=eyJpZCI6MTAwfQ==), and link-header (RFC 5988). Cursor-based is preferred for large, mutable datasets — it is stable under concurrent writes, whereas offset pagination drifts when rows are inserted.

Rate limiting is enforced via HTTP 429 responses with Retry-After headers or X-RateLimit-Remaining counters. Authentication uses Bearer tokens (OAuth 2.0), API keys (Authorization: Bearer {token}), or mTLS for internal services.

GraphQL APIs let the client specify the exact fields needed (introspection via __schema) — this reduces over-fetching but requires query construction. Mutations are writes; queries and subscriptions are reads.

🔑 Pagination arithmetic

For offset pagination with \(N\) total records and page size \(k\): total pages \(= \lceil N/k \rceil\). Request \(i\) fetches rows \([ik, \min((i+1)k, N))\). Cursor-based: each response returns the opaque next-cursor; stop when has_next = false.

Web Scraping: BeautifulSoup vs Scrapy

BeautifulSoup is a pure HTML/XML parser built on lxml or html.parser. It builds a parse tree from raw HTML bytes, letting you navigate by tag, CSS selector, or XPath. It has no scheduler or crawler — you supply URLs and call requests.get() yourself.

Scrapy is a full asynchronous crawl framework. Its event loop (Twisted) handles concurrent requests, throttling (AutoThrottle), middleware (cookies, proxies, retry), item pipelines (validate → persist), and a built-in duplicate URL filter (fingerprinting via canonical URL hash). Robots.txt compliance is baked in via ROBOTSTXT_OBEY = True.

⚠️ Ethics & Legality

Always check robots.txt (/robots.txt path), the site's Terms of Service, and applicable law (e.g., CFAA in the US, GDPR in the EU). Scraping personally identifiable information without consent is a data governance violation, not just a technical choice.

Databases: OLTP Reads for ML

Relational databases (PostgreSQL, MySQL) store normalized transactional records. For ML ingestion, avoid long-running queries on the primary — use read replicas or snapshots. Two patterns: (1) Full snapshot: SELECT * FROM orders WHERE updated_at < :cutoff — simple but expensive. (2) CDC (Change Data Capture): stream WAL (Write-Ahead Log) events via Debezium → Kafka → landing zone — incremental, low overhead.

Columnar analytical databases (BigQuery, Redshift, Snowflake) partition data by date and cluster by key columns — use partition filters to minimize scan cost. A query on 100 GB partitioned by day with a date predicate may scan only 500 MB.

Data Lakes: Object Storage + Columnar Formats

A data lake stores files in object storage (S3, GCS) organized by partition keys (e.g., s3://bucket/events/year=2024/month=06/day=15/part-0001.parquet). Parquet is the dominant format: columnar layout, dictionary encoding, RLE/bit-packing compression, Snappy or ZSTD codec. Reading only two columns from a 200-column Parquet file scans roughly \(2/200\) of the bytes vs. CSV.

$$\text{Read bytes} \approx \frac{|\text{projected columns}|}{|\text{total columns}|} \times \text{file size} \quad \text{(columnar benefit)}$$

Delta Lake / Apache Iceberg / Apache Hudi add ACID transactions, schema evolution, and time-travel on top of raw Parquet — critical for ML feature stores where historical consistency matters.

REST API: Paginated ingestion with retry & rate-limit handling

import time, requests
from typing import Iterator

def paginate_api(base_url: str, token: str, page_size: int = 200) -> Iterator[dict]:
    """
    Cursor-based paginator for a REST API.
    Yields one record dict at a time.
    Handles 429 (rate limit) with Retry-After backoff.
    """
    headers = {"Authorization": f"Bearer {token}"}
    params  = {"limit": page_size}
    session = requests.Session()
    session.headers.update(headers)

    while True:
        resp = session.get(base_url, params=params, timeout=30)
        if resp.status_code == 429:                   # rate-limited
            retry_after = int(resp.headers.get("Retry-After", 5))
            time.sleep(retry_after)
            continue
        resp.raise_for_status()
        data = resp.json()

        for record in data["items"]:
            yield record                              # one record at a time — memory-efficient

        cursor = data.get("next_cursor")
        if not cursor:
            break                                     # no more pages
        params["cursor"] = cursor

# Usage: stream straight into Parquet writer (never materialises full dataset in RAM)
import pyarrow as pa, pyarrow.parquet as pq
schema  = pa.schema([("id", pa.int64()), ("value", pa.float32())])
writer  = pq.ParquetWriter("output.parquet", schema)
batch   = []
for rec in paginate_api("https://api.example.com/data", token="SECRET"):
    batch.append(rec)
    if len(batch) >= 1000:
        writer.write_batch(pa.RecordBatch.from_pylist(batch, schema=schema))

Web Scraping: BeautifulSoup (one-page parser)

from bs4 import BeautifulSoup
import requests

def scrape_product_listing(url: str) -> list[dict]:
    """Parse an e-commerce product listing page."""
    resp = requests.get(url, headers={"User-Agent": "Mozilla/5.0"}, timeout=15)
    resp.raise_for_status()

    soup = BeautifulSoup(resp.text, "lxml")          # lxml is faster than html.parser

    products = []
    for card in soup.select("div.product-card"):     # CSS selector
        products.append({
            "name":  card.select_one("h2.name").get_text(strip=True),
            "price": float(card["data-price"]),      # data attribute
            "url":   card.find("a")["href"],
        })
    return products

Scrapy: Full crawler with item pipeline

# myproject/spiders/catalog_spider.py
import scrapy

class CatalogSpider(scrapy.Spider):
    name = "catalog"
    start_urls = ["https://example.com/catalog"]
    custom_settings = {
        "ROBOTSTXT_OBEY": True,          # respect robots.txt
        "AUTOTHROTTLE_ENABLED": True,    # auto-adjust concurrency
        "AUTOTHROTTLE_TARGET_CONCURRENCY": 2.0,
        "DOWNLOAD_DELAY": 1,             # floor delay between requests
    }

    def parse(self, response):
        # Extract current page items
        for product in response.css("div.product"):
            yield {
                "name":  product.css("h2::text").get(),
                "price": product.css("span.price::text").get(),
                "url":   response.urljoin(product.css("a::attr(href)").get()),
            }
        # Follow pagination
        next_page = response.css("a.next-page::attr(href)").get()
        if next_page:
            yield response.follow(next_page, self.parse)

import psycopg2, pandas as pd

def snapshot_table(conn_str: str, table: str, cutoff: str) -> pd.DataFrame:
    """Full snapshot with a cutoff timestamp — run on read replica."""
    query = f"""
        SELECT * FROM {table}
        WHERE updated_at >= %s
        ORDER BY updated_at
    """
    with psycopg2.connect(conn_str) as conn:
        return pd.read_sql(query, conn, params=(cutoff,))

Data Lake: Reading Parquet with column pruning & pushdown

import pyarrow.parquet as pq
import pyarrow.dataset as ds

# Column projection: only read needed columns (columnar advantage)
dataset = ds.dataset("s3://my-bucket/events/year=2024/", format="parquet")
table   = dataset.to_table(
    columns=["user_id", "event_type", "ts"],          # 3 of 40 cols → ~7.5% bytes
    filter=ds.field("event_type") == "purchase",      # predicate pushdown into file
)
df = table.to_pandas()
print(f"Rows: {len(df)}, Memory: {df.memory_usage(deep=True).sum() / 1e6:.1f} MB")

# Delta Lake with time-travel (requires deltalake package)
from deltalake import DeltaTable

df_v5 = dt.load_as_of_version(5).to_pandas()   # read historical version
🔑 Production Gotcha

Never read from the OLTP primary for ML — always a read replica or a snapshot export. A single SELECT * on a 10M-row table can saturate I/O and spike p99 latency for live traffic.

🎯 Decision Guide

Use APIs when a vendor provides official access — always prefer this over scraping the same site.
Use scraping only when no API exists, ToS permits it, and the data is not personal.
Use databases for entity-level labels (users, products, orders) from your own systems — use CDC for freshness.
Use data lakes as the canonical long-term store; land all other sources into the lake first, then query from there.

6
Key Takeaways
▼
  • Data quality determines model quality — garbage-in, garbage-out applies before any model exists.
  • Always land raw data first (Bronze/Raw layer), then clean (Silver), then feature-engineer (Gold) — the medallion architecture.
  • Cursor-based API pagination is more robust than offset pagination for mutable datasets.
  • Scrapy's AutoThrottle + ROBOTSTXT_OBEY are non-negotiable for production crawlers.
  • Parquet + predicate pushdown can reduce I/O by 10–100x vs CSV for wide tables with selective queries.
  • Delta Lake / Iceberg add ACID semantics and time-travel on top of raw Parquet — use them for ML feature stores.
  • The landing zone is the "single source of truth" — all downstream transformations are reproducible from it.
💡 The data engineering mindset

Think of data ingestion as a contract: the source has a schema, a latency guarantee, and a reliability SLA. Your pipeline must degrade gracefully when any of these breaks — dead-letter queues for bad records, circuit breakers for APIs, schema registries for lakes.
