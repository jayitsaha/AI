Chunking (Shallow Parsing)

Grouping tokens into flat, non-recursive phrases (NP, VP, PP) without building a full parse tree
Foundational NLP Sequence Labeling O(n)
1
Understanding Chunking
▼

What is it? Chunking (also called shallow parsing) takes a part-of-speech (POS) tagged sentence and groups adjacent tokens into short, non-overlapping, non-recursive phrases — noun phrases (NP), verb phrases (VP), prepositional phrases (PP) — without figuring out how those phrases attach to each other. It stops one level short of a full syntactic parse tree.

Analogy: Imagine highlighting a sentence with a marker: you draw a box around "the quick brown fox" and call it one unit, another box around "jumps" as another unit, without drawing arrows connecting the boxes to explain the full sentence structure. Full parsing is like an org chart showing who reports to whom; chunking is just circling the departments.

Chunking sits between POS tagging (per-token labels) and full constituency/dependency parsing (a complete recursive tree). It is fast — linear time — and gives "just enough" structure for tasks like named-entity recognition, information extraction, and shallow feature engineering for downstream classifiers.

💡 If you remember one thing

Chunking = flat bracketing of a POS tag sequence using a small grammar (often regular expressions over tags), producing non-recursive phrases tagged with the IOB scheme: \(B\text{-}NP\), \(I\text{-}NP\), \(O\), etc. It trades the expressiveness of a full parse tree for speed and robustness.

2
How Chunking Works Internally
▼

Input: A POS-Tagged Sequence

Chunking never looks at raw words directly — it operates on the POS tag stream, e.g. \(\langle DT, JJ, JJ, NN, VBZ, IN, DT, JJ, NN \rangle\) for "The quick brown fox jumps over the lazy dog". This abstraction is what makes chunking generalize: the same rule that chunks "the lazy dog" also chunks "a red car".

The Grammar: Regular Expressions Over Tags

A chunk grammar is a small set of patterns like NP: {<DT>?<JJ>*<NN>}, meaning "an optional determiner, zero or more adjectives, then a noun." Because these patterns are regular expressions (no recursion, no self-reference), the whole grammar can be compiled into a finite-state machine and applied to the tag string with a single linear scan.

The Scanning Process

A chunker walks the tag sequence left to right. At each position it asks: "does the grammar's pattern match starting here?" If yes, it greedily extends the match as far as the pattern allows, closes the chunk, and resumes scanning right after it. Tokens that match no pattern are left as \(O\) (outside any chunk).

Output: IOB-Tagged Tokens

The result is encoded token-by-token using IOB2 tags: B-NP marks the first token of a chunk, I-NP marks subsequent tokens inside the same chunk, and O marks tokens outside any chunk. This turns "bracketing" into a per-token sequence-labeling problem — which is exactly why modern chunkers are often trained as classifiers (CRFs, BiLSTM-CRF, or fine-tuned transformers) rather than hand-written regexes.

🔑 Design Decision: Why Regular, Not Context-Free?

A full CFG parser must resolve global ambiguity and attachment (e.g., PP-attachment), which is expensive and error-prone. By restricting the grammar to regular (non-recursive) patterns, chunking sacrifices nesting but gains \(O(n)\) time, robustness to ungrammatical input, and easy retraining as a token classifier.

3
Why It Works — The Formal View
▼

Chunking as a Regular Language

Let \(\Sigma\) be the alphabet of POS tags. A chunk grammar rule such as \(NP \to D?\,J^*\,N\) defines a regular language \(L_{NP} \subseteq \Sigma^*\). Because regular languages are closed under concatenation and Kleene star, the whole grammar (NP, VP, PP rules together) can be compiled into a single deterministic finite automaton (DFA) that scans a tag string of length \(n\) in one pass.

$$\text{time complexity} = O(n) \quad \text{vs. } O(n^3) \text{ for CKY-style CFG parsing}$$

Chunking as Sequence Labeling

Equivalently, chunking can be cast as finding the most likely IOB tag sequence \(\hat{y}\) given tags/words \(x\):

$$\hat{y} = \underset{y \in \{B\text{-}NP, I\text{-}NP, \dots, O\}^n}{\operatorname{argmax}} \; P(y \mid x)$$

A regex chunker sets \(P(y\mid x)\) deterministically from pattern matches. A learned chunker (CRF or neural) estimates \(P(y \mid x)\) from data and can be evaluated exactly like any tagger: precision, recall, and \(F_1\) computed over predicted chunk spans against gold spans.

$$F_1 = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}, \qquad \text{Precision} = \frac{|\text{correct chunks}|}{|\text{predicted chunks}|}$$

The IOB2 Validity Invariant

A well-formed IOB2 sequence never has an \(I\text{-}X\) tag immediately after \(O\) or after \(I\text{-}Y\) / \(B\text{-}Y\) with \(Y \ne X\) — every chunk must open with a \(B\) tag. This constraint is exactly what a Viterbi decoder or CRF's transition matrix enforces when chunking is learned rather than rule-based.

⚠️ Common Pitfall

Chunking is non-recursive by construction — a chunker cannot represent "NP containing a PP containing an NP" as nested structure. It can only flatly tag \(B\text{-}NP, I\text{-}NP, B\text{-}PP, B\text{-}NP, I\text{-}NP\) side by side. If your downstream task truly needs attachment/nesting (e.g., "the man with the telescope saw..."), you need a full parser, not a chunker.

Key Takeaways
▼

When to use chunking:

  • You need fast, robust phrase boundaries (NP/VP/PP) without full syntax — e.g. feature extraction for NER or IE pipelines
  • Input may be noisy or ungrammatical, where a full parser would fail catastrophically
  • You need a lightweight preprocessing step before a heavier neural model, or a classic baseline for span extraction

When NOT to use:

  • You need attachment decisions (which PP modifies which NP) — use a full constituency or dependency parser
  • The downstream task needs recursive structure (nested clauses, coordination scope)
  • Modern pipelines often replace rule-based chunking with a fine-tuned token classifier (BiLSTM-CRF, BERT+CRF) trained directly on IOB-labeled data such as CoNLL-2000
💡 Hierarchy

POS tagging (per-token labels) \(\subset\) Chunking (flat, non-recursive phrases via IOB tags) \(\subset\) Full parsing (recursive constituency/dependency tree). Each stage adds structure at the cost of complexity and brittleness.

Code Trace
▼
import re
# Tokens + Penn Treebank POS tags
tokens = ["The","quick","brown","fox","jumps","over","the","lazy","dog"]
tags = ["DT","JJ","JJ","NN","VBZ","IN","DT","JJ","NN"]
# Collapse tags to single symbols so the grammar is a plain regex
SYMBOL = {"DT":"D","JJ":"J","NN":"N","VBZ":"V","VBD":"V","IN":"I"}
symbols = "".join(SYMBOL[t] for t in tags) # -> "DJJNVIDJN"
# Regex grammar (regular language over POS symbols)
NP_RULE = re.compile(r"D?J*N") # {<DT>?<JJ>*<NN>}
VP_RULE = re.compile(r"V") # {<VBZ|VBD>}
PP_RULE = re.compile(r"I") # {<IN>}
def chunk(symbols, include_vp_pp=True):
claimed = [False] * len(symbols)
spans = []
for m in NP_RULE.finditer(symbols): # single linear scan
s, e = m.start(), m.end()
spans.append(("NP", s, e))
for i in range(s, e): claimed[i] = True
if include_vp_pp:
for i, sym in enumerate(symbols):
if claimed[i]: continue
if VP_RULE.fullmatch(sym): spans.append(("VP", i, i+1))
elif PP_RULE.fullmatch(sym): spans.append(("PP", i, i+1))
return sorted(spans, key=lambda s: s[1])
def to_iob(spans, n):
iob = ["O"] * n
for label, s, e in spans:
iob[s] = f"B-{label}"
for i in range(s+1, e): iob[i] = f"I-{label}"
return iob
spans = chunk(symbols)
print(list(zip(tokens, to_iob(spans, len(tokens)))))
# [('The','B-NP'), ('quick','I-NP'), ('brown','I-NP'), ('fox','I-NP'),
# ('jumps','B-VP'), ('over','B-PP'),
# ('the','B-NP'), ('lazy','I-NP'), ('dog','I-NP')]
# Production usage: NLTK's RegexpParser wraps this same idea
import nltk
grammar = "NP: {<DT>?<JJ>*<NN>}"
cp = nltk.RegexpParser(grammar)
tree = cp.parse(list(zip(tokens, tags))) # -> nltk.Tree, chunks as subtrees
