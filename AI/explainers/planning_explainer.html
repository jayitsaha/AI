1
Understanding Planning & Task Decomposition
▼

What is planning in AI? Planning is the process of finding a sequence of actions that transforms an initial state into a desired goal state. For an AI agent (e.g., a robot, a game character, a virtual assistant), this means figuring out "what to do next" to achieve a high-level objective within its environment.

Why task decomposition? Real-world goals are rarely single, atomic actions. "Make coffee" or "clean the house" are complex goals involving many sub-goals and actions. If an agent tries to find a single, long sequence of primitive actions for such a goal, the search space becomes astronomically large, making the problem intractable. Task decomposition breaks a complex problem into smaller, more manageable sub-problems, each with its own sub-goals.

Analogy: Imagine preparing a multi-course meal. The top-level goal is "Serve Dinner." This immediately decomposes into "Prepare Appetizer," "Cook Main Course," "Bake Dessert." Each of these then further decomposes: "Cook Main Course" might become "Chop Vegetables," "Sauté Meat," "Make Sauce." This hierarchical breakdown is intuitive for humans and essential for efficient AI planning.

💡 If you remember one thing

Planning is fundamentally a search problem in a state space. Task decomposition and hierarchical planning make this search tractable by pruning vast portions of the search space, focusing on relevant sub-goals and abstract actions first, then filling in the details.

2
How It Works: Flat vs. Hierarchical Planning
▼

Plan-and-Solve (Flat Planning)

In traditional "flat" planning, the agent's goal is to find a sequence of primitive actions (actions that can be directly executed in the environment) that leads from the initial state to the goal state. This is often modeled as a search problem (e.g., A*, BFS, DFS) in the state space. The planner considers all possible primitive actions at each step, trying to build a path:

  • Input: Initial state, goal state, set of primitive actions.
  • Output: A single sequence of primitive actions.
  • Challenge: For complex problems, the state space can be enormous, leading to a combinatorial explosion and extremely long planning times.

Hierarchical Planning (HTN)

Hierarchical Task Network (HTN) planning introduces an explicit hierarchy of tasks. Instead of directly searching for primitive actions, the planner first decomposes high-level, non-primitive tasks into smaller sub-tasks or primitive actions. This process continues until all tasks are broken down into primitive actions.

  • Tasks: Can be primitive (directly executable) or non-primitive (requiring decomposition).
  • Methods: Rules that specify how a non-primitive task can be decomposed into an ordered (or partially ordered) set of sub-tasks and primitive actions. Each method has preconditions that must be met to apply it.
  • Operators: Primitive actions with preconditions and effects (similar to flat planning).

The HTN planner searches for a sequence of method applications and primitive actions that decompose the initial high-level goal into a sequence of executable primitive actions, while respecting all preconditions.

Key Differences & Advantages

The core difference is that flat planning searches through a space of *states*, while HTN planning searches through a space of *plans* (specifically, task decompositions). HTN planning leverages domain knowledge embedded in the methods to guide the search, making it far more efficient for complex, real-world problems. It mimics how humans approach complex problems by first outlining major steps, then filling in the details.

🔑 Key Property

Hierarchical planning transforms the problem from "what primitive action to take next?" to "which method should I use to decompose this high-level task?". This shift dramatically reduces the effective branching factor in the search space, making planning tractable for problems that would be impossible for flat planners.

3
Why It Works: Formalisms & Benefits
▼

Formalizing Planning: States, Actions, and Goals

At its core, planning can be described by:

  • A set of possible states \(S\).
  • A set of actions \(A\), where each action \(a \in A\) has:
    • Preconditions \(Pre(a)\): a set of conditions that must be true in the current state for \(a\) to be applicable.
    • Effects \(Eff(a)\): a set of changes to the state that result from executing \(a\).
  • An initial state \(s_0 \in S\).
  • A goal condition \(G\): a set of conditions that must be true in a state for it to be a goal state.

A plan \(\pi = (a_1, a_2, \dots, a_k)\) is a sequence of actions that, when executed starting from \(s_0\), leads to a state \(s_k\) satisfying \(G\).

Hierarchical Task Networks (HTNs) Formalism

HTNs extend this by introducing tasks and methods:

  • A set of tasks \(T = T_P \cup T_C\), where \(T_P\) are primitive tasks (executable actions) and \(T_C\) are compound (non-primitive) tasks.
  • A set of methods \(M\), where each method \(m \in M\) is a rule for decomposing a compound task \(t_c \in T_C\). A method \(m\) for \(t_c\) has:
    • Preconditions \(Pre(m)\): conditions for applying the method.
    • Decomposition \(Dec(m)\): an ordered list of sub-tasks \((t_1, t_2, \dots, t_j)\) that replace \(t_c\).

The planning problem is to find a sequence of methods and primitive tasks that reduces the initial compound task into an executable sequence of primitive tasks, satisfying all preconditions along the way. The plan is complete when all tasks in the network are primitive.

$$\text{Plan} = \text{sequence of primitive actions } (a_1, \dots, a_k)$$ $$\text{HTN Method: } m = (t_c, Pre(m), Dec(m))$$ $$\text{Decomposition: } t_c \xrightarrow{m} (t_1, t_2, \dots, t_j)$$

Benefits of Hierarchical Planning

  • Scalability: By operating at different levels of abstraction, HTNs dramatically reduce the effective search space. The planner doesn't need to consider every primitive action at every step.
  • Reusability: Methods encapsulate domain knowledge about how to achieve common sub-goals, which can be reused across different top-level goals.
  • Human-Interpretability: The hierarchical structure of the plan often mirrors human problem-solving, making the plans easier to understand, debug, and validate.
  • Robustness: If a low-level primitive action fails during execution, the agent can attempt to re-plan for that specific sub-task without having to re-generate the entire plan from scratch.
⚠️ Common Pitfall

HTN planning is not guaranteed to find an optimal plan (e.g., shortest or cheapest) unless specific search strategies are employed. It is also not always complete: if the domain knowledge (methods) is incomplete or incorrect, the planner might fail to find a plan even if one exists. This contrasts with some flat planners that are complete for certain problem classes.

Key Takeaways
▼

When to use hierarchical planning:

  • Complex, long-horizon problems: When goals require many steps and involve intricate sub-goals (e.g., robotics, logistics, game AI).
  • Large state and action spaces: When flat planning becomes computationally intractable due to the sheer number of possible states and actions.
  • Human-in-the-loop systems: When plans need to be understandable and modifiable by human operators.
  • Leveraging domain expertise: When there's existing knowledge about how to break down tasks (e.g., "recipes" for common procedures).
  • Robustness to failure: When the agent needs to re-plan efficiently in response to unexpected events or failed actions.

When NOT to use:

  • Simple, short-horizon problems: For trivial tasks, the overhead of defining a hierarchy might outweigh the benefits; a simple search (BFS/DFS) might suffice.
  • Guaranteed optimality is critical: If finding the absolute shortest or cheapest plan is paramount, and the problem is tractable, a flat optimal planner (e.g., A*) might be preferred. HTNs often find "good enough" plans rather than optimal ones.
  • Decomposition knowledge is unknown or hard to acquire: If there's no clear way to define methods for task decomposition, building an HTN domain can be difficult.
💡 Big Picture

Hierarchical planning represents a powerful paradigm shift from pure search to knowledge-intensive problem-solving. It's a hybrid approach that combines the systematic exploration of search algorithms with structured domain knowledge, enabling AI agents to tackle real-world complexity in a more efficient, robust, and human-like manner.

Code Trace: Simplified HTN Planner
▼
class Task:
def __init__(self, name, is_primitive=False):
self.name = name
self.is_primitive = is_primitive
class Method:
def __init__(self, name, task_to_decompose, subtasks, preconditions=None):
self.name = name
self.task_to_decompose = task_to_decompose
self.subtasks = subtasks # List of Tasks or primitive strings
self.preconditions = preconditions or []
def htn_plan(current_state, task_list, methods):
if not task_list:
return [] # Empty plan for empty task list
current_task = task_list[0]
if current_task.is_primitive:
# Execute primitive action (or add to plan)
# Check preconditions, update state, etc. (simplified)
print(f"Executing: {current_task.name}")
return [current_task.name] + htn_plan(current_state, task_list[1:], methods)
else:
# Try to decompose compound task using available methods
for method in methods:
if method.task_to_decompose.name == current_task.name:
# Check method preconditions (simplified)
if all(cond in current_state for cond in method.preconditions):
print(f"Decomposing {current_task.name} with method {method.name}")
# Prepend subtasks to the current task list
new_task_list = method.subtasks + task_list[1:]
# Recursively plan for the new task list
result = htn_plan(current_state, new_task_list, methods)
if result is not None:
return result # Found a valid decomposition path
return None # No method found or no valid path from decomposition
# Example Usage (simplified "Make Coffee" domain)
# Define Tasks
make_coffee_task = Task("Make Coffee")
get_mug_task = Task("Get Mug")
brew_coffee_task = Task("Brew Coffee")
add_condiments_task = Task("Add Milk/Sugar")
go_to_cabinet = Task("Go to cabinet", is_primitive=True)
open_cabinet = Task("Open cabinet", is_primitive=True)
grab_mug = Task("Grab mug", is_primitive=True)
close_cabinet = Task("Close cabinet", is_primitive=True)
fill_water = Task("Fill water", is_primitive=True)
add_grounds = Task("Add coffee grounds", is_primitive=True)
start_machine = Task("Start machine", is_primitive=True)
wait_for_brew = Task("Wait for brew", is_primitive=True)
# Define Methods
method_make_coffee = Method("Decompose Make Coffee", make_coffee_task,
[get_mug_task, brew_coffee_task, add_condiments_task])
method_get_mug = Method("Decompose Get Mug", get_mug_task,
[go_to_cabinet, open_cabinet, grab_mug, close_cabinet])
method_brew_coffee = Method("Decompose Brew Coffee", brew_coffee_task,
[fill_water, add_grounds, start_machine, wait_for_brew])
all_methods = [method_make_coffee, method_get_mug, method_brew_coffee]
# Run the planner
initial_state = {"robot_at_home": True}
final_plan = htn_plan(initial_state, [make_coffee_task], all_methods)
print("Final Plan:", final_plan)
