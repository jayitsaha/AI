Understanding Feature Engineering for RecSys
▼

What is it? Every recommender system — from a candidate ranker to a click-through-rate model — ultimately scores a (user, item, context) triple with a single number. Feature engineering is the process of turning raw, heterogeneous signals about the user, the item, and the moment into a numeric vector \(x\) that a model can consume. The vector is built from four families: user features (who is asking), item features (what is being scored), context features (when/where/how), and cross features (how user and item signals interact with each other).

Analogy: Think of a matchmaker filling out a compatibility form. The user's profile ("likes hiking, budget-conscious") and the candidate's profile ("outdoor gear, mid-price") are useful alone, but the real signal is in the match: "user's hiking interest × item's outdoor category" or "user's budget × item's price". A model that only sees the two profiles separately can't easily learn that interaction — it has to be handed the crossed feature explicitly, or given enough capacity (embeddings, deep crosses) to discover it.

💡 If you remember one thing

A recommender's final feature vector is a concatenation \(x = [x_{\text{user}} \oplus x_{\text{item}} \oplus x_{\text{context}} \oplus x_{\text{cross}}]\). The first three blocks describe the three entities in isolation; the cross block is engineered (or learned) specifically to capture interaction signal that additive linear terms cannot express on their own.

2
How It Works Internally
▼

The Four Feature Families

User features live in a user feature store: demographics, long-run behavioral aggregates (avg. rating given, purchase frequency, tenure), and learned embeddings from past interaction sequences. They change slowly and can be precomputed offline.

Item features describe the candidate: price, category, popularity, freshness, content embeddings (text/image). They also live in an item feature store and are largely static between batch refreshes.

Context features capture the serving moment: time of day, day of week, device, location, query, position in session. These are computed online, at request time, and are the freshest signal available.

Cross features are explicit interaction terms between the other groups — e.g. \(x_{\text{rating}}\cdot x_{\text{item\_rating}}\) ("does this user tend to like items like this?"), a category-match indicator, or a hashed \((\text{user\_id}, \text{item\_id})\) conjunction. They inject the multiplicative structure that a purely additive (linear) model cannot learn on its own.

Why Crosses Aren't Automatic in Linear Models

A linear/logistic model computes \(z = w^\top x + b\), a strictly additive function of the raw features. If "user likes cheap items" and "item is cheap" are each features, their linear combination can never represent "user likes cheap items AND this item is cheap" — that requires a product term. Cross features hand the model that product directly, which is why they historically drove huge lifts in linear CTR models (e.g. Google's Wide & Deep, Facebook's GBDT+LR stack).

🔑 Key Property

Modern deep models (two-tower, DeepFM, DCN) try to learn crosses implicitly via embedding dot-products or explicit cross layers, reducing (but rarely eliminating) the need for hand-engineered cross features. In practice, teams still hand-craft a handful of high-signal crosses because they are interpretable, cheap, and robust to cold-start.

Why It Works — The Math
▼

From Additive to Multiplicative

A plain linear scorer over raw features is:

$$z(x) = w_0 + \sum_{i=1}^{d} w_i x_i$$

This can only express effects that add up independently. A degree-2 polynomial / explicit cross model adds pairwise products:

$$z(x) = w_0 + \sum_{i=1}^{d} w_i x_i \;+\; \sum_{i

Each \(w_{ij}x_ix_j\) term is exactly a hand-engineered cross feature. The trouble is that the number of possible pairs grows as \(O(d^2)\), and most pairs are useless or sparse — so practitioners select a small, meaningful subset (e.g. only user\(\times\)item pairs, not user\(\times\)user).

Factorization Machines: Learning the Crosses

Instead of a free parameter \(w_{ij}\) per pair (which needs enough data per pair to estimate), Factorization Machines factor the interaction weight into learned embeddings \(v_i \in \mathbb{R}^k\):

$$z(x) = w_0 + \sum_i w_i x_i + \sum_{i

Because \(\langle v_i, v_j\rangle\) is shared across every pair that touches feature \(i\), this generalizes to pairs that never co-occurred in training — the same trick that powers two-tower and DeepFM cross layers.

The Score → Probability Link

The final score \(z\) is passed through a link function — for click/purchase prediction, the logistic sigmoid:

$$P(\text{click} \mid u,i,c) = \sigma(z) = \frac{1}{1+e^{-z}}$$
⚠️ Common Pitfall

Cross features multiply sparsity: a user\(\times\)item ID cross has as many possible values as users \(\times\) items, so raw crosses are almost always hashed into a fixed number of buckets (the "hashing trick") to keep the feature space tractable, at the cost of occasional hash collisions.

Key Takeaways
▼

Design checklist for each family:

  • User features: demographics, long-run behavioral aggregates, sequence embeddings — precomputed, refreshed on a schedule (feature store).
  • Item features: content/catalog attributes, popularity/quality priors, content embeddings — also precomputed, watch for staleness on fast-moving catalogs.
  • Context features: time, device, location, session position, query — must be computed online at serving time; the freshest and often highest-leverage signal.
  • Cross features: explicit products/conjunctions between user and item signals — expensive to enumerate exhaustively, so pick a small high-value set or let an FM/DeepFM-style layer learn them.

When hand-engineered crosses matter most: cold-start items/users (embeddings haven't learned yet), simple linear/GBDT models with no interaction capacity, and interpretability-sensitive settings (fraud/ranking audits).

💡 Hierarchy

Raw features (user, item, context) ⊂ hand-crossed features (explicit products) ⊂ learned interactions (FM/DeepFM/DCN embeddings). Each layer trades engineering effort for the ability to capture richer, less-anticipated interaction patterns.

Code Trace
▼
import numpy as np
# --- user features (from user feature store) ---
user = {"age_norm": 0.62, "avg_rating": 0.81,
"purchases_norm": 0.35, "tenure_norm": 0.54}
# --- item features (from item feature store) ---
item = {"price_norm": 0.45, "popularity": 0.72,
"item_rating": 0.88, "is_new": 0.15}
# --- context features (computed online, at request time) ---
ctx = {"hour_norm": 0.79, "is_weekend": 1.0, "on_mobile": 1.0}
# --- cross features: explicit user x item interactions ---
cross = {
"rating_affinity": user["avg_rating"] * item["item_rating"],
"afford_match": user["purchases_norm"] * item["price_norm"],
"novelty_seek": user["tenure_norm"] * item["is_new"],
"category_match": 1.0, # user_fav_category == item_category
}
# --- assemble the full feature vector ---
x = np.array(list(user.values()) + list(item.values())
+ list(ctx.values()) + list(cross.values()))
# --- score with a linear model ---
w = np.array([0.3,0.9,0.5,0.2, -0.4,0.6,0.8,-0.3,
0.4,0.3,0.1, 1.2,0.7,0.5,1.5])
b = -4.0
z = x @ w + b
p_click = 1 / (1 + np.exp(-z))
print(f"score={z:.3f} P(click)={p_click:.3f}")
