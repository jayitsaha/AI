Byte-Level BPE

The tokenization backbone of GPT-2, RoBERTa, and modern LLMs -- no UNK tokens, ever
Intermediate NLP Tokenization Vocab: 50,257
1
Understanding Byte-Level BPE
▼

What is it? Byte Pair Encoding (BPE) is a subword tokenization algorithm that iteratively merges the most frequent adjacent pairs of symbols. Byte-level BPE starts from raw bytes (0-255) instead of Unicode characters. This means the base vocabulary is exactly 256 entries -- one per possible byte value -- and any text in any language or script can be represented without ever producing an unknown token.

Analogy: Imagine you're compressing a message using shorthand. You start by writing every letter individually. Then you notice "th" appears constantly, so you invent a single symbol for it. Then "the" is common, so that gets a symbol too. Byte-level BPE does exactly this, but starts from bytes so it can handle emoji, Chinese characters, Arabic script -- anything that can be encoded as UTF-8 bytes.

Key Innovation

By operating on bytes instead of Unicode characters, byte-level BPE guarantees a closed vocabulary: any input string can be tokenized, even if it contains characters never seen during training. The base 256-byte vocabulary is always sufficient as a fallback. This eliminates the dreaded <UNK> token that plagued earlier tokenizers.

2
How Byte-Level BPE Works Internally
▼

Step 1: UTF-8 Encoding

Every input string is first converted to a sequence of UTF-8 bytes. ASCII characters map to a single byte (e.g., 'H' = 0x48 = 72). Multi-byte characters expand: CJK characters use 3 bytes, and emoji use 4 bytes. For example, the fire emoji uses bytes [0xF0, 0x9F, 0x94, 0xA5].

Step 2: Byte-to-Visible-Character Mapping

GPT-2 applies a clever trick: it maps all 256 byte values to printable Unicode characters. Bytes 33-126 (printable ASCII) and 161-172, 174-255 map to themselves. The remaining bytes (0-32, 127-160, 173 -- control characters and whitespace) are mapped to Unicode characters starting at U+0100. This makes the vocabulary human-readable while remaining bijective.

Step 3: Iterative Pair Merging

Starting from the byte-level base vocabulary of 256 tokens, the algorithm scans the training corpus to find the most frequent adjacent pair of tokens. That pair is merged into a single new token and added to the vocabulary. This repeats until the desired vocabulary size is reached. GPT-2 performs 50,000 merges, arriving at a vocabulary of 50,257 tokens (256 base + 50,000 merges + 1 special <|endoftext|>).

Design Decision: Why Bytes?

Character-level BPE (as in the original Sennrich et al. 2016 paper) needs a base vocabulary of all Unicode characters seen in training -- potentially tens of thousands, and any unseen character becomes <UNK>. Byte-level BPE needs exactly 256 base tokens and can represent any Unicode string. The trade-off: multi-byte characters initially require more tokens, but frequent ones get merged into single tokens during BPE training.

The Math Behind BPE
▼

BPE is a greedy compression algorithm. At each iteration, we select the pair \((a, b)\) that maximizes:

$$\text{merge}^* = \underset{(a,b) \in V \times V}{\operatorname{argmax}} \; \text{freq}(a, b)$$

where \(\text{freq}(a, b)\) counts how many times tokens \(a\) and \(b\) appear adjacently in the corpus. The new token \(ab\) replaces all occurrences of the pair, and the vocabulary grows: \(V \leftarrow V \cup \{ab\}\).

Compression Ratio

The compression ratio after \(k\) merges can be expressed as:

$$\rho_k = \frac{|S_0|}{|S_k|}$$

where \(|S_0|\) is the initial sequence length (in bytes) and \(|S_k|\) is the length after \(k\) merges. For English text, GPT-2's tokenizer achieves roughly \(\rho \approx 3.5\text{-}4.0\), meaning 4 bytes of text compress to about 1 token on average.

UTF-8 Encoding Formula

A Unicode code point \(U\) is encoded into \(n\) UTF-8 bytes where: \(n = 1\) if \(U \leq \text{0x7F}\), \(n = 2\) if \(U \leq \text{0x7FF}\), \(n = 3\) if \(U \leq \text{0xFFFF}\), and \(n = 4\) if \(U \leq \text{0x10FFFF}\). The total byte count for a string determines the maximum possible token count before any BPE merges.

Trade-off

Byte-level BPE uses more tokens for rare multi-byte characters (e.g., a rare CJK character becomes 3 separate byte tokens). However, frequent multi-byte sequences get merged during training, so common non-ASCII text is still efficient. GPT-2's 50K merges capture most frequent multi-byte patterns.

6
Key Takeaways
▼

1. No UNK tokens. The 256-byte base vocabulary covers every possible input. This is the single most important advantage over character-level tokenizers.

2. Language-agnostic. No need to pre-define character sets for different languages. UTF-8 encoding handles everything uniformly.

3. GPT-2's vocabulary. 256 base bytes + 50,000 BPE merges + 1 special token = 50,257 total. This vocabulary is reused by GPT-3, GPT-4, and many other models.

4. Compression efficiency. English text achieves ~3.5-4x compression (bytes to tokens). Other languages vary: CJK ~2x, rare scripts ~1.5x.

5. Predecessors and successors. Byte-level BPE improved on character-level BPE (Sennrich 2016) and WordPiece (BERT). It was later refined by SentencePiece (unigram model) and tiktoken (optimized implementation for OpenAI models).
