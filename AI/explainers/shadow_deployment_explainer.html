Understanding Shadow Deployment
▼

What is it? Shadow deployment (a.k.a. "dark launch" or "shadow traffic") runs a new candidate model side-by-side with the live production model. Every incoming request is duplicated: the production model's answer is the one actually returned to the user, while the candidate's answer is computed on the exact same input, thrown away as far as the user is concerned, and only written to a log for later comparison.

Analogy: Imagine a hospital training a new junior doctor. The junior examines every real patient and writes a private diagnosis in a notebook — but the senior doctor's diagnosis is the one that actually goes on the chart and guides treatment. Nobody's care changes because of the junior's notes; they're compared against the senior's calls afterward to see how the junior is doing before ever letting them treat patients alone.

💡 If you remember one thing

Shadow deployment separates inference from influence: the shadow model sees real production inputs and produces real predictions, but those predictions never reach a user, a downstream system, or a business decision. That decoupling is what makes it zero-risk — even a badly broken shadow model cannot degrade the product.

2
How It Works Internally
▼

The Fork-and-Log Data Path

A request hits the serving layer (gateway / router). The router does a fork: it sends the request synchronously to the production model on the critical path, and asynchronously (fire-and-forget, usually via a message queue or a background task) to the shadow model. The user's response is built from the production model's output alone — the request handler does not wait for the shadow call to finish.

Why Asynchronous Matters

If the shadow call were synchronous and blocking, a slow or crashing shadow model would add latency or errors to real user traffic — defeating the entire point. So the shadow call is decoupled: dispatched on a separate thread/process/queue, with its own timeout, and any exception in the shadow path is swallowed and logged, never propagated to the response.

What Gets Logged

For every mirrored request the pipeline stores: the input features, the production prediction + latency, the shadow prediction + latency, and metadata (timestamp, request ID, model versions). An offline job later joins these records to compute agreement rate, prediction drift, latency/resource overhead, and error segments — all without a single shadow prediction ever touching a real user.

🔑 Key Property

Shadow deployment gives you production-distribution evaluation — the candidate model is tested on the real, live, non-stationary traffic distribution (not a static offline test set) — with a hard isolation guarantee: shadow failures cannot affect served responses because the serving decision never reads the shadow's output.

3
Why It Works — Measuring Agreement Offline
▼

Let \(p_i\) be the production model's prediction and \(s_i\) the shadow model's prediction on the same input \(x_i\), for mirrored requests \(i = 1, \dots, n\). Offline analysis reduces to comparing the two prediction streams.

Agreement Rate

$$\text{Agreement} = \frac{1}{n}\sum_{i=1}^{n} \mathbb{1}\big[\,|p_i - s_i| < \epsilon\,\big]$$

where \(\epsilon\) is a tolerance (for classifiers, this collapses to a simple label-match indicator). This is the single most-watched shadow metric: it estimates, with zero user risk, how often the candidate would have agreed with the incumbent had it been serving.

Mean Absolute Deviation & Regression Detection

$$\text{MAD} = \frac{1}{n}\sum_{i=1}^{n} |p_i - s_i| \qquad \text{flag } i \text{ if } |p_i - s_i| > k \cdot \sigma_{\text{diff}}$$

Individual requests whose disagreement exceeds \(k\) standard deviations of the diff distribution (typically \(k \approx 3\)) are flagged as candidate regressions. Slicing this by feature segment (e.g. "requests where \(x > \tau\)") is exactly how shadow testing catches a bug that only manifests on a slice of traffic — long before it would show up in an A/B test's aggregate metric.

⚠️ Common Pitfall

Shadow deployment measures prediction agreement, not ground-truth accuracy — labels for live traffic usually arrive late or never. High agreement with the incumbent is reassuring but does not prove the shadow model is correct, only that it behaves similarly (or how it differs). Pair shadow analysis with delayed-label evaluation where possible.

Key Takeaways
▼

When to use shadow deployment:

  • Before promoting a new model version and you want production-distribution signal with zero user risk
  • When ground-truth labels are slow/expensive, so agreement-with-incumbent is your best fast proxy
  • To measure real latency and resource overhead of a heavier candidate model under real load
  • To catch slice-specific regressions (a segment of traffic where the new model quietly breaks)

When NOT to rely on it alone:

  • When you need to measure actual business impact (clicks, conversions, revenue) — that requires an A/B test, since shadow predictions never reach users
  • When the shadow model's outputs would change future inputs (e.g. a recommender whose own past picks shape future traffic) — shadow can't observe that feedback loop
  • As the only gate before full rollout — pair with canary release for a final, low-traffic live check
💡 Where it sits in the rollout ladder

Offline eval (static test set) → Shadow deployment (real traffic, zero risk, no user impact) → Canary release (small % of real users, real risk) → Full rollout / blue-green cutover. Each stage trades less risk for less signal about real-world impact.

async def handle_request(req):
# 1. Production call is synchronous — on the critical path
prod_start = time.perf_counter()
prod_pred = prod_model.predict(req.features)
prod_latency = time.perf_counter() - prod_start
# 2. Fork: fire-and-forget shadow call, never awaited by the response path
asyncio.create_task(run_shadow(req, prod_pred, prod_latency))
# 3. Response is built from prod_pred ONLY
return Response(prediction=prod_pred)
async def run_shadow(req, prod_pred, prod_latency):
try:
shadow_start = time.perf_counter()
# same input, candidate model, strict timeout, isolated failure domain
shadow_pred = await asyncio.wait_for(
shadow_model.predict_async(req.features), timeout=0.5)
shadow_latency = time.perf_counter() - shadow_start
except Exception as e:
shadow_pred, shadow_latency = None, None # swallowed — never raised to user
log.warning(f"shadow inference failed: {e}")
# 4. Log for OFFLINE comparison — nothing here reaches the client
comparison_log.write(request_id=req.id, features=req.features,
prod_pred=prod_pred, prod_latency=prod_latency,
shadow_pred=shadow_pred, shadow_latency=shadow_latency)
# --- offline job, run hourly ---
df = comparison_log.read_recent()
agreement = (df.prod_pred.sub(df.shadow_pred).abs() < EPS).mean()
mad = df.prod_pred.sub(df.shadow_pred).abs().mean()
print(f"agreement={agreement:.1%} MAD={mad:.4f} n={len(df)}")
