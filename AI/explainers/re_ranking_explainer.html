Re-ranking: Cross-Encoder vs Bi-Encoder

The core trade-off between speed and accuracy in modern information retrieval
Intermediate NLP Information Retrieval O(N) vs O(N*M)
1
Understanding Re-ranking
▼

What is it? In information retrieval (e.g., search engines, recommendation systems), a user query often needs to be matched against millions or billions of documents. It's impossible to compute a high-quality relevance score for every document. Instead, a two-stage approach is common: first, a fast, coarse retriever (like BM25 or a simple embedding search) quickly narrows down the full corpus to a few hundred or thousand candidate documents. Second, a more sophisticated, computationally expensive model (the "re-ranker") then evaluates these candidates more deeply to produce a final, highly relevant ordered list.

Analogy: Imagine you're looking for a specific book in a giant library. You wouldn't browse every single shelf. First, you'd use the library's online catalog (the "initial retriever") to find a few dozen potentially relevant books. Then, you'd physically examine (the "re-ranker") only those few dozen books, reading their summaries, flipping through pages, to pick the absolute best ones.

💡 If you remember one thing

Re-ranking is the second stage of a two-stage retrieval system. It takes a small set of candidate documents (from a fast initial retriever) and a query, then scores and reorders them to produce a highly relevant final list. The key architectural choice for the re-ranker is between bi-encoders (fast, good) and cross-encoders (slow, better).

2
How Bi-Encoders and Cross-Encoders Differ
▼

Both bi-encoders and cross-encoders typically use transformer-based neural networks to understand text. The fundamental difference lies in when the query and document interact within the model:

Bi-Encoders: Encode Separately, Compare Later

A bi-encoder uses two independent (but often shared-weight) neural networks: one for the query (\(E_Q\)) and one for the document (\(E_D\)).

  1. The query \(q\) is encoded into a fixed-size vector representation: \(v_q = E_Q(q)\).
  2. Each candidate document \(d_i\) is encoded into its own vector: \(v_{d_i} = E_D(d_i)\). Crucially, these document embeddings can be pre-computed offline and stored in a vector database.
  3. Relevance is determined by computing a simple similarity score (e.g., dot product, cosine similarity) between \(v_q\) and each \(v_{d_i}\): \(score(q, d_i) = \text{sim}(v_q, v_{d_i})\).

Advantage: Very fast at inference time because only the query needs to be encoded live. Document embeddings are pre-calculated. The similarity calculation is trivial.

Disadvantage: Less accurate. The query and document never "see" each other directly within the transformer. The interaction is limited to a single dot product in the embedding space, which might miss subtle contextual cues.

Cross-Encoders: Encode Together, Score Directly

A cross-encoder uses a single, larger neural network (\(E_{CE}\)) that takes both the query and a document concatenated as a single input sequence.

  1. For each candidate document \(d_i\), the query \(q\) and document \(d_i\) are concatenated (e.g., [CLS] q [SEP] d_i [SEP]) and fed into the cross-encoder.
  2. The cross-encoder outputs a direct relevance score for that specific pair: \(score(q, d_i) = E_{CE}([q; d_i])\).

Advantage: Much more accurate. The query and document interact at every layer of the transformer, allowing for deep, fine-grained contextual understanding of their relationship. This captures nuances a bi-encoder cannot.

Disadvantage: Very slow at inference time. The cross-encoder must be run separately for *every* query-document pair in the candidate set. Document embeddings cannot be pre-computed. If there are \(N\) candidate documents, the cross-encoder runs \(N\) times.

🔑 Key Property

The choice between bi-encoder and cross-encoder is a fundamental trade-off between speed/scalability (bi-encoder) and accuracy/relevance quality (cross-encoder). Hybrid systems often use a bi-encoder for the initial retrieval, then a cross-encoder for the top-K re-ranking.

3
Why It Works — The Math & Complexity
▼

Bi-Encoder Formalism and Complexity

Let \(q\) be the query, and \(d_1, \dots, d_N\) be the \(N\) candidate documents. A bi-encoder uses two separate encoders, \(E_Q\) for the query and \(E_D\) for documents, which map text to dense vectors in \(\mathbb{R}^k\).

$$v_q = E_Q(q) \in \mathbb{R}^k \\ v_{d_i} = E_D(d_i) \in \mathbb{R}^k$$

The relevance score is then computed via a similarity function, typically cosine similarity or dot product:

$$score(q, d_i) = \text{sim}(v_q, v_{d_i}) = \frac{v_q \cdot v_{d_i}}{\|v_q\| \|v_{d_i}\|}$$

The computational cost at query time for \(N\) documents is: $$ \text{Cost}_{\text{bi-encoder}} = \underbrace{O(L_Q \cdot C_Q)}_{\text{encode query}} + \underbrace{O(N \cdot k)}_{\text{similarity ops}} $$ where \(L_Q\) is query length and \(C_Q\) is query encoder complexity (usually quadratic in length). Document encoding \(O(N \cdot L_D \cdot C_D)\) can be pre-computed, making query-time latency very low.

Cross-Encoder Formalism and Complexity

A cross-encoder uses a single encoder \(E_{CE}\) that takes the concatenated query and document as input. The input sequence length is \(L_{QD} = L_Q + L_D + \text{tokens}\). The model directly outputs a scalar relevance score.

$$score(q, d_i) = E_{CE}([q; d_i]) \in \mathbb{R}$$

The computational cost at query time for \(N\) documents is: $$ \text{Cost}_{\text{cross-encoder}} = \underbrace{O(N \cdot L_{QD} \cdot C_{CE})}_{\text{encode N pairs}} $$ where \(C_{CE}\) is the cross-encoder complexity (also typically quadratic in length). Since \(L_{QD}\) is often much larger than \(L_Q\), and the operation must be repeated \(N\) times, this is significantly slower than a bi-encoder for re-ranking a candidate set.

⚠️ Common Pitfall

Do not use a cross-encoder for initial retrieval against a massive corpus. Its \(O(N)\) cost for \(N\) documents means it would take too long to score even a small fraction of a large dataset. Always pair it with a faster initial retriever (or a bi-encoder) to narrow down the search space first.

Key Takeaways
▼

When to use Bi-Encoders:

  • Initial retrieval: When searching across a very large corpus (millions/billions of documents). The ability to pre-compute document embeddings makes them extremely fast.
  • Low-latency applications: Any scenario where response time is critical, as only the query needs real-time encoding.
  • Resource-constrained environments: Simpler models and fewer computations per query.

When to use Cross-Encoders:

  • Re-ranking a small candidate set: When you need the absolute highest relevance accuracy for a small set of already-filtered documents (e.g., top 100-1000 candidates).
  • Complex relevance judgments: When the relationship between query and document is highly nuanced and requires deep contextual interaction (e.g., semantic matching, question answering).
  • Offline evaluation/small datasets: When computational cost is less of a concern than maximizing accuracy.

Hybrid Systems: The Best of Both Worlds

Most production systems combine both: a bi-encoder (or BM25) for initial retrieval, followed by a cross-encoder for re-ranking the top N candidates. This balances scalability with accuracy effectively.

💡 Rule of Thumb

If you need to score many documents quickly, use a bi-encoder. If you need to score few documents accurately, use a cross-encoder. For real-world systems, combine them in a multi-stage pipeline.

Code Trace (Python Pseudocode)
▼
import torch
from transformers import AutoModel, AutoTokenizer
# --- Setup Models ---
# Bi-Encoder: two separate encoders, often shared weights
query_tokenizer = AutoTokenizer.from_pretrained("sentence-transformers/all-MiniLM-L6-v2")
query_model = AutoModel.from_pretrained("sentence-transformers/all-MiniLM-L6-v2")
doc_tokenizer = AutoTokenizer.from_pretrained("sentence-transformers/all-MiniLM-L6-v2")
doc_model = AutoModel.from_pretrained("sentence-transformers/all-MiniLM-L6-v2")
# Cross-Encoder: single model taking concatenated input
cross_tokenizer = AutoTokenizer.from_pretrained("cross-encoder/ms-marco-MiniLM-L-6-v2")
cross_model = AutoModel.from_pretrained("cross-encoder/ms-marco-MiniLM-L-6-v2")
# --- Pre-compute Document Embeddings (for Bi-Encoder) ---
corpus_docs = ["doc text 1", "doc text 2", "doc text 3", ...] # Large corpus
doc_embeddings = []
for doc_text in corpus_docs:
inputs = doc_tokenizer(doc_text, return_tensors='pt', truncation=True, padding=True)
with torch.no_grad():
doc_emb = doc_model(**inputs).last_hidden_state[:, 0, :].mean(dim=0) # CLS token emb
doc_embeddings.append(doc_emb)
doc_embeddings = torch.stack(doc_embeddings) # Store in vector DB
# --- Query-time Re-ranking ---
query = "What is the capital of France?"
candidate_docs = ["Paris is the capital.", "London is big.", "France is in Europe."] # From initial retriever
# BI-ENCODER Re-ranking
query_inputs = query_tokenizer(query, return_tensors='pt', truncation=True, padding=True)
with torch.no_grad():
query_emb = query_model(**query_inputs).last_hidden_state[:, 0, :].mean(dim=0)
bi_encoder_scores = []
for i, doc_text in enumerate(candidate_docs):
# In real world, doc_emb would be retrieved from vector DB by ID
doc_inputs = doc_tokenizer(doc_text, return_tensors='pt', truncation=True, padding=True)
with torch.no_grad():
current_doc_emb = doc_model(**doc_inputs).last_hidden_state[:, 0, :].mean(dim=0)
score = torch.nn.functional.cosine_similarity(query_emb, current_doc_emb, dim=0)
bi_encoder_scores.append((score.item(), doc_text))
bi_encoder_scores.sort(key=lambda x: x[0], reverse=True)
print("Bi-Encoder Reranked:", [d for s,d in bi_encoder_scores])
# CROSS-ENCODER Re-ranking
cross_encoder_scores = []
for doc_text in candidate_docs:
inputs = cross_tokenizer(query, doc_text, return_tensors='pt', truncation=True, padding=True)
with torch.no_grad():
score = cross_model(**inputs).logits.squeeze().item() # Direct relevance score
cross_encoder_scores.append((score, doc_text))
cross_encoder_scores.sort(key=lambda x: x[0], reverse=True)
print("Cross-Encoder Reranked:", [d for s,d in cross_encoder_scores])
