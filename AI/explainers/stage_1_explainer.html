1
Understanding Candidate Generation
▼

What is it? In modern recommender systems and search engines, the process of finding relevant items happens in multiple stages. The first stage, Candidate Generation (also known as Retrieval), is designed for speed. Its job is to efficiently filter a massive corpus of items (millions or even billions) down to a much smaller, more manageable set (hundreds or thousands) of potentially relevant "candidates." These candidates are then passed to a second, more computationally expensive Ranking stage.

Analogy: Imagine you're looking for a book at a gigantic library with millions of books. You can't possibly read every summary. Instead, you first go to the "fiction" section (a broad filter), then look for books by "sci-fi" (another filter), and maybe pick out 50 books that look promising. This is candidate generation. You then take those 50 books to a cozy chair and carefully read their first few pages to decide which one to borrow (the ranking stage).

💡 If you remember one thing

Candidate generation prioritizes recall and speed over precision. It aims to find *most* relevant items without being too slow, even if it brings in some irrelevant ones. The goal is to avoid missing good candidates, knowing that the subsequent ranking stage will sort out the noise.

2
How Retrieval Works Internally
▼

The Core Problem: Scale

A typical e-commerce site might have millions of products, a streaming service millions of movies, or a social network billions of posts. For any given user query or profile, a brute-force comparison against every single item is computationally infeasible, especially with strict latency requirements (e.g., a few milliseconds for a search query).

Common Techniques for Candidate Generation

To overcome the scale problem, candidate generation methods rely on efficient data structures and approximate algorithms:

  • Embedding-based Retrieval (Vector Search): This is a dominant modern approach. Both users/queries and items are represented as dense vectors (embeddings) in a high-dimensional space. Semantic similarity is then approximated by vector distance (e.g., cosine similarity, Euclidean distance). Fast Approximate Nearest Neighbor (ANN) search algorithms (like HNSW, FAISS, ScaNN) are used to find items whose embeddings are "close" to the user/query embedding.
  • Inverted Indexes (Keyword Search): Traditional search engines use inverted indexes, mapping terms to documents. Techniques like TF-IDF or BM25 score documents based on keyword overlap with the query. While effective for keyword matching, they struggle with semantic similarity (e.g., "car" vs "automobile").
  • Collaborative Filtering (Matrix Factorization): Based on past user-item interactions. For example, finding items frequently bought by users similar to the current user. This can be precomputed or done with fast lookups.
  • Rule-Based / Heuristic Methods: Simple rules like "most popular items," "recently viewed," "items from the same category," or "items often bought together." These are fast but less personalized.

Design Decision: Why Two Stages?

The two-stage (or multi-stage) architecture is a fundamental trade-off between speed and accuracy. Stage 1 (Retrieval) is cheap and broad, ensuring high recall. Stage 2 (Ranking) is expensive and precise, using complex models (e.g., deep neural networks, large language models) with many features to fine-tune relevance for the small set of candidates. Trying to run a full ranking model on millions of items would be too slow and costly.

🔑 Key Property

Embedding-based retrieval transforms the problem of finding relevant items into an Approximate Nearest Neighbor (ANN) search problem. The challenge is to find points in a high-dimensional space that are close to a query point, without exhaustively checking every single point.

3
Why It Works — Embedding Similarity
▼

Embeddings as Semantic Vectors

The magic behind embedding-based retrieval is the ability to represent complex entities (words, users, items, images) as dense numerical vectors. These embeddings are learned by neural networks such that semantically similar items are mapped to nearby points in the embedding space. For example, a movie embedding for "The Matrix" would be close to "Blade Runner" and "Inception", but far from "My Little Pony".

Measuring Similarity: Cosine Similarity and Euclidean Distance

Given a user query embedding \(q \in \mathbb{R}^d\) and an item embedding \(i \in \mathbb{R}^d\), their similarity can be quantified in several ways:

1. Cosine Similarity: Measures the cosine of the angle between two vectors. It's scale-invariant, meaning only the direction matters, not the magnitude. Values range from -1 (opposite) to 1 (identical).

$$\text{sim}_{\text{cos}}(q, i) = \frac{q \cdot i}{\|q\| \|i\|} = \frac{\sum_{k=1}^d q_k i_k}{\sqrt{\sum_{k=1}^d q_k^2} \sqrt{\sum_{k=1}^d i_k^2}}$$

2. Euclidean Distance: Measures the straight-line distance between two points in space. Smaller distance implies higher similarity. Note that if vectors are normalized (e.g., \(\|q\|=\|i\|=1\)), Euclidean distance and Cosine similarity are directly related: \(\|q-i\|^2 = 2 - 2 \cdot \text{sim}_{\text{cos}}(q, i)\).

$$\text{dist}_{\text{euc}}(q, i) = \|q - i\| = \sqrt{\sum_{k=1}^d (q_k - i_k)^2}$$

For retrieval, we typically want to find items that maximize similarity (e.g., cosine) or minimize distance (e.g., Euclidean).

The Approximate Nearest Neighbor (ANN) Problem

To find the \(K\) most similar items to a query \(q\) from a corpus of \(N\) items, a naive approach would compute similarity to all \(N\) items and sort them. This takes \(O(N \cdot d)\) time (where \(d\) is embedding dimension), which is too slow for large \(N\). ANN algorithms aim to find "good enough" nearest neighbors in \(O(d \log N)\) or even \(O(d)\) time, at the cost of sacrificing a small amount of accuracy (i.e., not always finding the *absolute* closest neighbors).

$$\text{Goal: Find } \{i_1, \dots, i_K\} \subseteq \text{Corpus} \quad \text{such that } \text{sim}(q, i_j) \text{ is maximized}$$

Popular ANN techniques include Locality Sensitive Hashing (LSH), tree-based methods (KD-trees, Annoy), and graph-based methods (HNSW). Each has different trade-offs in terms of speed, memory, and recall.

⚠️ Common Pitfall

Choosing the right similarity metric and ANN algorithm is crucial. Cosine similarity is often preferred for text/user embeddings where direction (semantic meaning) is more important than magnitude (e.g., a very enthusiastic user vs. a casual one). Euclidean distance can be sensitive to magnitude. The "best" ANN algorithm depends heavily on the dataset size, dimensionality, and latency requirements.

Key Takeaways
▼

When to use Candidate Generation / Retrieval:

  • Any system dealing with a large corpus of items (millions+) that needs to serve personalized recommendations or search results with low latency.
  • As the first stage in a multi-stage ranking pipeline, where subsequent stages are more computationally intensive.
  • When you need to balance high recall (finding most relevant items) with computational efficiency.

When to be careful:

  • Cold Start Problem: New users or items lack sufficient interaction data to generate good embeddings or collaborative filtering signals. Hybrid approaches (e.g., rule-based for new items) are often needed.
  • Bias: If the training data for embeddings or collaborative filtering is biased, the retrieval system will perpetuate those biases, potentially leading to unfair or unrepresentative candidate sets.
  • Semantic Drift: User interests or item meanings can change over time. Embeddings need to be regularly updated or "refreshed" to stay relevant.
  • Recall vs. Precision: While retrieval prioritizes recall, if the candidate set is too noisy (low precision), the subsequent ranking stage might struggle to find truly relevant items. Tuning the size of the candidate set (K) is critical.
💡 Modern Best Practice

Many production systems use a combination of retrieval techniques to maximize recall. For example, a primary embedding-based ANN retrieval, supplemented by an inverted index for exact keyword matches, and a collaborative filtering component for serendipitous discovery. This ensures robustness and covers various user intents.

Code Trace: Brute-Force K-NN Retrieval
▼
import numpy as np
from scipy.spatial.distance import cosine
# --- 1. Generate Embeddings ---
def generate_embeddings(num_items, dim=2):
# In a real system, these would be learned from data
return np.random.rand(num_items, dim) * 10 - 5 # Scale to [-5, 5]
item_embeddings = generate_embeddings(num_items=500, dim=2)
query_embedding = np.array([1.5, 2.0]) # Example user query
# --- 2. Define Similarity Metric ---
def calculate_cosine_similarity(vec1, vec2):
# Cosine distance = 1 - cosine similarity
return 1 - cosine(vec1, vec2)
def calculate_euclidean_distance(vec1, vec2):
return np.linalg.norm(vec1 - vec2)
# --- 3. Brute-Force K-NN Retrieval (Naive Candidate Generation) ---
def retrieve_knn_candidates(query_emb, item_embs, k):
distances = []
for i, item_emb in enumerate(item_embs):
dist = calculate_euclidean_distance(query_emb, item_emb)
distances.append((dist, i)) # Store (distance, item_index)
distances.sort(key=lambda x: x[0]) # Sort by distance (ascending)
return [idx for dist, idx in distances[:k]] # Return top K item indices
# --- 4. Retrieve by Radius (Alternative) ---
def retrieve_radius_candidates(query_emb, item_embs, radius):
candidates = []
for i, item_emb in enumerate(item_embs):
dist = calculate_euclidean_distance(query_emb, item_emb)
if dist <= radius:
candidates.append(i)
return candidates
# Example usage:
k = 10
top_k_candidates = retrieve_knn_candidates(query_embedding, item_embeddings, k)
print(f"Top {k} candidates: {top_k_candidates}")
radius = 0.8
radius_candidates = retrieve_radius_candidates(query_embedding, item_embeddings, radius)
print(f"Candidates within radius {radius}: {radius_candidates}")
