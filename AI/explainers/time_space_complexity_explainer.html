Understanding Time & Space Complexity
▼

What is it? Every algorithm consumes two finite resources: time (how many steps it takes) and memory (how much RAM it occupies). Complexity analysis measures these as functions of input size \(n\), rather than in seconds or bytes, so the answer stays valid on any hardware and at any scale.

Analogy: Think of algorithms as recipes. Sorting \(n=10\) cards by hand is fine; sorting \(n=1{,}000{,}000\) the same way is hopeless. Complexity is asking "how much harder does this recipe get as I increase the number of ingredients?" A recipe whose work doubles with each extra ingredient is exponential — a catastrophe at scale. One whose work grows proportionally is linear — perfectly manageable.

Why does it matter for interviews? Every FAANG coding question ends with "what's the time and space complexity?" Getting the Big-O wrong — or giving the right answer without justification — is an automatic red flag. Complexity also drives design decisions: when a brute-force is \(O(n^2)\) and the interviewer hints "can you do better?", your job is to find an \(O(n \log n)\) or \(O(n)\) solution.

If you remember one thing

Big-O notation describes the asymptotic growth rate of an algorithm's resource usage — how the worst-case time (or space) scales as \(n \to \infty\). It discards constants and lower-order terms because, at scale, only the dominant term matters: \(O(2n^2 + 5n + 3) = O(n^2)\).

The Three Notations

  • \(O\) (Big-O) — upper bound (worst case): "it takes at most this many steps"
  • \(\Omega\) (Big-Omega) — lower bound (best case): "it takes at least this many steps"
  • \(\Theta\) (Big-Theta) — tight bound: "it takes exactly this order of steps in all cases"

In practice, interviewers say "what's the Big-O?" and mean the worst-case time or space. When you see "O(n log n)" for merge sort, it means both upper and lower bound are \(n \log n\), so the more precise answer is \(\Theta(n \log n)\).

Counting Operations & Memory — How to Analyze Any Algorithm
▼

Time Complexity: Count the Dominant Loop

The rule is simple: find the innermost loop, count how many times it executes as a function of \(n\), then keep only the fastest-growing term.

  • One loop over \(n\) elements → \(O(n)\)
  • Two nested loops over \(n\) → \(O(n^2)\)
  • Halving the input each step → \(O(\log n)\) (e.g., binary search)
  • A loop of \(n\) with a nested halving → \(O(n \log n)\) (e.g., merge sort)
  • A recursive call branching into 2 sub-calls of the same size → \(O(2^n)\) (e.g., naïve Fibonacci)

For a snippet like for i in range(n): for j in range(i, n): work(), the inner body runs \(\sum_{i=0}^{n-1}(n-i) = \frac{n(n+1)}{2}\) times, which is \(\Theta(n^2)\).

Space Complexity: Track What Stays Alive

Space counts peak simultaneous memory — not the total ever allocated. Ask: "at any single moment, how much extra memory is live?" Two main sources:

  • Auxiliary data structures: hash maps, arrays, queues allocated by your code
  • Recursion call stack: each active stack frame occupies memory. A recursive function with depth \(d\) uses \(O(d)\) stack space, regardless of how many total calls are made
Key Rule — Recursion Stack Space

Stack space = maximum depth of recursion, not total number of calls. For fib(n) naive, the tree has \(O(2^n)\) nodes but the stack depth is only \(O(n)\) — the deepest path has length \(n\). So space is \(O(n)\) even though time is \(O(2^n)\).

Annotated Code: Each Line's Contribution

def two_sum(nums, target): O(n²) time O(1) space
for i in range(len(nums)): # outer: n ×n
for j in range(i+1, len(nums)): # inner: n-i ×(n-i)
if nums[i]+nums[j]==target:
return [i, j] # O(1) work
def two_sum_fast(nums, target): O(n) time O(n) space
seen = {} # hash map O(n) aux
for i, v in enumerate(nums): # one pass: n ×1
if target-v in seen: # O(1) lookup
return [seen[target-v], i]
seen[v] = i # O(1) insert

The hash-map version trades \(O(n)\) extra space for dropping from \(O(n^2)\) to \(O(n)\) time — a classic time-space tradeoff.

The Formal Definitions — Why It Works
▼

Formal Big-O Definition

Let \(f(n)\) and \(g(n)\) be functions from naturals to non-negative reals. We say \(f(n) = O(g(n))\) if there exist positive constants \(c\) and \(n_0\) such that:

$$f(n) \leq c \cdot g(n) \quad \text{for all } n \geq n_0$$

In plain English: beyond some threshold \(n_0\), \(f\) is always bounded above by a constant multiple of \(g\). The constant \(c\) absorbs machine speed, language overhead, etc. — that's why we drop constants.

All Three Notations Together

$$f(n) = \Theta(g(n)) \iff f(n) = O(g(n)) \text{ AND } f(n) = \Omega(g(n))$$

Concretely: \(\frac{n(n-1)}{2} = \Theta(n^2)\) because \(\frac{1}{4}n^2 \leq \frac{n(n-1)}{2} \leq n^2\) for all \(n \geq 2\) — both constants \(c_1=\tfrac{1}{4}\) and \(c_2=1\) exist.

Key Rules for Derivations

  • Sum rule: \(O(f) + O(g) = O(\max(f,g))\) — only the dominant term survives
  • Product rule: \(O(f) \cdot O(g) = O(f \cdot g)\) — nested loops multiply
  • Transitivity: if \(f = O(g)\) and \(g = O(h)\) then \(f = O(h)\)
  • Log rule: \(\log_a n = \Theta(\log_b n)\) for any constants \(a,b > 1\) — log base doesn't matter in Big-O

Master Theorem (Divide and Conquer)

For recurrences of the form \(T(n) = a \cdot T(n/b) + f(n)\):

$$T(n) = a \cdot T\!\left(\frac{n}{b}\right) + f(n)$$
  • If \(f(n) = O(n^{\log_b a - \varepsilon})\): \(T(n) = \Theta(n^{\log_b a})\) — subproblem work dominates
  • If \(f(n) = \Theta(n^{\log_b a})\): \(T(n) = \Theta(n^{\log_b a} \log n)\) — equal split
  • If \(f(n) = \Omega(n^{\log_b a + \varepsilon})\): \(T(n) = \Theta(f(n))\) — combining work dominates

Merge sort example: \(a=2, b=2, f(n)=\Theta(n)\). Then \(\log_b a = \log_2 2 = 1\), so \(f(n)=\Theta(n^1)\) — Case 2 → \(T(n) = \Theta(n \log n)\). ✓

Common Pitfall — Amortized vs Worst-Case

A hash table lookup is amortized \(O(1)\) on average, but the worst case for a single lookup (all keys collide to one bucket) is \(O(n)\). When interviewers say "what's the complexity?", clarify: "is that average-case, worst-case, or amortized?" The distinction changes your answer.

Key Takeaways & Interview Patterns
▼

The Time-Space Tradeoff in Practice

The tradeoff is everywhere in DSA: spending more memory to buy speed. Examples:

  • Two-sum brute force \(O(n^2)\) time, \(O(1)\) space → hash-map version \(O(n)\) time, \(O(n)\) space
  • Naïve Fibonacci \(O(2^n)\) time, \(O(n)\) stack → Memoized \(O(n)\) time, \(O(n)\) cache
  • Linear search \(O(n)\) time, \(O(1)\) space → Build index / hash \(O(1)\) lookup, \(O(n)\) space
Interview Pattern

When an interviewer says "can you do better?", the answer is almost always: use a hash map, a two-pointer, a sliding window, binary search, or a heap. Each technique reduces time at the cost of some space or constraint (sorted input, etc.).

Space Complexity Checklist

  • Do you allocate a new array/hash? → that's \(O(n)\) aux space
  • Is the function recursive? → stack depth = \(O(\text{recursion depth})\)
  • Are you sorting in-place? → \(O(\log n)\) for quicksort's stack
  • Do you modify the input? → sometimes "in-place" is \(O(1)\) auxiliary

# ── Binary Search ── T: O(log n) S: O(1)
def binary_search(arr, target): # arr is sorted
lo, hi = 0, len(arr) - 1 # 2 variables: O(1) space
while lo <= hi: # loop runs ⌈log₂ n⌉ times
mid = (lo + hi) // 2 # O(1) per iteration
if arr[mid] == target: return mid
elif arr[mid] < target: lo = mid + 1 # discard left half
else: hi = mid - 1 # discard right half
return -1
# ── Merge Sort ── T: O(n log n) S: O(n)
def merge_sort(arr): # n = len(arr)
if len(arr) <= 1: return arr # base case: O(1)
mid = len(arr) // 2 # O(1)
left = merge_sort(arr[:mid]) # T(n/2) time; O(n/2) new array
right = merge_sort(arr[mid:]) # T(n/2) time; O(n/2) new array
return merge(left, right) # O(n) to merge: touches each element once
# Recurrence: T(n)=2T(n/2)+O(n) → T(n)=O(n log n) by Master Theorem
# Space: O(n) aux arrays at each level; log n levels but arrays freed
# Peak space at any moment = O(n) (one level's worth of aux arrays)
# ── Memoized Fibonacci ── T: O(n) S: O(n)
def fib(n, memo={}): # memo = hash map
if n <= 1: return n # base case: O(1)
if n in memo: return memo[n] # O(1) cache hit
memo[n] = fib(n-1,memo) + fib(n-2,memo) # each n solved once
return memo[n]
# Time: n unique subproblems, O(1) each → O(n)
# Space: O(n) cache entries + O(n) stack frames = O(n)
