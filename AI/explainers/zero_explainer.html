Understanding ZeRO
▼

What is it? ZeRO (Zero Redundancy Optimizer) is a set of memory optimization techniques developed by Microsoft DeepSpeed to enable training of extremely large deep learning models that would otherwise exceed GPU memory limits. It works by partitioning the model's memory footprint (optimizer states, gradients, and parameters) across multiple GPUs during data-parallel training, instead of replicating everything on every device.

Analogy: Imagine a large, complex project where each team member needs access to all project resources: the full plan, all current tasks, and all materials. In traditional data parallelism, every GPU is a team member with a full copy of everything. With ZeRO, the team decides to split responsibilities: in Stage 1, only the "project history" (optimizer states) is split; in Stage 2, "current tasks" (gradients) are also split; and in Stage 3, even parts of the "project plan" (parameters) are distributed. This way, no single team member (GPU) needs to hold a copy of the entire project, allowing for much larger projects overall.

💡 If you remember one thing

ZeRO stages progressively partition more components (optimizer states, gradients, and eventually parameters) across GPUs. This drastically reduces the memory footprint per GPU, allowing models with billions or even trillions of parameters to fit into available hardware, all while maintaining the simplicity and throughput benefits of data parallelism.

2
How ZeRO Works Internally
▼

The Memory Footprint of Large Models

Training large deep learning models demands significant GPU memory. The main components contributing to this memory footprint are:

  • Parameters (P): The model weights and biases. For FP32, this is \(4\) bytes per parameter.
  • Gradients (G): The gradients computed for each parameter during backpropagation. Also \(4\) bytes per parameter (FP32).
  • Optimizer States (OS): Auxiliary variables maintained by optimizers like Adam (e.g., first and second moment estimates, \(m\) and \(v\)). For Adam, this is typically \(2 \times 4 = 8\) bytes per parameter (FP32).
  • Activations: Intermediate outputs of layers during the forward pass, needed for backpropagation. This can be a very large component, but ZeRO does not directly partition activations.

In standard data parallelism with \(D\) GPUs, each GPU typically holds a full replica of P, G, and OS, leading to \(16N\) bytes per GPU for a model with \(N\) parameters (using FP32 and Adam). ZeRO aims to reduce this redundancy.

The Three Stages of ZeRO

ZeRO implements three stages of optimization, each partitioning a different set of memory components:

  1. ZeRO-1: Optimizer State Partitioning (OS)

    Only the optimizer states are partitioned across \(D\) GPUs. Each GPU stores a full copy of the model parameters (\(P\)) and gradients (\(G\)), but only \(1/D\) of the optimizer states (\(OS\)). During the optimizer step, gradients are still All-Reduced across GPUs, but each GPU only updates its local shard of optimizer states. This reduces memory for OS by a factor of \(D\).

  2. ZeRO-2: Optimizer State + Gradient Partitioning (OS+G)

    Both optimizer states and gradients are partitioned. Each GPU stores a full copy of the model parameters (\(P\)), but only \(1/D\) of the gradients (\(G\)) and \(1/D\) of the optimizer states (\(OS\)). After the backward pass, gradients are All-Reduced, but only the specific \(1/D\) shard of gradients relevant to each GPU's optimizer states is kept locally. This further reduces memory for G by a factor of \(D\).

  3. ZeRO-3: Optimizer State + Gradient + Parameter Partitioning (OS+G+P)

    All three components — parameters, gradients, and optimizer states — are partitioned. Each GPU only stores \(1/D\) of \(P\), \(1/D\) of \(G\), and \(1/D\) of \(OS\). This is the most aggressive stage. During the forward and backward passes, parameters are dynamically gathered (All-Gathered) onto the GPUs that need them for computation, then released. Gradients are computed, partitioned, and then updated on their respective shards. This achieves near-linear memory scaling with the number of GPUs.

Design Decision: ZeRO vs. Model Parallelism

ZeRO is a form of data parallelism with memory optimization. Unlike model parallelism (where different layers or parts of a model reside on different GPUs), ZeRO keeps the entire model logic on each GPU. This means it's generally easier to implement and provides better throughput for smaller models. ZeRO-3 blurs the lines by dynamically loading parameters, but the core idea remains: scale data-parallel training to larger models without complex model partitioning strategies.

🔑 Key Property

ZeRO is fundamentally a data parallelism optimization. It reduces memory redundancy by partitioning model states across GPUs, allowing each GPU to process a subset of the data batch while collectively training a much larger model. This contrasts with model parallelism, which partitions the model itself.

Why It Works — The Math
▼

Memory Footprint Derivation (per GPU)

Let \(N\) be the total number of parameters in the model. Assuming FP32 precision (\(4\) bytes per float) and an Adam optimizer (which typically uses two moment estimates, \(m\) and \(v\), for each parameter), the memory required for model states is:

  • Parameters (P): \(N \times 4\) bytes
  • Gradients (G): \(N \times 4\) bytes
  • Optimizer States (OS): \(N \times (4 \text{ bytes for } m + 4 \text{ bytes for } v) = N \times 8\) bytes

Total memory for model states on a single GPU in standard data parallelism (DDP) is therefore \(N \times (4 + 4 + 8) = 16N\) bytes.

Now, let \(D\) be the number of GPUs. ZeRO reduces this footprint as follows:

$$\begin{aligned} \text{Standard DDP: } & M_{GPU} = N \cdot (\text{size}(P) + \text{size}(G) + \text{size}(OS)) \\ & M_{GPU} = N \cdot (4 + 4 + 8) = 16N \text{ bytes} \end{aligned}$$
$$\begin{aligned} \text{ZeRO-1 (OS Partitioned): } & M_{GPU} = N \cdot (\text{size}(P) + \text{size}(G)) + \frac{N}{D} \cdot \text{size}(OS) \\ & M_{GPU} = N \cdot (4 + 4) + \frac{N}{D} \cdot 8 = 8N + \frac{8N}{D} \text{ bytes} \end{aligned}$$
$$\begin{aligned} \text{ZeRO-2 (OS+G Partitioned): } & M_{GPU} = N \cdot \text{size}(P) + \frac{N}{D} \cdot (\text{size}(G) + \text{size}(OS)) \\ & M_{GPU} = N \cdot 4 + \frac{N}{D} \cdot (4 + 8) = 4N + \frac{12N}{D} \text{ bytes} \end{aligned}$$
$$\begin{aligned} \text{ZeRO-3 (OS+G+P Partitioned): } & M_{GPU} = \frac{N}{D} \cdot (\text{size}(P) + \text{size}(G) + \text{size}(OS)) \\ & M_{GPU} = \frac{N}{D} \cdot (4 + 4 + 8) = \frac{16N}{D} \text{ bytes} \end{aligned}$$

These equations clearly show the progressive reduction in memory footprint per GPU, achieving a theoretical \(D\)-fold reduction in model states with ZeRO-3. Note that activation memory is not included here; it can still be significant and often requires techniques like activation checkpointing.

Communication Overhead

The memory savings come with increased communication. In ZeRO-1 and ZeRO-2, gradients are still All-Reduced, which is efficient. ZeRO-3 introduces All-Gather operations for parameters during forward and backward passes. This means parameters are gathered onto a GPU just before they are needed for computation, and then discarded. This "parameter-on-demand" approach can introduce significant communication latency, especially for models with many layers or small batch sizes where the communication-to-computation ratio becomes high. DeepSpeed mitigates this with various optimizations like overlapping communication with computation and CPU offloading for less frequently used parameters.

⚠️ Trade-off: Memory vs. Communication

While ZeRO-3 offers the greatest memory savings, its "parameter-on-demand" strategy requires frequent All-Gather operations. This can lead to increased communication overhead and potentially slower training, especially if network bandwidth is a bottleneck or if not carefully optimized (e.g., by overlapping communication and computation).

Key Takeaways
▼

When to use ZeRO:

  • Training very large models (e.g., >10B parameters) where standard data parallelism runs out of GPU memory.
  • When you want to scale data parallelism to more GPUs without needing to manually shard the model architecture (as in model parallelism).
  • To achieve higher throughput by using larger batch sizes, made possible by the reduced memory footprint.

When to be cautious or consider alternatives:

  • For smaller models (e.g., <1B parameters), the overhead of ZeRO (especially ZeRO-3's communication) might outweigh the memory benefits.
  • If communication bandwidth between GPUs is very limited, the All-Gather operations in ZeRO-3 can become a significant bottleneck.
  • When model parallelism is already required for other reasons (e.g., extremely long sequences that don't fit into a single GPU's compute capacity), ZeRO might not be the primary solution.
💡 Rule of Thumb

ZeRO is a powerful tool for scaling data-parallel training to unprecedented model sizes. Start with ZeRO-2 for a good balance of memory savings and communication efficiency. Only move to ZeRO-3 when ZeRO-2 is insufficient, and be prepared to fine-tune communication/computation overlap and CPU offloading strategies for optimal performance.

import deepspeed
import torch
# 1. Initialize DeepSpeed (usually from a config file)
# deepspeed --num_gpus=4 train.py --deepspeed --deepspeed_config ds_config.json
# Example ds_config.json for ZeRO-2:
# {
# "zero_optimization": {
# "stage": 2,
# "offload_optimizer": { "device": "cpu", "pin_memory": true },
# "offload_param": { "device": "cpu", "pin_memory": true } // for ZeRO-3
# },
# "train_batch_size": 16,
# "fp16": { "enabled": true }
# }
# 2. Model, Optimizer, Data Loader setup (standard PyTorch)
model = MyLargeModel()
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-5)
train_dataloader = get_train_dataloader()
# 3. Wrap with DeepSpeed (main change from vanilla PyTorch)
model_engine, optimizer, _, _ = deepspeed.initialize(
model=model,
optimizer=optimizer,
model_parameters=model.parameters()
)
# 4. Training loop (looks mostly like vanilla PyTorch)
for step, batch in enumerate(train_dataloader):
inputs, labels = batch
outputs = model_engine(inputs) # Forward pass
loss = some_loss_function(outputs, labels)
model_engine.backward(loss) # Backward pass
model_engine.step() # Optimizer step
# ZeRO-3 specific: parameters are gathered/released automatically
