Understanding SQL
▼

What is SQL? SQL (Structured Query Language) is the universal language for talking to relational databases. A relational database stores data in tables — rows and columns — and SQL lets you combine, filter, summarize, and transform that data without writing a for-loop.

Analogy: Think of a database as a well-organized filing cabinet with many labelled drawers (tables). SQL is the instruction sheet that tells the clerk: "Go to the Orders drawer, find everything from January, count how many per customer, and staple in the customer name from the Customers drawer." The clerk (query engine) figures out the fastest route.

💡 If you remember one thing

SQL is declarative: you say what you want, not how to get it. The query optimizer decides the execution plan. Mastery means understanding all five pillars: JOINs (combine tables), GROUP BY + aggregations (collapse rows), window functions (compute over rows without collapsing), CTEs (named subqueries for readability), and indexes + EXPLAIN (performance).

Joins & Aggregations — How They Work Internally
▼

Join Types — Four Variants, One Algorithm

All join types start from the same probe loop: for each row in the left table, find matching rows in the right table via the ON condition. What differs is what to do with unmatched rows:

Join TypeUnmatched left rowUnmatched right rowUse when
INNER JOINExcludedExcludedOnly want rows that exist in both
LEFT JOINKept (NULLs for right cols)ExcludedKeep all left rows, match if possible
RIGHT JOINExcludedKept (NULLs for left cols)Rare — equivalent to LEFT with tables swapped
FULL OUTER JOINKept (NULLs)Kept (NULLs)Find ALL rows, even unmatched in either

Join Execution Strategies

The query optimizer chooses from three physical algorithms (visible in EXPLAIN):

  • Nested Loop Join — iterate every left row, scan right. Cost \(O(n \cdot m)\). Best when one table is tiny or an index makes right-side lookups \(O(\log m)\).
  • Hash Join — build a hash table from the smaller table, probe with each row from the larger. Cost \(O(n + m)\) on average. Best for large unsorted tables.
  • Merge Join — both tables sorted on the join key; walk them in tandem. Cost \(O(n \log n + m \log m)\) including sort. Best when both sides already have an index (pre-sorted).
🔑 Key Property

A Hash Join on \(n\) and \(m\) rows has expected cost \(O(n + m)\) — it is the default for large equi-joins in PostgreSQL, MySQL 8+, and BigQuery when no usable index exists on the join key.

GROUP BY and Aggregation

After the optimizer resolves FROM + WHERE, GROUP BY partitions the result rows into buckets by the grouping key. Each bucket is collapsed to exactly one output row, and aggregate functions summarize each bucket:

$$\text{SELECT dept, } \underbrace{\text{COUNT}(*)}_{\text{rows per bucket}}, \underbrace{\text{AVG(salary)}}_{\text{mean of bucket}}, \underbrace{\text{SUM(revenue)}}_{\text{total of bucket}} \text{ FROM emp GROUP BY dept}$$

HAVING filters after grouping (WHERE filters before). Common mistake: filtering aggregates in WHERE instead of HAVING.

-- WRONG: cannot filter aggregates in WHERE
SELECT dept, COUNT(*) FROM emp WHERE COUNT(*) > 5 GROUP BY dept;
-- RIGHT: use HAVING for post-aggregation filter
SELECT dept, COUNT(*) AS headcount
FROM emp
GROUP BY dept
HAVING COUNT(*) > 5
ORDER BY headcount DESC;
⚠️ Common Mistake

SELECT * with GROUP BY — every column in SELECT must either be in GROUP BY or wrapped in an aggregate. If you write SELECT name, dept, COUNT(*) with GROUP BY dept, most RDBMS raise an error (MySQL may silently pick an arbitrary name per group).

Window Functions & CTEs
▼

Window Functions — The Big Idea

A window function computes a value for each row based on a window (a related set of rows) without collapsing the table. This is the superpower that GROUP BY lacks: you get per-row context AND aggregate statistics simultaneously.

$$\underbrace{f(\text{expr})}_{\text{aggregate fn}} \; \text{OVER} \; \Big(\underbrace{\text{PARTITION BY } p}_{\text{reset per group}} \; \underbrace{\text{ORDER BY } k}_{\text{define frame order}} \; \underbrace{\text{ROWS BETWEEN …}}_{\text{optional frame bounds}}\Big)$$

Window Function Anatomy

  • PARTITION BY — Divide rows into independent groups. The function resets at each partition boundary. Omitting it means one global partition.
  • ORDER BY — Defines the order within each partition. Required for ordered functions like LAG, LEAD, RANK, running totals.
  • Frame clause — Specifies which rows in the partition contribute. Default with ORDER BY: ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW (cumulative).

Key Window Functions

FunctionWhat it computesExample use case
ROW_NUMBER()Unique sequential int per rowDe-duplicate: keep first row per group
RANK()Rank with gaps on tiesLeaderboard: 1,2,2,4 (skips 3)
DENSE_RANK()Rank without gapsLeaderboard: 1,2,2,3
LAG(col, n)Value from n rows beforeMonth-over-month change
LEAD(col, n)Value from n rows afterChurn prediction: next event
SUM(col) OVER (…)Cumulative / rolling sumRunning revenue total

-- Running total of sales per department
SELECT
emp_id,
dept,
salary,
SUM(salary) OVER (
PARTITION BY dept -- reset counter at each new dept
ORDER BY emp_id -- accumulate in emp_id order
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
) AS running_total
FROM employees;
-- Month-over-month revenue change with LAG
SELECT month, revenue,
revenue - LAG(revenue, 1) OVER (ORDER BY month) AS mom_delta
FROM monthly_sales;

CTEs — Common Table Expressions

A CTE (WITH clause) names a subquery, making complex queries readable by decomposing them into named steps. It is NOT a performance optimization in most databases — the optimizer may inline or materialize it.

WITH high_value_orders AS ( -- Step 1: filter
SELECT customer_id, SUM(amount) AS total
FROM orders
GROUP BY customer_id
HAVING SUM(amount) > 1000
),
ranked AS ( -- Step 2: rank within filtered set
SELECT customer_id, total,
RANK() OVER (ORDER BY total DESC) AS rnk
FROM high_value_orders
)
SELECT * FROM ranked WHERE rnk <= 10; -- Step 3: top 10

Recursive CTEs

A recursive CTE has an anchor member (base case) and a recursive member that references the CTE itself. Use for hierarchical data (org charts, file paths, graph traversal):

WITH RECURSIVE subordinates AS (
-- Anchor: start at the CEO (manager_id IS NULL)
SELECT emp_id, name, manager_id, 0 AS depth
FROM employees WHERE manager_id IS NULL
UNION ALL
-- Recursive: find direct reports
SELECT e.emp_id, e.name, e.manager_id, s.depth + 1
FROM employees e
JOIN subordinates s ON e.manager_id = s.emp_id
)
SELECT * FROM subordinates ORDER BY depth, name;
💡 Window vs GROUP BY — The Decisive Test

Ask: "Do I need individual row data AND a group-level summary?" If yes → window function. If you only need the summary (one row per group) → GROUP BY. Example: salary as a % of department total requires both — use salary / SUM(salary) OVER (PARTITION BY dept).

Query Optimization
▼

How the Query Optimizer Works

The optimizer transforms your SQL into a physical execution plan (a tree of operators). It estimates the cost of each candidate plan using table statistics (row counts, column cardinality, histograms) and picks the cheapest. You cannot see the chosen plan without EXPLAIN.

Indexes — The Single Biggest Lever

An index is an auxiliary B-tree (or hash) structure on one or more columns that lets the engine find matching rows in \(O(\log n)\) instead of \(O(n)\) (full scan). The tradeoff: indexes consume disk and slow down INSERTs/UPDATEs.

  • B-tree index (default) — supports equality, range, ORDER BY, LIKE prefix. Use on columns in WHERE, JOIN ON, ORDER BY.
  • Hash index — equality only, faster lookup than B-tree. Useless for range queries.
  • Composite index — covers multiple columns. Column order matters: leftmost prefix rule — INDEX(a,b,c) helps queries on (a), (a,b), (a,b,c) but NOT on (b) alone.
  • Covering index — includes all columns the query needs; avoids heap lookup entirely (index-only scan).

EXPLAIN — Reading the Plan

EXPLAIN ANALYZE
SELECT o.order_id, c.name, o.amount
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE o.amount > 100;
-- Typical output (PostgreSQL):
-- Hash Join (cost=2.09..5.24 rows=3 actual time=0.08..0.13)
-- Hash Cond: (o.customer_id = c.customer_id)
-- -> Seq Scan on orders (rows=3 filter: amount>100)
-- -> Hash
-- -> Seq Scan on customers (rows=4)

Key fields to read in EXPLAIN: node type (Seq Scan = full scan, Index Scan = index used, Hash Join vs Nested Loop vs Merge Join), estimated vs actual rows (large discrepancy = stale statistics — run ANALYZE), actual time (ms per node).

Optimization Heuristics

TechniqueEffectExample
Filter early (pushdown)Reduces rows before expensive joinPut selective WHERE before JOIN, or in subquery

📐 Cost Model

Seq Scan cost \(\approx n \cdot c_{\text{io}}\). Index Scan cost \(\approx \log_B(n) \cdot c_{\text{io}} + k \cdot c_{\text{heap}}\) where \(k\) is rows matched and \(B\) is the B-tree branching factor (\(\approx 100\) for 8KB pages). Hash Join \(\approx n + m\); Nested Loop without index \(\approx n \cdot m\). This is why the optimizer avoids nested loops on large tables unless an index makes the inner lookup \(O(\log m)\).

Key Takeaways & Decision Guide
▼

Decision Tree

  • Need rows from two tables? → JOIN. Decide: INNER (only matches), LEFT (keep all left), FULL (keep all).
  • Need one summary row per group? → GROUP BY + aggregate. Filter groups with HAVING.
  • Need per-row stats AND keep all rows? → Window function with OVER (PARTITION BY … ORDER BY …).
  • Complex multi-step logic, or need to reuse a subquery? → CTE (WITH). Recursive CTE for hierarchies.
  • Query slow? → EXPLAIN ANALYZE first. Then add index on the filtered/joined/ordered column.

💡 Top Interview Tips

1. Always alias tables in joins. 2. Window functions run after WHERE/GROUP BY, before ORDER BY/LIMIT — know the logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → WINDOW → ORDER BY → LIMIT. 3. "Use EXISTS instead of IN for correlated subqueries on large tables" is a reliable optimization answer. 4. Adding an index on a foreign key column (used in JOIN ON) is the single highest-ROI optimization in OLTP databases.
