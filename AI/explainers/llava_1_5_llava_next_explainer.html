Understanding LLaVA-1.5 & LLaVA-NeXT
▼

What is it? LLaVA (Large Language and Vision Assistant) turns a text-only LLM into a chatbot that can "see" by bolting on a vision encoder and teaching the two to talk to each other. LLaVA-1.5 refined the recipe (MLP connector, academic-task data, higher-res CLIP). LLaVA-NeXT (a.k.a. LLaVA-1.6) then attacked a hard limit: the vision encoder only accepts a fixed 336×336 image, so a 1000×3000 receipt or a dense infographic gets squashed into a blurry square before the model ever sees it.

Analogy: Imagine reading a newspaper through a peephole the size of a postage stamp — you'd shrink the whole page down to fit, losing every headline. AnyRes instead slides the peephole over the page in a grid of overlapping-free patches, reads each patch at full size, and also takes one shrunk overview shot for context — then reports back everything it saw.

💡 If you remember one thing

LLaVA = frozen CLIP vision encoder + trainable MLP projector + LLM, trained with visual instruction tuning. LLaVA-NeXT's AnyRes keeps this exact recipe but first slices the input image into a grid of native-resolution tiles (plus one downsampled "base" view), encodes each tile independently, and concatenates all resulting visual tokens before feeding them — interleaved with the text prompt — into the LLM.

How It Works Internally
▼

The LLaVA-1.5 Pipeline

Three components, two of which are frozen or lightly-tuned: (1) a CLIP ViT-L/14-336px vision encoder that turns a 336×336 image into a 24×24 = 576 grid of patch embeddings (each patch is 14×14 pixels), (2) a small 2-layer MLP projector that maps each 1024-dim CLIP patch embedding into the LLM's token embedding space (e.g. 4096-dim for Vicuna-7B), and (3) the LLM itself (Vicuna/Llama), which receives the 576 projected "visual tokens" spliced into the text sequence exactly where an <image> placeholder appears, then autoregressively generates the answer.

Why LLaVA-1.5 Is Resolution-Capped

Because CLIP-ViT-L/14-336 was pretrained on 336×336 crops with a fixed 24×24 patch grid, any input image — a phone photo, a screenshot, a scanned document — is first resized/padded to exactly 336×336. A 4000×3000 photo of a whiteboard and a 336×336 thumbnail produce the same 576 visual tokens. Fine text, small objects, and dense layouts get blurred away before the LLM ever sees them.

The AnyRes Fix (LLaVA-NeXT)

AnyRes keeps the CLIP encoder frozen at its native 336×336 input size but changes what gets fed into it. Given the image's original aspect ratio, AnyRes picks the best-fitting resolution from a small set of candidate grids (e.g. 1×1, 1×2, 2×1, 2×2, 1×3, 3×1 tiles of 336px), resizes the image to that resolution, and slices it into non-overlapping 336×336 tiles. Each tile is encoded by CLIP independently (576 tokens each), and a separate base/global view (the whole image downsampled to 336×336) is encoded too, so the model retains overall scene context alongside the high-resolution local detail. All tile token grids are flattened row-major with a learned "newline" separator token inserted after each row so the LLM can recover 2-D layout, then the base-image tokens are appended, and the whole sequence is projected and spliced into the prompt just like in LLaVA-1.5.

🔑 Key Property

AnyRes is a pure input pre-processing + token-layout trick — it introduces zero new parameters in the vision encoder itself. The only new learned parameters are the row-break "newline" embedding and (in some configs) the projector is fine-tuned further; the CLIP backbone, patch size, and per-tile token count (576) never change. Resolution scales by adding more tiles, not by changing the encoder.

Design Decision: Why Tile Instead of Retrain CLIP at Higher Res?

Retraining or interpolating CLIP's position embeddings for arbitrary resolutions is possible but expensive and can degrade the pretrained visual representations. Tiling reuses the exact frozen 336px CLIP checkpoint unmodified — each tile is "just another 336×336 image" from CLIP's point of view — so all of CLIP's pretrained knowledge transfers perfectly, and resolution scaling becomes a cheap, training-light combinatorial choice (how many tiles) rather than an architecture change.

Why It Works — The Math
▼

Patch Tokenization

CLIP ViT-L/14 splits a \(336 \times 336\) image into patches of size \(14\times14\):

$$N_{\text{patch}} = \left(\frac{336}{14}\right)^2 = 24^2 = 576$$

Each tile — whether it's an AnyRes sub-tile or the base/global view — produces exactly \(576\) patch embeddings \(\{p_i\}_{i=1}^{576} \in \mathbb{R}^{1024}\), projected by the MLP connector \(f_\phi\):

$$h_i = f_\phi(p_i) = W_2 \, \sigma(W_1 p_i + b_1) + b_2 \in \mathbb{R}^{d_{\text{LLM}}}$$

AnyRes Resolution Selection

Given original image size \((W,H)\) and a candidate set of grid resolutions \(\mathcal{C} = \{(W_c, H_c)\}\) (each a multiple of 336 in each dimension), AnyRes picks the candidate that maximizes the effective resolution while minimizing wasted padding area. Let \(s = \min(W_c/W,\, H_c/H)\) be the scale factor that fits the image inside \((W_c,H_c)\) without distortion:

$$R_{\text{eff}}(W_c,H_c) = \min(sW, W_c)\cdot\min(sH, H_c), \qquad R_{\text{waste}} = W_c H_c - R_{\text{eff}}$$
$$(W^*,H^*) = \underset{(W_c,H_c)\,\in\,\mathcal{C}}{\operatorname{argmax}}\; R_{\text{eff}}(W_c,H_c) \quad\text{(ties broken by smallest } R_{\text{waste}}\text{)}$$

The chosen \((W^*,H^*)\) is always an integer multiple of \(336\) in both dimensions, giving a tile grid of \(r = H^*/336\) rows by \(c = W^*/336\) columns.

Total Visual Token Budget

With \(r \times c\) tiles plus one base/global view, and one learned newline token appended after every row of tiles to preserve 2-D structure:

$$N_{\text{visual}} = \underbrace{(r \cdot c)\cdot 576}_{\text{tiles}} \;+\; \underbrace{r}_{\text{row breaks}} \;+\; \underbrace{576}_{\text{base view}}$$

Compare this to plain LLaVA-1.5, which always has \(N_{\text{visual}} = 576\) regardless of input size. AnyRes trades a larger, input-dependent token budget for preserved fine detail — the LLM's context window (and \(O(n^2)\) attention cost) now scales with how large/rectangular the source image is.

⚠️ Common Pitfall

More tiles is not strictly better. Beyond ~6 tiles the token budget explodes (thousands of visual tokens per image), inflating both compute and the risk that the LLM's attention gets diluted across redundant, low-information tile tokens (e.g. tiling a mostly-blank background). LLaVA-NeXT caps the candidate grid set (typically up to \(2\times2\) or a few elongated shapes) rather than allowing unbounded tiling.

Key Takeaways
▼

When AnyRes helps most:

  • Document/OCR-heavy images — receipts, screenshots, slides, dense infographics with small text
  • Non-square, high aspect-ratio images (very wide or very tall) that a single square crop would butcher
  • Tasks needing fine-grained detail — counting small objects, reading fine print, chart reading

When it's overkill:

  • Simple natural images at low resolution — a single 336×336 pass is already sufficient and much cheaper
  • Tight latency/token budgets — every extra tile costs 576 more tokens through the LLM's \(O(n^2)\) attention
  • Tasks that are purely about holistic scene understanding, not local detail (the base/global view alone often suffices)
💡 Hierarchy

LLaVA-1.5 (fixed 576 tokens, 336×336 only) → LLaVA-NeXT / AnyRes (variable tiles, up to ~2880 tokens, native aspect ratio) → later multi-image / video LLaVA variants generalize AnyRes further with token-merging/pooling to keep the budget in check as resolution keeps climbing.

TILE = 336; PATCH = 14; GRID = TILE // PATCH # 24 -> 576 patches/tile
# 1. AnyRes: pick best-fit resolution from candidate grids
candidates = [(1,1),(1,2),(2,1),(2,2),(1,3),(3,1)] # (cols, rows) of TILE-sized tiles
def select_resolution(W, H, candidates):
best, best_eff, best_waste = None, -1, math.inf
for (c, r) in candidates:
Wc, Hc = c*TILE, r*TILE
s = min(Wc/W, Hc/H)
eff = min(s*W, Wc) * min(s*H, Hc)
waste = Wc*Hc - eff
if eff > best_eff or (eff == best_eff and waste < best_waste):
best, best_eff, best_waste = (c, r), eff, waste
return best # (cols, rows)

for j in range(rows) for i in range(cols)]
base_view = resize(image, (TILE, TILE)) # global context
# 3. Encode every tile + base view with the SAME frozen CLIP ViT-L/14-336

base_feats = clip(base_view).last_hidden_state[:, 1:, :] # (576,1024)

tile_tokens = [projector(f) for f in tile_feats] # rows x cols tensors of (576, d_llm)
base_tokens = projector(base_feats) # (576, d_llm)

for r in range(rows):
