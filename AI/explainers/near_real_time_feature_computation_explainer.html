Understanding Near-real-time Feature Computation
▼

What is it? Machine learning models often need features that reflect the very latest information, but also rely on long-term historical context. Near-real-time feature computation is the discipline of building data pipelines that can efficiently combine these two requirements: providing features that are fresh (minutes or seconds old) while maintaining consistency with the historical data used for model training, typically by leveraging both batch and streaming processing.

Analogy: Imagine a chef preparing ingredients for a complex dish. Some ingredients (like dried spices or pre-chopped vegetables) are prepared in large quantities once a day or week (batch). Other ingredients (like fresh herbs or a quick reduction) are prepared just moments before they're needed (real-time streaming). For a truly delicious dish, the chef needs to combine both: the long-term flavor base from batch ingredients, and the vibrant freshness from real-time ones. Near-real-time feature computation is the system that ensures both types of ingredients are available, fresh, and consistent when the final plate (prediction) is assembled.

💡 If you remember one thing

Near-real-time feature computation bridges the gap between static historical context and dynamic recent events. It's crucial for models where data freshness significantly impacts performance (e.g., fraud detection, recommendation engines), often implemented using dual batch/streaming pipelines feeding a centralized feature store.

How It Works Internally
▼

The Problem: Training-Serving Skew & Staleness

A common challenge in ML deployment is training-serving skew: features computed for training data differ from features computed for serving (real-time prediction). This can happen due to different code paths, data sources, or timing. Separately, many models simply need fresh data – a user's activity in the last 5 minutes is often more predictive than their activity last week.

The Solution: Dual Pipelines & the Feature Store

The standard pattern for near-real-time features involves two parallel data processing pipelines and a central feature store:

  1. Event Stream: Raw events (e.g., user clicks, transactions) flow into a message queue like Kafka or Kinesis.
  2. Streaming Pipeline: A stream processing engine (e.g., Flink, Spark Streaming) consumes events from the stream, computes low-latency aggregations (e.g., "count of user actions in last 5 minutes"), and writes these fresh features to the feature store. This runs continuously.
  3. Batch Pipeline: A batch processing system (e.g., Spark, Hive) processes large volumes of historical data on a schedule (e.g., daily, hourly). It computes features that require longer look-back windows or more complex aggregations (e.g., "average transaction value over last 30 days") and also writes these to the feature store.
  4. Feature Store: This critical component serves as a centralized repository for both batch and streaming features. It provides a consistent API for models to retrieve features for both online inference and offline training. It often handles point-in-time correctness for training data.
  5. Prediction Service: When a model needs to make a prediction, it queries the feature store for the latest available features, which combine outputs from both pipelines.

Design Decision: Why not just pure real-time?

While theoretically possible to compute all features in real-time, it's often prohibitively expensive and complex. Long-term aggregations (e.g., "user's lifetime value") are much more efficiently computed in batch. Moreover, maintaining consistency between training (which always uses historical data) and serving is much harder without a unified system like a feature store.

🔑 Key Property

The Feature Store is the linchpin of near-real-time feature computation. It ensures that the feature definitions and computation logic are identical for both training (offline) and serving (online) environments, directly addressing training-serving skew and providing a single source of truth for all features.

3
Why It Works — The Math / Principles
▼

Time-Windowed Aggregations

Many near-real-time features are time-windowed aggregations. These features summarize events within a specific time frame leading up to the current moment. The key difference between batch and streaming here is the length and update frequency of these windows.

Consider a sequence of events \(\{e_k\}\) occurring at times \(\{t_k\}\). A feature \(F(t)\) computed at time \(t\) over a window of length \(\Delta T\) can be generally expressed as:

$$F(t, \Delta T) = \text{Aggregate}\left(\{e_k \mid t - \Delta T \le t_k < t\}\right)$$

For example, the average transaction value over the last \(\Delta T\) period:

$$F_{avg}(t, \Delta T) = \frac{\sum_{\{k \mid t - \Delta T \le t_k < t\}} \text{value}(e_k)}{\text{count}(\{e_k \mid t - \Delta T \le t_k < t\})}$$

In a dual-pipeline setup, we might have:

  • Batch-computed feature: \(F_{batch}(t) = F_{avg}(t, \text{30 days})\), typically updated once a day.
  • Streaming-computed feature: \(F_{stream}(t) = F_{avg}(t, \text{5 minutes})\), updated continuously (e.g., every few seconds).

The model then uses both \(F_{batch}(t)\) and \(F_{stream}(t)\) to make predictions. The batch feature provides stable, long-term context, while the streaming feature captures immediate trends.

Point-in-Time Correctness for Training Data

For training, it's crucial that features reflect the state of the world at the time the event occurred, not the current time. The feature store facilitates this by storing features with timestamps. When generating training data, features are retrieved for a specific historical point in time. For example, if training a fraud model on a transaction from 3 months ago, the feature store would provide "average transactions in last 5 minutes as of 3 months ago," not "as of right now." This is often achieved through a combination of snapshotting batch features and event-time processing in streaming pipelines.

⚠️ Common Pitfall

The biggest risk is training-serving skew. If the logic for computing \(F_{batch}\) or \(F_{stream}\) differs even slightly between your offline training data generation and your online prediction service, your model's performance will degrade. A feature store mitigates this by enforcing a single, versioned definition and computation logic for all features.

Key Takeaways
▼

When to use near-real-time feature computation:

  • Fraud Detection: Immediate activity (e.g., transactions in the last minute) combined with historical spending patterns.
  • Recommendation Systems: Recent browsing/purchase history alongside long-term preferences.
  • Dynamic Pricing: Real-time demand signals blended with historical pricing trends.
  • Personalized Experiences: User's current context (e.g., location, recent searches) with their demographic data.
  • Preventing Training-Serving Skew: When consistency between training and inference feature logic is paramount.

When NOT to use:

  • Batch-only models: If your model's predictions are not sensitive to data freshness (e.g., predicting annual churn), the added complexity is unnecessary.
  • Low-latency is not critical: If a few hours or even a day of feature staleness is acceptable, simpler batch pipelines might suffice.
  • Small-scale projects: The operational overhead of managing streaming infrastructure and a feature store can be substantial for small teams or limited use cases.
  • Purely real-time features: If ALL features can be computed from the immediate request payload (e.g., simple rule-based systems), you might not need the dual-pipeline approach.
💡 Rule of Thumb

The decision to implement near-real-time feature computation hinges on the trade-off between model performance (driven by feature freshness) and system complexity/cost. For high-impact, real-time ML applications, the benefits of improved accuracy and reduced skew typically justify the engineering investment.

Code Trace — Pseudocode for Feature Pipelines
▼
# --- Core Components ---
class Event:
def __init__(self, user_id, timestamp, value):
self.user_id = user_id
self.timestamp = timestamp # Unix epoch ms
self.value = value # e.g., transaction amount
class FeatureStore:
def __init__(self): self.store = {}
def write_feature(self, user_id, feature_name, value, timestamp):
# Stores (user_id, feature_name, timestamp) -> value
self.store.setdefault(user_id, {})[feature_name] = {'value': value, 'ts': timestamp}
def get_feature(self, user_id, feature_name, as_of_ts=None):
# Retrieves the latest feature value for user_id, optionally as of a past timestamp
features = self.store.get(user_id, {})
return features.get(feature_name, {}).get('value', 0.0) # Default to 0 if not found
# --- Batch Feature Pipeline (e.g., daily average) ---
def run_batch_pipeline(historical_data, feature_store, current_batch_time):
# Process all events up to current_batch_time, e.g., for 24-hour window
daily_events = [e for e in historical_data if e.timestamp >= current_batch_time - 86400000 and e.timestamp < current_batch_time]
user_daily_sums = {}; user_daily_counts = {}
for event in daily_events:
user_daily_sums[event.user_id] = user_daily_sums.get(event.user_id, 0) + event.value
user_daily_counts[event.user_id] = user_daily_counts.get(event.user_id, 0) + 1
for user_id in user_daily_sums:
avg_value = user_daily_sums[user_id] / user_daily_counts[user_id]
feature_store.write_feature(user_id, 'daily_avg_tx', avg_value, current_batch_time)
# --- Streaming Feature Pipeline (e.g., 5-minute average) ---
def run_streaming_pipeline(event_stream, feature_store):
# Continuously processes events in micro-batches or event-by-event
# For simplicity, we'll simulate a rolling 5-min average in a simple way
current_window_events = {} # {user_id: [Event, Event, ...]}
while True: # This would be a continuous loop in a real stream processor
new_event = event_stream.read_next_event() # Blocking call
if not new_event: continue
current_window_events.setdefault(new_event.user_id, []).append(new_event)
# Remove old events from window (older than 5 minutes)
five_min_ago = new_event.timestamp - (5 * 60 * 1000)
current_window_events[new_event.user_id] = [e for e in current_window_events[new_event.user_id] if e.timestamp >= five_min_ago]
# Compute and write 5-minute average
user_events = current_window_events[new_event.user_id]
if user_events:
avg_value = sum(e.value for e in user_events) / len(user_events)
feature_store.write_feature(new_event.user_id, '5min_avg_tx', avg_value, new_event.timestamp)
# --- Prediction Service ---
def make_prediction(user_id, feature_store):
current_time = int(time.time() * 1000)
daily_avg_tx = feature_store.get_feature(user_id, 'daily_avg_tx', current_time)
five_min_avg_tx = feature_store.get_feature(user_id, '5min_avg_tx', current_time)
# Combine features and feed to model (e.g., a simple weighted average)
combined_feature = 0.3 * daily_avg_tx + 0.7 * five_min_avg_tx
return model.predict(combined_feature)
