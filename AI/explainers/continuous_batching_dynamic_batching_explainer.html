Continuous Batching / Dynamic Batching

Maximizing GPU utilization for LLM inference by processing requests as they arrive
Intermediate Deep Learning LLM Serving O(N) scheduler
1
Understanding Continuous Batching
▼

What is it? Large Language Model (LLM) inference often struggles with GPU underutilization. Requests arrive at arbitrary times, have varying prompt lengths, and require different numbers of generated tokens. Traditional static batching waits for a fixed number of requests to accumulate, pads them all to the maximum sequence length, and processes them together. This leads to significant idle GPU time and wasted computation on padding tokens. Continuous batching (also known as dynamic batching or in-flight batching) solves this by processing requests as they arrive, dynamically filling the GPU with tokens from multiple active requests, maximizing throughput and minimizing latency.

Analogy: Imagine a taxi service. Static batching is like waiting for a bus to fill up with 50 passengers before it departs, even if some passengers only need to go a short distance and others a long one. The bus is often half-empty, or it waits a long time to fill. Continuous batching is like a ride-sharing service: cars pick up and drop off passengers dynamically, always trying to fill available seats with new passengers or those continuing their journey. The cars are rarely idle, and passengers get to their destination faster without waiting for a full bus.

💡 If you remember one thing

Continuous batching transforms LLM inference from a "wait-and-process" model to a "stream-and-fill" model. Instead of large, sparse batches, it creates smaller, dense batches of actual tokens from a mix of active requests, leading to significantly higher GPU utilization, greater throughput (requests/second), and lower average latency.

How It Works Internally
▼

The Core Mechanism: Dynamic Token Scheduling

At each inference step (typically one token generation cycle), a continuous batching system performs the following:

  1. Request Queue Management: New incoming requests (prompts) are added to a pending queue.
  2. Active Request Pool: A pool of currently processing requests is maintained. These include requests whose prompts are still being processed and those actively generating new tokens.
  3. Dynamic Batch Construction: The scheduler intelligently selects tokens from the active request pool and the pending queue to form the next batch for the GPU. This batch is composed of a mix of:
    • Prompt tokens: For new requests, their entire prompt needs to be processed.
    • Generation tokens: For existing requests, one new token is generated per step.
  4. GPU Execution: The dynamically constructed batch of tokens (not requests!) is sent to the GPU. The actual batch size (total number of tokens) varies from step to step, limited only by GPU memory and computational capacity.
  5. Per-Request State Tracking: Each request's state (its KV cache, current generated length, remaining tokens to generate) is independently managed and updated.
  6. Completion and Eviction: Once a request has generated all its desired tokens, it is marked complete, its resources (especially KV cache) are freed, and it is removed from the active pool. This immediately makes space for new requests.

Design Decision: Why is this challenging to implement?

Implementing continuous batching is complex due to several factors:

  • KV Cache Management: The KV (Key-Value) cache, which stores intermediate attention states for each token, is a major memory consumer. With variable-length sequences and dynamic arrivals, efficient allocation and deallocation of KV cache blocks (often using a PagedAttention-like scheme) is critical to avoid fragmentation and maximize memory utilization.
  • Scheduling Logic: The scheduler must balance new prompt processing with ongoing token generation, potentially prioritizing certain requests or ensuring fairness.
  • Dynamic Tensor Shapes: The underlying GPU kernels must support dynamically sized batches and efficient memory access for non-contiguous KV cache blocks.
🔑 Key Property

The fundamental shift is from batching requests to batching tokens. The GPU is always busy processing a full capacity of tokens, regardless of how many individual requests those tokens belong to or where those requests are in their generation lifecycle. This keeps the GPU's compute units fed with useful work.

Why It Works — The Math of Efficiency
▼

The Problem with Static Batching: Padding Waste

In static batching, all sequences within a batch must be padded to the length of the longest sequence (or a fixed `max_seq_len`). If a batch has \(B\) requests, and their actual lengths are \(L_1, L_2, \dots, L_B\), but the maximum length is \(L_{\text{max}}\), then the total tokens processed are \(B \times L_{\text{max}}\). The useful work is \(\sum L_i\), so the utilization efficiency for a single batch is:

$$ \text{Efficiency}_{\text{static}} = \frac{\sum_{i=1}^B L_i}{B \cdot L_{\text{max}}} $$

When requests have highly variable lengths, this efficiency can be very low. Furthermore, the GPU often sits idle waiting for the next full batch to accumulate, adding "batching latency" to the overall request latency.

The Gain from Continuous Batching: Maximizing GPU Throughput

Continuous batching aims to keep the GPU fully utilized at its maximum token processing capacity at all times. If the GPU can process \(C_{\text{tokens}}\) tokens per second, and a request \(j\) has prompt length \(P_j\) and generates \(G_j\) tokens, its total effective length is \(P_j + G_j\). The total tokens processed over a time period \(\Delta T\) is approximately \(C_{\text{tokens}} \cdot \Delta T\). The throughput (requests per second) is then:

$$ \text{Throughput}_{\text{continuous}} \approx \frac{C_{\text{tokens}}}{\mathbb{E}[P_j + G_j]} $$

This throughput is much closer to the theoretical maximum of the hardware, as it minimizes idle time and padding waste. The key is that the batch size \(B_t\) at any given time step \(t\) is dynamic, composed of tokens from various requests:

$$ B_t = \sum_{i \in \text{active_requests}} (\text{tokens from request } i \text{ for step } t) $$

This \(B_t\) is kept as close as possible to the GPU's maximum physical token capacity, constrained by available memory for KV cache and computational limits.

⚠️ Memory Management is Key

While continuous batching maximizes compute utilization, it shifts the complexity to memory management, specifically for the KV cache. Each active request requires memory for its Key-Value cache (proportional to its current length). Efficiently allocating and deallocating these variable-sized blocks (e.g., using a PagedAttention-like virtual memory system) is paramount to avoid memory fragmentation and ensure a high number of concurrent requests can be handled without OOM errors.

Key Takeaways
▼

When to use Continuous Batching:

  • LLM Inference Serving: This is the primary use case for real-time, interactive LLM applications (e.g., chatbots, code generation).
  • High QPS (Queries Per Second) Environments: When many requests arrive concurrently and need low latency responses.
  • Variable Request Lengths: Especially beneficial when prompt and generation lengths vary widely, as it eliminates padding waste.
  • Maximizing GPU Throughput: When the goal is to extract the absolute maximum number of tokens generated per second from expensive GPU hardware.

When NOT to use / Alternatives:

  • Small Models / Low QPS: The overhead of dynamic scheduling and complex memory management might outweigh the benefits if GPU utilization is not a bottleneck.
  • Offline Batch Inference: For tasks where requests can be accumulated and processed in large, fixed batches (e.g., data processing, embeddings generation) without real-time constraints.
  • Very Short, Fixed-Length Sequences: If all requests have similar, short lengths, the benefits of dynamic batching diminish as static batching becomes more efficient.
💡 The Modern Standard for LLM Serving

Continuous batching, often combined with advanced KV cache management techniques like PagedAttention, has become the de facto standard for high-performance LLM inference servers (e.g., vLLM, TGI). It's a critical innovation that allows large models to be served efficiently and affordably to many users simultaneously.

Code Trace (Simplified Scheduler Logic)
▼
import collections
class Request:
def __init__(self, id, prompt_len, max_gen_len):
self.id = id
self.prompt_len = prompt_len
self.max_gen_len = max_gen_len
self.current_len = 0 # current total length (prompt + generated)
self.state = 'pending' # 'pending', 'processing_prompt', 'generating', 'completed'
self.kv_cache_blocks = [] # Simplified: list of allocated blocks
class Scheduler:
def __init__(self, gpu_max_tokens, kv_cache_manager):
self.gpu_max_tokens = gpu_max_tokens
self.kv_cache_manager = kv_cache_manager # Handles block allocation/deallocation
self.pending_requests = collections.deque()
self.active_requests = [] # Requests currently processing or generating
def add_request(self, request):
self.pending_requests.append(request)
def schedule_batch(self):
current_batch_tokens = 0
batch_to_run = []
next_active_requests = []
# 1. Prioritize new requests (prompt processing)
while self.pending_requests and current_batch_tokens < self.gpu_max_tokens:
req = self.pending_requests[0]
if self.kv_cache_manager.can_allocate(req.prompt_len + req.max_gen_len):
req = self.pending_requests.popleft()
req.state = 'processing_prompt'
req.kv_cache_blocks = self.kv_cache_manager.allocate(req.prompt_len + req.max_gen_len)
batch_to_run.append({'req': req, 'tokens': req.prompt_len})
current_batch_tokens += req.prompt_len
self.active_requests.append(req) # Move to active pool
else: break # No more space for new prompts
# 2. Add tokens for requests already in generation phase (1 token each)
for req in self.active_requests:
if req.state == 'processing_prompt': # Still processing prompt
# Assume prompt processing takes one step per prompt_len. This is simplified.
if req.current_len < req.prompt_len: # Still processing prompt
# This token was already accounted for in batch_to_run (cl33)
next_active_requests.append(req)
continue
else: # Prompt done, start generating
req.state = 'generating'
if req.state == 'generating':
if req.current_len < (req.prompt_len + req.max_gen_len):
if current_batch_tokens + 1 <= self.gpu_max_tokens:
batch_to_run.append({'req': req, 'tokens': 1}) # Add 1 token for generation
current_batch_tokens += 1
next_active_requests.append(req)
else: # No space for this request's next token, keep it active
next_active_requests.append(req)
else: # Request completed
req.state = 'completed'
self.kv_cache_manager.free(req.kv_cache_blocks)
self.active_requests = next_active_requests # Update active pool
return batch_to_run, current_batch_tokens # Return batch for GPU, total tokens
