Monitoring how much a model relies on each feature — and catching when that reliance quietly shifts

Understanding Feature Importance Drift
▼

What is it? Every deployed model leans on its input features to different degrees — some features (like credit score) usually drive most of the prediction, others barely matter. Feature importance drift is what happens when that internal weighting quietly changes over time: a feature that used to be decisive fades into the background, while another that used to be minor takes over, even though nobody retrained the model and the raw input data looks completely normal.

Analogy: Picture a chef who has been making the same soup for years using a fixed recipe: mostly stock, a little salt, a pinch of basil. The pantry looks unchanged — same jars, same brands, same shelf. But the chef has slowly, without noticing, started dumping in twice as much salt and barely touching the basil. The soup still comes out (the model still produces scores), but the recipe driving it has shifted underneath. Checking the pantry (the input data) tells you nothing is wrong. You have to taste-test what the soup is actually made of — that is what feature importance monitoring does.

💡 If you remember one thing

Data drift asks "do the inputs look different?" Feature importance drift asks "did the model change which inputs it listens to?" A model can pass every data-drift check and still be silently relying on a different feature than it did last month — importance monitoring is the only way to catch that.

How It Works Internally
▼

Step 1 — Establish a reference vector

At training or validation time, compute a per-feature importance score for every feature — usually permutation importance (shuffle one column, measure how much a metric like AUC drops) or mean absolute SHAP value across a holdout set. Normalize these scores so they sum to 1. This becomes the frozen reference importance vector \(r\), the model's "recipe" at launch.

Step 2 — Recompute on a rolling production window

On a schedule (daily or weekly), re-run the same importance procedure — same method, same code path — but on a rolling window of live scored traffic using the currently deployed model. This produces a current importance vector \(c_t\) for each time window \(t\). Because the exact same estimator is used both times, differences reflect a genuine change in reliance, not a change in methodology.

Step 3 — Compare, do not eyeball

Two complementary comparisons matter: ranking (did feature order change — Spearman rank correlation between \(r\) and \(c_t\)) and magnitude (did the shape of the distribution change even without full reordering — total variation / L1 distance between the normalized vectors). A feature can collapse from 25% to 4% contribution while never losing its rank position; only a magnitude metric catches that.

Step 4 — Run this alongside, not instead of, data drift

Standard data drift (PSI, KS-test) monitors the marginal distribution of each raw input. It answers "does income look different this month?" It does not answer "does the model care about income differently this month?" A model can have zero measurable data drift and severe importance drift simultaneously — this is the case this explainer walks through.

🔑 Design decision: why not just watch accuracy?

Accuracy and other outcome metrics often lag by weeks (labels take time to arrive) or never arrive at all in production (fraud, credit default). Feature importance can be recomputed the moment new predictions land, with no labels required — it is a leading indicator that a model's internal reasoning is shifting, well before that shift shows up as a measurable performance drop.

3
Why It Works — The Math
▼

Ranking divergence: Spearman rank correlation

Let \(\operatorname{rank}(v)\) map each feature to its position when importances are sorted descending. For reference ranks \(R_i\) and current ranks \(C_i\) over \(n\) features:

$$\rho = 1 - \frac{6 \sum_{i=1}^n (R_i - C_i)^2}{n(n^2-1)}$$

\(\rho = 1\) means identical ordering; \(\rho\) falls sharply whenever even one adjacent pair swaps places, because \((R_i - C_i)^2\) grows quadratically with how far a feature moves.

Magnitude divergence: total variation distance

Normalize both vectors to sum to 1, then measure how much probability mass would need to move to turn one into the other:

$$\mathrm{TVD}(r, c) = \tfrac{1}{2}\sum_{i=1}^n |r_i - c_i|, \qquad \mathrm{TVD} \in [0, 1]$$

Unlike Spearman, TVD is sensitive to a feature quietly losing half its weight even if it never changes rank — this is exactly the "collapsing contribution" failure mode.

Contrast: population stability index (plain data drift)

For a single raw feature, bucket its values into bins and compare the reference and current population percentages \(r_i, c_i\) per bin:

$$\mathrm{PSI} = \sum_{i=1}^k (c_i - r_i)\,\ln\!\left(\frac{c_i}{r_i}\right)$$

PSI \(< 0.1\) is conventionally "no meaningful shift." Crucially, PSI operates on the input distribution alone — it has no notion of the model at all, so it cannot detect importance drift by construction.

⚠️ Common pitfall

Permutation and SHAP importance estimates are themselves noisy, especially on small rolling windows. A single week's dip in \(\rho\) or bump in TVD can be sampling noise, not real drift. Production monitors typically require the alert condition to hold for several consecutive windows, or use bootstrap confidence intervals around the importance estimate, before paging anyone.

Key Takeaways
▼

When to monitor feature importance drift:

  • High-stakes, slow-feedback domains — credit risk, fraud, insurance underwriting — where true labels arrive weeks or months late
  • Models fed by many upstream pipelines, where a silent unit change, null-fill change, or schema change in one column can shift its usefulness without changing its distribution
  • Regulated settings where you must be able to explain, on demand, "what is this model actually using right now"

When it is less useful:

  • Very high-traffic, fast-feedback settings where outcome metrics are already available same-day — direct performance monitoring may be simpler and sufficient
  • Extremely small feature sets where a human can just read the SHAP summary plot manually each week
💡 Two metrics, two failure modes

Use Spearman rank correlation to catch reordering (a new feature becomes the top driver) and total variation distance to catch collapse (a feature keeps its rank but loses most of its weight). Neither one alone tells the whole story — pair them, and always plot them next to plain input data drift (PSI/KS) so you know whether the cause is upstream data or the model's own relationship to that data.

import numpy as np
from scipy.stats import spearmanr
# --- Step 1: reference importance, computed once at launch ---
ref_importance = permutation_importance(model, X_val, y_val).importances_mean
ref_vec = ref_importance / ref_importance.sum()
# --- Step 2: recompute weekly on a rolling production window ---
def weekly_importance(model, X_window, y_window):
imp = permutation_importance(model, X_window, y_window).importances_mean
return imp / imp.sum()
# --- Step 3a: ranking divergence ---
def rank_correlation(ref_vec, cur_vec):
rho, _ = spearmanr(ref_vec, cur_vec)
return rho
# --- Step 3b: magnitude divergence ---
def total_variation_distance(ref_vec, cur_vec):
return 0.5 * np.abs(ref_vec - cur_vec).sum()
# --- Step 3c: plain data drift, for contrast ---
def psi(ref_bins, cur_bins):
return np.sum((cur_bins - ref_bins) * np.log(cur_bins / ref_bins))
