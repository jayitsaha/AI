Understanding Docker
▼

What is it? Docker is a platform that uses OS-level virtualization to deliver software in packages called containers. These containers are isolated from each other and from the host system, bundling an application and all its dependencies (libraries, configs, etc.) into a single, consistent unit that can run reliably across different computing environments.

Analogy: Think of standard shipping containers. They provide a standardized way to package goods (your application and its dependencies) so they can be transported (deployed) on any ship, train, or truck (server, laptop, cloud VM) without worrying about what's inside or how it interacts with the vehicle. Docker solves the "it works on my machine" problem by ensuring your application always runs in the exact same environment.

💡 If you remember one thing

Docker provides lightweight, portable, and self-sufficient environments for applications. It separates your application from the underlying infrastructure, guaranteeing consistency from development to production. This is achieved through images (read-only blueprints) and containers (runnable instances of images).

How Docker Works Internally
▼

Images and Containers: The Blueprint and the House

A Docker Image is a read-only template that contains a set of instructions for creating a container. It's built from a Dockerfile. An image is composed of layers, each representing a Dockerfile instruction. These layers are cached, making builds fast and efficient. A Docker Container is a runnable instance of a Docker image. When you run an image, Docker adds a thin, writable layer on top of the image's read-only layers. All changes made by the container (e.g., writing logs, creating files) go into this writable layer, keeping the base image pristine.

Dockerfile: The Build Instructions

A Dockerfile is a plain text file that defines how to build a Docker image. It contains a sequence of commands, each of which creates a new layer in the image. Key instructions include:

  • FROM: Specifies the base image (e.g., ubuntu:latest, python:3.9-slim).
  • RUN: Executes commands during the image build process (e.g., `apt-get install`, `pip install`).
  • COPY / ADD: Copies files from the host into the image.
  • WORKDIR: Sets the working directory for subsequent instructions.
  • EXPOSE: Informs Docker that the container listens on the specified network ports at runtime.
  • CMD / ENTRYPOINT: Defines the default command to execute when a container starts.

Multi-Stage Builds: Leaner Images

For complex applications (especially compiled ones or those with large build dependencies), a single-stage Dockerfile can result in bloated images. Multi-stage builds allow you to use multiple FROM statements in a single Dockerfile. Each FROM instruction starts a new stage. You can then selectively copy artifacts from one stage to a final, much smaller stage, discarding all the build tools and intermediate files. This significantly reduces the final image size and attack surface.

GPU Support: nvidia-docker

Standard Docker containers run in an isolated environment and don't inherently have access to host GPU devices. For machine learning and deep learning workloads, GPU acceleration is crucial. nvidia-docker (or more recently, the NVIDIA Container Toolkit) is a set of tools that allows Docker containers to access NVIDIA GPUs. It works by injecting necessary GPU drivers, libraries (like CUDA and cuDNN), and device files into the container at runtime, effectively bridging the container's isolated environment with the host's GPU hardware.

🔑 Key Property

Docker leverages Linux kernel features like namespaces (for process, network, and filesystem isolation) and cgroups (for resource limiting) to achieve lightweight virtualization without the overhead of a full virtual machine. This makes containers much faster to start and more efficient with resources than traditional VMs.

Why It Works — The Principles of Containerization
▼

Layered Filesystem: Union Mounts

Docker images are built from a series of read-only layers. Each instruction in a Dockerfile typically creates a new layer. These layers are stacked on top of each other using a union filesystem (like OverlayFS). When a container runs, a thin, writable "container layer" is added on top. This mechanism is efficient because:

  • Caching: If an instruction hasn't changed, its layer is reused.
  • Sharing: Multiple containers can share the same base layers, saving disk space.
  • Copy-on-Write: Changes in the container only affect its top writable layer, leaving underlying image layers untouched.
$$ \text{ContainerFS} = \text{RWLayer} \cup \text{ImageLayer}_N \cup \dots \cup \text{ImageLayer}_1 $$

Where \(\cup\) denotes a union mount operation, giving precedence to higher layers for file access.

Image Immutability and Determinism

Once built, a Docker image is immutable. Its content is fixed, and it's identified by a unique SHA256 hash. This hash is a cryptographic checksum of its layers and metadata, ensuring that the image you build today is identical to the one you run tomorrow. This determinism is crucial for reproducible ML experiments.

$$ \text{ImageID}(I) = \text{SHA256}(\text{Layer}_1, \dots, \text{Layer}_N, \text{Config}) $$

Each layer's ID itself is a hash of its parent layer's ID and the command that created it, plus its filesystem changes.

Resource Isolation: Namespaces and Cgroups

Containers are not virtual machines; they share the host OS kernel. Their isolation is achieved through specific Linux kernel features:

  • Namespaces: Partition kernel resources (process IDs, network interfaces, mount points, user IDs) so that a process inside a container sees its own isolated view of the system. For example, a container's pid 1 is its own init process, not the host's.
  • Cgroups (Control Groups): Limit, account for, and isolate resource usage (CPU, memory, disk I/O, network) for groups of processes. This prevents one container from monopolizing host resources.
$$ \text{Container}_{\text{proc}} \subseteq \text{PIDNamespace}_{\text{Host}}, \quad \text{Container}_{\text{net}} \subseteq \text{NetNamespace}_{\text{Host}} $$

This means a container's processes and network are distinct views within the host's overall system, not entirely separate hardware emulations.

⚠️ Common Pitfall

Containers are not VMs. They share the host kernel. This means a vulnerability in the kernel affects all containers, and you cannot run a Windows container on a Linux host (without a VM). This shared kernel is also why they're so lightweight compared to VMs.

Key Takeaways
▼

When to use Docker:

  • Reproducible ML: Guarantee that your models train and predict identically across different environments.
  • Consistent Deployment: Package your ML inference service with all its dependencies for seamless deployment to cloud, edge, or on-premise.
  • Isolated Development: Develop multiple projects with conflicting dependencies on the same machine without environment clashes.
  • Scalability: Easily scale your application by spinning up more container instances.
  • CI/CD Pipelines: Integrate container builds and tests into automated workflows.

When NOT to use / be aware of:

  • Overhead for simple scripts: For extremely trivial scripts, the Docker overhead might be more than the benefit.
  • Shared Kernel: If strong kernel-level isolation or running different OS kernels is required, a full VM is still necessary.
  • Cold Start Latency: While faster than VMs, containers still have a startup time, which can be a factor for extremely latency-sensitive, bursty workloads.
  • Security concerns: While isolated, containers are not foolproof. Malicious code could potentially escape a container if the host kernel is vulnerable or misconfigured.
💡 Rule of Thumb

For any non-trivial ML project, especially those involving complex dependency stacks (specific Python versions, CUDA, cuDNN, PyTorch/TensorFlow versions), Docker is an indispensable tool for ensuring reproducibility and portability across the entire ML lifecycle.

Code Trace — Building & Running
▼
# Simple Dockerfile for a Python ML app (e.g., app.py with scikit-learn)
# Dockerfile
FROM python:3.9-slim-buster
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
# Build the image
docker build -t my-ml-app:latest .
# Run the container (CPU-only)
docker run -p 8000:8000 my-ml-app:latest
# For GPU support (assuming NVIDIA Container Toolkit installed)
# Dockerfile for GPU-enabled app (e.g., app.py with PyTorch/TensorFlow)
# Dockerfile.gpu
FROM nvcr.io/nvidia/pytorch:23.07-py3
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
# Build the GPU image
docker build -f Dockerfile.gpu -t my-gpu-app:latest .
# Run the GPU container (requires --gpus all or specific device IDs)
docker run --gpus all -p 8000:8000 my-gpu-app:latest
