Understanding Prediction Logging & Auditing
▼

What is it? Every time a deployed model serves a prediction, an MLOps system writes a durable record of the request (input features), the response (output, score, decision), which exact model artifact produced it (name + version), and the timestamp — before the answer is even returned to the caller. That record is never edited afterward; it can only be appended to. Auditing is the practice of later reconstructing "what did the model see, and why did it decide that", using these logs joined with real-world outcomes that often arrive weeks or months after the fact.

Analogy: It is the flight recorder ("black box") of an aircraft. It does not change how the model flies — it only watches and writes. If a regulator, a customer, or an incident responder later asks "why was this transaction blocked on March 1st?", the black box lets you replay the exact decision instead of guessing from memory or reconstructing it from scattered application logs.

💡 If you remember one thing

Log \((\text{input}, \text{output}, \text{model\_version}, \text{timestamp}, \text{request\_id})\) for every prediction before you return the response. The request_id is the join key that later lets you attach ground truth, replay decisions, and prove compliance — long after the moment has passed.

How It Works Internally
▼

The Append-Only Store

Every log record lands in a write-once-read-many (WORM) store — an object store with retention locks, an append-only Kafka topic feeding a data lake, or an immutable ledger table. No UPDATE or DELETE is permitted on past rows; corrections happen by appending a new "supersedes" record, never by mutating history. This guarantees that whatever an auditor reads later is exactly what was written at inference time.

Joining With Delayed Ground Truth

The true label — did the transaction turn out to be fraud, did the patient actually relapse — frequently arrives days, weeks, or months after the prediction. A separate feedback pipeline listens for these outcomes and joins them back to the original log row using the request_id correlation key. Only after this asynchronous join can you compute real-world accuracy, precision, recall, and drift — not just the model's confidence at serving time.

Replaying a Past Decision

To replay a decision means: pull the exact input and the exact model_version from the log, re-run inference through a model registry, and confirm the output matches what was originally returned. This only works if every model artifact is itself versioned and retrievable, and if the log captured the full request context — not a lossy summary.

Hash-Chained Immutability

Beyond "we promise not to edit it," a hash chain gives cryptographic tamper evidence: each record's hash is computed over its own payload plus the previous record's hash, so altering any single historical field cascades and invalidates every hash after it. An auditor — or an automated integrity check — detects tampering just by recomputing the chain.

🔑 Design Decision

Why hash-chain instead of just a timestamped database row? A database row can be edited in place — even with permissions, an admin (or a bug) can silently rewrite history. A hash chain makes any single-field edit mathematically detectable without needing to trust the storage layer's access controls at all.

Why It Works — The Math
▼

Hash-Chain Recurrence

Define the hash of record \(i\) as a function of the previous hash and this record's payload:

$$H_i = \mathrm{Hash}\big(H_{i-1} \,\|\, \text{payload}_i\big), \qquad H_0 = \text{genesis}$$

Because hash functions exhibit the avalanche effect, changing even one byte of \(\text{payload}_i\) produces an unrelated \(H_i\), which then changes \(H_{i+1}, H_{i+2}, \dots\) all the way to the tip of the chain. Detecting tampering reduces to: recompute the chain from the edited row forward and compare against a value you already trust — a previously published tip, or the hash everyone downstream has already seen.

Audit Metrics From the Join

Once predictions are joined with delayed outcomes, standard classification metrics fall out directly from the confusion counts:

$$\text{Precision} = \frac{TP}{TP+FP}, \quad \text{Recall} = \frac{TP}{TP+FN}, \quad \text{Accuracy} = \frac{TP+TN}{TP+TN+FP+FN}$$

where "positive" means the model's own actionable decision (e.g. BLOCK), not merely a raw score crossing an arbitrary line.

⚠️ Common Pitfall

A record still pending ground truth (no outcome has arrived yet) must be excluded from the denominator, not silently treated as correct. Counting pending rows as true negatives silently inflates accuracy and hides exactly the cases regulators care about most — the recent, still-unresolved decisions.

Key Takeaways
▼

When to log everything:

  • Any decision with a delayed or disputed outcome — credit, fraud, medical, safety
  • Regulatory drivers: EU AI Act high-risk logging duties, US SR 11-7 model risk management, GDPR "right to explanation"
  • Anything a customer could dispute months later

When sampling is acceptable:

  • Low-stakes, high-QPS traffic (e.g. recommendation re-ranking) where storage cost dominates risk — log a statistically sufficient sample plus 100% of decisions above a risk threshold

Common pitfalls:

  • Unbounded storage growth — add retention tiers and cold storage
  • PII sitting unencrypted in logs — hash or tokenize sensitive fields at write time
  • Clock skew across services — use one trusted time source, never client-supplied device time
💡 Hierarchy

Logging ⊂ Logging + Join (monitoring/drift) ⊂ Logging + Join + Replay + Hash-Chain (fully auditable). Each layer adds a guarantee the previous one lacked.
