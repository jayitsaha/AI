SLAM: Simultaneous Localization and Mapping

Building a map while simultaneously figuring out where you are on it
Intermediate Robotics Computer Vision Real-time
1
Understanding SLAM
▼

What is it? Simultaneous Localization and Mapping (SLAM) is a core problem in robotics and autonomous systems. It refers to the computational problem of building or updating a map of an unknown environment while simultaneously keeping track of an agent's (e.g., robot, drone, self-driving car) location within that environment. It's a chicken-and-egg problem: you need a map to localize yourself, but you need to know your location to build an accurate map.

Analogy: Imagine you're dropped blindfolded into a completely dark, unfamiliar house. You have a flashlight and a pen and paper. As you slowly walk around (motion), you periodically turn on your flashlight to see a few objects (sensing) and sketch them onto your paper (mapping). At the same time, you're trying to figure out where you are on your growing, incomplete sketch (localization). SLAM is the process of doing both at once, constantly refining your position estimate and your map as you explore.

💡 If you remember one thing

SLAM solves the "chicken-and-egg" problem of navigation: it iteratively refines both the robot's pose (position and orientation) and the map of its surroundings. The magic happens when the robot revisits a known area (a "loop closure"), allowing it to correct accumulated errors across its entire trajectory and map.

2
How SLAM Works Internally
▼

The Core SLAM Loop: Sense, Match, Estimate, Update

Most SLAM systems follow a general pipeline, often divided into a "front-end" and a "back-end":

  1. Sensing: The robot gathers data from its environment using sensors (e.g., cameras, LiDAR, IMU).
  2. Feature Extraction & Data Association (Front-End): From the raw sensor data, salient features (e.g., corners in images, points in a LiDAR scan) are extracted. These new observations are then matched (associated) with existing features in the current map. This is a critical step, as incorrect associations lead to severe errors.
  3. State Estimation & Map Update (Back-End): Using the robot's motion model and the associated sensor observations, a probabilistic framework (e.g., Kalman Filter, Particle Filter, Graph Optimization) estimates the robot's current pose and updates the positions of landmarks on the map.
  4. Loop Closure Detection & Correction (Back-End): A key part of SLAM. If the robot recognizes that it has returned to a previously visited location, it detects a "loop closure." This provides a strong constraint that allows the back-end to globally optimize the entire map and trajectory, correcting accumulated drift.

Sensor Modalities: Visual vs. LiDAR

Different sensors lead to different SLAM characteristics:

  • Visual SLAM: Uses cameras (mono, stereo, RGB-D). Relies on extracting visual features (e.g., SIFT, ORB, deep features) and tracking them across frames. Pros: rich information, low cost. Cons: sensitive to lighting, textureless environments, fast motion blur.
  • LiDAR SLAM: Uses LiDAR sensors to generate 3D point clouds. Relies on point cloud registration algorithms (e.g., ICP, GICP). Pros: robust to lighting, provides direct depth. Cons: high cost, sparse data, less distinctive features.
  • Sensor Fusion: Combining multiple sensors (e.g., camera + IMU, LiDAR + IMU) is common to leverage their complementary strengths and improve robustness.
🔑 Key Property

The fundamental challenge in SLAM is managing uncertainty. Both robot motion and sensor observations are noisy. Probabilistic methods are essential to model and propagate this uncertainty, allowing for consistent map and pose estimates, especially during loop closures where global consistency is enforced.

3
Why It Works — The Probabilistic Framework
▼

The SLAM Posterior

At its core, SLAM is a state estimation problem. We want to estimate the robot's trajectory (sequence of poses \(X_{1:k}\)) and the map of landmarks (\(M\)) given all past sensor observations (\(Z_{1:k}\)) and control inputs/odometry (\(U_{1:k}\)). This is represented by the posterior probability:

$$p(X_k, M | Z_{1:k}, U_{1:k})$$

This joint posterior is often too complex to compute directly. Instead, methods like Kalman filters, particle filters, or graph-based optimization approximate this by modeling the system's dynamics and observations.

Motion and Observation Models

The system typically involves two probabilistic models:

1. **Motion Model:** Describes how the robot's state changes over time based on control inputs. $$X_k = f(X_{k-1}, U_k) + w_k$$ Here, \(X_k\) is the robot's pose at time \(k\), \(U_k\) is the control input (e.g., wheel encoder readings, IMU data), \(f\) is the non-linear motion function, and \(w_k\) represents the process noise (e.g., wheel slip, IMU drift), typically assumed to be Gaussian: \(w_k \sim \mathcal{N}(0, Q_k)\).

2. **Observation Model:** Describes how sensor measurements relate to the robot's state and map landmarks. $$Z_k = h(X_k, M) + v_k$$ Here, \(Z_k\) is the observation at time \(k\), \(h\) is the non-linear observation function (e.g., transforming a landmark's global coordinates to sensor coordinates), and \(v_k\) is the observation noise (e.g., sensor inaccuracies), typically assumed Gaussian: \(v_k \sim \mathcal{N}(0, R_k)\).

Graph-Based SLAM: Optimizing Consistency

Modern SLAM often uses graph optimization, especially for loop closure. The robot's poses and landmark positions become nodes in a graph, and the motion and observation models become edges (constraints). The problem is then to find the configuration of nodes that best satisfies all constraints:

$$\min_{X, M} \left( \sum_{k} \|X_k - f(X_{k-1}, U_k)\|^2_{Q_k^{-1}} + \sum_{k, j} \|Z_{k,j} - h(X_k, M_j)\|^2_{R_{k,j}^{-1}} \right)$$

This objective function minimizes the sum of squared errors (Mahalanobis distance) weighted by the inverse of the covariance matrices (\(Q_k^{-1}\) and \(R_{k,j}^{-1}\)). Loop closures add new, often very strong, observation constraints between distant poses, forcing the entire graph to adjust and globally correct drift.

⚠️ Common Pitfall

The biggest challenge is data association. If an observation is incorrectly matched to a landmark (e.g., mistaking one tree for another identical-looking tree), it introduces a catastrophic "false positive" constraint that can severely corrupt the map and lead to divergence. Robust data association techniques (e.g., RANSAC, gating) are crucial, as is the ability to recover from such errors.

Key Takeaways
▼

When to use SLAM:

  • Autonomous navigation in unknown or dynamic environments (e.g., self-driving cars, delivery robots, drones).
  • Augmented Reality (AR) and Virtual Reality (VR) to track user pose and build virtual environments.
  • Robotics for mapping, exploration, and manipulation tasks.
  • Any application where a precise map and accurate localization are needed without prior infrastructure (GPS, beacons).

When NOT to use / Challenges:

  • Environments with known, static maps (just use localization/pose estimation).
  • Insufficient computational resources for real-time processing (SLAM is computationally intensive).
  • Degenerate environments (e.g., long, featureless corridors, pure rotation without translation) can lead to tracking loss.
  • Dynamic environments with many moving objects (dynamic SLAM is an active research area).
💡 Filter-based vs. Optimization-based SLAM

**Filter-based SLAM** (e.g., EKF SLAM, Particle Filter SLAM) processes data sequentially, updating the state at each step. It's efficient for small maps but suffers from consistency issues and high computational cost for large maps. **Optimization-based (Graph) SLAM** formulates the problem as a global optimization over all poses and landmarks. It's more computationally expensive per step but offers better global consistency and robustness to loop closures, making it dominant in modern applications.

Code Trace — Simplified Graph SLAM Loop
▼
import numpy as np
from scipy.optimize import least_squares
# Simplified 2D pose (x, y, theta) and landmark (lx, ly)
# Graph nodes: [x0,y0,t0, x1,y1,t1, ..., lx0,ly0, lx1,ly1, ...]
def residual_function(state_vector, odometry_constraints, obs_constraints):
residuals = []
num_poses = len(odometry_constraints) + 1
# Extract poses and landmarks from state_vector
poses = state_vector[:num_poses*3].reshape(-1, 3)
landmarks = state_vector[num_poses*3:].reshape(-1, 2)
# Odometry residuals (motion model)
for i in range(num_poses - 1):
x_prev, y_prev, th_prev = poses[i]
dx, dy, dth = odometry_constraints[i]
# Predict next pose based on odometry
pred_x = x_prev + dx * np.cos(th_prev) - dy * np.sin(th_prev)
pred_y = y_prev + dx * np.sin(th_prev) + dy * np.cos(th_prev)
pred_th = th_prev + dth
# Error between predicted and actual pose[i+1]
residuals.extend([poses[i+1,0] - pred_x, poses[i+1,1] - pred_y, poses[i+1,2] - pred_th])
# Observation residuals (sensor model)
for obs_idx, landmark_idx, dist, angle in obs_constraints:
x_robot, y_robot, th_robot = poses[obs_idx]
x_lm, y_lm = landmarks[landmark_idx]
# Predict observation based on current state_vector
dx_rel = x_lm - x_robot
dy_rel = y_lm - y_robot
pred_dist = np.sqrt(dx_rel**2 + dy_rel**2)
pred_angle = np.arctan2(dy_rel, dx_rel) - th_robot
# Error between predicted and actual observation
residuals.extend([pred_dist - dist, pred_angle - angle])
return np.array(residuals)
# --- Main SLAM Loop (simplified) ---
# 1. Initialize robot pose and empty map
# 2. For each new sensor reading and motion:
# a. Predict new robot pose based on odometry
# b. Extract features from sensor data
# c. Data Association: Match new features to existing map features
# - If new: add to map (with high uncertainty)
# - If known: add observation constraint to graph
# d. Loop Closure: Check if current area was visited before
# - If detected: add strong loop closure constraint to graph
# e. Optimization: If loop closure or enough new data, run least_squares
# - `least_squares(residual_function, initial_guess, ...)`
# - Update all poses and landmark positions in the graph
