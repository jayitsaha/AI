Higher-Order Gradients: Hessian-Vector Products

Exact curvature information, computed without ever forming the Hessian matrix
Advanced Optimization Autodiff O(n) memory, not O(n²)
1
Understanding Hessian-Vector Products
▼

What is it? The gradient of a function tells you which direction is "downhill." The Hessian describes how that gradient itself changes as you move — the curvature. A Hessian-vector product (HVP) answers "if I nudge my parameters slightly in direction \(v\), how does the gradient shift?" — and remarkably, it can be computed exactly, without ever building the full \(n \times n\) Hessian matrix.

Analogy: Driving on a hilly road, the slope under your tires right now is the gradient. How sharply that slope changes as you keep driving — is the road curving into a bowl or over a ridge? — is the curvature, the Hessian. You almost never need the full curvature map of every road (the Hessian matrix); you just need "if I steer this way, how does my slope change?" — one direction at a time. That's a Hessian-vector product.

💡 If you remember one thing

$$Hv = \nabla_x\big(\nabla f(x)^\top v\big)$$ Differentiating the scalar \(g(x)\cdot v\) a second time gives the exact Hessian-vector product — one extra backward pass, no \(O(n^2)\) matrix ever materializes.

2
How It Works Internally
▼

The Problem with an Explicit Hessian

For a model with \(n\) parameters, the Hessian is \(n \times n\). A 1-billion-parameter model would need an 8-exabyte Hessian — physically impossible to store, let alone invert for Newton's method.

Two Equivalent Exact Methods

(A) Forward-over-reverse (Pearlmutter's R-operator, 1994): run the reverse-mode backward pass that produces \(g(x) = \nabla f(x)\), but propagate a directional derivative \(\mathcal{R}_v\{\cdot\}\) through every intermediate quantity, seeded with direction \(v\) at the input. Output is \(Hv\) directly, in one combined pass.

(B) Reverse-over-reverse ("double backprop" — what PyTorch/JAX do): (1) forward pass computes \(L(x)\); (2) first backward pass computes \(g = \nabla_x L(x)\), keeping that backward computation itself differentiable; (3) form the scalar \(u = g \cdot v\); (4) a second backward pass differentiates \(u\) w.r.t. \(x\), producing \(Hv\) exactly.

Design Decision: Why Not Just Form H?

Because Krylov-subspace methods (Conjugate Gradient, Lanczos) — used in Newton-CG, trust-region optimization, and influence functions — only ever need the Hessian as a matrix-vector operator, never as an explicit matrix. HVP costs \(O(n)\) memory, the same order as a single gradient.

🔑 Key Property

Because the backward pass is built from ordinary differentiable operations (not a black box), calling autodiff a second time on the gradient's own graph is just... autodiff again. This is what create_graph=True enables in PyTorch.

3
Why It Works — The Derivation
▼

Let \(g(x) = \nabla f(x)\) and fix a constant vector \(v\). Define the scalar \(s(x) = g(x)^\top v = \sum_i g_i(x)\,v_i\). Since \(v\) doesn't depend on \(x\):

$$\nabla_x s(x) = \sum_i v_i \,\nabla_x g_i(x)$$

Now \(g_i(x) = \partial f/\partial x_i\), so \(\nabla_x g_i(x)\) is exactly column \(i\) of the Hessian. Substituting:

$$\nabla_x s(x) = \sum_i v_i\, H_{:,i} = Hv$$

This relies on Schwarz's theorem: continuous second partials make \(H\) symmetric (\(H^\top = H\)), so treating \(\nabla_x g_i\) as a column of \(H\) is valid even though the derivation naturally produces \(H^\top v\).

Cost: by the Baur–Strassen theorem, \(\text{cost}(\nabla f) \le c \cdot \text{cost}(f)\) with \(c \approx 5\), independent of \(n\). Since \(Hv\) is "just" differentiating a scalar built from \(g\), the same bound applies one level up: \(\text{cost}(Hv) = O(\text{cost}(\nabla f)) \ll O(n^2)\).

⚠️ Common Misconception

"To get \(Hv\) you must first build \(H\), then multiply." False — that's exactly what this trick avoids. \(H\) is never materialized; only two backward passes through the original graph.

Key Takeaways
▼

When to use exact HVP:

  • Newton-CG / trust-region optimization that needs true curvature
  • Influence functions — solving \(H^{-1}g\) via Conjugate Gradient using only \(Hv\)
  • Second-order MAML meta-gradients
  • Lanczos-based Hessian eigenvalue spectrum / sharpness analysis

When NOT to use it:

  • First-order methods (SGD/Adam) already converge fast enough
  • A cheap, always-PSD curvature proxy suffices — use Gauss-Newton/Fisher instead
  • Meta-learning at scale where FOMAML/Reptile's first-order approximation is "good enough"
💡 The Big Idea

Every "extra" derivative you want is just one more pass of autodiff through a graph that already contains the previous derivative. Second-order gradients aren't a special algorithm — they're ordinary backprop, applied twice.

Code Trace (PyTorch Double Backprop)
▼
w = torch.tensor([0.4, 0.6], requires_grad=True)
x = torch.tensor([1.0, 0.5])
v = torch.tensor([1.0, 0.0])
z = w @ x
h = torch.tanh(z)
L = h ** 2
# backward pass #1 -- KEEP graph differentiable
g, = torch.autograd.grad(L, w, create_graph=True)
# dot product with chosen direction v
u = g @ v
# backward pass #2 -- differentiate u = g.v again
Hv, = torch.autograd.grad(u, w)
print(Hv) # tensor([-0.1216, -0.0608])
