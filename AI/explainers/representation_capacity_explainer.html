Understanding Representation Capacity
▼

What is it? Representation capacity measures how many different functions an architecture could compute across every possible setting of its weights — not the specific function training actually finds. A single linear layer can only draw one straight decision boundary. Stack nonlinear layers and the achievable function class explodes: piecewise-linear "folds" of input space that can carve out arbitrarily intricate regions.

Analogy: Think of a box of LEGO bricks. A bigger, more varied brick set (more depth, more width, more nonlinearity) lets you build far more elaborate structures. But owning a huge brick set doesn't mean you'll build the castle in the instructions — you might build a chaotic pile that only looks right from one angle. Capacity is about what's buildable, not whether you'll build the right thing.

💡 If you remember one thing

Depth grows the number of representable functions exponentially; width grows it only polynomially. But more capacity is necessary, not sufficient, for good generalization — the gap is bridged by optimization and regularization, not by capacity alone.

How It Works Internally: Folding Space
▼

A ReLU unit defines a hyperplane \(\{x : w\cdot x + b = 0\}\): on one side it passes its input through unchanged, on the other it zeroes it out. A single layer of \(n\) such units in \(d\) dimensions partitions space into at most \(\sum_{j=0}^{d}\binom{n}{j}\) linear regions — inside each region the whole network computes one fixed affine map. That's polynomial growth in width.

Stacking layers is different: each downstream layer doesn't just add its own hyperplane arrangement, it re-applies that arrangement independently inside every region already carved out upstream — because ReLU folds space back onto itself, like folding paper before cutting it. Montúfar et al. (2014) proved this composition makes the region count grow exponentially in depth \(L\), not merely additively. Telgarsky (2016) sharpened this: certain "sawtooth" functions need \(2^{\Omega(L)}\) neurons in a shallow network but only \(O(L)\) neurons total in a deep one.

⚠️ Design decision

Why measure expressiveness via linear regions / VC-dimension instead of raw parameter count? Different weight settings (e.g. permuted neurons) can realize the identical function, so parameter count over-counts. Region-counting and VC-dimension are function-space measures — what actually matters for capacity.

3
Why It Works: VC Dimension & The Generalization Gap
▼

The VC dimension of a hypothesis class is the size of the largest point set it can "shatter" — realize every one of the \(2^n\) possible binary labelings of. For a ReLU network with \(W\) weights and depth \(L\), Bartlett, Harvey, Liaw & Mehrabian (2019) proved the near-tight bound:

$$\text{VCdim} = \Theta\!\left(WL\log(W/L)\right)$$

Classical PAC theory then bounds the generalization gap by a term that grows with VC-dimension and shrinks with more training data \(n\):

$$R(h) \le \hat{R}(h) + O\!\left(\sqrt{\tfrac{\text{VCdim}\cdot\log(n/\text{VCdim}) + \log(1/\delta)}{n}}\right)$$
⚠️ Common misconception

"A network's VC-dimension vastly exceeding its training-set size means it must catastrophically overfit." In practice this classical bound becomes vacuous for overparameterized deep nets, yet they generalize well anyway. Better explanations: norm/margin-based Rademacher bounds that scale with weight norms (not raw parameter count), the implicit bias of SGD toward flat/max-margin solutions, and double descent — test error can fall again past the interpolation threshold.

Key Takeaways
▼

Capacity ≠ learnability ≠ generalization: an architecture can be able to represent a function without SGD ever finding it, and finding it doesn't guarantee it generalizes. Depth is the exponentially cheaper lever for expressiveness, but costs optimization stability. Real data occupies a low-dimensional manifold, so the number of regions actually exercised is far below the worst-case bound. Use capacity-matching (architecture ↔ task complexity ↔ data volume) plus explicit regularization — not raw size — as your production dial.
