Position Bias & Debiasing in RecSys

Inverse propensity weighting and position-as-a-feature for unbiased learning to rank
Core Technique RecSys Learning to Rank O(n) per query
1
Understanding Position Bias
▼

What is it? When you log user clicks on a ranked list — search results, a recommendation carousel, a news feed — a click is not a clean signal of relevance. Users scan lists top-to-bottom (or left-to-right) and rarely examine everything. An item at rank 1 gets clicked far more than an equally-relevant item buried at rank 8, simply because more eyeballs reach rank 1. This confound between "was it seen" and "was it good" is position bias.

Analogy: Imagine a talent show where judges only watch the first three acts closely and skim the rest. A mediocre act that goes first can get more applause than a brilliant act that goes eighth — not because it's better, but because it was examined more carefully. If you trained a "talent model" purely from applause volume, you'd systematically learn to prefer whoever performs early.

💡 If you remember one thing

Observed click-through rate is a product of examination and relevance: $$P(\text{click}) = P(\text{examine} \mid \text{position}) \cdot P(\text{relevant} \mid \text{item})$$ Debiasing means dividing that product back apart — via inverse propensity weighting (IPW) or by feeding position in as a model feature — so the ranker learns true relevance, not "was it near the top."

2
How Debiasing Works Internally
▼

The Position-Based Propensity Model (PBM)

The standard click model assumes examination depends only on rank \(k\), and relevance depends only on the item \(i\), and clicks require both: \(C=1 \iff E=1 \text{ and } R=1\). The propensity \(p(k) = P(E=1\mid k)\) is typically a sharply decaying function of rank — empirically closer to \(1/k^{\eta}\) than to a straight line, reflecting how aggressively attention drops off after the first few results.

Route 1 — Inverse Propensity Weighting (IPW)

Instead of trusting a raw click, divide it by how likely it was to happen at all: \(\hat r(i) = c / p(k)\). A click at a low-propensity position (rank 8, hard to see) gets a big weight; a click at rank 1 (easy to see) gets weight ≈1. Averaged over many impressions, this recovers an unbiased estimate of relevance — exactly the same logic as inverse-propensity-score weighting in causal inference and off-policy evaluation.

Route 2 — Position as a Feature (PAL)

Alternatively, concatenate position \(k\) as an input feature during training: the model learns \(f(x_i, k)\) instead of \(f(x_i)\). At training time it fits the "examine × relevance" tangle; at serving time, you feed a constant, highly-examined position (e.g. \(k{=}1\)) for every candidate, or marginalize \(k\) out, forcing the model to fall back on relevance features alone. This is cheaper than IPW but requires the position effect to be learnable and separable from item features.

🔑 Key Property

IPW is a statistical correction applied after data collection; position-as-feature is an architectural correction applied during model design. Production unbiased-learning-to-rank (ULTR) systems often combine both: PAL to absorb most of the bias cheaply, IPW to formally certify unbiasedness of the resulting relevance estimates.

3
Why It Works — The Math
▼

Naive CTR Is a Biased Estimator

Let \(c_t \in \{0,1\}\) be the click on the \(t\)-th impression of item \(i\) at rank \(k_t\). The naive click-through estimator is \(\hat r_{\text{naive}}(i) = \frac{1}{|D_i|}\sum_{t \in D_i} c_t\). Taking expectation under the PBM:

$$\mathbb{E}[\hat r_{\text{naive}}(i)] = \mathbb{E}_k[\,p(k)\,]\cdot r_i \;\neq\; r_i \quad \text{unless } p(k)\equiv 1$$

Naive CTR systematically shrinks the apparent relevance of items shown lower in the list — and by different amounts depending on where each item happened to be shown, so it can't even be fixed with a single global rescaling.

IPW Removes the Bias

Reweight every click by the inverse of its propensity: \(\hat r_{\text{IPW}}(i) = \frac{1}{|D_i|}\sum_{t\in D_i} \frac{c_t}{p(k_t)}\). Since \(\mathbb{E}[c_t \mid k_t] = p(k_t)\, r_i\):

$$\mathbb{E}\!\left[\frac{c_t}{p(k_t)}\right] = \mathbb{E}_{k_t}\!\left[\frac{p(k_t)\, r_i}{p(k_t)}\right] = r_i \quad \Longrightarrow \quad \mathbb{E}[\hat r_{\text{IPW}}(i)] = r_i$$

This is exactly the Horvitz–Thompson estimator from survey sampling / causal inference, applied to clicks. It is provably unbiased regardless of how skewed the propensity curve is — as long as \(p(k) > 0\) everywhere an item could appear.

The Price: Variance

$$\operatorname{Var}\!\left[\frac{c_t}{p(k_t)}\right] \approx \frac{r_i\,(1 - p(k_t) r_i)}{p(k_t)}$$

As \(p(k)\to 0\), the weight \(1/p(k)\) explodes, and a single lucky/unlucky click at a rarely-examined position can swing the estimate wildly. This is the classic bias–variance trade-off of importance weighting.

⚠️ Common Pitfall

Deploying raw IPW with tiny estimated propensities (deep positions, sparse logs) can make training less stable than doing nothing. The standard fix is propensity clipping: \(p_{\text{clip}}(k) = \max(p(k), \tau)\) for a floor \(\tau\), trading a small, known bias for a large reduction in variance — the same trick used in off-policy RL and doubly-robust estimators.

5
Key Takeaways
▼

When you need position debiasing:

  • Training a ranker on implicit feedback (clicks, dwell time) rather than explicit relevance judgments
  • The logging policy shows items in different positions across sessions/experiments (needed to even estimate \(p(k)\))
  • Multi-slot surfaces: search results, feeds, carousels, ad slots, autocomplete suggestions
  • You suspect a "rich get richer" feedback loop — top items get more clicks, so the model reinforces keeping them on top

Practical checklist:

  • Estimate \(p(k)\) via randomized result interleaving, RandTop-\(n\) swaps, or a regression-EM click model — never assume a textbook curve
  • Clip or regularize propensities before dividing by them; monitor the effective sample size of the reweighted data
  • Combine IPW (for correctness) with position-as-a-feature (for training stability) in production ULTR pipelines
  • Validate offline gains with interleaving/counterfactual estimators before trusting a debiased ranker in an online A/B test
💡 Hierarchy

Naive CTR (ignores position, biased) ⊂ Position-as-feature (absorbs bias architecturally) ⊂ IPW (removes bias statistically, unbiased but higher variance) ⊂ Clipped / doubly-robust IPW (unbiased-ish, variance-controlled — what's actually shipped).

Code Trace
▼
import numpy as np
# 8 ranked positions, logged impressions + clicks per item
positions = np.arange(1, 9) # k = 1..8
clicks = np.array([550, 230, 125, 116, 55, 220, 53, 28])
impressions = np.full(8, 1000)
# Naive CTR -- confounds examination with relevance
ctr_naive = clicks / impressions
# Estimate examination propensity (e.g. via result randomization)
eta = 0.8
p_hat = (1.0 / positions) ** eta # p_hat[0] = 1.0
# Inverse propensity weighting -- unbiased relevance estimate
r_ipw = ctr_naive / p_hat
# Clip propensities to bound the importance weight 1/p
tau = 0.3
p_clip = np.maximum(p_hat, tau)
r_ipw_clipped = ctr_naive / p_clip # lower variance, small bias
# Re-rank by debiased relevance instead of raw CTR
debiased_rank_order = np.argsort(-r_ipw)
print("naive order:", np.argsort(-ctr_naive))
print("debiased order:", debiased_rank_order)
