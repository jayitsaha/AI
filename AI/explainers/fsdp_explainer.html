FSDP (Fully Sharded Data Parallel)

Sharding parameters, gradients, and optimizer states for massive models
Intermediate Deep Learning Distributed Training O(N) memory, O(N) comms
1
Understanding FSDP
▼

What is it? FSDP (Fully Sharded Data Parallel) is a distributed training strategy that shards a model's parameters, gradients, and optimizer states across multiple GPUs. Unlike traditional Data Parallel (DDP) where each GPU holds a full copy of the model, FSDP allows each GPU to store only a fraction of the model, enabling the training of models far larger than a single GPU's memory capacity.

Analogy: Imagine a huge library (your model) that's too big to fit on one shelf (a single GPU). Instead of making identical copies of the entire library for every person (DDP), FSDP breaks the library into many small sections (shards) and gives each section to a different librarian (GPU). When a librarian needs a book from another section to answer a query (perform a computation), they temporarily borrow it, use it, and then return it, ensuring no single librarian needs to store the entire library at once.

💡 If you remember one thing

FSDP achieves memory efficiency by ensuring that each GPU only ever stores a single shard of the model's parameters, gradients, and optimizer states. During computation, required parameter shards are dynamically gathered, used, and then freed, making it possible to scale to models with trillions of parameters.

2
How FSDP Works Internally
▼

The Memory Bottleneck

Training large neural networks is often limited by GPU memory. For a typical FP32 model, memory usage can be approximated as:

  • Parameters (P): \(4 \times \text{num_params}\) bytes
  • Gradients (G): \(4 \times \text{num_params}\) bytes
  • Optimizer States (O): For AdamW, this is typically \(2 \times 4 \times \text{num_params}\) bytes (for first and second moments), totaling \(8 \times \text{num_params}\) bytes.
  • Activations: Can be significant, but are handled by techniques like gradient checkpointing, orthogonal to FSDP's core.

Summing these, a single GPU can require up to \(16 \times \text{num_params}\) bytes just for model states, plus activations. This quickly exceeds available memory for models with billions of parameters.

The FSDP Solution: Shard Everything

FSDP addresses this by sharding (dividing) the model's parameters, gradients, and optimizer states across \(N\) GPUs. Each GPU \(i\) is responsible for storing only a contiguous shard \(\Theta_i\) of the global parameters \(\Theta\). The key steps during training are:

  1. Initialization: The full model is initialized on CPU, then sharded. Each GPU receives its \(1/N\) portion of parameters, gradients, and optimizer states.
  2. Forward Pass: When a layer \(L_k\) needs to compute, its full parameters \(\Theta_k\) are temporarily gathered onto all \(N\) GPUs using an `all-gather` collective communication operation. Each GPU then performs its local forward computation using its batch of data and the full \(\Theta_k\). Once the computation for \(L_k\) is done, the gathered \(\Theta_k\) are immediately freed to save memory. This process repeats layer by layer.
  3. Backward Pass: Gradients for each layer \(L_k\) are computed locally. Instead of `all-reducing` the full gradients (as in DDP), FSDP uses a `reduce-scatter` operation. This aggregates the local gradients from all GPUs and then scatters the *sharded* aggregated gradients back to the GPUs responsible for those parameter shards. These sharded gradients are then used to update only the local parameter shard.
  4. Optimizer Step: Each GPU performs its optimizer step using its local shard of parameters, gradients, and optimizer states. No global synchronization is needed for the optimizer step itself.

Design Decision: FSDP vs. ZeRO vs. DDP

FSDP is essentially a highly optimized implementation of the ZeRO-3 stage (Zero Redundancy Optimizer, stage 3) from Microsoft DeepSpeed.

  • DDP (Data Parallel): Each GPU has a full copy of P, G, O. Only gradients are `all-reduce`d. Memory: \(3 \times \text{full_model_memory}\).
  • ZeRO-1 / Optimizer State Sharding: Shards O across GPUs. Each GPU has full P, G. Memory: \(2 \times \text{full_model_memory} + 1/N \times \text{O_memory}\).
  • ZeRO-2 / Gradient Sharding: Shards O and G. Each GPU has full P. Memory: \(1 \times \text{full_model_memory} + 1/N \times (\text{G_memory} + \text{O_memory})\).
  • FSDP (ZeRO-3) / Full Sharding: Shards P, G, O. Each GPU only holds \(1/N\) of each. Memory: \(1/N \times (\text{P_memory} + \text{G_memory} + \text{O_memory}) + \text{temp_buffer_for_one_layer}\). This is the most memory-efficient approach.

🔑 Key Property

FSDP's memory efficiency comes from the fact that at any given moment, no GPU needs to store the entire model. The full model is only ever "reconstructed" temporarily, layer by layer, during the forward and backward passes via `all-gather` operations, and then immediately discarded.

3
Why It Works — The Math
▼

Memory Savings

Let \(P_{\text{total}}\) be the total number of parameters in the model. Assuming FP32 for parameters, gradients, and optimizer states (AdamW):

  • Memory for parameters: \(4 \cdot P_{\text{total}}\) bytes
  • Memory for gradients: \(4 \cdot P_{\text{total}}\) bytes
  • Memory for optimizer states: \(8 \cdot P_{\text{total}}\) bytes (for AdamW's two moments)

Total model state memory on a single GPU without FSDP (e.g., DDP):

$$M_{\text{DDP}} = (4 + 4 + 8) \cdot P_{\text{total}} = 16 \cdot P_{\text{total}} \quad \text{(bytes per GPU)}$$

With FSDP on \(N\) GPUs, each GPU stores only its shard of parameters, gradients, and optimizer states, plus a temporary buffer for one full layer's parameters during computation. Let \(P_{\text{layer max}}\) be the size of the largest layer's parameters.

$$M_{\text{FSDP}} = \frac{1}{N} (4 + 4 + 8) \cdot P_{\text{total}} + 4 \cdot P_{\text{layer max}} = \frac{16 \cdot P_{\text{total}}}{N} + 4 \cdot P_{\text{layer max}} \quad \text{(bytes per GPU)}$$

For very large models where \(P_{\text{total}} \gg P_{\text{layer max}}\), the memory scales as \(O(P_{\text{total}}/N)\), offering nearly \(N\)-fold memory reduction for model states compared to DDP.

Communication Overhead

The memory savings come at the cost of increased communication. For each layer \(L_k\), during the forward pass, an `all-gather` operation is performed to gather its full parameters. During the backward pass, a `reduce-scatter` operation is performed for its gradients. Each of these operations involves moving approximately \(P_k\) (parameters of layer \(k\)) bytes of data per GPU.

Total communication volume for parameters and gradients (per GPU, per iteration, assuming FP32):

$$C_{\text{FSDP}} = \sum_{k=1}^{\text{num_layers}} (4 \cdot P_k \text{ for all-gather} + 4 \cdot P_k \text{ for reduce-scatter}) = 8 \cdot P_{\text{total}} \quad \text{(bytes per GPU)}$$

This is equivalent to \(2 \times\) the total model parameter size being communicated per iteration. For DDP, only gradients are `all-reduce`d, so \(C_{\text{DDP}} = 4 \cdot P_{\text{total}}\). FSDP roughly doubles the communication volume compared to DDP, but this is a trade-off for its superior memory efficiency.

⚠️ Communication vs. Memory Trade-off

FSDP significantly reduces memory footprint, but it increases communication overhead. This means FSDP works best when the computation-to-communication ratio is high (e.g., large models, small batch sizes) and network bandwidth is plentiful. On systems with slow interconnects, the communication cost can outweigh the memory benefits.

Key Takeaways
▼

When to use FSDP:

  • Training very large models: FSDP is essential for models that don't fit on a single GPU (e.g., >10B parameters on 80GB A100s).
  • Memory-bound scenarios: When GPU memory is the primary constraint, FSDP offers significant relief by distributing model states.
  • Models with large individual layers: FSDP efficiently handles models where even single layers might be large, as it only gathers one layer at a time.
  • Good interconnect bandwidth: FSDP's communication overhead is manageable on high-bandwidth networks (e.g., NVLink, InfiniBand).

When NOT to use / be cautious:

  • Small models: For models that easily fit on a single GPU or within DDP's memory limits, FSDP's complexity and communication overhead might not be justified.
  • Communication-bound scenarios: On clusters with slow network interconnects, the increased `all-gather` and `reduce-scatter` traffic can make FSDP slower than DDP or even single-GPU training.
  • Debugging complexity: Distributed training, especially FSDP, adds layers of complexity to debugging and profiling.
💡 Big Picture

FSDP represents the current state-of-the-art for scaling deep learning models to unprecedented sizes. By intelligently sharding all model states and orchestrating on-demand data movement, it effectively turns a cluster of GPUs into a single, massive virtual GPU capable of housing models far beyond any single device's physical limits.

Code Trace (PyTorch FSDP)
▼
import torch
import torch.distributed as dist
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
from torch.distributed.fsdp.wrap import auto_wrap_policy, size_based_auto_wrap_policy
# 1. Initialize distributed environment
dist.init_process_group("nccl")
rank = dist.get_rank()
world_size = dist.get_world_size()
torch.cuda.set_device(rank)
# 2. Define your model (e.g., a simple Transformer block)
class MyModel(torch.nn.Module):
def __init__(self):
super().__init__()
self.layer1 = torch.nn.Linear(1024, 4096)
self.layer2 = torch.nn.Linear(4096, 4096)
self.layer3 = torch.nn.Linear(4096, 1024)
def forward(self, x):
return self.layer3(self.layer2(self.layer1(x)))
# 3. Wrap the model with FSDP
# auto_wrap_policy: defines how layers are nested/sharded
# backward_prefetch: prefetches next layer's params during backward for speed
model = MyModel().to(rank)
my_auto_wrap_policy = auto_wrap_policy(MyModel) # or size_based_auto_wrap_policy
fsdp_model = FSDP(model, auto_wrap_policy=my_auto_wrap_policy,
device_id=rank, backward_prefetch=FSDP.BackwardPrefetch.BACKWARD_PRE)
# 4. Optimizer and training loop
optimizer = torch.optim.AdamW(fsdp_model.parameters(), lr=1e-4)
loss_fn = torch.nn.MSELoss()
for epoch in range(5):
# Create dummy data for demonstration
input_data = torch.randn(2, 1024).to(rank)
target_data = torch.randn(2, 1024).to(rank)
optimizer.zero_grad()
output = fsdp_model(input_data) # Forward pass with all-gather
loss = loss_fn(output, target_data)
loss.backward() # Backward pass with reduce-scatter
optimizer.step() # Optimizer step on sharded states
if rank == 0:
print(f"Epoch {epoch}: Loss = {loss.item():.4f}")
dist.destroy_process_group()
