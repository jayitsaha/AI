ANN Trade-off: Recall vs Latency vs Memory

How index parameters move along the Pareto frontier — and why you can't have all three

Advanced Classical ML · ANN Part III — Classical ML
1
Understanding the Triangle
▾

Approximate Nearest Neighbor (ANN) search finds vectors close to a query — not necessarily the exact nearest neighbor, but close enough, fast enough. The core tension is that every ANN index must balance three resources simultaneously:

  • Recall — fraction of true nearest neighbors returned (0–1, higher is better)
  • Latency — wall-clock time per query (lower is better)
  • Memory — RAM consumed by the index structure (lower is better)
The Impossible Triangle
Improving recall almost always costs either more latency or more memory (or both). No single set of parameters dominates on all three axes — this is a fundamental Pareto trade-off, not an implementation detail.

The real-world analogy: imagine a library with millions of books (vectors). You want the 10 most relevant books to your topic (query). You can:
• Read every book exactly — perfect recall, enormous time (brute-force, O(Nd) latency)
• Use a card index to narrow candidates — fast but you might miss some books (ANN with low recall)
• Keep a giant cross-reference in RAM — faster lookup, but expensive to store

If You Remember One Thing
Higher recall requires visiting more candidates. More candidates costs more time and/or more memory to store the graph/partition structure. Every index parameter (nprobe, efSearch, PQ bits) is a dial that moves you along this Pareto curve.
2
How Index Parameters Move the Frontier
▾

Three major index families dominate production ANN and each has distinct parameters that trade off the triangle differently:

IVF (Inverted File Index) — nprobe

The index partitions \(N\) vectors into \(K\) Voronoi cells via k-means. At query time, the query is assigned to its nearest centroid, then nprobe cells are searched exhaustively.

  • nprobe=1: ~50–70% recall, 1× latency baseline — only the nearest cell searched
  • nprobe=8: ~85–90% recall, ~8× more vectors scanned
  • nprobe=K: 100% recall (degenerates to brute-force)

Latency scales roughly linearly with nprobe (assuming flat storage). Memory is fixed by \(K\) centroids plus the stored vectors.

HNSW (Hierarchical Navigable Small World) — efSearch

HNSW builds a multi-layer proximity graph. At query time a greedy beam search uses a candidate heap of size efSearch. Larger efSearch → more nodes visited → higher recall, higher latency. Memory cost is dominated by the graph edges: each vector stores up to \(M\) neighbors per layer (~\(4M\) bytes per vector for M=16).

  • efSearch=16: recall ≈ 0.85, ~0.3 ms/query (typical 1M dataset, 128-d)
  • efSearch=64: recall ≈ 0.96, ~0.9 ms/query
  • efSearch=256: recall ≈ 0.99, ~3 ms/query

PQ (Product Quantization) — num_bits / m subspaces

PQ compresses vectors from \(d\) float32 dimensions into \(m\) codes of \(b\) bits each. This reduces per-vector memory from \(4d\) bytes to \(m \cdot b/8\) bytes — a 32× compression for \(b=8\) bits.

The PQ Accuracy Cost
Compression is lossy. Fewer bits per subspace → lower precision distances → lower recall. PQ with 4 bits (16 centroids per subspace) typically loses 5–15% recall vs exact distances. PQ is almost always combined with IVF or HNSW as a re-ranking step.
Key Formulas
IVF scan fraction: \(\text{fraction scanned} = \text{nprobe}/K\)
HNSW per-query complexity: \(O(\log N \cdot \text{efSearch})\)
PQ memory per vector: \(m \cdot b / 8\) bytes vs \(4d\) bytes exact
3
The Pareto Frontier — Formal Treatment
▾

Define the Pareto frontier as the set of parameter configurations where no single parameter change improves one metric without harming another. Formally:

$$\mathcal{P} = \{(\text{recall}, \text{QPS}, \text{mem}) : \nexists \text{ config } c' \text{ s.t. } c' \succ c \text{ on all three}\}$$

where \(\succ\) denotes strict Pareto dominance.

For IVF, the expected recall when searching nprobe of \(K\) cells is:

$$\text{Recall@k}(\text{nprobe}) = \mathbb{E}\!\left[\frac{|\text{true top-}k \cap \text{candidates}(\text{nprobe})|}{k}\right]$$

Under the idealized model where each true neighbor falls in the nearest-centroid cell independently with probability \(p\), recall follows a binomial law:

$$\text{Recall}(n) \approx 1 - (1-p_1)^{n} \quad \text{where } p_1 = P(\text{true NN in searched cell})$$

Queries Per Second (QPS) decays inversely with nprobe (linear scan dominates):

$$\text{QPS}(\text{nprobe}) \approx \frac{\text{QPS}_{\text{base}}}{\text{nprobe}} \cdot \frac{K}{\text{nprobe}}$$

For HNSW with beam width efSearch, empirically the recall–latency curve follows:

$$\text{Recall}(\text{ef}) \approx 1 - e^{-\alpha \cdot \text{ef}} \quad \text{(empirical, } \alpha \approx 0.05 \text{ for typical configs)}$$
Common Misconception
"Recall@10 = 0.9 means 90% of queries are perfect." Wrong — it means on average 9 of the 10 returned neighbors are true neighbors. Individual queries may return 10/10 or 5/10. Tail latency (p99) often matters more than mean in production SLAs.

The QPS–Recall Pareto curve is typically plotted on recall (x-axis) vs QPS (y-axis), with each point representing a different parameter value. The curve is concave: the first gains in recall are cheap; the last few percent of recall are exponentially expensive.

Key Takeaways & Decision Guide
▾

When to use which index:

High QPS, moderate recall (0.85–0.95)IVF flat, nprobe=8–16nprobe, K=4096

Massive scale (1B+ vectors), GPU availableIVF-PQ on GPUnprobe, bits tuned by GPU SRAM

The Practitioner's Rule
Start by fixing your recall target (e.g. 0.95). Then sweep the relevant parameter (nprobe or efSearch) to find the lowest-latency config that meets the recall floor. Only apply PQ if memory is a hard constraint — it always costs recall.
  • The Pareto curve is concave: the final 1% of recall is expensive — don't over-optimize
  • Re-ranking with exact distances on the ANN candidate set is a powerful recall recovery trick
  • Measure recall@k with your actual query distribution, not synthetic benchmarks (ANN-Benchmarks)
  • efConstruct (HNSW build param) and nlist (IVF cluster count) set the ceiling on achievable recall — tuning at query time can't exceed the build-time ceiling
