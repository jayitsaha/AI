Understanding Pretraining Data
▼

What is it? Large Language Models (LLMs) learn from vast quantities of text, often trillions of tokens. This "pretraining data" is typically assembled from diverse sources like web crawls (e.g., Common Crawl), digitized books, and open-source code repositories. However, raw data is noisy, low-quality, and highly redundant. A critical pipeline of curation, filtering, and deduplication transforms this raw deluge into a clean, high-quality, and diverse dataset suitable for training.

Analogy: Imagine building a library for an AI. You start by just dumping every book, newspaper, website, and scrap of paper you can find into a giant pile. This pile is full of junk (spam, broken links), multiple copies of the same book, and unreadable scribbles. Before opening the library, you need librarians (curation) to sort out the trash, fix errors, and ensure you only have one copy of each unique, valuable item (deduplication). The AI learns much better from a well-organized, unique collection than from a messy, redundant one.

💡 If you remember one thing

High-quality, diverse, and deduplicated pretraining data is as crucial as model architecture or compute. Deduplication, in particular, prevents overfitting to repeated content, reduces training costs, and improves generalization. Techniques like MinHash and SimHash are essential for identifying near-duplicates at scale.

How the Pipeline Works Internally
▼

The Three Pillars of Data Preparation

Pretraining data pipelines generally involve three major stages:

  1. Data Collection: Sourcing raw text from various origins.
    • Web Crawls: Common Crawl, the largest and most common source, forms the base for datasets like C4, The Pile, RedPajama, and FineWeb.
    • Books: Digitized collections (e.g., Project Gutenberg, Google Books).
    • Code: GitHub, Stack Overflow.
    • Other: Wikipedia, academic papers, news articles, conversational data.
  2. Curation & Filtering: Improving raw data quality.
    • Boilerplate Removal: Removing navigation, ads, footers from web pages.
    • Language Identification: Filtering for target languages.
    • Quality Filtering: Heuristics like minimum/maximum document length, perplexity scores (low perplexity often means high quality), removal of explicit content, filtering by common keywords.
    • Format Conversion: Standardizing diverse formats (HTML, PDF, Markdown, plaintext) into clean text.
  3. Deduplication: Identifying and removing redundant content.
    • Exact Deduplication: Simple hash-based removal of identical documents.
    • Near-Deduplication: Using techniques like MinHash or SimHash to find documents that are highly similar but not identical (e.g., slight rephrasing, minor edits, different headers).

Design Decision: Why Near-Deduplication is Hard but Necessary

The web is full of slightly modified copies: news articles syndicated across many sites, boilerplate headers/footers, forum posts quoting previous messages, or even textbooks with minor revisions. Exact deduplication misses these. Near-deduplication is computationally intensive for petabyte-scale datasets, but it's crucial to prevent models from "memorizing" specific phrases, reduce dataset size, and ensure more diverse exposure to concepts, leading to better generalization.

🔑 Key Property

The goal is not just a large dataset, but a diverse and high-quality one. Each stage of the pipeline (collection, curation, deduplication) addresses a different aspect of this goal, transforming raw, noisy, and redundant data into a valuable training resource.

Why It Works — The Math of Near-Deduplication
▼

Jaccard Similarity and Shingling

To quantify similarity between two documents \(A\) and \(B\), we first represent them as sets of "shingles" — contiguous sequences of \(k\) characters or words. For example, with \(k=3\) words, the sentence "The quick brown fox jumps" becomes the shingles {"The quick brown", "quick brown fox", "brown fox jumps"}. The Jaccard similarity between two sets of shingles \(S_A\) and \(S_B\) is defined as:

$$J(S_A, S_B) = \frac{|S_A \cap S_B|}{|S_A \cup S_B|}$$

This metric ranges from 0 (no common shingles) to 1 (identical sets of shingles). Computing this directly for all pairs of documents is \(O(N^2)\) and intractable for large \(N\).

MinHash: Efficient Jaccard Estimation

MinHash is a technique to estimate Jaccard similarity without explicitly computing set intersections or unions. For each document, we create a "signature" by applying multiple hash functions to its shingles. For a set \(S\) and a permutation \(\pi\) of all possible shingles, define \(h_{\min}^\pi(S) = \min \{ \pi(s) \mid s \in S \}\). The fundamental property of MinHash is:

$$P(h_{\min}^\pi(S_A) = h_{\min}^\pi(S_B)) = J(S_A, S_B)$$

By using \(K\) different hash functions (or \(K\) permutations), we can form a signature vector for each document \(\text{Sig}(S) = [h_1(S), h_2(S), \dots, h_K(S)]\). The similarity between two signature vectors is then estimated by the fraction of components where they agree: \(\text{Approx } J(S_A, S_B) = \frac{\sum_{i=1}^K \mathbb{I}(h_i(S_A) = h_i(S_B))}{K}\).

Locality Sensitive Hashing (LSH): Scaling to Billions

Even comparing MinHash signatures pairwise is too slow. LSH helps find *candidate pairs* efficiently. Signatures are divided into \(r\) bands, each containing \(b\) rows (\(K = r \times b\)). For each band, we hash its \(b\)-length sub-vector. If two documents have identical hash values in *any single band*, they are considered a candidate pair. The probability of two documents with Jaccard similarity \(J\) becoming a candidate pair is:

$$P(\text{candidate}) = 1 - (1 - J^b)^r$$

This function forms an S-curve: documents with high similarity \(J\) have a high probability of being picked as candidates, while those with low \(J\) have a very low probability. This dramatically reduces the number of pairs that require a full similarity check.

⚠️ Common Pitfall

Choosing \(k\) for shingles, and \(r, b\) for LSH, involves trade-offs. A small \(k\) finds very local matches but can be noisy; a large \(k\) is more precise but less sensitive to minor rephrasing. Similarly, \(r\) and \(b\) control the "S-curve" of LSH: more bands (\(r\)) increases recall (finds more true duplicates) but also false positives; larger band size (\(b\)) increases precision (fewer false positives) but can miss some true duplicates. These parameters are tuned on validation sets.

Key Takeaways
▼

Why Pretraining Data Matters:

  • Scale: LLMs demand massive datasets (trillions of tokens).
  • Diversity: Exposure to varied domains (web, books, code) leads to broader capabilities.
  • Quality: Filtering low-quality content prevents the model from learning "garbage in, garbage out."
  • Uniqueness: Deduplication prevents overfitting, memorization, and wasted compute, improving generalization.

Practical Considerations:

  • The raw data is never used directly; it must go through extensive pipelines.
  • Deduplication is crucial for both reducing dataset size and improving model performance.
  • MinHash and LSH are cornerstone techniques for scalable near-deduplication.
  • Parameter tuning (shingle size \(k\), LSH bands \(r\) and rows \(b\)) is empirical and critical for balancing recall and precision.
  • The cost of data preparation (storage, compute for filtering/deduplication) is a significant part of LLM training.
💡 Big Picture

The entire pretraining data pipeline is a massive feat of data engineering. It's a continuous process of collecting, cleaning, and refining, directly impacting the capabilities, robustness, and efficiency of the resulting large language models. The best models are trained on the best data.

Code Trace — Simplified Deduplication
▼
import hashlib
import zlib # for fast non-cryptographic hashing
import random
def get_shingles(text, k=3):
words = text.lower().split()
if len(words) < k: return {text.lower()}
shingles = set()
for i in range(len(words) - k + 1):
shingles.add(" ".join(words[i:i+k]))
return shingles
def minhash_signature(shingles, num_hashes=128):
# Simulate multiple hash functions by using different seeds
signature = []
for seed in range(num_hashes):
min_hash = float('inf')
for shingle in shingles:
# Simple hash function: combine shingle hash with seed
h = zlib.crc32(shingle.encode('utf-8') + str(seed).encode('utf-8'))
if h < min_hash:
min_hash = h
signature.append(min_hash)
return signature
def jaccard_similarity(set1, set2):
intersection = len(set1.intersection(set2))
union = len(set1.union(set2))
return intersection / union if union > 0 else 0
def lsh_candidates(signatures, bands=4, rows_per_band=32):
candidates = set()
for i in range(bands):
band_hashes = {} # {band_hash: [doc_idx1, doc_idx2, ...]}
for doc_idx, sig in enumerate(signatures):
band_sig = tuple(sig[i*rows_per_band : (i+1)*rows_per_band])
band_hash = hashlib.sha1(str(band_sig).encode()).hexdigest()
if band_hash not in band_hashes:
band_hashes[band_hash] = []
band_hashes[band_hash].append(doc_idx)
for doc_list in band_hashes.values():
if len(doc_list) > 1:
for j in range(len(doc_list)):
for k in range(j + 1, len(doc_list)):
candidates.add(tuple(sorted((doc_list[j], doc_list[k]))))
return list(candidates)
# Example Usage:
documents = [
"Large language models are trained on massive datasets.",
"LLMs are trained on huge datasets for language understanding.",
"The quick brown fox jumps over the lazy dog.",
"Large language models are trained on massive datasets for improved performance."
]
all_shingles = [get_shingles(doc) for doc in documents]
signatures = [minhash_signature(s) for s in all_shingles]
candidates = lsh_candidates(signatures)
print("Candidate pairs:", candidates)
duplicates_to_remove = set()
threshold = 0.8 # Example threshold
for d1_idx, d2_idx in candidates:
sim = jaccard_similarity(all_shingles[d1_idx], all_shingles[d2_idx])
if sim >= threshold:
duplicates_to_remove.add(d2_idx) # Remove one of the pair
print(f"Doc {d1_idx} and {d2_idx} are duplicates (sim={sim:.2f})")
final_dataset = [doc for idx, doc in enumerate(documents) if idx not in duplicates_to_remove]
print("Final dataset size:", len(final_dataset))
