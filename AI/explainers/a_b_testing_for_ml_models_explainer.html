1
Understanding A/B Testing for ML
▼

What is it? Offline metrics (accuracy, AUC, NDCG on a held-out set) tell you how a model performs on historical data — they never tell you how real users will actually behave when the model changes what they see. A/B testing (online experimentation) randomly splits live traffic between the current production model ("control", model A) and a candidate ("treatment", model B), then measures a real business metric — conversion, click-through, revenue, retention — to decide, with statistical rigor, whether B is actually better.

Analogy: Think of two chefs cooking for random tables in the same restaurant on the same night. You cannot judge them by a recipe card (offline metric) — you have to watch what diners actually order more of, control for which tables got which chef, and make sure the difference in tips isn't just noise from a couple of big spenders. A/B testing is the disciplined way of watching those tables long enough, and rigorously enough, to trust the verdict.

💡 If you remember one thing

A/B testing turns "which model is better?" into a hypothesis test. Users are randomly (and consistently) assigned to arm A or B via hashing; we observe a conversion rate \(\hat{p}_A\), \(\hat{p}_B\) in each arm; and we only ship model B if the observed lift is large enough, and the sample is large enough, that the difference is very unlikely to be due to chance: $$z = \frac{\hat{p}_B - \hat{p}_A}{\sqrt{\hat{p}(1-\hat{p})\left(\frac{1}{n_A}+\frac{1}{n_B}\right)}}$$

2
How Online Experimentation Works Internally
▼

Step 1 — Deterministic Randomization

Every user (or session) needs a sticky, reproducible assignment: the same user must always land in the same arm for the life of the experiment, otherwise they experience both models and pollute the comparison. This is done by hashing a stable key — typically user_id + experiment_name — into a number, then bucketing it: hash(user_id, exp) % 100 < 50 → control, else → treatment. Hashing (not a stored database flag) means assignment is computed on the fly, is consistent across services, and requires no coordination.

Step 2 — Guardrails Before You Trust the Result

Before reading the headline metric, check Sample Ratio Mismatch (SRM): if you split 50/50 but observe 51.5/48.5 with a huge sample, something is broken (a bug in the assignment logic, bot traffic in one arm, or a logging pipeline dropping events) — and any metric read from a broken split is meaningless, no matter how significant it looks.

Step 3 — Accumulate the Metric, Don't Trust Small N

Each arm's conversion rate \(\hat{p} = x/n\) is a random variable — with few users it swings wildly. As \(n\) grows, the standard error \(\sqrt{\hat{p}(1-\hat{p})/n}\) shrinks like \(1/\sqrt{n}\), so confidence intervals visibly tighten around the true rate. This is exactly the Law of Large Numbers at work, and it is why "day 1 numbers" are almost always misleading.

Step 4 — Test, Don't Eyeball

Once enough data has accumulated, run a formal two-proportion z-test (or its Bayesian analogue) to get a p-value: the probability of seeing a lift this large (or larger) if the two models were truly identical. Only then combine statistical significance with the size of the lift and business cost of shipping to make the ship/no-ship call.

🔑 Key Property

The test is only valid if the sample size was fixed in advance (or a proper sequential procedure is used). Repeatedly checking the p-value and stopping the instant it dips below 0.05 — "peeking" — silently inflates the true false-positive rate far above the nominal 5%, which is the single most common way experimentation programs fool themselves.

3
Why It Works — The Math
▼

The Two-Proportion Z-Test

Model each user's conversion as a Bernoulli trial. Under the null hypothesis \(H_0: p_A = p_B\), the pooled estimate is:

$$\hat{p} = \frac{x_A + x_B}{n_A + n_B}, \qquad SE_{pooled} = \sqrt{\hat{p}(1-\hat{p})\left(\frac{1}{n_A}+\frac{1}{n_B}\right)}$$

The test statistic and two-sided p-value (via the standard normal CDF \(\Phi\)) are:

$$z = \frac{\hat{p}_B - \hat{p}_A}{SE_{pooled}} \qquad p\text{-value} = 2\big(1 - \Phi(|z|)\big)$$

We reject \(H_0\) (declare a statistically significant difference) when \(p\text{-value} < \alpha\), conventionally \(\alpha = 0.05\). The confidence interval for the lift itself uses the unpooled standard error, since we no longer assume the rates are equal:

$$(\hat{p}_B - \hat{p}_A) \pm z_{1-\alpha/2}\sqrt{\frac{\hat{p}_A(1-\hat{p}_A)}{n_A} + \frac{\hat{p}_B(1-\hat{p}_B)}{n_B}}$$

Sample Size and Power

Before running the test, decide how many users you need to reliably detect a minimum lift \(\Delta\) with power \(1-\beta\) (usually 80%) at significance \(\alpha\) (usually 5%):

$$n_{\text{per arm}} = \frac{2\,\bar p(1-\bar p)\,(z_{1-\alpha/2} + z_{1-\beta})^2}{\Delta^2}$$

Smaller \(\Delta\), or a smaller baseline conversion rate, both drive \(n\) up quickly — quadratically in \(1/\Delta\). This is why detecting a 1% relative lift on a 2% baseline conversion rate can require millions of users, while a 30% relative lift on a 20% baseline needs only a few thousand.

The Peeking Problem

The z-test's 5% false-positive guarantee holds for exactly one look at the data. If you check the p-value after every 100 users and stop as soon as it dips under 0.05, you are effectively running many correlated tests — under the null, the running p-value trace is a random walk that crosses any fixed threshold far more often than 5% of the time over repeated looks. Rigorous sequential testing fixes this with an alpha-spending function: the significance threshold at each interim look is tightened (a much smaller effective \(\alpha_k\)) so that the total false-positive probability across all looks still sums to the nominal 5%.

⚠️ Common Pitfall

Statistical significance is not the same as decision-worthiness. A tiny, "significant" lift (e.g. +0.05pp conversion) from a huge sample can be real yet practically worthless once you weigh in latency cost, infra cost, and guardrail metrics (e.g. did the new model hurt user trust or increase support tickets?). Always report the effect size and its confidence interval, not just the p-value.

Key Takeaways
▼

When to trust an A/B test result:

  • Sample Ratio Mismatch check passes (observed split ≈ intended split)
  • Sample size was pre-registered from a power calculation, or a proper sequential method was used
  • The metric moved by an amount that is both statistically and practically significant
  • Guardrail metrics (latency, error rate, unsubscribe rate) did not regress

Common failure modes:

  • Peeking at results daily and stopping the moment p < 0.05 — inflates false positives
  • Non-sticky assignment (a user flips arms between sessions) — dilutes the true effect
  • Novelty/primacy effects — a new model may look better (or worse) only because it's new
  • Underpowered tests on rare events — you conclude "no difference" when you simply couldn't detect one
💡 Hierarchy

Offline eval (fast, cheap, biased) → Fixed-horizon A/B test (rigorous, slow, all-or-nothing) → Sequential / multi-armed-bandit testing (rigorous, adaptive, ships winners faster). Each layer trades simplicity for speed while trying to preserve statistical validity.

Code Trace
▼
import hashlib, math
from scipy.stats import norm
# 1. Deterministic, sticky assignment
def assign(user_id, experiment="model_ab_v1"):
h = hashlib.md5(f"{user_id}-{experiment}".encode()).hexdigest()
bucket = int(h, 16) % 100
return "treatment" if bucket < 50 else "control"
# 2. Sample Ratio Mismatch guardrail (chi-square, 1 df)
def srm_check(n_control, n_treatment, expected_ratio=0.5):
n = n_control + n_treatment
exp_t = n * expected_ratio
chi2 = (n_treatment - exp_t) ** 2 / exp_t + (n_control - (n - exp_t)) ** 2 / (n - exp_t)
return chi2 < 3.841 # p > 0.05 at 1 df -> assignment looks healthy
# 3. Two-proportion z-test
def z_test(xA, nA, xB, nB):
pA, pB = xA / nA, xB / nB
p_pool = (xA + xB) / (nA + nB)
se = math.sqrt(p_pool * (1 - p_pool) * (1 / nA + 1 / nB))
z = (pB - pA) / se
p_value = 2 * (1 - norm.cdf(abs(z)))
return z, p_value
# 4. Sample size for a target lift
def required_n(p_base, delta, alpha=0.05, power=0.8):
z_a, z_b = norm.ppf(1 - alpha / 2), norm.ppf(power)
p_bar = p_base + delta / 2
return 2 * p_bar * (1 - p_bar) * (z_a + z_b) ** 2 / delta ** 2
# 5. Ship decision
z, p = z_test(xA=103, nA=1000, xB=118, nB=1000)
ship = (p < 0.05) and srm_check(1000, 1000)
print(f"z={z:.2f} p={p:.4f} decision={'SHIP' if ship else 'HOLD'}")
