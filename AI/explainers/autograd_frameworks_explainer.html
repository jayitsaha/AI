Autograd: Tape vs Graph

How PyTorch's dynamic tape, TensorFlow's GradientTape/static graph, and JAX's tracing all compute the same gradients
Advanced Deep Learning PyTorch · TensorFlow · JAX O(1) backward passes
1
Understanding Autograd
▼

What is it? Autograd is the machinery that automatically computes derivatives of a model's output with respect to every parameter that produced it, so you never hand-derive calculus for a million-parameter network. It records every math operation you run, then replays that record backward using the chain rule.

Analogy: Imagine baking a cake while someone writes down every step — add flour, mix, bake, ice. If you know how sensitive the final taste is to the icing (the last step), you can walk the recipe backward, multiplying "sensitivities" together, to learn how sensitive the taste is to the flour amount (the first step). That backward walk through the recorded recipe is exactly what autograd does over a tape (PyTorch) or a graph (classic TensorFlow 1).

💡 If you remember one thing

PyTorch rebuilds the computation tape fresh on every forward call ("define-by-run"). Classic TensorFlow 1 built the graph once, symbolically, before any data flowed ("define-then-run"). TensorFlow 2's GradientTape and JAX's tracing both moved toward the dynamic, PyTorch-like model — eager by default, compiled on demand.

2
How It Works Internally
▼

The Dynamic Tape (PyTorch, TF2 eager)

Every Tensor with requires_grad=True carries a hidden grad_fn pointer. When you write u = x * w, PyTorch's dispatcher intercepts the multiply, computes u immediately (eager execution — you can print(u) right away), and attaches a MulBackward0 node to u that remembers "my inputs were x and w, and here is how to compute local gradients." Each subsequent op appends another node, so the tape is literally a byproduct of running ordinary Python.

The Static Graph (TF1)

TF1 instead asked you to declare x = tf.placeholder(...) and build the entire expression symbolically before any real numbers existed. Nothing computes until sess.run(L, feed_dict={...}). The payoff: the whole graph is visible upfront, so the compiler can fuse and reorder operations for peak throughput. The cost: no native if/for on tensor values, and debugging means inspecting a symbolic graph instead of stepping through Python.

Design Decision: Why Save Outputs, Not Inputs?

Autograd engines save whatever is cheapest to reuse for the local derivative. Sigmoid's derivative is z(1-z) — expressible purely in terms of its own output z — so PyTorch's SigmoidBackward0 discards the input v and keeps only z, halving the memory that op needs to hold alive until backward().

🔑 Key Property

A tape/graph node stores exactly three things: a reference to its input tensors (or whatever subset is needed for the local derivative), the operation type, and a rule for computing local gradients. Backward propagation is just: multiply local gradients together along every recorded edge, chain-rule style.

3
Why It Works — The Math
▼

Reverse-Mode Automatic Differentiation

For a composition \(L = f_n(f_{n-1}(\dots f_1(x)\dots))\), the multivariate chain rule gives the gradient of the final scalar output with respect to any intermediate variable \(v_i\) as a vector-Jacobian product:

$$\bar{v}_i = \frac{\partial L}{\partial v_i} = \frac{\partial L}{\partial v_{i+1}} \cdot \frac{\partial v_{i+1}}{\partial v_i} = \bar{v}_{i+1} \, J_i$$

where \(J_i = \partial v_{i+1} / \partial v_i\) is the local Jacobian of step \(i\), and \(\bar{v}_{i+1}\) is the already-computed upstream gradient ("adjoint"). Reverse mode starts from \(\bar{L} = \partial L/\partial L = 1\) and walks the tape backward, left-multiplying by each local Jacobian in turn — never materializing a full Jacobian matrix, only ever a vector-Jacobian product.

Why Reverse Mode, Not Forward Mode?

Forward-mode AD propagates a directional derivative forward alongside the computation, and needs one full pass per input to get the gradient of a scalar loss with respect to every parameter — cost \(O(n)\) for \(n\) inputs. Reverse mode instead propagates one adjoint backward from the single scalar output, obtaining gradients for all \(n\) inputs in a single backward pass — cost \(O(1)\) relative to the number of parameters (same order as the forward pass itself). Since deep nets have millions of parameters and one scalar loss, reverse mode is the only tractable choice.

$$\text{Forward-mode: } O(n_{\text{inputs}}) \text{ passes} \qquad \text{Reverse-mode: } O(1) \text{ pass (for 1 output)}$$
📐 The Chain Rule at Each Tape Node

Every grad_fn implements one function: given the upstream gradient \(\bar{v}_{i+1}\), return \(\bar{v}_i = \bar{v}_{i+1} \cdot J_i\) for each input. For elementwise ops like sigmoid, \(J_i\) is diagonal so this is just elementwise multiply; for matmul, \(J_i\) application becomes another matmul.

⚠️ Common Misconception

"Autograd computes the Jacobian." It almost never does — that would be far too large and slow. It only ever computes vector-Jacobian products (reverse mode) or Jacobian-vector products (forward mode, used by torch.func.jvp and JAX's jvp). The full Jacobian is only formed if you explicitly request it (e.g. torch.autograd.functional.jacobian).

5
Key Takeaways
▼

When eager/dynamic (PyTorch default, TF2 default) wins:

  • Research & rapid iteration — native Python debugging with pdb/print statements
  • Data-dependent control flow — recursive trees, variable-length loops, early exits expressed as plain if/for
  • Prototyping novel architectures where the graph shape isn't known in advance

When a compiled graph (TF1-style, torch.compile, JAX jit) wins:

  • Production serving — fixed architecture, need max throughput/latency
  • Repeated calls to the same function shape — compile once, amortize across millions of calls
  • Multi-device / XLA-fused execution (TPUs particularly reward graph compilation)
💡 The Convergence

Modern frameworks give you both: PyTorch's dynamic tape is the default, and torch.compile traces it into a graph for speed. JAX defaults to functional tracing (closer to graph-mode) but stays eager until you wrap a function in jit. Pick eager for development, compile for the final training/serving loop.

Code Trace
▼
import torch
# Leaf tensors — autograd will track gradients for these
x = torch.tensor(2.0, requires_grad=True)
w = torch.tensor(0.5, requires_grad=True)
b = torch.tensor(-1.0, requires_grad=True)
target = torch.tensor(1.0)
# Forward pass — each op is EXECUTED immediately (eager)
# AND appended to the tape via a grad_fn on the output
u = x * w # u.grad_fn = MulBackward0
v = u + b # v.grad_fn = AddBackward0
z = torch.sigmoid(v) # z.grad_fn = SigmoidBackward0 (saves z, not v)
L = (z - target) ** 2 # L.grad_fn = PowBackward0
# Backward pass — walk the tape in reverse, seed dL/dL = 1.0
L.backward()
print(x.grad) # dL/dx = -0.125
print(w.grad) # dL/dw = -0.5
print(b.grad) # dL/db = -0.25
# --- Equivalent TF2 (GradientTape records explicitly) ---
with tf.GradientTape() as tape:
z = tf.sigmoid(x * w + b)
L = (z - target) ** 2
grads = tape.gradient(L, [x, w, b])
# --- Equivalent JAX (functional tracing, no tape at all) ---
loss_fn = lambda x, w, b: (jax.nn.sigmoid(x*w+b) - target)**2
dx, dw, db = jax.grad(loss_fn, argnums=(0,1,2))(x, w, b)
