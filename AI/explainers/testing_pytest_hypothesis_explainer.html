1
Understanding the Testing Pyramid
▼

What is this? Testing is how we prove code does what it claims. There are three layers: unit tests check one function in isolation (fast, many); integration tests check that multiple components work together (slower, fewer); property-based tests don't use fixed examples — instead they generate thousands of random inputs and verify an invariant always holds.

Analogy: Testing a calculator. A unit test says "3 + 4 must equal 7." An integration test says "the full calculation pipeline — including UI, parsing, and math engine — gives the right answer for a sequence of operations." Property-based testing says "for any two numbers a and b, addition must be commutative: add(a,b) == add(b,a)." Instead of writing 100 examples by hand, Hypothesis generates them automatically — and if one fails, it shrinks the input to the smallest possible counterexample.

💡 If you remember one thing

pytest is Python's standard test runner — simple assert statements, fixtures for setup/teardown, @pytest.mark.parametrize for data-driven tests. Hypothesis (property-based testing) is the secret weapon: instead of you writing examples, it generates random ones, finds a failure, and automatically shrinks it to the minimal breaking case.

2
How pytest and Hypothesis Work Internally
▼

pytest: Discovery → Collection → Execution

When you run pytest, it walks your directory tree looking for files matching test_*.py or *_test.py, then collects all functions starting with test_. Each test is run in isolation. If an assert statement fails, pytest captures the expression AST and rewrites it to show exactly what went wrong (e.g., assert result == 42 → "assert 41 == 42"). This is done via bytecode manipulation during import.

Fixtures are dependency-injected setup functions. A fixture marked @pytest.fixture is called automatically when a test function requests it by name in its parameter list. Scope controls lifetime: function (default — recreated per test), class, module, or session. Fixtures can yield (for teardown), and they can depend on other fixtures, forming a DAG.

Parametrize lets one test function run against a list of inputs: @pytest.mark.parametrize("x,y,expected", [(1,2,3), (0,0,0), (-1,1,0)]). Internally, pytest generates one test item per parameter tuple and reports them individually.

Hypothesis: Generate → Execute → Falsify → Shrink

Hypothesis uses strategies to describe the shape of inputs (e.g., st.integers(), st.lists(st.floats())). The engine maintains a database of previously found failures and uses a combination of random sampling and coverage-guided exploration. When a test passes for 100 examples (the default), Hypothesis considers it passing. When a failure is found, shrinking begins: Hypothesis tries systematically smaller/simpler variants of the failing input, binary-searching for the minimal counterexample. This is the key insight — debugging a 500-element list is hard; debugging the 2-element list that also fails is easy.

🔑 Key Property

Hypothesis's shrinking is automatic and structured: it knows the shape of its strategies, so it shrinks integers toward 0, strings toward empty, lists by removing elements, etc. After shrinking, the failure is deterministic and reproducible — the same minimal example is saved to Hypothesis's local database and will be replayed on every future test run.

Integration Tests

Integration tests call real subsystems — databases, file systems, HTTP endpoints. They're slower and more brittle than unit tests, but catch interface mismatches that mocks miss. Best practice: use pytest.fixture with scope="session" to spin up a test database once, and use transaction rollbacks or test containers to isolate state between tests.

⚠️ Common Mistake

Testing with only fixed examples gives false confidence. If you test sort([3,1,2]) and sort([1]), you may never discover that your sort crashes on empty lists or lists with duplicates. Property-based testing finds these automatically.

3
Why It Works — Invariants and Coverage
▼

Properties as Universal Quantifiers

A property-based test is a statement of the form \(\forall x \in D,\ P(x)\) — "for all inputs in the domain, property P holds." Unit tests check a finite set of \(x\); property-based tests sample from \(D\) and attempt to falsify \(P\).

Common invariant patterns in ML code:

  • Round-trip: \(\text{decode}(\text{encode}(x)) = x\) — serialization/deserialization
  • Commutativity: \(f(a, b) = f(b, a)\) — e.g., set union, symmetric distances
  • Monotonicity: \(a \leq b \Rightarrow f(a) \leq f(b)\) — e.g., loss decreasing with more data
  • Idempotency: \(f(f(x)) = f(x)\) — e.g., applying a mask twice
  • Output shape: for any input tensor of shape \((B, C, H, W)\), output shape is \((B, K)\)

Shrinking: Finding the Minimal Counterexample

When Hypothesis finds a failing input \(x_0\), it applies a shrinker that generates candidate inputs \(x' \prec x_0\) (smaller/simpler by some ordering). It greedily accepts any \(x'\) that still fails the property, iterating until no simpler failure exists. This is equivalent to finding a local minimum in the "complexity" ordering of the input space.

$$x^* = \underset{x' \prec x_0,\ \neg P(x')}{\operatorname{argmin}}\; \text{complexity}(x')$$

The ordering \(\prec\) is strategy-specific: for integers, \(|a| < |b|\); for lists, shorter is simpler; for strings, shorter with smaller character codes.

Coverage and the Bug-Finding Rate

If bugs occur with probability \(p\) per random sample, after \(n\) trials the probability of missing all bugs is \((1-p)^n\). With \(n = 100\) examples and \(p = 0.01\), you catch the bug with probability \(1 - 0.99^{100} \approx 63\%\). Hypothesis boosts effective \(p\) using coverage instrumentation (via bytecode tracing) to preferentially explore branches that haven't been hit.

$$P(\text{find bug in } n \text{ trials}) = 1 - (1-p)^n$$
📐 Key Formula

The expected number of trials to first find a bug with per-trial probability \(p\) is \(\mathbb{E}[T] = 1/p\) (geometric distribution). Hypothesis's coverage guidance effectively increases \(p\) by biasing sampling toward unexplored code paths.

Key Takeaways & When to Use What
▼

The Testing Pyramid: Many fast unit tests at the base, fewer integration tests in the middle, few (if any) slow E2E tests at the top. Property-based tests live at the unit/integration boundary — cheap to run, but broader coverage than fixed examples.

TypeSpeedScopeBest ForTool
Unit⚡ <1ms eachOne functionPure logic, transforms, mathpytest
Integration🐢 100ms–10sMultiple componentsDB queries, API calls, pipelinespytest + fixtures
Property-based⚡ fast (100 samples)One function, many inputsInvariants, edge cases, regressionsHypothesis
E2E / System🐢🐢 >1sFull systemUser journeys, deployment smoke testspytest + real infra

When to use property-based testing: sorting/search algorithms, serialization round-trips, mathematical invariants (commutativity, associativity), data shape contracts in ML pipelines (output shape, value ranges).

When NOT to use: tests that require exact expected outputs (use unit tests), tests that depend on external state (use integration tests with real fixtures), UI tests (wrong layer).

💡 ML-Specific Advice

Property-based tests shine for ML preprocessing pipelines: "for any batch of images, normalize() outputs values in [-1, 1]", "for any token sequence length ≤ 512, tokenizer output length ≤ 512", "encode then decode is identity for all valid labels". These catch silent data corruption that fixed examples miss.

Code Trace — From Unit to Property-Based
▼
import pytest
from hypothesis import given, settings
from hypothesis import strategies as st
# ── UNIT TEST (fixed examples) ─────────────────────
def sort_unique(lst): # deliberately buggy: drops duplicates
return sorted(set(lst)) # bug: set() removes duplicates!
def test_sort_basic():
assert sort_unique([3, 1, 2]) == [1, 2, 3] # PASSES
assert sort_unique([1]) == [1] # PASSES
# Bug not caught — no duplicates in examples!
# ── PARAMETRIZE (data-driven) ──────────────────────
@pytest.mark.parametrize("lst,expected", [
([3, 1, 2], [1, 2, 3]),
([], []),
([-1, 0, 1], [-1, 0, 1]),
])
def test_sort_parametrize(lst, expected):
assert sort_unique(lst) == expected # Still misses duplicates
# ── FIXTURE (setup/teardown) ───────────────────────
@pytest.fixture
def sample_data():
data = [3, 1, 4, 1, 5, 9] # data with duplicates
yield data
# teardown happens here (after yield)
def test_sort_with_fixture(sample_data):
result = sort_unique(sample_data)
assert len(result) == len(sample_data) # FAILS! 6 != 5
# ── PROPERTY-BASED (Hypothesis) ────────────────────
@given(st.lists(st.integers(-100, 100)))
def test_sort_length_preserved(lst):
"""Property: sort must not change list length."""
result = sort_unique(lst)
assert len(result) == len(lst) # Hypothesis finds [0, 0] fails!
# Hypothesis shrinks to minimal: [0, 0] (simplest duplicate)
@given(st.lists(st.integers()))
def test_sort_sorted_property(lst):
"""Property: output must be sorted."""
result = sort_unique(lst)
assert result == sorted(result) # This one actually PASSES
