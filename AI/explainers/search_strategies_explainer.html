Understanding Neural Architecture Search (NAS)
▼

What is it? Neural Architecture Search (NAS) is the process of automating the design of neural network architectures. Instead of human experts hand-crafting networks (like ResNet, Inception, Transformer), NAS algorithms explore a vast "search space" of possible architectures to find one that performs well on a given task, often outperforming human designs.

Analogy: Imagine you're trying to build the best possible Lego castle, but you have millions of unique Lego bricks and no instructions. Manually trying combinations is impossible. NAS is like hiring an army of robots: some randomly try combinations, some learn from past successes, some build a "master castle" that contains all possible designs, and some use gradient descent to smoothly morph one design into another until they find the best one. The goal is to find the optimal structure (sequence of operations, connections) for your task.

💡 If you remember one thing

NAS aims to automate the most time-consuming part of deep learning research: architecture design. It replaces manual trial-and-error with systematic search, often leading to better models but at a significantly higher computational cost than traditional hyperparameter tuning.

2
How Different Strategies Work
▼

The Search Space: A Graph of Operations

Most NAS methods define a search space as a Directed Acyclic Graph (DAG) where nodes represent feature maps and edges represent operations (e.g., convolution, pooling, skip connection). The task is to find the best sequence of operations and connections (a path through this graph) that forms a high-performing "cell" or full network.

1. Reinforcement Learning (RL-based NAS)

Pioneered by Zoph and Le (2017) with NASNet. An RNN "controller" acts as an agent, taking actions to construct an architecture (e.g., choosing operations and connections for a cell). After constructing an architecture, a "child model" is trained from scratch and evaluated. The controller receives a reward signal (e.g., validation accuracy) and updates its policy using policy gradient methods (like REINFORCE) to favor actions that led to better architectures. This is a discrete, iterative search.

2. Evolutionary Algorithms (EA-based NAS)

Inspired by biological evolution. A "population" of candidate architectures is maintained. In each generation, architectures are evaluated, and the best ones are selected to be "parents." New architectures ("offspring") are created through "mutation" (e.g., randomly changing an operation) and "crossover" (combining parts of two parent architectures). This process repeats, gradually evolving better architectures. Also a discrete, iterative search.

3. Differentiable Architecture Search (DARTS)

A key breakthrough, making NAS much faster. Instead of discrete choices, DARTS relaxes the categorical choice of operations into a continuous probability distribution. For each edge in the search graph, a "mixed operation" is defined as a weighted sum of all candidate operations. These weights are learned through gradient descent, alongside the network weights. After training, the final architecture is derived by taking the argmax of these architectural weights. This transforms the discrete search into a continuous optimization problem.

4. One-Shot NAS (Supernet & Weight Sharing)

Aims to reduce search cost by training only once. A "supernet" is constructed that encompasses all possible architectures in the search space. All candidate architectures are then viewed as "sub-networks" within this supernet, sharing weights. The supernet is trained once. After training, various sub-networks can be "extracted" and evaluated without re-training, simply by activating different paths through the supernet's shared weights. This dramatically reduces evaluation cost, as the weights are already "learned."

🔑 Key Trade-off

The core trade-off in NAS is between search cost (how many GPU-days to find an architecture) and search space expressiveness (how complex/diverse are the architectures it can find). Discrete methods (RL, EA) are computationally expensive but can explore highly complex spaces. Continuous/One-shot methods are much faster but may be constrained by the relaxation or supernet design.

Why It Works — The Underlying Math
▼

Reinforcement Learning (REINFORCE)

The controller RNN's policy \(\pi(a_t \mid h_t; \theta)\) generates a sequence of actions \(a_1, \dots, a_m\) that define an architecture \(A\). This architecture is trained to convergence, yielding a reward \(R(A)\) (e.g., validation accuracy). The goal is to maximize the expected reward:

$$J(\theta) = \mathbb{E}_{P(A;\theta)}[R(A)]$$

The policy gradient is estimated using REINFORCE:

$$\nabla_\theta J(\theta) = \sum_{t=1}^m \mathbb{E}_{P(A;\theta)}\left[ R(A) \nabla_\theta \log \pi(a_t \mid h_t; \theta) \right]$$

In practice, this is approximated by sampling an architecture \(A_k\), training it, getting \(R(A_k)\), and updating \(\theta\) with \(R(A_k) \sum_{t=1}^m \nabla_\theta \log \pi(a_t \mid h_t; \theta)\). Baselines are often used to reduce variance.

Differentiable Architecture Search (DARTS)

For each edge \((i,j)\) in the search space, DARTS defines a mixed operation \(o_{(i,j)}\) as a softmax-weighted sum of candidate operations \(\mathcal{O} = \{o_1, \dots, o_k\}\):

$$\bar{o}_{(i,j)}(x) = \sum_{o \in \mathcal{O}} \frac{\exp(\alpha_{o}^{(i,j)})}{\sum_{o' \in \mathcal{O}} \exp(\alpha_{o'}^{(i,j)})} o(x)$$

Here, \(\alpha^{(i,j)}\) are continuous architectural weights. DARTS then performs bi-level optimization:

  • Optimize network weights \(w\) to minimize training loss \(L_{train}(w, \alpha)\).
  • Optimize architectural weights \(\alpha\) to minimize validation loss \(L_{val}(w, \alpha)\).

This is typically done by alternating steps of gradient descent on \(w\) and \(\alpha\). After training, the discrete architecture is obtained by selecting the operation with the highest \(\alpha\) for each mixed operation.

⚠️ Common Pitfall

The computational cost of NAS is immense. Even "fast" methods like DARTS can require hundreds of GPU hours, and RL/EA-based methods can demand thousands. This makes NAS inaccessible without significant compute resources. Furthermore, architectures found on proxy tasks (e.g., smaller datasets, fewer epochs) may not transfer well to the full task, adding to the complexity.

Key Takeaways & Best Practices
▼

When to choose a strategy:

  • RL/Evolutionary: When the search space is highly complex, discrete, and you have ample compute. Can find highly novel architectures. Best for exploring uncharted territory.
  • Differentiable (DARTS): When compute is a concern and you need faster search. Works best with well-defined, local search spaces (e.g., cell-based search). Can sometimes find degenerate architectures if not regularized.
  • One-Shot (Supernet): When you need extremely fast evaluation of many architectures after an initial heavy training phase. Excellent for hardware-aware NAS or finding many sub-networks from a single training run.

General best practices:

  • Proxy Tasks: Often, NAS is run on smaller datasets (e.g., CIFAR-10 instead of ImageNet) or for fewer epochs to reduce search time. The chosen architecture is then transferred and trained on the full task.
  • Search Space Design: The quality of discovered architectures is highly dependent on the design of the search space. A poorly designed space limits the potential.
  • Cost vs. Performance: Always consider the trade-off. A small performance gain might not justify thousands of GPU hours.
💡 The Future of NAS

Modern NAS research increasingly focuses on reducing search cost further, making it more accessible, and integrating it with broader AutoML pipelines. Hybrid methods combining elements of different strategies are also emerging to leverage their respective strengths.

import torch.nn as nn
import torch.optim as optim
# Define candidate operations
OPS = {
'none': lambda C_in, C_out, stride: Zero(stride),
'avg_pool_3x3': lambda C_in, C_out, stride: nn.AvgPool2d(3, stride=stride, padding=1, count_include_pad=False),
'max_pool_3x3': lambda C_in, C_out, stride: nn.MaxPool2d(3, stride=stride, padding=1),
'skip_connect': lambda C_in, C_out, stride: Identity() if stride == 1 else FactorizedReduce(C_in, C_out),
'conv_3x3': lambda C_in, C_out, stride: ReLUConvBN(C_in, C_out, 3, stride, 1),
'conv_5x5': lambda C_in, C_out, stride: ReLUConvBN(C_in, C_out, 5, stride, 2),
}
class MixedOp(nn.Module):
def __init__(self, C_in, C_out, stride):
super(MixedOp, self).__init__()
self._ops = nn.ModuleList()
for primitive in OPS.keys():
op = OPS[primitive](C_in, C_out, stride)
self._ops.append(op)
def forward(self, x, weights):
# weights are softmax over alpha_ops for this edge
return sum(w * op(x) for w, op in zip(weights, self._ops))
class Cell(nn.Module):
def __init__(self, steps, C_prev_prev, C_prev, C):
super(Cell, self).__init__()
self.steps = steps
self.preprocess0 = FactorizedReduce(C_prev_prev, C) # Example preproc
self.preprocess1 = ReLUConvBN(C_prev, C, 1, 1, 0)
self._ops = nn.ModuleList()
# For each intermediate node, consider connections from all previous nodes
for i in range(self.steps):
for j in range(i + 2): # Connects from prev_prev, prev, and all intermediate nodes
stride = 1 # Simplified, typically handled by reduction cells
op = MixedOp(C, C, stride) # All ops for this edge
self._ops.append(op)
# Architectural weights (alpha) for each edge, for each operation
num_edges = sum(1 for i in range(self.steps) for j in range(i + 2))
self.arch_parameters = nn.Parameter(1e-3 * torch.randn(num_edges, len(OPS)))
def forward(self, s0, s1):
s0 = self.preprocess0(s0); s1 = self.preprocess1(s1)
states = [s0, s1]
