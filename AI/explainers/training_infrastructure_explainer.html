1
Understanding Training Parallelism
▼

What is it? As deep learning models grow, a single GPU often can't hold all the parameters, optimizer states, and gradients required for training. Even if it could, the computation might be too slow. Training parallelism refers to strategies for distributing the model, data, or computation across multiple GPUs (or even multiple machines) to overcome these memory and speed bottlenecks, enabling the training of truly massive models like large language models (LLMs).

Analogy: Imagine you have to bake a giant cake (train a huge model).

  • Single oven: You might not have a big enough oven (GPU memory), or it takes too long.
  • Multiple ovens, same recipe, different batter (Data Parallelism): You give the full recipe to several bakers, each gets a portion of the batter. They all bake their part, then combine their feedback (gradients) to improve the main recipe.
  • Assembly line (Pipeline Parallelism): One baker makes the base, passes it to the next for frosting, who passes it to another for decorations. The cake moves through stages.
  • Giant cake, split ingredients (Tensor Parallelism): The cake is so big, even one ingredient (e.g., a massive layer of frosting) needs multiple bakers to apply their portion simultaneously.

💡 If you remember one thing

The core challenge is that model parameters, gradients, and optimizer states (e.g., for Adam, these are two additional tensors per parameter) can consume hundreds of GBs. Parallelism schemes primarily aim to reduce the memory footprint on each device and/or speed up computation by distributing work across many devices, often by trading off communication bandwidth for memory and compute gains.

2
How Different Strategies Work
▼

1. Data Parallelism (DP)

This is the most common and easiest to implement. The full model is replicated on each GPU. Each GPU receives a different shard of the input data batch. During the forward and backward passes, each GPU computes its own gradients. Then, all gradients are averaged across GPUs (e.g., using `all-reduce`) to ensure all model replicas update their weights identically. This is effective for scaling batch size but doesn't help if the model itself is too large for a single GPU.

Memory Footprint: \(P_{\text{total}} + G_{\text{total}} + O_{\text{total}}\) per GPU (full model on each).

2. Pipeline Parallelism (PP)

When the model's layers are too numerous to fit on a single GPU, pipeline parallelism splits the model vertically. Different GPUs are responsible for different sequential layers of the network. A batch of data is split into smaller "micro-batches" that flow through the pipeline. While one GPU is processing a micro-batch for a later layer, an earlier GPU can start processing a new micro-batch for an earlier layer, creating a pipeline. This reduces the per-GPU memory footprint for model parameters.

Memory Footprint: \((P_{\text{total}} + G_{\text{total}} + O_{\text{total}}) / N_{\text{pipeline}}\) (approximately) per GPU.

3. Tensor Parallelism (TP) / Model Parallelism (MP) within a layer

For extremely large layers (e.g., the gigantic weight matrices in LLMs), even a single layer's parameters might not fit on one GPU. Tensor parallelism splits the tensors (e.g., weight matrices) of a single layer across multiple GPUs. For example, a matrix multiplication \(Y = XW\) can be split by columns of \(W\) (for \(Y = [Y_1, Y_2]\) where \(Y_1 = XW_1\), \(Y_2 = XW_2\)) or rows of \(W\). This requires fast inter-GPU communication within each layer operation.

Memory Footprint: \((P_{\text{layer}} + G_{\text{layer}} + O_{\text{layer}}) / N_{\text{tensor}}\) (for the split layer) per GPU.

4. 3D Parallelism (Megatron-LM)

This combines all three: Data Parallelism, Pipeline Parallelism, and Tensor Parallelism. For example, you might have a cluster of 8 GPUs. You could use 2-way Tensor Parallelism (split layers over 2 GPUs), 2-way Pipeline Parallelism (split model over 2 GPUs), and 2-way Data Parallelism (replicate the DP group over 2 sets of TP+PP groups). This is a highly complex setup but necessary for models with trillions of parameters.

5. Memory-centric Sharding (ZeRO, FSDP)

These techniques focus on reducing memory usage by sharding (partitioning) the model's components (optimizer states, gradients, and even parameters) across GPUs, rather than replicating them.

  • ZeRO (Zero Redundancy Optimizer, DeepSpeed): Progressively shards optimizer states (ZeRO-1), then gradients (ZeRO-2), and finally model parameters (ZeRO-3) across data-parallel GPUs. This removes redundancy and scales memory linearly with the number of GPUs.
  • FSDP (Fully Sharded Data Parallelism, PyTorch): A PyTorch-native implementation similar to ZeRO-3. It shards model parameters, gradients, and optimizer states across data-parallel GPUs. Parameters are gathered on demand for forward/backward passes and then discarded, minimizing memory.

🔑 Key Trade-offs

Each parallelism strategy involves trade-offs. Data parallelism is easy but memory-inefficient. Pipeline parallelism reduces model memory but introduces "pipeline bubbles" (idle time). Tensor parallelism requires very fast intra-layer communication. Sharding techniques are highly memory-efficient but add complexity and communication overheads for parameter gathering/sharding.

3
Why It Works — The Scaling Laws
▼

Memory Breakdown for Training

The total memory consumed during training is dominated by three main components for each parameter \(\theta_i\):

  1. Model Parameters (\(P\)): The weights themselves. If stored in FP32, this is 4 bytes/parameter.
  2. Gradients (\(G\)): Computed for each parameter during backpropagation. Also 4 bytes/parameter (FP32).
  3. Optimizer States (\(O\)): For adaptive optimizers like Adam, this includes momentum (\(m\)) and variance (\(v\)) estimates for each parameter. Each is 4 bytes/parameter (FP32). So, 8 bytes/parameter for Adam.

Thus, for a model with \(N\) parameters, a single GPU needs \(N \times (4 + 4 + 8) = 16N\) bytes for FP32 Adam training. For a 10B parameter model, that's 160 GB — far exceeding typical GPU memory (e.g., 80 GB for an A100).

Data Parallelism (DP) Scaling

With \(N_D\) GPUs for data parallelism, each GPU holds a full copy of the model parameters, gradients, and optimizer states. The batch size \(B\) is split into \(B/N_D\) per GPU. Communication involves all-reducing gradients:

$$\text{Memory per GPU (DP)} = 16N \text{ bytes}$$
$$\text{Communication (DP)} = \mathcal{O}(N) \text{ per step (all-reduce gradients)}$$

This does not reduce per-GPU memory for the model components, only allows larger effective batch sizes and faster computation if the model fits.

ZeRO / FSDP Scaling

These techniques shard the memory components across \(N_D\) data-parallel GPUs.

  • ZeRO-1 (Optimizer States Sharding): Each GPU is responsible for \(N/N_D\) optimizer states. $$\text{Memory per GPU (ZeRO-1)} = N \times (4 + 4 + 8/N_D) \text{ bytes}$$
  • ZeRO-2 (Optimizer States + Gradients Sharding): Each GPU is responsible for \(N/N_D\) optimizer states AND gradients. $$\text{Memory per GPU (ZeRO-2)} = N \times (4 + 4/N_D + 8/N_D) \text{ bytes}$$
  • ZeRO-3 / FSDP (Optimizer States + Gradients + Parameters Sharding): Each GPU is responsible for \(N/N_D\) of all three components. Parameters are gathered on demand for computation. $$\text{Memory per GPU (ZeRO-3)} = N \times (4/N_D + 4/N_D + 8/N_D) = 16N/N_D \text{ bytes}$$
This linear scaling of memory with \(N_D\) is crucial for models exceeding single-GPU capacity.

⚠️ Communication Overhead

While sharding dramatically reduces memory, it significantly increases communication. For FSDP/ZeRO-3, parameters must be gathered before a layer's forward/backward pass, then discarded. This involves `all-gather` operations for parameters and `reduce-scatter` for gradients, which can become a bottleneck on slower interconnects.

Key Takeaways
▼

When to use which strategy:

  • Data Parallelism (DP): Your model fits on a single GPU, but you want to train with a larger batch size or speed up computation. This is the first step for most distributed training.
  • Pipeline Parallelism (PP): Your model's layers (or activations) exceed single GPU memory. You can tolerate some pipeline "bubbles" (idle time) for significant memory savings.
  • Tensor Parallelism (TP): Individual layers (especially large linear layers or attention blocks in transformers) are too big for one GPU. Requires very high-bandwidth interconnects (e.g., NVLink within a node).
  • 3D Parallelism: For models with hundreds of billions to trillions of parameters, where all three bottlenecks (batch size, model layers, individual layer size) are present. Highly complex to configure and optimize.
  • ZeRO / FSDP: When optimizer states, gradients, or even parameters themselves exceed GPU memory, even with PP/TP. These are often combined with DP, and can be used with PP for even greater memory savings. They are the go-to for LLMs.

Common pitfalls:

  • Communication overhead: All parallelism strategies involve sending data between GPUs. This can become the bottleneck if the interconnect is slow (e.g., cross-node communication for TP).
  • Load imbalance: Uneven distribution of work can leave some GPUs idle, reducing efficiency. This is particularly challenging in PP and TP.
  • Debugging complexity: Distributed training setups are significantly harder to debug than single-GPU training.
  • Framework support: While basic DP is widely supported, advanced techniques like TP, PP, ZeRO, and FSDP require explicit framework support (e.g., PyTorch FSDP, DeepSpeed, Megatron-LM).
💡 The Future is Sharded

For the largest models, sharding techniques like FSDP and ZeRO-3 are becoming the default. By dynamically distributing model parameters, gradients, and optimizer states, they offer the most efficient memory scaling, often reducing the per-GPU memory footprint to a fraction of the total model size, enabling training on commodity hardware clusters that would otherwise be impossible.

Code Trace (PyTorch Examples)
▼
import torch
import torch.nn as nn
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
from torch.distributed.fsdp.wrap import enable_wrap, wrap
# 1. Basic DistributedDataParallel (DDP)
# - Model replicated on each GPU
# - Data sharded per GPU
# - Gradients all-reduced after backward pass
def run_ddp_example(rank, world_size, model, data):
dist.init_process_group("nccl", rank=rank, world_size=world_size)
model = model.to(rank)
ddp_model = DDP(model, device_ids=[rank])
optimizer = torch.optim.Adam(ddp_model.parameters())
output = ddp_model(data[rank]) # data[rank] is a shard
loss = output.sum()
loss.backward() # gradients computed and all-reduced by DDP
optimizer.step()
dist.destroy_process_group()
# 2. FullyShardedDataParallel (FSDP) - similar to ZeRO-3
# - Model parameters, gradients, optimizer states sharded
# - Parameters gathered per-layer during forward/backward
def run_fsdp_example(rank, world_size, model, data):
dist.init_process_group("nccl", rank=rank, world_size=world_size)
with enable_wrap(wrapper_cls=FSDP):
# Wrap individual layers or the whole model with FSDP
fsdp_model = FSDP(model.to(rank))
optimizer = torch.optim.Adam(fsdp_model.parameters())
output = fsdp_model(data[rank])
loss = output.sum()
loss.backward() # gradients are reduce-scattered by FSDP
optimizer.step()
dist.destroy_process_group()
# Note: Tensor and Pipeline Parallelism often involve custom model partitioning
# or specialized libraries (e.g., Megatron-LM, FairScale) beyond basic PyTorch.
