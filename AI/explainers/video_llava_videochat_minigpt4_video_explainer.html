1
Understanding Video MLLMs
▼

What is it? A video multimodal LLM (video-MLLM) lets you "chat" with a video: ask it what happens, when, or why, and it answers in natural language. Video-LLaVA, VideoChat, and MiniGPT4-Video are three landmark systems that all solve the same core problem — a video is way too much raw data (millions of pixels across hundreds of frames) to hand directly to a text-only language model — by turning frames into a short sequence of "visual tokens" the LLM can read like extra words.

Analogy: Imagine describing a movie to a friend over text message. You can't send every frame — you'd send a handful of key snapshots plus a short caption for each ("frame 1: person picks up cup", "frame 2: pours coffee"). The friend's brain (the LLM) then stitches those snapshots and your question together to answer "what did they do with the cup?" Video MLLMs automate exactly this: sample a few frames, compress each into a tiny set of embedding "words", and let the LLM read the whole thing as one long sentence.

The three systems differ mainly in how they compress frames into tokens: Video-LLaVA keeps every visual patch and relies on a shared image/video embedding space (LanguageBind) so no special video architecture is needed; VideoChat uses a learned Q-Former with a small fixed number of query tokens that "read off" the whole clip regardless of length; MiniGPT4-Video keeps a modest number of tokens per frame but also interleaves subtitle text so the LLM gets both what is seen and what is said.

💡 If you remember one thing

Every video-MLLM is the same recipe: sample frames → encode each frame → compress/project into a token budget → concatenate with the text instruction → feed into a pretrained LLM. The papers differ almost entirely in the "compress/project" step — that single design choice determines how many tokens a video costs and how well temporal information survives.

2
How It Works Internally
▼

Stage 1 — Frame Sampling

A raw clip has hundreds or thousands of frames at 24-30 fps. Encoding all of them is wasteful and mostly redundant (adjacent frames barely change). All three models use uniform temporal sampling: pick \(T\) frames evenly spaced across the clip, \(T\) typically 8-100 depending on the model and GPU budget. MiniGPT4-Video additionally extracts subtitles (ASR or provided captions) aligned to the same timestamps.

Stage 2 — Per-Frame Visual Encoding

Each sampled frame is independently encoded by a frozen ViT-style image encoder (CLIP ViT-L/14 for VideoChat/MiniGPT4-Video; LanguageBind's video/image towers, which are CLIP-initialized, for Video-LLaVA). A 224×224 frame with patch size 14 yields a 16×16 = 256-patch grid, so each frame becomes 256 patch embeddings of dimension \(d\) (e.g. 1024).

Stage 3 — Compression / Projection (the key design decision)

Feeding \(T \times 256\) raw patch tokens straight into the LLM would blow the context window past a few frames. Each model makes a different bet:

  • Video-LLaVA: No extra visual resampler — a single linear projection maps each patch embedding into the LLM's embedding space. It relies on LanguageBind pretraining a shared image-video-audio-depth embedding space via contrastive alignment, so images and videos already "look the same" to the projector — the same projection layer works for both modalities. Token cost still scales linearly with \(T\).
  • VideoChat: A Video Q-Former (BLIP-2 style) with a small fixed set of learnable query tokens (e.g. 32) cross-attends over the concatenated per-frame features (after a temporal transformer mixes frames together). Because the query count is fixed, the visual token budget is independent of clip length — a 10s and a 10-minute clip both cost 32 tokens, at the price of losing fine spatial detail.
  • MiniGPT4-Video: Each frame's 256 patches are merged/pooled down to a smaller fixed count (e.g. 64) via a linear layer that concatenates spatially-adjacent tokens before projecting — a middle ground that keeps some per-frame granularity. Crucially, the subtitle text tokens for that timestamp are interleaved right after the visual tokens of the corresponding frame, so the LLM sees "[frame k visual tokens][frame k subtitle text]" repeated per frame.

Stage 4 — Fusion & Autoregressive Decoding

The final sequence — system prompt + interleaved visual/subtitle tokens + the user's text instruction — is fed as one sequence into a pretrained decoder-only LLM (Vicuna-7B/13B or LLaMA-2). The LLM was instruction-tuned on video-QA / captioning data so that it learns to attend to the right visual tokens when generating the answer, exactly as it attends to text — visual tokens are just extra "words" in its vocabulary space.

🔑 Key Property

All three architectures decouple the (frozen, expensive-to-train) visual encoder from the (frozen or LoRA-tuned) LLM using a lightweight, cheaply-trained projector/resampler. Only the projector (and sometimes a LoRA adapter on the LLM) is trained on video-instruction data — this is why these models can be trained on a handful of GPUs instead of from scratch.

Why It Works — The Math
▼

Token Budget

Let \(T\) be the number of sampled frames, \(P\) the patches per frame from the visual encoder, and \(K\) the number of tokens each frame (or the whole clip) is compressed to. Let \(L_{txt}\) be the instruction (+ system prompt) length in tokens. The total sequence length fed to the LLM is:

$$L_{seq} \;=\; \underbrace{T \cdot P}_{\text{raw patches}} \xrightarrow{\text{compress}} \underbrace{f(T,K)}_{\text{visual tokens}} \;+\; L_{txt}$$

where \(f(T,K) = T \cdot K\) for per-frame compression (Video-LLaVA with \(K=P\), MiniGPT4-Video with \(K \ll P\)), or \(f(T,K) = K\) (constant in \(T\)) for a clip-level Q-Former (VideoChat). This single functional form explains the entire design space: linear-in-\(T\) architectures give up scalability for spatial fidelity; constant-in-\(T\) architectures give up fine detail for the ability to ingest arbitrarily long videos without exceeding the context window \(L_{max}\):

$$f(T,K) + L_{txt} \;\le\; L_{max} - L_{gen}$$

where \(L_{gen}\) is tokens reserved for the generated answer.

Shared Embedding Space via Contrastive Alignment

Video-LLaVA's trick of using one projector for both images and videos only works because LanguageBind pretrains its video/image/audio/depth encoders with a CLIP-style symmetric contrastive loss against a shared language anchor. For a batch of \(N\) video-text pairs \((v_i, t_i)\) with encoders \(g_v, g_t\):

$$\mathcal{L}_{contrastive} = -\frac{1}{N}\sum_{i=1}^{N} \log \frac{\exp(\text{sim}(g_v(v_i), g_t(t_i))/\tau)}{\sum_{j=1}^{N}\exp(\text{sim}(g_v(v_i), g_t(t_j))/\tau)}$$

where \(\text{sim}(\cdot,\cdot)\) is cosine similarity and \(\tau\) a learned temperature. Aligning every modality to the same language-anchored space means an image embedding and a video-frame embedding end up in comparable regions of \(\mathbb{R}^d\) — so a projector trained on image-text pairs transfers to video with minimal extra tuning.

Autoregressive Objective

Given visual tokens \(\mathbf{v} = (v_1,\ldots,v_{K'})\) and instruction tokens \(\mathbf{x}\), the LLM is trained with the standard next-token cross-entropy over the answer tokens \(\mathbf{y}=(y_1,\ldots,y_n)\), conditioning on everything before position \(t\):

The visual tokens are just prepended (or interleaved) into the same causal sequence — no separate cross-attention module is required once tokens live in the LLM's embedding space, which is precisely why the projector design in Stage 3 is the crux of the whole system.

⚠️ Common Pitfall

Uniform frame sampling assumes the "interesting" moment is evenly distributed in time. For long videos with brief key events (e.g. a 10-minute video where the answer depends on a 2-second action), a fixed, low \(T\) can simply miss the frame that matters — no amount of clever projection recovers information that was never sampled.

Key Takeaways
▼

When each design shines:

  • Video-LLaVA — best when you need images and videos handled by one unified model/projector with minimal architecture-specific engineering; token cost grows linearly with frames sampled.
  • VideoChat — best for long videos or when a fixed, small, predictable token/compute budget matters more than fine spatial detail; the Q-Former "reads off" a whole clip into a constant number of tokens.
  • MiniGPT4-Video — best when subtitles/ASR text is available and complements vision (lectures, movies, tutorials); interleaving visual + subtitle tokens per frame gives the LLM both modalities in sync.

Shared limitations across all three:

  • Uniform sampling can miss short, important events between sampled frames.
  • Frozen visual encoders trained on static images may not capture motion/temporal dynamics well — none of these truly model optical flow.
  • Token budget vs. context window is a hard constraint — longer/more frames eventually forces either fewer frames, harsher compression, or a bigger-context LLM.
💡 The One Axis That Matters

Rank the three by tokens-per-frame vs. temporal-scalability: Video-LLaVA (many tokens/frame, poor scaling) → MiniGPT4-Video (fewer tokens/frame + text, medium scaling) → VideoChat (fixed tokens regardless of length, best scaling, least spatial detail). Every later video-MLLM (LLaVA-NeXT-Video, Video-ChatGPT, VideoLLaMA, ...) sits somewhere on this same spectrum.

Code Trace

import torch, decord, numpy as np
# 1. Uniformly sample T frames from the raw clip
def sample_frames(video_path, T=8):
vr = decord.VideoReader(video_path)
idx = np.linspace(0, len(vr) - 1, T).astype(int)
return vr.get_batch(idx) # (T, H, W, 3)
# 2. Encode each frame independently (frozen ViT / LanguageBind)
def encode_frames(frames, visual_encoder):
with torch.no_grad():
feats = visual_encoder(frames) # (T, P=256, d)
return feats
# 3a. Video-LLaVA style: linear projector, no compression
def project_linear(feats, W_proj):
return (feats @ W_proj).flatten(0, 1) # (T*P, d_llm)
# 3b. VideoChat style: fixed-size Q-Former (K queries, clip-level)
def project_qformer(feats, query_tokens, qformer):
clip_feats = feats.flatten(0, 1) # (T*P, d)
return qformer(query_tokens, clip_feats) # (K, d_llm), K fixed e.g. 32
# 3c. MiniGPT4-Video style: per-frame merge + interleave subtitles
def project_merge_interleave(feats, subtitles, merge_proj):
seq = []
for t in range(feats.shape[0]):
vis_tok = merge_proj(feats[t]) # (K=64, d_llm)
seq += [vis_tok, tokenize(subtitles[t])]
return torch.cat(seq, dim=0)
# 4. Fuse with instruction and generate autoregressively
def video_chat(visual_tokens, instruction, llm, tokenizer):
text_emb = llm.embed(tokenizer(instruction))
input_embeds = torch.cat([visual_tokens, text_emb], dim=0)
return llm.generate(inputs_embeds=input_embeds[None], max_new_tokens=256)
