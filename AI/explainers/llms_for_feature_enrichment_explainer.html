Understanding LLM Feature Enrichment
▼

What is it? Recommender systems live or die on the quality of their features. Real catalogs are full of items with a title, a category, and a price — and nothing else. Real users type messy, unstructured queries like "something rugged for weekend hikes, not too expensive." Classic collaborative filtering and rule-based taggers cannot use any of that. LLM feature enrichment closes the gap: an LLM reads sparse item metadata and writes a rich, grounded description; another LLM call reads a raw user query and extracts a structured intent (category, style, price sensitivity, use-case). Both get embedded into the same feature space so retrieval and ranking can actually compare them.

Analogy: Imagine a store clerk with amnesia who only sees an item's barcode and price tag — that's your sparse metadata. Now imagine handing that clerk a magnifying glass and catalog knowledge so they can write "weatherproof ripstop trail backpack, olive green, built for weekend hikes." Separately, a second clerk translates a customer's rambling request ("rugged, not too pricey, earthy colors") into a checklist. Suddenly both clerks are speaking the same structured language, and matching them is trivial.

💡 If you remember one thing

LLM enrichment turns two ends of the funnel — sparse item metadata and unstructured user language — into dense, comparable feature vectors. The recommender never sees raw text; it sees $$\text{sim}(\vec{v}_{\text{item}}, \vec{v}_{\text{intent}}) = \frac{\vec{v}_{\text{item}} \cdot \vec{v}_{\text{intent}}}{\lVert \vec{v}_{\text{item}} \rVert \, \lVert \vec{v}_{\text{intent}} \rVert}$$ computed in a shared embedding space that the LLM helped populate.

2
How It Works Internally
▼

Two Pipelines, One Feature Space

Item side (offline, batch): a prompt template feeds an LLM the raw structured fields it does have (title, category, price, maybe a UPC-linked spec sheet). The LLM generates free text: a description, inferred attributes, use-cases, style tags. That text is grounded — the prompt instructs the model to only state what's plausible from the given fields, and a lightweight validator can strip claims the fields don't support. The generated text is then run through a text embedding model (or the same LLM's embedding head) to produce a dense vector alongside — or replacing — the old one-hot / sparse features.

User side (online, per-request): the raw query or session context is sent through a cheaper, low-latency LLM call (often a distilled or fine-tuned small model) that performs structured extraction: it returns a JSON object with fields like category, price sensitivity, style, occasion, and constraints. This intent object is embedded into the same feature space used for items.

Why Not Skip the LLM and Embed Raw Text Directly?

You can embed raw text directly with a bi-encoder, and many systems do. The LLM enrichment step adds value in three places: (1) it fills gaps — a three-word title becomes a 40-word description covering material, season, and audience that a raw-text embedder never had signal for; (2) it normalizes vocabulary — "affordable," "budget-friendly," and "cheap" all map toward the same latent price-tier signal; (3) it infers — from "rugged hiking backpack" an LLM can infer high durability and an outdoor-adventurer audience even if those words never appear verbatim.

🔑 Key Property

The item-side enrichment runs offline in batch (cheap, cacheable, can use a large model). The user-side extraction runs online per-request under a latency budget (must use a small/distilled model or aggressive caching of common query patterns). This asymmetry is the central systems-design decision.

3
Why It Works — The Math
▼

Feature Coverage

Model each item and each intent as a vector in a shared \(D\)-dimensional attribute space (material, style, use-case, season, price tier, durability, color tone, audience, brand tier, ...). Define coverage as the fraction of non-zero dimensions:

$$\text{coverage}(\vec{v}) = \frac{1}{D}\sum_{d=1}^{D} \mathbb{1}[\,v_d \neq 0\,]$$

Sparse metadata typically covers 1–3 of \(D \approx 9\) dimensions (\(\sim\)11–33%). A well-grounded LLM description routinely covers 7–9 of them (\(\sim\)78–100%) because natural language descriptions touch many attributes implicitly.

Matching Score

Retrieval/ranking scores items by cosine similarity between the item vector \(\vec{v}_{\text{item}}\) and the extracted intent vector \(\vec{v}_{\text{intent}}\):

$$\text{sim}(\vec{v}_{\text{item}}, \vec{v}_{\text{intent}}) = \frac{\vec{v}_{\text{item}} \cdot \vec{v}_{\text{intent}}}{\lVert \vec{v}_{\text{item}} \rVert \, \lVert \vec{v}_{\text{intent}} \rVert}, \qquad \vec{v}_{\text{item}}\cdot\vec{v}_{\text{intent}} = \sum_{d=1}^{D} v_{\text{item},d}\, v_{\text{intent},d}$$

Because sparse item vectors are mostly zero, most terms in the dot product vanish — the similarity is capped low no matter how well the item actually matches. Enrichment raises the number of non-zero, correctly-valued dimensions on both sides, which directly increases the achievable dot product and therefore the similarity score.

Expected Lift

If enrichment independently raises coverage on the item side from \(c_i\) to \(c_i'\) and preserves intent coverage \(c_u\), the expected number of "live" matching dimensions scales roughly with \(c_i \cdot c_u \to c_i' \cdot c_u\) — a multiplicative, not additive, gain. This is why enrichment often produces large relative lifts specifically for cold-start items, where \(c_i\) starts near zero.

⚠️ Common Pitfall

Coverage is not accuracy. An LLM can confidently generate a plausible-sounding attribute that is wrong (hallucination) — a "waterproof" claim on a jacket that isn't. Ungrounded enrichment can inflate similarity scores for the wrong reasons. Production systems constrain generation to fields supported by verified metadata, or downweight/flag LLM-inferred (vs. verified) dimensions separately in the scoring function.

Key Takeaways
▼

When to use LLM feature enrichment:

  • Cold-start items with thin metadata (new sellers, long-tail catalog, UGC marketplaces)
  • Free-text or conversational query surfaces where users don't use filter taxonomies
  • Cross-lingual or cross-vocabulary catalogs where keyword matching fails on synonyms
  • You have (or can build) a way to ground generation in verified fields to bound hallucination

When NOT to use / watch out:

  • High-value/regulated attributes (price, safety claims, ingredients) — never let an LLM invent these
  • Extremely tight latency budgets with no room for even a small distilled extraction model — precompute/cache instead
  • Catalogs that already have rich structured taxonomies — enrichment adds cost without much lift
  • No offline evaluation loop to catch enrichment drift or hallucinated attributes over time
💡 Systems Pattern

Item enrichment is a batch/offline job (run nightly, cache forever, use your biggest model). Intent extraction is an online/per-request job (must be fast, cache aggressively by normalized query, use a small model). Treat them as different engineering problems even though they share one embedding space.

# --- Item-side: offline batch enrichment ---
item = {"title": "Trailblaze 32L Pack", "category": "Bags", "price": 89}
prompt = f"""Given ONLY these verified fields: {item}
Write a grounded product description. Do not invent
materials, certifications, or claims not implied by the fields."""
description = llm.generate(prompt) # batch, cached forever
item_vec = embed_model.encode(description) # dense, D-dim
# --- User-side: online intent extraction ---
query = "something rugged for weekend hikes, not too expensive, earthy tones"
extract_prompt = f"""Extract JSON intent from: "{query}"
Fields: style, use_case, price_tier, color_tone. Infer implied
fields (e.g. durability, audience) from context."""
intent = small_llm.generate_json(extract_prompt) # fast, <50ms budget
intent_vec = embed_model.encode(json.dumps(intent))
# --- Matching ---
score = cosine_similarity(item_vec, intent_vec)
ranked_items = sorted(catalog, key=lambda i: -cosine_similarity(i.vec, intent_vec))
