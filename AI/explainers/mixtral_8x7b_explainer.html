Understanding Mixtral's Sparse MoE
▼

What is it? Mixtral 8x7B (Mistral AI, Dec 2023) is a decoder-only transformer where every feed-forward network (FFN) block is replaced by 8 expert FFNs plus a small router. For each token, the router picks just 2 of the 8 experts and blends their outputs. The name "8x7B" is misleading: it does not have 56B parameters — attention layers are shared, so the real total is ~47B, and because only 2/8 experts fire per token, only ~13B parameters do work on any given token.

Analogy: Imagine a hospital with 8 specialist doctors (cardiologist, neurologist, etc.) and a triage nurse (the router). A patient (token) doesn't see all 8 doctors — the nurse reads the symptoms and sends them to the two most relevant specialists, then combines their opinions weighted by how confident the nurse was in each referral. You get specialist-level care without paying for 8 consultations.

💡 If you remember one thing

Mixtral decouples total capacity from per-token compute. A learned router computes a softmax over 8 experts, keeps only the top-2 logits, renormalizes them, and combines expert outputs: $$y = \sum_{i \in \text{Top2}} \frac{\exp(g_i)}{\sum_{j\in\text{Top2}}\exp(g_j)} \cdot E_i(x)$$ Six experts stay completely idle for that token — zero FLOPs spent on them.

How the Router Works Internally
▼

Where MoE Sits in the Transformer Block

Every Mixtral layer keeps a standard grouped-query attention sub-block, but replaces the single dense FFN with a sparse MoE FFN. The router is a tiny linear layer \(W_g \in \mathbb{R}^{d_{model}\times 8}\) applied to the token's hidden state \(x\): \(g = W_g x\) produces 8 raw "gate logits," one per expert.

Top-K Gating, Step by Step

1. Compute logits \(g_1,\dots,g_8\) for all 8 experts. 2. Keep only the top-2 logits (by value), masking the other 6 to \(-\infty\). 3. Apply softmax over just those 8 slots — since 6 are \(-\infty\), their softmax probability is exactly 0, so effectively you renormalize over the surviving 2. 4. Run the token through only those two experts' FFNs (each a SwiGLU MLP identical in shape to a dense Mistral-7B FFN). 5. Sum the two expert outputs weighted by their softmax probabilities.

Design Decision: Why Top-2, not Top-1 or Top-4?

Top-1 (switch routing) is cheapest but gives the router no way to "hedge" between two plausible specializations and tends to destabilize training. Top-4 roughly doubles compute versus top-2 for diminishing quality gains. Mistral AI's ablations found top-2 the sweet spot: enough redundancy for stable gradients through the router (since gradients flow to 2 experts, not 1), while keeping active parameters near a single dense 13B model's compute budget.

🔑 Key Property

Routing is per-token, per-layer — a token can be sent to completely different expert pairs at each of the 32 layers. There is no notion of a single "expert" owning a token end-to-end; specialization emerges at the level of individual FFN sub-computations (empirically more tied to syntax/local patterns than to topic, contrary to early intuition).

Why It Works — The Math
▼

The Gating Function

Formally, for router weight matrix \(W_g\) and token hidden state \(x \in \mathbb{R}^{d}\):

$$g = W_g x \in \mathbb{R}^{8}, \qquad \mathcal{T} = \operatorname{TopK}(g, k{=}2)$$

The gating weight for expert \(i\) is a softmax restricted to the top-2 set \(\mathcal{T}\):

$$G_i(x) = \begin{cases} \dfrac{\exp(g_i)}{\sum_{j \in \mathcal{T}} \exp(g_j)} & i \in \mathcal{T} \\[4pt] 0 & i \notin \mathcal{T} \end{cases}$$

The layer output is a convex combination of only the selected experts' feed-forward computations:

$$y = \sum_{i=1}^{8} G_i(x)\, E_i(x) = \sum_{i \in \mathcal{T}} G_i(x)\, E_i(x)$$

Because \(G_i(x)=0\) for 6 of the 8 experts, those experts are never even evaluated for this token — this is what makes MoE sparse: the sum is written over all 8, but the compute graph only touches 2.

Load Balancing Auxiliary Loss

Left unchecked, the router tends to collapse onto a few favorite experts (rich-get-richer). Training adds an auxiliary loss that penalizes imbalance across a batch of \(T\) tokens, using the fraction of tokens routed to expert \(i\) (\(f_i\)) and the average router probability mass on expert \(i\) (\(P_i\)):

$$\mathcal{L}_{aux} = \alpha \cdot N \sum_{i=1}^{N} f_i \cdot P_i, \qquad f_i = \frac{1}{T}\sum_{t=1}^{T}\mathbb{1}[i \in \mathcal{T}_t], \quad P_i = \frac{1}{T}\sum_{t=1}^{T} \operatorname{softmax}(g_t)_i$$

This is minimized when routing is uniform (\(f_i = P_i = 1/N\) for all experts), pulling the loss toward an even load across experts — crucial for both training stability and inference throughput (no single expert becomes a bottleneck).

⚠️ Common Pitfall

The TopK is non-differentiable — you cannot backprop through "which experts were chosen." Gradients only flow through the softmax weights of the chosen experts, plus the auxiliary balancing loss. Experts that are rarely selected get rare, noisy gradient signal, which is why load balancing and careful initialization matter so much for MoE training stability.

Key Takeaways
▼

Why sparse MoE wins:

  • Inference FLOPs per token scale with active params (~13B), not total params (~47B) — roughly the speed of a dense 13B model with the knowledge capacity of a much larger one.
  • Memory footprint still requires storing all 47B parameters (all experts must be resident, since routing decisions vary per token) — MoE trades compute for VRAM/HBM.
  • Mixtral 8x7B matched or beat Llama-2 70B and GPT-3.5 on many benchmarks while running inference ~6x faster than a dense 47B-equivalent model.

When NOT to reach for MoE:

  • Memory-constrained deployment (edge devices, single small GPU) — you pay full storage cost regardless of sparsity.
  • Small models / small data regimes — routing collapse and instability are worse relative to the (small) capacity gain.
  • Latency-critical single-token generation at tiny batch size — MoE's throughput advantage shows up most at larger batches where expert-parallel routing is efficient.
💡 Mental Model

Dense model = every employee reviews every task. MoE = a smart dispatcher sends each task to the 2 best-suited employees out of 8. Total headcount (parameters) is large, but the payroll cost per task (FLOPs) stays small — as long as you can afford to keep the whole office staffed (VRAM).

import torch, torch.nn.functional as F
class SparseMoE(torch.nn.Module):
def __init__(self, d_model, d_ff, n_experts=8, top_k=2):
super().__init__()
self.gate = torch.nn.Linear(d_model, n_experts, bias=False)
self.experts = torch.nn.ModuleList(
[SwiGLU_FFN(d_model, d_ff) for _ in range(n_experts)])
self.top_k = top_k
def forward(self, x): # x: (tokens, d_model)
logits = self.gate(x) # (tokens, n_experts)
top_val, top_idx = logits.topk(self.top_k, dim=-1)
weights = F.softmax(top_val, dim=-1) # renormalize over top-2 only
out = torch.zeros_like(x)
for slot in range(self.top_k):
expert_id = top_idx[:, slot] # which expert each token picked
w = weights[:, slot].unsqueeze(-1) # gate weight for that pick
for e in expert_id.unique(): # batch tokens by expert (real
mask = expert_id == e # kernels use scatter/gather)
out[mask] += w[mask] * self.experts[e](x[mask])
return out, logits # logits needed for aux load-balancing loss
def load_balance_loss(logits, top_idx, n_experts):
probs = F.softmax(logits, dim=-1)
P = probs.mean(dim=0) # avg prob mass per expert
f = F.one_hot(top_idx, n_experts).float().sum(1).mean(0) # token frac
return n_experts * (f * P).sum() # minimized at uniform routing
