Understanding Grouped Query Attention
▼

What is it? Grouped Query Attention (GQA) is an optimization technique for Transformer models, particularly important for large language models (LLMs) like Llama 2 and Llama 3 during inference. It's a compromise between Multi-Head Attention (MHA) and Multi-Query Attention (MQA), aiming to reduce memory bandwidth requirements and improve inference speed while maintaining model quality.

The Problem: KV Cache During auto-regressive decoding (generating text token by token), each new token needs to attend to all previous tokens. To avoid recomputing Key (K) and Value (V) projections for past tokens, these are stored in a "KV cache". For long sequences and many attention heads (as in MHA), this cache can become very large, consuming significant GPU memory and bandwidth, which slows down inference.

Analogy: Imagine a large library (the Transformer model) with many researchers (Query heads) who each need to consult specific reference books (Key-Value pairs) from the archives (KV cache). In MHA, each researcher has their own dedicated set of reference books. In MQA, all researchers share just one set of reference books. GQA is like having several small groups of researchers, where each group shares a single set of reference books, striking a balance between individual access and shared resources.

💡 If you remember one thing

GQA reduces the size of the Key-Value (KV) cache by allowing multiple Query (Q) heads to share the same Key (K) and Value (V) projection matrices. This directly reduces memory usage and increases inference throughput, especially for long contexts.

2
From MHA to GQA
▼

Multi-Head Attention (MHA) — The Baseline

In standard MHA, the input token embeddings are projected into \(h\) separate Query (\(Q\)), Key (\(K\)), and Value (\(V\)) heads. Each head performs its own attention calculation independently. This allows the model to attend to different parts of the input sequence simultaneously, capturing diverse relationships. Critically, each of the \(h\) query heads has its own independent \(K\) and \(V\) projections.

During inference, the KV cache stores \(h \times d_k\) (for K) and \(h \times d_v\) (for V) values per token, where \(d_k\) and \(d_v\) are the dimension of keys and values for a single head. This scales linearly with the number of heads \(h\).

Multi-Query Attention (MQA) — Extreme Sharing

MQA takes the sharing to an extreme: all \(h\) Query heads share a single Key head and a single Value head. This means there's only one \(K\) projection and one \(V\) projection for all queries. The benefit is a drastically reduced KV cache size (by a factor of \(h\)), leading to much faster inference and lower memory usage. However, sharing a single K/V pair across all query heads can sometimes lead to a degradation in model quality, as the K/V representations might not be rich enough to serve all diverse query needs.

Grouped Query Attention (GQA) — The Middle Ground

GQA finds a balance. Instead of all \(h\) query heads sharing one K/V head, or each query head having its own K/V head, GQA groups the query heads into \(G\) groups. Each group of query heads then shares a dedicated K/V head. The number of K/V heads, \(h_{kv}\), is thus \(G\), where \(1 < G < h\). If \(G=1\), it becomes MQA. If \(G=h\), it becomes MHA.

This approach reduces the KV cache size by a factor of \(h/G\) compared to MHA, offering significant memory and bandwidth savings, while generally preserving more of the model's quality compared to MQA. Llama 2 uses GQA with \(G=8\) (for 70B model) or \(G=1\) (for 7B/13B, which is MQA), and Llama 3 uses GQA with \(G=8\) for its 70B model.

🔑 Key Trade-off

GQA navigates the trade-off between inference speed (favored by fewer KV heads) and model quality (favored by more KV heads). It offers a tunable parameter (\(G\)) to find the optimal point for a given model size and hardware constraint.

The Math Behind Attention & GQA
▼

The Core Attention Mechanism

The fundamental scaled dot-product attention function remains the same across MHA, MQA, and GQA:

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}\right)V$$

Here, \(Q\) (Query), \(K\) (Key), and \(V\) (Value) are matrices derived from the input embeddings. \(d_k\) is the dimension of the key vectors.

Multi-Head Attention (MHA) Formulation

In MHA, the input \(X\) is linearly projected into \(h\) sets of \(Q, K, V\) matrices. Each set corresponds to an "attention head". The outputs of these heads are then concatenated and linearly transformed:

$$\text{MHA}(X) = \text{Concat}(\text{head}_1, \dots, \text{head}_h)W^O$$ $$\text{where } \text{head}_i = \text{Attention}(XW_i^Q, XW_i^K, XW_i^V)$$

Each head \(i\) has its own projection matrices \(W_i^Q, W_i^K, W_i^V\). This means there are \(h\) distinct Key and Value projections, leading to a KV cache size proportional to \(h \times d_k \times \text{sequence_length}\).

Grouped Query Attention (GQA) Formulation

GQA modifies the MHA structure by introducing a grouping factor \(G\). There are still \(h\) Query heads, but only \(G\) Key heads and \(G\) Value heads. Each of the \(h\) Query heads belongs to one of the \(G\) groups, and all Query heads within a group share the same \(K\) and \(V\) projections for that group.

Let \(h\) be the total number of query heads and \(G\) be the number of key/value groups. Then the number of key/value heads is \(h_{kv} = G\). The attention output is still a concatenation of head outputs:

$$\text{GQA}(X) = \text{Concat}(\text{head}_1, \dots, \text{head}_h)W^O$$ $$\text{where } \text{head}_i = \text{Attention}(XW_i^Q, XW_{\text{group}(i)}^K, XW_{\text{group}(i)}^V)$$

Here, \(W_i^Q\) is unique for each query head \(i\), but \(W_{\text{group}(i)}^K\) and \(W_{\text{group}(i)}^V\) are shared across all query heads \(i\) that belong to the same group \(\text{group}(i)\). This reduces the KV cache size to be proportional to \(G \times d_k \times \text{sequence_length}\).

⚠️ Design Choice

The choice of \(G\) is critical. A smaller \(G\) (closer to MQA) means greater memory savings but potentially more quality degradation. A larger \(G\) (closer to MHA) preserves more quality but offers fewer memory savings. Modern LLMs like Llama 2/3 have found \(G=8\) to be a good balance for their larger models.

Key Takeaways & Practical Implications
▼

When to use GQA:

  • Large Language Model Inference: Crucial for deploying LLMs efficiently, especially with long context windows.
  • Memory-Constrained Environments: Helps fit larger models or longer sequences into available GPU memory.
  • High Throughput Requirements: Reduced KV cache size means less memory bandwidth contention, leading to faster token generation.
  • Specific Model Architectures: If the model's architecture (like Llama 2/3) is designed with GQA, it's essential for optimal performance.

When NOT to use / Considerations:

  • Model Training: GQA is primarily an inference optimization. During training, MHA is typically used to maximize model capacity and quality.
  • Small Models: For smaller models or short sequences, the KV cache overhead might not be significant enough to warrant GQA's complexity or potential minor quality trade-offs.
  • Maximal Quality is Paramount: If even a tiny degradation in quality is unacceptable, and hardware resources are not a constraint, MHA might still be preferred.
  • Poorly Chosen Grouping Factor (\(G\)): An excessively small \(G\) can lead to quality degradation, while \(G=h\) negates the benefits (becomes MHA).
💡 GQA Spectrum

GQA represents a continuum: MQA (\(G=1\)) is one extreme, offering maximum speedup but potential quality loss. MHA (\(G=h\)) is the other, offering maximum quality but higher memory/latency. GQA (\(1 < G < h\)) allows fine-tuning this balance.

Code Trace (Conceptual Python)
▼
import torch
import torch.nn as nn
class GQAAttention(nn.Module):
def __init__(self, dim, num_heads, num_query_groups, head_dim):
super().__init__()
self.num_heads = num_heads
self.num_query_groups = num_query_groups
self.head_dim = head_dim
self.num_kv_heads = num_heads // num_query_groups # Number of K/V heads
# Projection matrices for Q, K, V
self.q_proj = nn.Linear(dim, num_heads * head_dim, bias=False)
# K and V projections are smaller for GQA
self.k_proj = nn.Linear(dim, self.num_kv_heads * head_dim, bias=False)
self.v_proj = nn.Linear(dim, self.num_kv_heads * head_dim, bias=False)
self.o_proj = nn.Linear(num_heads * head_dim, dim, bias=False)
def forward(self, hidden_states, kv_cache=None):
batch_size, seq_len, _ = hidden_states.shape
# 1. Project to Q, K, V
query_states = self.q_proj(hidden_states).view(batch_size, seq_len, self.num_heads, self.head_dim)
key_states = self.k_proj(hidden_states).view(batch_size, seq_len, self.num_kv_heads, self.head_dim)
value_states = self.v_proj(hidden_states).view(batch_size, seq_len, self.num_kv_heads, self.head_dim)
# 2. Expand K/V for GQA (if num_query_groups > 1)
if self.num_query_groups != 1:
key_states = key_states.repeat_interleave(self.num_query_groups, dim=2)
value_states = value_states.repeat_interleave(self.num_query_groups, dim=2)
# 3. Transpose for attention calculation (batch, num_heads, seq_len, head_dim)
query_states = query_states.transpose(1, 2)
key_states = key_states.transpose(1, 2)
value_states = value_states.transpose(1, 2)
# 4. Scaled Dot-Product Attention
attn_weights = torch.matmul(query_states, key_states.transpose(-1, -2)) / (self.head_dim**0.5)
attn_weights = torch.softmax(attn_weights, dim=-1)
attn_output = torch.matmul(attn_weights, value_states)
# 5. Concatenate heads and project back
attn_output = attn_output.transpose(1, 2).contiguous().view(batch_size, seq_len, -1)
output = self.o_proj(attn_output)
return output
