Understanding DocVQA
▼

What is it? DocVQA (Document Visual Question Answering) is the task of answering a natural-language question about a document image — an invoice, receipt, form, or scanned report — where the answer is usually a short span of text physically printed somewhere on the page. Unlike plain-text QA, the model must jointly reason over three modalities: what the words say, where they are positioned (layout), and how they look (fonts, tables, checkboxes, logos).

Analogy: Imagine handing a photograph of a restaurant receipt to an assistant and asking "What's the tip amount?" A pure text reader who only gets a jumbled bag of words ("Tip", "Total", "$4.50", "$32.10") can't tell which number belongs to which label. A human glances at the 2D layout — the number sitting just to the right of the word "Tip" — and instantly knows. DocVQA models are built to use that same spatial cue.

💡 If you remember one thing

DocVQA fuses text, 2D layout (bounding boxes), and visual appearance into one representation, then either (a) extracts an answer span from OCR'd word boxes, or (b) generates the answer directly from pixels with no OCR at all. $$\text{answer} = f(\text{question}, \{\text{text}_i, \text{box}_i, \text{visual}_i\}_{i=1}^N)$$

How It Works Internally
▼

Two Competing Pipelines

OCR-based (LayoutLM family): An off-the-shelf OCR engine (Tesseract, cloud OCR) first reads the page and returns a list of words with bounding boxes \((x_0,y_0,x_1,y_1)\). Each word is tokenized, embedded, and given three additive embeddings: a text-token embedding, a 1D position embedding (its order in reading sequence), and a 2D layout embedding built from its box coordinates. A visual backbone (ResNet/Swin, in LayoutLMv2/v3) contributes patch features aligned to the same boxes. A transformer encoder then lets every word attend to every other word AND to visual patches jointly, producing a fused token representation used to predict an answer span (start/end token classifiers, like extractive QA).

OCR-free (Donut, Pix2Struct): Skips OCR entirely. The raw document image is split into patches, encoded by a vision transformer/Swin encoder, and a text decoder (BART-like, autoregressive) directly generates the answer token-by-token, conditioned on the question and the encoded image. There are no bounding boxes and no error-prone OCR step to propagate mistakes — but the model must implicitly learn to "read" during pretraining on millions of document images with synthetic OCR-pseudo-labels or text-image pairs.

Why 2D Position Matters (LayoutLM-style)

A word's meaning in a form is inseparable from its position. LayoutLM embeds each of \(x_0,y_0,x_1,y_1\) (plus width/height) through separate learned embedding tables, normalized to a fixed grid (e.g. 0–1000), and sums them onto the token embedding:

$$e_i = \text{Emb}_{\text{text}}(w_i) + \text{Emb}_{x_0}(x_{0,i}) + \text{Emb}_{y_0}(y_{0,i}) + \text{Emb}_{x_1}(x_{1,i}) + \text{Emb}_{y_1}(y_{1,i})$$

This lets self-attention learn spatial priors — e.g. "attend to the box directly below the header" — purely from data, without hand-coded rules.

The Resolution Bottleneck

Document text is tiny relative to natural images: a receipt digit might occupy an 8×8 pixel region. Standard vision transformers downsample to 224×224 or 384×384, which blurs small print into noise. High-res-aware models (Pix2Struct's variable-resolution patching, LayoutLMv3's 16×16 patch grid at higher input size) trade quadratic attention cost for legibility — patch count grows as \((\text{resolution}/\text{patch size})^2\), so doubling resolution to keep text sharp roughly quadruples compute.

🔑 Key Property

DocVQA models must jointly satisfy three constraints: textual grounding (read correctly), spatial grounding (know where things sit relative to each other), and resolution sufficiency (small glyphs must survive patchification). Losing any one collapses accuracy on real-world scanned documents.

Why It Works — The Math
▼

Cross-Attention Between Question and Document

Let \(q \in \mathbb{R}^d\) be the pooled question representation and \(k_i, v_i \in \mathbb{R}^d\) be the fused (text+layout+visual) key/value vectors for word box \(i\). The attention weight over word boxes is standard scaled dot-product attention:

$$\alpha_i = \frac{\exp(q^\top k_i / \sqrt{d})}{\sum_{j=1}^N \exp(q^\top k_j / \sqrt{d})}, \qquad c = \sum_{i=1}^N \alpha_i v_i$$

The context vector \(c\) is high whenever the question strongly matches a box's fused representation — this is exactly why "total amount" attends to the box that looks numeric and sits near the word "Total".

Answer Span Extraction (Extractive Head)

For OCR-based models, two linear heads map each token's final hidden state \(h_i\) to a start logit and end logit:

$$s_i = w_{\text{start}}^\top h_i, \quad e_i = w_{\text{end}}^\top h_i, \qquad \hat{i}_{\text{start}} = \arg\max_i s_i,\ \ \hat{i}_{\text{end}} = \arg\max_i e_i$$

Training minimizes cross-entropy between predicted and gold start/end indices, exactly like SQuAD-style extractive QA — but the token features already encode layout, so "which token" implicitly also means "which region of the page."

OCR-Free: Generation Likelihood

Donut/Pix2Struct instead maximize the likelihood of the answer sequence \(y_{1:T}\) token-by-token, conditioned on encoded image patches \(E = \text{Encoder}(\text{image})\) and the question prompt:

This is a standard autoregressive cross-entropy loss (like any seq2seq decoder) — no explicit span-index labels are needed, only ground-truth answer strings, which makes OCR-free training data cheaper to collect but harder to make faithful (the model can "hallucinate" plausible-looking but wrong numbers).

⚠️ Common Pitfall

OCR-based pipelines inherit every OCR error — a misread "8" as "B" propagates irrecoverably into the span extractor, since the extractor only sees OCR's output tokens. OCR-free models avoid this failure mode but pay for it with weaker exact-match reliability on rare formats, since decoding is generative and unconstrained.

Key Takeaways
▼

When to use OCR-based (LayoutLM/LayoutLMv3):

  • Clean, machine-printed documents where OCR is highly reliable (invoices, tax forms, structured templates)
  • You need exact span provenance — "the answer came from THIS box" — for auditability
  • You already run OCR in your pipeline for other purposes (search, indexing)

When to use OCR-free (Donut/Pix2Struct):

  • Messy, handwritten, low-quality scans where OCR itself frequently fails
  • You want a single end-to-end model with no external OCR dependency to maintain/version
  • Documents in scripts or layouts (tables, charts) that OCR engines handle poorly
💡 Hierarchy

Plain-text QA (ignores layout) ⊂ OCR-based DocVQA (adds 2D position + visual features on top of OCR text) ⊂ OCR-free DocVQA (learns to read AND locate AND answer jointly from raw pixels, at the cost of needing much larger pretraining corpora and higher inference resolution).

import numpy as np
# OCR gives word boxes normalized to a 0-1000 grid
words = ["Total:", "$1,240.00", "Date:", "03/14/2024"]
boxes = np.array([[120,300,180,320],
[190,300,290,320], # answer box
[120,340,170,360],
[180,340,260,360]])
# LayoutLM-style: sum text + 2D position embeddings
def layout_embed(text_emb, box, emb_tables):
x0, y0, x1, y1 = box
e = text_emb.copy()
e += emb_tables['x'][x0] + emb_tables['y'][y0]
e += emb_tables['x'][x1] + emb_tables['y'][y1]
return e
# Question-to-document cross attention (scaled dot-product)
def cross_attention(q, K, V, d):
scores = (K @ q) / np.sqrt(d)
alpha = np.exp(scores - scores.max())
alpha /= alpha.sum() # softmax
context = alpha @ V # weighted sum
return alpha, context
# Extractive span head: argmax over start/end logits
def extract_span(hidden_states, w_start, w_end):
start_logits = hidden_states @ w_start
end_logits = hidden_states @ w_end
return np.argmax(start_logits), np.argmax(end_logits)
# OCR-free (Donut-style): no boxes, decode answer directly
def donut_decode(image_patches, question, decoder):

while tokens[-1] != EOS:
logits = decoder(tokens, memory, question)
tokens.append(np.argmax(logits[-1])) # greedy decode
return detokenize(tokens)
