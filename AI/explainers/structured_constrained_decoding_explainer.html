1
Understanding Structured Decoding
▼

What is it? Large Language Models (LLMs) are designed to generate free-form text. However, for many applications (e.g., calling APIs, extracting data, generating code), we need the LLM's output to conform to a specific, machine-readable structure like JSON, XML, or a custom grammar. Structured decoding techniques ensure that the LLM's output strictly adheres to these rules, preventing malformed or invalid responses.

Why it's needed: Without structured decoding, LLMs often produce syntactically incorrect outputs (e.g., missing commas, unclosed brackets in JSON) or "hallucinate" extra fields. This breaks downstream parsing and automation. Structured decoding guarantees valid output, making LLMs reliable partners in automated workflows.

Analogy: Imagine a master chef (the LLM) who usually improvises magnificent dishes. Structured decoding is like handing the chef a very strict recipe (the grammar) and forcing them to follow it perfectly, ingredient by ingredient, step by step, ensuring the final dish (the output) is always exactly as specified, without any unexpected additions or omissions.

💡 If you remember one thing

Structured decoding works by actively constraining the LLM's vocabulary at each token generation step. Instead of letting the LLM pick any token, it's only allowed to choose tokens that maintain the validity of the output according to a predefined grammar. This is a "hard constraint," not just a "polite request" in the prompt.

2
How It Works Internally
▼

The Token Masking Process

At its core, structured decoding modifies the LLM's sampling process. For each token that the LLM is about to generate:

  1. The LLM computes a probability distribution (logits) over its entire vocabulary for the next token, given the preceding text.
  2. A grammar parser (often a finite state automaton, FSA) analyzes the current output prefix and the specified grammar. It determines precisely which tokens from the LLM's vocabulary are *syntactically valid* as the next token.
  3. A "mask" is applied to the LLM's logits: the logits of all *invalid* tokens are set to a very low negative number (effectively \(-\infty\)), making their probability zero after softmax.
  4. The LLM then samples (or deterministically picks) a token *only* from the remaining valid tokens.

This process repeats for every single token until the grammar indicates the output is complete.

JSON Mode: A Specialized Grammar

Many LLM APIs offer a dedicated "JSON mode." This is simply a pre-built, optimized grammar for the JSON specification. It ensures the output is always valid JSON, including handling nested objects, arrays, strings, numbers, booleans, and nulls. It's the most common form of structured decoding because JSON is ubiquitous for data exchange.

Grammar-Based (GBNF): The General Case

GBNF (Grammar-based Neural Format) is a generalized approach using a formal grammar syntax similar to Backus-Naur Form (BNF). Instead of a fixed JSON grammar, you provide a custom grammar that defines your desired output structure. This allows for:

  • Custom JSON schemas: e.g., "JSON where the 'name' field is always a string and 'age' is always an integer between 0 and 120."
  • Non-JSON formats: XML, CSV, specific programming language syntax (e.g., Python function definitions), or even simple constrained natural language.
The underlying mechanism of token masking remains the same, but the parser's logic is driven by your custom GBNF rules.

🔑 Key Property

The constraint is applied during generation, not after. Post-processing invalid output is inefficient (wasting LLM tokens on garbage) and often impossible to perfectly "fix." By masking logits, we ensure the LLM never even *considers* generating an invalid token, leading to 100% syntactically correct output.

3
Why It Works — The Math
▼

LLM's Probabilistic Output

An LLM generates text token by token. At each step \(k\), it computes a probability distribution over its vocabulary \(\mathcal{V}\) for the next token \(t_k\), given the preceding tokens \(t_1, \dots, t_{k-1}\):

$$P(t_k | t_1, \dots, t_{k-1}) = \frac{\exp(L_k)}{\sum_{t' \in \mathcal{V}} \exp(L_{t'})}$$

where \(L_k\) are the unnormalized log-probabilities (logits) for token \(t_k\).

Introducing the Constraint Function

Let's define a grammar-based constraint function \(C(t_1, \dots, t_k)\) which evaluates to 1 if the sequence \(t_1, \dots, t_k\) is a valid prefix according to the grammar, and 0 otherwise. This function is typically implemented by a parser that tracks the state of the grammar. To enforce the constraint, we modify the logits for the next token \(t_k\):

$$L'_k = \begin{cases} L_k & \text{if } C(t_1, \dots, t_{k-1}, t_k) = 1 \\ -\infty & \text{if } C(t_1, \dots, t_{k-1}, t_k) = 0 \end{cases}$$

This effectively sets the probability of any grammatically invalid next token to zero. The new, constrained probability distribution becomes:

$$P'(t_k | t_1, \dots, t_{k-1}) = \frac{\exp(L'_k)}{\sum_{t' \in \mathcal{V}} \exp(L'_{t'})}$$

The denominator now only sums over tokens \(t'\) that are valid according to the grammar, ensuring the probabilities still sum to 1 over the allowed subset of the vocabulary. This process ensures that the generated sequence \(t_1, \dots, t_N\) will always satisfy \(C(t_1, \dots, t_k)=1\) for all \(k\).

⚠️ Common Pitfall

Structured decoding does not guarantee the *semantic correctness* of the output, only its *syntactic validity*. An LLM might generate a valid JSON object like {"city": "banana", "temp": 5000}, which is syntactically perfect but semantically nonsensical. The grammar only dictates structure, not meaning.

Key Takeaways
▼

When to use structured decoding:

  • API Calls: When the LLM needs to generate arguments for a function call in a specific format (e.g., JSON).
  • Data Extraction: Extracting entities or information from unstructured text into a structured format.
  • Code Generation: Ensuring generated code snippets adhere to a language's syntax.
  • Form Filling: Generating responses that fit predefined fields and types.
  • Controlled Generation: Any scenario where the output must be machine-parseable and predictable.

When NOT to use / limitations:

  • Free-form text generation: For creative writing, open-ended chat, or summarization where flexibility is desired.
  • Semantic correctness: As noted, it doesn't guarantee the *meaning* is correct, only the *form*. LLMs can still hallucinate valid-looking but incorrect data.
  • Grammar complexity: Writing complex GBNF grammars can be challenging and error-prone, requiring careful debugging.
  • Performance overhead: Running the grammar parser at every token can add a small computational overhead, though often negligible compared to LLM inference.
💡 Big Picture

Structured decoding bridges the gap between the LLM's natural language capabilities and the structured world of software systems. It transforms LLMs from powerful text generators into reliable, programmable agents capable of interacting with APIs and databases with guaranteed format correctness.

import json
import re
import numpy as np
# --- Simplified GBNF Grammar (e.g., for {"city": "...", "temp": ...}) ---
# This would typically be a more sophisticated parser, e.g., using Lark or tree-sitter
GRAMMAR_RULES = {
"root": ["city_temp_object"],
"city_temp_object": [r"\{", r"\"city\"", r":", "string", r",", r"\"temp\"", r":", "number", r"\}"],
"string": [r"\"", "char_allowed*", r"\""],
"number": [r"-?", "digit+", r"(\." "digit+", r")?"],
"char_allowed": [r"[a-zA-Z0-9 ]"],
"digit": [r"[0-9]"],
"ws": [r" *"] # Whitespace rule
}
def get_valid_next_tokens(current_output: str, grammar_state) -> set[str]:
"""Determines valid next tokens based on current output and grammar state."""
# In a real system, this would involve a GBNF parser (FSA)
# that processes current_output and returns allowed characters/sub-tokens.
# For this conceptual example, we simulate it based on simple prefixes.
if not current_output: return {"{"}
if current_output == "{": return {" ", "\""}
if current_output == "{ \"city\"": return {" "}
if current_output == "{ \"city\" ": return {":"}
# ... many more rules ...
return {" "} # Fallback for demo
def mask_logits(logits: np.ndarray, vocab: list[str], valid_tokens: set[str]):
"""Sets logits of invalid tokens to -infinity."""
masked_logits = np.copy(logits)
for i, token in enumerate(vocab):
# This is a simplified check; real systems handle sub-word tokens.
if token not in valid_tokens:
masked_logits[i] = -np.inf # Effectively zero probability
return masked_logits
# --- Main generation loop ---
def generate_structured_output(llm_model, initial_prompt, grammar):
output = ""
grammar_state = grammar.initial_state() # Represents the parser's internal state
while not grammar_state.is_final():
# 1. Get raw logits from LLM
prompt = initial_prompt + output
raw_logits, vocab = llm_model.predict_next_token_logits(prompt)
# 2. Determine valid tokens based on grammar
valid_tokens = get_valid_next_tokens(output, grammar_state)
# 3. Mask invalid tokens
masked_logits = mask_logits(raw_logits, vocab, valid_tokens)
# 4. Sample (or argmax) from masked distribution
probabilities = np.exp(masked_logits) / np.sum(np.exp(masked_logits))
next_token_idx = np.random.choice(len(vocab), p=probabilities) # or np.argmax
next_token = vocab[next_token_idx]
output += next_token
grammar_state.update(next_token) # Advance parser state
return output
