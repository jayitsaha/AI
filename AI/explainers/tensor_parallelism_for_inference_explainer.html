Tensor Parallelism for Inference

Splitting large models across multiple GPUs to overcome memory limits and speed up inference

Understanding Tensor Parallelism
▼

What is it? Tensor parallelism (also known as model parallelism or intra-layer parallelism) is a technique to distribute the computations of a single neural network layer across multiple devices (e.g., GPUs). Instead of placing entire layers or duplicate models on different devices, tensor parallelism splits individual tensors (like weight matrices and activation vectors) into smaller chunks, allowing each device to process only a portion of the data and weights for a given operation. This is crucial for deploying very large models, such as large language models (LLMs), whose weights exceed the memory capacity of a single GPU.

Analogy: Imagine you have a massive, intricate tapestry (the LLM's weight matrix) that is too large for one person to hold or weave. Instead of having multiple people each weave an identical small tapestry (data parallelism) or different sections of the tapestry (pipeline parallelism), tensor parallelism means a team of weavers works *simultaneously on different parts of the same row or column* of the giant tapestry. Each weaver processes their assigned threads, and then they coordinate to combine their individual contributions into a complete row or column, before moving to the next part of the pattern.

💡 If you remember one thing

Tensor parallelism distributes the *components of a single operation* (typically matrix multiplications) across multiple devices. Each device holds a slice of the weights and computes a partial result, which then needs to be communicated and combined (e.g., concatenated or summed) to form the full layer output. This is essential for models whose total parameters or intermediate activations don't fit on one GPU.

2
How It Works Internally
▼

The Problem: Memory Walls for Large Models

Modern LLMs can have hundreds of billions or even trillions of parameters. A single 7B parameter model, stored in FP16 (2 bytes per parameter), requires 14 GB of memory for just its weights. Add activations, optimizer states (for training), and KV cache (for inference), and even a 24 GB GPU can quickly run out of memory. Tensor parallelism directly addresses this by splitting these large tensors across multiple GPUs, so no single GPU needs to hold the entire tensor.

Splitting Matrix Multiplications: Column vs. Row Parallel

The core of most neural network layers is a matrix multiplication: \(Y = XW + B\). Tensor parallelism focuses on how to split \(X\) (input activation), \(W\) (weight matrix), and \(B\) (bias vector) across \(P\) devices, and then combine the partial results.

  • Column Parallel (Output-split `W`): The weight matrix \(W\) is split column-wise (horizontally) into \(P\) sub-matrices: \(W = [W_1 | W_2 | \dots | W_P]\). Each \(W_i\) is placed on a different GPU. The input activation \(X\) is broadcast to all GPUs. Each GPU \(i\) computes \(Y_i = X W_i + B_i\). The partial outputs \(Y_i\) are then concatenated (an All-Gather communication operation) to form the full \(Y\). This is often used for the first linear layer in an MLP or attention block.
  • Row Parallel (Input-split `W`): The weight matrix \(W\) is split row-wise (vertically) into \(P\) sub-matrices: \(W = [W_1^\top | W_2^\top | \dots | W_P^\top]^\top\). The input activation \(X\) is also split column-wise (horizontally) into \(P\) sub-activations: \(X = [X_1 | X_2 | \dots | X_P]\). Each GPU \(i\) computes a partial product \(Z_i = X_i W_i\). These partial products \(Z_i\) are then summed (an All-Reduce communication operation) to get the final result \(Z = \sum Z_i\). This is typically used for the second linear layer in an MLP or attention block.

Design Decision: Minimizing Communication

Communication between GPUs (All-Gather, All-Reduce) is a major bottleneck. A common and efficient strategy, pioneered by Megatron-LM, is to alternate between column-parallel and row-parallel layers. If a column-parallel layer's output on GPU \(i\) is \(Y_i\), and the *next* layer is row-parallel, then \(Y_i\) can directly serve as the input slice \(X_i\) for the next layer on GPU \(i\), without an explicit All-Gather of \(Y\) and then a Split of \(X\). This "fused" pattern significantly reduces communication overhead.

🔑 Key Property

Tensor parallelism is fundamentally about distributing the *computation* of a single operation. For linear layers, this means splitting the weight matrix and carefully managing input activations and output partial sums/concatenations, with communication steps inserted strategically to preserve mathematical equivalence.

3
Why It Works — The Math
▼

The Core Operation: \(Y = XW + B\)

Consider a linear layer with input activation \(X \in \mathbb{R}^{B \times D_{in}}\), weight matrix \(W \in \mathbb{R}^{D_{in} \times D_{out}}\), and bias vector \(B \in \mathbb{R}^{1 \times D_{out}}\). The output is \(Y \in \mathbb{R}^{B \times D_{out}}\), where \(B\) is batch size. For inference, \(B=1\).

Column Parallel Linear Layer

Here, the output dimension \(D_{out}\) is split across \(P\) devices. The weight matrix \(W\) is split into \(P\) column slices, \(W_1, W_2, \dots, W_P\), where each \(W_p \in \mathbb{R}^{D_{in} \times (D_{out}/P)}\). The bias \(B\) is similarly split into \(B_p \in \mathbb{R}^{1 \times (D_{out}/P)}\). The input \(X\) is replicated (broadcast) to all \(P\) devices.

$$Y_p = X W_p + B_p \quad \text{for } p = 1, \dots, P$$

Each device \(p\) computes its partial output \(Y_p \in \mathbb{R}^{B \times (D_{out}/P)}\). To reconstruct the full output \(Y\), an All-Gather operation concatenates these partial outputs along the output dimension:

$$Y = \text{AllGather}(Y_1, \dots, Y_P) = [Y_1 | Y_2 | \dots | Y_P]$$

The full \(Y \in \mathbb{R}^{B \times D_{out}}\) is now available on all devices (or collected on a single device if needed for the next non-parallel operation).

Row Parallel Linear Layer

In this case, the input dimension \(D_{in}\) is split. The weight matrix \(W\) is split into \(P\) row slices, \(W_1, W_2, \dots, W_P\), where each \(W_p \in \mathbb{R}^{(D_{in}/P) \times D_{out}}\). The input activation \(X\) is also split into \(P\) column slices, \(X_1, X_2, \dots, X_P\), where each \(X_p \in \mathbb{R}^{B \times (D_{in}/P)}\). Each device \(p\) computes a partial product:

$$Z_p = X_p W_p \quad \text{for } p = 1, \dots, P$$

Each device \(p\) computes \(Z_p \in \mathbb{R}^{B \times D_{out}}\). To get the final result, these partial products are summed across all devices using an All-Reduce operation:

$$Y = \text{AllReduceSum}(Z_1, \dots, Z_P) + B = \sum_{p=1}^P Z_p + B$$

The full \(Y \in \mathbb{R}^{B \times D_{out}}\) is now available on all devices.

⚠️ Communication Overhead

Both Column Parallel and Row Parallel operations require communication. Column Parallel uses an All-Gather at the end of the operation, while Row Parallel uses an All-ReduceSum. These collective communication primitives are expensive, and their latency can dominate if not carefully managed or fused across layers. The optimal strategy minimizes these cross-device data transfers.

Key Takeaways
▼

When to use tensor parallelism:

  • Models too large for a single GPU: This is the primary driver. If the model's weights (and/or intermediate activations, especially the KV cache during inference) exceed VRAM, tensor parallelism is essential.
  • Maximizing throughput or minimizing latency for large models: By distributing computation, tensor parallelism can reduce the per-device compute load, leading to faster inference times, especially when combined with other parallelization strategies.
  • Specific architectures like Transformers: The highly modular nature of Transformer blocks (attention, MLPs) makes them well-suited for tensor parallelism, as operations within these blocks can be effectively split.

When NOT to use:

  • Small models: For models that easily fit on a single GPU, the overhead of communication between devices will outweigh any benefits.
  • When other parallelism types suffice: If data parallelism (for large batches) or pipeline parallelism (for deep models) can solve the problem without intra-layer splitting, they might be simpler to implement and manage.
  • High communication latency networks: Tensor parallelism relies heavily on fast inter-GPU communication (e.g., NVLink). If devices are connected over a slow network, the communication overhead can negate performance gains.
💡 Hierarchy & Combination

Tensor parallelism is often combined with other parallelization techniques. For instance, very large LLMs might use tensor parallelism (splitting layers) *within* each stage of a pipeline parallelism setup (splitting layers across devices in sequence), and then run multiple copies of this combined parallel model using data parallelism (splitting batches). This multi-dimensional approach is necessary for scaling to models with trillions of parameters.

Code Trace (PyTorch-like Pseudocode)
▼
import torch
import torch.nn as nn
import torch.distributed as dist
class ColumnParallelLinear(nn.Module):
def __init__(self, in_features, out_features, world_size):
super().__init__()
self.in_features = in_features
self.out_features_per_partition = out_features // world_size
self.weight = nn.Parameter(torch.randn(in_features, self.out_features_per_partition))
self.bias = nn.Parameter(torch.randn(self.out_features_per_partition))
def forward(self, input_):
# Input is replicated across all GPUs
# Local matrix multiplication (X @ W_p)
output_parallel = torch.matmul(input_, self.weight) + self.bias
# All-Gather: Concatenate partial outputs to get full output on all GPUs
output = torch.empty(input_.size(0), self.out_features_per_partition * dist.get_world_size(),
dtype=output_parallel.dtype, device=output_parallel.device)
dist.all_gather_into_tensor(output, output_parallel) # Y = [Y_1 | Y_2 | ... | Y_P]
return output
class RowParallelLinear(nn.Module):
def __init__(self, in_features, out_features, world_size):
super().__init__()
self.in_features_per_partition = in_features // world_size
self.out_features = out_features
self.weight = nn.Parameter(torch.randn(self.in_features_per_partition, out_features))
self.bias = nn.Parameter(torch.randn(out_features)) # Bias is not partitioned
def forward(self, input_):
# Input_ is already partitioned (e.g., from a previous ColumnParallel layer)
# Local matrix multiplication (X_p @ W_p)
output_parallel = torch.matmul(input_, self.weight)
# All-Reduce: Sum partial outputs to get full output on all GPUs
output = dist.all_reduce(output_parallel, op=dist.ReduceOp.SUM, async_op=False) # Z = sum(Z_p)
output = output + self.bias # Add bias after all-reduce
return output
