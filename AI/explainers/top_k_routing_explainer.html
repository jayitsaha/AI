Top-k Routing: Selecting k Experts per Token

The gating mechanism that makes sparse Mixture-of-Experts transformers compute-efficient
Foundational Sparse MoE LLM Systems O(k/N) compute
1
Understanding Top-k Routing
▼

What is it? In a sparse Mixture-of-Experts (MoE) transformer, the single dense feed-forward block is replaced by \(N\) parallel "expert" feed-forward networks plus a small router (gating network). For every token, the router does not run all \(N\) experts — it picks just the top \(k\) (usually \(k{=}1\) or \(k{=}2\)) experts whose gate score is highest, runs only those, and combines their outputs weighted by the (renormalized) gate values. The rest of the experts do nothing for that token.

Analogy: Think of a hospital triage desk. A large staff of specialists (the experts) is on call, but a patient (a token) doesn't see all of them — a triage nurse (the router) reads the symptoms and sends the patient to the 1 or 2 most relevant specialists. The hospital can afford to employ hundreds of specialists precisely because each patient only occupies two of their schedules, not all of them.

💡 If you remember one thing

Only \(k\) of \(N\) experts actually execute for each token: $$y = \sum_{i \,\in\, \text{TopK}(h(x))} g_i(x)\, E_i(x)$$ Total parameters scale with \(N\) (cheap to add — they just sit idle), but compute per token scales with \(k\) (expensive — this is what you pay for at inference time).

How Top-k Routing Works Internally
▼

The Gating Network (Router)

A router is nothing more than a small linear layer \(W_g \in \mathbb{R}^{d\times N}\) shared by every token. For a token representation \(x \in \mathbb{R}^d\), it produces one raw logit per expert: \(h(x) = xW_g \in \mathbb{R}^N\). These logits say "how relevant is expert \(i\) for this token" — nothing has been normalized or selected yet.

Softmax Over Experts

Passing \(h(x)\) through a softmax turns the \(N\) logits into a proper probability distribution over experts, \(G(x) \in \Delta^{N-1}\), where every expert gets a non-negative weight and all weights sum to 1. If routing stopped here, every expert would still have to run (just scaled by a small weight) — that's a dense MoE, and it buys you no compute savings.

Top-k Selection

The sparsity comes from a hard, non-differentiable step: keep only the \(k\) experts with the largest logits and mask everything else to \(-\infty\) before the (re)normalization. Only those \(k\) experts are ever dispatched to — the router's forward pass decides, for each token independently, exactly which \(k\) of the \(N\) expert FFNs will be invoked.

Weighted Combination

The chosen experts run on the token, and their outputs are combined using the renormalized gate weights (the \(k\) surviving weights are re-softmaxed so they sum to exactly 1, since the discarded experts contribute zero). This is why "renormalized" matters — without it, the combined output would be systematically too small.

Design Decision: Why Sparsity Saves Compute

A dense FFN layer costs \(O(N)\) expert-FLOPs per token because every expert runs. Top-k routing costs \(O(k)\) expert-FLOPs per token — the router adds a negligible \(O(N)\) matrix-vector product, but the (much larger) expert computation only happens \(k\) times instead of \(N\) times. This decouples parameter count (which can grow to hundreds of billions by adding more experts) from inference compute (which stays fixed at \(k\) experts' worth of FLOPs).

🔑 Key Property

Sparse scaling: total model capacity grows with \(N \times d_{ff}\) (nearly free — unused experts are just idle memory), while active compute per token grows only with \(k \times d_{ff}\). This is exactly how trillion-parameter MoE models run at the FLOP cost of a much smaller dense model.

Why It Works — The Math
▼

Router Logits and Softmax Gate

$$h(x) = x W_g \in \mathbb{R}^N \qquad G(x)_i = \operatorname{softmax}(h(x))_i = \frac{e^{h_i(x)}}{\sum_{j=1}^{N} e^{h_j(x)}}$$

Top-k Masking and Renormalized Gate

Define the top-k mask that keeps only the \(k\) largest logits:

$$\text{TopK}(h(x))_i = \begin{cases} h_i(x) & \text{if } h_i(x) \text{ ranks in the top } k \\ -\infty & \text{otherwise} \end{cases} \qquad G(x) = \operatorname{softmax}\big(\text{TopK}(h(x))\big)$$

Since \(e^{-\infty}=0\), softmax of the masked vector automatically renormalizes over exactly the \(k\) surviving experts. The final output sums only over the selected set:

$$y = \sum_{i \,\in\, \text{TopK}} G(x)_i \, E_i(x)$$

Noisy Top-k Gating (Shazeer et al., 2017)

Vanilla top-k routing is prone to always picking the same few experts, which starves the rest of training signal. Shazeer's "Outrageously Large Neural Networks" adds tunable Gaussian noise to the logits before the top-k is taken, so a token's selection is not perfectly deterministic during training:

$$h_i(x) = (xW_g)_i + \mathcal{N}(0,1)\cdot\operatorname{softplus}\big((xW_{noise})_i\big)$$

The noise magnitude is itself learned per expert, so the model can anneal exploration down over training while still occasionally letting under-used experts compete for tokens.

Load-Balancing Auxiliary Loss

Left unconstrained, the router tends to collapse: a few experts get all the traffic (and thus all the gradient updates and further reinforcement), while the rest are starved and stay undertrained. Switch Transformer adds a differentiable auxiliary loss that multiplies the fraction of tokens dispatched to each expert by the fraction of router probability mass it received, and encourages both to be uniform:

$$\mathcal{L}_{aux} = \alpha \cdot N \sum_{i=1}^{N} f_i \cdot P_i \qquad f_i = \tfrac{1}{T}\!\sum_t \mathbb{1}[\text{token } t \to \text{expert } i] \qquad P_i = \tfrac{1}{T}\!\sum_t G(x_t)_i$$

\(\mathcal{L}_{aux}\) is minimized (for fixed total mass) when every \(f_i = P_i = 1/N\) — i.e. traffic is perfectly balanced across experts. GShard uses a similar pair of terms it calls importance loss (squared coefficient-of-variation of total router probability per expert) and load loss (a differentiable surrogate for the actual token counts).

Capacity Factor and Token Dropping

Because each expert is typically a fixed-size buffer in a distributed system, it can only accept a maximum number of tokens per batch — its capacity:

$$\text{capacity} = \left\lceil \text{capacity\_factor} \times \frac{k \cdot T}{N} \right\rceil$$

If more tokens than that route to one expert, the overflow tokens are simply dropped for that expert — they skip its transformation entirely and pass forward only through the residual connection. A capacity factor \(>1\) (e.g. 1.25) gives experts slack to absorb imbalance without dropping too many tokens.

⚠️ Common Pitfall

Capacity factor is a tradeoff knob, not a free lunch: too low and heavily-loaded experts silently drop (and thus degrade) many tokens; too high and you waste memory/compute on padding and pay more all-to-all communication cost in expert-parallel training. The auxiliary loss reduces — but never eliminates — the need for capacity slack.

Key Takeaways
▼

Reference systems:

  • Switch Transformer (\(k{=}1\)): the simplest possible router — one expert per token. Halves routing communication versus \(k{=}2\) and needs no renormalization (a single softmax weight is used as-is), yet matches or beats \(k{=}2\) quality when paired with a careful aux loss and selective precision.
  • GShard (\(k{=}2\)): introduced random tie-breaking, an explicit capacity limit with token dropping, and the importance+load auxiliary losses at massive scale (up to thousands of experts) for machine translation.
  • Mixtral 8x7B (\(N{=}8\), \(k{=}2\)): a dense-equivalent LLM with ~46.7B total parameters but only ~12.9B active per token (~28%) — routing decouples how big the model is from how expensive each forward pass is.

Common pitfalls:

  • Router collapse / load imbalance: a few experts get reinforced early and hog all the traffic — the "rich get richer" failure mode this whole mechanism has to fight.
  • Training instability: router logits can grow unboundedly large; ST-MoE's "router z-loss" penalizes large logits to keep gating well-behaved.
  • Token dropping: a too-tight capacity factor silently degrades accuracy on the dropped tokens — they never see their intended expert.
  • Communication overhead: in expert-parallel training/serving, tokens must be shuffled (all-to-all) to the GPU that hosts their chosen expert — a real systems cost that grows with \(k\).
💡 Hierarchy

Dense FFN (\(k{=}N\), every expert always runs) \(\supset\) Top-k MoE (\(k \ll N\), sparse compute, needs load balancing) \(\supset\) Hard routing without noise/aux-loss (collapses in practice). Each step trades a little modeling freedom for a lot of compute efficiency — provided load balancing keeps all \(N\) experts trained.

import torch, torch.nn.functional as F
def moe_layer(x, W_g, experts, k=2, capacity_factor=1.25):
N = len(experts) # total experts
logits = x @ W_g # [N] router logits
if training: # noisy top-k gating
noise = randn_like(logits) * F.softplus(x @ W_noise)
logits = logits + noise
topk_val, topk_idx = logits.topk(k) # select k largest logits
gates = F.softmax(topk_val, dim=-1) # renormalized over chosen k
capacity = ceil(capacity_factor * k * T / N)
y = 0.0
for g, i in zip(gates, topk_idx):
if dispatched[i] >= capacity:
continue # token dropped -> residual only
y += g * experts[i](x) # only k experts actually run
dispatched[i] += 1
f = dispatch_fraction_per_expert() # load-balance stats
P = router_prob_per_expert.mean(0)
aux_loss = alpha * N * (f * P).sum() # Switch Transformer aux loss
return y, aux_loss
