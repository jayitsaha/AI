Understanding Reproducibility
▼

What is it? Reproducibility in machine learning is the ability to consistently obtain the same results from a computational experiment when using the same input data, code, and computational environment. It's about ensuring that if you or a colleague re-run your model training script, you get the exact same trained model and evaluation metrics every single time.

Analogy: Imagine a master chef's recipe. If you follow it precisely — using the exact ingredients, measurements, cooking temperature, and time — you expect to bake an identical cake every time. If you "just eyeball" the sugar, use a different brand of flour, or cook in a different oven, the cake might come out differently. In ML, the "ingredients" are data, the "recipe" is your code, and the "oven" is your computational environment. Reproducibility means controlling all these factors.

💡 If you remember one thing

Reproducibility is not just about scientific rigor; it's a practical necessity for debugging, collaboration, deployment, and validating research. It ensures that changes in your code lead to predictable changes in your results, rather than obscure, random fluctuations.

2
The Reproducibility Checklist
▼

1. Random Seeds

Most ML algorithms rely on pseudo-random number generators (PRNGs) for tasks like weight initialization, data shuffling, or dropout. Without setting a fixed "seed," these PRNGs start from a different point each time, leading to different random sequences and thus different results. It's crucial to set seeds for Python's random module, NumPy, and any deep learning framework (PyTorch, TensorFlow).

2. Environment Pinning

Your code doesn't run in a vacuum. It depends on specific versions of libraries (e.g., TensorFlow 2.10 vs 2.15), Python itself, CUDA drivers, and even the operating system. Minor version bumps can introduce changes in numerical operations or behavior. Environment pinning (e.g., using requirements.txt, Conda environments, or Docker containers) ensures that the exact software stack is recreated for every run.

3. Deterministic Operations

Even with seeds set, some operations, especially on GPUs, can be non-deterministic due to parallelization strategies or floating-point arithmetic differences. For example, certain CUDA convolution algorithms or atomic operations might not produce identical results across runs. Deep learning frameworks provide flags (e.g., PyTorch's torch.backends.cudnn.deterministic = True) to force deterministic behavior, often at a slight performance cost.

4. Config Files (Hydra, OmegaConf, etc.)

Hardcoding hyperparameters and other experiment settings (e.g., learning rate, model architecture, dataset paths) makes experiments fragile and non-reproducible. Accidental changes, or simply forgetting which exact parameters were used for a specific run, are common pitfalls. Using structured configuration files (YAML, JSON) managed by tools like Hydra or OmegaConf ensures that all parameters are explicitly defined, versioned, and easily loaded, making experiments transparent and repeatable.

🔑 Key Property

Reproducibility is a multi-layered problem. Addressing one source of non-determinism (e.g., setting seeds) won't guarantee full reproducibility if other sources (e.g., environment differences or non-deterministic GPU ops) are still active. A comprehensive approach is required.

3
Formalizing Reproducibility
▼

The Deterministic Function Principle

At its core, a reproducible ML experiment can be viewed as a deterministic function. Let \(f\) be the function representing your entire ML pipeline, from data loading to model evaluation. Its output \(O\) should be solely determined by its inputs \(I\).

$$O = f(I)$$

For reproducibility, we demand that if we run the pipeline twice with inputs \(I_1\) and \(I_2\), then \(I_1 = I_2 \implies O_1 = O_2\). The challenge lies in defining \(I\).

Deconstructing the Input \(I\)

The "input" to an ML experiment is far more than just the training data. It's a tuple of many components:

$$I = (D, C, E, H, S, P)$$

Where:

  • \(D\): Dataset (raw data, preprocessing steps, augmentations).
  • \(C\): Code (model architecture, training loop, loss functions, optimizer).
  • \(E\): Environment (OS, Python version, library versions, CUDA/cuDNN versions).
  • \(H\): Hardware (CPU/GPU model, number of cores/GPUs, memory).
  • \(S\): State (random seeds for all PRNGs).
  • \(P\): Parameters (hyperparameters, model configurations).

A change in *any* of these components can lead to a different output \(O\). The goal of a reproducibility checklist is to fix all components of \(I\) that are within our control.

Pseudo-Randomness and Seeds

A Pseudo-Random Number Generator (PRNG) is a deterministic algorithm that produces a sequence of numbers that appear random. Given an initial state, called the "seed," the sequence is entirely predictable:

$$R_k = \text{PRNG}(\text{seed}, k)$$

where \(R_k\) is the \(k\)-th "random" number. By fixing the seed, we ensure that the \(S\) component of \(I\) remains constant across runs. Without a fixed seed, \(S\) effectively becomes a random variable itself, making \(O\) non-deterministic.

⚠️ The "Irreducible Noise" Problem

Even with all practical measures, some minute variations can persist due to factors outside direct control, such as CPU instruction reordering, OS scheduler variations, or network I/O timing. For most ML tasks, these differences are negligible, but for extreme scientific precision, they can be a challenge. Reproducibility often refers to "bit-for-bit" identical results or "statistically identical" results.

5
Key Takeaways
▼

When to prioritize reproducibility:

  • Debugging: If results vary between runs, it's impossible to isolate whether a code change caused a bug or if it's just random noise.
  • Collaboration: Team members need to build on each other's work without encountering inconsistent baselines.
  • Deployment & Monitoring: Ensuring that a deployed model performs as expected and that retraining yields consistent results.
  • Scientific Research: Fundamental for validating experimental findings and allowing others to replicate results.
  • Hyperparameter Tuning: If your baseline is noisy, it's hard to tell if a hyperparameter change actually improved performance or if it was luck.

When to acknowledge limitations (and trade-offs):

  • Performance Cost: Forcing deterministic GPU operations (e.g., cuDNN) can sometimes be slower than their non-deterministic counterparts.
  • External Factors: True real-world randomness (e.g., new data streams, non-deterministic system calls beyond your control) is irreducible.
  • Approximate Reproducibility: For some exploratory tasks, minor floating-point differences or slight variations might be acceptable, focusing on statistical reproducibility rather than bit-for-bit.
💡 Rule of Thumb

Reproducibility is a spectrum, not a binary. Implement the checklist items incrementally, starting with random seeds and environment pinning, then adding deterministic ops and config files as your project matures and requires higher fidelity results. Always document your reproducibility efforts.

Code Trace: Implementing Reproducibility
▼

1. Setting Random Seeds (Python, NumPy, PyTorch)

import random
import numpy as np
import torch
def set_all_seeds(seed):
random.seed(seed)
np.random.seed(seed)
torch.manual_seed(seed)
torch.cuda.manual_seed_all(seed) # for multi-GPU
set_all_seeds(42)

2. Environment Pinning (requirements.txt)

Use pip freeze > requirements.txt to save exact versions. Recreate with pip install -r requirements.txt.

# requirements.txt example
torch==2.0.1+cu118
torchvision==0.15.2+cu118
numpy==1.24.3
pandas==2.0.3
scikit-learn==1.3.0
hydra-core==1.3.2

3. Forcing Deterministic Operations (PyTorch)

import torch
torch.backends.cudnn.deterministic = True
torch.backends.cudnn.benchmark = False # often recommended with deterministic
torch.use_deterministic_algorithms(True) # for certain CPU ops in PyTorch 1.8+
# Note: May incur performance penalty.
