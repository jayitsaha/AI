Understanding Pipeline Parallelism
▼

What is it? A large neural network has too many layers to fit on one GPU. Pipeline parallelism cuts the stack of layers into consecutive groups called "stages", and places each stage on a different device. Device 0 holds the first few layers, device 1 the next few, and so on. A single input has to pass through device 0, then device 1, then device 2, then device 3, in order — exactly like an assembly line.

Analogy: Think of a car factory with 4 stations: chassis, engine, paint, wheels. If you build one car completely before starting the next, three of the four stations sit idle while the fourth works. The factory only becomes efficient once several cars are moving through the line at once, each at a different station simultaneously. In pipeline parallelism, those "cars" are "micro-batches" — small slices of a training batch sent through the pipeline one after another so every device stays busy.

💡 If you remember one thing

Splitting layers across devices is easy; keeping every device busy is the hard part. The idle time created while the pipeline "fills" and "drains" is called the bubble, and its size is $$\text{bubble \%} = \frac{p-1}{m+p-1}$$ where \(p\) is the number of stages (devices) and \(m\) is the number of micro-batches per training step.

2
How It Works Internally
▼

Splitting the Model

Given \(L\) total layers and \(p\) devices, a partition function assigns a contiguous block of layers to each device — e.g. layers \([1..L/p]\) to device 0, \([L/p{+}1..2L/p]\) to device 1, and so on. Only activations (the output tensor of a stage) cross device boundaries during the forward pass, and only gradients with respect to those activations cross back during the backward pass. Weights never move.

The Naive Version — and Why It Is Slow

If you feed the whole batch through as ONE unit, device 1 cannot start until device 0 finishes, device 2 cannot start until device 1 finishes, and so on. During the forward pass only one device is ever active; the other \(p-1\) sit idle. The same happens in reverse during the backward pass. Utilization is only \(1/p\) — with 4 devices, 75% of the cluster's compute is wasted at any instant.

The Fix — Micro-batches

Split the mini-batch into \(m\) smaller micro-batches and stream them through the pipeline. As soon as device 0 finishes micro-batch 0's forward pass, it immediately starts on micro-batch 1's forward pass while device 1 works on micro-batch 0. This creates a diagonal "wavefront" of activity across the device-time grid — several devices busy at once, on different micro-batches.

Design Decision: GPipe (fill-then-drain) vs 1F1B (PipeDream)

The classic GPipe schedule runs all forward passes for all micro-batches first, then all backward passes. This is simple but forces every early stage to keep every micro-batch's activations in memory until the matching backward pass finally arrives — memory scales with \(m\). The 1F1B ("one-forward-one-backward") schedule interleaves forward and backward passes as early as dependencies allow, bounding the number of activations held in flight by roughly \(p\) instead of \(m\), at the same steady-state throughput.

🔑 Key Property

The pipeline bubble is a fill/drain cost paid once per training step, not per micro-batch. More micro-batches amortize that fixed cost over more useful work, shrinking the bubble fraction — but each micro-batch is smaller, so very large \(m\) can hurt per-device compute efficiency and increase communication overhead.

3
Why It Works — The Math
▼

Deriving the Bubble Fraction

Let \(p\) be the number of stages and \(m\) the number of micro-batches, and normalize the time to process one micro-batch through one stage (forward or backward) to 1 unit. The forward wave needs \(p-1\) steps to fill the pipeline plus \(m\) steps for the micro-batches to arrive at the last stage: \(T_{fwd} = m + p - 1\). The backward wave mirrors this: \(T_{bwd} = m + p - 1\). Total wall-clock time per training step:

$$T_{total} = 2(m + p - 1)$$

Each device performs \(m\) forward and \(m\) backward units of useful work, i.e. \(2m\) busy units, out of \(T_{total}\) total units. The idle (bubble) time per device is therefore:

$$T_{bubble} = T_{total} - 2m = 2(p-1)$$

Dividing idle time by total time gives the bubble fraction — the number quoted throughout this explainer:

$$\text{bubble \%} = \frac{T_{bubble}}{T_{total}} = \frac{2(p-1)}{2(m+p-1)} = \frac{p-1}{m+p-1}$$

As \(m \to \infty\) with \(p\) fixed, bubble % \(\to 0\): a big enough batch amortizes the fill/drain cost to nothing. As \(p\) grows with \(m\) fixed, the bubble fraction grows — more stages means more fill/drain relative to useful work, unless \(m\) is scaled up alongside \(p\).

⚠️ Common Pitfall

A smaller bubble is not free. Shrinking the bubble by increasing \(m\) means each micro-batch is smaller, which can drop per-GPU compute below the efficient matmul regime, and adds more cross-device communication rounds. In practice, engineers pick \(m\) as the smallest value that keeps the bubble acceptable (often \(m \approx 4p\) to \(8p\)) rather than the largest possible \(m\).

Key Takeaways
▼

When to use pipeline parallelism:

  • The model is too deep/large to fit on one device even after other tricks (mixed precision, activation checkpointing)
  • You have a fast interconnect between a small number of device groups (pipeline parallelism needs less bandwidth than tensor parallelism)
  • You can afford to tune micro-batch count \(m\) large enough (e.g. \(4p\)-\(8p\)) to keep the bubble small

When NOT to use / watch out for:

  • Very few micro-batches (\(m\) close to \(p\)) — the bubble dominates and utilization collapses
  • GPipe-style scheduling with huge \(m\) — peak activation memory grows linearly with \(m\), can blow the memory budget
  • Uneven layer partitioning — if one stage has much more compute than another, that stage becomes the bottleneck regardless of the schedule
💡 Hierarchy

Pipeline parallelism (split by layer) is one of three axes of model parallelism, alongside tensor parallelism (split a single layer's matmuls across devices) and data parallelism (split the batch, replicate the whole model). Modern large-scale training combines all three — "3D parallelism" — with pipeline parallelism used across the slowest interconnect (e.g. across nodes) because it needs the least communication per step.

# Simplified pipeline schedule simulator (GPipe "F-then-B" vs 1F1B)
def simulate(stages, microbatches, policy="gpipe"):
next_fwd = [0] * stages # next micro-batch idx ready to forward, per stage
next_bwd = [0] * stages # next micro-batch idx ready to backward, per stage
inflight = [0] * stages # activations currently held per stage
peak_mem = 0
t = 0
schedule = []
while any(next_bwd[s] < microbatches for s in range(stages)):
for s in range(stages):
fwd_ready = next_fwd[s] < microbatches and \
(s == 0 or next_fwd[s-1] > next_fwd[s])
bwd_ready = next_bwd[s] < microbatches and \
next_fwd[s] > next_bwd[s] and \
(s == stages - 1 or next_bwd[s+1] > next_bwd[s])
if policy == "gpipe": # always prefer forward
choice = "F" if fwd_ready else ("B" if bwd_ready else None)
else: # 1F1B: drain a backward first
choice = "B" if bwd_ready else ("F" if fwd_ready else None)
if choice == "F":
schedule.append((s, t, "F", next_fwd[s]))
next_fwd[s] += 1; inflight[s] += 1
peak_mem = max(peak_mem, inflight[s])
elif choice == "B":
schedule.append((s, t, "B", next_bwd[s]))
next_bwd[s] += 1; inflight[s] -= 1
t += 1
return schedule, t, peak_mem
# Live bubble fraction (closed form -- matches the simulation exactly)
bubble_pct = (stages - 1) / (microbatches + stages - 1)
