1
Understanding Serving Metrics
▼

What is serving? In machine learning, "serving" refers to deploying a trained model to make predictions (inferences) in a production environment. Users send requests, the model processes them, and returns a response. This process is governed by two critical metrics: throughput and latency.

Throughput: How many requests per second (RPS) the system can handle. A high-throughput system can process many requests concurrently or in quick succession. This is often limited by CPU/GPU capacity, memory bandwidth, or network I/O.

Latency: How long it takes to process a single request, from the moment it arrives until the response is sent. We often look at percentiles: P50 (median), P90 (90% of requests are faster than this), P99 (99% of requests are faster). P99 latency is crucial for user experience, as it captures the "worst-case" for most users.

Analogy: Imagine a popular restaurant. Throughput is how many meals they can serve per hour. Latency is how long a customer waits from ordering until their food arrives. If too many customers arrive at once, the kitchen (servers) gets overwhelmed, and customers (requests) start waiting in a long line (queue), increasing their latency. To maintain good service, the restaurant might hire more chefs (add more servers) or expand its kitchen (scale up infrastructure).

💡 If you remember one thing

Throughput and latency are inversely related under increasing load. For a fixed capacity, pushing for higher throughput inevitably increases latency due to queueing. Service Level Objectives (SLOs) define the acceptable balance.

2
Queueing, Saturation & Autoscaling
▼

The Role of Queues

When an incoming request arrives and all available servers are busy, the request doesn't disappear; it waits in a queue. The longer a request waits in the queue, the higher its total latency. As the request arrival rate approaches or exceeds the system's processing capacity, the queue grows indefinitely, and latency "explodes" towards infinity. This state is called saturation.

Little's Law (informally): For a stable system, the average number of requests in the system (queue + in-service) is equal to the average arrival rate multiplied by the average time a request spends in the system. This shows a fundamental link: to reduce time-in-system (latency) for a given arrival rate (throughput), you must reduce the number of requests waiting or being processed concurrently (by adding more capacity).

Autoscaling to Manage Load

Autoscaling is the dynamic adjustment of the number of active servers (or "replicas") in response to changing load. This is typically horizontal scaling: adding or removing identical server instances. Autoscalers monitor metrics like CPU utilization, request queue length, or (ideally) actual P99 latency, and then add servers if metrics exceed a threshold, or remove them if capacity is underutilized.

  • Scale Up: Add servers when demand increases or latency breaches an SLO.
  • Scale Down: Remove servers when demand decreases to save costs.

Design Decision: Why not just always over-provision?

Always having many idle servers ready for peak load is simple but expensive. Cloud resources are billed per-hour (or per-second), so over-provisioning wastes money. Autoscaling aims to optimize cost by matching capacity to demand, but it comes with its own challenges:

  • Cold Start: New servers take time to initialize (e.g., load model weights), introducing a temporary latency spike.
  • Threshing: Rapid, frequent scaling up and down can lead to instability.
  • Cost of Autoscaler: The autoscaling logic itself consumes resources and adds complexity.
🔑 Key Property

The fundamental tradeoff is between latency and cost. Autoscaling attempts to find the sweet spot, providing low latency when needed while minimizing idle resources. This is often expressed via Service Level Objectives (SLOs).

3
Why It Works — Queueing Theory Basics
▼

The Utilization Factor \(\rho\)

At the heart of queueing theory is the utilization factor, \(\rho\). It represents how busy your servers are. For a system with \(k\) identical servers, each capable of processing requests at an average rate of \(\mu\) (requests per unit time), and an overall arrival rate of \(\lambda\) requests per unit time:

$$\rho = \frac{\lambda}{k \cdot \mu}$$

Here, \(\frac{1}{\mu}\) is the average service time per request (how long one server takes to process one request). If \(\rho \ge 1\), the system is saturated: requests arrive faster than they can be processed, and the queue will grow infinitely long. For a stable system, we must have \(\rho < 1\).

Average Queueing Delay

The average time a request spends waiting in the queue, \(W_q\), is highly dependent on \(\rho\). For a simple single-server queue (M/M/1 model), the formula is:

$$W_q = \frac{\rho}{\mu(1-\rho)}$$

This formula illustrates the "knee" in the latency curve: as \(\rho\) approaches 1, the denominator \((1-\rho)\) approaches 0, causing \(W_q\) to skyrocket. For multiple servers (M/M/k model), the math is more complex but the qualitative behavior is the same: latency explodes as utilization approaches 100%.

Total Response Time (Latency)

The total latency for a request, \(T\), is the sum of its queueing delay and its actual service time, \(S\):

$$T = W_q + S$$

Since \(S = 1/\mu\), for an M/M/1 system, this becomes \(T = \frac{1}{\mu(1-\rho)}\). This shows that to keep latency low, we must keep \(\rho\) significantly below 1 (e.g., \(\rho < 0.8\)). If \(\lambda\) increases, we must increase \(k\) to keep \(\rho\) in check. This is precisely what autoscaling aims to do.

⚠️ Common Pitfall

Focusing only on average (P50) latency can be misleading. While average latency might be acceptable, P99 latency can be much higher due to occasional queueing spikes. SLOs should specify high percentiles (P90, P99) to ensure a good experience for almost all users.

Key Takeaways
▼

When to prioritize throughput vs. latency:

  • Latency-sensitive: User-facing applications (e.g., search, recommendations, real-time bidding). High P99 latency directly impacts user experience and conversion rates. Prioritize low latency, even if it means slightly lower peak throughput or higher cost.
  • Throughput-sensitive: Batch processing, offline analytics, data ingestion. Here, the total volume of work processed per hour is more important than individual request times. Higher throughput with acceptable average latency is the goal.

SLOs are crucial:

  • Define quantitative targets for latency (P90, P99), throughput, and error rates.
  • They align engineering efforts with business impact.
  • They provide clear signals for when to scale, optimize, or alert.

Autoscaling is a powerful tool, but not a silver bullet:

  • Benefits: Cost optimization, automatic responsiveness to load spikes, improved reliability.
  • Limitations: Cold start latency, potential for "thrashing" (rapid scale up/down), difficulty predicting highly volatile or spiky traffic patterns, and the overhead of the autoscaler itself.
  • Considerations: Choose appropriate metrics (CPU, queue depth, or actual latency), tune thresholds carefully, and implement cooldown periods to prevent instability.
💡 Rule of Thumb

For most interactive ML serving, latency (especially P99) is king. Users notice slow responses. Throughput is a constraint you try to meet *while* maintaining latency SLOs. Autoscaling is the primary mechanism to achieve this balance in dynamic cloud environments.

import time, random, collections
class Request:
def __init__(self, arrival_time):
self.arrival_time = arrival_time
self.start_service_time = None
self.finish_time = None
class Server:
def __init__(self, id):
self.id = id
self.is_busy = False
self.finish_processing_at = 0
self.current_request = None
def simulate_step(current_time, queue, servers, arrival_rate, service_time_mu):
# 1. New requests arrive (Poisson process approximation)
num_arrivals = random.poisson(arrival_rate / 1000) # per ms
for _ in range(num_arrivals):
queue.append(Request(current_time))
# 2. Servers process requests
for server in servers:
if server.is_busy and current_time >= server.finish_processing_at:
server.current_request.finish_time = current_time
# completed_requests.append(server.current_request) # Store for latency stats
server.is_busy = False
server.current_request = None
if not server.is_busy and queue:
req = queue.popleft()
server.current_request = req
server.is_busy = True
req.start_service_time = current_time
# Service time is ~Gaussian around service_time_mu
service_duration = max(1, random.gauss(service_time_mu, service_time_mu * 0.1))
server.finish_processing_at = current_time + service_duration
def autoscaler_logic(current_latency_p90, current_servers, slo_target_ms, scale_up_factor=1.2, scale_down_factor=0.8, cooldown_steps=10):
global last_scale_action_time, autoscaler_cooldown_period
if time.time() - last_scale_action_time < autoscaler_cooldown_period:
return current_servers # Cooldown in effect
if current_latency_p90 > slo_target_ms * 1.1: # 10% buffer for scale up
new_servers = int(current_servers * scale_up_factor)
print(f"Latency breach ({current_latency_p90}ms), scaling up to {new_servers} servers.")
last_scale_action_time = time.time()
return max(current_servers + 1, min(10, new_servers)) # Cap at 10, min +1
elif current_latency_p90 < slo_target_ms * 0.5 and current_servers > 1: # Scale down if well below SLO
new_servers = int(current_servers * scale_down_factor)
print(f"Latency low ({current_latency_p90}ms), scaling down to {new_servers} servers.")
last_scale_action_time = time.time()
return max(1, new_servers) # Min 1 server
return current_servers
