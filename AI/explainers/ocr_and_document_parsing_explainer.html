Understanding OCR & Document Parsing
▼

What is it? Optical Character Recognition (OCR) turns pixels into text. But a scanned invoice or form isn't just "text" — it's text arranged in a specific spatial structure: a title, an address block, a table of line items. Document parsing goes further than plain OCR: it must (1) find where text lives on the page (detection), (2) figure out what the characters say (recognition), and (3) reconstruct how the pieces relate — reading order, paragraphs, table cells, key-value fields (layout/structure parsing).

Analogy: Imagine handing a photo of a filled-out form to someone who has never seen a form before. They first need to notice "there's ink here, here, and here" (detection) — like circling regions with a highlighter. Then they need to sound out each circled region into words (recognition) — like a child learning to read. Finally they need to figure out the form's logic: "this label goes with that value, these three lines are one paragraph, read top-to-bottom then left-to-right" (structure parsing) — like assembling a jigsaw puzzle back into a coherent story.

Summary: Modern OCR pipelines are two-stage (detect boxes, then recognize text inside each box via a CTC or attention decoder) or increasingly single-stage / OCR-free, where a vision-encoder-to-text-decoder transformer (e.g., Donut) reads the raw image and emits structured text directly, skipping explicit box detection entirely.

💡 If you remember one thing

OCR is three separable problems wearing one name: where (detection — a bounding-box regression problem), what (recognition — a sequence-labeling problem, classically solved with CTC), and how it's organized (layout parsing — a reading-order / graph problem). State-of-the-art systems either chain specialized models for each, or replace all three with one end-to-end vision-to-text transformer.

How the Pipeline Works Internally
▼

Stage 1 — Text Detection

A detector (e.g., DBNet, EAST, or a Faster-R-CNN/YOLO variant) runs a CNN backbone over the page and predicts, for every pixel or anchor, a probability of being text plus a geometry regression (box offsets or a text/border segmentation map). Because a single line of text can trigger many overlapping candidate boxes, detectors emit a dense proposal set that must be pruned via Non-Maximum Suppression (NMS): sort proposals by confidence, keep the top box, discard any remaining box whose Intersection-over-Union (IoU) with it exceeds a threshold, repeat.

Stage 2 — Recognition (CTC / seq2seq)

Each detected box is cropped, rectified (de-skewed/de-warped so the text baseline is horizontal), and resized to a fixed height. A CNN extracts a feature map that is sliced into a left-to-right sequence of columns; an RNN or Transformer encoder turns this into a sequence of per-timestep logits over the character vocabulary plus a special blank token. Two decoding families dominate: CTC (Connectionist Temporal Classification — assumes conditional independence between timesteps but trains without needing character-level alignment) and attention/seq2seq decoders (autoregressive, can model output dependencies but are slower and can "hallucinate" repeated or dropped characters).

Stage 3 — Layout & Reading-Order Parsing

Once every box has a recognized string, the boxes must be ordered and grouped. A geometric heuristic clusters boxes into text lines by vertical (y-axis) overlap, sorts lines top-to-bottom, and sorts boxes within a line left-to-right — this recovers simple reading order. For genuinely complex documents (multi-column pages, tables, forms) this heuristic breaks, so modern systems use a learned layout model (e.g., LayoutLM, a graph neural network over boxes, or a reading-order transformer) that consumes box coordinates + recognized text + visual features jointly.

Design Decision: Why Split Detection from Recognition?

Splitting lets each stage use an architecture suited to its geometry: detection is a dense, translation-equivariant pixel task (CNNs excel here); recognition is a 1-D sequence task (RNN/Transformer excel here). The cost is error propagation — a missed detection can never be recovered by the recognizer. This motivates OCR-free architectures like Donut (Document Understanding Transformer), which replace the entire detect→recognize→parse chain with a single vision encoder (Swin Transformer) feeding an autoregressive text decoder that emits structured tokens (e.g., XML/JSON-like key-value pairs) directly from pixels — no bounding boxes, no separate OCR engine at all.

🔑 Key Property

CTC's core trick is marginalizing over all possible alignments between a fixed-length frame sequence and a variable-length label sequence, using a blank token to absorb "no new character here" frames and to separate repeated adjacent characters (so "hello" doesn't collapse to "helo"). This lets the network be trained end-to-end from (image, text) pairs with no frame-level character labels.

Why It Works — The Math (CTC & Reading Order)
▼

CTC Loss: Summing Over Alignments

Let the encoder produce \(T\) timesteps, each a distribution \(y_t\) over the alphabet \(\Sigma \cup \{\text{blank}\}\). Define the many-to-one collapse map \(\mathcal{B}\), which deletes blanks and merges consecutive repeats, e.g. \(\mathcal{B}(\text{"a-ab-"}) = \text{"aab"}\). For target label \(\ell\), CTC defines the probability of that label as a sum over every path (raw frame-level sequence) \(\pi\) that collapses to it:

$$p(\ell \mid x) = \sum_{\pi \, : \, \mathcal{B}(\pi) = \ell} \prod_{t=1}^{T} y_t(\pi_t)$$

This sum is over exponentially many paths, but it factorizes along a trellis, so it is computed efficiently with a forward-backward dynamic program (like the forward algorithm for HMMs) in \(O(T \cdot |\ell|)\) time. The training loss is the negative log-likelihood:

$$\mathcal{L}_{CTC} = -\log p(\ell \mid x)$$

Greedy (Best-Path) Decoding — What the Diagram Shows

At inference, exact best-label decoding is intractable, so most systems use greedy decoding: take the arg-max character at every timestep independently, forming a raw path \(\pi^g = \arg\max_t y_t\), then apply the same collapse \(\mathcal{B}(\pi^g)\):

$$\hat{\ell} = \mathcal{B}\big(\arg\max_{\pi_1}y_1,\, \dots,\, \arg\max_{\pi_T}y_T\big)$$

This is an approximation (the true best label may need a non-greedy path), but it is \(O(T)\) and works well in practice; beam search over the trellis recovers most of the remaining gap.

Reading-Order as a Sorting Problem

Given detected boxes \(\{b_i = (x_i, y_i, w_i, h_i)\}\), naive reading order sorts by \(y_i\) then \(x_i\). This fails when two boxes are on the "same visual line" but have slightly different \(y\) (skew, uneven baselines). The robust version clusters boxes into lines using a tolerance band: two boxes belong to the same line if their vertical centers differ by less than \(\alpha \cdot \max(h_i, h_j)\) for a small \(\alpha\) (e.g., 0.5), then sorts clusters by mean \(y\), and boxes within a cluster by \(x\). This is exactly the algorithm the interactive diagram runs live on the invoice boxes.

⚠️ Common Pitfall

CTC's conditional-independence assumption between timesteps means it cannot directly model output-language dependencies (e.g., that "Q" is almost always followed by "U"). This is why CTC recognizers are often paired with an external language model at decode time, or replaced by attention-based seq2seq decoders when strong linguistic priors matter. Greedy CTC decoding can also produce "sticky" errors: a single low-confidence blank can merge two characters that should stay separate.

Key Takeaways
▼

When to use the classic detect → recognize → parse pipeline:

  • You need precise bounding boxes (redaction, highlighting, click-to-verify UIs)
  • Documents vary wildly in layout and you need a general-purpose, inspectable detector
  • You need to swap in domain-specific recognizers (handwriting, receipts, license plates)

When to use OCR-free / end-to-end transformers (e.g., Donut, Pix2Struct):

  • The task is really "extract these fields" (key-value/JSON), not "get every box"
  • You want to avoid compounding detection + recognition errors
  • Training data is (image, structured-text) pairs rather than (image, box, char) triples
💡 Hierarchy

Detection (where) → Recognition (what, via CTC or attention) → Layout parsing (how it's organized) are three independently-solvable sub-problems in classic OCR. OCR-free transformers collapse all three into one learned mapping from pixels to structured text, trading interpretability and localizability for simplicity and fewer compounding errors.

def iou(a, b):
xA, yA = max(a.x, b.x), max(a.y, b.y)
xB, yB = min(a.x+a.w, b.x+b.w), min(a.y+a.h, b.y+b.h)
inter = max(0, xB-xA) * max(0, yB-yA)
union = a.w*a.h + b.w*b.h - inter
return inter / union if union > 0 else 0
