Understanding FP-Growth
▼

What is it? FP-Growth (Frequent-Pattern Growth) finds every set of items that co-occurs often enough across a transaction database — the same job Apriori does, but without ever building or testing candidate itemsets. It compresses the whole database into a single compact tree (the FP-tree) that shares repeated prefixes, then recursively mines that tree by peeling off one item at a time.

Analogy: Imagine writing down every shopping basket as a path through a shared trie, letter by letter, where popular items sit near the trunk and rare ones sit out on the branches. Instead of asking "does {bread, milk, eggs} occur often enough?" for every possible triple (Apriori's approach), FP-Growth asks the tree directly: "show me every path that ends in eggs" — and reads the answer off the branches instead of guessing and checking.

💡 If you remember one thing

FP-Growth scans the database exactly twice — once to count item frequencies, once to build the tree — and then mines all frequent itemsets recursively from that tree, generating zero candidate itemsets along the way. Everything downstream of the two scans is pure tree traversal.

2
How FP-Growth Works Internally
▼

Two Scans, One Tree

Scan 1 counts the support of every item in the database. Items below the minimum support threshold min_sup are discarded, and the survivors are sorted by descending frequency into the F-list — the canonical item order used everywhere downstream.

Scan 2 revisits every transaction, drops its infrequent items, reorders what remains to match the F-list, and inserts that ordered item sequence into the FP-tree one item at a time: if a child node for the current item already exists, its count is simply incremented; otherwise a brand-new child node is created. Because every transaction is sorted the same way, transactions that share a frequent prefix (like "milk, bread, …") walk down the same path and merge, which is what keeps the tree small.

Header Table & Node-Links

Every distinct item in the tree also gets one entry in a header table, pointing to its first occurrence. Each node of that item then links to the next node of the same item anywhere else in the tree — a node-link chain. Following an item's chain from the header table visits every node for that item in the whole tree without ever having to rescan the tree from the root, which is exactly what mining needs.

🔑 Design decision — why sort by descending frequency?

Putting the most frequent items closest to the root maximizes prefix sharing: popular items are far more likely to appear together near the top of many transactions, so ordering by frequency keeps the tree as compact as possible — often a fraction of the size of the raw database.

3
Why It Works — Conditional Pattern Bases & Recursive Mining
▼

Conditional Pattern Base

To find every frequent itemset that ends in some item \(z\), follow \(z\)'s node-link chain. For each node of \(z\), walk from that node up to (but not including) the root, recording the path of items with a weight equal to \(z\)'s count at that node. The multiset of all such weighted paths is \(z\)'s conditional pattern base — every prefix that ever co-occurred with \(z\), read straight off the tree.

Conditional FP-Tree & Recursion

Re-count the items inside \(z\)'s conditional pattern base and keep only those that are still \(\ge\) min_sup within that sub-problem. Build a brand-new, usually much smaller, conditional FP-tree from just those weighted paths. Then recurse: mine that conditional tree exactly the same way, prefixing every pattern it produces with \(z\). The base case is a conditional tree that is empty (no more frequent extensions) or a single path (every subset of that path, combined with the suffix built so far, is immediately frequent with support equal to the minimum count along the chosen items).

$$\text{support}(\{z\}\cup S)=\sum_{\text{node } n \text{ of } z} n.\text{count} \quad\text{restricted to paths containing all items in } S$$

From Itemsets to Association Rules

Once the frequent itemsets are known, generating rules is arithmetic, not search: for a frequent itemset \(Z\) and a split \(Z = X \cup Y\), the rule \(X \Rightarrow Y\) has confidence \(\text{support}(Z)/\text{support}(X)\) — both supports were already computed while mining, so no extra database pass is needed.

⚠️ Common Pitfall

FP-Growth's efficiency depends on the tree staying compact. On very sparse, high-cardinality data (few shared prefixes — e.g. near-unique baskets) the conditional trees stop shrinking and the recursion can approach Apriori's cost. It shines specifically on dense, correlated data such as retail baskets, clickstreams, or web logs.

Key Takeaways
▼

When FP-Growth wins:

  • Dense, correlated transaction data (market baskets, clickstreams, web logs) where transactions share long prefixes
  • Low min_sup thresholds, where Apriori's candidate explosion is worst
  • Repeated mining at different thresholds — the tree is built once and reused

When it's less ideal:

  • Extremely sparse, high-dimensional data with almost no shared prefixes — the tree barely compresses anything
  • The full FP-tree itself doesn't fit in memory (array-based / top-down variants exist for this case)
  • Only a handful of itemsets are needed — a targeted search may be cheaper than building the whole tree
💡 Apriori vs. FP-Growth

Apriori generates candidates level-by-level and re-scans the database once per level (generate-and-test). FP-Growth scans the database exactly twice, compresses it into a tree, and mines it by divide-and-conquer recursion over shrinking conditional trees — same correctness guarantee, dramatically less repeated work.

Code Trace
▼
# Scan 1: count support of every item
counts = {}
for t in transactions:
for item in t:
counts[item] = counts.get(item, 0) + 1
# Keep frequent items, sort by support desc (F-list)
f_list = sorted([i for i in counts if counts[i] >= min_sup],
key=lambda i: (-counts[i], i))
# Scan 2: insert each transaction into the FP-tree
def insert(items, node, header):
if not items: return
first, rest = items[0], items[1:]
if first in node.children:
node.children[first].count += 1
else:
node.children[first] = Node(first, 1, node)
header[first].append(node.children[first])
insert(rest, node.children[first], header)
root, header = Node(None, 0, None), defaultdict(list)
for t in transactions:
ordered = [i for i in f_list if i in t]
insert(ordered, root, header)
# Recursively mine conditional pattern bases
def mine(header, order, suffix, results):
for item in reversed(order):
support = sum(n.count for n in header[item])
results.append((suffix + [item], support))
base = conditional_pattern_base(item, header)
sub_order = frequent_items(base, min_sup)
if sub_order:
mine(build_tree(base, sub_order), sub_order, suffix + [item], results)
