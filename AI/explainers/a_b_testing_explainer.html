Understanding Experimentation
▼

What is it? A/B testing is a controlled experiment to compare two versions (A and B) of a product feature, webpage, or marketing campaign to determine which performs better on a specific metric. By randomly assigning users to experience either version, we can infer a causal link between the change and the observed outcome.

Analogy: Imagine two chefs trying out a new ingredient for their signature dish. Chef A uses the traditional ingredient (Control), while Chef B uses the new one (Treatment). To know if the new ingredient truly improves the dish, they need to gather feedback from a sufficient number of taste-testers. If they ask too few, any perceived difference might just be luck. If they keep asking indefinitely, they waste time and ingredients. A/B testing helps them determine the right number of testers and when to make a confident decision.

💡 If you remember one thing

A/B tests are designed to establish causality. They are hypothesis tests where we assume no difference (the null hypothesis) and collect evidence to see if we can confidently reject that assumption in favor of an alternative (that a difference exists).

Core Principles & Challenges
▼

The A/B Testing Workflow

A typical A/B test involves these steps:

  1. Define Metric: Choose a quantifiable success metric (e.g., click-through rate, conversion rate, revenue per user).
  2. Formulate Hypotheses:
    • Null Hypothesis (\(H_0\)): There is no difference between A and B. (\(p_A = p_B\))
    • Alternative Hypothesis (\(H_1\)): There is a difference between A and B. (\(p_A \ne p_B\))
  3. Calculate Sample Size: Determine how many users are needed to detect a meaningful difference with desired confidence.
  4. Random Assignment: Randomly split users into Control (A) and Treatment (B) groups.
  5. Collect Data: Run the experiment for the calculated duration, collecting data on the chosen metric.
  6. Analyze Results: Use statistical tests (e.g., Z-test) to calculate a p-value and confidence intervals.
  7. Decision: Based on the p-value and pre-defined significance level, decide whether to reject \(H_0\).

Key Parameters for Sample Size

The required sample size for an A/B test depends on:

  • Significance Level (\(\alpha\)): The probability of making a Type I error (false positive, rejecting \(H_0\) when it's true). Commonly 0.05.
  • Statistical Power (\(1-\beta\)): The probability of correctly rejecting \(H_0\) when \(H_1\) is true (avoiding a Type II error, false negative). Commonly 0.80.
  • Minimum Detectable Effect (MDE): The smallest difference between A and B that is considered practically significant. Smaller MDEs require larger sample sizes.
  • Baseline Conversion Rate (\(p_A\)): The expected performance of the control group.

Beyond Fixed-Horizon A/B: Sequential Testing & MABs

Standard A/B tests run for a fixed duration. However, this has limitations:

  • The "Peeking Problem": Repeatedly checking results before the experiment ends inflates the Type I error rate, leading to false positives.
  • Resource Waste: If an A/B test is clearly winning or losing early, continuing to run it to full sample size wastes time and potentially revenue.

Sequential testing addresses the peeking problem by adjusting the decision boundaries over time. Multi-armed bandits (MABs) go a step further, dynamically allocating more traffic to better-performing variants during the experiment, balancing "exploration" (trying all options) and "exploitation" (using the best option found so far).

🔑 Key Property

A well-designed A/B test minimizes the risk of drawing wrong conclusions. Sample size calculation is crucial for ensuring sufficient power to detect a meaningful effect, while sequential testing and MABs offer ways to manage risk and resources more efficiently over time.

Why It Works — The Core Equations
▼

1. Sample Size Calculation (for proportions)

To determine the minimum number of users needed per group (\(n\)) for a two-sample proportion test, given \(\alpha\), \(1-\beta\), baseline \(p_A\), and MDE \(p_B - p_A\):

$$n = \frac{(Z_{1-\alpha/2} \sqrt{p_A(1-p_A) + p_B(1-p_B)} + Z_{1-\beta} \sqrt{p_B(1-p_B)})^2}{(p_B - p_A)^2}$$

A simplified version often used for quick estimates assumes \(p_A \approx p_B \approx \bar{p}\):

$$n = \frac{2 \cdot (Z_{1-\alpha/2} + Z_{1-\beta})^2 \cdot \bar{p}(1-\bar{p})}{\text{MDE}^2}$$

Here, \(Z_x\) is the \(x\)-th quantile of the standard normal distribution (e.g., \(Z_{0.975} \approx 1.96\) for \(\alpha=0.05\), \(Z_{0.80} \approx 0.84\) for power \(0.80\)).

2. Z-test for Difference in Proportions

Once data is collected, we calculate the observed proportions \(\hat{p}_A = \text{conversions}_A / n_A\) and \(\hat{p}_B = \text{conversions}_B / n_B\). The test statistic for the difference in proportions is:

$$Z = \frac{(\hat{p}_B - \hat{p}_A)}{\sqrt{\hat{p}(1-\hat{p})(1/n_A + 1/n_B)}}$$

where \(\hat{p} = (\text{conversions}_A + \text{conversions}_B) / (n_A + n_B)\) is the pooled proportion under the null hypothesis. We then compare this \(Z\) value to the critical \(Z_{1-\alpha/2}\) value or compute a p-value.

3. Multi-Armed Bandits: UCB1 Algorithm

For a multi-armed bandit with \(K\) arms, the Upper Confidence Bound (UCB1) algorithm selects arm \(A_t\) at time \(t\) as:

$$A_t = \arg\max_{j \in \{1, \dots, K\}} \left[ \bar{X}_j(t) + \sqrt{\frac{2 \ln t}{N_j(t)}} \right]$$

where \(\bar{X}_j(t)\) is the average reward (e.g., conversion rate) of arm \(j\) up to time \(t\), and \(N_j(t)\) is the number of times arm \(j\) has been pulled. The second term is the "exploration bonus," which encourages trying less-pulled arms or arms with high uncertainty. Other MAB algorithms like epsilon-greedy use different exploration strategies.

⚠️ Common Pitfall

The sample size calculation and Z-test assume a fixed horizon. If you repeatedly check (or "peek") at your A/B test results and stop early when a boundary is crossed, you drastically inflate your actual Type I error rate. This means you'll declare a winner more often than your chosen \(\alpha\) level suggests, leading to false positives. Sequential testing and MABs are designed to mitigate this, but come with their own trade-offs.

Key Takeaways
▼

When to use each method:

  • Fixed-Horizon A/B Testing:
    • Pros: Provides clear statistical guarantees (p-values, confidence intervals) for a causal effect. Widely understood and accepted.
    • Cons: Inefficient if effects are very large or very small. Susceptible to the "peeking problem" if not run to full sample size.
    • Best for: Precise causal inference, validating critical product changes, situations where Type I error control is paramount.
  • Sequential Testing:
    • Pros: Allows early stopping, saving time and resources. Maintains Type I error control despite continuous monitoring.
    • Cons: More complex to set up. Can have lower power for small effects compared to a fixed-horizon test of the same duration.
    • Best for: Experiments where early detection of strong effects (positive or negative) is valuable, or when resources (time, traffic) are limited.
  • Multi-Armed Bandits (MABs):
    • Pros: Maximizes cumulative reward during the experiment by dynamically allocating traffic to better-performing variants. Automatically balances exploration and exploitation.
    • Cons: Does not provide traditional p-values or confidence intervals for causal inference. More complex to analyze for long-term effects.
    • Best for: Optimization problems (e.g., ad serving, recommendation engines), many-variant tests, scenarios where maximizing immediate reward is prioritized over precise statistical inference.

General Considerations:

  • Sample Size is King: For any hypothesis test, ensure you have enough data to detect a meaningful effect with sufficient power.
  • Randomization: Proper randomization is fundamental to ensure groups are comparable and to attribute observed differences to the variant, not confounding factors.
  • Choose Wisely: The best experimentation strategy depends on your goals (causal inference vs. optimization), available resources, and risk tolerance.
💡 Big Picture

Experimentation methods represent a spectrum of trade-offs between statistical rigor (A/B testing) and adaptive optimization (Multi-Armed Bandits). Understanding these trade-offs allows you to select the right tool for the right problem, maximizing learning and impact.

import numpy as np
from scipy.stats import norm
def calculate_sample_size(pA, MDE, alpha=0.05, power=0.80):
# MDE is absolute difference: pB = pA + MDE
pB = pA + MDE
if pB >= 1 or pB <= 0: return np.inf # Invalid pB
Z_alpha = norm.ppf(1 - alpha / 2)
Z_beta = norm.ppf(power)
# Standard error under H0 (pooled p) and H1 (individual pA, pB)
pooled_p = (pA + pB) / 2
std_err_H0 = np.sqrt(2 * pooled_p * (1 - pooled_p))
std_err_H1 = np.sqrt(pA * (1 - pA) + pB * (1 - pB))
# Formula for sample size per group
n = (Z_alpha * std_err_H0 + Z_beta * std_err_H1)**2 / (MDE**2)
return int(np.ceil(n))
def run_z_test(nA, convA, nB, convB):
if nA == 0 or nB == 0: return 1.0, 0, 0 # p-value, diff, CI
pA_hat = convA / nA
pB_hat = convB / nB
diff = pB_hat - pA_hat
# Pooled proportion for standard error under H0
pooled_p_hat = (convA + convB) / (nA + nB)
se_diff_H0 = np.sqrt(pooled_p_hat * (1 - pooled_p_hat) * (1/nA + 1/nB))
Z_score = diff / se_diff_H0
p_value = 2 * (1 - norm.cdf(abs(Z_score))) # Two-tailed
# Confidence Interval for the difference (using unpooled SE)
se_diff_unpooled = np.sqrt(pA_hat*(1-pA_hat)/nA + pB_hat*(1-pB_hat)/nB)
Z_critical = norm.ppf(1 - 0.05 / 2) # For 95% CI
ci_lower = diff - Z_critical * se_diff_unpooled
ci_upper = diff + Z_critical * se_diff_unpooled
return p_value, diff, ci_lower, ci_upper
class UCB1Bandit:
def __init__(self, n_arms):
self.n_arms = n_arms
self.counts = np.zeros(n_arms) # N_j(t)
self.rewards = np.zeros(n_arms) # sum of rewards for arm j
self.avg_rewards = np.zeros(n_arms) # X_bar_j(t)
self.total_pulls = 0 # t
def select_arm(self):
# Play each arm once initially to get non-zero counts
if self.total_pulls < self.n_arms:
return self.total_pulls
ucb_values = self.avg_rewards + np.sqrt(
2 * np.log(self.total_pulls) / self.counts
)
return np.argmax(ucb_values)
def update(self, chosen_arm, reward):
self.counts[chosen_arm] += 1
self.rewards[chosen_arm] += reward
self.avg_rewards[chosen_arm] = self.rewards[chosen_arm] / self.counts[chosen_arm]
self.total_pulls += 1
