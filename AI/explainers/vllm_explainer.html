Understanding Paged Attention
▼

What is it? When large language models (LLMs) generate text, they need to store a "Key-Value (KV) cache" for each token in the sequence. This cache grows with sequence length, consuming significant GPU memory. Traditional methods allocate this memory contiguously, leading to severe fragmentation and underutilization, especially with dynamic batching (where requests have varying lengths and arrival/departure times). Paged Attention (introduced by vLLM) solves this by managing the KV cache like an operating system manages virtual memory: breaking it into fixed-size "blocks" that can be stored non-contiguously, mapped via a "page table."

Analogy: Imagine a library (GPU memory) with shelves (memory blocks). If each reader (LLM request) needs to reserve a *contiguous* block of shelves for their entire book collection (KV cache), the library quickly becomes fragmented. Even if there are many empty shelves, a new reader might not find a large enough *single continuous* section. Paged Attention is like allowing readers to store their books on *any* available shelf, anywhere in the library, keeping track of which shelf holds which book using a small index card (page table). This way, every empty shelf can be used, maximizing library capacity.

💡 If you remember one thing

Paged Attention decouples the logical (contiguous) view of a KV cache from its physical (non-contiguous) storage. This eliminates fragmentation, enabling dynamic batching to achieve near-optimal GPU memory utilization and significantly higher LLM serving throughput.

How Paged Attention Works Internally
▼

The Problem: KV Cache Fragmentation

During LLM inference, the self-attention mechanism requires access to all previously computed Key and Value vectors (the KV cache) for each new token. For a sequence of length \(L\), a KV cache consumes memory proportional to \(L \times D\), where \(D\) is the hidden dimension. When multiple requests are processed in a dynamic batch, their sequence lengths vary. If each request's KV cache must be stored in a contiguous chunk of GPU memory, releasing a request's memory creates "holes." These holes often aren't large enough for new, longer requests, leading to wasted memory (external fragmentation).

This is further exacerbated by the fact that LLMs generate tokens one by one: a request starts small and its KV cache grows dynamically. Reserving the maximum possible length upfront wastes memory for shorter sequences; re-allocating on every token is too slow.

The Solution: Paged Attention

Paged Attention addresses this by treating the KV cache like an operating system treats virtual memory, adapting the concept of paging:

  1. Fixed-size Blocks: The entire GPU memory allocated for KV caches is divided into fixed-size physical blocks. Each block stores a fixed number of tokens (e.g., 16 or 32 tokens' worth of K and V vectors).
  2. Logical Blocks & Page Tables: For each running request, its KV cache is conceptually divided into logical blocks. A page table (a small array specific to that request) maps these logical blocks to arbitrary, non-contiguous physical blocks in GPU memory.
  3. Dynamic Allocation: As a request generates new tokens, it needs more KV cache space. Instead of resizing a contiguous chunk, Paged Attention simply allocates a new physical block from a global "free list" and updates the request's page table to point to it.
  4. Efficient Deallocation & Reuse: When a request finishes, all its physical blocks are returned to the free list. Because blocks are fixed-size and non-contiguous, any freed block can be immediately reused by any other request, eliminating external fragmentation.

Design Decision: Why Fixed-Size Blocks?

Fixed-size blocks simplify memory management significantly. It means any free block is identical to any other, making allocation and deallocation constant-time operations (just add/remove from a linked list or bitmap). This predictability is crucial for high-performance GPU kernels. Variable-sized blocks would reintroduce fragmentation problems, albeit at a finer granularity.

🔑 Key Property

Paged Attention allows sharing of KV cache blocks between requests (e.g., in speculative decoding or beam search) and efficient swapping of blocks to/from CPU memory when GPU memory is constrained. These are direct benefits of the virtual memory analogy.

Why It Works — The Math
▼

Memory Usage & Fragmentation in Naive KV Caching

The memory for the KV cache for a single token is \(2 \times H \times D_{head}\) bytes (where \(H\) is number of heads, \(D_{head}\) is head dimension, and we store both Key and Value vectors). For a sequence of length \(L\), this is \(L \times (2 \times H \times D_{head})\). If we have \(N\) concurrent requests, each with an allocated maximum length \(L_{max}\) but currently using \(L_{actual,i}\) tokens:

$$\text{Total Naive KV Cache Memory} = \sum_{i=1}^N L_{max,i} \times (2 \times H \times D_{head})$$

The wasted memory due to *internal* fragmentation (allocating \(L_{max}\) but using less) is \(\sum_{i=1}^N (L_{max,i} - L_{actual,i}) \times (2 \times H \times D_{head})\). Even worse is *external* fragmentation: if a request of length \(L\) needs \(L\) contiguous tokens, and we only have free blocks of length \(L/2\), those blocks are unusable. This leads to a much lower effective batch size.

Memory Usage in Paged Attention

With Paged Attention, memory is allocated in fixed-size blocks of \(B\) tokens. A request of length \(L\) needs \(\lceil L/B \rceil\) blocks. The total memory used is strictly proportional to the actual number of tokens generated across all requests:

$$\text{Total Paged Attention Memory} = \sum_{i=1}^N \lceil L_{actual,i}/B \rceil \times B \times (2 \times H \times D_{head})$$

The internal fragmentation within a block (e.g., a block has 16 tokens, but only 13 are used) is minimized, and external fragmentation is eliminated. The memory overhead for page tables is small: for \(N\) requests each with \(K\) blocks, it's \(N \times K \times \text{sizeof(pointer)}\).

Attention Computation with Paged Attention

The attention mechanism computes output \(O = \text{softmax}(Q K^\top / \sqrt{D_{head}}) V\). With Paged Attention, the \(K\) and \(V\) vectors for a sequence are scattered across non-contiguous physical blocks. The attention kernel needs to be modified to gather these \(K\) and \(V\) vectors from their respective physical blocks using the request's page table. This introduces an indirect memory access, but modern GPUs are highly optimized for such patterns, and the performance gain from reduced memory pressure far outweighs this overhead.

$$K_i = \text{load\_block}(\text{page\_table}_i[\text{logical\_block}_i]), \quad V_i = \text{load\_block}(\text{page\_table}_i[\text{logical\_block}_i])$$

The core attention computation itself remains unchanged, but the data loading stage is adapted.

⚠️ Implementation Complexity

Implementing Paged Attention requires significant changes to the attention kernel itself (e.g., CUDA C++ code), as it needs to perform indirect memory lookups via the page tables. This is not a trivial change, which is why frameworks like vLLM are so valuable.

Key Takeaways
▼

When to use Paged Attention (vLLM):

  • Serving LLMs in production where high throughput and low latency are critical.
  • When dealing with dynamic workloads where request arrival times and sequence lengths are unpredictable.
  • When GPU memory is a bottleneck and you need to maximize the number of concurrent requests.
  • For advanced features like speculative decoding or beam search, which benefit from KV cache sharing.

When it might not be strictly necessary:

  • Offline batch processing with fixed, uniform sequence lengths (though it still helps).
  • Very small models where KV cache memory is negligible.
  • If you are only running a single request at a time (no concurrency).
💡 Big Picture

Paged Attention is a prime example of how system-level optimizations (like virtual memory management) can dramatically improve the efficiency of deep learning models. It transforms LLM serving from a memory-bound, fragmented process into a highly efficient, high-throughput system, making large models more accessible and cost-effective.

Code Trace — Simplified Paged Attention Logic
▼
import collections
class BlockManager:
def __init__(self, num_gpu_blocks):
self.num_gpu_blocks = num_gpu_blocks
self.free_blocks = collections.deque(range(num_gpu_blocks))
self.ref_counts = [0] * num_gpu_blocks # For block sharing
def allocate_block(self):
if not self.free_blocks:
return None # Out of memory
block_id = self.free_blocks.popleft()
self.ref_counts[block_id] = 1
return block_id
def free_block(self, block_id):
self.ref_counts[block_id] -= 1
if self.ref_counts[block_id] == 0:
self.free_blocks.append(block_id)
class Request:
def __init__(self, request_id, block_manager):
self.id = request_id
self.block_manager = block_manager
self.page_table = [] # Maps logical_idx -> physical_block_id
self.num_tokens = 0
def append_token(self, block_size):
self.num_tokens += 1
logical_block_idx = (self.num_tokens - 1) // block_size
if logical_block_idx == len(self.page_table):
# Need a new physical block
new_block = self.block_manager.allocate_block()
if new_block is None:
raise MemoryError("Out of GPU memory blocks!")
self.page_table.append(new_block)
def release_memory(self):
for block_id in self.page_table:
self.block_manager.free_block(block_id)
self.page_table = []
self.num_tokens = 0
# Example Usage
bm = BlockManager(num_gpu_blocks=64)
req1 = Request(1, bm)
req2 = Request(2, bm)
# Simulate token generation for req1
for _ in range(10): req1.append_token(block_size=4)
print(f"Req1 page table: {req1.page_table}")
# Simulate token generation for req2
for _ in range(6): req2.append_token(block_size=4)
print(f"Req2 page table: {req2.page_table}")
# Release req1 memory
req1.release_memory()
print(f"Free blocks after req1 release: {list(bm.free_blocks)}")
