Beam Search Decoding

Keep the top-B partial sequences by cumulative log-probability — expand, score, prune, repeat
Intermediate NLP / Decoding Sequence Generation O(B·V) per step
1
Understanding Beam Search
▼

What is it? When a language model generates text token-by-token, at every step it must pick a next word from a huge vocabulary. Picking the single best word each time (greedy decoding) is fast but short-sighted — a locally great word can lead to a globally bad sentence. Beam search hedges against this by tracking several candidate sentences at once, instead of committing to just one.

Analogy: Imagine exploring a maze with a flashlight, but you're only allowed to remember your B most promising paths at any moment. At each junction, you look one step ahead down every corridor from every path you're tracking, then throw away all but the B best-looking paths so far. You never see the whole maze, but by keeping several parallel guesses alive you're far less likely to get trapped by a single early wrong turn than if you'd committed to only one path.

💡 If you remember one thing

Beam search keeps the B highest cumulative-log-probability partial sequences alive at every decoding step. It expands each one by the full vocabulary, scores every extension, and prunes back down to the top B — trading extra compute for a better (though still not guaranteed optimal) final sequence than greedy search.

2
How Beam Search Works Internally
▼

The Algorithm, Step by Step

Start with a single beam holding just the start token, with cumulative log-probability 0. At every decoding step, for each of the current B beams, run the model forward to get a distribution over the entire vocabulary \(V\) for the next token. This produces \(B \times V\) candidate continuations. Score each candidate as the parent's cumulative score plus the new token's log-probability, sort all \(B \times V\) candidates by score, and keep only the top \(B\) — everything else is discarded (pruned) forever, including the parent beams that produced them.

A beam "finishes" when it emits the end-of-sequence token. Finished beams are set aside and no longer expanded; they compete with the still-growing beams only at the very end, once all beams have finished or a maximum length is reached.

Why Expand All B Beams by the Full Vocabulary?

Greedy decoding only ever considers the single best next token given the single best prefix so far — if that token turns out to doom the rest of the sentence, there's no way back. Beam search instead explores B different prefixes in parallel and, crucially, evaluates all \(V\) extensions of all \(B\) of them before deciding what survives. A token that looked mediocre under the current best prefix might combine with a slightly worse prefix to produce the actual best overall sequence — beam search catches this because it never discards a prefix just because it wasn't rank #1 last round, only if it fails to make the cut after full expansion.

Design Decision: Why Not Just Track More Beams?

Compute and memory scale as \(O(B \cdot V)\) per step, and beam search is not guaranteed to find the true highest-probability sequence — it's a heuristic pruning of an exponential search tree of size \(V^T\). Past a certain point, increasing \(B\) gives diminishing or even negative returns: very large beams tend to favor short, generic, high-probability-per-token outputs (a phenomenon well documented in neural machine translation), which is exactly why length normalization exists.

🔑 Key Property

Beam search is breadth-limited best-first search over the tree of possible token sequences. At every depth it keeps exactly B nodes alive — no more, no less — making it a fixed-memory approximation to exhaustive search, with \(B{=}1\) reducing exactly to greedy decoding.

Why It Works — The Math
▼

Cumulative Sequence Score

Given source/context \(x\) (nothing, for unconditional LMs, or an input for translation/summarization), the model defines a probability over the next token conditioned on everything generated so far. The score of a full candidate sequence \(y_{1:t}\) is the sum of per-token log-probabilities:

$$\text{score}(y_{1:t}) = \sum_{i=1}^{t} \log P(y_i \mid y_{

Working in log-space turns a product of many probabilities (which underflows to 0 numerically) into a sum, and turns "maximize the joint probability" into "maximize the cumulative log-prob" — the same ranking, but numerically stable and additive, which is exactly what lets beam search compare partial sequences of different lengths at each step by simple addition.

The Length Bias Problem

Since every \(\log P(y_i\mid \cdot) \le 0\), the cumulative score is monotonically non-increasing as the sequence grows — a 3-token sequence can never score lower (more negative) than the same sequence extended to 10 tokens with any additional tokens attached. Left uncorrected, raw beam search is systematically biased toward short outputs, because every additional token can only subtract from the score.

Length Normalization

The standard fix (popularized by Google's Neural Machine Translation system) divides the cumulative score by a function of length before comparing candidates of different lengths, most simply:

$$\text{score}_{\text{norm}}(y_{1:T}) = \frac{1}{T^{\alpha}} \sum_{i=1}^{T} \log P(y_i \mid y_{

where \(T\) is the finished sequence's length and \(\alpha \in [0,1]\) is a tunable strength. \(\alpha{=}0\) recovers raw unnormalized scoring (favors short sequences); \(\alpha{=}1\) normalizes by the arithmetic mean log-probability per token (favors long sequences less penalized for length); values around \(0.6\)–\(0.7\) are common in practice. A closely related refinement, the coverage penalty used in encoder-decoder MT models, adds a term rewarding sequences whose attention weights collectively "cover" the source input, discouraging both under- and over-translation.

⚠️ Common Pitfall

Beam search finds a heuristically good sequence, not the global-maximum-probability one — pruning is irreversible, so a token that is second-best right now can permanently eliminate the eventual best full sequence. Larger \(B\) reduces this risk but never eliminates it, and in open-ended generation (chit-chat, story writing) large-beam search tends to produce bland, repetitive text because it optimizes for the "safest" high-probability path — this is why sampling methods (top-k, nucleus) are usually preferred over beam search for creative generation.

Key Takeaways
▼

When to use beam search:

  • Tasks with a roughly "correct" target output — machine translation, summarization, speech-to-text, structured code/SQL generation
  • When output quality matters more than latency/throughput (beam search costs \(B\times\) the compute of greedy decoding)
  • Combined with length normalization whenever outputs can vary meaningfully in length

When NOT to use it:

  • Open-ended, creative generation (chat, stories, brainstorming) — beam search over-concentrates on high-probability, generic, repetitive text; sampling (top-k / nucleus / temperature) is preferred
  • Extremely latency-sensitive serving where greedy or small-\(B\) beams / speculative decoding are needed
  • Very large \(B\) rarely helps and can even hurt quality past a task-specific sweet spot (typically \(B{=}4\)–\(10\) in MT)
💡 Hierarchy

Greedy search (\(B{=}1\)) ⊂ Beam search (\(B{>}1\), fixed-width heuristic) ⊂ Exhaustive search (\(B{=}V^T\), intractable). Beam search is the practical middle ground — and diverse beam search further tweaks it to stop the \(B\) beams from collapsing into near-duplicate sequences that differ only in their last token.

Code Trace — Beam Search From Scratch
▼
import numpy as np
def beam_search(model_logprobs, bos, eos, B=3, max_len=20, alpha=0.6):
"""model_logprobs(prefix) -> log P(next_token) for every token in V."""
beams = [([bos], 0.0)] # (token_sequence, cumulative_logp)
finished = []
for _ in range(max_len):
if not beams:
break
candidates = []
for seq, logp in beams:
next_logps = model_logprobs(seq) # shape (V,)
for token, tok_logp in enumerate(next_logps):
candidates.append((seq + [token], logp + tok_logp))
# keep only the top-B of all B*V candidates
candidates.sort(key=lambda c: c[1], reverse=True)
beams = []
for seq, logp in candidates[:B]:
if seq[-1] == eos:
finished.append((seq, logp)) # freeze this beam
else:
beams.append((seq, logp)) # keep expanding
finished += beams # force-finish anything still running at max_len
# length-normalized comparison across different-length sequences
def norm_score(seq, logp):
T = len(seq) - 1 # exclude BOS
return logp / (T ** alpha)
finished.sort(key=lambda c: norm_score(*c), reverse=True)
return finished[0] # best sequence, cumulative logp

In production (e.g. HuggingFace generate(num_beams=B, length_penalty=alpha)), the same logic runs batched on GPU tensors instead of Python lists — but the algorithm is identical: expand all beams by the full vocabulary, sort, truncate to B, repeat.
