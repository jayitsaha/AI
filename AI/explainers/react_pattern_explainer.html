1
Understanding the ReAct Pattern
▼

What is it? ReAct (Reasoning + Acting) is a prompting pattern for LLM agents that interleaves two kinds of generated text in the same running context: free-form reasoning steps ("Thoughts") and structured tool calls ("Actions"). Each Action's real-world result ("Observation") is appended back into the context before the next Thought is generated. Instead of a model silently guessing an answer (plain chain-of-thought) or blindly issuing tool calls with no visible plan (act-only agents), a ReAct agent narrates its plan, checks that plan against real evidence, and revises the plan — all inside one autoregressive trace.

Analogy: Picture a detective thinking out loud: "I think the culprit left through the window (Thought) — let me check the latch (Action) — it is locked from the inside (Observation) — so that is not how they left, let me reconsider (Thought)..." The detective never commits to a theory without checking it against evidence, and never checks evidence without first stating why. ReAct gives an LLM the same discipline: think, then check, then think again.

💡 If you remember one thing

ReAct writes \(\text{Thought}_t\), \(\text{Action}_t\) and \(\text{Observation}_t\) into the same growing context window, so every action is chosen by the latest reasoning and every reasoning step is grounded by the latest tool result — reasoning and acting bootstrap each other, turn after turn.

2
How ReAct Works Internally
▼

The Prompt Structure

A ReAct prompt begins with a handful of few-shot exemplars showing the full Thought/Action/Observation format, followed by the real question. Nothing about the underlying model changes — it is still an ordinary autoregressive LLM doing next-token prediction. What changes is what gets fed into the context at each turn.

The Loop

At turn \(t\): (1) the model generates a Thought — a sentence of internal reasoning that does not touch the environment; (2) the model then generates an Action such as Search[query], Lookup[string], or Finish[answer]; (3) a calling harness parses the action type, executes it against the matching tool (search API, calculator, database, code interpreter, ...), and appends the tool's raw return value as the Observation; (4) the loop repeats with the newest Observation now visible in context. It terminates when the model emits Finish[...] or a maximum step budget is hit.

🔑 Design Decision

Why interleave instead of plan-then-act (write the whole plan first, execute after) or think-once-then-act (one chain-of-thought, then a single tool call)? Both alternatives commit to a plan before any evidence exists. ReAct defers each decision to the moment right after the newest Observation, so an empty or misleading search result can trigger a different query immediately, rather than only being discovered after the whole plan has already failed.

Why It Works — Formalizing the Loop
▼

The Augmented Action Space

A standard tool-using agent is a Markov Decision Process where an action changes the environment state: \(a_t \sim \pi_\theta(a_t \mid s_t)\), \(s_{t+1} = \text{Env}(s_t, a_t)\). ReAct augments the action space with an unbounded space of language "thoughts" \(\mathcal{L}\) that leave the environment untouched:

$$\hat{\mathcal{A}} = \mathcal{A} \cup \mathcal{L}, \qquad s_{t+1} = \begin{cases} s_t & \hat a_t \in \mathcal{L} \ \text{(thought — internal only)} \\ \text{Env}(s_t,\hat a_t) & \hat a_t \in \mathcal{A} \ \text{(tool action)} \end{cases}$$

The policy conditions on the entire interleaved trace so far, so the trajectory likelihood under the frozen LLM is just ordinary next-token prediction over an extended context — no architecture change is required:

Why Grounding Beats Pure Recall

In a \(k\)-hop factual chain, chain-of-thought-only reasoning must recall every intermediate fact from parametric memory with per-hop error rate \(\epsilon_{\text{param}}\), and errors compound with no correction signal:

$$P(\text{all } k \text{ hops correct})_{\text{CoT-only}} \approx (1-\epsilon_{\text{param}})^{k}$$

ReAct instead injects a retrieved Observation at every hop that confirms or overrides the guess, bounding the effective per-hop error by retrieval error \(\epsilon_{\text{retr}}\), which for well-posed factual lookups is typically far smaller than parametric recall error:

$$P(\text{all } k \text{ hops correct})_{\text{ReAct}} \approx (1-\epsilon_{\text{retr}})^{k} \gg (1-\epsilon_{\text{param}})^{k} \quad \text{when } \epsilon_{\text{retr}} \ll \epsilon_{\text{param}}$$

⚠️ Common Pitfall

Grounding is not automatic immunity to error. Agents can fall into thought-action loops that repeat the same failed query verbatim, or exhibit reasoning hallucination — a Thought asserts a "fact" that no Observation actually supports, and later Actions build on that false premise. ReAct reduces compounding error; it does not eliminate it.

Key Takeaways & Comparison
▼
DimensionCoT-onlyAct-onlyReAct
External groundingNone — parametric memory onlyFull, every step touches a toolFull, and reasoning cites which fact came from where
InterpretabilityHigh trace, but can be fabricatedLow — no stated rationale between callsHigh — trace shows both plan and evidence
Mid-task error recoveryNone — no new information ever arrivesImplicit only, via blind retriesExplicit — a Thought can flag a bad Observation and redirect
Extra latency / tokensLowest — no tool round-tripsMedium — tool calls, no reasoning tokensHighest — reasoning + action tokens every turn
Typical failure modeFluent hallucination of "facts"Repeats bad queries with no visible diagnosisThought-action loops if failure goes unrecognized

When to use ReAct: multi-hop QA, tasks needing current or external facts, tasks needing an auditable decision trail, or any tool that can return noisy/irrelevant results.

When NOT to use: latency-critical single-fact lookups (skip to Act-only), tasks with no tools available (fall back to plain CoT), or very long-horizon tasks where a dedicated plan-and-replan structure amortizes better than paying reasoning-token cost on every single turn.

💡 Decision Rule

Use CoT-only when the answer already lives fully inside the model's parameters and speed matters. Use Act-only when the task is unambiguous tool orchestration. Use ReAct when the task is multi-hop, needs external grounding, and you need to see why the agent did what it did.

def react_agent(question, tools, llm, max_steps=6):
ctx = f"Question: {question}\n"
facts = {}
for i in range(1, max_steps + 1):
# 1. REASON: generate a thought conditioned on the full context
thought = llm(REACT_PROMPT + ctx + f"Thought {i}:")
ctx += f"Thought {i}: {thought}\n"
# 2. ACT: generate the next action (search / lookup / finish)
action = llm(REACT_PROMPT + ctx + f"Action {i}:")
ctx += f"Action {i}: {action}\n"
if action.startswith("Finish"):
return action[len("Finish["):-1] # stop condition
# 3. OBSERVE: execute the tool call against the real environment
obs = tools.run(action) # Search[...] / Lookup[...]
ctx += f"Observation {i}: {obs}\n"
facts.update(extract_facts(obs))
return None # exceeded max_steps without Finish
