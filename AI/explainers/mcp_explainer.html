A standard for AI model-tool integration and robust context management

Understanding MCP
▼

What is it? The Model Context Protocol (MCP) is a proposed standard for how AI models (especially large language models, LLMs) interact with external tools and manage their operational context. It defines a structured way for models to declare capabilities, make tool calls, receive tool outputs, and consistently handle dynamic information like chat history, retrieved documents, and user state.

Analogy: Imagine a highly intelligent but isolated librarian (the LLM). They can answer questions based on the books they have. If a user asks for "today's weather," the librarian needs a phone (a tool) to call the weather service. MCP is the standard operating procedure for the librarian to:

  1. Know what a "phone" is and how to ask for it (tool manifests).
  2. Know how to dial a number and ask a precise question ("give me weather for X") (structured tool calls).
  3. Understand the answer from the weather service (structured tool outputs).
  4. Remember the conversation history and the user's location (context management).
💡 If you remember one thing

MCP formalizes the "tool use" and "context management" patterns that are often ad-hoc in LLM applications. It enables robust, multi-turn, and agentic behaviors by providing structured interfaces for the model's inputs and outputs:

$$\text{ModelInput} = \text{Prompt} + \text{ContextState} + \text{ToolOutputs} + \text{ToolManifests}$$

And similarly for structured tool calls in the output.

How It Works Internally
▼

The Core Mechanisms

MCP defines several key components that work together within an agentic loop:

  • Tool Manifests: Before interaction, an orchestrator (agent runtime) provides the AI model with a list of available tools and their capabilities (function names, argument schemas, descriptions) in a structured format (e.g., JSON Schema). The model "learns" what actions it can take.
  • Structured Tool Calls: When the model determines a tool is needed, instead of generating a natural language response, it outputs a structured object (e.g., JSON) representing the tool call, including the tool's name and its arguments. This is unambiguous and machine-readable.
  • Tool Execution & Output: The orchestrator intercepts the tool call, executes the requested action (e.g., calling an API), and captures its output. This output is then formatted and injected back into the model's context for the next turn.
  • Context Management: Beyond tool outputs, MCP standardizes how other dynamic information is handled:
    • Chat History: Previous turns of the conversation are maintained and passed to the model.
    • Retrieval-Augmented Generation (RAG): Relevant documents or data from external knowledge bases are retrieved and injected.
    • User/Session State: Variables like user preferences, current location, or session IDs are managed and provided.

Design Decision: Why a Protocol, Not Just Prompt Engineering?

Many early LLM applications used complex prompt engineering to guide models toward tool use or context understanding. This is brittle, non-standardized, and prone to "hallucinations" where the model invents tool calls or misinterprets context. MCP provides a strict, machine-readable interface:

  • Decoupling: Separates the model's decision-making (what tool to call) from the tool's implementation (how to call it).
  • Interoperability: Enables different models and orchestrators to use the same tools.
  • Reliability: Reduces ambiguity, making agent behavior more predictable and debuggable.
  • Efficiency: Structured inputs/outputs are easier for machines to parse and generate than free-form text.
🔑 Key Property

MCP ensures a clear separation of concerns: the AI model decides what action to take (if any), while the orchestrator (agent runtime) is responsible for how to execute that action and manage the overall information flow. This modularity is crucial for building scalable and robust AI agents.

Why It Works — The Formal Structure
▼

Information Flow & State Transition

At its core, MCP defines the structured inputs and outputs that drive an AI agent's decision-making process. We can formalize the information streams and the agentic loop:

The model's input stream at any time step \(t\) is a composite of various structured and unstructured data:

$$\text{InputStream}_t = \{ \text{Prompt}_t, \text{ContextState}_t, \text{ToolOutputs}_t, \text{ToolManifests} \}$$

The model processes this input and produces an output stream, which can either be a natural language response or a structured tool call:

$$\text{OutputStream}_t = \{ \text{NaturalLanguageResponse}_t \mid \text{ToolCall}_t \}$$

The agent operates in a continuous loop, where the output of one step informs the input of the next. If a tool call is made, an external executor processes it, generating tool outputs that become part of the next input stream:

$$\text{AgentLoop}: \text{InputStream}_t \xrightarrow{\text{Model}} \text{OutputStream}_t \xrightarrow{\text{Executor}} \text{ToolOutputs}_{t+1} \to \text{InputStream}_{t+1}$$

This loop ensures that the model always has access to the most up-to-date information for its decisions.

Structure of a Tool Call and Context

MCP specifies the precise structure for tool calls and context objects to ensure machine-readability and prevent ambiguity:

  • ToolCall: A structured object, typically JSON, detailing the action to be taken.
    • $$\text{ToolCall} = \{ \text{name}: \text{string}, \text{arguments}: \text{JSONDictionary} \}$$
  • ContextState: A composite object containing all relevant dynamic information.
    • $$\text{ContextState} = \{ \text{chat\_history}: \text{list}, \text{retrieved\_documents}: \text{list}, \text{user\_state}: \text{dict}, \text{environment}: \text{dict} \}$$
⚠️ Common Pitfall

A major pitfall in agent design is over-reliance on the LLM's ability to "understand" loosely structured text for tool calls or context. Without a strict protocol like MCP, models can hallucinate tool names, invent arguments, or misinterpret context, leading to unpredictable and unreliable agent behavior. MCP significantly mitigates these risks by enforcing machine-readable schemas.

Key Takeaways
▼

When to use MCP:

  • Building complex AI agents: For applications that require LLMs to perform multi-step reasoning, interact with external systems, or maintain state across turns.
  • Ensuring reliability and robustness: When agent behavior needs to be predictable and debuggable, reducing the risk of LLM hallucinations in tool calls or context interpretation.
  • Decoupling concerns: To cleanly separate the LLM's role (decision-making) from the orchestrator's role (execution and state management).
  • Interoperability: When you need to swap out different LLMs or orchestrators while keeping the same set of tools and context mechanisms.
  • RAG systems: To standardize how retrieved documents are formatted and injected into the LLM's context.

When NOT to use:

  • Simple, single-turn interactions: If your application is purely text-in, text-out without external actions or memory, the overhead of MCP is unnecessary.
  • Pure content generation: When the LLM is used solely for creative writing, summarization, or translation, without needing to interact with real-world data or services.
  • Latency-critical simple tasks: For extremely low-latency tasks where the overhead of JSON parsing and tool orchestration might be a bottleneck, and simpler direct API calls suffice.
💡 Big Picture

The Model Context Protocol is a fundamental building block for the next generation of AI systems. It transforms LLMs from mere language generators into capable, autonomous agents by providing a standardized, reliable framework for them to perceive their environment, act upon it through tools, and maintain a coherent understanding of their ongoing context. It moves AI from "chatbots" to "do-bots."

import json
from dataclasses import dataclass, field
from typing import List, Dict, Any, Callable, Optional
# 1. Tool Manifests: How tools declare themselves
@dataclass
class ToolManifest:
name: str
description: str
parameters: Dict[str, Any] # JSON Schema for arguments
func: Callable # The actual Python function
# 2. Context State: Dynamic information for the model
@dataclass
class ContextState:
chat_history: List[Dict[str, str]] = field(default_factory=list)
retrieved_documents: List[str] = field(default_factory=list)
user_state: Dict[str, Any] = field(default_factory=dict)
tool_outputs: List[Dict[str, Any]] = field(default_factory=list)
# 3. AI Model (LLM) Interface
class AIModel:
def __init__(self, name="LLM"): self.name = name
def generate(self, prompt: str, context: ContextState, tool_manifests: List[ToolManifest]) -> Dict[str, Any]:
# In a real LLM, this would be an API call or inference.
# It returns either a natural language response OR a tool call.
# The model "decides" based on prompt, context, and available tools.
# Example: if "weather" in prompt, it might return a tool_call.
return {"type": "response", "content": "..."} # or {"type": "tool_call", "name": "...", "args": {...}}
# 4. Orchestrator (Agent Runtime)
class Orchestrator:
def __init__(self, model: AIModel):
self.model = model
self.tools: Dict[str, ToolManifest] = {}
self.context = ContextState()
def register_tool(self, tool_manifest: ToolManifest):
self.tools[tool_manifest.name] = tool_manifest
def execute_tool_call(self, tool_call: Dict[str, Any]) -> Dict[str, Any]:
tool_name = tool_call.get("name")
args = tool_call.get("args", {})
if tool_name not in self.tools:
return {"error": f"Tool '{tool_name}' not found."}
try:
result = self.tools[tool_name].func(**args)
return {"tool_name": tool_name, "result": result}
except Exception as e:
return {"error": f"Error executing tool '{tool_name}': {e}"}
def run_agent_turn(self, user_prompt: str) -> str:
self.context.chat_history.append({"role": "user", "content": user_prompt})
# Prepare input for LLM
tool_manifests_list = list(self.tools.values())
model_output = self.model.generate(user_prompt, self.context, tool_manifests_list)
if model_output.get("type") == "tool_call":
tool_result = self.execute_tool_call(model_output)
self.context.tool_outputs.append(tool_result)
# Recursively call or loop to let model process tool_result
# For simplicity, we'll just return the tool result as response here
return f"Tool Executed: {tool_result}"
else:
self.context.chat_history.append({"role": "assistant", "content": model_output["content"]})
return model_output["content"]
