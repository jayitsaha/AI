Weight Tying

Sharing the input embedding matrix and output projection in language models
Foundational NLP / LLMs Regularization O(V·d) params saved
1
Understanding Weight Tying
▼

What is it? Every language model has two embedding-shaped matrices: an input embedding \(E \in \mathbb{R}^{V \times d}\) that turns token IDs into vectors, and an output projection \(W_{out}\) that turns the model's final hidden state back into a score for every token in the vocabulary. Weight tying simply sets \(W_{out} = E^\top\) — the same matrix is reused for both jobs instead of learning two separate ones.

Analogy: Imagine a bilingual dictionary. Looking up a word to find its meaning (input embedding) and looking up a meaning to find the matching word (output projection) are inverse operations over the same vocabulary of concepts. It would be wasteful — and inconsistent — to maintain two unrelated dictionaries for these two directions. Weight tying says: use one dictionary, read it forwards for input and backwards for output.

Why it matters: In models with huge vocabularies (GPT-2's 50,257 BPE tokens), the embedding matrix can hold a large fraction of all parameters. Tying halves that footprint and, empirically, improves language-model quality because the input and output token representations are forced to live in the same geometric space.

💡 If you remember one thing

Weight tying reuses the input embedding matrix as the output (softmax) projection: $$W_{out} = E^\top \quad\Longrightarrow\quad \text{logits} = h\,E^\top$$ This cuts embedding parameters in half and makes the output logit for token \(j\) literally the dot product between the hidden state \(h\) and token \(j\)'s own input vector.

How It Works Internally
▼

The Untied Baseline

A standard decoder-only LM has a stack of transformer blocks that turn a token embedding into a contextual hidden state \(h \in \mathbb{R}^d\). To get a distribution over the next token, \(h\) is projected to vocabulary size via a linear layer \(W_{out} \in \mathbb{R}^{d \times V}\): \(\text{logits} = hW_{out}\), then softmax. Without tying, \(E\) (lookup table) and \(W_{out}\) (output head) are separate learned parameters — nothing forces them to agree with each other, even though both are supposed to encode "what a token means."

Tying the Weights

Weight tying constrains \(W_{out} = E^\top\). Concretely, the output logit for candidate token \(j\) becomes \(\text{logit}_j = h \cdot E_j\) — the dot product of the hidden state with token \(j\)'s input embedding row. Geometrically, this turns next-token prediction into a nearest-neighbor search: the model picks whichever token's embedding vector points in the most similar direction to \(h\).

Design Decision: Why Share Instead of Regularize?

An alternative would be an auxiliary loss pulling \(E\) and \(W_{out}\) together. Tying is stronger and cheaper: it's an exact architectural constraint (zero extra loss terms, zero extra compute for a regularizer) that also removes ~\(Vd\) parameters outright. Press & Wolf (2017) additionally showed tying acts as effective regularization — the shared matrix receives gradient signal from both the input-embedding-lookup path and the output-softmax path every step, so rare tokens get more, better-shaped updates than they would from either role alone.

The Scaling Subtlety

Input embeddings are typically initialized with small variance (\(\sim 1/\sqrt{d}\)) because they are summed with positional encodings and fed into normalization layers. Output projections traditionally have different, often larger, effective scale. The original Transformer paper (Vaswani et al., 2017) compensates by multiplying the shared embedding weights by \(\sqrt{d_{model}}\) before use, keeping the input-embedding branch and the logit branch numerically well-scaled despite sharing parameters.

🔑 Key Property

Tying makes the input and output vocabularies literally the same learned space. A token's meaning-as-context (used to predict it) and meaning-as-target (used to be predicted) are forced to coincide — which is exactly the symmetry a language model should have.

3
Why It Works — The Math
▼

Gradient Accounting — Why Tying Regularizes

Let \(\mathcal{L}\) be the cross-entropy loss for predicting the true next token \(t\) from context. With tying, the softmax logits are \(z = hE^\top\), so \(z_j = h \cdot E_j\). The gradient with respect to the shared matrix has two additive contributions:

$$\frac{\partial \mathcal{L}}{\partial E_j} = \underbrace{(p_j - \mathbb{1}[j=t])\,h}_{\text{output-head gradient (all }j\text{)}} \; + \; \underbrace{\frac{\partial \mathcal{L}}{\partial h_{\text{in}}}\Big|_{j = \text{input token}}}_{\text{input-lookup gradient (only if }j\text{ was fed in)}}$$

where \(p = \text{softmax}(z)\). Every row of \(E\) gets an output-side update proportional to its softmax error every single step (dense signal), while only the handful of rows corresponding to tokens actually present in the batch get the input-side update (sparse signal). Untied models split this into two disjoint parameter pools, each seeing only one signal — tying merges them, so rare tokens (which rarely appear as input) still get shaped by appearing as a candidate output.

Parameter Count

For vocabulary size \(V\) and model width \(d\):

$$\text{Untied: } 2Vd \qquad \text{Tied: } Vd \qquad \text{Savings: } Vd \text{ parameters } (50\%\text{ of embedding params})$$

For GPT-2 small (\(V{=}50{,}257\), \(d{=}768\)): untied embeddings cost \(2 \times 50{,}257 \times 768 \approx 77.2\)M parameters; tied costs \(\approx 38.6\)M — a savings of 38.6M parameters, non-trivial next to the model's ~124M total.

Effect on the Loss Landscape

Constraining \(W_{out}=E^\top\) removes degrees of freedom, which mechanically raises achievable training loss in the worst case — but empirically lowers validation perplexity, because the constraint is a good inductive bias, not an arbitrary one: it prevents the output head from overfitting an idiosyncratic representation disconnected from the semantically meaningful embedding space that generalizes better.

⚠️ Common Pitfall

Tying is not automatically free lunch for every architecture. In very large vocabularies with small \(d\) (e.g., character-level or multilingual sentencepiece models with huge \(V\)), forcing \(W_{out}=E^\top\) can bottleneck output expressivity — the softmax weight vectors and the input embedding vectors may genuinely want different geometry. Some large-scale LLMs (e.g., early GPT-3-scale configs, PaLM in some variants) intentionally untie for exactly this reason.

Key Takeaways
▼

When to use weight tying:

  • Autoregressive / masked language models with large vocabularies (GPT-2, GPT-3 early configs, BERT-style MLM heads, ELMo)
  • Encoder-decoder translation models — often tie source embedding, target embedding, AND the pre-softmax matrix (three-way tying, as in the original Transformer)
  • Parameter-constrained or on-device models, where every saved parameter matters
  • Any setting where \(d\) is reasonably large relative to \(V\), so the shared space has enough capacity for both roles

When NOT to use:

  • Extremely large \(V\) with small \(d\), where input and output need different geometry
  • Multilingual / multi-domain output heads where the output distribution has structure the input space doesn't need
  • When empirical ablation on your task shows tying hurts (always verify — it's an inductive bias, not a law)
💡 Origins

Introduced by Press & Wolf, "Using the Output Embedding to Improve Language Models" (2017) and independently by Inan et al., "Tying Word Vectors and Word Classifiers" (2017); adopted as standard practice by Vaswani et al., "Attention Is All You Need" (2017), which also introduced the \(\sqrt{d_{model}}\) embedding scaling to accompany it.

import numpy as np
# Vocab of 6 toy tokens, embedding dim 4
V, d = 6, 4
E = np.random.randn(V, d) * 0.4 # nn.Embedding weight
# ── UNTIED: separate output head ──
W_out = np.random.randn(V, d) * 0.3 # nn.Linear(d, V).weight
h = transformer_blocks(E[token_id]) # hidden state, shape (d,)
logits_untied = h @ W_out.T # shape (V,)
# ── TIED: reuse E as the output head ──
logits_tied = h @ E.T # W_out = E.T, no new params
# PyTorch equivalent
class TiedLM(nn.Module):
def __init__(self, V, d):
super().__init__()
self.embed = nn.Embedding(V, d)
self.lm_head = nn.Linear(d, V, bias=False)
self.lm_head.weight = self.embed.weight # <-- the tying
def forward(self, tokens):
x = self.embed(tokens) * (d ** 0.5) # Vaswani et al. scaling
h = self.transformer(x)
return self.lm_head(h) # logits, uses tied weight
# Param count check
tied_params = V * d
untied_params = 2 * V * d
print(f"Saved {untied_params - tied_params} params ({100*(1 - tied_params/untied_params):.0f}%)")
