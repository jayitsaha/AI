Understanding ONNX Export
▼

What is it? You train a model in PyTorch. Now you need to serve it from a C++ backend, a mobile phone, a browser, or a chip that has never heard of Python. ONNX (Open Neural Network Exchange) is a framework-neutral file format that describes a model as a computation graph — a set of standard mathematical operators (Conv, MatMul, Relu, Softmax, …) wired together by tensors. Exporting to ONNX means translating "PyTorch's private vocabulary" into this shared vocabulary that many runtimes understand.

Analogy: Think of a shipping container. Factories around the world build wildly different products, but as long as everything is packed into a standard container, any port, ship, or crane can move it — nobody needs to understand what is inside. ONNX is that container for neural networks: PyTorch, TensorFlow, and JAX each "pack" their model differently internally, but once exported to ONNX, any compliant runtime (ONNX Runtime, TensorRT, CoreML, OpenVINO) can "unload and run" it.

💡 If you remember one thing

Export = trace the concrete sequence of tensor operations a model actually executes, map each op to a versioned ONNX operator (an "opset"), then optimize the resulting graph (constant folding, operator fusion) before handing it to a runtime that picks the fastest available backend (CPU / CUDA / TensorRT) per node.

2
How Export Works Internally
▼

From Eager Python to a Static Graph

PyTorch normally runs eagerly: nn.Module.forward() is plain Python, executed op-by-op with no persistent graph. To export, torch.onnx.export() feeds a real (or symbolic) input through the model while tracing — recording every tensor operation that actually fires, along with the concrete shapes involved. The result is a directed acyclic graph: nodes are operators, edges are tensors flowing between them.

Opset Mapping

Each recorded op (e.g. nn.Conv2d, nn.BatchNorm2d, F.softmax) is translated by an exporter symbolic function into one or more standard ONNX operators from a specific opset (operator-set version, e.g. opset 17). A framework op can expand into several ONNX nodes (nn.Linear → MatMul + Add), or several framework ops can later collapse into one ONNX node during optimization.

Graph Optimization

Once the raw graph exists, ONNX Runtime's graph optimizer runs passes that shrink it without changing outputs: constant folding evaluates any subgraph whose inputs are all compile-time constants (shape tensors, padding, precomputed BatchNorm terms) once, ahead of time, replacing it with a literal. Operator fusion merges chains of ops that are always executed back-to-back — classically Conv → BatchNorm → Relu becomes one fused kernel, and MatMul → Add becomes a single Gemm node — eliminating intermediate memory round-trips and per-node kernel-launch overhead.

Design Decision: Why Trace Instead of Re-implement?

The alternative would be hand-writing an ONNX graph for every model — impossibly slow. Tracing reuses the model's own PyTorch code to generate the graph automatically. The trade-off: tracing only records the path actually executed for the given input, so Python-level control flow (an if that branches on a tensor value, a variable-length loop) is not captured faithfully — torch.jit.script or torch.export are needed when control flow must be preserved structurally.

🔑 Key Property

An ONNX graph is a closed, versioned contract: given an opset number, every consumer (ONNX Runtime, TensorRT, CoreML) agrees on exactly what each operator computes. That contract — not the original training framework — is what makes the model portable.

3
Why It Works — The Math of Graph Optimization
▼

Constant Folding as Partial Evaluation

If a node computes \(g(x) = h(f(c), x)\) where \(c\) is known at export time (a shape, a padding value, a frozen BatchNorm statistic) and \(f\) has no dependence on the runtime input \(x\), then the compiler can precompute \(k = f(c)\) once and rewrite the graph as \(g'(x) = h(k, x)\):

$$g(x) = h(f(c), x) \;\equiv\; g'(x) = h(k, x), \qquad k = f(c) \text{ computed once, offline}$$

This is exactly the classical compiler technique of partial evaluation — specializing a program with respect to its known inputs — applied to a tensor graph instead of source code.

Operator Fusion as Function Composition

If node A always feeds node B with no other consumer of A's output, the two can be replaced by their composition \(B \circ A\) computed in a single kernel:

$$(B \circ A)(x) = B(A(x))$$

For \(\mathrm{Conv} \to \mathrm{BatchNorm} \to \mathrm{Relu}\), fusion algebraically folds the BatchNorm's scale \(\gamma/\sqrt{\sigma^2+\epsilon}\) and shift directly into the convolution's weights and bias, so BatchNorm disappears as a separate node entirely — it becomes arithmetic baked into \(W\) and \(b\).

A Simple Latency Model

Each execution provider (backend) has a raw per-op compute factor and a fixed per-node dispatch overhead. Total estimated latency for a graph with node-cost sum \(C\) and \(N\) nodes on backend \(b\) is modeled as:

$$L_b = C \cdot f^{compute}_b \;+\; N \cdot f^{overhead}_b$$

Fusion reduces both terms: \(C\) shrinks slightly (fewer memory round-trips) and \(N\) shrinks a lot (fewer kernel launches) — which is why fusion helps every backend, and helps GPU-style backends the most, since their per-launch overhead \(f^{overhead}_b\) is largest.

⚠️ Common Pitfall

Constant folding and fusion are only valid because the graph is static after tracing. If the original model has data-dependent control flow that tracing silently "baked in" for one input shape, the exported graph can silently produce wrong results for a different input — always export with representative dynamic_axes and validate numerically against the original framework before trusting the optimized graph.

5
Key Takeaways
▼

When to export to ONNX:

  • Serving from a different language/runtime than training (C++, Java, browser via ONNX.js/WebGPU, mobile via CoreML/NNAPI)
  • You need a single artifact that many backends (CPU, CUDA, TensorRT, OpenVINO, DirectML) can all consume
  • You want graph-level optimizations (fusion, constant folding) that are hard to hand-write yourself
  • You need to decouple the serving stack's dependencies from the (often heavier, faster-moving) training framework

When NOT to rely on it:

  • Models with heavy data-dependent control flow or custom CUDA kernels that have no ONNX operator equivalent
  • Extremely fast-moving research code where re-exporting every iteration outweighs the deployment benefit
  • Whenever you skip numerical validation — a successful export is not proof of correctness, only of op-mapping coverage
💡 Hierarchy

Trace (capture the ops) → Map (opset translation) → Optimize (fold constants, fuse ops) → Partition (assign subgraphs to execution providers) → Execute (each provider picks its fastest kernel). Every stage only ever shrinks the graph or speeds up a node — the computed function never changes.

Code Trace
▼
import torch, onnx, onnxruntime as ort
model = TinyCNN().eval()
dummy = torch.randn(1, 3, 224, 224)
# Step 1-2: run forward() once, RECORD every op + shape (tracing)
torch.onnx.export(
model, dummy, "model.onnx",
input_names=["input"], output_names=["logits"],
opset_version=17,
dynamic_axes={"input": {0: "batch"}, "logits": {0: "batch"}},
)
# Step 3: inspect the raw exported graph (opset-mapped, unoptimized)
onnx_model = onnx.load("model.onnx")
onnx.checker.check_model(onnx_model)
print(len(onnx_model.graph.node), "nodes before optimization")
# Step 4-6: constant fold + fuse ops via the ORT graph optimizer
opts = ort.SessionOptions()
opts.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
opts.optimized_model_filepath = "model.opt.onnx"
# Step 7-9: run the SAME graph on different execution providers
provider_stacks = [
["CPUExecutionProvider"],
["CUDAExecutionProvider", "CPUExecutionProvider"],
["TensorrtExecutionProvider", "CUDAExecutionProvider", "CPUExecutionProvider"],
]
for providers in provider_stacks:
session = ort.InferenceSession("model.onnx", opts, providers=providers)
outputs = session.run(["logits"], {"input": dummy.numpy()})
