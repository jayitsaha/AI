Understanding Document Chunking
▼

What is it? Document chunking is the process of splitting a larger document into smaller, manageable pieces (chunks). This is a critical preprocessing step for many Large Language Model (LLM) applications, especially those involving Retrieval Augmented Generation (RAG). LLMs have a limited "context window" (the amount of text they can process at once), so large documents must be broken down to fit.

Analogy: Imagine you have a massive textbook. If you want to find a specific piece of information, you don't read the whole book. Instead, you might look at the table of contents (semantic/recursive chunking), flip to a specific chapter (large chunk), then scan paragraphs (smaller chunks) for keywords. Chunking is like creating that intelligent index and breaking the book into logically sized pieces so an LLM can efficiently "read" the relevant parts.

💡 If you remember one thing

Effective chunking is a trade-off: chunks must be small enough to fit into an LLM's context window and be relevant to a query, but large enough to retain sufficient context and not fragment important information. The goal is to maximize the chance of retrieving the most useful information for a given query.

2
How Different Strategies Work
▼

Why Chunk? The Core Problem

LLMs excel at understanding and generating text, but their ability is constrained by the maximum number of tokens they can process in a single input (the context window). For documents larger than this window, direct input is impossible. Chunking addresses this by:

  • Fitting context: Breaking documents into pieces that fit the LLM's input limit.
  • Improving retrieval: Smaller, more focused chunks lead to more precise vector embeddings, improving the accuracy of semantic search (RAG).
  • Reducing cost: Processing shorter chunks is generally cheaper and faster.

Overview of Common Strategies

The choice of chunking strategy significantly impacts RAG performance. Each method has a different philosophy for defining "meaningful" boundaries:

  • Fixed-size chunking: The simplest method. Documents are split into chunks of a predefined length (e.g., 500 tokens), often with a specified overlap between chunks to maintain continuity. It's fast but can cut sentences or paragraphs mid-stream.
  • Sentence-based chunking: Splits documents strictly along sentence boundaries. Each chunk is one or more complete sentences. This respects linguistic structure but can create many very small chunks, potentially fragmenting context.
  • Recursive chunking: A hierarchical approach. It attempts to split documents using a list of delimiters (e.g., first by `\n\n` for paragraphs, then by `\n` for lines, then by `.` for sentences, etc.). If a chunk is still too large, it tries the next smaller delimiter. This preserves logical document structure better.
  • Semantic chunking: A more advanced method that uses LLMs or embedding models to identify semantically coherent sections. Chunks are formed where there's a significant shift in topic or meaning, aiming to keep related ideas together.
  • Parent-child chunking: This strategy creates two types of chunks: small, dense "child" chunks (e.g., individual sentences or small paragraphs) and larger "parent" chunks that provide broader context. When a child chunk is retrieved, its parent chunk can also be fetched to enrich the LLM's understanding.
🔑 Key Property

The goal of any chunking strategy is to create chunks that are as self-contained and semantically complete as possible, while adhering to size constraints. The "best" strategy is highly dependent on the nature of the documents and the types of queries expected.

3
Formalizing Chunking Strategies
▼

Fixed-size Chunking

Given a document \(D\) as a sequence of tokens, and a desired chunk size \(L\) and overlap \(O\), chunks \(C_k\) are formed by selecting substrings:

$$C_k = D[\text{start}_k : \text{start}_k + L]$$

where the starting position for the next chunk is calculated as:

$$\text{start}_{k+1} = \text{start}_k + L - O$$

This ensures that each chunk \(C_k\) covers \(L\) tokens, and adjacent chunks share \(O\) tokens, providing continuity. For \(O=0\), chunks are non-overlapping.

Recursive Chunking

This method employs a list of delimiters, \(\mathcal{D} = [d_1, d_2, \dots, d_m]\), ordered from coarsest to finest (e.g., `\n\n`, `\n`, `.`, ` `). The algorithm proceeds recursively:

  1. Split the current text by the first delimiter \(d_1\).
  2. For each resulting segment, if it's smaller than \(L\), it becomes a chunk.
  3. If it's larger than \(L\), recursively apply the process with the next delimiter \(d_2\).

This prioritizes preserving larger structural units (paragraphs, sections) before breaking them down into smaller ones (sentences, words).

Semantic Chunking (Conceptual)

While not a direct mathematical formula, semantic chunking aims to cluster text segments based on their meaning. Conceptually, for a sequence of sentences \(s_1, s_2, \dots, s_N\), an embedding model \(E\) generates vectors \(v_i = E(s_i)\). Chunks are formed by grouping sentences such that the similarity within a chunk is maximized, and similarity across chunk boundaries is minimized. This might involve techniques like K-means clustering on sentence embeddings or identifying "breaks" in a similarity matrix:

$$\text{Chunk}_k = \{ s_i, \dots, s_j \} \quad \text{s.t. } \text{similarity}(v_x, v_y) \text{ is high for } x,y \in \text{Chunk}_k$$

This method is computationally more intensive but can yield highly relevant chunks for RAG.

⚠️ Practical Consideration

The choice of chunk size \(L\) and overlap \(O\) (for fixed-size/recursive) or the granularity of delimiters (for recursive) is often determined experimentally. There's no one-size-fits-all solution, and fine-tuning these parameters can significantly impact retrieval quality and LLM performance.

Key Takeaways
▼

When to use each strategy:

  • Fixed-size: Simple, fast, predictable. Good for unstructured text or when strict size limits are paramount. Risk: cuts ideas mid-sentence.
  • Sentence-based: Preserves linguistic units. Good for documents where individual sentences are highly informative. Risk: many small chunks, potential context fragmentation.
  • Recursive: Robust, adaptive to document structure. Generally a good default for structured documents (e.g., Markdown, code). Prioritizes larger logical units.
  • Semantic: Best for conceptual retrieval, where the "meaning" of a chunk is more important than its exact linguistic boundaries. Ideal for complex knowledge bases. Computationally more expensive.
  • Parent-child: Excellent for queries requiring both precise answers and broad context. Child chunks provide specificity, parent chunks provide the surrounding narrative. More complex to implement and manage.

Common Pitfalls:

  • Too small chunks: Loss of essential context, leading to poor retrieval and LLM hallucinations.
  • Too large chunks: Hit LLM context window limits, introduce irrelevant noise into retrieval, increase cost.
  • Ignoring overlap: Leads to context gaps between chunks, especially for fixed-size methods.
  • Misaligned boundaries: Cutting sentences or paragraphs in half can destroy semantic coherence.
💡 Rule of Thumb

Start with recursive chunking as a robust default. If documents are highly structured (e.g., legal, technical manuals), consider parent-child. For nuanced question-answering, explore semantic chunking. Always experiment with chunk sizes and overlaps on your specific data.

import re
from typing import List, Dict, Any
def get_token_count(text: str) -> int:
# Placeholder for actual tokenizer (e.g., tiktoken)
return len(text.split())
def fixed_size_chunking(text: str, chunk_size: int, overlap: int) -> List[str]:
chunks = []
current_pos = 0
while current_pos < len(text):
end_pos = min(current_pos + chunk_size, len(text))
chunks.append(text[current_pos:end_pos])
current_pos += chunk_size - overlap
if current_pos >= len(text) - overlap and end_pos == len(text): # Avoid infinite loop on small last chunk
break
return chunks
def sentence_based_chunking(text: str, chunk_size: int) -> List[str]:
sentences = re.split(r'(?<=[.!?])\s+', text)
chunks = []
current_chunk_sentences = []
current_chunk_tokens = 0
for sentence in sentences:
sentence_tokens = get_token_count(sentence)
if current_chunk_tokens + sentence_tokens > chunk_size and current_chunk_sentences:
chunks.append(" ".join(current_chunk_sentences))
current_chunk_sentences = [sentence]
current_chunk_tokens = sentence_tokens
else:
current_chunk_sentences.append(sentence)
current_chunk_tokens += sentence_tokens
if current_chunk_sentences:
chunks.append(" ".join(current_chunk_sentences))
return chunks
def _recursive_split(text: str, delimiters: List[str], chunk_size: int) -> List[str]:
if get_token_count(text) <= chunk_size or not delimiters:
return [text]
current_delimiter = delimiters[0]
parts = text.split(current_delimiter)
chunks = []
for part in parts:
if get_token_count(part) > chunk_size:
chunks.extend(_recursive_split(part, delimiters[1:], chunk_size))
else:
chunks.append(part)
return chunks
def recursive_chunking(text: str, chunk_size: int) -> List[str]:
delimiters = ["\n\n", "\n", ". ", "? ", "! ", " "] # Ordered from large to small
return _recursive_split(text, delimiters, chunk_size)

def semantic_chunking_conceptual(sentences: List[str], semantic_ids: List[int], chunk_size: int) -> List[str]:
chunks = []
current_chunk_sentences = []
current_chunk_tokens = 0
for i, sentence in enumerate(sentences):
sentence_tokens = get_token_count(sentence)
# If new sentence's semantic ID differs AND current chunk is not empty, start new chunk
if current_chunk_sentences and semantic_ids[i] != semantic_ids[i-1]:
chunks.append(" ".join(current_chunk_sentences))
current_chunk_sentences = [sentence]
current_chunk_tokens = sentence_tokens
elif current_chunk_tokens + sentence_tokens > chunk_size and current_chunk_sentences:
chunks.append(" ".join(current_chunk_sentences))
current_chunk_sentences = [sentence]
current_chunk_tokens = sentence_tokens
else:
current_chunk_sentences.append(sentence)
current_chunk_tokens += sentence_tokens

def parent_child_chunking_conceptual(full_document_text: str, child_chunk_size: int) -> Dict[str, Any]:
# Children are small, dense chunks (e.g., single sentences or small paragraphs)
child_chunks = sentence_based_chunking(full_document_text, child_chunk_size)
# Parents are larger, contextual chunks (e.g., full paragraphs or sections)
# For simplicity, let's say parent chunks are paragraphs.
parent_chunks = full_document_text.split("\n\n")
# In a real system, you'd link children to their corresponding parent IDs.
# Here we just return them separately for visualization.
return {"child_chunks": child_chunks, "parent_chunks": parent_chunks}
