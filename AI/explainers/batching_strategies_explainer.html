Understanding Inference Batching
▼

What is it? A GPU is most efficient when it processes many inputs at once — matrix multiplies scale sublinearly with batch size, so running 8 requests together can cost only slightly more than running 1. Batching is the scheduling policy that decides when incoming requests get grouped together and sent to the model. The catch: requests don't arrive all at once — they trickle in randomly over time — so the scheduler must trade off "wait for more requests to fill the batch" against "answer this request now."

Analogy: Think of an elevator. Static batching is an elevator that only moves once exactly 8 people are inside — if only 3 people show up, everyone waits, possibly forever. Dynamic batching is an elevator that leaves once it's full OR after 10 seconds, whichever comes first — bounded wait, better utilization. Continuous (adaptive) batching is like a paternoster lift with no doors — people step on and off different floors continuously, and no one waits for anyone else's ride to finish, even though many people are in the shaft at once.

💡 If you remember one thing

Static and dynamic batching fire a batch as one atomic unit — every request in it starts and finishes together. Continuous batching (used by vLLM, TensorRT-LLM, Orca, TGI) schedules at the level of a single decode iteration: a finished sequence frees its slot immediately, and a queued request is admitted into that slot on the very next iteration — no one waits for the whole batch to drain.

2
How Each Strategy Works Internally
▼

Static Batching

The server accumulates requests in a queue until exactly \(B\) of them are present, then runs one forward pass on all \(B\) together. Simple, and it maximizes GPU utilization per pass — but the first request in the queue must wait for \(B-1\) more requests to show up. At low traffic that wait can be unbounded.

Dynamic Batching

Same idea, but with an escape hatch: the batch fires when it reaches max size \(B\) or a timeout \(T\) elapses since the oldest queued request arrived — whichever happens first. This caps worst-case latency at \(T\) while still batching aggressively under load. Almost every production serving stack (TF Serving, Triton, TorchServe) implements this.

Adaptive / Continuous Batching

Static and dynamic batching assume every request in a batch takes the same amount of compute and finishes at the same time — true for fixed-shape vision/tabular models, false for autoregressive LLM generation where one prompt might need 5 tokens and another 500. Continuous batching (a.k.a. iteration-level scheduling, introduced by the Orca paper and used in vLLM/TGI/TensorRT-LLM) treats the GPU as a fixed number of "slots." At every decode step, any slot whose sequence just finished is immediately refilled from the queue, while every other slot advances its own sequence by one token. The batch composition is fluid — new requests join mid-flight without waiting for the whole cohort to finish.

🔑 Key Property

Continuous batching decouples admission (when a request starts) from completion (when a request finishes) at the granularity of one model step, instead of one whole batch. This is what makes it dramatically better for variable-length generative workloads.

3
Why It Works — The Math
▼

Expected Queueing Wait (Static Batching)

Requests arrive as a Poisson process with rate \(\lambda\). To fill a batch of size \(B\), the server waits for \(B-1\) more arrivals after the first request. Since inter-arrival times are exponential with mean \(1/\lambda\), the expected wait for the first request in the batch is:

$$\mathbb{E}[\text{wait}] = \frac{B-1}{\lambda}, \qquad \mathbb{E}[\text{latency}] = \frac{B-1}{\lambda} + T_{\text{proc}}(B)$$

where \(T_{\text{proc}}(B) \approx T_0 + kB\) is the (mildly batch-size-dependent) forward-pass time. As \(\lambda \to 0\) (low load), wait time diverges — this is the static-batching latency cliff.

Dynamic Batching Bounds the Wait

$$\mathbb{E}[\text{wait}] = \min\!\left(\frac{B-1}{\lambda},\; T_{\text{timeout}}\right)$$

The timeout \(T_{\text{timeout}}\) is a knob: smaller values bound tail latency tighter at the cost of smaller (less GPU-efficient) batches under low load.

Continuous Batching Throughput

With \(S\) concurrent slots and mean per-token service time \(\bar{s}\), the system behaves like an \(M/M/S/S\)-style loss-free server as long as slots are refilled instantly on completion. Steady-state GPU utilization and max sustainable throughput are:

$$\rho = \frac{\lambda \cdot \bar{s} \cdot \bar{L}}{S}, \qquad \text{Throughput}_{\max} \approx \frac{S}{\bar{s}}$$

where \(\bar{L}\) is the mean number of decode steps per request. Because slots refill immediately rather than waiting for the slowest sequence in a cohort, \(\rho\) stays high even when request lengths are highly variable — the key structural advantage over static/dynamic batching for LLMs.

⚠️ Common Pitfall

Continuous batching isn't free — it requires the model's KV cache to support per-sequence, variable-length memory (paged attention, etc.), because slots now hold sequences at different generation lengths simultaneously. Static/dynamic batching can assume a single fixed tensor shape for the whole batch; continuous batching cannot.

Key Takeaways
▼

When to use each:

  • Static batching — offline/batch scoring jobs where all inputs are known ahead of time and latency doesn't matter (nightly recommendation scoring, bulk embeddings).
  • Dynamic batching — online serving of fixed-shape models (image classifiers, embedding models, small transformers) with a latency SLA; Triton/TF-Serving-style deployments.
  • Continuous / adaptive batching — autoregressive LLM serving where output length is unknown ahead of time and requests have wildly different generation lengths; this is the default in vLLM, TGI, TensorRT-LLM, and Orca-style schedulers.

Watch out for:

  • Static batching can starve requests indefinitely under low load — there's no bound on tail latency.
  • Dynamic batching's timeout is a direct latency/throughput dial — tune it per SLA, not once globally.
  • Continuous batching needs paged/chunked KV-cache memory management or it will fragment GPU memory as sequences of different lengths coexist.
💡 Hierarchy

Static (fires on count only) ⊂ Dynamic (fires on count OR timeout) ⊂ Continuous (fires — refills — every single iteration, per-slot). Each generalizes the previous by shrinking the unit of scheduling from "whole batch" down to "one iteration."

Code Trace
▼
# --- Static batching ---
def static_batch(queue, B):
batch = []
while len(batch) < B:
batch.append(queue.pop()) # blocks until B requests arrive
return run_model(batch) # fires ONLY when full
# --- Dynamic batching ---
def dynamic_batch(queue, B, timeout_ms):
batch = []
deadline = now() + timeout_ms
while len(batch) < B and now() < deadline:
if queue:
batch.append(queue.pop())
return run_model(batch) # fires on B OR timeout
# --- Continuous (adaptive) batching ---
def continuous_batching_loop(queue, slots):
while True:
for slot in slots:
if slot.is_free() and queue:
slot.assign(queue.pop()) # admit mid-flight, no wait
active = [s for s in slots if s.busy]
step_decode(active) # ONE token per active seq
for slot in active:
if slot.sequence.is_finished():
emit(slot.sequence)
slot.free() # refilled next iteration
