Understanding Tool Use & Function Calling
▼

What is it? Large Language Models (LLMs) are great at understanding and generating human-like text. But to interact with the real world — booking flights, sending emails, querying databases — they need to produce structured, machine-readable commands. "Tool use" (or "function calling") is the capability where an LLM, given a user's natural language query and a list of available tools (APIs) with their specifications (JSON Schema), decides if a tool is needed, which one, and generates the precise JSON arguments to call it.

Analogy: Imagine a highly intelligent but physically confined research assistant. They can understand complex requests and access vast libraries of knowledge. But to *act* in the world (e.g., "order a book," "schedule a meeting"), they need to instruct a separate, specialized "robot arm" (the tool). Function calling is the precise, structured command language (JSON) that the assistant uses to tell the robot arm exactly what to do, based on a manual (JSON Schema) describing what the arm can do and what inputs it needs.

💡 If you remember one thing

Function calling bridges the gap between LLM reasoning and real-world action. It transforms an LLM's free-form text generation into reliable, schema-validated API calls, making LLMs programmable agents rather than just conversational interfaces.

2
How It Works Internally
▼

The Core Mechanism

The process involves several steps, usually orchestrated by an external application:

  1. Tool Definition: The developer provides the LLM (via the API) with a list of available functions. Each function includes its name, a natural language description (for the LLM to understand its purpose), and a JSON Schema describing the required and optional arguments.
  2. User Query & LLM Call: A user submits a query (e.g., "What's the weather in London?"). The application sends this query *along with the tool definitions* to the LLM.
  3. LLM Generation: The LLM, instead of generating a direct natural language response, might generate a special token indicating a "function call," followed by a JSON object containing the function's name and its arguments, all conforming to the provided schema.
  4. Parsing & Validation: The application parses the LLM's output. It then validates the generated JSON against the specified schema to ensure all required fields are present and data types/formats are correct.
  5. Tool Execution (Optional): If the JSON is valid, the application executes the actual external function (e.g., calls a weather API) with the LLM-generated arguments.
  6. Tool Output & Multi-turn: The result from the tool (e.g., weather data) is then fed back to the LLM as part of a subsequent prompt. The LLM uses this information to generate a final, natural language response to the user.

JSON Schema: The Contract

JSON Schema is a powerful, standardized way to describe the structure and validation rules for JSON data. For function calling, it acts as a contract between the LLM and the external tool. Key elements:

  • type: Specifies the data type (e.g., "string", "number", "object", "array").
  • properties: Defines the expected keys (arguments) within a JSON object and their respective schemas.
  • required: An array of property names that *must* be present.
  • enum: A list of allowed values for a string property (e.g., ["celsius", "fahrenheit"]).
  • description: A human-readable explanation of the property's purpose, crucial for the LLM.
🔑 Key Property

The LLM is fine-tuned on vast datasets of tool definitions and corresponding valid JSON outputs. This training teaches it to understand JSON Schema and generate syntactically and semantically correct JSON when prompted with tool descriptions, not just rely on in-context examples.

Why It Works — Probabilistic Constrained Generation
▼

LLM Generation as a Probability Distribution

At its core, an LLM predicts the next token based on the preceding tokens and the input prompt. This is a conditional probability distribution over the vocabulary:

$$P(t_i | t_{

When tool definitions are provided, the prompt effectively expands to include these definitions, guiding the model's token generation towards tool calls:

$$P(t_i | t_{

The "trick" of function calling is that during pre-training and/or fine-tuning, the LLM has learned to associate specific natural language intents (e.g., "What's the weather?") with the structured syntax of tool calls (e.g., {"name": "get_weather", "args": {...}}) when tool definitions are present in the context.

Schema as a Strong Prior / Soft Constraint

The JSON Schema provided for each tool acts as a powerful statistical prior during generation. The LLM's internal representation learns that certain token sequences (e.g., "location": "...") are highly probable following a "get_weather" function name, and that `location` is a `string` and `required`. While not a hard constraint during token-by-token generation (the model *could* still generate invalid JSON), the learned probabilities strongly favor valid structures.

Consider the probability of generating a sequence of tokens that forms a valid JSON for a `get_weather` call:

$$P(\text{JSON}_{\text{valid}} | \text{Prompt}, \text{get\_weather\_schema}) = \prod_{i=1}^k P(t_i | t_{

The LLM's training aims to maximize this probability for correct tool calls, making it highly likely to generate a valid JSON object. If a generated token sequence would lead to an invalid JSON structure (e.g., a missing required field, or a string where a number is expected), the model's internal "grammar" of JSON (learned from vast data) assigns a lower probability to such sequences.

⚠️ Common Pitfall

Function calling is not foolproof. The LLM might still: (1) refuse to call a tool when it should, (2) call a tool with incorrect or hallucinated arguments, or (3) generate malformed JSON. Robust applications include post-generation validation (against the schema) and error handling to gracefully recover from such cases.

Key Takeaways

    
▼

  

  

    
When to leverage Tool Use / Function Calling:

    
    
      
  • Structured Output: When your application needs machine-readable JSON (not just natural language) from the LLM.
    • 
      
  • External Integration: To connect LLMs with external APIs, databases, or custom code, enabling them to perform actions beyond pure text generation.
    • 
      
  • Grounding & Accuracy: To ground LLM responses in real-world data (e.g., current weather, up-to-date stock prices) rather than relying on potentially outdated or hallucinated internal knowledge.
    • 
      
  • Complex Workflows: Orchestrating multi-step processes where the LLM acts as a planner, delegating specific tasks to tools.
    • 
    

    
When to reconsider or use with caution:

    
    
      
  • Simple Q&A: For tasks that only require a natural language response and no external action, tool use adds unnecessary complexity and latency.
    • 
      
  • Latency-Sensitive Applications: Executing external tools adds network latency. If real-time response is paramount, a direct LLM response might be preferred.
    • 
      
  • Over-reliance: Don't use tools for tasks the LLM is already perfectly capable of doing internally (e.g., simple arithmetic, general knowledge questions).
    • 
      
  • Security: Always validate LLM-generated arguments server-side before executing any tool, especially for functions that modify data or access sensitive resources.
    • 
    

    

      
💡 Big Picture

      
Function calling is a fundamental building block for LLM agents. By allowing LLMs to interact with the world in a structured, programmatic way, it transforms them from passive text generators into active problem-solvers capable of planning, executing, and iterating on tasks.

from jsonschema import validate, ValidationError

      

      
# 1. Define available tools with JSON Schema

      
tools = [

      
    {

      
        "name": "get_current_weather",

      
        "description": "Get the current weather in a given location",

      
        "parameters": { # JSON Schema for function arguments

      
            "type": "object",

      
            "properties": {

      
                "location": {"type": "string", "description": "City and state, e.g. Boston, MA"},

      
                "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}

      
            },

      
            "required": ["location"]

      
        }

      
    },

      
    # ... other tool definitions (e.g., send_email)

      
]

      

      
# 2. Simulate LLM interaction (replace with actual API call)

      
def call_llm_with_tools(user_query, available_tools):

      
    # In a real scenario, this would be an API call to OpenAI/Anthropic/etc.

      
    # The LLM's response would be structured, e.g., messages[0].tool_calls

      
    if "weather" in user_query.lower() and "boston" in user_query.lower():

      
        return {

      
            "tool_name": "get_current_weather",

      
            "tool_args": {"location": "Boston, MA", "unit": "fahrenheit"}

      
        }

      
    return {"tool_name": None, "tool_args": None} # No tool call

      

      
# 3. Implement actual tool functions

      
def get_current_weather(location, unit="fahrenheit"):

      
    # This would call a real weather API

      
    if "boston" in location.lower():

      
        return f"70°{unit[0].upper()} and sunny in Boston, MA"

      
    return "Weather data not available for this location."

      

      
# 4. Orchestration logic (main loop)

      
def orchestrate_tool_call(user_query):

      
    llm_response = call_llm_with_tools(user_query, tools)

      
    tool_name = llm_response["tool_name"]

      
    tool_args = llm_response["tool_args"]

      

      
    if tool_name:

      
        # Find the schema for validation

      
        tool_schema = next((t["parameters"] for t in tools if t["name"] == tool_name), None)

      
        if not tool_schema: return "Error: Tool definition not found."

      

      
        # Validate LLM-generated arguments against schema

      
        try:

      
            validate(instance=tool_args, schema=tool_schema)

      
        except ValidationError as e:

      
            return f"Validation Error: {e.message}"

      

      
        # Execute the tool

      
        if tool_name == "get_current_weather":

      
            tool_output = get_current_weather(**tool_args)

      
        else:

      
            tool_output = f"Unknown tool: {tool_name}"

      

      
        # Feed tool output back to LLM for final response (multi-turn)

      
        final_llm_response = f"Based on the tool output: {tool_output}"

      
        return final_llm_response

      
    else:

      
        return "No tool call needed. LLM responds directly."
