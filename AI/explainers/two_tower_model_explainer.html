Two-Tower Retrieval Model

Separate user & item encoders projected into a shared space, searched with approximate nearest neighbours
Foundational Recommender Systems Retrieval / Candidate Generation O(log N) ANN query
1
Understanding the Two-Tower Model
▼

What is it? When a recommender system has to pick a handful of relevant items out of millions (or billions), it can't afford to score every item against every user with a big joint neural network — that's O(N) heavy computation per request. The two-tower model splits the problem in half: a User Tower encodes user features into a vector, an independent Item Tower encodes item features into a vector of the same dimensionality, and the two never see each other's raw inputs. Relevance is just the dot product (or cosine similarity) between the two vectors, in a shared embedding space.

Analogy: Imagine two translators who never talk to each other. One translates "what this user likes" into a universal language; the other translates "what this movie is about" into the same universal language. If the two translations land near each other in that language, they're a good match — even though the translators worked completely independently.

💡 If you remember one thing

Because the Item Tower never looks at the user, every item's embedding can be computed once, offline, for the whole catalog, and dropped into an approximate nearest neighbour (ANN) index. At request time you only run the (cheap) User Tower once, then query the index: $$\text{top-}K = \operatorname*{arg\,top\text{-}K}_{i \in \text{catalog}} \; \cos\big(f_u(x_u),\, f_i(x_i)\big)$$ This turns retrieval from an O(N) scan into an O(log N)-ish index lookup.

How It Works Internally
▼

Two Encoders, Zero Cross-Features

Each tower is typically an embedding layer (for categorical IDs) followed by an MLP: \(f_u(x_u) = \text{MLP}_u(x_u) \in \mathbb{R}^d\) and \(f_i(x_i) = \text{MLP}_i(x_i) \in \mathbb{R}^d\). The critical architectural constraint is that no feature ever crosses between the towers before the final similarity function. That's what makes item embeddings precomputable — a cross-encoder that concatenates \((x_u, x_i)\) and feeds them into one network (like a ranking model) cannot be cached this way, because every user-item pair needs its own forward pass.

The Shared Embedding Space

Both towers output vectors of the same dimension \(d\), usually L2-normalized so that the dot product equals cosine similarity, keeping scores bounded in \([-1, 1]\) and training well-behaved:

$$u = \frac{f_u(x_u)}{\lVert f_u(x_u) \rVert_2}, \qquad v_i = \frac{f_i(x_i)}{\lVert f_i(x_i) \rVert_2}, \qquad s(u, i) = u^\top v_i = \cos(\theta_{u,i})$$

Serving Pipeline: Offline vs. Online

Offline (batch): run the Item Tower over the entire catalog once, build an ANN index (FAISS, ScaNN, HNSW, Annoy) over all item embeddings, refresh periodically as the catalog changes.

Online (real time): run the User Tower once for the incoming request (cheap — one forward pass), query the prebuilt ANN index for the top-K nearest item vectors, then hand those K candidates to a heavier second-stage ranking model that does use cross-features for the final ordering.

🔑 Key Property

Two-tower models solve candidate generation (recall stage), not final ranking. They must be fast enough to search millions of items in milliseconds — accuracy is traded for speed via approximate nearest neighbour search, and a downstream ranker recovers precision on the shortlist.

3
Why It Works — The Math
▼

Training: Contrastive / Sampled Softmax Loss

Given a batch of \((u, i^+)\) positive pairs (user, item they engaged with), the standard objective treats every other item in the batch as a cheap negative (in-batch negatives) and maximizes the softmax probability of the true positive:

$$\mathcal{L} = -\log \frac{\exp\big(s(u, i^+)/\tau\big)}{\sum_{j \in \text{batch}} \exp\big(s(u, i_j)/\tau\big)}$$

where \(\tau\) is a temperature that sharpens or softens the distribution. The gradient of this loss pulls \(u\) and \(v_{i^+}\) together and pushes \(u\) away from every negative \(v_{i_j}\) — exactly the contrastive signal that shapes the shared space so cosine similarity means relevance.

ANN Search: Why It Beats Brute Force

Exact retrieval scores every item: \(O(N \cdot d)\) per query. For \(N = 10^8\) that is far too slow for a real-time request. ANN structures avoid the full scan:

IVF (cluster-based): run k-means on the item embeddings offline to get \(k\) centroids (a coarse index). At query time, compare \(u\) to only the \(k\) centroids — \(O(k \cdot d)\) — then exhaustively score just the items inside the \(n_{\text{probe}}\) nearest cells: \(O(\frac{N}{k} \cdot n_{\text{probe}} \cdot d)\), typically orders of magnitude cheaper than scanning everything.

HNSW (graph-based): item embeddings form a multi-layer navigable graph; a query greedily hops toward closer neighbours from a fixed entry point, converging in roughly \(O(\log N)\) hops instead of a linear scan.

⚠️ Common Pitfall

ANN search is approximate — recall@K < 1.0 by design. An item can be a true top match yet sit in the "wrong" partition and get missed entirely. Also, naive in-batch negatives bias training toward popular items (they appear as negatives more often), and item embeddings go stale the moment the catalog changes, requiring periodic re-indexing.

Key Takeaways
▼

When to use two-tower + ANN:

  • Candidate generation / recall stage of large-scale recommenders (YouTube, Pinterest, Google Play, e-commerce search)
  • Semantic / dense retrieval for search and question answering
  • Ads targeting and lookalike audience retrieval
  • Any setting with millions+ candidates and a tight latency budget

When NOT to use:

  • Small catalogs (thousands of items) — brute-force exact search is already fast and simpler
  • When user-item feature interactions matter a lot for the final decision — two-tower can't model them; you still need a cross-feature ranker downstream
  • Cold-start items/users with no history — the towers have little signal to encode
💡 Hierarchy

Exact brute-force kNN (perfect recall, O(N)) ⊃ IVF / HNSW / PQ (ANN) (near-perfect recall, O(log N)–O(√N)) — each ANN method trades a controllable amount of recall for a large speedup, and the two-tower architecture is what makes the item side of that trade cacheable in the first place.
