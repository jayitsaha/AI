Dynamic Quantization

Quantizing activations on-the-fly for efficient inference in LLMs and beyond
Intermediate Deep Learning MLOps / Systems ~2-4x speed/memory

Understanding Dynamic Quantization
▼

What is it? Quantization reduces the numerical precision of model parameters (weights) and intermediate computations (activations) from high-precision floats (e.g., 32-bit, FP32) to lower-precision integers (e.g., 8-bit, INT8). This saves memory and enables faster computations on specialized hardware. Dynamic quantization is a post-training technique where model weights are converted to INT8 once, but activations are quantized dynamically at inference time, meaning their quantization parameters (scale and zero-point) are computed on-the-fly for each tensor based on its actual value range.

Analogy: Imagine a master chef (your model) who typically measures ingredients with extreme precision (FP32). Now, they need to cook faster for a large crowd, using simpler tools (INT8). For staple ingredients (like weights) that are always the same, they can pre-measure and store them in simpler containers. But for fresh, variable ingredients (like activations, e.g., a batch of vegetables that varies in size and weight), they quickly weigh *each batch* to determine the best way to fit them into the simpler containers, ensuring minimal waste (quantization error). This dynamic measurement for variable inputs is key to maintaining quality while speeding up the process.

💡 If you remember one thing

Dynamic quantization is an inference-only technique. Weights are pre-quantized (static), but activations are quantized per-tensor at runtime by observing their actual min/max values. This adapts to the highly variable ranges of activations, minimizing quantization error without needing a calibration dataset.

How It Works Internally
▼

The Core Mechanism: Weights Static, Activations Dynamic

Dynamic quantization follows a specific pipeline during inference:

  1. Weights (W) are statically quantized: Before inference, the model's weights are converted from FP32 to INT8 (or other integer types). This is a one-time process, and their scale and zero-point are fixed. They remain INT8 throughout inference.
  2. Activations (X) are FP32 inputs: When an input (or an intermediate activation tensor) arrives at a layer, it is initially in FP32 format.
  3. Dynamic scale and zero-point computation: For each incoming activation tensor, its actual minimum and maximum FP32 values are observed. Based on this observed range and the target integer range (e.g., \([-128, 127]\) for signed INT8), a specific quantization scale (\(S\)) and zero-point (\(Z\)) are computed.
  4. Quantize activations: The FP32 activation tensor is then quantized to INT8 using the dynamically computed \(S\) and \(Z\).
  5. Quantized computation: Operations like matrix multiplications are performed using the INT8 weights and the newly quantized INT8 activations. This is where the primary speedup and memory savings occur.
  6. Dequantize results: The output of these INT8 operations is typically dequantized back to FP32 for subsequent layers, especially for non-linear operations (like ReLU, Softmax) that are often more stable in FP32, or for the final output.

The "dynamic" aspect refers exclusively to the activations. Weights are always statically quantized in this scheme.

Why Dynamic for Activations?

Unlike weights, which are fixed after training, the value distribution of activations can vary significantly not only between different layers but also for different inputs to the same layer. A fixed, pre-determined quantization scale for activations would either lead to severe clipping (if the scale is too small) or poor utilization of the integer range (if the scale is too large), resulting in high quantization error. By computing \(S\) and \(Z\) dynamically for each activation tensor, we ensure the optimal mapping from the observed FP32 range to the available INT8 range, thus minimizing information loss.

🔑 Key Property

Dynamic quantization is a pragmatic trade-off. It offers most of the memory and speed benefits of integer arithmetic while sidestepping the need for a calibration dataset (required by static quantization) and mitigating the accuracy drop that fixed-range activation quantization would cause. The runtime overhead of finding min/max is usually negligible for large tensors.

Why It Works — The Math
▼

The Quantization and Dequantization Formulas

The core of quantization is mapping a real-valued float \(F\) to an integer \(Q\) and back. This linear mapping is defined by a scale factor \(S\) and a zero-point \(Z\):

$$Q = \text{round}\left(\frac{F}{S} + Z\right) \quad \text{and} \quad F \approx (Q - Z) \cdot S$$

Here, \(Q\) is clamped to the target integer range (e.g., \([-128, 127]\) for INT8). The zero-point \(Z\) represents the FP32 value of \(0\) in the quantized integer domain, ensuring that \(0\) can be represented exactly (important for ReLU activations).

Deriving Scale and Zero-Point Dynamically (Asymmetric Quantization)

For a given FP32 tensor, we observe its minimum value \(\text{min}_{fp32}\) and maximum value \(\text{max}_{fp32}\). Let the target integer range be \([\text{min}_{int}, \text{max}_{int}]\) (e.g., \([-128, 127]\) for signed INT8). We want to linearly map \([\text{min}_{fp32}, \text{max}_{fp32}]\) to \([\text{min}_{int}, \text{max}_{int}]\). The scale \(S\) is the ratio of the ranges:

$$S = \frac{\text{max}_{fp32} - \text{min}_{fp32}}{\text{max}_{int} - \text{min}_{int}}$$

The zero-point \(Z\) is then derived by determining what integer value corresponds to \(\text{min}_{fp32}\):

$$Z = \text{min}_{int} - \text{round}\left(\frac{\text{min}_{fp32}}{S}\right)$$

This is called asymmetric quantization because the zero-point is typically non-zero, allowing the integer range to fully cover the observed FP32 range, even if it's entirely positive or negative.

Symmetric Quantization (Common for Weights)

For weights, a common practice is symmetric quantization, where the zero-point \(Z\) is fixed at \(0\). This simplifies calculations but requires the FP32 range to be centered around zero. The scale is determined by the maximum absolute value:

$$S = \frac{\max(|\text{min}_{fp32}|, |\text{max}_{fp32}|)}{\text{max}_{int}} \quad (\text{assuming } \text{min}_{int} = -\text{max}_{int})$$

The integer range then becomes \([-\text{max}_{int}, \text{max}_{int}]\). Symmetric quantization can introduce more error if the FP32 range is highly asymmetric (e.g., \([0.1, 10.0]\)), as it would force the quantized range to be \([-10.0, 10.0]\), wasting half the integer range.

⚠️ Common Pitfall

The overhead of dynamic min/max finding and scale/zero-point computation, while small for large tensors, can become a bottleneck for layers with many small tensors (e.g., element-wise operations, or very small batch sizes). For optimal performance, ensure your runtime environment (e.g., GPU, specialized NPU) has hardware support for efficient min/max finding and quantization parameter calculation.

Key Takeaways
▼

When to use Dynamic Quantization:

  • Memory-constrained inference: Reduces model size and activation memory footprint, critical for edge devices or large models (e.g., LLMs).
  • Latency-sensitive applications: Exploits faster integer arithmetic on modern hardware (e.g., GPU Tensor Cores, NPUs).
  • Models with highly varying activation ranges: Especially beneficial for RNNs, LSTMs, and certain transformer layers where activation distributions can shift dramatically.
  • No calibration dataset available: Unlike static quantization, dynamic quantization does not require a representative dataset to pre-calibrate activation ranges, simplifying deployment.
  • First step for post-training quantization: It's often the easiest and most robust post-training quantization method to apply, providing good performance-accuracy trade-offs out of the box.

When NOT to use Dynamic Quantization:

  • Accuracy is paramount: While good, dynamic quantization still introduces approximation error. If absolute FP32 accuracy is non-negotiable, avoid it.
  • Models with many small tensors: The overhead of dynamically computing min/max and S/Z for many small tensors can negate performance gains.
  • Static quantization achieves better accuracy: For some models and tasks, static quantization (with a good calibration set) can achieve higher accuracy by optimizing for the exact distribution of activations.
  • Training: Dynamic quantization is for inference only. For quantization during training, you would use Quantization-Aware Training (QAT).
💡 Rule of Thumb

Dynamic quantization is a robust "set-and-forget" post-training quantization technique for inference. It offers significant speedups and memory reductions for many models, especially those with recurrent layers or large fully-connected layers, without requiring extensive fine-tuning or data collection. Think of it as `qint8` for weights, and `fp32 -> qint8` on-the-fly for activations.

Code Trace — PyTorch Example
▼
import torch
import torch.nn as nn
import torch.quantization as quantization
# 1. Define a simple model (e.g., a linear layer)
class MyModel(nn.Module):
def __init__(self):
super().__init__()
self.linear = nn.Linear(10, 5) # FP32 weights/bias
def forward(self, x):
return self.linear(x)
model_fp32 = MyModel()
# 2. Prepare the model for dynamic quantization
# This tells PyTorch which layers to dynamically quantize.
# For dynamic, typically only nn.Linear and nn.RNN/LSTM/GRU are supported.
model_fp32.eval() # Set to evaluation mode (essential!)
qconfig = quantization.get_default_dynamic_qconfig('fbgemm')
model_prepared = quantization.prepare_dynamic(model_fp32, qconfig_dict={'': qconfig})
# 3. Convert the prepared model to a quantized model
# This step performs the actual quantization. Weights are converted to INT8.
# Activations are left as FP32, but the layer is wrapped to handle dynamic quantization.
model_quantized = quantization.convert_dynamic(model_prepared)
print("Quantized Model:")
print(model_quantized)
# 4. Inference with the quantized model
# Activations (input_fp32) will be dynamically quantized at runtime.
input_fp32 = torch.randn(1, 10)
output_quantized = model_quantized(input_fp32)
# Compare memory usage (rough estimate)
# print(f"FP32 model size: {sum(p.numel() * p.element_size() for p in model_fp32.parameters()) / 1024**2:.2f} MB")
# print(f"Quantized model size: {sum(p.numel() * p.element_size() for p in model_quantized.parameters()) / 1024**2:.2f} MB")
