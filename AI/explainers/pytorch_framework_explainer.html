Understanding PyTorch
▼

What is it? PyTorch is a scientific computing library that treats tensors (multi-dimensional arrays of numbers) as first-class objects. Its killer feature is dynamic autograd: as your Python code runs operations on tensors, PyTorch secretly builds a computation graph. When you call .backward(), it traverses that graph in reverse to compute all the gradients you need to train a neural network.

Analogy: Imagine you're baking a cake and someone follows you around writing down every step — which ingredients you mixed, in what order, at what temperature. If the cake comes out wrong, they can trace back exactly which step to blame and tell you how to adjust each one. PyTorch's autograd is that note-taker: it watches every tensor operation, then propagates "how wrong was I?" backwards through all those steps.

💡 If you remember one thing

PyTorch's define-by-run (dynamic) graph: the computational graph is built as ops execute, not before. This means if/for/while in your model are real Python — no static graph compilation needed. .backward() walks the graph in reverse applying the chain rule; .grad on each leaf accumulates the gradient.

How Autograd & nn.Module Work Internally
▼

Tensor Internals

A torch.Tensor is a view over a contiguous block of memory (a storage). The tensor carries: a dtype, a device, shape, stride, and — critically — a grad_fn attribute pointing to the backward function that created it, plus a requires_grad flag.

🔑 The Two Tensor Worlds

Leaf tensors (created by the user, not by ops): requires_grad=True → grad_fn=None. Their .grad is populated by .backward(). Non-leaf tensors (outputs of ops): have a grad_fn, and their .grad is NOT retained by default (use .retain_grad() to keep it).

Dynamic Computation Graph (Define-by-Run)

Every time you perform an operation on a tensor with requires_grad=True, PyTorch creates a Function object (a C++ struct behind the Python API) that records: the operation, references to its input tensors, and the rule for computing the backward gradient. This Function is stored as output.grad_fn. The full graph is an implicit DAG of these Function nodes.

Contrast with TensorFlow 1.x's define-and-run: there, you built a static graph then fed data. PyTorch rebuilds the graph every forward pass — so if/for branches are real Python with real values, making debugging trivial.

autograd.backward() — The Engine

Calling loss.backward() initializes the gradient of loss to 1.0 and invokes the C++ autograd engine. The engine performs a reverse BFS/topological traversal of the grad_fn DAG, calling each Function's .backward() (the VJP — vector-Jacobian product). Each call accumulates into the .grad attribute of leaf tensors.

⚠️ Common Mistake: Forgetting zero_grad()

optimizer.zero_grad() (or set_to_none=True for efficiency) MUST be called before each forward pass. PyTorch accumulates gradients into .grad — without clearing, gradients from multiple batches sum together. This is intentional (useful for gradient accumulation tricks), but catastrophic if forgotten.

nn.Module — The Parameter Container

nn.Module wraps tensors into a tree of sub-modules. Its key jobs: (1) parameter registration — any nn.Parameter assigned as an attribute is auto-registered and returned by .parameters(); (2) hooks — forward/backward hooks can intercept activations or gradients; (3) state_dict — serializes weights; (4) train/eval mode — switches BatchNorm and Dropout behavior.

Hooks for Inspecting Internals

PyTorch provides four hook types: register_forward_hook (fires after forward on a layer's output), register_forward_pre_hook (fires on input), register_backward_hook / register_full_backward_hook (fires on gradient). Use hooks to debug vanishing gradients, extract activations for visualization, or implement gradient clipping per-layer.

The Math — Chain Rule & Gradient Mechanics
▼

The Chain Rule — What autograd Computes

For a composition \(L = f_n \circ \cdots \circ f_1(x)\), the chain rule gives:

$$\frac{\partial L}{\partial \theta_i} = \frac{\partial L}{\partial a_n} \cdot \frac{\partial a_n}{\partial a_{n-1}} \cdots \frac{\partial a_{i+1}}{\partial \theta_i}$$

autograd computes this via reverse-mode AD (backpropagation). At each node it computes the vector-Jacobian product (VJP): given upstream gradient \(\bar{v}\) and the Jacobian \(J\) of the op, it returns \(\bar{v}^\top J\) — never materializing the full Jacobian.

$$\text{VJP: } \bar{v}^\top J = \bar{v}^\top \frac{\partial \text{output}}{\partial \text{input}}$$

Numerical Trace: 2-Layer ReLU Network

Setup: \(x=[2.0, 3.0]\), \(W_1 \in \mathbb{R}^{2 \times 2}\), \(b_1 \in \mathbb{R}^2\), \(W_2 \in \mathbb{R}^{1 \times 2}\), \(b_2 \in \mathbb{R}\), target \(y=3.0\).

Forward:

$$z_1 = W_1 x + b_1 = [1.70,\ 2.20], \quad a_1 = \text{relu}(z_1) = [1.70,\ 2.20]$$
$$z_2 = W_2 a_1 + b_2 = 2.00, \quad L = \tfrac{1}{2}(z_2 - y)^2 = 0.500$$

Backward: \(\frac{\partial L}{\partial z_2} = z_2 - y = -1.00\). Then:

$$\frac{\partial L}{\partial W_2} = \frac{\partial L}{\partial z_2} \cdot a_1^\top = -1.0 \times [1.70, 2.20] = [-1.70,\ -2.20]$$
$$\frac{\partial L}{\partial a_1} = \frac{\partial L}{\partial z_2} \cdot W_2 = -1.0 \times [0.6, 0.4] = [-0.60,\ -0.40]$$
$$\frac{\partial L}{\partial z_1} = \frac{\partial L}{\partial a_1} \odot \mathbf{1}[z_1 > 0] = [-0.60,\ -0.40] \odot [1, 1] = [-0.60,\ -0.40]$$
$$\frac{\partial L}{\partial W_1} = \frac{\partial L}{\partial z_1} \otimes x^\top = \begin{bmatrix}-1.2 & -1.8 \\ -0.8 & -1.2\end{bmatrix}$$
📐 Mixed Precision (AMP) — The Scaler Math

FP16 has range ≈ \(6 \times 10^{-5}\) to \(65504\). Small gradients underflow. AMP's GradScaler multiplies the loss by scale \(s\) (e.g. 65536) before backward, giving gradients \(s \cdot g\). After backward, unscale: \(g' = g/s\). If any \(g'\) is inf/NaN, skip the step and halve \(s\); else step and (optionally) grow \(s\). FP16 matmuls run in Tensor Cores (≈ 8× throughput), weights/master copy remain FP32.

⚠️ ReLU Dead Neuron Problem

If \(z_1 \leq 0\), the ReLU gradient mask is 0. That neuron's upstream parameters receive zero gradient — permanently if the neuron stays negative. This is the "dying ReLU" problem. Leaky ReLU / ELU / GELU fix this by keeping a small gradient for negative inputs.

x = torch.tensor([2.0, 3.0]) # leaf, requires_grad=False
W1 = nn.Parameter(torch.tensor([[0.5,0.2],[-0.3,0.8]])) # leaf, requires_grad=True

a1 = torch.relu(z1) # a1=[1.70,2.20]; a1.grad_fn=ReluBackward; saves mask=[1,1]
W2 = nn.Parameter(torch.tensor([0.6, 0.4]))
z2 = a1 @ W2 + b2 # z2=2.000; z2.grad_fn=AddmmBackward
y_true = torch.tensor(3.0)
loss = 0.5 * (z2 - y_true)**2 # loss=0.500; loss.grad_fn=MseLossBackward
loss.backward() # seeds gradient=1.0 at root, starts BFS traversal
# dL/dz2 = z2 - y_true = 2.00 - 3.00 = -1.000
# W2.grad = dL/dz2 * a1 = [-1.70, -2.20]; b2.grad = -1.00
# dL/da1 = dL/dz2 * W2 = [-0.60, -0.40] (VJP through AddmmBackward)
# dL/dz1 = dL/da1 * relu_mask = [-0.60,-0.40]*[1,1] = [-0.60,-0.40]
# W1.grad = outer(dL/dz1, x) = [[-1.2,-1.8],[-0.8,-1.2]]; b1.grad=[-0.6,-0.4]
optimizer.step() # theta -= lr * theta.grad (e.g., W2 -> [0.617, 0.422])
optimizer.zero_grad(set_to_none=True) # CRITICAL: clear .grad for next batch

AMP · DDP · FSDP · torch.compile
▼

Mixed Precision Training (AMP)

Use torch.amp.autocast(device_type='cuda') as a context manager around forward + loss. Inside, eligible ops (matmul, conv) automatically run in FP16 (or BF16 on Ampere+) for ≈2–4× speedup and 50% memory. Use torch.amp.GradScaler to scale loss before backward so small FP16 gradients don't underflow.

💡 BF16 vs FP16

BF16 (bfloat16) has the same exponent range as FP32 but fewer mantissa bits. It rarely overflows — so no GradScaler needed on Ampere/Hopper GPUs. Prefer BF16 for LLMs; FP16 for older hardware. Use dtype=torch.bfloat16 in autocast.

Distributed Data Parallel (DDP)

DDP wraps your model: each GPU runs an identical copy. After each backward, gradients are all-reduced (averaged) across all ranks using the NCCL backend — so every GPU has identical gradients and stays in sync. The key insight: all-reduce happens overlapping with backward via bucket-based gradient communication, minimizing idle time.

Setup: dist.init_process_group("nccl"), wrap model in DDP(model, device_ids=[rank]), use DistributedSampler in DataLoader. Each rank sees a disjoint data shard — global batch size = per-GPU batch × world size.

⚠️ DDP Pitfalls

(1) Don't call .backward() inside with model.no_sync(): unless intentionally doing gradient accumulation — sync is suppressed. (2) All conditional branches must be consistent across ranks or DDP hangs. (3) BatchNorm by default is NOT synced across ranks — use nn.SyncBatchNorm for that.

Fully Sharded Data Parallel (FSDP)

DDP replicates parameters on every GPU — infeasible for 70B+ models. FSDP shards parameters, gradients, and optimizer states across GPUs. During forward/backward, each layer's parameters are all-gathered (temporarily unsharded) just-in-time, then resharded. This lets you fit models that are N× larger than a single GPU's memory, where N is the world size.

FSDP2 (PyTorch 2.x) uses DTensor for cleaner sharding semantics. Key configs: ShardingStrategy.FULL_SHARD (max savings), SHARD_GRAD_OP (keep full params during forward, shard grads), auto_wrap_policy to choose which layers to wrap.

TorchScript

TorchScript serializes PyTorch models to a static graph (IR) that can be deployed without Python. Two modes: torch.jit.trace (records ops for a specific input shape — fast but doesn't capture control flow) and torch.jit.script (compiles Python subset — handles if/for but requires type annotations). Produces a ScriptModule saveable with torch.jit.save() and loadable in C++ via LibTorch.

torch.compile (PyTorch 2.x)

torch.compile(model) applies the full optimization stack: (1) TorchDynamo — JIT-traces Python bytecode into FX graphs, capturing subgraphs where PyTorch ops are called; (2) AOT Autograd — traces both forward AND backward at graph level; (3) TorchInductor (default backend) — generates fused Triton GPU kernels, eliminating Python overhead, kernel launch latency, and memory round-trips.

Typical speedup: 20–50% on training, up to 2× on inference. Use mode="max-autotune" for aggressive kernel tuning (slow first run), mode="reduce-overhead" for small models. Incompatible with dynamic shapes by default — pass dynamic=True for variable-length inputs.
