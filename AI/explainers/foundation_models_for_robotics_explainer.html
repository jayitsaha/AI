Understanding Foundation Models for Robotics
▼

What is it? For decades, a robot manipulation policy was a bespoke pipeline: perception, planning, and control tuned per-task, per-robot. Foundation models for robotics flip this: pretrain one very large transformer on huge, diverse data (web images/text and/or teleoperated robot trajectories), then have it directly emit low-level actions for many tasks, objects and instructions it has never explicitly been trained on — the same "scale + generality" recipe that worked for language and vision.

Analogy: A classically-trained robot policy is like a line cook who only knows three exact recipes. RT-1 is a chef who has watched 130,000 kitchen demonstrations and can generalize across dishes. RT-2 is that chef after also reading the entire internet — now they recognize an ingredient they've never cooked with because they've read about it. SayCan is the maître d' who checks with the chef what dishes make sense (language) but also physically walks into the kitchen to see what's actually available right now (affordance) before committing to an order.

💡 If you remember one thing

A Vision-Language-Action (VLA) model treats robot control as next-token prediction: images and instructions go in, and discretized action tokens come out — exactly like a language model, just with a vocabulary that includes motor commands. SayCan then adds a second signal, an affordance function, so the language model's plan is filtered by what is physically possible: $$a^\star = \arg\max_{a} \; \underbrace{p_{\text{LLM}}(a \mid \text{instruction})}_{\text{useful?}} \cdot \underbrace{p_{\text{value}}(c_a=1 \mid s)}_{\text{doable?}}$$

How It Works Internally
▼

RT-1: a transformer that speaks actions

RT-1 (Robotics Transformer 1) ingests a short history of camera images and a natural-language instruction. Images pass through an EfficientNet CNN whose features are FiLM-conditioned on the instruction embedding — the language literally modulates which visual features matter. A TokenLearner module compresses each frame to just 8 salient tokens so the sequence stays short enough for a transformer to attend over in real time. The transformer then autoregressively predicts discretized action tokens (arm position/rotation deltas, gripper closedness, base motion, an episode-termination flag), each binned into one of 256 values. RT-1 was trained on ~130k teleoperated episodes spanning 700+ tasks on a real fleet of mobile manipulators.

RT-2: actions are just more text

RT-2 asks: why train a robot-only transformer from scratch when web-scale vision-language models already understand objects, spatial relations and instructions? RT-2 starts from a pretrained VLM (e.g. PaLI-X or PaLM-E) and co-fine-tunes it — continuing training on a mixture of the original web data (captioning, VQA) and robot trajectories, where actions are represented as literal number-strings ("1 128 91 241 5 101 127 217") reusing the model's existing text tokenizer. Nothing architecturally changes; a VLA is "just" a VLM whose output vocabulary happens to include motor-command numbers.

SayCan: let language propose, let affordances decide

An LLM is great at decomposing "bring me a snack" into candidate steps, but it has no idea whether a sponge is currently within reach of the gripper — it can hallucinate physically infeasible plans. SayCan grounds the LLM by pairing it with a library of learned, single-skill affordance functions (value functions trained with reinforcement learning) that estimate, from the current visual state, the probability each candidate skill can actually succeed right now. The LLM's language score and the affordance's feasibility score are multiplied per candidate, and the robot executes the arg-max skill — then the loop repeats with updated context.

🔑 Key Property

All three ideas compose along different axes: RT-1 gives a real-time tokenized action interface; RT-2 injects web-scale semantic priors into that interface; SayCan adds closed-loop, affordance-grounded long-horizon planning on top of any such low-level skill set.

RT-X / Open X-Embodiment: sharing a body plan isn't required

RT-X pools demonstration data from 22+ robot embodiments — single-arm tabletop manipulators, bi-manual ALOHA rigs, mobile manipulators, quadrupeds — with different sensors, camera placements and action spaces, into one training mixture for a single checkpoint. Despite the mismatched action spaces, jointly-trained RT-1-X / RT-2-X models outperform models trained only on a single embodiment's own data, showing that skills learned by one robot body can positively transfer to another.

Why It Works — The Math
▼

Discretizing continuous control

Each continuous action dimension \(a_i \in [a_{\min}, a_{\max}]\) (an arm-pose delta, a gripper command, ...) is uniformly binned into one of \(N=256\) integer tokens:

$$\text{tok}(a_i) = \operatorname{clip}\!\left(\left\lfloor \frac{a_i - a_{\min}}{a_{\max}-a_{\min}}(N-1) \right\rceil,\; 0,\; N-1\right)$$

An 8-dimensional action becomes an 8-token "sentence" the transformer predicts left-to-right — identical machinery to predicting the next word.

One loss to rule them all

Both RT-1 and RT-2 are trained with plain autoregressive next-token cross-entropy over the action tokens \(a_{1:T}\), conditioned on the multimodal context \(s\) (image history + instruction). For RT-2, the SAME loss is applied whether the target tokens are an image caption or an action string, in the same batch:

SayCan's affordance-grounded decoding

Given instruction \(i\), current state \(s\), and a fixed library of skills \(\mathcal{A}\), SayCan scores every candidate skill \(a \in \mathcal{A}\) by combining two independently-trained probabilities and executes the highest-scoring one:

$$f(a \mid i, s) = \underbrace{p_{\text{LLM}}(a \mid i)}_{\text{semantically useful}} \times \underbrace{p_{\text{value}}(c_a = 1 \mid s)}_{\text{physically feasible}} \qquad a^\star = \arg\max_{a \in \mathcal{A}} f(a \mid i, s)$$

Cross-embodiment data weighting

RT-X trains on a mixture of datasets \(d\) of very different sizes. Naively sampling proportional to episode count \(N_d\) would let huge datasets drown out small ones, so RT-X uses temperature-scaled ("square-root-like") mixture weights:

$$w_d = \frac{N_d^{\alpha}}{\sum_{d'} N_{d'}^{\alpha}}, \qquad 0 < \alpha < 1$$
⚠️ Common Pitfall

SayCan's product score is a greedy, one-step-lookahead heuristic — it can commit to a locally-good skill that dead-ends a long-horizon plan, and it inherits every blind spot of both the LLM (hallucinated subgoals) and the affordance model (miscalibrated value estimates on out-of-distribution scenes).

Key Takeaways
▼

When this recipe shines:

  • Multi-task manipulation where hand-coding a policy per task doesn't scale
  • Instructions/objects at deployment that were never in the robot demo data (RT-2's web transfer)
  • Long-horizon, language-specified tasks needing step decomposition (SayCan)
  • Pooling scarce robot data across many labs/robots to reach useful scale (RT-X)

When NOT to reach for it:

  • High-frequency, high-precision contact-rich control (insertion, cutting) — token-level 256-bin discretization and transformer inference latency can be too coarse/slow
  • Safety-critical settings needing verifiable guarantees — these are learned, imperfectly-calibrated policies, not certified controllers
  • Tiny data/compute budgets — the gains come specifically from web/cross-robot scale
💡 How the pieces fit together

RT-1 is the tokenized action interface. RT-2 upgrades that interface's brain with web-scale semantics. SayCan wraps any such skill set with LLM-proposed, affordance-checked long-horizon planning. RT-X scales the training data itself across robot bodies. They are complementary axes, not competing methods.

def tokenize_action(a, a_min, a_max):
frac = (a - a_min) / (a_max - a_min)
return int(clip(round(frac * (N_BINS - 1)), 0, N_BINS - 1))
def detokenize(tok, a_min, a_max):
return a_min + (tok / (N_BINS - 1)) * (a_max - a_min)

# ---- SayCan: LLM proposes, affordance functions dispose ----
def saycan_step(instruction, state, skills):
scored = []
for skill in skills:
p_lang = llm_score(instruction, skill) # "is this useful?"
p_afford = value_fn(state, skill) # "is this doable now?"
scored.append((skill, p_lang * p_afford))
best_skill, best_score = max(scored, key=lambda kv: kv[1])
return best_skill
