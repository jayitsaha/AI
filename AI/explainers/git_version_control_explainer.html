Understanding Git — The Core Idea
▼

What is it? Git is a distributed version control system that tracks changes to files over time. Every developer has a complete copy of the entire project history on their local machine — no central server is needed to commit, branch, or view history. You can work offline, share changes later, and merge parallel streams of work.

Analogy: Think of Git as a time machine crossed with a parallel-universe machine. Every commit is a saved snapshot of your whole project at a moment in time (time machine). Every branch is a parallel universe where you try out changes without affecting the main timeline. When you're happy, you can merge the parallel universe back into the main one.

Key insight — content-addressed storage: Unlike older systems that store diffs, Git stores complete snapshots. But it's not wasteful: it uses a content-addressed object store. Every file, tree (directory), and commit is stored under a SHA-1 (now transitioning to SHA-256) hash of its content. Identical content is only stored once.

💡 If you remember one thing

Git is a directed acyclic graph (DAG) of commit objects. Each commit points to its parent(s). Branches are simply named pointers to commits. HEAD is a pointer to the current branch pointer. This is not a metaphor — it's the literal data structure on disk in .git/objects/.

The Four Git Object Types

  • blob — stores file content (raw bytes). The SHA is sha1("blob " + size + "\0" + content).
  • tree — stores a directory listing: mode, name, and blob/tree SHA for each entry.
  • commit — stores a pointer to a root tree, parent commit SHA(s), author, committer, timestamp, and message.
  • tag — a named, signed pointer to any other object (usually a commit).

How Git Works Internally — Objects & the DAG
▼

The Commit Object in Detail

When you run git commit, Git performs these steps internally:

  1. Hash each staged file into a blob object: \(\text{SHA}_{blob} = \text{SHA1}(\texttt{"blob "} + n + \texttt{"\textbackslash0"} + \text{content})\)
  2. Build a tree object for each directory, recursively hashing entries.
  3. Build the root tree — a snapshot of the entire working tree.
  4. Create a commit object containing: root tree SHA, parent commit SHA(s), author, committer, and message.
  5. Update the current branch ref (e.g., .git/refs/heads/main) to point to the new commit SHA.
$$\text{SHA}_{commit} = \text{SHA1}\bigl(\text{"commit"} \;\|\; \text{tree}_{SHA} \;\|\; \text{parent}_{SHA} \;\|\; \text{author} \;\|\; \text{message}\bigr)$$

Because the commit SHA depends on its parent SHA (which depends on its parent, etc.), the chain is cryptographically tamper-evident: altering any historical commit changes every descendant SHA.

Branches and HEAD — Movable Pointers

A branch is literally a 41-byte file containing a commit SHA. main is stored at .git/refs/heads/main. HEAD is stored at .git/HEAD and normally contains ref: refs/heads/main (a symbolic ref). When you commit, Git advances the branch pointer. When you checkout a different branch, Git changes what HEAD points to and updates the working tree.

Merge vs Rebase — Two Strategies for Integration

Merge creates a new merge commit with two parents — it preserves the exact history of both branches. The resulting DAG has a "diamond" shape. Merge is non-destructive: no existing commits are changed.

Rebase re-applies commits from one branch onto another by creating new commit objects with new SHAs (the content diff is the same, but parent pointers and timestamps differ). The result is a linear history. Rebase rewrites history — never rebase commits already pushed to a shared remote.

⚠️ Golden Rule of Rebasing

Only rebase commits that exist exclusively in your local branch. Once commits are on a shared remote, rebasing causes diverging histories for teammates who have already based work on those commits — their git pull will show conflicts and duplicate commits.

Fast-Forward Merge

If the target branch (e.g., main) is a direct ancestor of the source branch (feature), Git can perform a fast-forward merge: it simply moves the main pointer forward to feature's tip. No merge commit is created. Use --no-ff to force a merge commit if you want to preserve branch topology in the log.

Branching Strategies — Git Flow, GitHub Flow, Trunk-Based
▼

Git Flow (Nvie, 2010)

Designed by Vincent Driessen for software with explicit versioned releases. Uses two long-lived branches:

  • main (or master) — always reflects production-ready code, tagged with version numbers.
  • develop — integration branch for features. Never deployed directly.

Supporting branch types: feature/* branches off develop; release/* branches off develop for stabilisation; hotfix/* branches off main for emergency patches (merged back to both main and develop). Pros: clear structure for versioned software. Cons: heavy overhead; the develop branch creates a merge bottleneck; poor fit for continuous delivery.

GitHub Flow (GitHub, 2011)

Streamlined for teams deploying continuously. Only one long-lived branch: main. Every change starts as a feature branch off main, gets a Pull Request (PR) with code review, passes CI, then merges to main and deploys immediately. Pros: simple, fast, great for CD. Cons: no explicit staging for releases; managing multiple concurrent versions is harder.

Trunk-Based Development (TBD)

Developers commit directly to main (trunk) multiple times per day — or use very short-lived feature branches (< 1 day). Large changes are hidden behind feature flags, not long-lived branches. Requires: comprehensive CI, feature flags, robust test coverage. This is how Google, Meta, and most high-velocity teams ship. Pros: eliminates merge hell, fastest integration. Cons: demands very high CI discipline and feature-flag infrastructure.

🔑 Decision Rule

Choose Git Flow if you ship versioned artifacts users install. Choose GitHub Flow for simple web/SaaS with one deployed version. Choose Trunk-Based Dev if you have strong CI and want to eliminate merge overhead — it's the gold standard for large engineering orgs.

Git LFS — Handling Large Files
▼

Why Large Files Break Git

Git stores every version of every file in .git/objects/. For source code (text files with small diffs), this is efficient — blobs compress well and pack files deduplicate. But binary large files (ML model weights, video assets, datasets, compiled binaries) have two problems: (1) they don't compress or delta-compress well, so every version is stored in full; (2) cloning or fetching requires downloading all historical versions, making the repo unusably large. A 1 GB model file committed 10 times = 10 GB in .git/objects/.

Git LFS Architecture

Git LFS (Large File Storage, open-sourced by GitHub in 2015) replaces large file blobs with tiny pointer files in the Git history, while the actual binary content is stored on a separate LFS server (GitHub LFS, GitLab LFS, S3-backed Artifactory, etc.).

A pointer file is a plain text file committed to Git that contains:

version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b1258daaa5e2ca24d17e2393
size 134217728

When you git checkout a branch, the LFS smudge filter intercepts the pointer file and downloads the actual binary from the LFS server, replacing the pointer with the real content. When you git add a tracked file, the clean filter uploads the binary and writes the pointer. This is transparent to the user.

Setup & Configuration

  • git lfs install — installs smudge/clean filters globally in ~/.gitconfig.
  • git lfs track "*.pth" — adds a rule to .gitattributes: *.pth filter=lfs diff=lfs merge=lfs -text.
  • git add .gitattributes — commit the tracking rules so all collaborators use LFS for the same patterns.
  • Subsequent adds/commits/pushes work exactly as normal; LFS transfers happen automatically.
⚠️ LFS Pitfalls

Bandwidth quota: GitHub LFS free tier gives 1 GB storage + 1 GB/month bandwidth. Large ML models exhaust this quickly — budget for a paid plan or self-host. Migration: Adding LFS after the fact requires git lfs migrate import to rewrite history — all collaborators must re-clone. Forking: GitHub forks do not share LFS storage — each fork has its own quota.

Alternatives to Git LFS

  • DVC (Data Version Control) — tracks large files/datasets with a separate remote (S3, GCS, Azure), similar pointer pattern but optimised for ML pipelines. Better for datasets that change frequently.
  • Git Annex — similar pointer pattern, more flexible backends, but harder to set up.
  • Artifact registries (MLflow Model Registry, W&B Artifacts) — purpose-built for ML model versioning; integrate with experiment tracking.

Key Takeaways & When to Use What
▼

Summary of core invariants:

  • Every Git object is immutable and content-addressed — you cannot secretly alter history.
  • Branches and tags are cheap: they're just 41-byte files holding a SHA. Create them freely.
  • Merge preserves history; rebase rewrites it. Never rebase shared history.
  • Fast-forward merges are clean linear history; use --no-ff to preserve branch evidence in the log.
  • Git LFS decouples binary asset storage from Git object storage — essential for ML projects with model checkpoints or large datasets.

Choosing a branching strategy:

  • Versioned library/desktop app → Git Flow for structured release management.
  • Simple web service, small team → GitHub Flow for speed and simplicity.
  • Large team, strong CI, continuous deploy → Trunk-Based Development to eliminate merge overhead.

Common interview traps: "What is a detached HEAD?" (HEAD points directly at a commit SHA, not a branch ref — commits made in this state are orphaned when you checkout a branch). "What does git reset --hard do vs git revert?" (reset moves the branch pointer backwards, rewriting history; revert creates a new commit undoing changes, preserving history — always prefer revert on shared branches).

💡 The Big Picture

Git's power comes from three elegant ideas working together: content-addressed storage (SHA gives identity), DAG of commits (immutable, tamper-evident chain), and lightweight branch pointers (O(1) branching). Everything else — merging, rebasing, stashing, cherry-picking — is just graph manipulation on top of these primitives.
