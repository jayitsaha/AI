Dynamic Resolution: Native Aspect-Ratio Vision for MLLMs

How modern multimodal LLMs tile any image size/shape into a variable-length token grid instead of squashing it into a fixed square crop

1
Understanding Dynamic Resolution
▼

What is it? Early multimodal LLMs (CLIP-ViT, LLaVA-1.0, BLIP-2) forced every input image through a fixed square resize — usually 224×224 or 336×336 pixels — before feeding it to the vision encoder. A 4000×1200 panoramic photo and a 400×400 icon both got squashed or cropped to the exact same square canvas, always producing the exact same number of vision tokens. Dynamic resolution (a.k.a. "native resolution" or "any-resolution" vision input) removes that straitjacket: the model resizes only enough to respect a patch grid and a token budget, preserves the true aspect ratio, and lets the number of vision tokens vary per image — a 3:1 banner and a 1:1 square both get seen at (nearly) their native shape.

Analogy: Imagine a print shop that only sells one frame size — 8×8 inches, square. Every photo you bring in, tall or wide, gets stretched or cropped to fit that square, and detail near the edges is lost. Dynamic resolution is switching to a shop that cuts custom mats: a panoramic photo gets a wide frame, a portrait gets a tall one, and nothing outside a sensible size range is squeezed or discarded. The "frame" size (token budget) can still be capped so huge images don't blow up compute, but the *shape* is preserved.

One-sentence summary: Dynamic resolution resizes an image to the nearest patch-grid-aligned size that (a) keeps its original aspect ratio and (b) fits inside a min/max token budget, so the vision token sequence length is a live function of image shape rather than a hard-coded constant.

💡 If you remember one thing

Fixed-resolution encoders throw away information (via crop) or distort geometry (via stretch) before the model ever sees the pixels. Dynamic resolution instead computes $$H', W' = \arg\min_{H',W'} \; \big| \tfrac{H'}{W'} - \tfrac{H}{W}\big| \quad \text{s.t. } H',W' \equiv 0 \!\!\pmod{p{\cdot}m},\; \text{pixels}(H',W') \in [P_{min}, P_{max}]$$ — the resize is aspect-preserving and grid-aligned, and the resulting token count is computed, not assumed.

How It Works Internally
▼

The Problem with Fixed Crops

A ViT patch embedding layer is just a strided convolution: it needs \(H\) and \(W\) to be divisible by the patch size \(p\) (e.g. 14px). The classic fix was "resize-then-center-crop-to-224", which (1) discards pixels outside the crop, (2) distorts thin/wide layouts (a receipt, a whiteboard, a wide chart) into a square, and (3) allocates the *same* 256–729 tokens to a tiny icon and a dense infographic — wasting compute on the icon and starving the infographic of resolution where it needs it most (small text, dense UI).

Approach A — Tile + Thumbnail (LLaVA-UHD, InternVL, "AnyRes")

Pick a small set of allowed aspect-ratio buckets (e.g. 1:1, 1:2, 2:1, 1:3, 3:1 grids of 336px tiles). Given an image, choose the bucket whose aspect ratio and total pixel count is closest, resize into that grid, slice it into fixed-size tiles that each go through the SAME frozen 336×336 ViT independently, and concatenate all tile tokens plus one global low-res "thumbnail" tile for holistic context. Token count is then discrete but shape-adaptive: a 2×1 image gets 2× the tiles of a 1×1 image.

Approach B — Native Patch + Windowed/2D-RoPE (Qwen2-VL, NaViT)

Instead of quantizing into tile buckets, resize continuously: compute a scale factor \(s\) so the pixel count lands in \([P_{min}, P_{max}]\), snap \(H,W\) to the nearest multiple of \(p \cdot m\) (patch size × spatial-merge factor), then run the ViT with 2D (or windowed) attention directly on the *native* grid — no cropping, no padding, no tiling seams. A patch-merger (e.g. a small MLP) fuses each \(m\times m\) block of patch embeddings into one token, cutting sequence length by \(m^2\) before the tokens reach the LLM.

Design Decision: Why Not Just Interpolate Fixed Position Embeddings?

ViTs originally had a fixed, learned 1D or 2D position embedding table sized for one grid (e.g. 16×16 patches). Bicubic-interpolating that table to a new grid size (as ViT-based detectors do for different input sizes) works but degrades for extreme aspect ratios and very large grids, because the interpolation was never trained to preserve the *relative* geometric structure well beyond the training regime. Native-resolution models instead use 2D Rotary Position Embeddings (2D-RoPE / M-RoPE), which encode row and column offsets analytically as rotation angles — they generalize to arbitrary \((h,w)\) grids with zero interpolation error because the encoding is a closed-form function of position, not a learned lookup table.

🔑 Key Property

Native-resolution vision encoding decouples sequence length from a hard-coded constant and makes it a deterministic function of image geometry: \(N_{tokens} = \frac{H'}{pm}\cdot\frac{W'}{pm}\). The position encoding scheme (2D-RoPE or interpolated embeddings) must be able to consume the resulting \((h,w)\) grid coordinates for any \(h,w\), not just the ones seen during pretraining.

Why It Works — The Math
▼

The Smart-Resize Function

Given a raw image of height \(H\) and width \(W\), patch size \(p\) and merge factor \(m\), define the aspect-preserving rescale factor:

$$s = \sqrt{\dfrac{\operatorname{clip}(H\cdot W,\; P_{min},\; P_{max})}{H \cdot W}}$$

This scales total pixel count into the budget \([P_{min}, P_{max}]\) while \(s\) itself preserves \(H/W\) exactly (both dimensions scale by the same factor). Then snap to the patch-merge grid so the convolutional patch embedding divides evenly:

$$H' = \operatorname{round}\!\Big(\dfrac{sH}{pm}\Big)\cdot pm \qquad W' = \operatorname{round}\!\Big(\dfrac{sW}{pm}\Big)\cdot pm$$

The resulting vision-token sequence length is then fully determined — not hard-coded:

$$N_{tokens} = \dfrac{H'}{pm}\cdot\dfrac{W'}{pm}$$

2D Position Encoding for an Arbitrary Grid

Let each merged token sit at grid coordinate \((r,c)\) with \(0 \le r < H'/pm,\; 0 \le c < W'/pm\). Split the rotary embedding's channel dimension in half, and apply ordinary 1D RoPE rotation independently along each axis:

$$\text{RoPE}_{2D}(x)_{r,c} = \big[\text{RoPE}_{1D}(x_{[1..d/2]}; r) \;\Vert\; \text{RoPE}_{1D}(x_{[d/2{+}1..d]}; c)\big]$$

Because \(\text{RoPE}_{1D}(\cdot;\theta)\) is a closed-form rotation matrix parameterized continuously by the position index \(\theta\), it is defined for any integer \(r,c\) — there is no fixed lookup table to run out of bounds on, so grids of shape \(3\times 40\) or \(60\times 60\) are handled identically to the grids seen in training.

Attention Cost as a Function of Aspect Ratio

Full self-attention over \(N\) tokens costs \(O(N^2 d)\). Since \(N = h\cdot w\) depends on both \(H'\) and \(W'\), a very elongated image (large \(H'/W'\)) at fixed pixel budget yields the same \(N\) as a square image of equal area — attention cost is invariant to aspect ratio at fixed budget, only to total resolution. This is what allows capping \(P_{max}\) to bound worst-case compute regardless of how extreme the aspect ratio is.

⚠️ Common Pitfall

Rounding \(H'\) and \(W'\) to the nearest multiple of \(pm\) is not guaranteed to preserve \(H/W\) exactly — independent rounding of two dimensions introduces small aspect-ratio drift, worse for small images (few patches) than large ones. This is why \(P_{min}\) is set high enough that even a 1-patch-row image still gets several patches per axis, keeping rounding error a small fraction of the grid.

Key Takeaways
▼

When native/dynamic resolution helps most:

  • Documents, screenshots, UIs, receipts, whiteboards — thin text is destroyed by squashing to a square
  • Extreme aspect ratios: panoramas, tall infographics, comic strips
  • Mixed batches of tiny icons and dense charts, where a single fixed token budget is either wasteful or insufficient
  • Multi-image / video-frame reasoning where relative resolution across frames carries information

Trade-offs to know:

  • Variable sequence length complicates batching (need padding/masking or ragged batch kernels)
  • Requires position encodings that generalize to unseen grid shapes (2D-RoPE, or careful embedding interpolation)
  • Tile-based methods (LLaVA-UHD/InternVL) add tile-boundary artifacts; native-patch methods (Qwen2-VL/NaViT) avoid seams but need custom attention kernels for ragged native-resolution batches
  • Still bounded by \(P_{max}\) — "dynamic" does not mean "unlimited"; extremely high-res images are still downsampled
💡 Hierarchy

Fixed-crop ViT (one resolution, one token count) ⊂ Tile+thumbnail AnyRes (discrete aspect buckets, tile-level tokens) ⊂ Native-resolution / NaViT-style (continuous aspect ratio, patch-merge tokens, 2D-RoPE). Each generalizes the previous by relaxing the assumption that every image must be seen at the same shape.

Code Trace
▼
import math
# Qwen2-VL-style "smart resize": aspect-preserving, grid-aligned
def smart_resize(H, W, patch=14, merge=2, min_px=56*56, max_px=1024*28*28):
unit = patch * merge # 28px: one merged token's footprint
# 1. scale factor that puts total pixels inside [min_px, max_px]
area = H * W
target = min(max(area, min_px), max_px)
s = math.sqrt(target / area)
# 2. snap both dims to a multiple of `unit` (so patchify divides evenly)
H_new = round(s * H / unit) * unit
W_new = round(s * W / unit) * unit
H_new, W_new = max(H_new, unit), max(W_new, unit)
return H_new, W_new
# 3. token grid + sequence length
def token_grid(H_new, W_new, patch=14, merge=2):
unit = patch * merge
h_tok, w_tok = H_new // unit, W_new // unit
return h_tok, w_tok, h_tok * w_tok # (rows, cols, N_tokens)
# 4. 2D-RoPE position ids for the merged token grid
def rope_2d_positions(h_tok, w_tok):
ids = [(r, c) for r in range(h_tok) for c in range(w_tok)]
return ids # fed to rotary embedding: half channels rotate by r, half by c
H, W = 900, 1600 # native landscape photo
H2, W2 = smart_resize(H, W)
h_tok, w_tok, n = token_grid(H2, W2)
print(f"{H}x{W} -> {H2}x{W2} -> grid {h_tok}x{w_tok} -> {n} tokens")
