From static test sets to live A/B tests and deep dives into performance segments
Foundational MLOps Experimentation Intermediate
1
Understanding Model Evaluation
▼

What is it? Model evaluation is the critical process of assessing how well a machine learning model performs its intended task. It's not just about getting a number; it's about understanding the model's strengths, weaknesses, and readiness for deployment. This process involves a spectrum of techniques, from static analysis on historical data to live experiments with real users.

Analogy: Imagine a chef developing a new recipe. First, they taste it themselves in the kitchen (offline evaluation) — does it meet their internal quality standards? Then, they serve it to a small group of trusted friends and get feedback (online A/B test) — do real people like it more than the old recipe? Finally, they might ask their friends specific questions: "Do you like it if you're a vegetarian? What about if you're a child?" (slice analysis) to understand if it works for everyone, or only certain groups.

💡 If you remember one thing

Offline evaluation is fast and reproducible but can miss real-world dynamics. Online evaluation (A/B testing) is the gold standard for causal impact but is slow and risky. Slice analysis is crucial to uncover hidden biases or performance issues in specific user segments, complementing both.

2
How Each Evaluation Method Works
▼

1. Offline Evaluation: The Lab Test

Offline evaluation involves using a held-out portion of historical data (the test set) to measure a model's performance. It's typically performed after training and before deployment. Common steps include:

  1. Data Splitting: Divide your dataset into training, validation, and test sets. The test set is untouched during training and hyperparameter tuning.
  2. Prediction: Run the trained model on the test set to generate predictions.
  3. Metric Calculation: Compare predictions against ground truth labels using appropriate metrics (e.g., accuracy, precision, recall, F1-score for classification; MSE, R² for regression).
  4. Analysis: Review metrics, confusion matrices, ROC curves, etc., to understand model behavior.

Pros: Fast, cheap, reproducible, allows rapid iteration. Cons: Cannot fully capture real-world user behavior, data drift, or feedback loops.

2. Online Evaluation: The A/B Test

Online evaluation, most commonly through A/B testing, involves deploying a new model to a subset of live users and comparing its performance against a control group (running the old model or no model). This is the gold standard for measuring causal impact on business metrics.

  1. Hypothesis Formulation: Define what you expect to happen (e.g., "New model will increase CTR by 5%").
  2. Randomization: Randomly assign users to a control group (Group A) or a treatment group (Group B). This ensures groups are statistically similar.
  3. Deployment: Deploy the new model to Group B, while Group A continues with the baseline.
  4. Metric Monitoring: Collect data on key business metrics (e.g., click-through rate, conversion rate, revenue per user, engagement) for both groups.
  5. Statistical Analysis: After collecting sufficient data, compare metrics between groups and determine if observed differences are statistically significant.

Pros: Measures true causal impact on live users, captures real-world interactions. Cons: Slow, expensive, risky (negative user experience), requires careful statistical design.

3. Slice Analysis: The Deep Dive

Slice analysis (or subgroup analysis) involves breaking down model performance by different segments or "slices" of the data. This is crucial for identifying biases, fairness issues, or areas where the model underperforms for specific user groups or data characteristics.

  1. Define Slices: Identify relevant subgroups (e.g., demographic groups, geographic regions, device types, time of day, content categories).
  2. Segment Data: Filter your test set (for offline) or A/B test data (for online) into these defined slices.
  3. Compute Metrics Per Slice: Calculate the same evaluation metrics (offline or online) for each individual slice.
  4. Compare and Investigate: Look for significant discrepancies. An overall "good" model might be terrible for a specific slice, indicating bias or a need for targeted improvements.

Pros: Uncovers hidden performance issues, crucial for fairness and robustness, provides actionable insights. Cons: Can lead to "p-hacking" if too many slices are checked without correction, smaller slices may lack statistical power.

🔑 Key Property

These methods are complementary. Strong offline metrics are a prerequisite for online testing. Positive A/B test results are the ultimate validation. Slice analysis is a diagnostic tool to ensure robust and fair performance across the entire user base.

Why It Works — The Math
▼

Offline: Classification Metrics from the Confusion Matrix

For binary classification, the confusion matrix categorizes predictions into four types:

  • True Positives (TP): Correctly predicted positive class.
  • True Negatives (TN): Correctly predicted negative class.
  • False Positives (FP): Incorrectly predicted positive (Type I error).
  • False Negatives (FN): Incorrectly predicted negative (Type II error).

Key metrics are then derived:

$$\text{Accuracy} = \frac{\text{TP} + \text{TN}}{\text{TP} + \text{TN} + \text{FP} + \text{FN}}$$
$$\text{Precision} = \frac{\text{TP}}{\text{TP} + \text{FP}} \quad \text{(of predicted positives, how many were correct?)}$$
$$\text{Recall} = \frac{\text{TP}}{\text{TP} + \text{FN}} \quad \text{(of actual positives, how many were found?)}$$

The F1-score is the harmonic mean of Precision and Recall: \(F1 = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}\). Each metric tells a different story about model performance.

Online: Statistical Significance in A/B Testing

When comparing a metric like Click-Through Rate (CTR) between two groups, we're comparing two proportions. For large sample sizes, we can use a Z-test for two population proportions to determine if the observed difference is statistically significant.

Given control group \(C\) with \(n_C\) users and \(x_C\) clicks, and treatment group \(T\) with \(n_T\) users and \(x_T\) clicks, the sample CTRs are \(\hat{p}_C = x_C/n_C\) and \(\hat{p}_T = x_T/n_T\). The pooled proportion is \(\hat{p} = (x_C + x_T) / (n_C + n_T)\). The Z-statistic is:

$$Z = \frac{(\hat{p}_T - \hat{p}_C) - 0}{\sqrt{\hat{p}(1-\hat{p})\left(\frac{1}{n_C} + \frac{1}{n_T}\right)}}$$

We then compare \(|Z|\) to a critical value (e.g., 1.96 for a 95% confidence level) or compute a p-value. If the p-value is below a significance level (e.g., 0.05), we reject the null hypothesis that there is no difference between the groups.

⚠️ Common Pitfall

Offline metrics are necessary but not sufficient. A model optimized for F1-score on a test set might still fail in production due to issues like data distribution shift, latency requirements, or negative user feedback loops not captured by static data. Always validate with live users if possible.

Key Takeaways
▼
Method Purpose Pros Cons
Offline Evaluation Initial model quality check, rapid iteration Fast, cheap, reproducible, detailed metric analysis Doesn't capture live user behavior, data drift, feedback loops
Online Evaluation (A/B Test) Causal impact on business metrics, real-world validation Gold standard for causality, captures live user interaction Slow, expensive, risky (negative impact), ethical concerns, complex setup
Slice Analysis Identify biases, performance disparities in subgroups Uncovers hidden issues, crucial for fairness and robustness Can lead to p-hacking, small slices may lack statistical power

When to use each:

  • Offline: Always the first step. Use to filter out clearly bad models and iterate rapidly on model architecture and hyperparameters.
  • Online: For any model that directly interacts with users or impacts key business metrics. Essential for high-stakes deployments.
  • Slice: As a diagnostic tool alongside both offline and online evaluation. Crucial for understanding model fairness, robustness, and identifying targeted improvement areas.

Common Pitfalls:

  • Over-relying on offline metrics: A great F1-score doesn't guarantee production success.
  • Premature A/B testing: Deploying an unvetted model can harm users and business.
  • Ignoring statistical power: Ending an A/B test too early or with too few users can lead to false conclusions.
  • "P-hacking" in slice analysis: Testing too many slices without adjusting for multiple comparisons can lead to spurious findings.
💡 Full-Stack Evaluation

A robust evaluation strategy integrates all three: offline for speed, online for truth, and slice analysis for depth. This holistic approach ensures models are not only performant but also fair, robust, and truly beneficial in the real world.

import numpy as np
from scipy import stats
# --- 1. Offline Evaluation Metrics ---
def calculate_metrics(tp, fn, fp, tn):
accuracy = (tp + tn) / (tp + fn + fp + tn)
precision = tp / (tp + fp) if (tp + fp) > 0 else 0
recall = tp / (tp + fn) if (tp + fn) > 0 else 0
f1 = (2 * precision * recall) / (precision + recall) if (precision + recall) > 0 else 0
return {'accuracy': accuracy, 'precision': precision, 'recall': recall, 'f1': f1}
# Example usage:
# metrics = calculate_metrics(tp=80, fn=20, fp=10, tn=90)
# print(metrics)
# --- 2. Online Evaluation (A/B Test Z-test for proportions) ---
def ab_test_proportions(clicks_control, users_control, clicks_treatment, users_treatment):
p_c = clicks_control / users_control
p_t = clicks_treatment / users_treatment
# Pooled proportion
p_pooled = (clicks_control + clicks_treatment) / (users_control + users_treatment)
# Standard error of the difference
se_diff = np.sqrt(p_pooled * (1 - p_pooled) * (1/users_control + 1/users_treatment))
# Z-statistic
z_stat = (p_t - p_c) / se_diff
# P-value (two-tailed)
p_value = 2 * (1 - stats.norm.cdf(abs(z_stat)))
# Confidence interval for the difference (95%)
se_diff_unpooled = np.sqrt(p_c*(1-p_c)/users_control + p_t*(1-p_t)/users_treatment)
margin_of_error = stats.norm.ppf(0.975) * se_diff_unpooled
ci_lower = (p_t - p_c) - margin_of_error
ci_upper = (p_t - p_c) + margin_of_error
return {
'p_control': p_c, 'p_treatment': p_t, 'diff': p_t - p_c,
'z_stat': z_stat, 'p_value': p_value, 'ci': [ci_lower, ci_upper]
}
# Example usage:
# ab_results = ab_test_proportions(100, 1000, 120, 1000)
# print(ab_results)
