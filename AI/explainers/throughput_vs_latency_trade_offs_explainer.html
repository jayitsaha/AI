Throughput vs Latency Trade-offs

Optimizing for total work done vs. individual response time in systems design
Foundational Systems Design Performance O(1) concept
1
Understanding Throughput and Latency
▼

What are they? In any system that processes work (a server, a factory, a data pipeline), two fundamental metrics describe its performance:

  • Throughput: The total amount of work completed per unit of time. This is a measure of capacity. Examples: requests per second (RPS), transactions per minute (TPM), gigabytes processed per hour.
  • Latency: The time it takes for a single unit of work to complete from start to finish. This is a measure of responsiveness. Examples: response time for a single API call, end-to-end delay for a data packet, time to process one image.

These two metrics are often inversely related, presenting a fundamental trade-off in system design. Optimizing aggressively for one can often degrade the other.

Analogy: Imagine a coffee shop. If they make one coffee at a time, each customer gets their drink quickly (low latency). But if there's a line, total coffees served per hour might be low (low throughput). If they start making coffee in batches (e.g., a huge pot of drip coffee), they can serve more people per hour (high throughput), but the first person in line might wait longer for the pot to brew (higher latency for that individual's request). Adding more baristas (parallelism) can help both, but might introduce new coordination overheads.

💡 If you remember one thing

Throughput is about quantity over time (how many?); latency is about time per quantity (how fast for one?). They are often at odds: techniques that boost throughput (like batching) can increase latency, and vice-versa.

2
How the Trade-off Arises Internally
▼

Sources of the Trade-off

The tension between throughput and latency often stems from how systems manage resources and overheads:

  • Batching: Processing multiple items together (a "batch") can amortize fixed overhead costs (e.g., setting up a database connection, loading a model into GPU memory, context switching between tasks). This makes the system more efficient per item, boosting throughput. However, an individual item must wait for its batch to fill or for the entire batch to complete, increasing its individual latency.
  • Parallelism: Using multiple workers (CPU cores, GPUs, threads) to process tasks simultaneously. This generally increases throughput. If tasks are truly independent and resources are abundant, parallelism can also keep latency low. However, coordination overheads (locks, shared memory, network communication) between parallel workers can introduce delays, potentially increasing latency or even reducing throughput if contention is high.
  • Resource Contention: When multiple tasks or workers compete for limited resources (CPU cycles, memory bandwidth, network I/O), they might experience delays. Higher throughput usually means more tasks are active, leading to more contention and thus higher latency for individual tasks.

Design Decision: Which Metric to Prioritize?

The choice depends entirely on the application's requirements:

  • Latency-sensitive applications: Real-time systems, interactive user interfaces, high-frequency trading, self-driving cars. Here, even small delays are critical. Batching is minimized, and parallelism is carefully managed to avoid coordination overheads.
  • Throughput-sensitive applications: Batch processing, data analytics, scientific simulations, video encoding. Here, the total volume of work processed is paramount, even if individual items take longer. Large batch sizes and aggressive parallelism are common.

Most real-world systems need a balance. For example, a web server needs good average latency for user experience, but also high enough throughput to handle peak traffic without crashing.

🔑 Key Property

The fundamental trade-off arises because many systems have fixed overheads that can be amortized over multiple items (boosting throughput) but add delay to each item (increasing latency), and limited resources that introduce contention as utilization increases.

Why It Works — The Math Behind the Trade-off
▼

Modeling a Simple Processing Pipeline

Consider a system with the following parameters:

  • \(P\): Time to process a single item's core work (e.g., 10 ms/item).
  • \(O\): Fixed overhead cost incurred per batch of items (e.g., 5 ms/batch for setup).
  • \(B\): Batch size, the number of items processed together in one go.
  • \(W\): Number of parallel workers available.

Time for One Batch

The total time required for a single worker to process one batch of \(B\) items is the sum of the fixed overhead and the processing time for all items in the batch:

$$T_{\text{batch}} = O + B \cdot P$$

This equation clearly shows that increasing the batch size \(B\) directly increases the time spent per batch. This is the core driver of latency increases with batching.

Latency of a Single Item

If we define latency for an item as the time from when it enters a batch until its processing in that batch is complete (assuming it's the last item in the batch), then:

$$L_{\text{item}} = T_{\text{batch}} = O + B \cdot P$$

This definition captures the "wait time" an item experiences due to batching. To minimize \(L_{\text{item}}\), we would choose \(B=1\) (no batching) and minimize \(O\) and \(P\).

System Throughput

The total system throughput, in items per unit time, considers all workers processing batches in parallel. Each worker completes one batch in \(T_{\text{batch}}\) time, processing \(B\) items. Thus, each worker's throughput is \(B/T_{\text{batch}}\). With \(W\) workers, the total throughput is:

$$\text{Throughput} = \frac{W \cdot B}{T_{\text{batch}}} = \frac{W \cdot B}{O + B \cdot P}$$

Here, the trade-off becomes clear. To increase throughput, we can increase \(W\) or \(B\). Increasing \(B\) increases \(T_{\text{batch}}\) (and thus \(L_{\text{item}}\)), but if \(O\) is significant, the increase in \(B\) can amortize \(O\) more effectively, leading to a net gain in throughput despite the longer \(T_{\text{batch}}\).

⚠️ Important Simplification

This model assumes no contention between workers and that workers are always busy if there's work. In reality, additional overheads (e.g., context switching, shared resource contention, network latency) can arise with more workers, potentially reducing the effective \(W\) or increasing \(O\), making the actual throughput lower than predicted.

Key Takeaways
▼

When to prioritize Throughput:

  • Batch processing: ETL jobs, scientific computations, video rendering.
  • High fixed overheads: When setting up a task is expensive (e.g., launching a VM, loading a large model). Batching amortizes this cost.
  • Resource-intensive tasks: When tasks consume a lot of CPU/GPU/memory, maximizing utilization (and thus throughput) is key.

When to prioritize Latency:

  • Interactive user experiences: Web applications, gaming, real-time dashboards. Users expect immediate feedback.
  • Real-time control systems: Robotics, autonomous vehicles, industrial automation. Delays can have critical consequences.
  • High-frequency trading: Millisecond differences can mean millions in profit or loss.

The balancing act:

Many systems require a compromise. Techniques like micro-batching (small batches to gain some amortization without excessive latency) or asynchronous processing (offloading heavy work to background queues so the user gets an immediate response) are common strategies to navigate this trade-off.

💡 Rule of Thumb

If your system is bottlenecked by startup costs or resource contention, increasing batch size or parallelism can boost throughput. If it's bottlenecked by individual item processing time or user experience, focus on reducing \(P\) and \(O\), and minimize batching.

Code Trace — Simplified Calculation
▼
import math
def calculate_performance_metrics(P_item_ms, O_batch_ms, B_batch_size, W_num_workers):
"""
Calculates system throughput and average item latency.
P_item_ms: Time to process one item's core work (milliseconds).
O_batch_ms: Fixed overhead cost per batch (milliseconds).
B_batch_size: Number of items processed together in one batch.
W_num_workers: Number of parallel workers.
"""
# 1. Time for one batch on a single worker
T_batch_ms = O_batch_ms + (B_batch_size * P_item_ms)
# 2. Latency for a single item (worst-case within a batch)
# This is the time from when the item enters the batch until the batch completes.
L_item_ms = T_batch_ms
# 3. System Throughput (items per second)
# Each worker processes B items in T_batch_ms.
# Convert T_batch_ms to seconds for items/sec.
if T_batch_ms == 0: # Avoid division by zero if all times are zero (unrealistic)
TP_items_per_sec = math.inf
else:
TP_items_per_sec = (W_num_workers * B_batch_size) / (T_batch_ms / 1000)
return TP_items_per_sec, L_item_ms
# --- Example Usage ---
# Scenario 1: Low latency, low throughput (single item, single worker)
tp1, lat1 = calculate_performance_metrics(P_item_ms=20, O_batch_ms=5, B_batch_size=1, W_num_workers=1)
print(f"Scenario 1: Throughput={tp1:.2f} items/s, Latency={lat1:.2f} ms")
# Scenario 2: Higher throughput via batching (larger batch, single worker)
tp2, lat2 = calculate_performance_metrics(P_item_ms=20, O_batch_ms=5, B_batch_size=5, W_num_workers=1)
print(f"Scenario 2: Throughput={tp2:.2f} items/s, Latency={lat2:.2f} ms")
# Scenario 3: Higher throughput via parallelism (single item, multiple workers)
tp3, lat3 = calculate_performance_metrics(P_item_ms=20, O_batch_ms=5, B_batch_size=1, W_num_workers=4)
print(f"Scenario 3: Throughput={tp3:.2f} items/s, Latency={lat3:.2f} ms")
# Scenario 4: Max throughput (batching + parallelism)
tp4, lat4 = calculate_performance_metrics(P_item_ms=20, O_batch_ms=5, B_batch_size=5, W_num_workers=4)
print(f"Scenario 4: Throughput={tp4:.2f} items/s, Latency={lat4:.2f} ms")
