1
Understanding Spark for Feature Computation
▼

What is it? Apache Spark is a distributed compute engine for processing datasets far too large for one machine. For ML, its most common job is feature computation: reading raw events (clicks, transactions, logs) at the scale of hundreds of millions or billions of rows, and turning them into per-entity feature vectors — "average spend per user last 30 days," "click-through rate per item," etc. — that are later written to a feature store or training table.

Analogy: Imagine a warehouse with 500 million invoices that need to be sorted, cleaned, and summed up per customer. One clerk (a single machine) would take forever. Spark hires 20 teams of 4 clerks each (executors × cores), hands every team a stack of invoices (a partition), and lets them work in parallel. The catch: to compute "total spend per customer," clerks must first regroup invoices by customer name — that regrouping, where paperwork physically moves between teams, is the shuffle, and it is the most expensive step in the whole job.

💡 If you remember one thing

Spark splits data into partitions and schedules one task per partition per core. Transformations that keep each partition self-contained (map, filter) are narrow and free to parallelize. Transformations that need data from other partitions (groupBy, join) are wide and force a shuffle — an all-to-all network exchange that is usually the bottleneck in feature pipelines.

2
How It Works Internally
▼

Driver, Executors, and Partitions

A Spark job has one driver process that holds the logical plan and coordinates work, and many executor processes (JVMs on cluster nodes) that actually run tasks. Each executor has a fixed number of cores, and each core runs one task at a time. The input dataset is split into partitions — contiguous chunks of rows — and Spark's goal is to keep #partitions ≈ some multiple of total cores so no core sits idle.

Lazy Evaluation and the DAG

Calling .filter() or .map() on a DataFrame does not touch data. Spark only records a logical plan — a directed acyclic graph (DAG) of transformations. Nothing executes until an action (.write(), .collect(), .count()) is called. This laziness lets Spark's Catalyst optimizer rewrite the whole chain first — pushing filters down, pruning unused columns, combining maps — before ever reading a byte, which is impossible if execution happens eagerly line by line.

Narrow vs. Wide Dependencies

When the DAG is turned into an execution plan, each edge is classified: a narrow dependency means each output partition depends on exactly one input partition (map, filter, union) — these can be pipelined into a single stage with zero data movement. A wide dependency means each output partition may depend on every input partition (groupByKey, reduceByKey, join, distinct, repartition) because rows with the same key can currently live anywhere. Wide dependencies force a stage boundary: Spark must materialize a shuffle before the next stage can start.

Design Decision: Why Shuffle at All?

An alternative would be broadcasting every partition to every other partition and filtering locally — but that is O(n²) in network traffic. Instead, Spark's shuffle hash-partitions each row by hash(key) % numReducePartitions, writes it to local disk in buckets, and reducers pull only the bucket meant for them. This is O(n) data movement, but it is still disk + network bound and typically 10–100× slower per byte than an in-partition map.

🔑 Key Property

A Spark job compiles to a graph of stages, where stage boundaries occur exactly at wide dependencies. Everything inside one stage runs as pipelined, shuffle-free tasks; everything between stages must pass through a shuffle write + shuffle read.

3
Why It Works — The Math of Cost & Skew
▼

Task Parallelism

With \(P\) partitions and \(C\) total cores across the cluster, tasks run in waves:

$$\text{waves} = \left\lceil \frac{P}{C} \right\rceil$$

If every partition takes the same time \(t\) to process, an ideal stage finishes in \(\text{waves} \times t\). This is why Spark practitioners tune the partition count: too few partitions under-utilizes cores; too many adds scheduling overhead.

Shuffle Volume

For \(N\) rows with average serialized size \(b\) bytes after the map side, the shuffle write is:

$$\text{shuffle bytes} \approx N \times b$$

This must be written to disk by every mapper task and read back over the network by every reducer task — a full shuffle touches disk twice and the network once per byte, which is why minimizing shuffled columns (select only what you need before a groupBy) is one of the highest-leverage Spark optimizations.

Skew: When One Key Dominates

Hash partitioning assumes keys are roughly uniform. If a fraction \(f\) of rows share one hot key (a bot account, a default/null value, a viral item), that single reduce partition receives:

$$\text{rows}_{\text{skewed}} = f \times N_{\text{shuffled}} \qquad \text{skew ratio} = \frac{\text{rows}_{\text{skewed}}}{N_{\text{shuffled}} / P}$$

Because a stage only completes when its slowest task finishes (a classic straggler problem), stage latency becomes:

$$T_{\text{stage}} = \max\Big(\text{waves} \times t_{\text{avg}},\ t_{\text{skewed}}\Big)$$

Even with 79 idle, finished cores, the whole stage — and everything downstream — waits on that one task.

⚠️ Common Pitfall

Adding more executors does not fix skew — every additional core still waits on the same oversized partition. The real fixes are salting (append a random suffix to the hot key, aggregate in two phases), broadcast joins (skip the shuffle entirely for small dimension tables), or Spark 3's Adaptive Query Execution (AQE), which detects skewed partitions at runtime and automatically splits them into sub-tasks.

Key Takeaways
▼

When Spark is the right tool for feature computation:

  • Raw source data exceeds single-machine memory/CPU (hundreds of millions to billions of rows)
  • Features require aggregations across the full history per entity (groupBy, window functions)
  • You need the same batch logic to run as a scheduled, fault-tolerant, re-runnable pipeline (lineage-based recovery — a lost partition is just recomputed from its DAG, not the whole job)

When NOT to reach for Spark:

  • Data fits comfortably in one machine's RAM — pandas/Polars/DuckDB will be faster with zero cluster overhead
  • You need sub-second, per-request feature lookups — that's an online feature store (Redis/DynamoDB), not a batch shuffle engine
  • Your keys are known to be extremely skewed and small in number — a simple broadcast join beats a full shuffle every time
💡 Mental Model

Read the physical plan (.explain()) and count the Exchange nodes — each one is a shuffle boundary and a stage split. Minimizing exchanges (filter early, select only needed columns, broadcast small tables, salt hot keys) is 90% of Spark feature-pipeline tuning.

Code Trace
▼
from pyspark.sql import functions as F
# 1. Read raw clickstream events: 500M rows, 200 input partitions
events = spark.read.parquet("s3://logs/clickstream/")
print(events.rdd.getNumPartitions()) # 200 -- NARROW so far, nothing has run
# 2. Narrow transform: drop malformed rows (1:1 per partition)
valid = events.filter(F.col("user_id").isNotNull() & F.col("event_ts").isNotNull())
# 3. Narrow transform: project raw event into a feature tuple (still 1:1)
mapped = valid.select("user_id", F.col("amount").alias("spend"), "event_ts")
# 4. Nothing has executed yet -- this is all still lazy DAG / lineage
mapped.explain(True) # shows logical plan, zero jobs run
# 5. WIDE transform: groupBy triggers a shuffle -- new stage boundary
features = mapped.groupBy("user_id").agg(
F.sum("spend").alias("total_spend"),
F.count("*").alias("num_events"))
# 6. Shuffle: hash(user_id) % 200 assigns rows to reduce partitions
# -- one hot user_id (bot traffic) makes one reducer far bigger than the rest
# 7. ACTION triggers the DAG scheduler to build stages and run tasks
features.count() # first action -- Stage 0 (read/filter/map) then Stage 1 (shuffle+agg)
# 8. Mitigate skew: salt the hot key, aggregate twice, or enable AQE
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
# 9. Write features out; driver collects task metrics, job marked complete
features.write.mode("overwrite").parquet("s3://feature-store/user_features/")
