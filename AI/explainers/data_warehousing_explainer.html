What Is a Data Warehouse?
▾

A data warehouse is a central repository that consolidates data from many operational systems — order processing, CRM, ERP — so analysts can query it without slowing down live applications. Think of the operational systems as the kitchen of a restaurant (fast, transactional, one order at a time) and the warehouse as the weekly accounting ledger (slow to write, designed to answer "how many burgers did we sell last month?")

💡 One-Sentence Summary
A data warehouse separates running the business (OLTP) from understanding the business (OLAP) using a schema optimised for analytical aggregation over millions of rows.

Two dominant schema styles govern how tables are laid out inside a warehouse:

  • Star schema — one central fact table joined to several dimension tables. Wide, denormalized, lightning-fast for aggregation.
  • Snowflake schema — dimensions are themselves normalized into sub-dimension tables. Saves storage; adds joins.
Key Concept
The fact table stores numeric measurements (revenue, quantity, clicks). The dimension tables store descriptive attributes (customer name, product category, date). You join dimensions to facts to answer "total revenue by product category in Q3."

Modern warehouses (BigQuery, Snowflake, Redshift) and the emerging lakehouse pattern (Delta Lake, Apache Iceberg) extend these ideas with columnar storage, data versioning, and unified batch + streaming ingestion.

2
Dimensional Modeling — Star & Snowflake Schemas
▾

The Fact Table

A fact table contains one row per measurable event — a sale, a click, a page view. It stores foreign keys to each dimension and numeric measures. For an e-commerce platform:

Example Fact Table — fact_sales
sale_id | date_key | product_key | customer_key | store_key | revenue | quantity

Star Schema — Denormalized Dimensions

In a star schema every dimension is one flat table. The dim_product table stores product_id, category, sub_category, brand, color all together — no further normalization. This means:

  • Queries require at most one JOIN per dimension (typically 4-6 joins in a query).
  • Column cardinality can be high (color might repeat millions of times).
  • Simpler SQL, faster execution on columnar engines.
Why "Star"?
Draw fact table in the center, dimension tables radiating outward — it looks exactly like a star.

Snowflake Schema — Normalized Sub-Dimensions

A snowflake schema normalizes dimensions: dim_product no longer holds category_name directly — instead it holds a category_key that references dim_category, which itself may reference dim_department. Consequences:

  • Eliminates update anomalies: renaming a category updates one row, not millions.
  • Queries require more JOINs — can hurt performance on row-oriented engines.
  • Modern columnar warehouses handle snowflake fine; traditional RDBMS prefers star.
⚠️ Common Mistake
Snowflake schema ≠ Snowflake the company. Snowflake (the cloud DW product) supports both star and snowflake schema designs.

Grain

The grain of a fact table is the most atomic level of measurement it stores. A fact table at transaction grain has one row per individual sale. A fact table at daily grain has one row per product per day. Choosing grain is the most important design decision — it determines what queries are possible without approximation.

$$\text{Grain} = \text{unit of one row in } \mathcal{F} \quad \Rightarrow \quad \text{finest grain} = \text{max flexibility}$$

OLTP vs OLAP — Storage, Queries, Trade-offs
▾

OLTP — Online Transaction Processing

An OLTP system (PostgreSQL, MySQL, Oracle) is optimised to execute thousands of small read/write transactions per second. Each transaction touches a tiny number of rows — "insert this order", "update this customer's email". The schema is 3NF-normalized to prevent update anomalies.

  • Storage layout: Row-oriented (NSM — N-ary Storage Model). All columns of one row are stored together on disk.
  • Index strategy: B-tree indexes on primary keys + foreign keys for fast point lookups.
  • Query pattern: Short, selective; often uses indexes to read 1–100 rows.
  • Concurrency: Multi-version concurrency control (MVCC), ACID guarantees.

OLAP — Online Analytical Processing

An OLAP system (BigQuery, Redshift, DuckDB, Snowflake) is optimised to scan billions of rows and aggregate them — "total revenue by region last quarter". It reads only the columns it needs.

  • Storage layout: Column-oriented (DSM — Decomposition Storage Model). All values of one column stored together, enabling compression and vectorized SIMD scans.
  • Compression: Run-length encoding (RLE), dictionary encoding, delta encoding drastically reduce I/O.
  • Query pattern: Full scans over wide tables; GROUP BY, window functions, aggregates.
  • Concurrency: Optimistic; typically read-heavy, batch writes (ETL/ELT).

The Core Trade-off
Row-store is optimal when you need all columns of a few rows (OLTP point lookups). Column-store is optimal when you need a few columns across all rows (OLAP aggregations). A workload cannot be fully optimal for both simultaneously — this is why separate systems exist.

The Modern Lakehouse

The lakehouse pattern (Delta Lake, Apache Iceberg, Apache Hudi) combines the low-cost object storage of a data lake (S3, GCS) with ACID transactions and schema enforcement from a traditional warehouse. It eliminates the ETL copy step between lake and warehouse: ML training and BI queries read from the same Parquet files. Compute engines (Spark, Trino, DuckDB) are decoupled from storage — true separation of compute and storage.

The Math — Aggregates, Cardinality, Column Pruning
▾

Aggregation Queries

The canonical OLAP query computes a grouped aggregate over a fact table joined to dimensions. Let \(\mathcal{F}\) be the fact table with \(N\) rows, \(\mathcal{D}_i\) the \(i\)-th dimension table, and \(k\) the number of dimensions. A star-join query is:

$$Q = \pi_{\text{dim.attr, } \text{agg}(f.measure)} \left( \mathcal{F} \bowtie \mathcal{D}_1 \bowtie \mathcal{D}_2 \bowtie \cdots \bowtie \mathcal{D}_k \right) \div \text{GROUP BY dim.attr}$$

Where \(\bowtie\) is a foreign-key equi-join and \(\pi\) is the projection (column selection). The key insight is that foreign-key joins are many-to-one: each fact row joins to exactly one dimension row. This means the result cardinality cannot exceed \(|\mathcal{F}|\).

Column Pruning — I/O Savings

Suppose a fact table has \(C = 50\) columns but a query only references \(c = 3\). In a row store, a full scan reads all \(C\) columns even if unused. In a column store, only the \(c\) needed columns are read from disk:

$$\text{I/O}_{\text{row}} = N \cdot C \cdot w, \qquad \text{I/O}_{\text{col}} = N \cdot c \cdot w$$

where \(w\) is bytes per cell. The speedup ratio is:

$$\text{Speedup} = \frac{\text{I/O}_{\text{row}}}{\text{I/O}_{\text{col}}} = \frac{C}{c} = \frac{50}{3} \approx 16.7\times$$

With compression (dictionary encoding reduces cardinality-\(d\) columns from \(\log_2(N)\) bits per value to \(\log_2(d)\) bits), practical speedups of 20–100× are common.

RLE Compression Gain

Run-length encoding replaces a column of \(n_r\) repeated values with \(\langle \text{value}, n_r \rangle\) pairs. For a region column with \(R\) distinct values each repeated \(N/R\) times, the compression ratio is:

$$\text{CR}_{\text{RLE}} = \frac{N \cdot w}{R \cdot (w + 4)} \approx \frac{N}{R} \quad \text{(when } w \ll N/R \text{)}$$

A region column with \(N=10^8\) rows and \(R=10\) regions gives \(\text{CR} \approx 10^7\) — the column collapses from 100 M rows to 10 pairs.

Snowflake Normalization Redundancy

Let \(\mathcal{D}\) be a dimension table with \(n_d\) rows, attribute \(A\) with cardinality \(d_A \ll n_d\), and attribute \(B\) functionally dependent on \(A\) (\(A \to B\)). In a star schema, \(B\) is stored \(n_d\) times (once per row). In a snowflake, a sub-dimension table stores \(B\) only \(d_A\) times:

$$\text{Storage}_{\text{star}} = n_d \cdot (w_A + w_B), \qquad \text{Storage}_{\text{snowflake}} = n_d \cdot w_A + d_A \cdot w_B$$
$$\text{Savings} = (n_d - d_A) \cdot w_B$$

This matters most when \(n_d\) is large (millions of rows) and \(d_A\) is small (dozens of categories). For typical product dimensions this is modest; for customer demographics with many dependents it can be significant.

⚠️ Normalization Trade-off
The storage saved by snowflaking must be weighed against the extra JOIN cost at query time. On a columnar warehouse with vectorized execution, the extra JOIN is often cheaper than the storage gain. On a row-store RDBMS, each extra JOIN may add seconds. Profile before snowflaking.

Interview Cheat Sheet
  • Star vs Snowflake: star = more JOINs avoided, snowflake = less redundancy
  • OLTP row-store: optimal for point lookups (uses B-tree index)
  • OLAP column-store: optimal for aggregations (column pruning + compression)
  • Fact table grain = unit of one row = most important design decision
  • Slowly Changing Dimensions (SCD): how do you track history of dimension changes?
  • Lakehouse: ACID on object storage via transaction log (Delta Log / Iceberg manifest)
