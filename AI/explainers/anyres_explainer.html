AnyRes: Adaptive Image Slicing

LLaVA-NeXT's trick for high-resolution vision-language understanding: pick a tile grid, slice, encode, concatenate.
Advanced Multimodal / VLM Vision Encoding O(tiles) tokens
1
Understanding AnyRes
▼

What is it? Vision encoders like CLIP-ViT-L/14 are pretrained on fixed 336×336 crops. If you just squash a 1600×1200 screenshot down to 336×336, all the small text and fine detail get blurred into mush before the model even sees them. AnyRes (introduced in LLaVA-NeXT / LLaVA-1.6) fixes this without retraining the vision encoder: it keeps the native tile size (336×336) fixed, and instead adapts how many tiles it cuts the image into, choosing a grid whose shape best matches the image's own aspect ratio.

Analogy: Think of a museum photographing a giant mural. Instead of shrinking one photo of the whole wall (losing brush detail), they take several close-up shots — a grid of tiles — at native camera resolution, plus one wide shot for context. Stitch the close-ups back together (mentally) and you get both the fine detail and the big picture.

💡 If you remember one thing

AnyRes encodes an image twice: once as a downsized global thumbnail (336×336, for holistic context) and once as a set of native-resolution local tiles from a grid chosen to fit the image's aspect ratio. Total visual tokens: $$N_{tok} = (r \times c + 1)\cdot t$$ where \(r\times c\) is the chosen grid and \(t\) is tokens produced per 336×336 tile.

How AnyRes Works Internally
▼

The Problem With a Single Fixed Crop

CLIP-ViT-L/14-336 was pretrained on 336×336 images and produces \(24 \times 24 = 576\) patch tokens per image. Earlier VLMs (LLaVA-1.5) resized every input to 336×336 regardless of native size. A 4000×3000 photo of a whiteboard gets crushed 12× along each axis — any text smaller than a few pixels simply disappears before the transformer ever runs.

Step 1 — Choose a Grid From a Candidate Set

LLaVA-NeXT defines a small set of allowed "pinpoint" resolutions, each an integer multiple of the tile size 336 along both axes — e.g. \(1{\times}2\), \(2{\times}1\), \(2{\times}2\), \(3{\times}1\), \(1{\times}3\) (rows × cols). Given the input image's raw width/height, it computes, for every candidate grid, an effective resolution (how many original pixels survive after the best-fit downscale) and a wasted resolution (empty canvas padding beyond the image). It picks the grid that maximizes effective resolution, breaking ties by minimum waste — implemented exactly as select_best_resolution() in the official repo.

Step 2 — Resize, Tile, and Encode

The image is resized (preserving aspect ratio, then letterbox-padded) to exactly \(W = c \cdot 336\) by \(H = r \cdot 336\) pixels, then sliced into \(r \times c\) non-overlapping 336×336 tiles. Each tile is fed independently through the frozen CLIP encoder → 576 patch tokens. Separately, the original image is resized directly to 336×336 (no tiling) to produce one global thumbnail — this preserves holistic layout/context that gets lost when everything is chopped into pieces.

Step 3 — Concatenate Into the LLM's Context

All local-tile token sequences plus the global thumbnail's token sequence are concatenated (with learned newline/separator tokens marking row breaks) and projected into the LLM's embedding space, appearing in the prompt alongside the text tokens.

Design Decision: Why Not Just Use the Biggest Grid Always?

Larger grids capture more detail but tokens scale linearly with tile count — an 8-tile image costs \(9\times 576 \approx 5{,}200\) visual tokens before a single text token is read, blowing up context length and quadratic attention cost. AnyRes caps the candidate set so the token budget stays bounded, trading a little resolution for tractable inference cost — a deliberate detail-vs-budget compromise, not a limitation.

🔑 Key Property

AnyRes never retrains or resizes the vision encoder's native input resolution. It only changes the number of encoder calls — the model sees more independent 336×336 windows, not a differently-shaped one. This is why it drops into any CLIP-style backbone with zero architecture changes.

Why It Works — The Math
▼

Effective & Wasted Resolution

Let the original image be \((W_o, H_o)\). For a candidate grid resolution \((W, H) = (c\cdot 336,\, r\cdot 336)\), define the fitting scale factor:

$$s = \min\!\left(\frac{W}{W_o},\ \frac{H}{H_o}\right)$$

This is the largest scale that lets the whole image fit inside the candidate canvas without cropping. The downscaled image occupies \((\lfloor sW_o\rfloor, \lfloor sH_o\rfloor)\) pixels. Effective resolution is the pixel area actually preserved (capped by the original area — you can't "recover" more detail than existed):

$$R_{\text{eff}} = \min\big(\lfloor sW_o\rfloor \cdot \lfloor sH_o\rfloor,\ W_o H_o\big) \qquad R_{\text{waste}} = WH - R_{\text{eff}}$$

The selection rule is a lexicographic argmax over the candidate set \(\mathcal{C}\):

$$(r^*, c^*) = \underset{(r,c)\,\in\,\mathcal{C}}{\operatorname{argmax}}\; R_{\text{eff}}(r,c) \quad\text{ties broken by }\ \underset{(r,c)}{\operatorname{argmin}}\; R_{\text{waste}}(r,c)$$

Token Budget as a Function of Grid Shape

If each 336×336 tile yields \(t\) tokens (576 for raw CLIP patches, or 144 after a 2×2 average-pool compression), the total visual sequence length is:

$$N_{tok}(r,c) = \underbrace{(r\cdot c)}_{\text{local tiles}} \cdot t \;+\; \underbrace{1}_{\text{global thumbnail}} \cdot\, t \;=\; (rc+1)\,t$$

This is linear in the number of tiles \(rc\), while self-attention cost over the full context is quadratic in \(N_{tok}\) — so an unbounded candidate set would make attention cost grow as \(O((rc)^2)\), which is why \(\mathcal{C}\) is capped.

Proof Sketch: The Rule Maximizes Pixel Coverage Subject to the Cap

Among a fixed candidate set, \(R_{\text{eff}}\) is monotonically non-decreasing in how closely a candidate's aspect ratio \(W/H\) matches \(W_o/H_o\) — when they match exactly, \(s\) simultaneously saturates both axes and \(R_{\text{eff}} = W_o H_o\) (perfect coverage, zero information loss from resizing). The argmax rule therefore always prefers the best aspect-ratio match available in \(\mathcal{C}\); the waste tie-break then picks the *smallest* such canvas (least padding, fewest wasted tile-tokens on background).

⚠️ Common Pitfall

Effective resolution maximization can pick a larger grid than intuition suggests whenever it's the only candidate that fully covers the original pixel area — even if that grid's aspect ratio looks like a poor visual match. This is a known quirk: production configs curate \(\mathcal{C}\) carefully (e.g. LLaVA-NeXT-34B extends it to 1344px pinpoints) specifically to avoid pathological picks for extreme aspect ratios.

Key Takeaways & Comparison
▼

AnyRes sits in a family of "how do we feed a fixed-resolution vision transformer a variable-resolution image?" solutions. Each competing approach makes a different trade-off:

ApproachMechanismTokens scale withDetail preserved
LLaVA-1.5 (fixed)Single resize to 336²constantLow for large images
AnyRes (LLaVA-NeXT)Grid of native tiles + thumbnailO(tiles)High, bounded cost
Qwen-VL / Qwen2-VLNative dynamic resolution ViT, packed patchesO(pixels)High, variable cost
NaViTNative aspect-ratio training, patch packingO(pixels)High, no tiling seams
InternVL (pixel shuffle)Tiling + channel-space downsampleO(tiles / 4)High, token-efficient

When AnyRes shines: document/OCR-heavy images, screenshots, charts, infographics — anywhere small text or fine structure would vanish under a single 336×336 resize.

When it's overkill: natural photos where holistic scene understanding dominates (a single thumbnail captures most of the signal) — tiling adds token cost for little accuracy gain.

  • Tile count grows with image complexity of aspect ratio matching, not raw pixel count — a 4K image with a common aspect ratio may use the same grid as a 1080p one.
  • The global thumbnail is what lets the model reason about layout/relationships between tiles (a tile alone has no idea what's above or beside it, only learned separator tokens hint at position).
  • Token compression (2×2 pooling per tile) is the standard lever for trading fine detail against context-length budget in production deployments.
💡 Hierarchy

Fixed-res encoding (1 call) ⊂ AnyRes tiling (bounded grid of calls + thumbnail) ⊂ Native-resolution ViTs (continuous, unbounded patch packing). Each relaxes the previous stage's resolution ceiling at the cost of more tokens or more architecture change.

Code Trace
▼
import numpy as np
# Candidate grids: (rows, cols) at tile=336px, matching LLaVA-NeXT pinpoints
TILE = 336
CANDIDATES = [(1,2), (2,1), (2,2), (3,1), (1,3)]
def select_best_resolution(orig_w, orig_h, candidates):
best, max_eff, min_waste = None, -1, float('inf')
for (r, c) in candidates:
W, H = c * TILE, r * TILE
scale = min(W / orig_w, H / orig_h)
down_w, down_h = int(orig_w*scale), int(orig_h*scale)
eff = min(down_w * down_h, orig_w * orig_h)
waste = W * H - eff
if eff > max_eff or (eff == max_eff and waste < min_waste):
best, max_eff, min_waste = (r, c, W, H), eff, waste
return best
def tile_and_encode(image, grid, clip_encoder, tokens_per_tile=576):
r, c, W, H = grid
resized = resize_and_pad(image, (W, H)) # letterbox to grid canvas
tiles = split_into_tiles(resized, TILE) # r*c tiles of 336x336
local_tokens = [clip_encoder(t) for t in tiles] # each -> 576 tokens
thumbnail = resize(image, (TILE, TILE)) # global context view
global_tokens = clip_encoder(thumbnail)
return np.concatenate(local_tokens + [global_tokens]) # -> (r*c+1)*576 tokens
# Example
grid = select_best_resolution(1200, 400, CANDIDATES) # -> (1, 3, 1008, 336)
visual_tokens = tile_and_encode(image, grid, clip_vit_l14)
print(visual_tokens.shape) # (4 * 576, hidden_dim) = (2304, hidden_dim)
