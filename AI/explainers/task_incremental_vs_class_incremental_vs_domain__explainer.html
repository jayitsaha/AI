Continual Learning Settings: Task-Incremental, Class-Incremental, Domain-Incremental

Defining the challenges for models learning sequentially without forgetting
Foundational Deep Learning Continual Learning Problem Definition
1
Understanding Continual Learning Settings
▼

What is it? Continual Learning (CL), also known as Lifelong Learning, is the field of machine learning concerned with training models on a stream of data where tasks or data distributions change over time. The core challenge is to learn new information without "catastrophically forgetting" previously acquired knowledge. The specific setting or scenario defines what information the model has access to during training and, crucially, during inference.

Analogy: Imagine a medical AI assistant learning new diseases. Initially, it learns to diagnose common colds. Later, it's trained on flu symptoms. Then, on pneumonia. Then, on allergies. If it forgets how to diagnose colds after learning flu, it's failing at continual learning. The three settings define how the "exams" are structured:

  • Task-Incremental: The AI knows exactly which "exam" it's taking (e.g., "This is a cold diagnosis task, use the cold model").
  • Class-Incremental: The AI knows it's a "respiratory illness exam," but doesn't know if it's cold, flu, or pneumonia. It must pick from all diseases it has ever learned.
  • Domain-Incremental: The AI is still diagnosing colds, but now from a new data source (e.g., patient notes instead of lab results). The classes (cold/no cold) are the same, but the input data "domain" has shifted.
💡 If you remember one thing

The fundamental difference between these settings lies in the availability of task/domain identity at test time, and whether new tasks introduce new classes or just new data distributions for existing classes. This dictates the difficulty of the problem and the appropriate evaluation metrics.

2
How Each Setting Defines the Problem
▼

Task-Incremental (TI) Learning

In the Task-Incremental setting, the model is explicitly told which task it is currently performing during inference. This is the "easiest" of the three settings because it allows for task-specific components, such as a separate output head (classifier) for each task, or a routing mechanism that activates task-specific sub-networks. The model's primary challenge is to prevent interference between the shared feature extractor's parameters, ensuring that learning new tasks doesn't degrade performance on previous tasks.

  • Task ID at Test Time: YES
  • New Classes per Task: YES (typically)
  • Output Space: Task-specific (e.g., a classifier for Task A, another for Task B).
  • Primary Challenge: Preventing forgetting of task-specific knowledge in shared parameters.

Class-Incremental (CI) Learning

Class-Incremental learning is often considered the most challenging and realistic setting. Here, the model is NOT given a task ID during inference. Instead, it must classify an input into one of all classes seen so far across all tasks, using a single, unified output head. This means the model must learn to distinguish new classes from old classes, and also distinguish between old classes themselves, without the luxury of knowing which task a test sample belongs to. Catastrophic forgetting is particularly severe here, as the model's output layer is constantly being updated to accommodate new classes, often at the expense of old ones.

  • Task ID at Test Time: NO
  • New Classes per Task: YES
  • Output Space: Unified, encompassing all classes learned across all tasks.
  • Primary Challenge: Catastrophic forgetting of old classes while correctly classifying new ones, all within a single classifier.

Domain-Incremental (DI) Learning

In the Domain-Incremental setting, the classes themselves remain constant across tasks, but the input data distribution (the "domain") changes. For example, a model might learn to classify cats and dogs in natural images (Domain 1), then in sketches (Domain 2), then in paintings (Domain 3). The model is not provided with the domain ID at test time, so it must be robust to these domain shifts while maintaining high accuracy on the fixed set of classes. This setting often tests a model's ability to learn domain-invariant features or to quickly adapt to new visual styles/data characteristics.

  • Task ID at Test Time: NO (or Domain ID)
  • New Classes per Task: NO (classes are fixed)
  • Output Space: Unified, fixed set of classes.
  • Primary Challenge: Adapting to new data distributions (domains) without losing performance on previous domains for the same classes.
🔑 Key Property

The availability of a task identifier at test time is the single most important differentiator. Task-Incremental settings have it, making them easier. Class-Incremental and Domain-Incremental settings do not, forcing the model to learn more robust, generalized representations or suffer from severe forgetting.

3
Formalizing the Continual Learning Objective
▼

The General Continual Learning Objective

At its core, Continual Learning aims to train a model \(\theta\) on a sequence of tasks \(T_1, T_2, \dots, T_N\), where each task \(T_t\) is associated with a dataset \(D_t\). The ultimate goal is to achieve low loss on all tasks seen so far, while only having access to data from the current task \(D_t\) at training time. Formally, after learning task \(T_t\), we want to achieve low loss on all previous tasks \(T_1, \dots, T_t\):

$$ \min_{\theta} \sum_{k=1}^t \mathcal{L}(D_k; \theta) $$

However, the specific form of \(\mathcal{L}\) and how \(\theta\) is structured depends heavily on the incremental setting.

Task-Incremental (TI) Objective

In TI, a task ID \(t\) is available at test time. This often implies that the model can have task-specific components, such as a shared feature extractor \(f(\cdot;\theta_{shared})\) and task-specific classifiers \(h_k(\cdot;\theta_k)\). The loss for task \(T_t\) would then be:

$$ \mathcal{L}_{TI}(D_t; \theta) = \mathbb{E}_{(x,y) \sim D_t} \left[ \text{loss}\left(h_t\left(f(x;\theta_{shared})\right), y\right) \right] $$

During inference, given an input \(x\) and its task ID \(t\), the prediction is simply \(h_t(f(x;\theta_{shared}))\). The challenge becomes ensuring \(\theta_{shared}\) remains effective for all \(h_k\) without being overwritten. This is often tackled by parameter isolation or regularization techniques that protect parameters important for previous tasks.

Class-Incremental (CI) & Domain-Incremental (DI) Objectives

For both CI and DI, no task/domain ID is available at test time. This implies a single, unified classifier \(h(\cdot;\theta_{head})\) that must handle all classes (CI) or all domains for the same classes (DI). The loss for task \(T_t\) in these settings is typically:

$$ \mathcal{L}_{CI/DI}(D_t; \theta) = \mathbb{E}_{(x,y) \sim D_t} \left[ \text{loss}\left(h\left(f(x;\theta_{shared})\right), y\right) \right] $$

The key difference is in the definition of the output space and classes within \(D_t\). In CI, \(D_t\) introduces entirely new classes not seen in \(D_1, \dots, D_{t-1}\). The head \(h\) must expand its output dimensionality or adapt its weights to include these new classes, while still correctly classifying classes from \(D_1, \dots, D_{t-1}\). In DI, \(D_t\) contains the same classes as previous tasks, but the input distribution \(P(x)\) for these classes has changed. The head \(h\) remains fixed in terms of output classes, but the feature extractor \(f\) must learn to extract robust features across different domains.

⚠️ Evaluation Metrics are Key

Beyond the training objective, careful consideration of evaluation metrics is crucial. In TI, accuracy is typically measured per-task. In CI, accuracy is measured over all classes seen so far. Forgetting is often quantified as the drop in performance on old tasks after learning new ones. Metrics like Average Incremental Accuracy or Backward Transfer are specifically designed to capture these nuances.

Choosing the Right Setting:

  • Task-Incremental is often used for benchmarking new CL algorithms, as it isolates the forgetting problem to the feature extractor. It's less reflective of real-world scenarios where task identity is unknown.
  • Class-Incremental is the most challenging and realistic for applications like object recognition in a continuously growing world. Solutions often involve replay, regularization, or architectural modifications to protect old knowledge.
  • Domain-Incremental is relevant for models deployed in dynamic environments (e.g., self-driving cars encountering new weather conditions, medical imaging from new scanner types). Techniques often focus on domain generalization or adaptation.
💡 Big Picture

Understanding these distinctions is paramount for designing, evaluating, and comparing Continual Learning algorithms. A method that performs well in Task-Incremental might fail catastrophically in Class-Incremental, highlighting the importance of matching the evaluation setting to the real-world problem.

Code Trace (PyTorch-like Pseudocode)
▼
import torch
import torch.nn as nn
# A generic model for Continual Learning
class ContinualModel(nn.Module):
def __init__(self, num_tasks, num_classes_per_task, feature_dim=64):
super().__init__()
self.feature_extractor = nn.Sequential(
nn.Linear(2, feature_dim), nn.ReLU(), # Input is 2D for visualization
nn.Linear(feature_dim, feature_dim), nn.ReLU()
)
# Task-specific heads for Task-Incremental
self.task_heads = nn.ModuleList([
nn.Linear(feature_dim, num_classes_per_task) for _ in range(num_tasks)
])
# Unified head for Class/Domain-Incremental
self.unified_head = nn.Linear(feature_dim, num_tasks * num_classes_per_task) # Max classes
def forward(self, x, task_id=None, setting='CI'):
features = self.feature_extractor(x)
if setting == 'TI' and task_id is not None:
return self.task_heads[task_id](features) # Use specific head
elif setting in ['CI', 'DI']:
return self.unified_head(features) # Use unified head
else:
raise ValueError("Invalid setting or missing task_id for TI")
# Training loop sketch for different settings
def train_continual(model, tasks_data, setting='CI', epochs=10):
optimizer = torch.optim.Adam(model.parameters(), lr=0.001)
criterion = nn.CrossEntropyLoss()
for task_id, task_data in enumerate(tasks_data):
print(f"--- Training on Task {task_id+1} ({setting}) ---")
for epoch in range(epochs):
for inputs, labels in task_data:
optimizer.zero_grad()
if setting == 'TI':
outputs = model(inputs, task_id=task_id, setting='TI')
elif setting == 'CI':
# Labels might need remapping for unified head
outputs = model(inputs, setting='CI')
elif setting == 'DI':
outputs = model(inputs, setting='DI')
loss = criterion(outputs, labels)
loss.backward()
optimizer.step()
