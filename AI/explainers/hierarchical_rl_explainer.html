Understanding Hierarchical RL
▼

What is it? Hierarchical Reinforcement Learning (HRL) is a paradigm that structures decision-making in complex environments by breaking down a long-horizon task into a sequence of simpler, shorter-horizon sub-tasks. Instead of a single agent learning to choose every primitive action from scratch, HRL typically involves two or more levels of policies operating at different timescales and levels of abstraction.

Analogy: Imagine building a house. A "flat" RL agent would try to learn every single nail hammered, every brick laid, in sequence. A hierarchical agent would have a "Manager" (high-level policy) that decides on broad goals, like "Lay the foundation," "Build the walls," or "Install the roof." For each of these goals, a "Worker" (low-level policy) takes over, figuring out the precise sequence of actions (e.g., for "Lay the foundation": "dig trench," "pour concrete," "level surface"). The Manager only intervenes once a sub-goal is achieved, or after a certain time, making the overall learning process much more manageable.

💡 If you remember one thing

HRL tackles the challenges of sparse rewards and long-horizon credit assignment by introducing intermediate goals and intrinsic rewards. This allows agents to learn efficient strategies for complex tasks much faster than traditional "flat" RL approaches, which struggle with the vast search space of primitive actions.

2
How HRL Works Internally
▼

The Options Framework (Sutton et al., 1999)

The options framework extends the standard Markov Decision Process (MDP) to a Semi-Markov Decision Process (SMDP). An "option" is a temporally extended action defined by three components:

  1. Initiation Set \(I \subseteq \mathcal{S}\): The set of states in which the option can be chosen.
  2. Option Policy \(\pi_o(a|s)\): A policy that dictates primitive actions \(a\) while the option \(o\) is executing.
  3. Termination Condition \(\beta_o(s)\): A probability distribution over states, indicating the chance of the option terminating in state \(s\).

A high-level "Manager" policy chooses an option \(o\). Once chosen, the low-level option policy \(\pi_o\) takes over, executing primitive actions until the option terminates. The Manager then selects a new option. This enables learning at a coarser temporal granularity.

Feudal Networks (Dayan & Hinton, 1993; Vezhnevets et al., 2017)

Inspired by the feudal system, this architecture typically involves a "Manager" network and a "Worker" network. The Manager operates on a slower timescale, observing the full state \(s_t\) and outputting a sub-goal \(g_t\) (often a vector in a latent space) to the Worker. The Worker, operating on a faster timescale, receives this sub-goal and tries to achieve it by selecting primitive actions \(a_t\). The Worker is typically rewarded intrinsically for making progress towards the Manager's sub-goal, while the Manager receives the extrinsic reward from the environment.

Goal-Conditioned Reinforcement Learning

Many HRL approaches can be viewed through the lens of Goal-Conditioned RL. Here, the low-level policy is explicitly trained to reach arbitrary goals. The policy \(\pi(a|s, g)\) takes not only the current state \(s\) but also a desired goal \(g\) as input. The high-level Manager's role then simplifies to just selecting appropriate goals \(g\) for the low-level policy to achieve. This often involves learning a goal-reaching policy offline, then using a high-level planner or policy to string together these goal-reaching behaviors.

Design Decision: Why Not Just End-to-End RL?

Flat, end-to-end RL struggles with: 1) Sparse Rewards: If rewards are only given at the very end of a long task, learning is inefficient. HRL creates intermediate intrinsic rewards. 2) Long Horizon: The number of possible action sequences grows exponentially, making exploration difficult. HRL reduces the effective horizon for the high-level policy. 3) Transferability: Low-level skills (e.g., "open door") learned for one sub-goal can often be reused for other sub-goals or even different tasks.

🔑 Key Property

The core idea across all HRL variants is decomposition: breaking a complex problem into smaller, more manageable sub-problems. This usually manifests as policies operating at different temporal scales and with different reward functions (extrinsic for high-level, intrinsic for low-level).

Why It Works — The Math
▼

Bellman Equations for Options

In the options framework, the value function of a state \(s\) when choosing an option \(o\) is defined over the entire duration of the option's execution. Let \(R_t\) be the primitive reward at time \(t\), \(\gamma\) the discount factor, and \(\tau_o\) the random duration of option \(o\). The value of taking option \(o\) in state \(s\) is:

$$Q(s, o) = \mathbb{E}_{\pi_o, \tau_o} \left[ \sum_{k=0}^{\tau_o-1} \gamma^k R_{t+k+1} + \gamma^{\tau_o} V(S_{t+\tau_o}) \mid S_t=s, O_t=o \right]$$

where \(V(s)\) is the value of state \(s\) under the high-level policy, which selects options. The expected return from an option includes the sum of discounted rewards received while the option executes, plus the discounted value of the next state when the option terminates. The Manager's (high-level) value function then becomes:

$$V(s) = \max_o Q(s, o)$$

This formulation allows the Manager to learn optimal sequences of options, effectively abstracting away the primitive actions. The termination condition \(\beta_o(s)\) also plays a crucial role, determining when control returns to the Manager. For an option \(o\) with policy \(\pi_o\) and termination \(\beta_o\), the overall policy \(\pi(a|s)\) is:

$$\pi(a|s) = \sum_o \mu(o|s) \pi_o(a|s) \quad \text{where } \mu(o|s) \text{ is the Manager's policy}$$

This shows how the high-level policy \(\mu\) selects an option, and the option's policy \(\pi_o\) then dictates the low-level actions. The learning algorithms for options typically involve extending Q-learning or SARSA to this SMDP setting.

⚠️ Common Pitfall

Defining good options or goals is often the hardest part of HRL. If options are too primitive, the hierarchy offers little benefit. If they are too complex or poorly chosen, the worker may struggle to learn them, or the manager may struggle to sequence them effectively. The success of HRL heavily relies on a meaningful decomposition of the task.

Key Takeaways
▼

When to use Hierarchical RL:

  • Complex, long-horizon tasks: Where the path to the final reward involves many steps and sub-objectives.
  • Sparse reward environments: When the agent receives feedback only rarely, HRL provides intrinsic rewards for intermediate achievements.
  • Improved exploration: High-level policies can direct the agent to explore relevant parts of the state space, avoiding random wandering.
  • Transfer learning: Learned low-level skills (options/goal-conditioned policies) can often be reused in new tasks or environments, reducing training time.
  • Interpretability: The hierarchical structure can make the agent's decision-making process easier to understand.

When NOT to use:

  • Simple tasks with dense rewards: The overhead of designing and training a hierarchical system might outweigh the benefits.
  • When sub-goals are hard to define: If a task cannot be naturally decomposed into meaningful sub-goals, HRL may not be suitable.
  • Computational overhead: Training multiple interacting policies can sometimes be more complex and resource-intensive than a single flat policy, if not carefully designed.
💡 Big Picture

Hierarchical RL is a powerful approach for scaling RL to real-world problems. By mimicking human-like planning (breaking down problems), it enables agents to tackle challenges that are intractable for flat learning algorithms, opening doors for more capable and robust AI systems in complex domains like robotics, autonomous driving, and strategic gaming.

import torch
import torch.nn as nn
import torch.optim as optim
# --- 1. Manager Network (High-Level Policy) ---
class Manager(nn.Module):
def __init__(self, state_dim, goal_dim, num_subgoals):
super().__init__()
self.fc1 = nn.Linear(state_dim, 128)
self.fc_goal = nn.Linear(128, goal_dim) # Output a goal embedding
self.fc_subgoal_selector = nn.Linear(128, num_subgoals) # For discrete goals
def forward(self, state):
h = torch.relu(self.fc1(state))
# For continuous goal space (Feudal/GCRL)
goal_embedding = torch.tanh(self.fc_goal(h))
# For discrete sub-goals (Options)
subgoal_logits = self.fc_subgoal_selector(h)
return goal_embedding, subgoal_logits # Manager outputs a goal or chooses an option
# --- 2. Worker Network (Low-Level Policy) ---
class Worker(nn.Module):
def __init__(self, state_dim, goal_dim, action_dim):
super().__init__()
self.fc1 = nn.Linear(state_dim + goal_dim, 128) # State + Goal as input
self.fc_action = nn.Linear(128, action_dim)
def forward(self, state, goal):
x = torch.cat([state, goal], dim=-1) # Concatenate state and goal
h = torch.relu(self.fc1(x))
action_logits = self.fc_action(h)
