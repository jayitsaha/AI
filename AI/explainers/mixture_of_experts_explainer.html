Understanding Mixture of Experts
▼

What is it? In a normal transformer, every single token passes through the same feed-forward network (FFN). Mixture of Experts (MoE) replaces that one FFN with a bank of \(N\) smaller FFNs ("experts") plus a tiny router (gating network). For each token, the router picks only the top-\(k\) experts (typically \(k=1\) or \(2\)) and the token is only processed by those. The rest of the experts stay idle for that token.

Analogy: Think of a hospital with 8 specialist doctors instead of 1 generalist. A patient (token) doesn't see all 8 — a triage nurse (router) reads the symptoms and sends the patient to the 2 most relevant specialists. The hospital as a whole "knows" far more (8 specialties worth of knowledge = huge parameter count), but any single patient visit only costs 2 consultations worth of time (small compute per token).

💡 If you remember one thing

MoE decouples total parameters from per-token compute. A model can have 8× the parameters of a dense model while spending roughly the same FLOPs per token, because only \(k\) of \(N\) experts activate — this is called sparse activation.

How MoE Works Internally
▼

The MoE Layer, Step by Step

An MoE layer swaps the transformer's FFN sublayer for: (1) a router \(g\) — a single linear layer mapping the token's hidden state \(x \in \mathbb{R}^d\) to \(N\) logits, one per expert; (2) \(N\) expert FFNs \(E_1,\dots,E_N\), each a normal 2-layer MLP; (3) a combine step that mixes the outputs of only the top-\(k\) experts, weighted by the router.

$$h = g(x) \in \mathbb{R}^N \quad\Rightarrow\quad p = \operatorname{softmax}(h) \quad\Rightarrow\quad \mathcal{T} = \operatorname{top\text{-}}k(p)$$

Only the experts in \(\mathcal{T}\) actually run. Their probabilities are renormalized to sum to 1, and the token's output is the weighted sum:

$$y = \sum_{i \in \mathcal{T}} \frac{p_i}{\sum_{j \in \mathcal{T}} p_j} \, E_i(x)$$

Design Decision: Why Top-k and Not All Experts?

Running all \(N\) experts (a "dense mixture") would use every parameter but cost \(N\times\) the FLOPs of one FFN — no compute savings. Running only \(k \ll N\) experts keeps FLOPs close to a single dense FFN while still letting the model store \(N\times\) the parameters. This is the whole point: capacity scales with \(N\), compute scales with \(k\).

The Load-Balancing Problem

Left unchecked, the router quickly collapses: a few experts become "favorites" and get all the tokens (and all the gradient signal), while others are never selected and never improve — a rich-get-richer feedback loop. This wastes capacity and can even overflow an expert's fixed token capacity (buffer size), causing tokens to be silently dropped. MoE training therefore adds an auxiliary load-balancing loss that penalizes uneven routing, alongside (or instead of, in newer designs) per-expert bias terms that nudge underused experts to get picked more.

🔑 Key Property

MoE is a form of conditional computation: which parameters run is a function of the input itself, decided at inference time by a learned router — not fixed by architecture. Switch Transformer (Fedus et al. 2021) popularized \(k=1\) routing; Mixtral 8x7B (2023) uses \(k=2\) of \(N=8\) experts per layer.

Why It Works — The Math
▼

Router Probabilities

For token \(x\) with router weight matrix \(W_g \in \mathbb{R}^{N\times d}\), the gate logits and probabilities are:

$$h_i = w_{g,i}^\top x, \qquad p_i = \frac{e^{h_i}}{\sum_{j=1}^{N} e^{h_j}}, \quad i=1,\dots,N$$

Top-\(k\) routing keeps only the \(k\) largest \(p_i\) and zeroes the rest — this is what makes computation sparse: experts outside the top-\(k\) receive no forward or backward pass for that token.

The Switch Transformer Load-Balancing Loss

Over a batch of \(T\) tokens, define for each expert \(i\): the dispatch fraction \(f_i\) (share of tokens routed to expert \(i\) as their top choice) and the router mass \(P_i\) (average router probability the gate assigns to expert \(i\), across all tokens, not just the ones dispatched to it):

$$f_i = \frac{1}{T}\sum_{t=1}^{T} \mathbb{1}[\arg\max_j p^{(t)}_j = i], \qquad P_i = \frac{1}{T}\sum_{t=1}^{T} p^{(t)}_i$$

The auxiliary loss is the scaled dot product of these two vectors:

$$\mathcal{L}_{aux} = \alpha \cdot N \sum_{i=1}^{N} f_i \cdot P_i$$

Since \(\sum_i f_i = \sum_i P_i = 1\), the minimum of \(\sum_i f_i P_i\) is \(1/N\) (reached when both vectors are uniform), giving \(\mathcal{L}_{aux}^{min} = \alpha\). Any imbalance pushes \(\sum_i f_i P_i\) above \(1/N\), so gradient descent on \(\mathcal{L}_{aux}\) pushes the router toward uniform \(f_i\) and \(P_i\). Multiplying by \(N\) keeps the loss scale roughly constant as \(N\) changes.

Why multiply \(f\) (non-differentiable, from argmax) by \(P\) (differentiable, from softmax)? \(f_i\) alone can't be backpropagated through (it's a hard count), but \(P_i\) can. The product lets gradients flow through \(P_i\) while \(f_i\) still reflects the true hard-routing imbalance the loss is trying to fix.

⚠️ Common Pitfall

Load balancing is a soft constraint, not a guarantee — a bad batch can still overflow an expert's fixed capacity \(C\) (typically \(C = \frac{T}{N}\times\text{capacity factor}\)), and overflow tokens get dropped (skip the expert, pass through via residual only). Newer approaches (DeepSeek-V3) instead add a per-expert bias to logits, updated by a simple sign rule based on load — balancing routing without a gradient-based auxiliary loss at all.

Key Takeaways
▼

When MoE shines:

  • You want a much larger model (more knowledge capacity) without paying proportionally more inference FLOPs
  • You can shard experts across devices (expert parallelism) — routing becomes a natural distribution axis
  • Pretraining compute is the bottleneck, not parameter/VRAM count (MoE trades memory for compute)

When NOT to reach for MoE:

  • Memory-constrained single-device serving — MoE needs all experts resident even though only a few run per token
  • Small models / small data, where routing instability and load imbalance outweigh the capacity benefit
  • You need simple, fully deterministic latency — token-dependent routing adds variance and drop-risk under capacity limits
💡 The Core Trade

Dense FFN: params = compute, always. MoE: params = \(N\times\) one expert, compute ≈ \(k\times\) one expert. Switch Transformer (\(k{=}1\)) pushes this trade-off furthest; Mixtral (\(k{=}2\) of 8) balances quality and stability. Load balancing is what keeps the "sparse" promise from silently degrading into "\(k\) experts do all the work."

Code Trace
▼
import torch, torch.nn as nn, torch.nn.functional as F
class MoELayer(nn.Module):
def __init__(self, d_model, d_ff, n_experts=6, k=2):
super().__init__()
self.router = nn.Linear(d_model, n_experts, bias=False)
self.experts = nn.ModuleList([
nn.Sequential(nn.Linear(d_model, d_ff), nn.ReLU(),
nn.Linear(d_ff, d_model))
for _ in range(n_experts)])
self.n_experts, self.k = n_experts, k
def forward(self, x): # x: (tokens, d_model)
logits = self.router(x) # (tokens, n_experts)
probs = F.softmax(logits, dim=-1)
topk_p, topk_i = probs.topk(self.k, dim=-1)
topk_p = topk_p / topk_p.sum(dim=-1, keepdim=True) # renormalize
out = torch.zeros_like(x)
for slot in range(self.k):
idx = topk_i[:, slot] # which expert, per token
w = topk_p[:, slot].unsqueeze(-1) # its weight
for e in range(self.n_experts): # dispatch by expert (batched)
mask = (idx == e)
if mask.any():
out[mask] += w[mask] * self.experts[e](x[mask])
# ── load-balancing auxiliary loss (Switch Transformer) ──
f = F.one_hot(topk_i[:, 0], self.n_experts).float().mean(0) # dispatch frac
P = probs.mean(0) # avg router prob per expert
aux_loss = self.n_experts * (f * P).sum()
return out, aux_loss
