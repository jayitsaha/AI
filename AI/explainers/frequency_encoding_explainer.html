🔢 Frequency / Count Encoding
Replace each category with how often it appears in the training set
🟡 Intermediate Part III · Classical ML Feature Encoding O(n) encoding
1
The 30-Second Version

What is this?

Every categorical column (like City or Browser) holds text labels that most ML models can't use directly. Frequency encoding swaps each label with a single number: how many times that label appeared in your training data. "London" might become 4200, "Paris" 1800, "Osaka" 93 — all computed before training begins.

Real-World Analogy

Imagine you're organising concert ticket sales by venue. Instead of writing "Madison Square Garden" everywhere, you stamp each ticket with the total number of shows ever held at that venue. A stadium that hosted 500 concerts gets the number 500. A tiny club that had 12 gets 12. Every venue is now a number your spreadsheet formulas (or model) can crunch.

💡 If you remember one thing

Frequency encoding maps each category \(c\) to \(\text{freq}(c) = \frac{\text{count}(c)}{N}\) (proportion) or simply \(\text{count}(c)\) (raw count). It is computed entirely from the input column — no target variable needed — so it carries zero risk of target leakage.

2
Why It Exists — Historical Context

The Problem

One-hot encoding (OHE) expands a column with \(K\) unique categories into \(K\) binary columns. For small \(K\) (e.g., Gender with 2 values) that is fine. For high-cardinality columns — Zip Code (40 000+ values), Product SKU (millions), User ID — OHE produces a matrix so wide it runs out of RAM and drowns tree models in irrelevant splits.

What Came Before

Label encoding assigns an arbitrary integer 0, 1, 2, … to each category. It is compact but injects a fake ordinal relationship: "Cat=2 > Dog=1 > Bird=0" implies an ordering that does not exist. Linear models are misled; tree models are fine but still see no signal from the integer itself.

The Breakthrough

Practitioners noticed that the raw occurrence count of a category is often a meaningful feature by itself — rare categories are statistically different from common ones. Simply replacing each label with its count (or proportion) became a standard preprocessing trick in Kaggle competitions circa 2013–2015, popularised through shared notebooks and competition write-ups rather than a formal paper.

Core Concepts & Theory
🔑 Key Concept

Frequency encoding is a univariate, unsupervised, invertible map from a categorical feature to a scalar. It depends only on the marginal distribution of that column, not on the target \(y\).

Two variants

  • Count encoding — replace with the raw integer count \(\text{count}(c)\).
  • Frequency encoding — replace with the proportion \(\hat{p}(c) = \text{count}(c)/N\), where \(N\) = total training rows. Values lie in \((0, 1]\).

Both carry identical information (one is a constant multiple of the other), but normalised frequency is preferred when the training set size changes (e.g., cross-validation folds) because the values stay comparable across folds.

Formal Definition

Let \(\mathcal{C} = \{c_1, c_2, \ldots, c_K\}\) be the set of unique categories in column \(X\), observed over \(N\) training samples. Define:

$$\text{count}(c_k) = \sum_{i=1}^{N} \mathbf{1}[x_i = c_k]$$
$$\hat{p}(c_k) = \frac{\text{count}(c_k)}{N}$$

The encoded column \(\tilde{X}\) is constructed by the lookup \(\tilde{x}_i = \hat{p}(x_i)\).

Collision Property

If \(\text{count}(c_j) = \text{count}(c_k)\) for \(j \neq k\), then \(\tilde{x} = \hat{p}(c_j) = \hat{p}(c_k)\). The model cannot distinguish these categories from the encoded feature alone. This is the fundamental limitation of frequency encoding.

⚠️ Collision Warning

In a dataset with many rare categories (counts of 1, 2, 3, …), huge numbers of categories share the same count, creating a massive collision cluster. Tree models handle this gracefully (the split point separates groups by count level); linear models get confused. In extreme cases, combine frequency encoding with another encoding for the collision bucket.

  • Understanding of categorical vs. numerical features
  • Train/test split discipline (fit the encoder on train only)
  • Basic pandas / sklearn API familiarity

The Math Behind It

Step-by-step derivation

We want to transform categorical feature \(X \in \mathcal{C}^N\) into a numeric vector \(\tilde{X} \in \mathbb{R}^N\) using only the training distribution.

Step 1 — Count occurrences. For each unique category \(c_k\):

$$n_k = |\{i : x_i = c_k\}| = \sum_{i=1}^{N} \mathbf{1}[x_i = c_k]$$

Step 2 — Compute proportions. Divide by total training rows:

$$\hat{p}_k = \frac{n_k}{N}, \quad \sum_{k=1}^{K} \hat{p}_k = 1$$

Step 3 — Build the lookup map. Construct \(\phi: \mathcal{C} \to (0,1]\):

$$\phi(c_k) = \hat{p}_k$$

Step 4 — Apply at both train and test time. For any sample \(x_i\):

$$\tilde{x}_i = \phi(x_i) = \hat{p}_{k(i)}, \quad \text{where } k(i) = \arg\min_k \mathbf{1}[x_i = c_k]$$

Unseen categories at test time. If \(x_j \notin \mathcal{C}\) (novel category at inference), the standard strategy is to assign a small fallback value. Common choices:

  • Assign 0 (treat as never-seen)
  • Assign \(1/N\) (treat as a single occurrence)
  • Assign the mean frequency across training categories
$$\phi_{\text{fallback}} = \frac{1}{N} \quad \text{or} \quad \phi_{\text{fallback}} = \frac{1}{K} \sum_{k=1}^{K} \hat{p}_k = \frac{1}{K}$$
📐 Collision Probability Formula

Two uniformly drawn distinct categories \(c_j, c_k\) collide iff \(n_j = n_k\). Under a Zipf-distributed categorical variable with parameter \(s\), the collision probability for two random categories grows as \(\mathcal{O}(K^{-2s})\). For \(s \approx 1\) (common in NLP / e-commerce), collisions remain frequent for large \(K\).

⚠️ Common Misconception

"Frequency encoding is the same as target encoding." They are completely different. Target encoding replaces categories with the mean of the target variable for that category. Frequency encoding replaces with the marginal count of the category — it never looks at the target. Target encoding is powerful but prone to leakage if implemented carelessly; frequency encoding is always leak-free.

Code Implementation

From Scratch (NumPy / pandas)

import numpy as np
import pandas as pd
def frequency_encode(train_col, test_col=None, normalize=True):
"""Frequency-encode a categorical column.
Args:
train_col : pd.Series — training categories
test_col : pd.Series — test categories (optional)
normalize : bool — True → proportions (0,1], False → raw counts
Returns:
(train_enc, test_enc, freq_map)
"""
# Step 1: count occurrences on TRAINING data only
freq_map = train_col.value_counts(normalize=normalize)
# freq_map is a Series: index = category, value = freq/count
# Step 2: map training column (NaN for unseen = impossible here)
train_enc = train_col.map(freq_map)
test_enc = None
if test_col is not None:
# Step 3: map test column — unseen categories become NaN
test_enc = test_col.map(freq_map)
# Fallback: fill NaN with the smallest observed frequency
fallback = freq_map.min() if normalize else 1
test_enc = test_enc.fillna(fallback)
return train_enc, test_enc, freq_map
# ── Example usage ──────────────────────────────────────────────
train = pd.Series(["London","Paris","London","Osaka","Paris","London","Tokyo","Paris"])
test = pd.Series(["Osaka","London","Berlin"]) # "Berlin" unseen
tr_enc, te_enc, fmap = frequency_encode(train, test, normalize=True)
print(fmap)
# London 0.375 (3/8)
# Paris 0.375 (3/8) ← collision with London!
# Osaka 0.125 (1/8)
# Tokyo 0.125 (1/8) ← collision with Osaka

Production Usage (sklearn Pipeline)

from sklearn.base import BaseEstimator, TransformerMixin
from sklearn.pipeline import Pipeline
import pandas as pd, numpy as np
class FrequencyEncoder(BaseEstimator, TransformerMixin):
def __init__(self, normalize=True, handle_unknown="min"):
self.normalize = normalize # proportion vs count
self.handle_unknown = handle_unknown # "min", "zero", "mean"
def fit(self, X, y=None): # y intentionally ignored — no leakage
self.freq_maps_ = {}
for col in X.columns:
self.freq_maps_[col] = X[col].value_counts(normalize=self.normalize)
return self
def transform(self, X):
out = X.copy()
for col, fmap in self.freq_maps_.items():
out[col] = X[col].map(fmap)
# Handle unseen categories
if self.handle_unknown == "zero": fallback = 0
elif self.handle_unknown == "mean": fallback = fmap.mean()
else: fallback = fmap.min() # "min"
out[col] = out[col].fillna(fallback)
return out
# ── In a full pipeline ─────────────────────────────────────────
from sklearn.ensemble import GradientBoostingClassifier
pipe = Pipeline([
("freq_enc", FrequencyEncoder(normalize=True)),
("model", GradientBoostingClassifier()),
])
pipe.fit(X_train, y_train) # ✓ encoder sees only train distribution
🚨 Critical Gotcha

Never call value_counts() on the full dataset before the train/test split. The test-set category frequencies leak into the training encoder, inflating model performance on evaluation. Always fit the encoder on X_train only, then transform X_test separately.

Interview Deep-Dive

Q1 (Easy) — What is frequency encoding?

A: Replace each category with the proportion (or count) of times it appears in the training data. It is computed without the target variable, requires no expansion of feature dimensionality, and handles high-cardinality columns efficiently.

Q2 (Easy) — How does it differ from label encoding?

A: Label encoding assigns arbitrary integers (e.g., A→0, B→1, C→2), injecting a false ordinal relationship. Frequency encoding assigns values that reflect the actual marginal distribution — the numeric magnitude carries real statistical meaning (frequency rank) even if the ordering is not guaranteed to match target relevance.

Q3 (Medium) — What is the collision problem and when does it matter?

A: If two categories appear equally often, they receive the same encoded value. The model cannot distinguish them. This matters most when: (a) the equally-frequent categories have different relationships with the target; (b) there are many rare categories all with count 1 (a common scenario in user-ID columns). Mitigation: combine with another encoding, or use count encoding + rank encoding jointly.

Q4 (Medium) — Should you use count or proportion? Does it matter?

A: For a fixed training set, count and proportion are linearly related by \(N\), so tree models (which only care about rank order of splits) treat them identically. For linear models, proportion keeps the feature scale stable when the training-set size changes across CV folds — prefer proportion. When comparing models trained on different-sized folds, proportion is definitely more stable.

Q5 (Medium) — How do you handle unseen categories at inference time?

A: Three common strategies: (1) assign 0 — signals "never seen during training", safe for trees; (2) assign the global minimum training frequency — conservative but non-zero; (3) assign the mean training frequency — neutral guess. The best choice depends on the model: for trees, strategy (1) may isolate unseen categories in a clean leaf; for linear models, strategy (3) is less disruptive.

Q6 (Hard) — Compare frequency encoding vs. target encoding under data leakage risk.

A (PhD-level): Target encoding replaces \(c_k\) with \(\mathbb{E}[y \mid X = c_k]\), estimated from training data. If the estimator uses the same row to compute the mean and train the model, it introduces a form of look-ahead bias — especially damaging for rare categories where the within-category sample is tiny and noisy. Smoothing (e.g., \(\hat{\mu}_k = \frac{n_k \bar{y}_k + \lambda \bar{y}}{n_k + \lambda}\)) and out-of-fold estimation mitigate this. Frequency encoding has zero leakage risk because it never observes \(y\). The trade-off: frequency encoding discards target information entirely, while correctly-regularised target encoding can be far more informative — especially in tree models where frequency alone may not induce good splits aligned with the target.

A (Research Scientist/Engineer level): In a properly constructed CV loop, use TargetEncoder(cv=5, smooth='auto') (sklearn ≥ 1.3) which applies cross-fitting to avoid leakage. Frequency encoding never needs such care and is safer for junior engineers. Prefer target encoding when category rarity is low (each category has many rows); prefer frequency encoding when the column is very high-cardinality (millions of SKUs) or when you need a guaranteed leak-free baseline.

Q7 (Hard) — How does frequency encoding interact with gradient-boosted trees?

A: GBTs split numeric features at thresholds. Frequency encoding converts categories to a scalar, giving the tree a frequency-ordered axis to split on. This is particularly powerful when category frequency is correlated with the target (e.g., popular cities have different patterns than obscure ones). However, the tree learns to split on frequency level, not on the original category identity. Two categories sharing the same frequency value are placed in the same leaf — the collision problem directly limits model expressiveness.

System Design Angle

In a real-time serving pipeline, frequency encoding is cheap to update: maintain a rolling count table and recompute \(\hat{p}_k\) periodically. Unlike target encoding, you do not need labels to update it, making it suitable for real-time feature stores where labels arrive with a delay.

🚨 Red Flags (Wrong Answers)
  • "Frequency encoding can cause target leakage" — False. It never touches \(y\).
  • "It's the same as label encoding" — No. Label encoding uses arbitrary integers; frequency encoding uses statistically meaningful counts.
  • "You can compute it on the full dataset before splitting" — Classic leakage trap.

  • K < 15, linear model → One-Hot Encoding
