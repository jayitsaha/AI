Understanding KV-cache
▼

What is it? In Transformer models (like LLMs), the self-attention mechanism requires computing "Key" (K) and "Value" (V) vectors for every token in the input sequence. When generating text token by token, we need to attend to *all* previously generated tokens. Recomputing K and V for the entire sequence at each step is computationally wasteful. The KV-cache is a mechanism to store these K and V vectors for past tokens, so they can be reused without recomputation.

Analogy: Imagine you're writing a long essay. Every time you write a new sentence, you need to refer back to all previous sentences to ensure coherence. If you had to re-read the entire essay from the beginning *every time* you added a new sentence, it would be slow. The KV-cache is like a "scratchpad" where you quickly jot down the key ideas (K) and supporting details (V) of each sentence as you write it, so when you add a new sentence, you only need to glance at your scratchpad, not re-read the whole essay.

💡 If you remember one thing

KV-cache makes LLM inference much faster by avoiding redundant computations of past K/V pairs. However, it consumes a significant amount of GPU memory, often becoming the primary bottleneck for serving multiple concurrent requests, especially with variable sequence lengths.

2
KV-cache: The Memory Bottleneck
▼

The Mechanism: Storing K & V Vectors

For each layer and each attention head in a Transformer, when a token \(x_i\) is processed, it generates a Key vector \(K_i\) and a Value vector \(V_i\). These are concatenated into a "Key-Value cache" for the entire sequence. When the next token \(x_{i+1}\) is generated, its Query vector \(Q_{i+1}\) will attend to \(K_1, \dots, K_i\) and combine with \(V_1, \dots, V_i\). The cache stores these past K and V vectors.

The size of the KV-cache for a single sequence is proportional to: (num_layers * num_heads * 2 * head_dim * sequence_length * sizeof(float)). For large models and long sequences, this quickly becomes gigabytes per sequence.

The Memory Problem: Fragmentation & Waste

When serving multiple LLM requests concurrently, each request has a different and unpredictable length. Traditional KV-cache management suffers from:

  1. Static Allocation: Pre-allocating the maximum possible sequence length for every request wastes a huge amount of memory if most requests are short.
  2. Dynamic Allocation (Contiguous): Allocating memory as needed is better, but if each sequence needs its KV-cache to be in a contiguous block of GPU memory, freeing and allocating blocks of different sizes leads to severe memory fragmentation. This means you might have plenty of *total* free memory, but not enough *contiguous* free memory to satisfy a new, large request.

This fragmentation drastically reduces the number of concurrent requests a GPU can handle, leading to low GPU utilization and high latency.

Design Decision: Why not just recompute?

Recomputing the K/V pairs for all past tokens for every new token would make inference \(O(L^2)\) instead of \(O(L)\) (where \(L\) is the sequence length). For typical LLM sequence lengths (hundreds to thousands of tokens), this is far too slow for real-time applications. The performance gain from caching far outweighs the memory challenges, making efficient memory management a critical system problem.

🔑 Key Property

The KV-cache is a large, dynamic data structure. Its memory footprint is proportional to the sum of all active sequence lengths. Efficiently packing these variable-length caches into fixed-size GPU memory is the core challenge solved by Paged Attention.

Why It Works — The Paged Attention Analogy
▼

Self-Attention & KV-cache in Equations

For a token \(x_i\), we compute its Query, Key, and Value vectors:

$$Q_i = x_i W_Q, \quad K_i = x_i W_K, \quad V_i = x_i W_V$$

To compute the output for token \(i\), its Query \(Q_i\) attends to all past Keys \(K_j\) (for \(j \le i\)) and combines with their corresponding Values \(V_j\):

$$\text{Attention}(Q_i, K_{1..i}, V_{1..i}) = \sum_{j=1}^i \text{softmax}\left(\frac{Q_i K_j^\top}{\sqrt{d_k}}\right) V_j$$

The KV-cache stores \((K_j, V_j)\) for \(j < i\), so only \(K_i\) and \(V_i\) need to be computed for the new token, then appended to the cache.

Paged Attention: Virtual Memory for LLMs

The core idea of Paged Attention (introduced by vLLM) is to manage the KV-cache memory like an operating system manages virtual memory. Instead of requiring each sequence's KV-cache to be a single contiguous chunk of GPU memory, it divides the KV-cache into fixed-size "blocks."

Each block can store the K and V vectors for a fixed number of tokens (e.g., 4, 8, or 16 tokens). A block table (similar to a page table in OS) maps the logical indices of a sequence's tokens to their physical block locations in GPU memory. This means a sequence's KV-cache can be stored in non-contiguous physical blocks.

$$\text{sequence\_tokens}[t] \quad \xrightarrow{\text{Block Table}} \quad \text{physical\_block\_id}[t/\text{block\_size}] \quad \xrightarrow{\text{offset}} \quad \text{KV\_cache\_memory}$$

This virtual memory approach solves the fragmentation problem. When a sequence needs more memory (i.e., generates a new token), the system simply allocates a new *free block* from anywhere in GPU memory and adds its physical ID to the sequence's block table. When a sequence finishes, its blocks are returned to a global free pool, without creating unfillable gaps.

🔑 Key Property

Paged Attention decouples the logical continuity of a sequence's KV-cache from its physical contiguity in GPU memory. This allows for flexible allocation, eliminates fragmentation, and enables efficient memory sharing (e.g., for speculative decoding or batching with shared prefixes).

Key Takeaways
▼

When to use Paged Attention (or similar virtual memory approaches):

  • High-throughput LLM serving scenarios (e.g., API endpoints, large-scale deployments).
  • When dealing with highly variable input/output sequence lengths, which is common in real-world use cases.
  • To maximize GPU utilization and reduce inference latency when running multiple concurrent requests.
  • When memory sharing (e.g., for prompt caching, speculative decoding, or LoRA adapters) is desired, as block-level management simplifies this.

When NOT to use / Consider alternatives:

  • Single-user, low-throughput scenarios where the overhead of block management might not be justified.
  • Models small enough that KV-cache memory is not a bottleneck.
  • Custom hardware or very specific use cases where a different memory layout might be more optimal.
💡 The Big Picture

Paged Attention is a crucial systems-level optimization that bridges the gap between the theoretical efficiency of KV-caching and the practical realities of GPU memory management. By applying principles from operating system virtual memory, it transforms a fragmented, underutilized resource into a highly efficient, dynamically allocatable pool, enabling LLMs to serve more users faster.

import numpy as np
class BlockManager:
def __init__(self, num_gpu_blocks, tokens_per_block):
self.num_gpu_blocks = num_gpu_blocks
self.tokens_per_block = tokens_per_block
self.free_blocks = list(range(num_gpu_blocks)) # Pool of free block IDs
self.allocated_blocks = {} # {block_id: owner_seq_id}
def allocate(self, num_blocks, seq_id):
if len(self.free_blocks) < num_blocks:
raise MemoryError("Not enough free blocks")
allocated_ids = []
for _ in range(num_blocks):
block_id = self.free_blocks.pop(0) # Take from front for simplicity
self.allocated_blocks[block_id] = seq_id
allocated_ids.append(block_id)
return allocated_ids
def free(self, block_ids):
for block_id in block_ids:
if block_id in self.allocated_blocks:
del self.allocated_blocks[block_id]
self.free_blocks.append(block_id) # Return to pool
self.free_blocks.sort() # Keep sorted for predictable allocation
class Sequence:
def __init__(self, seq_id, initial_tokens, block_manager):
self.seq_id = seq_id
self.logical_to_physical = [] # List of physical block IDs
self.length = 0
self.block_manager = block_manager
self.append_tokens(initial_tokens)
def append_tokens(self, num_new_tokens):
new_total_length = self.length + num_new_tokens
required_blocks = np.ceil(new_total_length / self.block_manager.tokens_per_block).astype(int)
blocks_to_allocate = required_blocks - len(self.logical_to_physical)
if blocks_to_allocate > 0:
new_blocks = self.block_manager.allocate(blocks_to_allocate, self.seq_id)
self.logical_to_physical.extend(new_blocks)
self.length = new_total_length
def free_all_blocks(self):
self.block_manager.free(self.logical_to_physical)
self.logical_to_physical = []
self.length = 0
