Handling thousands of frames within a fixed token budget
Advanced Multimodal / Video-LLM Long-Context O(N·(c+M)) vs O(N²)
1
Understanding Streaming Attention for Video
▼

What is it? A one-hour video sampled at 1 frame/sec gives 3,600 frames. Encode each frame into ~64 vision tokens and you get 230,400 tokens — far beyond any LLM's context window, and full self-attention over them costs \(O(N^2)\). Streaming attention for video is a family of techniques that ingest the frame stream chunk-by-chunk and keep only a small, fixed-size memory bank of tokens, no matter how long the video runs.

Analogy: Imagine a security guard watching a live camera feed all day, but only allowed one notebook with 1,024 lines. She can't write down everything — so she skips near-duplicate moments (nothing changed), jots dense summaries instead of verbatim transcripts, and periodically compresses yesterday's pages into a single condensed line to make room for today's. The notebook never grows, yet she can still answer "what happened three hours ago?"

💡 If you remember one thing

Streaming video attention trades a hard bound on memory for a small amount of lossy compression: keyframe selection removes redundant frames, token merging shrinks each frame's token count, and a fixed-size memory bank (with eviction) absorbs new information by compressing old information — keeping the token budget \(B\) constant even as the number of frames \(F \to \infty\).

2
How It Works Internally
▼

The Token Explosion Problem

A vision encoder (ViT/CLIP-style) turns each frame into \(t\) patch tokens (commonly 24–256 after pooling). Concatenating \(F\) frames naively gives \(N = F \times t\) tokens fed into the LLM. Both the KV-cache memory (linear in \(N\)) and the attention compute (quadratic in \(N\)) blow up: at \(F=3{,}600\), \(t=64\), \(N = 230{,}400\) — an order of magnitude past typical 32K–128K context windows, and self-attention cost scales as \(N^2\).

The Streaming Pipeline

Instead of materializing all tokens at once, the stream is processed in chunks of \(c\) frames (e.g. \(c=60\), one minute at 1 fps), sequentially, in four stages per chunk:

  • Keyframe selection — compute frame-to-frame similarity (e.g. cosine distance of pooled embeddings); drop frames that are near-duplicates of a recently kept one. Keeps only the frames that carry new information.
  • Token merging (ToMe-style) — within each kept frame, merge spatially/semantically similar patch tokens (bipartite soft matching), cutting tokens-per-frame roughly in half or more.
  • Memory write (cross-attention pooling) — a small set of \(M\) learned query tokens (Perceiver-resampler style) cross-attend over the chunk's surviving tokens and compress them into exactly \(M\) memory tokens, regardless of how many tokens the chunk started with.
  • KV eviction — the memory bank has a hard cap \(B\). It always keeps an attention sink (the very first chunk, à la StreamingLLM) and a high-fidelity recent window (the last few chunks); once the bank fills up, older "middle" chunks are pairwise merged/re-pooled into a shrinking coarse region so total size never exceeds \(B\).
🔑 Key Property

The memory bank size is independent of stream length: \(\text{Tokens}(k) = \min(k\cdot M,\, B)\) for \(k\) chunks processed so far. Past a saturation point (\(k \approx B/M\)) the bank is exactly full and stays at \(B\) forever — an hour-long or a week-long video occupies the same token budget.

Design Decision: Why Eviction Instead of Just Truncating?

Naively truncating (drop the oldest chunk's tokens entirely) loses early context permanently — bad for questions like "what happened at the very start?". Keeping a sink chunk plus a coarsened, ever-compressing middle region (as in StreamingLLM / H2O / MovieChat-style memory consolidation) preserves a trace of every chunk at progressively lower resolution, rather than hard-dropping it.

3
Why It Works — The Math
▼

Cost Comparison

Full attention over the entire concatenated stream costs:

$$\text{Cost}_{\text{full}} = O(N^2 d), \qquad N = F \times t$$

Streaming attention processes \(K = F/c\) chunks, each attending only over its own \(c\) tokens plus the bounded memory \(M\), so the accumulated cost is:

$$\text{Cost}_{\text{stream}} = O\!\Big(\sum_{k=1}^{K} c\,(c+M)\Big) = O\big(K\cdot c\,(c+M)\big) = O\big(N\,(c+M)\big)$$

Since \(c, M \ll N\), this is linear in \(N\) rather than quadratic — the whole point of never materializing the full \(N\times N\) attention matrix.

Memory Write as Cross-Attention Pooling

Each chunk's compression into fixed-size memory uses learned query vectors \(Q_{\text{mem}} \in \mathbb{R}^{M\times d}\) (Perceiver-resampler style) that cross-attend over the chunk's keys/values \(K_k, V_k \in \mathbb{R}^{c'\times d}\) (\(c'\) = tokens surviving keyframe filtering + merging):

$$\text{Mem}_k = \operatorname{softmax}\!\left(\frac{Q_{\text{mem}} K_k^\top}{\sqrt{d}}\right) V_k \;\in\; \mathbb{R}^{M \times d}$$

Because \(Q_{\text{mem}}\) has a fixed number of rows \(M\), the output is always \(M\) tokens no matter how large \(c'\) is — this is what makes the memory bank size decoupled from the stream length.

Bounded Memory Bank Size

$$\text{Tokens}(k) = \min(k \cdot M,\; B), \qquad \rho = \frac{F \cdot t}{\text{Tokens}(K)}\;\text{(compression ratio)}$$
⚠️ Common Pitfall

Compression is lossy. Aggressive keyframe dropping or over-merging can silently discard the one frame that answers the query (a rare event, a sudden cut). Systems must balance the budget \(B\) against recall — pure recency windows forget the past entirely, which is why attention sinks and hierarchical (not uniform) eviction matter.

Key Takeaways
▼

When streaming/memory attention shines:

  • Hour+ long videos, egocentric/lifelog streams, live camera feeds — anything where \(F \times t\) blows past the context window
  • Question-answering or captioning that needs some access to distant past events, not just the last few seconds
  • Deployment under a hard latency/memory budget (edge devices, real-time assistants)

When NOT to bother:

  • Short clips that already fit comfortably in context — the compression only adds complexity and risk of losing detail
  • Tasks needing pixel-exact recall of every frame (e.g. precise re-identification) — heavy merging/eviction hurts fine-grained recall
💡 Hierarchy

Full attention (all \(N\) tokens, \(O(N^2)\)) → Keyframe sampling (fewer frames, same cost shape) → Token merging (fewer tokens/frame) → Streaming memory + KV eviction (bounded \(B\) tokens regardless of \(N\)). Each stage trades a bit more fidelity for a lot more scalability.

Code Trace
▼
TOKENS_PER_FRAME = 64
CHUNK_FRAMES = 60 # 1 min @ 1 fps
KEEP_RATIO = 0.55 # keyframe selection survival rate
MERGE_TOKENS = 24 # tokens/frame after ToMe merge
MEM_SLOTS = 96 # fixed output size of memory write
BUDGET = 1024 # hard memory-bank cap
memory_bank = [] # grows, then gets re-compressed
prev_kept_embeds = None
for chunk in video_stream(chunk_frames=CHUNK_FRAMES):
# 1. keyframe selection: drop near-duplicate frames
kept = [f for f in chunk if not is_redundant(f, prev_kept_embeds)]
prev_kept_embeds = embed([kept[-1]])
# 2. tokenize + token merging (ToMe bipartite soft matching)
tokens = [vit_encode(f) for f in kept] # c' x TOKENS_PER_FRAME
tokens = [tome_merge(t, target=MERGE_TOKENS) for t in tokens]
chunk_tokens = concat(tokens) # variable length
# 3. memory write: fixed-size cross-attention pooling
mem_k = cross_attention(Q=learned_queries[:MEM_SLOTS],
K=chunk_tokens, V=chunk_tokens) # always MEM_SLOTS
memory_bank.append(mem_k)
# 4. KV eviction: keep sink + recent window, re-pool the middle
if total_tokens(memory_bank) > BUDGET:
memory_bank = evict_and_merge(memory_bank, sink=1, recent=3, budget=BUDGET)
answer = llm_generate(query, context=memory_bank) # attends over <= BUDGET tokens
