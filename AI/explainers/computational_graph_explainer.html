How a framework builds a DAG of operations while computing your output — and caches every intermediate for backprop

1
Understanding the Computational Graph
▼

What is it? When code computes an output, it chains together small operations — add, multiply, matmul, ReLU. The forward pass is running those operations. As it runs, the framework silently records a computational graph: nodes are operations (or input tensors), edges are the tensors flowing between them.

Analogy: An assembly line. Each station (node) takes parts from earlier stations (edges) and performs one operation, then passes its output further down the line. The blueprint of "which station feeds which" is the graph. Running the belt once is the forward pass — and a good factory manager logs what every station produced, because quality control (backprop) will later walk back down the line and inspect exactly those numbers.

💡 If you remember one thing

The forward pass doesn't just compute an output — it builds a DAG of every operation performed and caches every intermediate tensor, because backprop later needs to replay that exact graph in reverse using those cached values.

2
How It Works Internally
▼

Graph Construction, One Op at a Time

Consider q = x + y then f = q * z. In a dynamic ("define-by-run") framework like PyTorch, x + y calls the Add primitive's forward routine, which computes the sum, allocates a new node q, sets q.grad_fn = AddBackward pointing back at (x, y), and marks q as requiring grad. This graph construction happens as ordinary Python executes — one statement, one node.

Caching: the Non-Obvious Part

Mul's backward formula needs both operands (\(\partial(qz)/\partial q = z\), \(\partial(qz)/\partial z = q\)), so its forward call caches q and z right there. This is why the forward pass exists as more than "just compute the number" — every op stashes exactly what its own local derivative will need later.

Topological Order for Free

In a dynamic graph, a node can only be built after its parents' Python statements have returned — program order is already a valid topological order, no explicit sort needed. Static-graph frameworks (graph described declaratively before running) DO need an explicit topological sort (Kahn's algorithm) before execution.

🔑 Key Property

A node is safe to evaluate exactly when all of its parents are done. This is precisely what topological order guarantees — and exactly why the graph must be acyclic: a cycle would leave no valid evaluation order.

3
Why It Works — The Math
▼

Formalizing the Forward Pass

For a node \(v\) with parents \(\operatorname{pa}(v)\) in graph \(G\):

$$x_v = \operatorname{op}_v\big(\{x_u : u \in \operatorname{pa}(v)\}\big), \quad \text{evaluated in any topological order of } G$$

A topological order always exists because \(G\) is a finite DAG: Kahn's algorithm repeatedly removes a node with in-degree 0; if it ever got stuck, every remaining node would have in-degree \(\geq 1\), which forces a cycle — contradicting acyclicity.

Why the Cache Matters

Reverse-mode AD (backprop) accumulates gradients via the chain rule, using cached forward values to evaluate each local Jacobian:

$$\bar{x}_u = \sum_{v\,:\,u \in \operatorname{pa}(v)} \bar{x}_v \cdot J_{v,u}\big(x_u^{\text{cached}}\big)$$

Without the cache, evaluating \(J_{v,u}\) would require recomputing \(x_u\) — and everything upstream of it — all over again.

⚠️ Common Misconception

"The graph IS the network's layers." Not quite — the graph is a trace of primitive tensor ops, far more fine-grained. A single nn.Linear call expands into matmul + add nodes, each cached separately.

Interactive Walkthrough
▼

Step through building & evaluating the graph for \( f(x,y,z) = (x+y)\cdot z \).

📐 Static (define-and-run)

The full graph is described symbolically before any data flows — like TensorFlow 1.x's Session.run(). It's compiled & optimized once (fused ops, memory planning), then executed repeatedly. Needs an explicit topological sort. Data-dependent control flow needs special ops (tf.cond).

⚡ Dynamic (define-by-run)

The graph is built as the code executes — like PyTorch autograd. Every forward call constructs a fresh graph from scratch. Topological order = program order, for free. Native Python if/for just works. JIT tracers (torch.compile) can still fuse it into a fast static graph afterward.

Key Takeaways
▼

Static vs Dynamic, in one line: static graphs are built once, run many times (compile then execute); dynamic graphs are built fresh every forward call as the ops actually run (trace as you go).

When it matters most:

  • Debugging a new architecture → dynamic graphs give real Python stack traces
  • Production throughput on a stable architecture → trace once (torch.compile / tf.function / jax.jit) to get static-graph-level speed
  • Very deep graphs → caching every intermediate costs O(depth) memory; gradient checkpointing trades that cache back for compute
  • Shared nodes (used by two branches) → cached once, but gradients from every consumer are summed during backward
💡 The One Invariant

Forward pass = build the DAG + evaluate it in topological order + cache what backward will need. Everything else (static vs dynamic, checkpointing, fusion) is an engineering trade-off layered on top of that one invariant.

Code Trace
▼
x, y, z = Node(-2.0), Node(5.0), Node(-4.0)
# q = x + y --> builds AddBackward node, edges x->q, y->q
q = x + y
# f = q * z --> builds MulBackward node, CACHES q.value & z.value
f = q * z
order = topological_order(f)
print([n.op or 'leaf' for n in order])
# -> ['leaf', 'leaf', 'leaf', 'add', 'mul']
print('f =', f.value) # f = -12.0
# backward reuses the CACHE -- no recomputation
f.grad = 1.0
for node in reversed(order): node._backward()
print(x.grad, y.grad, z.grad) # -4.0 -4.0 3.0
