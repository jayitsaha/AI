Understanding GPU Cluster Management
▼

What is it? A GPU cluster is a shared pool of machines, each with several GPUs, used by many people at once. Two very different pieces of software make this sharing possible: SLURM, a batch scheduler that decides which user's job gets which whole slice of GPUs and for how long, and Ray, a distributed runtime that runs inside a slice and breaks work into thousands of tiny tasks and long-lived actors spread across many GPUs at once.

Analogy: SLURM is airport ground control — it books runway slots (whole jobs) for airlines (users) so nobody collides, using priority and a clever trick called backfill to squeeze small flights into gaps without delaying anyone important. Ray is the flight crew once you're airborne — hundreds of tiny coordinated tasks (drink service, navigation checks, radio calls) executed in parallel by dozens of crew members (worker processes), sharing a common supply closet (the object store) instead of everyone carrying their own copy of everything.

💡 If you remember one thing

SLURM answers "which user gets which GPUs, for how long" across a multi-tenant cluster; Ray answers "how do I split one allocation into thousands of parallel tasks with microsecond-scale coordination." In production they compose: sbatch reserves the nodes, then Ray starts inside that reservation.

How It Works Internally
▼

SLURM: Controller, Priority Queue, Backfill

slurmctld (the controller) tracks every node's GPUs via generic resources (gres=gpu:N). Pending jobs sit in a priority queue ranked by a multifactor score (age waiting, fair-share history, job size, QoS). The scheduler tries jobs strictly in priority order — but a large, high-priority job that needs 26 free GPUs right now will block every lower-priority job behind it, even if the cluster has plenty of idle capacity for them individually. That wastes GPU-hours.

The fix is the EASY backfill algorithm: SLURM computes a projected start time for the top blocked job (based on when running jobs are expected to finish), then lets any lower-priority job start immediately as long as its own finish time does not push past that reservation. Short, small jobs slip into the gaps for free; the big job's promised start time is never violated.

Ray: Head Node, Raylets, Object Store

Once sbatch grants a node allocation, ray start --head launches the Global Control Store (cluster metadata) and a driver process; every other node runs a raylet — a local scheduler plus a per-node Plasma object store (shared memory). Ray distinguishes tasks (stateless functions, scheduled fresh each call, cheap to move anywhere) from actors (stateful classes pinned to one process/GPU for their whole lifetime — perfect for a loaded model replica). Scheduling is bottom-up: a task is tried on its local raylet first (sub-millisecond); only if no local resource is free does it escalate to the cluster-wide scheduler.

🔑 Key Property

SLURM schedules at the granularity of whole jobs over minutes-to-hours; Ray schedules at the granularity of individual tasks over milliseconds. Neither replaces the other — Ray typically runs inside a SLURM (or Kubernetes) allocation.

Design Decision: Why Per-Node Object Stores, Not One Central Store?

A single centralized store would force every task's inputs and outputs through one network hop, no matter where the task ran. Per-node Plasma stores mean a task reading data already produced on the same node gets a zero-copy shared-memory pointer — no serialization, no network. Only cross-node reads pay the network+copy cost, and Ray's scheduler is locality-aware, so it prefers placing tasks near their data.

Why It Works — The Math
▼

Cluster Utilization

At any time \(t\), let \(R(t)\) be the set of running jobs and \(g_i\) the GPUs held by job \(i\), out of a cluster total \(G\):

$$U(t) = \frac{1}{G}\sum_{i \in R(t)} g_i$$

The Backfill Guarantee

Let \(\tau_{\text{top}}\) be the reserved start time computed for the highest-priority pending job (from the projected completion times of currently running jobs). A lower-priority candidate job \(q\), submitted at time \(t\) with estimated duration \(d_q\), is allowed to backfill only if:

$$t + d_q \le \tau_{\text{top}}$$

Proof sketch that this never delays the top job: by construction, every backfilled job releases its GPUs at or before \(\tau_{\text{top}}\). Since the reservation already accounts for currently running jobs' completions, and backfilled jobs are required to vacate before \(\tau_{\text{top}}\), the set of GPUs reserved for the top job is guaranteed free at \(\tau_{\text{top}}\) regardless of how many small jobs backfilled around it.

Ray Throughput & Zero-Copy Speedup

For \(N\) tasks completed over elapsed wall-clock time \(T\), task throughput is simply \(N/T\). Zero-copy locality gives a latency ratio between a same-node (shared memory) read and a cross-node (network + serialize) read:

$$\text{speedup} = \frac{L_{\text{remote}}}{L_{\text{local}}}$$
⚠️ Common Pitfall

Backfill only helps if job duration estimates (--time in SLURM) are accurate. Users who pad their time limits "just in case" shrink the gaps backfill can exploit, and jobs that underestimate get killed at the limit — both waste GPU-hours. Likewise, over-decomposing Ray work into millions of sub-millisecond tasks adds more scheduling overhead than it saves; the right task grain matters.

Key Takeaways
▼

When to reach for SLURM:

  • Multi-tenant HPC/GPU clusters shared across teams needing fair-share & accounting
  • Whole-node or whole-job batch workloads (training runs measured in hours)
  • Need for hard resource isolation and priority/QoS policy enforcement

When to reach for Ray:

  • Thousands of small, heterogeneous tasks (hyperparameter sweeps, data preprocessing, RL rollouts)
  • Stateful serving actors that must stay warm (loaded model replicas)
  • Need sub-millisecond scheduling latency and zero-copy data sharing between tasks
💡 In Practice

Large-scale LLM training and serving stacks typically run both: sbatch/SLURM reserves the physical GPU allocation across nodes, and a Ray (or similar) runtime starts inside it to orchestrate the fine-grained parallel work. Neither tool alone covers both granularities well.

# Start the Ray head on node 0
srun --nodes=1 --ntasks=1 -w "$HEAD_NODE" \
ray start --head --port=6379 --num-gpus=8 &
sleep 10
# Start Ray workers on the remaining 3 nodes
srun --nodes=3 --ntasks=3 --exclude="$HEAD_NODE" \
ray start --address="$HEAD_NODE:6379" --num-gpus=8 &
