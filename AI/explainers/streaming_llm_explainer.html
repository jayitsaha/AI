Understanding Streaming LLM & Attention Sink
▼

What is it? Large Language Models (LLMs) operate with a fixed-size "context window." To handle conversations or documents longer than this window, "streaming LLMs" use techniques like sliding window attention to discard older tokens as new ones arrive, keeping the active context within limits. The "attention sink" mechanism is an empirical discovery: the first few tokens (e.g., system prompt, initial greeting) are disproportionately important and should *never* be discarded, even if they are old. They act as stable anchor points for attention.

Analogy: Imagine you're writing a long story, but your notepad only has 10 lines. As you write new lines, the oldest one at the top gets erased to make room. This works for a while, but if the first few lines set up the entire plot or character (e.g., "Once upon a time, in a land far away..."), losing them would make the rest of the story incoherent. An "attention sink" is like dedicating the first 2 lines of your notepad to *always* be those crucial opening sentences, no matter how many new lines you write. Only the lines *after* those fixed ones get erased.

💡 If you remember one thing

Attention sink tokens are a small, fixed set of initial tokens (often from the prompt) that are always retained in the KV cache, even when a sliding window mechanism would normally discard them. They provide stable "anchor points" for subsequent tokens to attend to, preventing attention dilution and performance degradation in long-context streaming inference.

How It Works Internally
▼

The KV Cache: Memory for Attention

In a Transformer's self-attention mechanism, each token generates a Query (Q), Key (K), and Value (V) vector. To generate a new token, its Query vector attends to the Key vectors of all preceding tokens to compute attention scores. These scores are then used to weight the Value vectors, producing the context vector for the new token. For efficient generation, the Keys and Values of previously generated tokens are stored in a "KV cache" (also called past_key_values) so they don't need to be recomputed for every new token.

The Problem: Naive Sliding Window Attention

When the sequence length exceeds the maximum context window size (e.g., 4096 tokens), the KV cache becomes too large. A common strategy for "streaming" is to implement a sliding window: as a new token is generated, the oldest token's KV entry is simply discarded to keep the cache size constant. This is simple, but it has a critical flaw: the initial prompt tokens (e.g., "User: Hello! What is the capital of France?") are often the most important for establishing context and persona. When these are discarded, later tokens lose their stable attention targets, leading to reduced coherence and quality, sometimes called "attention dilution" or "context drift."

The Attention Sink Solution

The attention sink mechanism modifies the sliding window strategy. Instead of always dropping the absolutely oldest token, it guarantees that the first \(S\) tokens of the sequence (the "attention sink" tokens) are *never* dropped from the KV cache. When the context window is full and a new token arrives:

  1. Identify the set of tokens currently in the KV cache.
  2. If the number of tokens in cache exceeds the window size, remove the oldest token that is *not* one of the \(S\) attention sink tokens.
  3. Add the new token's KV entries to the cache.

This ensures that the initial context, which often receives high attention from subsequent tokens, remains stable throughout the generation process, even for very long sequences.

🔑 Key Property

The attention sink ensures a persistent, stable set of initial tokens in the KV cache. This prevents the "cold start" problem where new tokens struggle to find strong, stable attention targets as older, crucial context is continually discarded, thereby improving the long-term coherence and quality of streaming LLM generation.

Why It Works — The Math
▼

Standard Self-Attention

For a query vector \(q_i\) of the \(i\)-th token and key vectors \(k_j\) of preceding tokens, the attention scores are computed as:

$$ \text{score}(q_i, k_j) = \frac{q_i k_j^\top}{\sqrt{d_k}} $$

These scores are then normalized using a softmax function to get attention weights \( \alpha_{ij} \). The context vector for token \(i\) is a weighted sum of value vectors \(v_j\):

$$ \text{Attention}(Q, K, V)_i = \sum_{j=1}^i \alpha_{ij} v_j = \sum_{j=1}^i \frac{\exp\left(\frac{q_i k_j^\top}{\sqrt{d_k}}\right)}{\sum_{l=1}^i \exp\left(\frac{q_i k_l^\top}{\sqrt{d_k}}\right)} v_j $$

In streaming inference, the KV cache stores \(K = [k_1, \dots, k_N]\) and \(V = [v_1, \dots, v_N]\) for tokens \(1\) to \(N\).

Impact of Sliding Window on Attention

When a naive sliding window drops the oldest token \(k_1, v_1\), the denominator of the softmax function for subsequent tokens changes. If \(q_i\) (for \(i > 1\)) had a strong attention score with \(k_1\), removing \(k_1\) means its contribution to the sum \( \sum_{l=1}^i \exp\left(\frac{q_i k_l^\top}{\sqrt{d_k}}\right) \) is lost. This forces the attention distribution to re-normalize over the remaining tokens, potentially leading to a significant shift in attention weights for \(q_i\), even if \(q_i\) is far from \(k_1\).

The "attention sink" paper (Xiao et al., 2023) empirically found that the first few tokens \(k_1, \dots, k_S\) consistently receive high attention from later tokens, even very distant ones. This is because these tokens often represent the "root" of the conversation or task instruction. By explicitly retaining these \(S\) tokens, the softmax denominator for any \(q_i\) (where \(i > S\)) always includes these stable, high-attention terms:

$$ \text{Attention}(Q, K_{\text{sink}}, K_{\text{window}}, V_{\text{sink}}, V_{\text{window}})_i = \sum_{j \in \{\text{sink tokens, window tokens}\}} \frac{\exp\left(\frac{q_i k_j^\top}{\sqrt{d_k}}\right)}{\sum_{l \in \{\text{sink tokens, window tokens}\}} \exp\left(\frac{q_i k_l^\top}{\sqrt{d_k}}\right)} v_j $$

This mathematical stability of the softmax denominator, particularly for tokens that consistently draw attention, is key to maintaining performance. It prevents the "attention dilution" that occurs when the most salient context points are arbitrarily removed.

⚠️ Common Pitfall

The attention sink is an empirical fix. It doesn't fundamentally change the quadratic complexity of attention or allow infinite context. It's a heuristic that leverages the observed behavior of LLMs to stabilize streaming inference within a constrained context window. If the crucial context is *not* in the first few tokens (e.g., a long document where the key info is in the middle), the attention sink might not be as effective.

Key Takeaways
▼

When to use Attention Sink:

  • Long-context streaming inference: When generating responses that exceed the LLM's fixed context window (e.g., chatbots, long document summarization, code generation).
  • Maintaining coherence: To prevent "attention dilution" or "context drift" where the model forgets crucial initial instructions or persona set by the prompt.
  • Performance-critical applications: It offers a simple, low-overhead way to improve quality with sliding window attention without complex architectural changes.

When NOT to use / Limitations:

  • Short prompts/contexts: If the total sequence length never approaches or exceeds the context window, the sliding window (and thus attention sink) mechanism is not activated.
  • Models not designed for streaming: While it can be applied to many models, its benefits are most pronounced in scenarios where a sliding window is already necessary.
  • Crucial context in the middle: If the most important information for future tokens is *not* in the initial few tokens, the attention sink may not fully address the problem. Other techniques like Ring Attention or RecurrentGemma might be more suitable.
💡 Big Picture

The attention sink is a practical, empirically-driven optimization that significantly improves the quality and coherence of streaming LLM inference by stabilizing the attention mechanism. It's a testament to how crucial the initial prompt tokens are for guiding an LLM's behavior over extended interactions.

Code Trace (Python/PyTorch-like Pseudocode)
▼
import torch
class StreamingLLM:
def __init__(self, model, max_window_size=8, attention_sink_size=0):
self.model = model
self.max_window_size = max_window_size
self.attention_sink_size = attention_sink_size
self.kv_cache = None # Stores (keys, values) for all past tokens
self.current_sequence_length = 0
def generate_next_token(self, input_ids):
# input_ids: tensor of the current token(s) to process
if self.kv_cache is None:
# First forward pass, initialize cache
outputs = self.model(input_ids, use_cache=True)
self.kv_cache = outputs.past_key_values
self.current_sequence_length = input_ids.shape[-1]
return outputs.logits
# Prepare KV cache for next token generation
past_length = self.current_sequence_length
if past_length >= self.max_window_size:
# Sliding window logic (per attention head/layer)
new_kv_cache = []
for layer_kv in self.kv_cache:
keys, values = layer_kv # (batch, num_heads, seq_len, head_dim)
# Keep sink tokens, then take the most recent (window_size - sink_size) tokens
# If sink_size is 0, this is a naive sliding window
sink_keys = keys[:, :, :self.attention_sink_size, :]
sink_values = values[:, :, :self.attention_sink_size, :]
# Remaining tokens in the window (excluding sink tokens)
non_sink_window_keys = keys[:, :, past_length - (self.max_window_size - self.attention_sink_size):, :]
non_sink_window_values = values[:, :, past_length - (self.max_window_size - self.attention_sink_size):, :]
# Concatenate sink tokens with the sliding window tokens
keys_to_pass = torch.cat([sink_keys, non_sink_window_keys], dim=2)
values_to_pass = torch.cat([sink_values, non_sink_window_values], dim=2)
new_kv_cache.append((keys_to_pass, values_to_pass))
self.kv_cache = new_kv_cache
# Adjust current_sequence_length to reflect the "shifted" window length
self.current_sequence_length = self.max_window_size - input_ids.shape[-1]
# Forward pass with updated cache
outputs = self.model(input_ids, past_key_values=self.kv_cache, use_cache=True)
self.kv_cache = outputs.past_key_values
self.current_sequence_length += input_ids.shape[-1]
return outputs.logits
