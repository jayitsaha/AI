Batch size selection and gradient accumulation — trading gradient noise for throughput
Intermediate Deep Learning Optimization O(1) per step
1
Understanding Mini-Batch Training
▼

What is it? Instead of computing a gradient from the entire dataset (full-batch, slow but exact) or from a single example (pure SGD, fast but wildly noisy), mini-batch training computes the gradient from a small random subset of \(B\) examples at a time. Each mini-batch gradient is a noisy but unbiased estimate of the true full-dataset gradient — you take many cheap, slightly-wrong steps instead of few expensive, exact ones.

Analogy: Imagine polling voters to estimate an election result. Polling all 300 million people gives you the exact answer but takes forever. Polling 1 random person is instant but useless — the answer swings wildly. Polling a random sample of 1,000 people gives you a good estimate, fast, with quantifiable uncertainty that shrinks as you poll more people. Batch size is exactly that sample size.

💡 If you remember one thing

The variance of a mini-batch gradient estimate shrinks as \(1/B\): $$\operatorname{Var}\!\left(\hat{g}_B\right) = \frac{\sigma^2}{B}$$ Doubling the batch size only buys you a \(\sqrt{2}\times\) reduction in gradient noise — that's why batch size has sharply diminishing returns, and why the noise itself (not just averaging it away) is often what makes SGD generalize well.

How Batch Size Selection Works Internally
▼

Two Costs Pulling in Opposite Directions

Every training step costs roughly the same wall-clock time whether \(B=32\) or \(B=256\), because modern accelerators parallelize the forward/backward pass across the batch dimension almost for free — up to a hardware-dependent ceiling. So throughput (examples/sec) roughly scales with \(B\) until you saturate compute or run out of memory. Meanwhile, the statistical quality of each gradient step only improves as \(1/\sqrt{B}\) (standard deviation, not variance). The optimizer needs many noisy-but-cheap steps far more than it needs few precise-but-expensive ones — up to a point.

Small Batches: Noise as Implicit Regularization

With small \(B\) (e.g. 8–64), each step's gradient direction deviates substantially from the true descent direction. This noise acts like an annealing/regularization force: it kicks the parameters out of sharp, narrow minima that fit training data too precisely, and tends to settle in wide, flat basins that generalize better to unseen data. This is the empirical basis for the well-documented large-batch generalization gap — models trained with very large batches often reach lower training loss but worse test accuracy than the same model trained with smaller batches, for the same number of epochs.

Large Batches: Linear LR Scaling + Warmup

If you must use a large batch (for throughput, or because you're doing data-parallel training across many GPUs), the fix from Goyal et al. (2017) is to scale the learning rate linearly with batch size, combined with a brief warmup:

$$\eta(B) = \eta_0 \cdot \frac{B}{B_0}, \qquad \text{ramp } \eta \text{ from } 0 \to \eta(B) \text{ over the first few epochs}$$

The intuition: a bigger batch gives a less noisy but smaller-magnitude-per-example-weighted gradient signal (since you're averaging over more examples), so you can afford a proportionally larger step — but jumping straight to the large LR at initialization destabilizes training, hence the warmup.

Design Decision: Why Not Always Use the Largest Batch That Fits?

Because raw throughput isn't the only objective — final model quality is. Practitioners typically pick the largest batch size that doesn't hurt generalization, tuned jointly with learning rate, rather than the largest batch that fits in memory. This is why batch size is treated as a first-class hyperparameter, not just an engineering knob.

🔑 Key Property

A mini-batch gradient is an unbiased estimator of the full-batch gradient — \(\mathbb{E}[\hat{g}_B] = \nabla \mathcal{L}(\theta)\) — regardless of \(B\). Batch size controls only the variance of that estimate, never its expected direction. This is why SGD converges (in expectation) at any batch size, just with different noise/step-size trade-offs.

3
Why It Works — The Math
▼

Deriving the Noise Scale

Let \(g_i = \nabla_\theta \ell(\theta; x_i)\) be the per-example gradient for example \(i\), with mean \(\nabla\mathcal{L}(\theta)\) and per-coordinate variance \(\sigma^2\) across the dataset. A mini-batch of \(B\) i.i.d. examples gives the estimator:

$$\hat{g}_B = \frac{1}{B}\sum_{i=1}^{B} g_i, \qquad \mathbb{E}[\hat{g}_B] = \nabla\mathcal{L}(\theta)$$

Since the \(g_i\) are independent samples, variances add and scale by \(1/B^2\):

$$\operatorname{Var}(\hat{g}_B) = \operatorname{Var}\!\left(\frac{1}{B}\sum_i g_i\right) = \frac{1}{B^2}\sum_i \operatorname{Var}(g_i) = \frac{\sigma^2}{B}$$

So the standard deviation (noise magnitude) of the gradient estimate falls as \(\sigma/\sqrt{B}\) — a classic Monte-Carlo rate. This is exactly why the curve of "gradient quality" vs. batch size flattens out: going from \(B{=}8\) to \(B{=}32\) (4×) roughly halves the noise, but going from \(B{=}512\) to \(B{=}2048\) (also 4×) buys the identical proportional improvement while costing 4× more compute — diminishing marginal value per FLOP.

Gradient Accumulation: Simulating a Big Batch Without the Memory

If the true desired batch is \(B\) but only a micro-batch of size \(m < B\) fits in accelerator memory, split \(B\) into \(K = B/m\) micro-batches, run forward+backward on each without updating weights, and sum the resulting gradients before taking one optimizer step:

$$\hat{g}_B = \frac{1}{K}\sum_{k=1}^{K} \hat{g}_{m}^{(k)}, \qquad \hat{g}_m^{(k)} = \frac{1}{m}\sum_{i \in \text{micro-batch } k} g_i$$

Because the mean of means over disjoint equal-sized partitions equals the overall mean, this is mathematically identical to computing the gradient over the full batch \(B\) in one shot — same expectation, same variance \(\sigma^2/B\). The only difference is wall-clock time (K sequential passes instead of 1 parallel pass) versus peak memory (only \(m\) examples' activations live at once instead of \(B\)).

⚠️ Common Pitfall

Frameworks accumulate gradients by summation, not averaging, by default (e.g. PyTorch's loss.backward() adds into .grad). If your per-micro-batch loss is already averaged over \(m\) examples, you must divide the accumulated gradient by \(K\) (or divide the loss by \(K\) before each backward call) — otherwise your effective learning rate is silently \(K\times\) too large.

Key Takeaways
▼

How to choose batch size:

  • Small batches (8–64): more regularization from noise, slower wall-clock throughput, needed when memory is tight or you want the generalization benefit
  • Large batches (512+): higher throughput / better hardware utilization, but need linear LR scaling + warmup, and may hit a generalization gap
  • Sweep batch size and LR together — they are coupled hyperparameters, not independent ones

When to use gradient accumulation:

  • You want a large effective batch (for stability, or to match a paper's training recipe) but the model + activations don't fit in memory at that batch size
  • You're fine-tuning a large model on a single GPU and need the statistical behavior of a much bigger batch
  • Not a substitute for data/model parallelism when you need actual wall-clock speedup — accumulation trades time for memory, it does not save time
💡 Effective Batch Size

$$B_{\text{eff}} = m \times K \times N_{\text{devices}}$$ where \(m\) = per-device micro-batch, \(K\) = accumulation steps, \(N_{\text{devices}}\) = number of parallel devices. The gradient noise scale \(\sigma/\sqrt{B_{\text{eff}}}\) depends only on this product — accumulation, data-parallelism, and literally bigger batches are statistically interchangeable ways of assembling the same \(B_{\text{eff}}\).

micro_batch_size = 8
accum_steps = 8 # effective batch = 8 * 8 = 64
optimizer.zero_grad()
for k in range(accum_steps):
x, y = next(micro_batch_loader) # size m = 8
logits = model(x)
loss = loss_fn(logits, y) / accum_steps # pre-divide!
loss.backward() # SUMS into .grad
# activations for this micro-batch freed here —
# peak memory ~ O(m), not O(m * accum_steps)
optimizer.step() # ONE update using the accumulated grad
optimizer.zero_grad()
