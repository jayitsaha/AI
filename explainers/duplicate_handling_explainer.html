Duplicate Handling

Detecting and resolving duplicate records in ML datasets

Intermediate Data Cleaning Classical ML

What Is Duplicate Handling?

Real-world data inevitably contains repeated records. Web scraping harvests the same page twice, form submissions are resubmitted on network error, and database merges combine overlapping sources without deduplication. Two fundamental types exist: exact duplicates are byte-for-byte identical across key fields, while fuzzy duplicates represent the same real-world entity with slight variation — a typo, an abbreviated name, or a different email domain.

ML models trained on duplicates memorize those examples, leading to overfitting and inflated evaluation metrics. The business stakes are real: a customer churn model that counts Alice Smith three times over-weights her behavior; a recommendation engine re-recommends already-purchased items because training duplicates skew item embeddings; a fraud detector trained on duplicated fraud cases learns to over-fire on those specific patterns.

Exact vs Fuzzy Duplicates

Exact duplicates share identical values across all or selected key fields. Detection is simple: compute a hash over the composite key and flag collisions — a classic hash-set approach running in \(O(n)\) time.

Fuzzy duplicates require similarity measures. Jaccard similarity over token sets captures overlap between string representations:

$$J(A,B) = \frac{|A \cap B|}{|A \cup B|}$$

\(J(A,B)\) ranges from 0 (completely disjoint) to 1 (identical). Levenshtein distance counts single-character edits (insert, delete, substitute) between two strings. Fuzzy deduplication is also known as record linkage or entity resolution in the database literature.

Deduplication Strategies

Once duplicates are detected, a resolution strategy must be chosen. Keep-first retains the record with the lowest sort index (stable ordering), discarding subsequent duplicates — good when the earliest record is canonical. Keep-last retains the most recently seen record, useful for event logs where the latest state is authoritative. Aggregate merges numerical fields (sum purchases, mean ratings, concatenate text) to avoid discarding information.

For probabilistic fuzzy matching, the Fellegi-Sunter model assigns each field comparison a match probability \(m\) (probability of agreement given same entity) and non-match probability \(u\) (given different entities). The log-likelihood ratio per field is \(\lambda = \log(m/u)\), and records are linked when the sum of \(\lambda\) values exceeds a threshold.

Leakage and Evaluation Integrity

Duplicates that span the train/test boundary cause data leakage: the model memorizes a training record and achieves a free correct prediction on the test duplicate — inflating accuracy without generalization. If fraction \(f\) of the test set are duplicates of training rows, and the model correctly predicts all of them:

$$\text{Acc}_{\text{inflated}} = \text{Acc}_{\text{true}} \cdot (1-f) + f$$

With \(f = 0.13\) and \(\text{Acc}_{\text{true}} = 0.81\): \(0.81 \times 0.87 + 0.13 = 0.835 \approx 0.84\). A 3-point inflation from contamination alone. The rule is non-negotiable: always deduplicate before splitting into train and test sets.

Naive pairwise similarity is \(O(n^2)\) — infeasible at scale. Blocking partitions records by a cheap key (e.g., first letter of name), then only compares within blocks. Reduces \(\binom{6}{2}=15\) pairs to 4 candidate pairs — a 73% reduction for this small example, and orders of magnitude at scale. Common blocking keys: Soundex codes, first 3 characters, ZIP code prefix, or learned blocking via LSH (Locality-Sensitive Hashing).

After detection, choose a resolution strategy. Keep-First preserves the earliest record; Keep-Last the most recent. Aggregate combines numerical fields. For customer purchase data, aggregation captures total lifetime spend. For event logs, keep-last captures the most recent state. The choice must match business semantics — there is no universally correct answer.
