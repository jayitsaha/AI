1
Understanding Docstrings & Sphinx
▼

What is a docstring? A docstring is a string literal placed at the very start of a Python module, class, function, or method — immediately after the def or class line, enclosed in triple quotes. Python stores it as the object's __doc__ attribute. Running help(fn) displays it in the REPL. There are two dominant formatting conventions: NumPy style (sections delimited by a dashed underline) and Google style (sections marked by an indented colon-header). Both convey the same information — parameter names, types, return values, raised exceptions, and usage examples — just with different visual grammar.

What is Sphinx? Sphinx is the de-facto Python documentation generator. It reads source files, extracts docstrings via its autodoc extension, converts them to HTML (or PDF, ePub) via a theme, and publishes a complete API reference site. It supports two markup languages: reStructuredText (reST) natively, and MyST Markdown via the myst-parser plugin.

Analogy: Imagine every scientist at a research institute fills out a standardised experiment summary card (the docstring) after each experiment. Sphinx is the archivist who collects all those cards, formats them into a beautiful printed journal with a table of contents and index, and ships it to every library worldwide. The scientists chose between two card formats: NumPy format (underlined tables) and Google format (indented lists). The archive looks identical either way.

💡 If you remember one thing

A docstring is the machine-readable contract of a function. Sphinx autodoc + napoleon extract that contract from your source, translate NumPy or Google style to reST, and emit polished HTML. The style choice is source-code-only — both produce identical published output.

2
NumPy vs Google Style — Side by Side
▼

Both styles document the same function standardize(X, axis, ddof). The semantic content is identical — they differ only in how sections are delimited. NumPy style dominates scientific Python (NumPy, SciPy, pandas, scikit-learn). Google style dominates general Python and projects following Google's open-source style guide.

NumPy Style
def standardize(X, axis=0, ddof=1): """Standardize to zero mean, unit variance. Parameters ---------- X : ndarray of shape (n, p) Input data matrix. axis : int, default 0 Axis for statistics. ddof : int, default 1 Delta degrees of freedom. Returns ------- X_std : ndarray Standardized array, same shape as X. Raises ------ ValueError If ddof >= X.shape[axis]. Examples -------- >>> import numpy as np >>> X = np.array([[1,3],[2,4],[3,5]]) >>> standardize(X) array([[-1., -1.], [ 0., 0.], [ 1., 1.]]) """
Google Style
def standardize(X, axis=0, ddof=1): """Standardize to zero mean, unit variance. Args: X (ndarray): Input data matrix of shape (n, p). axis (int): Axis along which to compute statistics. Default 0. ddof (int): Delta degrees of freedom for std. Default 1. Returns: ndarray: Standardized array, same shape as X. Raises: ValueError: If ddof >= X.shape[axis]. Example: >>> X = np.array( ... [[1,3],[2,4],[3,5]]) >>> standardize(X) """

Key Structural Differences

NumPy: Each section header is followed by a line of dashes exactly as long as the header. Parameters are documented one per line as name : type then an indented description. Ideal when type annotations are verbose (e.g., ndarray of shape (n, p, q)) because they live on their own line.

Google: Sections use a single colon-header like Args:. Each parameter is name (type): description on one line, with continuation lines indented. Compact for short signatures but awkward for complex array shape annotations.

Math Inside Docstrings

Both styles support reST inline math. The standardization formula the function implements: \(z_i = \frac{x_i - \bar{x}}{s}\) where \(s = \sqrt{\frac{1}{n - \text{ddof}}\sum_{j}(x_j - \bar{x})^2}\). In a docstring this appears as :math:\`z_i = \\frac{x_i - \\bar{x}}{s}\`. Block math uses a .. math:: directive.

⚠️ Do Not Mix Styles

Sphinx's napoleon extension auto-detects style per docstring. Mixing NumPy and Google conventions in the same project causes ambiguous parses. Enforce consistency with pydocstyle --convention=numpy or ruff --select D in your CI pipeline.

3
How Sphinx Autodoc Works Internally
▼

The 6-Stage Pipeline

Running sphinx-build -b html docs/ docs/_build/html/ executes six stages. The interactive visualization in Card 4 animates each stage. Here is the full internal mechanism:

Stage 1 — Source: Write the docstring

The developer writes a function with PEP 484 type annotations (def foo(x: int) -> float) and a NumPy or Google docstring. The docstring may contain inline reST markup, :math:\`...\` for formulas, and >>> doctest examples that will be auto-verified.

Stage 2 — autodoc: Import & introspect

sphinx.ext.autodoc imports the module at build time using Python's import machinery. It calls inspect.signature(fn) for the parameter list and reads fn.__doc__ for the raw docstring. Directives in your .rst files like .. autofunction:: mymodule.standardize trigger this. Warning: since the module is actually imported, Sphinx build must run in an environment where your package is installed.

Stage 3 — napoleon: Style → reST translation

sphinx.ext.napoleon post-processes the raw docstring before it reaches the reST parser. It detects the style by looking for underlines (NumPy) or colon-headers (Google), then rewrites:

# NumPy section header
Parameters → :param X: Input data matrix …
---------- :type X: ndarray of shape (n, p)
X : ndarray … → :param axis: Axis for statistics.
:type axis: int
# Google section header
Args: → :param X: Input data matrix …
X (ndarray): … → :type X: ndarray

Stage 4 — reST Parser: Build the AST

Sphinx's docutils parser reads the translated reST and builds a typed document tree (AST). Each node is one of: section, paragraph, field_list (parameters), literal_block (code), math (formulas), pending_xref (cross-references not yet resolved). The entire project's AST is built before any output is written, enabling global cross-reference resolution.

Stage 5 — Resolve cross-references

Sphinx collects all pending_xref nodes across all pages and resolves them. A :func:\`numpy.linalg.solve\` reference uses the intersphinx extension: Sphinx downloads NumPy's objects.inv inventory file and finds the URL for that function. Local references like :class:\`MyModel\` are resolved from the project's own object inventory built in Stage 4.

Stage 6 — HTML Builder: Emit output

The HTML builder visits each AST node with the Visitor pattern and writes HTML. Field-list nodes become <dl class="field-list">. Code blocks get syntax highlighted via Pygments. Math nodes emit MathJax or KaTeX scripts. The theme (Furo, Read the Docs, PyData) provides CSS. The builder also writes searchindex.js for client-side search.

🔑 Key Property — One-Way Pipeline

The pipeline is deterministic and one-way: source → HTML. Given the same source and conf.py, Sphinx always produces identical output. This makes docs part of CI: broken cross-references (--nitpicky mode) or failing doctests abort the build exactly like failing tests.

Production Setup: conf.py, Doctest & Intersphinx
▼

Minimal conf.py

# conf.py — Sphinx project configuration
extensions = [
"sphinx.ext.autodoc", # extract docstrings from source
"sphinx.ext.napoleon", # NumPy/Google → reST translation
"sphinx.ext.doctest", # run and verify >>> examples
"sphinx.ext.intersphinx", # cross-project hyperlinks
"sphinx.ext.viewcode", # [source] link per function
]
# napoleon settings
napoleon_google_docstring = True # accept Google style
napoleon_numpy_docstring = True # accept NumPy style
napoleon_use_param = True # emit :param x: fields
napoleon_use_rtype = True # emit :rtype: field
# autodoc settings
autodoc_typehints = "description" # types in body, not sig
autodoc_default_options = {
"members": True, # document all public members
"undoc-members": False, # skip undocumented
"show-inheritance": True, # show base classes
}
# intersphinx: link to external projects
intersphinx_mapping = {
"python": ("https://docs.python.org/3/", None),
"numpy": ("https://numpy.org/doc/stable/", None),
"pandas": ("https://pandas.pydata.org/docs/", None),
}

Doctest — Docs as Living Tests

Every >>> block in a docstring is an executable test. Running sphinx-build -b doctest imports your module and verifies each example matches its expected output. This turns documentation into a lightweight regression suite that catches documentation rot — examples that silently stopped working after a refactor.

def clamp(x: float, lo: float, hi: float) -> float:
"""Clamp x to [lo, hi].
Parameters
----------
x : float Value to clamp.
lo : float Lower bound (inclusive).
hi : float Upper bound (inclusive).
Returns
-------
float
Clamped value; satisfies lo <= result <= hi.
Examples
--------
>>> clamp(5.0, 0.0, 3.0) # above range
3.0
>>> clamp(-1.0, 0.0, 3.0) # below range
0.0
>>> clamp(2.0, 0.0, 3.0) # in range
2.0
"""
return max(lo, min(hi, x))
💡 Doctest Math Verification

For a function implementing \(z = \frac{x - \mu}{\sigma}\), doctest verifies the numerical output. The docstring says it and the test proves it simultaneously. Add >>> import doctest; doctest.testmod() to catch failures without even running Sphinx — works in plain Python too.

6
Key Takeaways & When to Use What
▼

Docstrings are first-class code. Unlike comments, docstrings are accessible at runtime (fn.__doc__), queryable by IDEs, parsed by linters, and tested by doctest. They are the primary API documentation surface for any Python package.

Style choice is project-wide. NumPy style is verbose and readable at a glance — ideal for scientific functions with many array parameters and rich type annotations. Google style is compact — preferred for shorter signatures, monorepo codebases, or teams following Google conventions.

Sphinx makes docs part of CI. A broken cross-reference or a failing doctest can abort the build in --nitpicky mode, treating documentation quality the same as test coverage.

  • Use pydocstyle --convention=numpy or ruff --select D to enforce style in CI
  • Use sphinx-autobuild for live-reload docs during development
  • Host on Read the Docs for automatic builds and versioning on every git push
  • Use intersphinx to hyperlink into NumPy / SciPy / Python docs for free
  • Prefer autodoc_typehints = "description" so PEP 484 annotations appear in the body, not cluttering the signature
