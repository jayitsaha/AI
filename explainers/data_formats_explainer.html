1
Understanding the Formats
▼

Every data pipeline involves a choice of file format. That choice determines how fast you can read, how much disk you use, whether you can query by column without reading everything, and whether different tools can interoperate without copying data.

There are two fundamental storage orientations:

CSV JSON Avro ← Row-oriented
Parquet ORC Arrow/Feather ← Columnar
HDF5 ← Hierarchical array store
Key Insight

Row formats excel at writing entire records (OLTP inserts, streaming events). Columnar formats excel at reading a few columns from millions of rows (analytics, ML feature extraction). Arrow is the in-memory bridge that lets both worlds share data without copying.

One-sentence profiles

  • CSV — Flat text, universal, schema-free, slow, no compression. The "lowest common denominator."
  • JSON — Self-describing, nested-friendly, human-readable, verbose (repeated keys every row).
  • Avro — Row-oriented binary with schema evolution via Avro IDL; default in Kafka.
  • Parquet — Columnar binary, Snappy/ZSTD compression, predicate pushdown; de-facto analytics standard.
  • ORC — Columnar binary optimized for Hive/Hadoop; slightly better compression than Parquet at cost of ecosystem.
  • HDF5 — Hierarchical container for n-dimensional arrays; preferred in science / ML checkpointing.
  • Arrow/Feather — Language-agnostic in-memory columnar standard; zero-copy IPC across Python, Rust, Go, Java.
If You Remember One Thing

Use Parquet for analytics, Arrow for in-process data exchange, Avro for streaming schemas, HDF5 for arrays — and never use CSV for anything larger than a spreadsheet.

2
Row-Oriented vs. Columnar Storage
▼

Row-oriented storage (CSV / JSON / Avro)

In a row store, all fields of record i are written contiguously. A 4-row table with columns [name, age, salary, dept, score, city] occupies disk like this:

Block 0: | Alice | 31 | 95000 | Eng | 88 | NYC |
Block 1: | Bob | 27 | 72000 | Mkt | 74 | LA |
Block 2: | Carol | 34 |110000 | Eng | 92 | SF |
Block 3: | Dave | 29 | 68000 | HR | 61 | CHI |

SELECT salary, score FROM t requires reading all 4 blocks — all 24 fields — to extract 8 values. I/O amplification = 3×. With 100 columns and 2 needed: amplification = 50×.

Columnar storage (Parquet / ORC / Arrow)

A column store writes each column contiguously. The salary and score columns now occupy their own independent byte ranges:

col[name]: Alice Bob Carol Dave
col[age]: 31 27 34 29
col[salary]: 95000 72000 110000 68000 ← read this
col[dept]: Eng Mkt Eng HR
col[score]: 88 74 92 61 ← read this
col[city]: NYC LA SF CHI

SELECT salary, score reads only the green rows above: 8 values, 4 columns never touched. I/O cost = 8/24 = 33% of the row-oriented equivalent.

When Row Wins

Writing a full new record (INSERT) or reading full rows (point lookups by primary key) is cheaper in row stores — you pay one sequential write / one seek. Columnar writes require updating N separate column chunks for every new row. This is why OLTP databases (Postgres, MySQL) are row-oriented and OLAP warehouses (Redshift, BigQuery, DuckDB) are columnar.

Parquet internal structure

Parquet nests three levels of structure:

  • Row Group (128 MB default) — a horizontal partition of rows. Each file has 1–N row groups.
  • Column Chunk — all values for one column within one row group. This is the unit of I/O.
  • Page (1 MB default) — smallest unit within a column chunk; has its own encoding and optional compression.

Each row group stores a footer with per-column statistics (min, max, null count, distinct count). This footer is the secret to predicate pushdown.

$$\text{I/O saved} = 1 - \frac{|\text{columns needed}|}{|\text{total columns}|} \quad \text{(column pruning)}$$

Compression, Encoding & Predicate Pushdown
▼

Columnar encoding schemes

Because a column stores values of a single type, it can exploit data regularity far more aggressively than a row store:

EncodingBest forExampleSavings
DictionaryLow-cardinality stringsdept = {Eng:0, Mkt:1, HR:2} → store [0,1,0,2]8B → 2 bits/value
Run-Length (RLE)Sorted or repeated vals[A,A,A,B,B,A,A] → [(A,3),(B,2),(A,2)]7 → 3 tuples
DeltaMonotone / sequential IDs[1000,1001,1002] → [1000,+1,+1]4B → 1B per subsequent
Bit-packingSmall integersscore ∈ [0,100] → 7 bits (not 32)4B → 0.875B
ZSTD / SnappyPost-encoding bytesGeneral-purpose byte compressionAdditional 2–4×

These encodings are applied per column chunk, selected automatically by the writer. The result: Parquet files are typically 3–10× smaller than the equivalent CSV, often 2× smaller than gzip-CSV.

Predicate pushdown

Given WHERE salary > 100000, a Parquet reader:

  1. Reads the file footer (kilobytes) to get per-row-group statistics for the salary column.
  2. For each row group where max(salary) ≤ 100000, the entire row group is skipped without decompressing.
  3. For surviving row groups, only the salary column chunk is decompressed and scanned.
  4. Only after identifying matching row indices are other columns fetched (projection + predicate combined).
$$\text{pages read} = \left|\{g \in G : \max_g(\text{salary}) > 100000\}\right| \times \frac{|\text{projected cols}|}{|\text{total cols}|}$$

ORC additionally stores bloom filters per stripe enabling IN-predicate pushdown for high-cardinality columns (e.g. WHERE user_id IN (...)) with sub-millisecond false-positive checks.

Splittability

For distributed processing (Spark, Hadoop MapReduce), a format must be splittable: the engine must be able to hand different byte ranges to different workers without decompressing from the start of the file.

FormatSplittable?Mechanism
CSV (raw)Yes (line-seekable)Seek to any byte, scan to next newline
CSV.gzNoGZIP is not seekable
JSON LinesYesEach line is independent JSON object
AvroYes (sync markers)Sync marker every 64 KB allows mid-file splits
ParquetYes (row groups)Row group metadata in footer; each group independent
ORCYes (stripes)Stripes (default 256 MB) are independent
HDF5PartialDataset chunks can be read in parallel; MPI-IO needed
Schema & Typing

CSV has no schema — everything is a string; the reader guesses types (and guesses wrong). JSON carries types within each record (number vs string). Avro ships a JSON schema alongside the binary. Parquet/ORC embed a typed schema (including nested maps/arrays) in the file footer. Arrow carries a typed schema in the IPC metadata. Typed formats catch errors early, enable better compression, and eliminate the "why did pandas read my ID column as float?" class of bugs.

▼

Decision guide

  • Storing ML training data for repeated reading: Parquet. Column pruning + predicate pushdown pays off enormously at scale.
  • Kafka / streaming events with evolving schema: Avro + Schema Registry. Backward/forward compatible schema evolution built-in.
  • Fast in-process data exchange (pandas → DuckDB → polars): Arrow. Zero serialization cost.
  • Scientific simulation arrays, checkpoints: HDF5. Native support for multi-dimensional typed arrays, metadata groups, chunked I/O.
  • One-time export to Excel / stakeholder: CSV. Universal reader support.
  • Hive metastore on HDFS: ORC. Historically better Hive integration; Parquet now equally supported.
Common Mistakes

1. Using CSV.gz in Spark — not splittable, forces single-partition read. Use Parquet.  2. Writing one Parquet file per partition from Spark — creates millions of tiny files; coalesce or use maxRecordsPerFile.  3. Using JSON for columnar analytics — parsing overhead is 10–100× slower than Parquet.  4. HDF5 for columnar analytics — it is an array store, not a query engine; use Parquet + DuckDB instead.

Code: Read / Write in Python
▼

Reading / Writing — Production Python

# ── CSV ──────────────────────────────────────────────────────────────────
import pandas as pd
df = pd.read_csv('data.csv', usecols=['salary','score'], dtype={'salary':int})
df.to_csv('out.csv', index=False)
# ── JSON Lines ────────────────────────────────────────────────────────────
df = pd.read_json('data.jsonl', lines=True) # each line = one JSON object
df.to_json('out.jsonl', orient='records', lines=True)
# ── Parquet (via pyarrow) ─────────────────────────────────────────────────
df = pd.read_parquet('data.parquet', columns=['salary','score']) # column pruning
df.to_parquet('out.parquet', engine='pyarrow', compression='zstd', row_group_size=100_000)
# Predicate pushdown via pyarrow.parquet directly:
import pyarrow.parquet as pq
table = pq.read_table('data.parquet', filters=[('salary', '>', 100_000)],
columns=['name','salary','score'])
# ── ORC ──────────────────────────────────────────────────────────────────
import pyarrow.orc as orc
table = orc.read_table('data.orc') # returns Arrow Table
orc.write_table(table, 'out.orc')
# ── Avro (via fastavro) ───────────────────────────────────────────────────
import fastavro
schema = fastavro.parse_schema({
'type': 'record', 'name': 'Employee',
'fields': [{'name':'name','type':'string'},{'name':'salary','type':'int'}]
})
with open('out.avro','wb') as f:
fastavro.writer(f, schema, records)
with open('data.avro','rb') as f:
records = list(fastavro.reader(f))
# ── HDF5 (h5py) ───────────────────────────────────────────────────────────
import h5py, numpy as np
with h5py.File('data.h5','w') as f:
f.create_dataset('embeddings', data=np.random.randn(100_000, 768),
chunks=(1000, 768), compression='gzip', compression_opts=4)
with h5py.File('data.h5','r') as f:
emb = f['embeddings'][0:1000] # reads only first 1000 rows (chunked)
# ── Arrow / Feather (zero-copy IPC) ──────────────────────────────────────
import pyarrow as pa, pyarrow.feather as feather
table = pa.Table.from_pandas(df) # no copy if df already Arrow-backed
feather.write_feather(table, 'out.feather', compression='lz4')
table2 = feather.read_table('out.feather') # memory-mapped: zero-copy read
# DuckDB can query an Arrow table directly — no serialization at all:
import duckdb
result = duckdb.query("SELECT salary, score FROM table WHERE salary > 100000").df()
Performance Rule of Thumb

For a 1 GB CSV file with 50 columns and a 2-column query:
CSV read: ~12s  |  Parquet (column prune): ~0.4s  |  Parquet + predicate pushdown: <0.1s  |  Arrow in-process: <0.01s
Columnar formats are not just "a bit faster" — they are an order-of-magnitude faster at analytic workloads.
