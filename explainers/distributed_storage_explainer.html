1
Understanding Distributed Storage
▼

What is it? When data grows beyond what a single disk can hold, you spread it across many machines. Distributed storage solves two hard problems: how to keep data safe when machines fail, and how to make reading/writing fast across thousands of nodes.

Analogy: Imagine a library with one copy of every book. If that building burns down, everything is lost. A smarter library makes three photocopies of every book and stores them in three branches across the city. If one branch floods, two branches still have the book. HDFS does exactly this with 128 MB "blocks." Object stores like S3 go further — they're like a postal warehouse where you put a sealed box (object) on a shelf with a unique label (key), and the warehouse invisibly copies it across continents.

💡 If you remember one thing

HDFS gives you a filesystem abstraction (files, directories, blocks, rack-aware replication) best for MapReduce-era batch jobs. S3/GCS give you a flat key-value store (bucket + key) over HTTPS with near-infinite scale and 11-nines durability. The modern data lakehouse stores data in object storage and computes on separate clusters — storage and compute decouple.

Two paradigms at a glance

HDFS (Hadoop Distributed File System) — born at Yahoo! in 2006, ported from Google's GFS paper. Gives you a POSIX-like tree namespace. A master node (NameNode) holds all metadata in memory; data lives in 128 MB blocks spread across DataNodes, each block replicated ×3 for fault tolerance. Ideal for sequential scans of huge files.

S3 / GCS (object stores) — flat namespace of bucket/key pairs. No directories (prefixes simulate them). HTTP PUT/GET interface. Internally striped across dozens of independently failing storage shards with Reed–Solomon erasure coding, achieving 11-nines (99.999999999%) annual durability. Cost is \(\approx\$0.023/\text{GB·month}\) — ~10× cheaper than NFS or HDFS-equivalent on-prem storage.

2
HDFS: Block Replication & Rack Awareness
▼

NameNode — the single metadata server

The NameNode holds the entire filesystem namespace in RAM: an inode tree mapping every file path to a sequence of block IDs, and a block map from each block ID to the DataNodes that hold its replicas. For a cluster with 100 million files, this is \(\approx\)200 GB of heap — which is why large clusters deploy a Standby NameNode for HA. The NameNode never touches actual data bytes; it only answers metadata queries and directs clients to DataNodes.

DataNodes — where bytes live

Each DataNode stores blocks as flat files in its local filesystem. Every 3 seconds, DataNodes send a heartbeat to the NameNode. Every 6 hours they send a full block report. If the NameNode doesn't hear from a DataNode for 10 minutes, it declares it dead and triggers re-replication of all blocks that now have fewer than 3 replicas.

Block size and the write pipeline

Default block size: 128 MB (configurable up to 512 MB). A 1 GB file becomes 8 blocks. When a client writes, it sets up a write pipeline: bytes flow Client → DN₁ → DN₂ → DN₃ in a chain; acknowledgments flow back in reverse. This maximises network bandwidth — data traverses each link only once rather than three times.

$$\text{Write bandwidth} = \min(B_{\text{client} \to \text{DN}_1},\; B_{\text{DN}_1 \to \text{DN}_2},\; B_{\text{DN}_2 \to \text{DN}_3})$$

The pipeline degrades gracefully: if DN₂ fails mid-write, the client automatically opens a new pipeline to a replacement DataNode for the remaining packets.

Rack awareness — why it matters for fault tolerance

HDFS knows your physical topology. For a replication factor \(r = 3\), the default placement policy is: replica 1 on the same node as the writer (or a random local node), replica 2 on a different rack, replica 3 on the same rack as replica 2 but a different node. This ensures:

  • Survival of a complete rack failure (at least 1 replica on a different rack)
  • Efficient writes (2 replicas in-rack = one inter-rack hop)
  • Local reads when a replica is on the same node as the reader
🔑 Rack-Aware Placement Rule

With \(r = 3\): place replicas on 2 racks (not 3), distributing as 1 + 2. This balances write cost (fewer cross-rack hops) against fault tolerance (survives a full rack outage).

Numerical trace: 1 GB file write

File = 1,073,741,824 bytes. Block size = 134,217,728 bytes (128 MiB). Blocks = 8. Replication = 3. Total bytes written across network ≈ 8 × 128 MiB × 3 = 3,072 MiB. At 1 Gbps inter-rack bandwidth: \(3072 \times 8 / 1000 \approx 24.6\) seconds end-to-end pipeline time (pipeline overlap reduces this in practice to ~10–15 s).

⚠️ NameNode SPOF

Classic HDFS has a single NameNode. If it fails, the cluster is unavailable even though all data is safe on DataNodes. HDFS HA (Hadoop 2.x+) fixes this with a Standby NameNode + shared edit log via ZooKeeper quorum journals. Always deploy in HA mode in production.

Object Stores: S3 / GCS Architecture
▼

Flat namespace: bucket + key

Object stores abandon the filesystem tree. Every object is identified by s3://bucket-name/path/to/key. Internally this is a flat key–value map. The "directory" illusion is a client-side convention: list objects with prefix data/2024/ and you get back all keys sharing that prefix. There is no inode, no rename-is-atomic guarantee, and no true append (you must re-upload the whole object or use multipart).

Multipart upload and internal sharding

For objects >5 MB, S3 recommends multipart upload. The client splits the object into parts (minimum 5 MB each, up to 10,000 parts, maximum object size 5 TB). Each part is uploaded independently, often in parallel. S3 assembles them server-side with a single CompleteMultipartUpload call. Internally, S3 strips the object across many storage nodes using Reed–Solomon erasure coding — far more storage-efficient than 3× replication:

$$\text{RS}(k, m): \text{ split object into } k \text{ data shards, generate } m \text{ parity shards}$$
$$\text{Storage overhead} = \frac{k + m}{k} \quad \text{e.g., RS}(10, 4) \Rightarrow 1.4\times \text{ vs HDFS's } 3\times$$

Consistency model evolution

Original S3 (pre-2020) had eventual consistency for overwrite PUTs and DELETEs — a PUT followed immediately by a GET could return the old version. In December 2020, AWS upgraded S3 to strong read-after-write consistency: a successful PUT guarantees that any subsequent GET from any region returns the new data. GCS has always offered strong consistency for object reads/writes within a bucket.

💡 Consistency guarantee (post-2020)

S3 now guarantees: write → read sees new object; delete → list does not show object; list → read is consistent. The exception: S3 versioning and bucket-level policies still have eventual propagation delays.

GCS vs S3: key differences

GCS (Google Cloud Storage) uses Google's Colossus filesystem under the hood. Notable differences: GCS supports object compositions (server-side concatenation without re-upload), uniform bucket-level access tying permissions to IAM uniformly, and turbo replication (guaranteed cross-region replication within 15 minutes). GCS billing model charges per operation (Class A/B), while S3 charges per request type. Both achieve 11-nines durability through geographic replication and erasure coding.

📐 Durability: 11-nines

11-nines = \(1 - 10^{-11}\) annual durability. If you store 10 million objects, expected loss per century ≈ 0.001 objects. This is achieved by storing data in at least 3 geographically separated availability zones with RS erasure coding, continuous background integrity checks (bit-rot detection via checksums), and automatic healing.

Durability Math & Consistency Models
▼

Replication durability

Let \(p_f\) be the probability a single storage node fails independently in a year. HDFS blocks replicated across \(r\) nodes: a block is lost only if all \(r\) replicas are simultaneously unavailable:

$$P(\text{block lost}) = p_f^r$$

With 4-nines availability (\(p_f = 10^{-4}\)) and \(r = 3\): \(P = 10^{-12}\) — 1 block lost per trillion block-years. In a cluster of 10 billion blocks, expect ~0.01 block losses per year (ignoring correlated failures like rack-level power outage, which rack awareness mitigates).

Erasure coding overhead

Reed–Solomon RS\((k, m)\) encodes \(k\) data shards into \(k + m\) shards such that any \(k\) of the \(k+m\) shards suffice to reconstruct the data. Storage overhead:

$$\text{overhead} = \frac{k + m}{k} \quad \Rightarrow \quad \text{RS}(10,4) = 1.4\times, \quad \text{Replication-3} = 3\times$$

Object stores use RS(10,4) or RS(6,3) internally. This gives 10–17% overhead vs. 3× replication's 200% overhead — a major cost advantage at cloud scale.

CAP theorem positioning

HDFS is CP: strong consistency (single authoritative NameNode), but sacrifices Availability during NameNode failover. S3/GCS are AP: available and partition-tolerant, trading away strict consistency (though both now offer strong read-after-write). The CAP tradeoff is resolved differently based on use-case: ML training jobs favor availability (partial reads OK), financial ledgers favor consistency.

Write amplification and throughput

HDFS pipeline write amplification = \(r = 3\) (3× bytes on the network). S3 multipart: each part is uploaded once, assembled once. Net amplification ≈ 1× for data bytes, plus erasure coding overhead at the storage layer. For sequential scan throughput, HDFS achieves \(\approx 1\text{ GB/s}\) per DataNode with direct streaming; S3 achieves \(\approx 100\text{ MB/s}\) per GET request but scales horizontally to \(\sim\)tens of GB/s aggregate with parallel prefix requests.

⚠️ Correlated failure — the hidden risk

The durability formula \(p_f^r\) assumes independent failures. A rack-level power cut kills all replicas on the same rack simultaneously — correlated, not independent. Rack awareness places at most 2 of 3 replicas on the same rack; a full rack failure reduces \(r_{\text{effective}}\) from 3 to 1 momentarily, dramatically increasing risk until HDFS re-replicates (\(\approx\) minutes). Object stores mitigate this via geographic zones.

The Lakehouse: Why Object Storage Won
▼

The compute-storage coupling problem

HDFS tightly couples storage and compute: you run MapReduce on the DataNodes because moving data is expensive. Scaling storage meant scaling compute (and vice-versa) even if you only needed one. At petabyte scale this is deeply wasteful — a 100-node HDFS cluster buying 100 CPU servers just to add disk.

Why object storage decouples them

Object stores expose a simple HTTP GET — any compute cluster anywhere can read from S3 at the same cost. This enables ephemeral compute: spin up 500 Spark workers for 2 hours, process data from S3, discard the workers. Pay $80 in compute instead of running a permanent 100-node HDFS cluster at $10,000/month. This is why Databricks (Delta Lake), Apache Iceberg, and Apache Hudi all use object storage as the canonical storage layer.

🔑 The Lakehouse Pattern

Store data in object storage (Parquet/ORC files in S3/GCS) + metadata layer (Delta Log / Iceberg catalog) = lakehouse. You get the cheap scalable storage of a data lake plus ACID transactions, schema evolution, and time-travel of a data warehouse — without coupling storage to compute.

When HDFS still wins

HDFS remains relevant for: (1) ultra-low-latency streaming pipelines where S3's 100–200 ms first-byte latency is unacceptable; (2) on-premises deployments without cloud access; (3) HBase, where HDFS provides the random-write append log (HLog) that object stores can't efficiently replicate; (4) legacy Hadoop ecosystems too costly to migrate.
