Eliminating nondeterminism so ML experiments can be repeated, compared, and trusted

1
Understanding Reproducibility
▼

What is it? Reproducibility means running the same training code twice produces bitwise identical results — same loss curve, same weights, same predictions. Without it, you cannot tell if a performance improvement came from your change or from random luck.

Analogy: Imagine a kitchen recipe where the chef adds "a pinch of salt" each time — but the pinch is different every time. Two chefs following the same recipe produce different dishes. Reproducibility is like replacing "a pinch" with "3.2 g on a calibrated scale" — and sealing the kitchen so the temperature is identical too.

💡 If you remember one thing

There are four independent axes of nondeterminism in a typical PyTorch training run: (1) Python/NumPy/Torch RNG seeds, (2) GPU atomic operations and cuDNN algorithm selection, (3) DataLoader worker ordering and hash randomization, (4) environment drift — different library versions on different machines. Each must be addressed independently.

Why it matters for ML: A model with validation accuracy 87.3% on run A and 87.9% on run B may be the same model — the difference is noise, not signal. Papers are retracted and promotions are undeserved because teams never verified their results were signal, not seed.

2
Sources of Nondeterminism — Deep Dive
▼

Source 1: Unseeded Python / NumPy / Torch RNGs

Python, NumPy, and PyTorch each maintain an independent pseudo-random number generator (PRNG) state. A PRNG is a deterministic function \(f: s \mapsto (v, s')\) — given the same seed \(s_0\), it always produces the same sequence \(v_1, v_2, \ldots\). Without seeding, the OS supplies a random \(s_0\) (typically from /dev/urandom), so every run gets a different state trajectory.

Weight initialization (Kaiming, Xavier), dropout masks, data augmentation (random crops/flips), and mini-batch shuffling all consume from these RNGs. Miss seeding even one of the three, and results diverge.

$$s_0 \xrightarrow{\text{set\_seed}} \text{PRNG}_\text{Python},\; \text{PRNG}_\text{NumPy},\; \text{PRNG}_\text{Torch},\; \text{PRNG}_\text{CUDA}$$

Source 2: GPU Atomic Operations & cuDNN Non-Determinism

CUDA kernels that use floating-point reductions (scatter-add, group convolutions, softmax across large tensors) execute threads in non-deterministic order on the GPU. Floating-point addition is not associative: \((a + b) + c \neq a + (b + c)\) in IEEE 754 due to rounding. Thread scheduling varies between runs, so the summation order differs, producing different round-off at each step.

cuDNN further selects convolution algorithms dynamically via benchmarking (torch.backends.cudnn.benchmark = True). The chosen algorithm may differ between runs if timing varies, giving different numerics even with the same seed.

⚠️ GPU Atomics Are the Hardest Source to Fix

torch.use_deterministic_algorithms(True) forces PyTorch to use deterministic (but slower) fallback kernels for all ops that have known non-deterministic implementations. Some operations (e.g., certain sparse/indexing ops) will raise a RuntimeError rather than silently produce non-deterministic results — this is intentional.

Source 3: DataLoader Workers & Hash Randomization

When num_workers > 0, each worker process is forked and gets an independent PRNG state seeded from the worker ID — not from your global seed. The order in which workers finish and enqueue batches is non-deterministic (OS scheduling). Fix: provide a worker_init_fn that seeds each worker, and set generator=torch.Generator().manual_seed(seed) on the DataLoader.

Python's hash randomization (PYTHONHASHSEED, enabled by default since Python 3.3) randomizes the iteration order of sets and dicts. Code that iterates over a dict.keys() or builds a layer from a set will produce different orderings across processes.

Source 4: Environment Drift

Two runs on different machines — or the same machine months apart — may use different PyTorch, CUDA, cuDNN, or numpy versions. Numerical kernels are updated between versions, so results differ even with identical seeds. The fix is environment pinning: lock every dependency to an exact version and distribute via a container (Docker) or lock file (requirements.txt with hashes, conda-lock).

3
The Fix Stack — Making Experiments Reproducible
▼

Fix 1: Seed All RNGs

Call a single seed_everything(seed) helper at the top of every training script, before any model, dataset, or optimizer is created. You must seed all four generators: Python's random, NumPy, PyTorch CPU, and PyTorch CUDA.

Fix 2: Disable cuDNN Benchmark, Enable Deterministic Mode

Set torch.backends.cudnn.deterministic = True and torch.backends.cudnn.benchmark = False. This prevents cuDNN from timing and selecting different conv algorithms across runs. Then call torch.use_deterministic_algorithms(True) to make PyTorch error on any non-deterministic op rather than silently proceeding.

The performance cost is real — deterministic ops can be 5–30% slower on GPU. A common practice: train with non-deterministic mode for speed, but verify final results with deterministic mode before reporting.

Fix 3: Deterministic DataLoader

Pass a seeded generator and a worker_init_fn. Also set PYTHONHASHSEED in the environment before launching the script:

Key Pattern

PYTHONHASHSEED=42 python train.py

Fix 4: Pin the Environment

  • pip: pip freeze > requirements.txt then ship it. Add --require-hashes for cryptographic pinning.
  • conda: conda-lock generates a per-platform lock file that pins every transitive dependency.
  • Docker: use a pinned base image (pytorch/pytorch:2.2.0-cuda12.1-cudnn8-devel) and install from the lock file in the Dockerfile. The image digest is the ultimate pin.
🔑 The Reproducibility Hierarchy

Seed-only → same machine, same code, deterministic results within run. + Deterministic algorithms → bitwise identical even across restarts. + Environment pin → reproduces across machines and time. + Docker/OCI image → the gold standard: anyone, anywhere, any time.

Key Takeaways & Trade-off Guide
▼

When full reproducibility is non-negotiable:

  • Research paper results that must be independently verified
  • Regulated ML (healthcare, finance) where audit trails are required
  • Debugging: bisecting a training run to find where results diverged
  • Ablation studies where you are measuring small differences (<0.5% accuracy)

When partial reproducibility is acceptable:

  • Production training where only the final checkpoint matters, not intermediate steps
  • Large-scale distributed training where deterministic ops are prohibitively slow
  • Teams that report mean ± std over multiple seeds rather than a single run

💡 Practical Recommendation

Always seed for reproducibility within a run. Gate your CI/CD on a reproduce_check job that runs the same 100-step training loop twice with the same seed and asserts bitwise-identical loss values. This catches new nondeterministic ops introduced by dependency upgrades before they reach production.

Code Reference — Seed Everything Template
▼
import os, random
import numpy as np
import torch
def seed_everything(seed: int = 42) -> None:
# 1. Python built-in random
random.seed(seed)
# 2. Python hash randomization (must also set env var before launch)
os.environ["PYTHONHASHSEED"] = str(seed)
# 3. NumPy
np.random.seed(seed)
# 4. PyTorch CPU
torch.manual_seed(seed)
# 5. PyTorch GPU (all devices)
torch.cuda.manual_seed_all(seed)
# 6. cuDNN: disable benchmarking, enable deterministic mode
torch.backends.cudnn.deterministic = True
torch.backends.cudnn.benchmark = False
# 7. Deterministic algorithms (raises on non-det ops)
torch.use_deterministic_algorithms(True, warn_only=False)
# 8. CUBLAS deterministic (needed for torch >= 1.8 on some ops)
os.environ["CUBLAS_WORKSPACE_CONFIG"] = ":4096:8"
def make_deterministic_loader(dataset, seed, **kwargs):
"""DataLoader with deterministic worker seeding."""
def worker_init(worker_id):
worker_seed = seed + worker_id
np.random.seed(worker_seed)
random.seed(worker_seed)
g = torch.Generator()
g.manual_seed(seed)
return torch.utils.data.DataLoader(
dataset, generator=g,
worker_init_fn=worker_init, **kwargs
)
