Gradient Accumulation

Simulating large-batch training on small-memory GPUs
Intermediate Deep Learning Training / MLOps O(1) extra memory
1
Understanding Gradient Accumulation
▼

What is it? You want to train with a big batch of, say, 512 examples because large batches give smoother, more reliable gradient estimates. But your GPU only has enough memory to hold 128 examples at once. Gradient accumulation lets you fake the big batch: run 4 smaller "micro-batches" of 128 through the model, add up their gradients instead of immediately updating the weights, and only update the weights once, after all 4 have been processed.

Analogy: Imagine you need to lift a 400 lb barbell but can only carry 100 lb at a time. You can't magically hold 400 lb at once — but you can make four trips, stacking 100 lb plates onto a cart each time, and only push the fully-loaded cart once. The end result (400 lb moved, once) is the same as if you'd carried it all in one go — you just paid with more trips (time) instead of more strength (memory).

💡 If you remember one thing

Gradient accumulation trades compute time for memory: instead of one optimizer step per large batch, you take K forward/backward passes on small micro-batches, sum their gradients, and take one optimizer step — mathematically equivalent to having processed the full batch at once.

How It Works Internally
▼

The Normal Training Step

Ordinarily, one optimizer step looks like: zero_grad() → forward(batch) → loss.backward() → optimizer.step(). The backward() call computes gradients and writes them into each parameter's .grad buffer.

The Accumulation Trick

PyTorch's .backward() doesn't overwrite .grad — it adds to whatever is already there. Gradient accumulation exploits this directly: call zero_grad() once, then loop over K micro-batches calling forward() and backward() for each without calling optimizer.step() or zero_grad() in between. Each backward() adds its micro-batch gradient onto the running total. Only after the K-th micro-batch do you call optimizer.step(), then finally zero_grad() to reset the buffer for the next effective batch.

Loss Normalization by K

There's a subtlety: if each micro-batch loss is the mean over its own m samples, summing K of those means overcounts by a factor of K relative to the mean over all N = K·m samples. The fix is to divide each micro-batch's loss by K before calling backward(), so the accumulated gradient buffer ends up numerically identical to running one giant batch of size N through the model in a single shot.

Design Decision: Why Not Just Use a Smaller Batch?

You could just train with batch size 128 and skip the trick — but small batches produce noisier gradient estimates, may interact poorly with learning-rate schedules tuned for large batches, and some architectures (very large transformers) need large effective batch sizes for training stability. Accumulation reproduces the large-batch gradient signal exactly, without the large-batch memory cost.

🔑 Key Property

Gradient accumulation changes how many forward/backward passes happen per optimizer step — it does not change the model, the loss function, or (in exact arithmetic) the resulting gradient. Wall-clock time per effective batch goes up roughly linearly with K; peak memory stays flat at the micro-batch size.

Why It Works — The Math
▼

Full-Batch Gradient

For a batch of \(N\) samples, the mean loss and its gradient with respect to parameters \(\theta\) are:

$$\mathcal{L}_N(\theta) = \frac{1}{N}\sum_{i=1}^{N} \ell(f_\theta(x_i), y_i), \qquad g_N = \nabla_\theta \mathcal{L}_N(\theta) = \frac{1}{N}\sum_{i=1}^{N}\nabla_\theta \ell_i$$

Splitting Into K Micro-Batches

Split the \(N\) samples into \(K\) micro-batches of size \(m\), so \(N = Km\). Micro-batch \(k\) has its own mean loss \(\mathcal{L}_k = \frac{1}{m}\sum_{i \in B_k}\ell_i\). If we scale each micro-batch loss by \(1/K\) before calling backward(), the gradients that accumulate are:

$$g_{\text{accum}} = \sum_{k=1}^{K} \nabla_\theta\!\left(\frac{\mathcal{L}_k}{K}\right) = \sum_{k=1}^{K}\frac{1}{K}\cdot\frac{1}{m}\sum_{i\in B_k}\nabla_\theta \ell_i = \frac{1}{Km}\sum_{i=1}^{N}\nabla_\theta \ell_i = \frac{1}{N}\sum_{i=1}^{N}\nabla_\theta \ell_i = g_N$$

The accumulated gradient is exactly the full-batch gradient. One optimizer step on \(g_{\text{accum}}\) is identical (in exact arithmetic) to one optimizer step on \(g_N\) computed from a single giant batch.

Learning-Rate Scaling

Because \(g_{\text{accum}} = g_N\), the step itself needs no rescaling to match a big-batch step. But if your goal is to change the effective batch size \(B_{\text{eff}} = Km\) relative to some baseline, the well-known linear-scaling heuristic still applies: when \(B_{\text{eff}}\) grows by a factor \(c\), scale the learning rate by roughly \(c\) too (with warmup), since fewer, larger, less-noisy steps are taken per epoch.

$$\eta_{\text{new}} \approx \eta_{\text{base}} \cdot \frac{B_{\text{eff}}}{B_{\text{base}}}$$
⚠️ Common Pitfall — BatchNorm

BatchNorm computes its mean/variance statistics from whatever batch is physically in memory — the micro-batch of size \(m\), not the effective batch of size \(N\). Gradient accumulation fixes the gradient to match a big batch, but the normalization statistics are still computed on tiny \(m\)-sized slices, which can be noisy and biased if \(m\) is small. Fixes: use GroupNorm/LayerNorm instead, synchronize/accumulate BN running stats manually, or accept the mismatch when \(m\) is reasonably large (e.g. \(m \ge 32\)).

Key Takeaways
▼

When to use gradient accumulation:

  • Your desired batch size doesn't fit in GPU/TPU memory at once
  • You need large effective batches for training stability (e.g. large transformer pretraining, contrastive losses that benefit from more negatives)
  • You want to match a paper's reported batch size on cheaper hardware

When NOT to rely on it blindly:

  • Model uses BatchNorm with a small micro-batch — statistics won't match a true large-batch run
  • Wall-clock time matters more than batch size — accumulation adds no parallelism, only more sequential compute
  • You forgot to divide the loss by K — this silently inflates the effective learning rate by a factor of K
💡 Rule of Thumb

Effective batch size \(B_{\text{eff}} = K \times \text{micro\_batch\_size}\). Peak memory is governed only by micro_batch_size, never by \(K\). Accumulation is "free" extra batch size paid for entirely in extra time, not extra memory.

Code Trace
▼
K = 3 # micro-batches per effective batch
micro_bs = 4 # samples per micro-batch (fits in memory)
optimizer.zero_grad() # clear grad buffer ONCE per effective batch
for k in range(K):
micro_batch = next(loader) # m samples only
pred = model(micro_batch.x) # forward pass
loss = loss_fn(pred, micro_batch.y) # mean over m samples
loss = loss / K # normalize so sum == full-batch mean
loss.backward() # ADDS grad onto .grad buffer
# NOTE: no optimizer.step(), no zero_grad() inside this loop!
optimizer.step() # ONE update, using the accumulated gradient
optimizer.zero_grad() # reset buffer for the next effective batch
