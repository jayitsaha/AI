Data types, control flow, functions, classes, decorators, generators & iterators — from first principles

The 30-Second Version
▼

What is this? Python's core language is a small set of building blocks — ways to store data (types), make decisions (control flow), package logic (functions), blueprint objects (classes), and extend behavior non-invasively (decorators, generators, iterators). Every Python program is assembled from these pieces.

Real-world analogy: Think of Python like a kitchen. Data types are your ingredients (int = number, str = text, list = shopping bag, dict = labeled jars). Control flow is the recipe steps ("if the onion is brown, add garlic"). Functions are reusable sub-recipes you name and call anytime. Classes are templates for kitchen equipment — a "BlenderClass" produces blender objects each with their own speed. Decorators are labels you paste on the recipe card: "@ time it" or "@ log every call." Generators are like a slow-drip coffee machine — they produce one drop at a time, on demand, instead of filling the entire jug at once.

💡 If you remember one thing

Python's generators and iterators implement lazy evaluation: a yield suspends execution, saves all local state, and hands back control. When next() is called again, execution resumes exactly where it left off — enabling infinite sequences with \(O(1)\) memory.

Why These Features Exist — Historical Context
▼

The Problem — ABC & Modula's Rigidity

Guido van Rossum designed Python (released 1991) as a reaction to ABC — a teaching language that was safe but not extensible. ABC had no modules, no exceptions, no first-class functions. C was powerful but required manual memory management. Python aimed for the sweet spot: readable enough to teach, expressive enough for production.

Why Generators Were Invented (PEP 255, 2001)

Before generators, producing a lazy sequence required writing a full iterator class with __iter__ and __next__ methods — verbose boilerplate. PEP 255 introduced yield: a function that yields becomes a generator function. Its frame is suspended mid-execution and resumed on each next() call. This made producer-consumer pipelines trivial to write.

Decorators (PEP 318, 2004)

Before @decorator syntax, wrapping a function required: func = logged(func) — error-prone (easy to forget) and visually disconnected from the function definition. PEP 318 introduced the @ syntax so the transformation sits right above the function — declarative and impossible to miss.

🔑 Evolution Timeline

Python 1.0 (1994): core types, classes, exceptions → Python 2.2 (2001): generators (PEP 255), new-style classes → Python 2.4 (2004): decorators (PEP 318) → Python 2.5 (2006): send() on generators, coroutines → Python 3.3 (2012): yield from for generator delegation → Python 3.5 (2015): async/await (built on generator protocol).

Key insight: async/await in Python 3.5+ is not a separate mechanism — it is literally the iterator protocol extended. An async def function is a coroutine, and asyncio's event loop calls .__next__() / .send() on it just like a generator. Understanding generators is understanding async Python.

Core Concepts & Theory
▼

Data Types — Everything is an Object

In Python, every value is an object with an identity (id()), a type (type()), and a value. The built-in types are: int, float, complex, bool, str, bytes, list, tuple, set, frozenset, dict, NoneType. Key distinction: mutable (list, dict, set) vs immutable (int, str, tuple, frozenset). Immutable objects can be interned/cached; mutable cannot safely be dictionary keys.

Control Flow — Truthiness & Short-Circuit

Python's control flow uses truthiness not boolean coercion: any object evaluates to True or False in a boolean context. Falsy values: 0, 0.0, "", [], {}, None, False. The and/or operators short-circuit AND return the actual object, not True/False: x = x or default is idiomatic Python.

Functions — First-Class Citizens

Functions are objects. They can be passed as arguments, returned from functions, stored in data structures, and have attributes (func.__name__, func.__doc__, func.__defaults__). Closures capture variables from the enclosing scope by reference (not by value) — a common source of bugs in loops.

The Iterator Protocol

An iterable is any object implementing __iter__(), which returns an iterator. An iterator implements both __iter__() (returns self) and __next__() (returns next value or raises StopIteration). The for x in obj loop calls iter(obj), then repeatedly calls next() until StopIteration.

$$\text{for } x \text{ in } obj \;\equiv\; it = \text{iter}(obj);\; \text{while True: try:} \; x = \text{next}(it) \text{ except StopIteration: break}$$

Generator Protocol

A generator function contains yield. Calling it returns a generator object (which IS an iterator). The frame is not executed until next() is called. On each next(): execution resumes from the previous yield, runs until the next yield, suspends again, and returns the yielded value. When the function body exits, StopIteration is raised automatically.

The Decorator Pattern

A decorator is a callable that takes a function and returns a replacement function. The @decorator syntax is syntactic sugar:

@logged
def add(a, b): return a + b
# exactly equivalent to:
def add(a, b): return a + b
add = logged(add)

Class & MRO

Classes are objects of type type (a metaclass). Attribute lookup follows the Method Resolution Order (MRO), computed by the C3 linearization algorithm: Python searches the class, then parent classes left-to-right, depth-first but linearized to avoid duplicate visits. super() moves to the next class in the MRO — not necessarily the direct parent.

⚠️ Common Pitfalls

Mutable default arguments: def f(x=[]): creates the list ONCE at definition time, shared across all calls. Use None as sentinel. Late-binding closures: funcs = [lambda: i for i in range(3)] — all lambdas see the final value of i (=2). Generator exhaustion: a generator can only be iterated once. After StopIteration, subsequent calls also raise StopIteration.

From Scratch: The Iterator Protocol

class CountUp:
    """A reusable iterable that counts from start to stop."""
    def __init__(self, start, stop):
        self.start = start; self.stop = stop

    def __iter__(self):
        # Returns a fresh iterator each time — CountUpIter holds state
        return CountUpIter(self.start, self.stop)

class CountUpIter:
    def __init__(self, current, stop):
        self.current = current; self.stop = stop

    def __iter__(self): return self  # iterators return themselves

    def __next__(self):
        if self.current >= self.stop:
            raise StopIteration  # signal exhaustion
        val = self.current
        self.current += 1
        return val

# Usage — both work identically:
for n in CountUp(1, 4): print(n)  # 1 2 3

Generator equivalent (5 lines vs 20):

def count_up(start, stop):
    while start < stop:
        yield start   # suspend here, return start to caller
        start += 1    # resume here on next() call

for n in count_up(1, 4): print(n)  # 1 2 3

Decorator — with functools.wraps (production pattern):

import functools, time

def timer(func):
    """Decorator: prints elapsed time of any function call."""
    @functools.wraps(func)  # preserves __name__, __doc__, __annotations__
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        result = func(*args, **kwargs)   # forward the actual call
        elapsed = time.perf_counter() - t0
        print(f"{func.__name__} took {elapsed:.4f}s")
        return result
    return wrapper

@timer
def slow_sum(n): return sum(range(n))

slow_sum(10**7)  # slow_sum took 0.2341s

Interview Q&A

Q1: What is the difference between an iterable and an iterator?
An iterable implements __iter__() and returns an iterator. An iterator implements both __iter__() (returning itself) and __next__(). A list is iterable but not an iterator; calling iter([]) creates a list_iterator. Key distinction: iterables are reusable (each iter() call returns a fresh iterator), while iterators are stateful and single-pass.

Q2: What happens when you call a generator function?
Nothing in the function body executes. You get back a generator object (a suspended frame). Only when you call next() does the body start executing — until the first yield, which suspends and returns the yielded value.

Q3: Why does functools.wraps matter in decorators?
Without it, the wrapper function replaces the original's __name__, __doc__, __annotations__, and __module__. This breaks introspection, docstring access, and tools like Sphinx. functools.wraps copies these attributes from the wrapped function to the wrapper.

Q4: Explain Python's MRO with diamond inheritance.
Python uses C3 linearization. For class D(B, C) where both B and C inherit from A: MRO is [D, B, C, A, object]. Python visits each class exactly once, preserving left-to-right order and ensuring no class appears before its subclasses. super() delegates to the next class in this MRO — not the direct parent.

Q5: What is yield from?
yield from iterable delegates to a sub-generator or iterable: it transparently forwards next(), send(), throw(), and close() calls, and captures the sub-generator's return value. It's essential for generator-based coroutines and is what asyncio was originally built on.

Key Takeaways & Related Topics
▼

When you internalize these concepts, Python's "magic" disappears:

  • for x in obj = iter(obj).__next__() in a loop until StopIteration
  • A decorator = a function that returns a function. Nothing more, nothing less.
  • A generator = a function whose frame can be suspended mid-execution via yield
  • async/await = generators + an event loop that calls send() instead of next()
  • Class attribute lookup = walk the MRO list, check __dict__ of each entry
💡 The Unified Model

Python's entire concurrency story — generators, coroutines, asyncio, async for, async with — reduces to the iterator protocol. If you deeply understand __iter__/__next__/StopIteration, you understand the foundation of modern async Python.
