Ring Attention for Distributed Long-Context

Sharding the sequence across a device ring so context length scales with cluster size, not GPU memory
Advanced LLMs / Distributed Systems Long Context O(N/R) memory per device
1
Understanding Ring Attention
▼

What is it? A Transformer's context window is limited by how much memory one GPU has, because standard attention needs every query to see every key/value pair for the full sequence. Ring Attention removes this limit by splitting the sequence into blocks, giving one block to each device, and passing the key/value (KV) blocks around a ring of devices while each device keeps computing attention with whatever block currently sits in its hands. No device ever needs the whole sequence at once.

Analogy: Imagine a study group where the textbook is too big for any one person to hold. Instead, everyone keeps their own question ("query") and one chapter of the book. Each person reads their chapter, notes anything relevant to their question, then passes the chapter to their neighbor and receives a new one — in a circle. After every chapter has passed through every pair of hands, each person has consulted the entire book, but no one ever held more than one chapter at a time.

💡 If you remember one thing

Ring Attention shards Q, K, V by sequence position across devices arranged in a ring. Each device keeps a fixed Q block and rotates KV blocks around the ring over \(R\) steps, accumulating exact attention output with online softmax — communication of KV blocks is overlapped with compute, so per-device memory is \(O(N/R)\) instead of \(O(N)\), while the attention result is numerically identical to full attention.

2
How Ring Attention Works Internally
▼

The Memory Wall

Vanilla self-attention materializes an \(N \times N\) score matrix, and even memory-efficient variants like FlashAttention still need the full \(K\) and \(V\) tensors — \(O(N)\) — resident on the device computing a query block. At context lengths of 1M+ tokens, \(K\)/\(V\) alone can exceed a single GPU's HBM, long before compute becomes the bottleneck.

Sequence Parallelism + a Ring Topology

Ring Attention (Liu, Zaharia & Abbeel, 2023) splits the sequence of length \(N\) into \(R\) contiguous blocks, one per device: device \(i\) permanently owns query block \(Q_i\) and starts by owning key/value block \((K_i, V_i)\). Devices are logically arranged in a ring. At each of \(R\) rounds:

  • Compute — every device computes attention scores between its resident \(Q_i\) and whichever KV block it currently holds, and folds the result into a running (unnormalized) output using online softmax.
  • Communicate — every device simultaneously sends its current KV block to its ring-neighbor and receives a new one from the other neighbor — a single non-blocking peer-to-peer transfer, not an all-gather.

Because step \(r\)'s communication only feeds step \(r+1\)'s compute, the KV send/receive for round \(r+1\) is issued while round \(r\)'s compute is still running. If compute per block takes at least as long as one KV transfer, communication is fully hidden — the wall-clock cost approaches pure compute time, not compute + communication.

Design Decision: why a ring and not all-to-all?

An all-gather would require \(O(N)\) memory again once gathered. A ring needs each device to hold only two KV blocks at a time (current + incoming) — \(O(N/R)\) — and needs exactly \(R\) point-to-point hops to guarantee every query block meets every KV block exactly once, with predictable, overlappable communication.

🔑 Key Property

After \(R\) rounds, every \(Q_i\) has attended to every \((K_j, V_j)\) exactly once. The output is mathematically identical to standard full attention — Ring Attention is an exact, communication-efficient reformulation, not an approximation.

3
Why It Works — Online Softmax
▼

For a query \(q\), standard attention over keys/values \(\{(k_j, v_j)\}_{j=1}^{N}\) with scale \(d\) is:

$$\text{Attn}(q) = \sum_{j=1}^{N} \frac{\exp(s_j - m)}{\sum_{l=1}^{N}\exp(s_l - m)}\, v_j, \qquad s_j = \frac{q \cdot k_j}{\sqrt{d}}, \qquad m = \max_j s_j$$

The problem: computing \(m\) and the denominator normally requires seeing all \(N\) keys at once. Online softmax (used inside FlashAttention and reused by Ring Attention) computes this incrementally, one block at a time, by carrying three running statistics: the running max \(m\), the running normalizer \(l\), and the running weighted accumulator \(\text{acc}\).

The Update Rule

Given running state \((m, l, \text{acc})\) and a new block contributing score \(s\) and value \(v\):

$$m' = \max(m, s) \qquad \alpha = e^{m - m'}$$
$$l' = \alpha \, l + e^{s - m'} \qquad \text{acc}' = \alpha \, \text{acc} + e^{s - m'} v$$

\(\alpha = e^{m-m'}\) is the correction factor: whenever a new block raises the running max, every previously accumulated term is rescaled down by exactly the right amount so the final ratio stays exact. After the last block, the true attention output is simply:

$$\text{Attn}(q) = \frac{\text{acc}}{l}$$

In Ring Attention this is applied per device, per round: each device's \((m_i, l_i, \text{acc}_i)\) triple is updated using whatever KV block currently sits in its hands, regardless of the order blocks arrive in — the ring order is arbitrary, only completeness (seeing all \(R\) blocks) matters.

⚠️ Common Misconception

"Ring Attention approximates long-context attention." It does not — online softmax is algebraically exact. Given infinite precision it returns bit-identical results to computing softmax over the whole sequence at once; in practice, floating-point rounding differences are negligible (same order as any reduction reordering).

Key Takeaways
▼

When to use Ring Attention:

  • Context length exceeds what fits in one device's HBM (documents, books, video, genomics, multi-hour audio)
  • You have a multi-GPU/multi-node cluster with fast peer-to-peer interconnect (NVLink, InfiniBand)
  • You need an exact attention result, not a sparse/linear approximation
  • Combined with causal masking, blocks can be skipped once a device's queries only need past blocks — further cutting communication

When NOT to use:

  • Short sequences that already fit comfortably on one device — the ring adds coordination overhead for no benefit
  • Slow interconnects where KV transfer time dwarfs compute time — communication can no longer hide behind compute and the ring stalls
  • Single-GPU training/inference — there's no ring to form
💡 Hierarchy

FlashAttention makes single-device attention memory-efficient via online softmax over tiled blocks in one GPU's SRAM. Ring Attention takes that exact same online-softmax tiling and distributes the tiles across devices connected in a ring, so the "tile" boundary becomes a network hop instead of a memory-hierarchy boundary — this is why context length now scales with cluster size, not single-GPU memory.

Code Trace — From-Scratch Ring Attention (single process, simulated)
▼
import numpy as np
R = 4 # number of devices / ring size
d = 8 # head dim
Q = [np.random.randn(1, d) for _ in range(R)] # device i's query block
K = [np.random.randn(1, d) for _ in range(R)] # device i's OWN key block
V = [np.random.randn(1, 1) for _ in range(R)] # device i's OWN value block
# running online-softmax state per device
m = [-np.inf] * R
l = [0.0] * R
acc = [0.0] * R
def online_update(m_i, l_i, acc_i, s, v):
m_new = max(m_i, s)
alpha = np.exp(m_i - m_new) # correction for past terms
l_new = alpha * l_i + np.exp(s - m_new)
acc_new = alpha * acc_i + np.exp(s - m_new) * v
return m_new, l_new, acc_new
cur_K, cur_V = list(K), list(V) # each device currently holds block i
for round in range(R):
# ── COMPUTE: use whatever KV block is currently held ──
for i in range(R):
s = float(Q[i] @ cur_K[i].T) / np.sqrt(d)
m[i], l[i], acc[i] = online_update(m[i], l[i], acc[i], s, cur_V[i])
# ── COMMUNICATE: send to next device, receive from previous (overlaps next compute) ──
cur_K = [cur_K[(i - 1) % R] for i in range(R)]
cur_V = [cur_V[(i - 1) % R] for i in range(R)]
output = [acc[i] / l[i] for i in range(R)] # exact full-attention result, O(N/R) memory

In production (e.g. JAX/PyTorch), the compute loop and the isend/irecv collective for the next block are issued together and the compute kernel runs while the network transfer is in flight, so step round+1's communication cost is hidden behind step round's compute — this overlap is the entire point of the ring topology.
