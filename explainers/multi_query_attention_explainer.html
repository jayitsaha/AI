Multi-Query & Grouped-Query Attention

How LLaMA-2, Mistral and friends shrink the KV cache and speed up autoregressive inference by making query heads share their Key/Value heads.

Intermediate Transformers / Attention Inference Efficiency
1
Understanding the Concept
▼

What is this? In standard multi-head attention, every attention head keeps its own private set of Key (K) and Value (V) projections. That means an 8-head model stores 8 separate K/V tensors per token, per layer. Multi-Query Attention (MQA) makes every head share one single K/V pair. Grouped-Query Attention (GQA) is the compromise: heads are split into a handful of groups, and heads inside a group share one K/V pair.

Analogy: Imagine 32 analysts (query heads) all trying to read from a shared filing cabinet. Multi-Head Attention gives each analyst their own private cabinet (fast to search, but you need 32 cabinets of storage). MQA gives all 32 analysts one shared cabinet (cheap storage, but everyone is filtering the same raw material). GQA splits the analysts into, say, 8 teams of 4, each team sharing one cabinet — most of the storage savings, almost none of the quality loss.

One-sentence summary: MQA/GQA reduce the number of Key/Value heads relative to Query heads so the KV cache — the real inference-time memory and bandwidth bottleneck — shrinks proportionally, at little to no cost in model quality.

If you remember one thing

Query heads stay at full count (they define representational capacity); only the K/V heads are reduced and shared — because it's the KV cache, not the query projection, that must be re-read from memory at every single decoding step.

2
How It Works Internally
▼

In vanilla multi-head attention (MHA) with \(h\) heads and head dimension \(d_h\), the projections are \(W^Q, W^K, W^V \in \mathbb{R}^{d_{model}\times h \cdot d_h}\), producing \(h\) independent \((Q_i, K_i, V_i)\) triples. During autoregressive decoding, every generated token appends a new K and V vector per head, per layer to the KV cache, which must be streamed back from HBM for every subsequent token. With \(h=32\) heads this means 32 separate K/V read streams — the dominant cost at small batch sizes, because attention becomes memory-bandwidth bound, not compute bound.

MQA (Shazeer, 2019) collapses \(W^K\) and \(W^V\) down to a single head: all \(h\) query heads attend against the same \(K, V\) — i.e. \(W^K, W^V \in \mathbb{R}^{d_{model}\times d_h}\). The KV cache shrinks by a factor of \(h\) (e.g. 32×), and the memory-bandwidth bottleneck during decoding shrinks by the same factor, giving large inference speedups. The cost: with only one shared K/V representation, the model has less flexibility, and quality can degrade — especially in larger models, and training can become unstable.

GQA (Ainslie et al., 2023) interpolates: partition the \(h\) query heads into \(G\) groups (\(1 \le G \le h\), \(h\) divisible by \(G\)); heads within a group share one K/V head, giving \(G\) distinct K/V heads total. \(G=1\) recovers MQA exactly; \(G=h\) recovers standard MHA exactly. Practically, existing MHA checkpoints are uptrained into GQA by mean-pooling each group's original K/V heads into one, then fine-tuning briefly — this is exactly how LLaMA-2-70B (\(h=64\), \(G=8\)) and Mistral-7B (\(h=32\), \(G=8\)) were built.

Design decision: why not just shrink Q too?

Query heads are read once per token to compute attention scores and are never cached — they cost nothing extra to keep at full count. It is specifically the cached K/V tensors, re-read at every decoding step for every prior token, that dominate memory traffic. Shrinking Q would hurt representational diversity for free; shrinking K/V removes the actual bottleneck.

3
Why It Works — The Math
▼

Standard scaled dot-product attention for head \(i\) is:

$$\text{head}_i = \text{softmax}\!\left(\frac{Q_i K_i^\top}{\sqrt{d_h}}\right) V_i$$

In MHA, \(K_i, V_i\) are distinct per head \(i = 1, \dots, h\). In GQA with \(G\) groups, we define a mapping \(g(i) = \lceil i \cdot G / h \rceil\) that assigns each query head to one of \(G\) groups, and reuse the shared K/V for the whole group:

$$\text{head}_i = \text{softmax}\!\left(\frac{Q_i K_{g(i)}^\top}{\sqrt{d_h}}\right) V_{g(i)}, \qquad g(i) \in \{1,\dots,G\}$$

The KV cache footprint (per layer, per token) is the quantity that actually matters for inference cost:

$$\text{Cache}_{\text{layer}} = 2 \times G \times d_h \times \text{bytes}, \qquad \text{Cache}_{\text{total}} = L \times B \times S \times \text{Cache}_{\text{layer}}$$

where the factor 2 is for storing both K and V, \(L\) is the number of layers, \(B\) is batch size, and \(S\) is sequence length. Because \(G\) appears as a simple linear multiplier and everything else is fixed by the architecture, cache size (and the memory bandwidth needed to stream it) scales linearly in \(G\) — going from \(G=h\) (MHA) to \(G=1\) (MQA) is an exact \(h\times\) reduction, independent of sequence length or batch size.

Common misconception

"GQA makes the model itself smaller/faster to train." Not quite — the parameter count reduction is modest (only \(W^K, W^V\) shrink) and FLOPs for the QK/AV matmuls are essentially unchanged. The win is almost entirely at autoregressive decoding time, where KV cache reads are memory-bandwidth bound; prefill (processing the prompt) and training throughput barely move.

When to use GQA: almost any modern decoder-only LLM intended for autoregressive serving at scale — it is now close to a default choice (LLaMA-2/3, Mistral, Gemma all use it) because it gets nearly all of MQA's inference speedup with negligible quality loss.

When to use plain MHA: small models, encoder-only or bidirectional models where KV cache during generation isn't the bottleneck, or when you cannot afford any quality regression and compute/memory budget is not constrained.

When to use pure MQA: extreme-throughput serving scenarios (e.g. very long context, very large batch) where cache bandwidth dominates and a small quality hit is acceptable — original use case in Google's PaLM and PaLM-2.

Decision rule

Pick \(G\) as large as your memory/bandwidth budget allows before it starts hurting decode latency — in practice \(G \in \{8, 16\}\) (dividing \(h\) evenly) is the sweet spot used by most 2023–2025 open LLMs.

6
Key Takeaways
▼

MQA and GQA are both about one thing: shrinking the KV cache, the tensor of past Keys/Values that autoregressive decoding must re-read from memory at every single generated token. Query heads stay full-count; only the number of distinct K/V heads (\(G\)) drops. \(G=h\) is ordinary MHA, \(G=1\) is MQA, anything in between is GQA.

Cache size and decode-time memory bandwidth scale linearly in \(G\), so halving \(G\) roughly halves cache memory and read bandwidth at generation time — with prefill compute and parameter count barely affected. GQA is the practical default in modern open-weight LLMs (LLaMA-2/3, Mistral, Gemma) because it recovers almost all of MQA's speed with almost none of its quality cost, typically via brief "uptraining" of an existing MHA checkpoint.

Related topics: Flash Attention (kernel-level speedup, orthogonal to MQA/GQA), KV-cache quantization, PagedAttention/vLLM (cache memory management), Multi-Head Latent Attention (MLA, used in DeepSeek-V2/V3 — compresses KV into a low-rank latent instead of sharing heads).
