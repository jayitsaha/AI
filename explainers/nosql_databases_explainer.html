NoSQL Databases

Document · Key-Value · Column-Family · Graph — when to break free from SQL
Intermediate Data Engineering Systems CAP Theorem
1
The 30-Second Version
▼

What is it? SQL databases store data as rigid rectangular tables with fixed columns, like a spreadsheet. NoSQL ("Not Only SQL") databases abandon that rigid shape to store data in formats that better match real-world structures: nested JSON documents, instant key→value lookups, wide column rows sorted for fast range scans, or networks of connected nodes and relationships.

Analogy: Think of data storage like packing for a trip. SQL is a suitcase with fixed compartments — everything must fit the preset grid. NoSQL is four specialized bags: a zip-lock pouch for instant access (Redis), a folder full of rich documents (MongoDB), a filing cabinet with variable-width drawers sorted by date (Cassandra), and a spider-web of sticky notes connected by labeled strings (Neo4j). Each bag shines for its specific job.

One-sentence summary: NoSQL databases trade SQL's general-purpose expressiveness and ACID guarantees for specialized data models and massive horizontal scalability.

💡 If you remember one thing

NoSQL is not "better than SQL" — it's purpose-built for specific access patterns. Pick MongoDB when your data is nested JSON. Pick Redis for sub-millisecond lookups and caching. Pick Cassandra for write-heavy time-series at global scale. Pick Neo4j when relationships ARE the data and you need to traverse them fast.

Why This Exists — Historical Context
▼

The Scaling Crisis (2000s)

Relational databases (PostgreSQL, MySQL, Oracle) were dominant through the 1990s — designed for single-machine ACID correctness. By the mid-2000s, internet companies like Google, Amazon, and Facebook hit a wall: a single PostgreSQL server couldn't handle millions of concurrent users. Sharding relational databases horizontally was painful — cross-shard joins are slow, schema migrations lock tables, and ACID across shards requires expensive distributed transactions.

The Breakthrough Papers

2003 — Google Bigtable (Chang et al.): Sparse, distributed, persistent sorted map. Introduced the column-family concept. Inspired Apache HBase and Cassandra.
2007 — Amazon Dynamo (DeCandia et al.): Key-value store built around eventual consistency, consistent hashing, and vector clocks for conflict resolution. Inspired Cassandra, Riak, and AWS DynamoDB.
2000 — CAP Theorem (Eric Brewer): Formally proven by Gilbert & Lynch (2002): distributed systems can guarantee at most 2 of Consistency, Availability, Partition tolerance simultaneously.
2009 — MongoDB 1.0: Document model with JSON/BSON, dynamic schema, rich secondary indexes, aggregation framework.
2009 — Redis 1.0 (Salvatore Sanfilippo): In-memory key-value with native data structures (lists, sets, sorted sets, hashes, streams).

🔑 Key Insight

The CAP theorem forced an explicit design choice. NoSQL systems pick their tradeoff: MongoDB (CP), Redis (AP in Cluster mode, CP in single-node), Cassandra (tunable AP→CP via quorum writes), Neo4j (CP). SQL's ACID guarantee requires coordination that kills write throughput once you go multi-node.

The Four Families — Core Concepts
▼
📄 Document — MongoDB

Stores self-describing JSON/BSON documents in collections. Fields can be nested objects or arrays — no fixed schema required. Rich query operators, secondary indexes, and a powerful aggregation pipeline. Best for: catalogs, user profiles, CMS, any hierarchical data where structure varies per record.

⚡ Key-Value — Redis

Hash map at planetary scale in RAM. \(O(1)\) GET/SET. Values can be strings, lists, sets, sorted sets, hashes, bitmaps, HyperLogLogs, streams. Persistence via RDB snapshots + AOF log. Best for: sessions, caching, real-time leaderboards, pub/sub message queues, rate limiting.

📊 Column-Family — Cassandra

Rows identified by partition key (hashed → node assignment). Columns sorted by clustering key within each partition. LSM-tree writes (CommitLog → MemTable → SSTable). Tunable consistency via replication quorum. Best for: time-series, IoT telemetry, event logs, globally distributed write-heavy workloads.

🕸️ Graph — Neo4j

Native storage for nodes + labeled typed relationships. Adjacency pointers stored directly — traversals cost \(O(\text{degree})\) not \(O(N \log N)\) joins. Cypher declarative query language. Best for: social networks, fraud detection, recommendation engines, knowledge graphs, network topology.

CAP Theorem

In any distributed system, you can guarantee at most 2 of 3 properties simultaneously:

$$\text{CAP Theorem}: \;\; \text{Consistency} \;+\; \text{Availability} \;+\; \text{Partition Tolerance} \;\leq\; 2$$

Since network partitions are an unavoidable reality in distributed systems, the practical tradeoff reduces to CP vs AP. A CP system (MongoDB, Neo4j) rejects writes during a partition to preserve consistency. An AP system (Cassandra in AP mode, Redis Cluster) serves stale reads during a partition to preserve availability.

MongoDB: Denormalization vs SQL Normalization

SQL splits data into many normalized tables and joins at query time. MongoDB denormalizes — embed related data inside one document. A blog post embeds its comments array. This eliminates the join at read time: one document read = complete response. The tradeoff: data duplication — if an author's name changes, every post document containing it must be updated.

Rule of thumb: embed data that is always read together and belongs to one owner. Reference (use IDs) for data shared across many documents.

Cassandra: Query-First Data Modeling

Cassandra has no joins and no subqueries. Every query must be satisfiable by a single partition key lookup — all data for a query must live on one node (or its replicas). Design the table schema by starting with the query pattern, not the normalized data shape. If you need two different query patterns, create two separate denormalized tables.

⚠️ Common Pitfall

Cassandra secondary indexes (ALLOW FILTERING) work but are a performance trap at scale — they fan out to every node. Always model with the access pattern as the primary key. If your query patterns change, you may need to migrate your entire data model.

The Math — Hashing, Quorum, and Traversal Complexity
▼

Consistent Hashing (Cassandra / DynamoDB)

Nodes and keys are mapped to points on a virtual ring \([0, 2^{32})\) via a hash function \(h\). A key \(k\) is stored on the first node clockwise from \(h(k)\):

$$\text{node}(k) = \arg\min_{n_i} \bigl((h(k) - h(n_i)) \bmod 2^{32}\bigr)$$

When a node joins or leaves, only \(\tfrac{K}{N}\) keys need to move on average (where \(K\) = total keys, \(N\) = number of nodes). This is far better than modular hashing (\(\text{key} \bmod N\)) which remaps nearly all keys on topology change. Virtual nodes (vnodes) give each physical node multiple ring positions, smoothing load imbalances.

Quorum Reads/Writes — Tunable Consistency

Cassandra replicates each partition to \(RF\) nodes (Replication Factor). A quorum \(Q = \lfloor RF/2 \rfloor + 1\) of nodes must respond for strong consistency. For \(RF = 3\), \(Q = 2\):

$$\text{Strong Consistency} \iff W + R > RF \quad \Longrightarrow \quad W=2,\; R=2 \;\text{(quorum)}$$

Set \(W=1, R=1\) for maximum availability with eventual consistency. Set \(W=RF, R=RF\) for all-nodes consistency at the cost of availability. The knob lets you trade latency for durability: \(W=3\) guarantees no data loss even if 2 nodes fail simultaneously (for \(RF=3\)).

Graph Traversal Complexity (Neo4j)

In a relational database, finding friends-of-friends requires a JOIN whose cost grows with the total table size \(O(N \cdot M)\). Neo4j stores adjacency lists natively — each node has direct pointers to its neighbor nodes. Traversing one hop costs \(O(\deg(v))\). A depth-\(k\) traversal from a starting node costs:

$$\text{Cost}_{\text{depth-}k} = \sum_{i=0}^{k} \bar{d}^{\,i} = \frac{\bar{d}^{k+1} - 1}{\bar{d} - 1} \quad (\bar{d} = \text{average degree})$$

This is independent of \(N\) (total node count). A 6-hop social graph traversal that takes minutes in SQL (full-table join) takes milliseconds in Neo4j because it never touches irrelevant nodes.

📐 LSM-Tree Write vs B-Tree

Cassandra's LSM-tree turns writes into sequential appends (CommitLog + MemTable flush). Write amplification is \(W_A = O(\log_T N)\) where \(T\) is the size-ratio between levels. B-trees used by PostgreSQL/MySQL do random reads-before-writes for page updates: \(W_A = O(\log_B N)\) but with random I/O that is ~100× slower on spinning disks and ~10× slower on SSDs. LSM wins on write-heavy workloads; B-tree wins on read-heavy (no SSTable merge scan needed).

MongoDB — CRUD + Aggregation Pipeline

from pymongo import MongoClient
client = MongoClient("mongodb://localhost:27017")
db = client["shop"]
products = db["products"]
# Insert a nested document (no fixed schema)
products.insert_one({
"_id": "prod:001", "name": "Laptop", "price": 999.99,
"tags": ["electronics", "computing"],
"specs": {"ram_gb": 16, "cpu": "M2", "storage_gb": 512}
})
# Query with nested field filter + projection
docs = products.find(
{"specs.ram_gb": {"$gte": 16}, "price": {"$lt": 1500}},
{"name": 1, "price": 1} # only return these fields
)
# Aggregation pipeline: avg price per tag
result = products.aggregate([
{"$unwind": "$tags"}, # explode array
{"$group": {"_id": "$tags", # group by tag
"avg_price": {"$avg": "$price"}}},
{"$sort": {"avg_price": -1}} # sort desc
])

Redis — Sorted Set Leaderboard

import redis
r = redis.Redis(host="localhost", port=6379, decode_responses=True)
# Add players: ZADD key score member (O(log n) per add)
r.zadd("leaderboard:2024", {"alice": 9500, "bob": 8200, "carol": 9800})
# Top 3 — reverse range (highest score first) O(log n + m)
top3 = r.zrevrange("leaderboard:2024", 0, 2, withscores=True)
# → [('carol', 9800.0), ('alice', 9500.0), ('bob', 8200.0)]
# Atomic increment (race-condition safe) O(log n)
r.zincrby("leaderboard:2024", 300, "bob") # bob: 8200 → 8500
# Rank of a player (0-indexed from top) O(log n)
rank = r.zrevrank("leaderboard:2024", "alice") # → 1
# Session cache with TTL (auto-expiry)
r.setex("session:tok7f2", 3600, "user:alice") # expires in 1h

Cassandra CQL — Time-Series Schema (query-first design)

-- Query pattern: "get readings for device X from time T1 to T2"
-- Primary key: partition=device_id (→ single node), cluster=ts DESC
CREATE TABLE sensor_readings (
device_id TEXT,
ts TIMESTAMP,
temp_c FLOAT,
humidity FLOAT,
PRIMARY KEY ((device_id), ts)
) WITH CLUSTERING ORDER BY (ts DESC);
-- Write: no read-before-write, O(1) sequential append
INSERT INTO sensor_readings (device_id, ts, temp_c, humidity)
VALUES ('sensor-42', toTimestamp(now()), 23.5, 61.2);
-- Read: single-partition range scan — never touches other nodes
SELECT ts, temp_c, humidity FROM sensor_readings
WHERE device_id = 'sensor-42'
AND ts > '2024-01-01 00:00:00'
LIMIT 100;

Neo4j Cypher — Graph Queries

// Create users and relationships
CREATE (alice:User {name:"Alice", id:1})
CREATE (bob:User {name:"Bob", id:2})
CREATE (carol:User {name:"Carol", id:3})
CREATE (alice)-[:FOLLOWS {since:"2023-01-01"}]->(bob)
CREATE (bob)-[:FOLLOWS]->(carol)
// 2-hop friends-of-friends (never touches unconnected nodes)
MATCH (me:User {name:"Alice"})-[:FOLLOWS*2]->(fof:User)
WHERE NOT (me)-[:FOLLOWS]->(fof) AND me <> fof
RETURN fof.name AS recommendation
// → "Carol"
// Shortest path (BFS internally, O(V+E) worst case)
MATCH p = shortestPath(
(a:User {name:"Alice"})-[:FOLLOWS*]-(b:User {name:"Carol"})
)
RETURN length(p) AS hops, [n IN nodes(p) | n.name] AS path
// → hops: 2, path: ["Alice", "Bob", "Carol"]
