Encoder–Decoder Framework

How sequence-to-sequence models compress an input into a single vector and generate an output one token at a time — and why that single vector became the bottleneck attention was invented to break.

Foundational Sequence Models & NLP O(n) encode / O(m) decode
1
Understanding the Concept
▾

What is this? Many problems take a sequence in and produce a different sequence out — translating a French sentence to English, turning speech audio into text, or summarizing a long article into three sentences. The encoder–decoder framework is the blueprint for this: one network (the encoder) reads the entire input and squashes it into a single fixed-size summary vector, and a second network (the decoder) reads that summary and generates the output one piece at a time, feeding each generated piece back in to produce the next.

Analogy: Imagine a translator who first listens to an entire foreign sentence, closes their eyes, and condenses everything they heard into a single mental impression — then, without looking back at the original sentence, speaks the translation one word at a time, using only that mental impression (plus what they've already said) to decide the next word.

Summary: Encoder compresses input → fixed-size context vector → decoder autoregressively expands it back into an output sequence, one token per step.

If you remember one thing

The encoder and decoder communicate through exactly one fixed-size vector, no matter how long the input or output is — that single hand-off point is both the elegance and the Achilles' heel of the framework.

2
How It Works Internally
▾

The problem it solves: before 2014, sequence models mostly assumed input and output were the same length and aligned position-by-position (e.g. tagging each word with a part of speech). Translation, summarization, and speech recognition don't work that way — a 5-word French sentence might need a 7-word English sentence, with words reordered. Sutskever, Vinyals & Le ("Sequence to Sequence Learning with Neural Networks," NeurIPS 2014) and, in parallel, Cho et al. ("Learning Phrase Representations using RNN Encoder–Decoder for Statistical Machine Translation," EMNLP 2014) proposed decoupling input length from output length entirely via two separate recurrent networks joined at one vector.

Encoder pass: the encoder is an RNN (originally LSTM/GRU) that reads input tokens \(x_1, x_2, \dots, x_T\) one at a time, updating a hidden state \(h_t = f(x_t, h_{t-1})\) at each step. After the last token, \(h_T\) becomes the context vector \(c\) — a fixed-size numerical fingerprint of the entire input, regardless of whether \(T\) was 3 tokens or 300.

Decoder pass: the decoder is a second RNN, initialized with \(s_0 = c\) (and in Cho et al.'s variant, fed \(c\) again at every decoding step, not just at initialization). At each step \(t\), it looks at its previous hidden state \(s_{t-1}\), the token it emitted last time \(y_{t-1}\), and the context \(c\), to compute a new hidden state \(s_t\) and a probability distribution over the output vocabulary. It samples/argmaxes a token, emits it, and feeds that token back in as the next input — this is autoregressive generation: each output depends on all previously generated outputs.

Design decision: why route everything through one vector?

Fixing the interface to a single vector of constant dimensionality lets the decoder be completely decoupled from the encoder's input length — any encoder architecture can plug into any decoder as long as both agree on the size of \(c\). The cost: \(c\) has to represent an entire sentence's meaning in, say, 512 numbers, no matter if the sentence has 5 words or 50. This is the information bottleneck that later motivated attention (Bahdanau et al., 2015), which replaces the single \(c\) with a weighted combination of all encoder states, recomputed fresh at every decoder step.

3
The Math & Why It Works
▾

The encoder recurrence at each timestep \(t = 1,\dots,T\):

$$h_t = \tanh(W_x x_t + W_h h_{t-1} + b), \qquad c = h_T$$

The decoder recurrence at each timestep \(t = 1,\dots,M\), conditioning on the fixed context \(c\) at every step:

$$s_t = \tanh(W_x^{dec} y_{t-1} + W_h^{dec} s_{t-1} + W_c c + b^{dec})$$

The output distribution over the vocabulary at step \(t\) comes from a linear projection followed by softmax:

$$p(y_t \mid y_{<t}, x_1,\dots,x_T) = \operatorname{softmax}(W_o s_t + b_o)$$

Training maximizes the log-likelihood of the target sequence, teacher-forced with the ground-truth previous token instead of the model's own (possibly wrong) prediction:

$$\mathcal{L} = -\sum_{t=1}^{M} \log p(y_t^{*} \mid y_{<t}^{*}, x_{1:T})$$

Why it works (chain rule of probability): factorizing the joint probability of the whole output sequence into a product of per-token conditionals is exact by the chain rule — no approximation is needed there. The approximation is entirely in what each conditional is allowed to depend on: only \(c\) (a fixed-size summary) instead of the full, unbounded input. As \(T\) grows, \(c\) must encode proportionally more information into the same number of dimensions, so recall of early tokens degrades — this is measurable empirically as BLEU score dropping sharply on sentences longer than ~20 tokens for pure encoder–decoder models (Cho et al. 2014).

Common misconception

"The decoder can look back at the input whenever it needs to." It cannot — in the vanilla framework the decoder never sees the individual input tokens or their hidden states again after encoding finishes. It only ever sees \(c\). This is exactly the constraint attention removes by giving the decoder a fresh, query-dependent weighted view over all encoder hidden states \(h_1, \dots, h_T\) at every generation step.

When to still use the plain framework

Understanding vanilla encoder–decoder is essential because it's the conceptual skeleton every later architecture — attention-augmented RNNs, and the Transformer's encoder–decoder stack itself — still follows: read everything, form a representation, generate conditioned on that representation. Attention and cross-attention are best understood as answers to "how do we stop compressing everything into one vector?", not as a different framework altogether.

Key takeaways: (1) Two networks, one interface — the context vector. (2) Decoding is autoregressive: each token depends on everything generated so far. (3) Fixed-size \(c\) is an information bottleneck that gets worse with longer inputs. (4) Attention (and later, full self-/cross-attention in Transformers) exists specifically to remove this bottleneck.

Code Trace (From Scratch)
▾

Minimal NumPy sketch of the exact recurrence used in the visualization above (tanh RNN encoder → context-conditioned tanh RNN decoder):

def encoder(tokens, Wx, Wh, b):
h = np.zeros(Wh.shape[0])
for x in tokens:
h = np.tanh(Wx @ x + Wh @ h + b) # recurrence
return h # h_T becomes context c
def decoder_step(y_prev, s_prev, c, Wxd, Whd, Wc, bd, Wo, bo):
s = np.tanh(Wxd @ y_prev + Whd @ s_prev + Wc @ c + bd)
logits = Wo @ s + bo
probs = np.exp(logits - logits.max())
probs /= probs.sum() # softmax
y_t = np.argmax(probs) # greedy decode
return s, y_t, probs

Notice c never changes across decoder steps — it's computed once by encoder() and reused as-is in every call to decoder_step. That single reused array is the entire information bottleneck in code form.
