Gradient Checking

Verifying analytic (backprop) gradients against centered finite-difference numerical estimates — a debugging tool, not a training technique.
Intermediate Optimization & Debugging O(n) forward passes Important — Interview Topic
1
Understanding the Concept
▾

Backpropagation is just calculus turned into code — and code has bugs. A sign flip, a transposed matrix, a missed chain-rule factor: your network will often still run, still produce a loss number, and even appear to train a little. It just silently learns worse than it should. Gradient checking is the fix: compute the gradient a second, independent way and compare.

The independent way is numerical differentiation. Nudge one parameter up by a tiny amount ε, run the forward pass, note the loss. Nudge it down by ε, run forward again. The slope between those two points approximates the true derivative — no calculus required, just the definition of a derivative applied with a small but finite step.

💡 Key Insight

Use the centered difference \((f(x+\epsilon)-f(x-\epsilon))/2\epsilon\), not the one-sided \((f(x+\epsilon)-f(x))/\epsilon\). Centering cancels the leading error term via symmetry, turning a rough estimate into one accurate to ~7 significant digits — for the same computational cost.

This is purely a debugging tool. It costs one extra forward pass per parameter, which is far too slow for training (backprop already gives you the exact gradient for every parameter in a single backward pass). You run it once, offline, in double precision, on a small toy version of any custom gradient you hand-write — then you turn it off.

How It Works Internally
▾

A gradient check runs alongside your hand-written or autodiff-generated backward pass and treats it as a black box to audit. The recipe, parameter by parameter:

  • 1. Flatten. Pack every trainable tensor (weights, biases, per-layer) into one long vector \(\theta \in \mathbb{R}^n\), and do the same for the analytic gradient \(g_{analytic} = \nabla_\theta \mathcal{L}\) produced by your backward pass.
  • 2. Perturb. For each index \(i\) (or a random subsample — checking every dimension of a real network is too slow), set \(\theta_i \mathrel{+}= \epsilon\), run a full forward pass, record \(\mathcal{L}^+\). Reset, set \(\theta_i \mathrel{-}= \epsilon\), forward again, record \(\mathcal{L}^-\).
  • 3. Estimate. \(g_{numeric}[i] = (\mathcal{L}^+ - \mathcal{L}^-) / (2\epsilon)\). This costs 2 forward passes per checked dimension — hence \(O(n)\) forward passes total, versus the single backward pass that produced all of \(g_{analytic}\) at once.
  • 4. Compare. Compute the relative error \( \|g_{analytic}-g_{numeric}\| / \max(\|g_{analytic}\|,\|g_{numeric}\|) \) per element and flag anything above a threshold.
⚠ Practical Gotchas

Use double precision (float64) — float32 round-off swamps the signal. Fix all randomness (dropout masks, data augmentation, random seeds) before comparing, or the two forward passes aren't evaluating the same function. Check kinked functions like ReLU or hinge loss away from the kink, or expect a benign mismatch there. Regularization terms count too — check the full loss, not just the data term.

< 1e-7Excellent — almost certainly correct
1e-7 – 1e-4OK for functions with kinks (ReLU, max, hinge)

Why It Works — The Math
▾

Expand \(f\) with a Taylor series around \(x\). The forward (one-sided) difference keeps only the first term and leaves an \(O(\epsilon)\) error:

$$ \frac{f(x+\epsilon)-f(x)}{\epsilon} = f'(x) + \tfrac{1}{2}\epsilon f''(x) + O(\epsilon^2) $$

Now expand in both directions and subtract. The even-order terms — including that dangerous \(f''(x)\) term — cancel exactly by symmetry, leaving only odd-order remainder terms starting at \(\epsilon^2\):

$$ \frac{f(x+\epsilon)-f(x-\epsilon)}{2\epsilon} = f'(x) + \tfrac{1}{6}\epsilon^2 f'''(x) + O(\epsilon^4) $$

That's the whole trick: centering turns a first-order approximation into a second-order one for free. This truncation error shrinks as \(\epsilon \to 0\) — but on a real computer, floating point introduces a competing round-off error. Evaluating \(f(x+\epsilon)\) and \(f(x-\epsilon)\) each carries absolute error \(\sim u \cdot |f(x)|\) (machine epsilon \(u \approx 2.2\times10^{-16}\) for float64), and dividing by \(2\epsilon\) amplifies it:

$$ \text{total error}(\epsilon) \;\approx\; \underbrace{C_1 \epsilon^2}_{\text{truncation, ↓ as }\epsilon\downarrow} \;+\; \underbrace{\frac{C_2\, u}{\epsilon}}_{\text{round-off, ↑ as }\epsilon\downarrow} $$

Minimizing this sum over \(\epsilon\) gives the optimal step size \(\epsilon^\star \approx (3u)^{1/3}\), numerically about \(10^{-5}\) to \(10^{-6}\) for float64 — which is exactly why 1e-5 is the textbook default and why shrinking ε "to be safe" can silently make your check worse, not better.

Key Takeaways
▾
  • Centered, not one-sided. \((f(x+\epsilon)-f(x-\epsilon))/2\epsilon\) is \(O(\epsilon^2)\) accurate for the same cost as the \(O(\epsilon)\) one-sided version — always prefer it.
  • ε has a sweet spot, not a "smaller is better." Around \(10^{-5}\)–\(10^{-6}\) in float64 balances Taylor truncation error against floating-point round-off; go much smaller and cancellation destroys precision.
  • Read relative error, not absolute error. Absolute error doesn't account for gradient scale; use \(|a-n|/\max(|a|,|n|)\) and judge against the 1e-7 / 1e-4 / 1e-2 bands.
  • Kinks are expected false alarms. Non-smooth points (ReLU at 0, max, hinge boundaries) genuinely disagree with a finite-difference straddling them — that's math, not a bug. Check nearby points instead.
  • Debug tool, not a training method. \(O(n)\) forward passes per check versus one backward pass for the exact gradient — run it once on a tiny model, in double precision, with randomness fixed, then delete it.
