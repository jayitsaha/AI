1
Understanding Data Versioning
▼

What is it? In software engineering, Git lets every developer know exactly which version of every file they have — you can roll back, branch, merge, and compare. Data science has the same problem: datasets change (new rows added, labels corrected, preprocessing tweaked), but without tracking, you lose the connection between "model trained on data v3" and what "data v3" actually was. Data versioning tools apply version-control concepts to datasets, not just code.

Analogy: Imagine a legal archive. A clerk (Git) tracks who signed what document and when, but the physical folders (datasets — often gigabytes) live in a warehouse, not in the clerk's office. The clerk stores only a tiny receipt with the folder's unique barcode (content hash). To fetch the folder, you show the receipt. DVC works exactly this way. LakeFS goes further: the entire warehouse itself has branching — a team can work on a "feature branch" of 10 TB of data without copying it. Delta Lake is a transaction log stapled to Parquet files on S3/GCS — every INSERT/UPDATE/DELETE is an ACID-committed entry, giving you SQL-style time-travel.

💡 If you remember one thing

All three tools version data by indirection: Git ↔ content hash (DVC), object-store copy-on-write + Git-like refs (LakeFS), or an append-only transaction log over Parquet (Delta Lake). The actual bytes move lazily; the version identifier is tiny.

Why it matters for ML: Reproducibility is impossible without knowing exactly which data produced a model. Regulatory requirements (GDPR audit trails, FDA submissions) demand data lineage. Feature stores and model registries are incomplete without data version pointers alongside model weights.

2
How Each Tool Works Internally
▼

DVC — Git tracks .dvc pointer files; data lives in remote storage

When you run dvc add data/train.csv, DVC computes a SHA-256 hash of the file, writes a .dvc pointer file (≈200 bytes of YAML) into Git, and moves the actual bytes into .dvc/cache/ organized as ab/cdef1234... (first 2 chars = directory, rest = filename). When you push to a remote (S3, GCS, Azure, SSH), DVC copies only cache entries that don't already exist there — content-addressed deduplication. Checking out an old commit restores the old .dvc file, then dvc pull fetches the correct bytes using the hash.

Pipelines: dvc.yaml describes DAG stages (each stage: command + deps + outputs). DVC tracks which stages are stale via dvc.lock (sha256 of every input), running only invalidated stages — the same idea as Make, but data-aware.

🔑 DVC Key Invariant

The content hash is deterministic: \(\text{hash}(D) = \text{SHA-256}(D)\). Two identical datasets always get the same hash → automatic deduplication. No history is ever lost from the cache.

LakeFS — Git-like semantics over an object store

LakeFS sits in front of S3/GCS as a proxy. It implements a Git-like ref model (branches, commits, tags, merge) over object storage. Each branch is a lightweight pointer to a commit. A commit records a snapshot of the entire namespace — which S3 keys exist and what their etag/version is — without copying the underlying bytes (copy-on-write). Only changed objects are new; unchanged objects are shared across commits via pointer deduplication in an internal PostgreSQL/DynamoDB metadata store.

S3-compatible API: Existing tools (Spark, pandas, boto3) access data at s3://repo/branch/path — no code changes. Merges detect conflicts (same key modified on both branches) and surface them for resolution.

🔑 LakeFS Key Invariant

A commit is a Merkle-tree–inspired manifest of (path → object_id) pairs. Branch creation is \(O(1)\) — it copies one pointer. Data isolation is guaranteed: reads on branch A never see uncommitted writes on branch B.

Delta Lake — ACID transaction log over Parquet

Delta Lake stores data as Parquet files in a directory, plus a hidden _delta_log/ folder. Every write produces a new JSON log entry (or Parquet checkpoint every 10 commits) recording which Parquet files were added, removed, and metadata changes. Reading the table means reading the latest log to find the live file set. ACID is implemented via optimistic concurrency: writers read the log, compute their changes, then atomically append a new log entry — if two writers conflict, the loser retries. Time-travel is trivial: replaying the log up to any timestamp or version number gives you the exact live file set at that point.

Schema evolution: The log records schema changes per commit. Readers can merge schemas forward or enforce compatibility constraints. Z-ordering and data skipping statistics are stored in the log as per-file column stats.

🔑 Delta Lake Key Invariant

The transaction log is a monotonically growing sequence: \(\{l_0, l_1, \ldots, l_n\}\). The live table state at version \(v\) is \(\bigcup_{i=0}^{v} \text{adds}(l_i) \setminus \bigcup_{i=0}^{v} \text{removes}(l_i)\). ACID atomicity: a transaction either appends exactly one \(l_i\) or fails entirely — no partial state.

3
Guarantees & Formal Properties
▼

Content Addressing & Collision Probability

DVC and LakeFS both use SHA-256 content hashing. The probability of two distinct files \(A \neq B\) having the same hash (collision) is bounded by the birthday paradox:

$$P(\text{collision after } n \text{ files}) \approx 1 - e^{-n^2 / (2 \cdot 2^{256})}$$

For \(n = 10^{12}\) files, this probability is \(\approx 10^{-54}\) — astronomically small. Content-addressed storage is cryptographically safe for deduplication.

Delta Lake ACID Guarantees

Delta Lake satisfies all four ACID properties:

  • Atomicity: A writer atomically appends exactly one log entry \(l_n\) via cloud-provider put-if-absent semantics. No partial writes are visible.
  • Consistency: Schema is validated against the log before every write. Constraint violations abort the transaction.
  • Isolation: Optimistic concurrency — writer reads at version \(v\), attempts to write \(l_{v+1}\); if another writer already wrote \(l_{v+1}\), the conflict is detected and the loser retries from \(l_{v+1}\).
  • Durability: Log files are written to object storage (S3/GCS) with their own strong durability guarantees (≥11 nines).
$$\text{Live}(v) = \left(\bigcup_{i=0}^{v} \text{Added}_i\right) \setminus \left(\bigcup_{i=0}^{v} \text{Removed}_i\right)$$

Time-travel to version \(v\): simply evaluate \(\text{Live}(v)\) by replaying the log up to entry \(v\). Spark reads the Parquet files in \(\text{Live}(v)\) directly — no data movement required.

LakeFS Branching Complexity

Branch creation is \(O(1)\): copy one ref pointer. Reading a branch's namespace requires a metadata lookup returning \(O(|\text{changed files}|)\) delta from the parent commit. Merge is \(O(|\text{changed files on both branches}|)\) for conflict detection.

$$|\text{Merge cost}| = O(|\Delta A \cup \Delta B|) \ll O(|\text{total objects}|)$$

This copy-on-write property means even a 100 TB lake can be branched instantly — only the metadata changes.

⚠️ Common Misconception

Delta Lake's ACID isolation is serializable only within a single table. Cross-table transactions (spanning multiple Delta tables) are not ACID — you need Delta Lake's UniForm or a transaction coordinator. LakeFS, by contrast, provides cross-table isolation at the branch level since all tables in a branch share one atomic commit.

🎯 Decision Guide

Use DVC when: you already use Git, your data is file-oriented (CSVs, images, model weights), and you want ML pipeline reproducibility with minimal infrastructure.
Use LakeFS when: you have a large data lake (S3/GCS) shared across teams, you need data isolation during ETL jobs (branch = experiment sandbox), and governance/compliance requires atomic multi-file commits.
Use Delta Lake when: your data is tabular (structured), you use Spark or Trino, you need ACID writes + SQL time-travel, and you're building a feature store or analytical lakehouse.

Anti-patterns: Don't use DVC for a 100 TB Parquet lake (file-level versioning at that scale is impractical). Don't use Delta Lake for arbitrary binary files (images, audio). Don't use LakeFS as your primary compute layer — it's a versioning proxy, not a query engine.

DVC: Minimal from-scratch pointer writer

# dvc_mini.py — implement core DVC pointer logic from scratch
import hashlib, os, yaml, shutil
def sha256_file(path: str) -> str:
"""Compute SHA-256 of a file, streaming to handle large files."""
h = hashlib.sha256()
with open(path, 'rb') as f:
for chunk in iter(lambda: f.read(65536), b''):
h.update(chunk)
return h.hexdigest()
def dvc_add(filepath: str, cache_dir: str = '.dvc/cache'):
"""Add a file to DVC tracking (mimics `dvc add`)."""
md5 = sha256_file(filepath) # content hash
cache_path = os.path.join(cache_dir, md5[:2], md5[2:])
os.makedirs(os.path.dirname(cache_path), exist_ok=True)
shutil.copy2(filepath, cache_path) # copy to content-addressed cache
pointer = {'outs': [{'md5': md5, 'path': filepath}]}
with open(filepath + '.dvc', 'w') as f:
yaml.dump(pointer, f) # write .dvc pointer into Git
return md5
def dvc_checkout(dvc_file: str, cache_dir: str = '.dvc/cache'):
"""Restore data from cache using .dvc pointer (mimics `dvc checkout`)."""
with open(dvc_file) as f:
meta = yaml.safe_load(f)
for out in meta['outs']:
md5 = out['md5']
cache_path = os.path.join(cache_dir, md5[:2], md5[2:])
shutil.copy2(cache_path, out['path']) # restore bytes

Delta Lake: Transaction log replay (from scratch)

# delta_mini.py — minimal Delta Lake transaction log simulation
import json, os, glob
LOG_DIR = '_delta_log'
def write_transaction(table_path: str, added: list, removed: list):
"""Append one ACID log entry."""
log_path = os.path.join(table_path, LOG_DIR)
os.makedirs(log_path, exist_ok=True)
version = len(glob.glob(f'{log_path}/*.json')) # next version
entry = {'add': added, 'remove': removed, 'version': version}
log_file = os.path.join(log_path, f'{version:020d}.json')
# Atomic write: write + rename is OS-level put-if-absent
with open(log_file + '.tmp', 'w') as f:
json.dump(entry, f)
os.rename(log_file + '.tmp', log_file) # atomic on POSIX
return version
def read_at_version(table_path: str, version: int) -> set:
"""Time-travel: compute live file set at any version."""
log_path = os.path.join(table_path, LOG_DIR)
live = set()
for v in range(version + 1):
log_file = os.path.join(log_path, f'{v:020d}.json')
if not os.path.exists(log_file): break
entry = json.load(open(log_file))
live.update(entry.get('add', []))
live.difference_update(entry.get('remove', []))
return live # set of Parquet file paths at that version
# Example usage:
write_transaction('/data/events', ['part-0.parquet'], [])
write_transaction('/data/events', ['part-1.parquet'], [])
write_transaction('/data/events', ['part-2.parquet'], ['part-0.parquet'])
print(read_at_version('/data/events', 1)) # {'part-0.parquet','part-1.parquet'}
print(read_at_version('/data/events', 2)) # {'part-1.parquet','part-2.parquet'}
