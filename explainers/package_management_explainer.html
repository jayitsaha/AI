Package Management: pip, conda, poetry & Virtual Environments

Isolating per-project dependencies, resolving version conflicts, and locking reproducible environments
Intermediate Software Engineering Programming Must Know
1
Understanding Package Management
▼

What is this? When you write Python code, you rely on external packages (libraries) — things like NumPy, Flask, or PyTorch. Package management is the system that downloads, installs, and tracks which exact version of each library your project needs. Without it, every project on your machine would fight over the same shared copies of packages.

Analogy: Imagine you're a chef who works at three different restaurants. Each restaurant has its own recipe that requires specific ingredient brands and vintages — Restaurant A needs "Heinz ketchup, 2022 batch", Restaurant B needs "Hunt's ketchup, 2023 batch". You can't store just one brand of ketchup in a communal fridge. Instead, each restaurant has its own separate pantry (a virtual environment). Package managers are the supply-chain system that stocks each pantry exactly as specified.

💡 If you remember one thing

A virtual environment is a self-contained directory with its own Python interpreter and site-packages/ folder. Every tool — pip, conda, poetry — ultimately installs packages into an isolated directory like this. The difference is how they resolve which versions to install and what they can install (pure Python vs. binary C libraries).

The Three Tools and Their Roles

pip is Python's built-in package installer. It reads from PyPI (Python Package Index) and installs packages into whatever Python environment is currently active. It does not manage environments itself — you create a venv first, then use pip inside it.

conda is both a package manager AND an environment manager. Unlike pip, it can install packages that contain compiled C/C++ code (CUDA drivers, BLAS libraries, LLVM) without requiring a compiler on your machine. It manages entire Python installations, not just Python packages.

poetry is a dependency management and packaging tool built on top of pip. Its killer feature is a sophisticated version resolver and a poetry.lock file that guarantees byte-identical environments across machines and time.

🔑 Key Property

The Dependency Hell problem: Project A needs numpy==1.21, Project B needs numpy==1.24. Without isolation, you can only have one version. Virtual environments solve isolation; lockfiles solve reproducibility; resolvers solve conflict detection.

2
How the Tools Work Internally
▼

venv Internals: What Actually Happens

When you run python -m venv .venv, Python creates a directory with this structure:

.venv/
├── bin/
│ ├── python # symlink → /usr/bin/python3.10
│ ├── pip # venv-local pip script
│ └── activate # shell script that rewires PATH
├── lib/
│ └── python3.10/
│ └── site-packages/ # ← packages install HERE
└── pyvenv.cfg # records base interpreter path

The critical file is activate. It prepends .venv/bin to your shell's PATH. After activation, typing python finds .venv/bin/python first; typing pip install numpy installs into .venv/lib/python3.10/site-packages/. Deactivating (or opening a new shell) restores the original PATH. The venv's python itself is typically a symlink to the system interpreter — sharing the interpreter binary but having a completely separate module search path.

pip Internals: How It Resolves and Installs

pip uses a two-phase process: resolution then installation. Resolution: pip reads METADATA files from PyPI wheel packages to discover transitive dependencies. It uses a depth-first greedy approach — pick the newest version satisfying a constraint, recurse into its deps. If a contradiction is found, it raises a ResolutionImpossible error (the new resolver in pip≥23.2 can backtrack, older pip would error immediately or install an incompatible set silently). Installation: pip downloads the wheel (.whl) file, which is a ZIP containing pre-compiled code and a RECORD file listing all installed files. It extracts them into site-packages/.

conda Internals: SAT Solver + Binary Packages

conda environments store a complete Python installation (not a symlink like venv). Each env in ~/.conda/envs/myenv/ has its own bin/python binary, so you can have Python 3.8 and 3.11 simultaneously. conda's resolver (libmamba since 2022) translates the version constraints into a Boolean Satisfiability (SAT) problem and finds a globally consistent solution across all channels. Critically, conda packages can include C shared libraries — a cudatoolkit package literally ships libcudart.so. This is why conda is preferred for deep learning pipelines that need CUDA/MKL without compilation.

poetry Internals: PubGrub + Lockfile

poetry uses the PubGrub algorithm (originally from Dart's pub). It maintains a set of "incompatibilities" — constraints that cannot simultaneously be true. As it selects versions, it derives new incompatibilities from the transitive dependency graph. When a conflict is found, it backtracks minimally by resolving the incompatibility, then resumes. This is more efficient than naive SAT because it prunes the search space early. The result is written to poetry.lock with exact versions, hashes, and the full transitive dependency graph.

⚠️ Common Gotcha

requirements.txt lists direct dependencies with loose version pins (numpy>=1.20). Without a lockfile, running pip install -r requirements.txt six months later may install a newer numpy that breaks your code. Always pair requirements.txt with pip freeze > requirements-frozen.txt or use poetry/pip-tools for proper lockfiles.

The Version-Solving Problem & Lockfiles
▼

Formal Statement of the Version-Solving Problem

Let \(\mathcal{P} = \{p_1, p_2, \ldots, p_n\}\) be the set of packages. Each package \(p_i\) has an ordered set of available versions \(V_i = \{v_{i,1} \prec v_{i,2} \prec \cdots \prec v_{i,k_i}\}\). Each version \(v_{i,j}\) carries a set of constraints \(C_{i,j} = \{(p_\ell, R_{\ell})\}\) specifying required version ranges \(R_\ell\) for dependency packages. The solver must find an assignment:

$$A: \mathcal{P} \to V \quad \text{s.t.} \quad \forall p_i, \forall (p_\ell, R_\ell) \in C_{i, A(p_i)}: A(p_\ell) \in R_\ell$$

This is equivalent to constraint satisfaction. In the general case (arbitrary number of packages with arbitrary constraints), this problem is NP-complete — reducible from 3-SAT. In practice, the constraint graph is sparse (most packages depend on few others) so solvers are efficient.

Version Specifiers (PEP 440)

Python's versioning standard (PEP 440) defines a total ordering on version strings. The constraint operators form a lattice:

$$R = \{==, !=, \geq, \leq, \gt, \lt, \sim=, ===\}$$

The compatible release operator \(\sim=2.5\) means \(\geq 2.5, == 2.*\) (same major). The intersection of constraints forms the acceptable range:

$$\text{acceptable}(p) = \bigcap_{c_i \in \text{constraints}(p)} \{v \in V_p : v \text{ satisfies } c_i\}$$

If this intersection is empty, the dependency is unsatisfiable.

Lockfiles: Mathematical Reproducibility

A lockfile records the exact resolved assignment \(A^*\) plus a cryptographic hash of each package's distribution file. For pip-tools (pip-compile):

$$\text{lockfile} = \{(p_i, A^*(p_i), \text{sha256}(\text{wheel}_{p_i, A^*(p_i)}))\}_{p_i \in \mathcal{P}}$$

Installing from a lockfile is deterministic: the installer downloads the exact wheel file and verifies its SHA-256 hash before extraction. This guarantees bit-for-bit identical environments across machines, CI servers, and time.

📜 Key Formula

The satisfiability condition for a full dependency graph: a valid environment exists iff the constraint hypergraph has a consistent coloring — one version per package satisfying all pairwise constraints. Equivalently: \(\exists A \text{ s.t. } \forall (p_i \to p_j, R): A(p_j) \in R\).

Semantic Versioning and the Resolution Space

Under Semantic Versioning (SemVer), \(MAJOR.MINOR.PATCH\): PATCH changes are bug-fixes (backward-compatible); MINOR adds features (backward-compatible); MAJOR is breaking. The constraint \(\geq 1.2.0, <2.0.0\) accepts any \(1.x.y\) with \(x \geq 2\) or \(x = 2, y \geq 0\). pip's ~=1.2.0 means \(\geq 1.2.0, == 1.2.*\) (only patch updates).

⚠️ SemVer in Practice

Python packages often violate SemVer — a "minor" version bump may break APIs. This is why lockfiles matter: even if SemVer says two versions are compatible, your actual code may not be. Never rely on SemVer alone for reproducibility; always lock exact versions in production/research.

🎯 Decision Guide

Need CUDA/GPU libraries or non-Python deps? → conda (or mamba for speed).
Pure Python library or web app with a team? → poetry (best DX, reproducibility).
Simple script or teaching? → pip + venv (built-in, universal).
Existing conda env but need pip packages? → conda activate, then pip install (careful with mixing!).

🚫 Mixing pip and conda

Installing pip packages into a conda env can break conda's dependency tracking. conda doesn't know about pip-installed packages, so subsequent conda install commands may override or conflict with pip-installed ones. If you must mix: install conda packages first, then pip packages last, and never run conda install after pip install in the same env.

Key Takeaways & Interview Tips
▼

Interview Q&A

Q: What's the difference between pip and conda?
A: pip only installs Python packages from PyPI; conda installs binary packages (including C libraries like CUDA) from Anaconda channels. conda also manages Python versions per environment, while pip requires a pre-existing Python install and a separate tool (venv/virtualenv) for environment isolation.

Q: What is a lockfile and why does it matter for reproducibility?
A: A lockfile (e.g., poetry.lock, pip freeze output, conda-lock.yml) records the exact version AND cryptographic hash of every package in the resolved dependency graph. Without it, pip install -r requirements.txt run six months later may install different patch versions that break your code. With a lockfile, you get bit-for-bit identical environments across machines and time.

Q: What is dependency hell and how do virtual environments help?
A: Dependency hell occurs when two projects need incompatible versions of the same package. Virtual environments create isolated site-packages directories per project, so each project has its own copy of packages at the required version. They don't magically resolve version conflicts within a single project — that's the resolver's job.

Q: (Hard) Why is version solving NP-complete?
A: Version solving can encode 3-SAT: each package-version selection is a boolean variable, and version constraints are clauses. A valid assignment satisfying all constraints is a satisfying assignment for the SAT instance. In practice, package graphs are sparse so resolution is fast, but adversarial cases (deeply nested conflicting deps) can cause exponential backtracking.

🔎 Quick Reference

python -m venv .venv && source .venv/bin/activate — create & activate venv
pip install -r requirements.txt — install from loose pins
pip freeze > requirements-frozen.txt — capture exact versions
poetry add numpy — add dep + resolve + update lock
poetry install --sync — install exactly what's in poetry.lock
conda create -n myenv python=3.11 numpy cuda-toolkit — full binary env
mamba install ... — same as conda, 10-100x faster resolver
