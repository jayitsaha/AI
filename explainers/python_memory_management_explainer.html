1
Understanding Python Memory Management
▼

What is it? Every Python object lives in memory. CPython (the standard Python interpreter) tracks how many variables point to each object using a counter called the reference count. When nothing points to an object anymore (count hits zero), CPython immediately frees that memory — no pause, no delay. This is the primary memory management strategy.

The problem: Reference counting alone cannot free two objects that point to each other (a "cycle"). Even with no external references, each keeps the other's count above zero. CPython therefore adds a second mechanism: a cyclic garbage collector that periodically hunts and frees these cycles.

Analogy: Imagine a library book has a checkout counter. Each person who borrows it increments a tally; returning it decrements. When the tally hits zero the book goes back to the shelf immediately. But if two people simultaneously list each other as "holding" the book (a bureaucratic loop), the tally never reaches zero. A librarian must then run a manual audit — that's the GC.

💡 If you remember one thing

CPython uses reference counting as the primary mechanism — objects are freed immediately when their count reaches 0. A secondary generational cyclic GC handles the minority case of cycles. Weak references point to objects without incrementing the count, intentionally allowing them to die.

2
How CPython Memory Works Internally
▼

The PyObject Header

Every CPython object starts with a C struct that contains (at minimum) two fields: ob_refcnt (the reference count) and ob_type (pointer to the type object). When you write x = [1, 2, 3], CPython allocates a PyListObject on the heap and sets ob_refcnt = 1. The name x is a pointer in the local namespace dictionary to that address.

🔑 Reference Count Rules

Incremented by: assigning to a new variable, passing as function argument, appending to a container, binding to an attribute.
Decremented by: del statement, variable going out of scope, reassigning a variable, removing from a container.
When count → 0: tp_dealloc is called immediately (synchronous, not deferred).

The Cycle Problem

Consider two Node objects: a.ref = b and b.ref = a. After del a, b, the external refcount of each drops to 1 (from the cross-references), not to 0. Neither object ever frees. This memory leak cannot be handled by reference counting alone.

The Generational Cyclic GC

CPython maintains three "generations" of container objects (lists, dicts, sets, user classes — primitives like ints/strings cannot form cycles). Objects promoted through generations: they start in generation 0 and survive to generation 1 then 2. GC runs when the generation's object count crosses a threshold (defaults: gen0=700, gen1=10 collections, gen2=10 collections). The algorithm is a variant of mark-and-sweep: compute the number of internal references, subtract from the refcount; if the result is 0 the object is unreachable and part of a cycle.

Weak References

A weakref.ref(obj) creates a reference that does NOT increment ob_refcnt. It registers a callback with the object's __weakref__ slot. When the real refcount hits 0 and the object is freed, all weak references to it become None automatically. This is used for caches (e.g., weakref.WeakValueDictionary) that should not prevent garbage collection of cached values.

⚠️ CPython-Only Guarantee

Immediate deallocation on ob_refcnt → 0 is a CPython implementation detail. PyPy, Jython, and GraalPy use different GC strategies. Code that relies on __del__ being called at a precise time will behave differently on other runtimes.

3
The Algorithms — Reference Counting & Cycle Detection
▼

Reference Counting Invariant

For any live object \(O\), CPython maintains the invariant:

$$\texttt{ob\_refcnt}(O) = \#\{\text{pointers to } O \text{ from stack frames, globals, containers, attributes}\}$$

When a pointer is created, CPython calls Py_INCREF(op) which executes op->ob_refcnt++. When a pointer is destroyed, Py_DECREF(op) executes:

$$\texttt{Py\_DECREF}(op) \equiv \begin{cases} op\text{->}ob\_refcnt{-}{-} & \text{if } ob\_refcnt > 1 \\ \text{call } tp\_dealloc(op) & \text{if } ob\_refcnt = 1 \end{cases}$$

Cycle Detection Algorithm (Simplified)

For each container object in the generation, the GC computes effective refcount:

$$\texttt{gc\_refs}(O) = \texttt{ob\_refcnt}(O) - \#\{\text{references to } O \text{ from within the same GC generation}\}$$

Objects with \(\texttt{gc\_refs} = 0\) after this subtraction are unreachable — all references to them come from within the cycle. The GC calls their tp_dealloc and breaks the cycle. Objects with \(\texttt{gc\_refs} > 0\) are reachable and are promoted to the next generation.

Complexity

  • Reference counting: \(O(1)\) per pointer create/destroy. Zero pause time. Overhead: one atomic increment/decrement per operation.
  • Cyclic GC: \(O(n)\) per collection where \(n\) = number of container objects in the generation. GC pauses execution (stop-the-world) during collection.
  • Weak references: \(O(1)\) to create; \(O(k)\) to notify \(k\) callbacks when the object dies.
📐 Key Insight: Why Generational?

The generational hypothesis: most objects die young. Scanning only generation 0 (700 newly created objects) is cheap and catches most garbage. Long-lived objects (generation 2) are rarely garbage. The three-generation design makes GC pauses short in practice.

When to Care About This in Practice

  • Finalizers (__del__): Objects with __del__ methods that form cycles are placed in gc.garbage (uncollectable in Python ≤ 3.3, collectable but warned in 3.4+).
  • Caches: Use weakref.WeakValueDictionary for caches so entries expire when no external reference holds the value.
  • Large object graphs: Explicitly break cycles with del obj.parent or use __slots__ (slotted classes can still cycle but GC handles them).
  • GC tuning: gc.set_threshold(700, 10, 10) — lower gen0 threshold = more frequent collection of short-lived garbage; raise it to reduce GC overhead for throughput-intensive code.
  • Disabling GC: gc.disable() for micro-benchmarking, or in web servers where request handlers create no cycles.
🔴 Common Bug: Accidental Cycle via Closure

A closure that captures self in a method assigned to self.callback creates a cycle: self → callback → cell → self. Use weakref.ref(self) inside the closure, or clean up in __del__.

6
Interview Deep-Dive
▼

Q1 (Easy): How does Python manage memory?

CPython uses reference counting as the primary mechanism. Every object stores ob_refcnt. Each new reference increments it; each reference dropped decrements it. When it reaches 0, the object is immediately deallocated. A secondary cyclic garbage collector handles reference cycles (two objects pointing to each other whose external refcount would never reach 0).

Q2 (Medium): What is the GIL and how does it relate to reference counting?

The Global Interpreter Lock (GIL) is a mutex that ensures only one thread executes Python bytecode at a time. Its original purpose was to make reference counting thread-safe without per-object locks. Without the GIL, two threads doing Py_INCREF/Py_DECREF concurrently could corrupt the count (race condition). Python 3.13+ introduces experimental free-threading (no-GIL mode) which replaces simple ob_refcnt with per-object biased reference counting.

Q3 (Medium): What is a reference cycle? Give a code example.

A cycle exists when object A references B, and B references A (directly or indirectly). Neither can reach ob_refcnt = 0 from reference counting alone. Example: a = []; b = [a]; a.append(b). After del a, b, both list objects still have refcount 1 from each other's reference.

Q4 (Hard): How does CPython's cyclic GC detect unreachable cycles?

The GC algorithm works in two phases: (1) For every container object in the generation, temporarily subtract the internal reference count (references from other objects in the same generation). This gives the "effective external refcount." (2) Any object whose effective external refcount is 0 is unreachable — it's part of a cycle with no external roots. The GC calls tp_dealloc for these and clears the cycle. Objects surviving this are promoted to the next generation. The algorithm is \(O(n)\) where \(n\) is the number of containers in the generation.

Q5 (Expert): When would you use weakref in production?

Three patterns: (1) Cache without prolonging lifetime — weakref.WeakValueDictionary for an object cache; entries evaporate when the object has no other owner. (2) Observer/event pattern — listeners stored as weak references so they can be GC'd without explicitly unregistering. (3) Break cycles in large object graphs — parent-to-child strong references, child-to-parent weak references (common in tree structures). Also note: not all objects support weak references — a class must have a __weakref__ slot (automatically added for user-defined classes, but not for bare object(), built-in types, or slotted classes unless explicitly added).

💡 Interview Follow-up Trap

"Is Python garbage collected?" Yes — at two levels. Most developers think only of the cyclic GC, but the primary mechanism is reference counting, which is not traditionally called "garbage collection." Showing you know both and their interaction is the senior-level answer.
