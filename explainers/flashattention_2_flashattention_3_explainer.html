Understanding FlashAttention-2 & -3
▼

What is it? FlashAttention (v1) already solved the memory-bandwidth problem of self-attention: instead of writing the full N×N attention matrix to slow GPU memory (HBM), it processes attention in small tiles that fit in fast on-chip SRAM, using an "online softmax" trick to get the exact same output. FlashAttention-2 and FlashAttention-3 do not change that math at all — they change how the tiled work is scheduled across the GPU's streaming multiprocessors (SMs) and warps, so the hardware's tensor cores stay busy instead of idling.

Analogy: Picture a restaurant kitchen. FlashAttention-1 has cooks (warps) who must repeatedly stop and reconcile a shared running tally with each other — lots of chatter, and if there aren't many separate orders (long sequence, few heads/batches) most cooks stand idle. FlashAttention-2 reorganizes so each cook owns one dish start-to-finish and never needs to sync with anyone else — and dishes are handed out per-seat (sequence position) rather than per-table (batch), so there's always enough independent work to keep every cook busy. FlashAttention-3 goes further: it hires dedicated "runners" who only fetch ingredients (async memory loads) while the cooks only cook (matmuls), overlapping the two — and adds a fast, slightly-lower-precision cooking mode (FP8) for when exact precision isn't required.

One-sentence summary: FA2 improves GPU work partitioning (loop order + warp assignment) to raise utilization from ~25-40% to ~50-73% of peak FLOPs; FA3 adds Hopper-specific asynchrony (warp specialization, GEMM/softmax overlap) and FP8 to push utilization to ~75% (FP16) and beyond with FP8.

💡 If you remember one thing

FA2 and FA3 compute mathematically identical (FP16/BF16) attention output to FA1 — token for token. The speedups come entirely from systems engineering: fewer non-matmul FLOPs, parallelizing across the sequence-length dimension, and overlapping memory transfer with compute.

How It Works Internally
▼

FlashAttention-1's bottleneck

FA1's kernel loops with KV-blocks on the outer loop and Q-blocks on the inner loop, inside a thread block that owns a fixed (batch, head) pair. Because every Q-block is revisited on every outer KV iteration, the running statistics \(m_i, l_i, O_i\) for all Q-blocks must stay resident simultaneously, and within a block the KV dimension is split across 4 warps — each warp holds only a partial score/output for its KV slice, so the warps must synchronize and combine partial sums through shared memory before moving on. Parallelism is limited to grid = batch × heads, which starves the GPU when sequences are long but batch×heads is small (exactly the long-context LLM inference regime).

FlashAttention-2: swap the loop, split by Q not KV

Loop reorder. FA2 swaps the loop order: the outer loop is now over Q-blocks, and each thread block in the grid owns one Q-block for its entire lifetime, looping over all KV-blocks internally and writing its output exactly once at the end. The grid dimension becomes (Q-blocks × batch × heads) — parallelism now scales with sequence length too, not just batch size.

Warp reassignment. Within a thread block, FA2 splits the Q rows across the 4 warps (instead of KV columns). Each warp owns a private slice of Q rows and independently streams through every KV-block, maintaining its own \(m,l,O\) — no cross-warp reduction is ever needed, only a shared read of K/V tiles loaded once into shared memory.

Causal skip. For causal (autoregressive) masking, FA2 also skips KV-blocks entirely above the diagonal — roughly halving the work for causal LLM attention.

FlashAttention-3: asynchrony + FP8 on Hopper

FA3 targets Hopper (H100/H200) hardware features directly:

  • Warp-group specialization. Warps are split into producer warp-groups, which issue asynchronous TMA (Tensor Memory Accelerator) copies of the next K/V tile from HBM into shared memory, and consumer warp-groups, which run the WGMMA matmul + softmax on the current tile — forming a software pipeline where memory fetches for tile i+1 overlap with compute on tile i.
  • GEMM/softmax "ping-pong". \(\exp(\cdot)\) runs on the Special Function Unit, not the tensor cores, so naively it stalls the tensor cores. FA3 interleaves two concurrent consumer warp-groups so that one group's softmax overlaps with the other group's WGMMA matmul — tensor cores are never idle waiting on the SFU.
  • FP8 low precision. Q and K (optionally P and V) are quantized to FP8 (e4m3) per tile, doubling tensor-core throughput on Hopper. Per-tile scale factors and an "incoherent processing" step (multiplying by a random orthogonal/Hadamard matrix before quantizing) spread outlier magnitude across dimensions, cutting quantization error roughly 2.6× versus naive per-tensor FP8.
🔑 Design decision: why swap the loop instead of just adding more warps?

More warps only help if there is independent work to hand them. Swapping the loop order creates one independent unit of work per Q-tile, which the GPU's grid scheduler can spread across every SM — this is precisely what matters when batch×heads is too small to saturate the chip (a single long prompt, few attention heads), which is the dominant regime in modern LLM inference and training on long context.

Why It Works — The Math
▼

Online (tiled) softmax recurrence

Split \(K,V\) into blocks \(K_j, V_j\) of size \(B_c\). For a Q-block with running max \(m_i\), running sum \(l_i\), and running (unnormalized) output \(O_i\), processing block \(j\) updates:

$$S_i^{(j)} = \frac{Q_i K_j^\top}{\sqrt{d}}, \quad m_i^{(j)} = \max\!\big(m_i^{(j-1)}, \text{rowmax}(S_i^{(j)})\big)$$
$$P_i^{(j)} = \exp\!\big(S_i^{(j)} - m_i^{(j)}\big), \quad \alpha^{(j)} = \exp\!\big(m_i^{(j-1)} - m_i^{(j)}\big)$$
$$l_i^{(j)} = \alpha^{(j)} l_i^{(j-1)} + \text{rowsum}(P_i^{(j)}), \quad O_i^{(j)} = \alpha^{(j)} O_i^{(j-1)} + P_i^{(j)} V_j$$

After the last KV-block \(T_c\), normalizing once gives the exact softmax output: \(O_i = \text{diag}(l_i^{(T_c)})^{-1} O_i^{(T_c)}\). This telescoping rescale is mathematically identical to computing softmax over the full row at once — no approximation.

IO complexity — the actual bottleneck

Standard attention materializes \(S,P \in \mathbb{R}^{N\times N}\), costing \(\Theta(N^2)\) HBM reads/writes. Tiling with SRAM budget \(M\) reduces this to \(\Theta(N^2 d^2 M^{-1})\) HBM accesses (Dao et al., 2022) — and this is provably optimal up to a constant factor for all \(M \in [d, Nd]\). Extra memory drops from \(O(N^2)\) to \(O(N)\) (just the running \(m,l,O\) vectors).

Non-matmul FLOPs — where FA2/FA3 actually win

The matmul FLOPs (\(QK^\top\) and \(PV\)) total \(4N^2d\) regardless of implementation — that part is fixed. But \(\max\), \(\exp\), rescale, and divide run on the CUDA-core / SFU path, which on an H100 is roughly two orders of magnitude slower per-FLOP than the tensor-core path used for matmuls. FA2's loop swap removes redundant rescaling of \(O\) across revisited Q-blocks, cutting non-matmul FLOPs roughly in half versus FA1. FA3's ping-pong scheduling goes further: it doesn't reduce non-matmul FLOP count, it overlaps that work in time with tensor-core matmuls so it costs close to zero extra wall-clock.

⚠️ Common misconception

"FlashAttention approximates attention." In FP16/BF16 it does not — the output is exact softmax attention to floating-point precision, just computed with a different memory access pattern. FP8 mode in FA3 is the one place a genuine speed/accuracy trade-off is made explicitly, not an inherent property of the tiling algorithm.

Key Takeaways
▼

When to use which:

  • FlashAttention-2 — default choice on Ampere/Ada GPUs (A100, RTX 30/40-series); ~2× faster than FA1, reaching up to ~230 TFLOPs/s (~73% of A100's 312 TFLOPs FP16 peak) on favorable shapes.
  • FlashAttention-3 — requires Hopper (H100/H200) for TMA + WGMMA + native FP8 tensor cores; ~1.5-2× faster than FA2 on the same hardware, reaching ~740 TFLOPs/s (~75% of FP16 peak) and up to ~1.2 PFLOPs/s in FP8.
  • Both are drop-in kernels used under the hood by PyTorch's scaled_dot_product_attention, vLLM, xFormers, and most LLM training/serving stacks — you rarely call them directly.

When NOT to reach for FP8 mode: tasks sensitive to attention-score precision (e.g. some long-context retrieval or fine-grained reasoning benchmarks) may see accuracy regressions; FA3's FP16/BF16 path is still exact and usually the safer default.

💡 Hierarchy

FA1 (tiling + online softmax, exact, batch-parallel only) ⊂ FA2 (+ loop swap, Q-parallel warps, causal skip) ⊂ FA3 (+ warp specialization, async TMA pipelines, GEMM/softmax overlap, optional FP8). Each layer keeps the previous one's math exact and only improves scheduling — except FP8, which is an explicit precision trade-off.

Code Trace
▼
import numpy as np
# Q: one Q-tile (Br=4 rows), K/V: full sequence split into 2 KV-tiles (Bc=4)
scale = 1.0 / np.sqrt(d) # d = 4
m = np.full(Br, -np.inf) # running row max
l = np.zeros(Br) # running row sum
O = np.zeros((Br, d)) # running (unnormalized) output
for j, (Kj, Vj) in enumerate([(K0, V0), (K1, V1)]): # loop over KV-tiles (FA2: inner loop)
S = scale * (Q @ Kj.T) # (Br, Bc) tile score
m_new = np.maximum(m, S.max(axis=1)) # update running max
alpha = np.exp(m - m_new) # rescale factor for old stats
P = np.exp(S - m_new[:, None]) # unnormalized weights
l = alpha * l + P.sum(axis=1) # update running sum
O = alpha[:, None] * O + P @ Vj # update running output
m = m_new
O = O / l[:, None] # single final normalize — exact softmax(QK^T/sqrt(d))@V
