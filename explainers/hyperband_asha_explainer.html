Understanding Hyperband & ASHA
▼

What is it? Hyperband is a hyperparameter search algorithm that treats tuning as a resource-allocation problem: instead of training every candidate config to completion, it gives everyone a small budget first, ruthlessly eliminates the worst performers, and reinvests the freed compute into training the survivors longer. ASHA is the asynchronous, cluster-scale version of the same idea.

Analogy: A singing competition. Round 1 gives every contestant 30 seconds — obviously bad singers are cut immediately. Round 2 gives survivors 2 minutes. The finalists get a full song. Nobody wastes a full song's worth of judging time on someone who was clearly off-key. Hyperband runs several versions of this competition with different "how strict is round 1" settings so a slow-starter contestant never sinks the whole search. ASHA is the version where judges don't all wait for the slowest singer to finish before scoring — promotions happen the instant enough evidence exists.

💡 If you remember one thing

Successive Halving = train many configs cheaply, keep only the top \(1/\eta\), double their budget, repeat. Hyperband = run that tournament at several elimination-aggressiveness settings so you're never stuck with the wrong one. ASHA = run it with no synchronization barrier so it scales to hundreds of parallel workers.

How It Works Internally
▼

Successive Halving — The Inner Loop

Sample \(n\) configs, train all of them to budget \(r_{min}\), rank by validation metric, keep the top \(\lfloor n/\eta \rfloor\) (discard the rest permanently), multiply the survivors' budget by \(\eta\), and repeat until one config remains at max budget \(R\).

The n vs r Trade-off — Why Hyperband Exists

A single SH run must commit upfront to a point on the aggressiveness spectrum: large \(n\) with tiny \(r_{min}\) explores broadly but risks killing a slow-starting config; small \(n\) with large \(r_{min}\) is safe but explores narrowly. Hyperband removes this choice — it runs SH at every bracket \(s = s_{max}, \dots, 0\), each costing roughly the same total budget \(B\), and returns the best config found across all brackets.

ASHA — Removing the Synchronization Barrier

Synchronous SH/Hyperband can't advance a rung until every config in it finishes — one straggler stalls hundreds of idle workers. ASHA instead lets each worker promote a config the instant it finishes, if its metric ranks in the top \(1/\eta\) among everything reported at that rung so far. No global barrier, no idle workers.

🔑 Key Property

At every rung of Successive Halving, resource consumed \(n_i \cdot r_i\) is constant — equal to \(n \cdot r_{min}\). This is what turns an exponential full-training cost into a logarithmic one.

3
Why It Works — The Math
▼

The Budget Invariant

Let \(n_i = n\cdot\eta^{-i}\) configs remain at rung \(i\), each with budget \(r_i = r_{min}\cdot\eta^{i}\). Resource spent at rung \(i\):

$$n_i \cdot r_i = (n\cdot\eta^{-i})(r_{min}\cdot\eta^{i}) = n\cdot r_{min} \;=\; \text{const}$$

Independent of \(i\) — every rung costs the same, no matter how few configs remain.

Total Budget: Exponential → Logarithmic

The tournament stops at \(n_i=1\), i.e. after \(s+1 = \lfloor\log_\eta n\rfloor + 1\) rungs, giving:

$$B_{SH} = (s+1)\cdot n \cdot r_{min} = O(n\, r_{min}\log_\eta n) \;\ll\; B_{full} = n\cdot R$$

ASHA's Asynchronous Promotion Rule

A config finishing rung \(i\) with metric \(m\), given \(k\) prior reports at that rung, is promoted if:

$$\operatorname{rank}(m \mid m_1,\dots,m_k) \le \left\lceil \frac{k+1}{\eta}\right\rceil$$

A continuously-updated version of SH's exact top-\(1/\eta\) cut, computable the instant any single job finishes.

⚠️ Common Misconception

"SH/Hyperband/ASHA guarantee finding the globally best config." False — they assume low-budget rank correlates with high-budget rank. A config needing a long warm-up (e.g. LR warmup) can be eliminated before its quality shows. Hedging over brackets mitigates, but never eliminates, this risk.

Key Takeaways
▼

When to use:

  • Successive Halving alone — quick prototyping, single machine, cheap checkpoint/resume.
  • Hyperband — small cluster, want a hedge against a bad (n, r) choice, sync pauses are acceptable.
  • ASHA — large distributed clusters, heterogeneous job durations, production HPO platforms.

When NOT to use:

  • Cheap models where full training is already fast — checkpoint/rung bookkeeping isn't worth it.
  • Search spaces where early performance poorly predicts final performance (delayed-payoff curricula).
💡 Hierarchy

Successive Halving (one aggressiveness) ⊂ Hyperband (hedges over aggressiveness, synchronous) ⊂ ASHA (same hedge, but asynchronous — no idle workers). Each generalizes the previous by relaxing an assumption.

def successive_halving(sample_config, train_and_eval, n, r_min, R, eta=3):
configs = [sample_config() for _ in range(n)]
r = r_min
while True:
losses = [train_and_eval(cfg, r) for cfg in configs] # resume, don't restart
if len(configs) == 1 or r >= R:
best = argmin(losses); return configs[best], losses[best]
keep = max(1, len(configs) // eta) # top 1/eta survive
order = argsort(losses)
configs = [configs[i] for i in order[:keep]]
r = min(r * eta, R) # promote budget
def hyperband(sample_config, train_and_eval, R, eta=3):
s_max = floor(log(R, eta)); B = (s_max + 1) * R
results = []
for s in range(s_max, -1, -1): # aggressive -> conservative
n = ceil((B / R) * eta**s / (s + 1)); r_min = R * eta**(-s)
results.append(successive_halving(sample_config, train_and_eval, n, r_min, R, eta))
return min(results, key=lambda t: t[1]) # best across ALL brackets
def asha_report(rung_results, rung_idx, config_id, metric, eta=3):
reported = rung_results.setdefault(rung_idx, [])
reported.append((config_id, metric)); k = len(reported)
rank = sorted(m for _, m in reported).index(metric) + 1
return rank <= ceil(k / eta) # promote NOW, no waiting
