Python's control flow for errors: try/except/else/finally + the with-statement lifecycle
Intermediate Python Mastery Core Language Must Know
1
Understanding Exceptions & Context Managers
▼

What is an exception? An exception is Python's way of saying "something went wrong, and I don't know what to do." When code encounters an unexpected situation — dividing by zero, opening a missing file, calling a method on None — it raises an exception object and immediately stops executing. If no handler catches it, Python prints a traceback and terminates.

The four clauses: try marks the risky block. except catches and handles specific exception types. else runs only if no exception was raised. finally runs always — whether the try succeeded, failed, or even if there is a return inside the try.

What is a context manager? A context manager is an object that guarantees a setup and teardown pair: acquire a resource before the body runs, release it after — even if the body raises an exception. The with statement invokes this contract. Instead of scattering cleanup code across every possible exit path, you write it once in __exit__.

If you remember one thing

finally and __exit__ are both guaranteed cleanup mechanisms. finally is ad-hoc (attached to one try/except block). __exit__ is reusable, composable, and can suppress exceptions. Prefer context managers for any resource that has a matching acquire/release pair.

2
How It Works Internally
▼

Exception Propagation (the call stack)

Every active function call lives on the call stack as a frame. When an exception is raised inside a frame, Python searches that frame for a matching except clause. If none is found, the frame is popped and the search continues in the caller's frame. This "unwinding" continues up the stack until either a handler is found or the stack is exhausted (unhandled exception).

The exception object itself carries the traceback — a linked list of frame snapshots recording exactly where it was raised and how it propagated. You can inspect this with traceback module or sys.exc_info().

Control-Flow Semantics (precise order)

  1. Execute try body.
  2. If exception raised → jump to matching except (if any); then skip else.
  3. If no exception → skip all except clauses; run else body.
  4. Always run finally (even if there is a return inside try/except).
  5. If finally itself has a return, it overrides any pending exception — a notorious footgun.

The with-statement protocol

When Python encounters with expr as target:, it evaluates expr to get the context manager object, calls cm.__enter__(), and binds the return value to target. The body then executes. On exit (normal or exceptional), Python calls cm.__exit__(exc_type, exc_val, exc_tb). If __exit__ returns a truthy value, the exception is suppressed; otherwise it re-propagates.

Key Property

__exit__ is always called — even when the body raises. Returning True from __exit__ swallows the exception. Returning False (or None) lets it propagate. This is how contextlib.suppress is implemented.

Common Pitfall

A return inside finally silently discards any exception. Similarly, raising a new exception inside finally replaces the original — the original context is attached as __context__ but the traceback will show the new exception. Both are hard-to-debug traps.

3
Why It Works — Formal Semantics
▼

Exception Hierarchy

Python exceptions form a class hierarchy rooted at BaseException. The key sub-classes are:

$$\text{BaseException} \supset \text{Exception} \supset \text{RuntimeError}, \text{ValueError}, \text{OSError}, \ldots$$

except Exception catches everything user-facing. except BaseException also catches KeyboardInterrupt, SystemExit, and GeneratorExit — almost always wrong. Each except clause checks the raised exception's type with isinstance(exc, ExcType), so subclasses are caught by base-class handlers.

Exception Chaining

Python 3 distinguishes two kinds of chaining:

  • Implicit chaining (__context__): when a new exception is raised while another is being handled, the original is stored in exc.__context__.
  • Explicit chaining (__cause__): raise NewError(...) from original — sets __cause__ and the traceback says "The above exception was the direct cause of..."

To suppress the chain entirely (e.g., when converting to a cleaner API error): raise AppError(...) from None.

Context Manager as RAII

The with-statement is Python's version of C++ RAII (Resource Acquisition Is Initialization). The invariant: if __enter__ returns without exception, __exit__ will be called exactly once. This is a guarantee, not a convention. It makes resource leak impossible as long as the context manager is implemented correctly.

$$\text{Invariant: } \text{enter}() \text{ succeeds} \implies \text{exit}() \text{ called exactly once}$$
Suppress semantics

If __exit__ returns \(\text{True}\), the exception is swallowed and execution continues after the with block. If it returns \(\text{False}\) (or None), the exception re-propagates exactly as if the with block were not there.

Key Takeaways & Comparison
▼

When to use try/except

  • Catching specific, recoverable errors — always name the exception type (except ValueError), never bare except:.
  • Converting low-level errors to domain errors (raise AppError from db_error).
  • Implementing retry logic or fallbacks.

When to use context managers (with)

  • Any resource with a matching open/close or acquire/release: files, locks, database connections, network sockets, temporary directories.
  • Temporarily changing global state (decimal precision, warnings filter, mocked objects in tests).
  • Whenever you'd otherwise need a try/finally just to call cleanup code.

Comparison: three cleanup strategies

StrategySyntaxProsCons
try/finallytry: ... finally: cleanup()Always runs cleanup, explicitVerbose, not reusable
Context Manager (class)with resource as r: ...Reusable, composable, can suppressBoilerplate (__enter__/__exit__)
contextlib.contextmanager@contextmanager def f(): yieldMinimal code, generator-basedSlightly harder error handling
Decision rule

Use with for reusable resource pairs. Use try/finally for one-off cleanup inside a function. Avoid bare except: — it catches KeyboardInterrupt and SystemExit, making your program impossible to kill. Use except Exception: at most, or better, name the exact type.

Code Reference
▼

Complete pattern reference

# ── Exception handling ──────────────────────────────────────────
try:
result = risky_operation() # 1. Try the risky code
except ZeroDivisionError as e: # 2a. Catch specific type
handle_zero_div(e)
except (ValueError, TypeError) as e: # 2b. Catch multiple types
handle_value_or_type(e)
except Exception as e: # 2c. Catch all user exceptions
log_and_reraise(e) # (avoid bare except:)
else: # 3. Runs ONLY if no exception
process(result)
finally: # 4. ALWAYS runs
cleanup()
# ── Custom exception with chaining ──────────────────────────────
class AppError(Exception):
def __init__(self, msg, code=None):
super().__init__(msg)
self.code = code
try:
db.connect()
except OSError as e:
raise AppError("DB unavailable", code=503) from e # explicit chain
# ── Context manager (class) ──────────────────────────────────────
class ManagedFile:
def __init__(self, path, mode='r'):
self.path, self.mode = path, mode
def __enter__(self):
self.f = open(self.path, self.mode) # acquire
return self.f # returned as `as` target
def __exit__(self, exc_type, exc_val, exc_tb):
self.f.close() # release (always)
return False # don't suppress exceptions
with ManagedFile("data.txt") as f:
data = f.read()
# ── Context manager (generator) ─────────────────────────────────
from contextlib import contextmanager, suppress
@contextmanager
def managed_file(path):
f = open(path)
try:
yield f # __enter__ returns here
finally:
f.close() # __exit__ equivalent
with suppress(FileNotFoundError): # contextlib.suppress: __exit__ returns True
os.remove("maybe_exists.txt")
