Understanding Mixed Precision Training
▼

What is it? Neural networks are normally trained with every number — weights, activations, gradients — stored as 32-bit floats (FP32). Mixed precision training does most of the arithmetic in a narrower 16-bit format (FP16 or BF16) while keeping a full-precision FP32 "master copy" of the weights for updates. The result: roughly 2× less memory traffic, 2–8× faster matrix multiplies on modern GPU tensor cores, and (if done correctly) nearly identical final accuracy.

Analogy: Imagine doing arithmetic with a pocket calculator that only shows 3 significant digits instead of 7. Most calculations are fine — you just round a bit. But if a number is tiny (like 0.00000004), a 3-digit display might round it straight down to 0.000, and that value silently vanishes from your calculation. That's exactly what happens to small gradients in FP16 — unless you rescale them first so they land in the calculator's visible range.

💡 If you remember one thing

Mixed precision = compute fast in 16-bit, but accumulate and update weights in 32-bit. FP16's narrow exponent range makes small gradients underflow to zero, so training multiplies the loss by a scale factor \(S\) before backprop (loss scaling) and divides the gradients by \(S\) back out before the optimizer step. BF16 has FP32's exponent range, so this trick is usually unnecessary.

How It Works Internally
▼

Three float formats, three trade-offs

An IEEE-754-style float is split into a sign bit, exponent bits (control range — how big/small a number can be) and mantissa bits (control precision — how many significant digits). FP32 uses 1+8+23 bits. FP16 uses 1+5+10: five fewer exponent bits shrinks the representable range to roughly \([6\times10^{-5},\ 65504]\), so anything smaller underflows to zero and anything larger overflows to infinity. BF16 uses 1+8+7: it keeps FP32's full 8-bit exponent (same range, roughly \([10^{-38},\ 3\times10^{38}]\)) but sacrifices mantissa bits, so it is coarser (only ~2-3 decimal digits of precision) yet essentially immune to the over/underflow that plagues FP16.

The master-weights pattern

Weight updates are the sum of many small gradient-times-learning-rate terms. If weights themselves were stored in FP16, updates smaller than the mantissa's resolution would round away to nothing — training would stall. So mixed precision keeps an FP32 master copy of every weight. Each step: (1) cast weights down to FP16/BF16, (2) run the forward and backward pass in low precision (fast matmuls), (3) cast gradients back up to FP32, (4) apply the optimizer update to the FP32 master weights. Only the compute-heavy matmuls/convolutions run in low precision; reductions like softmax and batch-norm statistics are usually kept in FP32 for stability.

Design decision: why not just use BF16 everywhere?

BF16 avoids loss scaling entirely, which is operationally simpler — this is why TPUs and newer GPU training recipes (e.g. most LLM pretraining) default to BF16. But its 7-bit mantissa gives coarser rounding than FP16's 10-bit mantissa, which can matter for gradient accumulation over long sequences or very deep networks. FP16 is more numerically precise per bit spent, provided you manage its range with loss scaling — which is why it remains common, especially on older GPUs (V100-era) that support FP16 tensor cores but not BF16.

🔑 Key Property

The exponent bits set the range (over/underflow risk); the mantissa bits set the precision (rounding error). FP16 trades range for precision relative to FP32; BF16 trades precision for range. Loss scaling is a range-management trick — it does nothing to fix precision loss.

3
Why It Works — The Math
▼

Loss scaling as a chain-rule trick

Let \(L\) be the true loss and \(S > 0\) a scalar scale factor. Backprop through a scaled loss \(L' = S \cdot L\) multiplies every gradient in the graph by the same constant \(S\), by linearity of the chain rule:

$$\frac{\partial L'}{\partial w} = S \cdot \frac{\partial L}{\partial w} \quad \text{for every weight } w$$

Because every gradient gets multiplied by the same \(S\), this is a pure re-scaling — it does not change the direction of the gradient, only its magnitude. If we pick \(S\) large enough to shift small gradients up into FP16's representable range before they are rounded, none of them silently flush to zero. After the backward pass we must divide back out before the optimizer step (typically after copying gradients to FP32):

$$\hat{g}_w = \frac{1}{S}\frac{\partial L'}{\partial w} \approx \frac{\partial L}{\partial w}$$

Dynamic loss scaling algorithm

Picking a fixed \(S\) is fragile — too small and gradients still underflow, too large and gradients overflow to \(\pm\infty\)/NaN. Dynamic loss scaling adapts \(S\) automatically:

$$S_{t+1} = \begin{cases} S_t / \beta & \text{if any gradient is Inf/NaN this step (skip the update)} \\ S_t \cdot \gamma & \text{if } N \text{ consecutive steps had no Inf/NaN} \\ S_t & \text{otherwise} \end{cases}$$

Typical defaults (PyTorch AMP): start \(S_0 = 2^{16}\), growth factor \(\gamma = 2\), backoff factor \(\beta = 2\), growth interval \(N = 2000\) steps. This is a hill-climbing search: keep pushing \(S\) upward to catch more underflowing gradients, and snap back down the instant an overflow is detected, discarding that step's (corrupted) update.

⚠️ Common Misconception

"Loss scaling fixes precision loss." It does not — it only fixes range problems (underflow to zero / overflow to Inf). The 10-bit FP16 mantissa still rounds every value to ~3 significant decimal digits regardless of \(S\). This is exactly why BF16, which shares FP32's exponent range, mostly sidesteps loss scaling: its problem was never range, so there's rarely anything to rescale.

Key Takeaways
▼

When to use mixed precision:

  • Training on GPUs with tensor cores (V100/A100/H100) — near-free 2-3× speedup on matmul-heavy models
  • Large models where activation memory is the bottleneck — FP16/BF16 halves it
  • Modern LLM/vision pretraining — BF16 is close to the default choice today

When to be careful:

  • FP16 on GPUs without native BF16 support — you need dynamic loss scaling, not optional
  • Very deep or recurrent nets with long gradient chains — precision loss from BF16's 7-bit mantissa can compound; consider FP16 + scaling or full FP32 for the most sensitive ops (e.g. loss/softmax)
  • Custom losses that already produce very large or very small values — inspect the gradient histogram before trusting default scale settings
💡 Rule of Thumb

FP32 everywhere = safe but slow. FP16 + master weights + dynamic loss scaling = fast, needs range management. BF16 + master weights = fast, range management usually unnecessary, slightly coarser precision. Frameworks like PyTorch (torch.cuda.amp) and DeepSpeed automate all of this — you rarely hand-roll the scaling loop yourself.

model = model.cuda() # FP32 master weights
opt = torch.optim.AdamW(model.parameters(), lr=3e-4)
scaler = torch.cuda.amp.GradScaler() # dynamic loss scaling
for x, y in loader:
opt.zero_grad()
with torch.autocast(device_type='cuda', dtype=torch.float16):
out = model(x) # forward runs in FP16
loss = loss_fn(out, y) # loss computed in FP32
scaled_loss = scaler.scale(loss) # L' = S * L
scaled_loss.backward() # grads scaled by S too
scaler.unscale_(opt) # g_hat = grad / S (FP32)
torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
scaler.step(opt) # skips step if Inf/NaN found
scaler.update() # grow/backoff S dynamically
