Weight Normalization

Decoupling weight direction from weight magnitude to speed up and stabilize optimization
Intermediate Deep Learning Optimization O(n) per weight vector
1
Understanding Weight Normalization
▼

What is it? Every trainable weight vector in a neural network layer has two separate jobs: it points in a direction (which combination of input features to respond to) and it has a magnitude (how strongly to respond). Ordinary weight vectors \(w\) tangle these two jobs into one set of numbers. Weight Normalization simply rewrites \(w\) as a unit-length direction \(v/\|v\|\) times a separate learnable scalar \(g\): \(w = g \cdot v / \|v\|\). Direction and scale become two independent knobs the optimizer can turn.

Analogy: Think of an arrow on a dartboard. Instead of controlling the arrow's tip position \((x, y)\) directly — where every correction accidentally changes both aim and power — you control aim (a unit vector \(\hat v\)) and throw strength (\(g\)) separately. Adjusting your aim no longer accidentally changes how hard you throw, and vice versa.

💡 If you remember one thing

Weight Normalization reparameterizes each weight vector as $$w = g\,\frac{v}{\|v\|}$$ so the optimizer learns direction (\(v\)) and magnitude (\(g\)) with separate, better-conditioned gradients — with none of BatchNorm's dependence on mini-batch statistics.

2
How It Works Internally
▼

The Problem: Why Was This Invented?

Before Weight Normalization (Salimans & Kingma, 2016), the dominant fix for slow/unstable training was Batch Normalization (Ioffe & Szegedy, 2015), which normalizes activations using mini-batch mean and variance. That works well but ties the model's behaviour to the statistics of whatever batch happens to be sampled — noisy with small batches, awkward for RNNs, GANs, and reinforcement learning where batches are small, correlated, or don't exist in the usual sense. WeightNorm asks: can we get similar optimization benefits by reparameterizing the weights themselves, with zero dependence on batch statistics?

The Reparameterization

Every weight vector \(w \in \mathbb{R}^n\) feeding a unit is rewritten using a new direction vector \(v \in \mathbb{R}^n\) and a scalar \(g \in \mathbb{R}\):

$$w = g\,\frac{v}{\|v\|_2}$$

At initialization, \(g\) is simply set to \(\|w\|\) and \(v\) to \(w\), so \(w\) is numerically unchanged — WeightNorm changes how gradients flow, not the initial function computed. From then on, \(g\) and \(v\) are trained by ordinary SGD/Adam like any other parameters; \(w\) is recomputed from them on every forward pass.

Design Decision: Why a Scalar \(g\) and Not Just Normalize?

Simply forcing \(\|w\|=1\) (pure normalization with no \(g\)) would throw away the network's ability to control activation scale — a real degree of freedom the model needs. Keeping \(g\) as a free scalar preserves full expressive power (the reparameterization is exact: any \(w\) is reachable) while still separating the "which direction" question from the "how big" question in the gradient.

Numerical Trace

Say \(v = [3, 4]\) so \(\|v\| = 5\), and \(g = 5\). Then \(\hat v = v/\|v\| = [0.6, 0.8]\) and \(w = g\hat v = [3, 4]\) — matches \(v\) exactly because \(g\) was chosen equal to \(\|v\|\). Now suppose training nudges \(g \to 6\) while \(v\) stays fixed: \(w = 6 \times [0.6, 0.8] = [3.6, 4.8]\) — pure rescaling along the same direction, no direction drift. That clean separation is the entire mechanism.

🔑 Key Property

The map \((g, v) \mapsto w\) is scale-invariant in \(v\): replacing \(v\) with \(\alpha v\) for any \(\alpha>0\) leaves \(w\) unchanged. This means gradient descent on \(v\) naturally moves orthogonal to \(v\) (pure rotation), while \(g\) alone controls magnitude — the two updates cannot fight each other the way they can in raw \(w\)-space.

3
Why It Works — The Math
▼

Deriving the Gradients

Let \(L\) be the loss and let \(g_w \equiv \nabla_w L\) be the gradient with respect to the ordinary weight vector (whatever backprop would normally hand you). Using the chain rule through \(w = g\, v/\|v\|\):

$$\nabla_g L = \frac{g_w \cdot v}{\|v\|} = g_w \cdot \hat v$$

The gradient on \(g\) is just the component of \(g_w\) that points along the current direction \(\hat v\) — a single scalar, cheap and well-scaled.

$$\nabla_v L = \frac{g}{\|v\|}\left(g_w - \frac{g_w \cdot v}{\|v\|^2}\,v\right) = \frac{g}{\|v\|}\Big(I - \hat v \hat v^\top\Big) g_w$$

The gradient on \(v\) is the component of \(g_w\) orthogonal to \(\hat v\) (via the projection matrix \(I - \hat v\hat v^\top\)), scaled by \(g/\|v\|\). Orthogonal-only updates mean moving \(v\) rotates the direction without directly re-scaling \(w\) — direction and magnitude genuinely decouple.

The Self-Stabilizing Property

Because \(\nabla_v L\) is scaled by \(g/\|v\|\), if \(\|v\|\) grows, the gradient on \(v\) automatically shrinks — for a fixed \(g_w\), doubling \(\|v\|\) halves \(\|\nabla_v L\|\). This is an automatic, per-parameter learning-rate decay with no scheduler and no batch statistics involved, exactly the stabilization effect the paper reports.

📐 Formula Box

$$w = g\frac{v}{\|v\|}, \qquad \nabla_g L = g_w\cdot\hat v, \qquad \nabla_v L = \frac{g}{\|v\|}(I-\hat v\hat v^\top)g_w$$

⚠️ Common Misconception

WeightNorm is not a normalization of activations like BatchNorm/LayerNorm — it never touches the data flowing through the network. It only reparameterizes how the weight tensor itself is represented and differentiated. The two techniques are complementary and were historically often combined with mean-only batch normalization for the best results.

Key Takeaways
▼

When to use WeightNorm:

  • Small or non-i.i.d. batches — RNNs, RL policy networks, GANs (batch statistics are unreliable or undefined)
  • You want BatchNorm-like optimization speedups without adding a batch-dependent op to the compute graph
  • Combined with a data-dependent init (paper's recipe) for a strong, batch-free warm start

When NOT to use:

  • Large-batch CNN image classification, where BatchNorm's regularizing noise and running statistics already work well
  • You need the implicit regularization effect of BatchNorm's batch noise — WeightNorm has weaker/no such effect
  • Modern transformer stacks — LayerNorm/RMSNorm dominate here since they normalize activations, not just weights
💡 Hierarchy

WeightNorm reparameterizes weights (no batch dependence) while BatchNorm/LayerNorm normalize activations. They solve the same symptom — slow, ill-conditioned optimization — from two different ends of the forward pass, and can be used together.

Code Trace
▼
import torch, torch.nn as nn
# ── From scratch: reparameterize one weight vector ──
class WeightNormLinear(nn.Module):
def __init__(self, in_f, out_f):
super().__init__()
v0 = torch.randn(out_f, in_f) * 0.05 # raw direction param
self.v = nn.Parameter(v0)
self.g = nn.Parameter(v0.norm(dim=1)) # init g = ||v|| (exact match)
self.bias = nn.Parameter(torch.zeros(out_f))
def forward(self, x):
v_hat = self.v / self.v.norm(dim=1, keepdim=True) # unit direction
w = self.g.unsqueeze(1) * v_hat # w = g * v/||v||
return x @ w.T + self.bias
# ── Production usage: torch.nn.utils.parametrizations ──
layer = nn.Linear(256, 256)
layer = torch.nn.utils.parametrizations.weight_norm(layer, name='weight', dim=0)
# layer.parametrizations.weight.original0 -> g (magnitude)
# layer.parametrizations.weight.original1 -> v (direction)
# ⚠️ Gotcha: g and v get separate entries in the optimizer / weight decay —
# applying weight decay to g shrinks magnitude only, decay on v shrinks
# direction noise without touching ||w|| the same way as decay on raw w.
