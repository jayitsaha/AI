Understanding ML Design Patterns
▼

What are they? Design patterns are reusable blueprints for structuring object interactions. The Gang of Four (GoF) catalogue from 1994 identified 23 patterns; four of them — Strategy, Factory, Observer, and Decorator — appear constantly in ML frameworks like PyTorch, Keras, scikit-learn, and HuggingFace.

Analogy: Think of a Swiss Army knife. The blade, scissors, and screwdriver all share the same handle interface, can be swapped in/out, and each adds exactly one capability without touching the others. That's these four patterns at work simultaneously.

💡 If you remember one thing

Strategy swaps algorithms at runtime. Factory centralises creation. Observer decouples event producers from consumers. Decorator wraps behaviour without modifying the original. Together they enable the plug-and-play architecture that makes frameworks extensible.

Why ML specifically needs these: ML codebases are experiment-heavy. Researchers swap optimisers, loss functions, data augmentation, and metrics constantly. Without patterns, each swap requires grep-and-replace across dozens of files. With patterns, a config change reroutes the entire system.

2
The Four Patterns — Internals & ML Use Cases
▼

Strategy — Swap algorithm at runtime

The Strategy pattern defines a family of algorithms behind a common interface, encapsulates each one, and makes them interchangeable. The Context (e.g., Trainer) delegates work to whichever ConcreteStrategy (SGD, Adam, AdaGrad) is currently injected. The crucial guarantee: the Context never inspects the type of the strategy; it only calls the interface method step(params, grads).

Key Concept

Every optimizer in PyTorch is a Strategy. torch.optim.Optimizer is the abstract interface; SGD, Adam, AdamW, RMSprop are concrete strategies. Trainer.optimizer.step() is the delegation call.

Loss function as Strategy: criterion = nn.CrossEntropyLoss() vs nn.MSELoss() vs a custom focal loss — all expose the same __call__(pred, target) interface. Swapping is one line, not a rewrite.

Factory — Centralise object creation

The Factory (or Factory Method / Abstract Factory) encapsulates the which class? and how to configure it? decisions. A ModelFactory.build(config) receives a dictionary and returns an nn.Module. The client never calls ResNet50(...) directly — it cannot even spell the class name; it only knows nn.Module. This is exactly how timm.create_model("resnet50", pretrained=True) and AutoModel.from_pretrained("bert-base-uncased") are implemented.

Key Concept

Factory = a function/class whose job is to create other objects. The registry pattern (a dict mapping name → builder class) is the standard ML variant. HuggingFace's AutoModel uses exactly this: a class name string maps to the model class in a registry dict.

Observer — Decouple event producers from consumers

The Observer (also called Publish-Subscribe) lets a Subject (Trainer) notify a list of Observers (Callbacks) when events occur, without knowing anything about them. Keras callbacks, PyTorch Lightning hooks, and HuggingFace TrainerCallback all implement this. The Subject fires: on_train_begin, on_epoch_end(logs), on_batch_end(logs). Any new observer (checkpoint saver, LR scheduler, Wandb logger) registers without changing the Trainer at all.

⚠ Common Mistake

Confusing Observer with Strategy. Observer is about notification (1 producer → N consumers), Strategy is about behaviour selection (1 slot → 1 algorithm). A Trainer uses both: Strategy for the optimizer, Observer for callbacks.

Decorator — Add behaviour without subclassing

A Decorator wraps an existing object (or function) to add new behaviour, exposing the same interface. Python's @functools.wraps, @torch.no_grad(), @torch.compile, and @lru_cache are all decorators. The core function is untouched; each decorator adds exactly one responsibility (timing, caching, grad-disabling) and delegates to the wrapped function. Decorators compose: @timer @no_grad @cache def forward(x) is three decorators stacked — call order is outermost first.

Call Chain

Call: forward(x) → timer.__call__(x) → no_grad.__call__(x) → cache.__call__(x) → original forward(x). Return value bubbles back up the same chain.

3
Formal Properties & Mathematics
▼

Design patterns are fundamentally about interface contracts and substitution. The mathematical backbone is the Liskov Substitution Principle (LSP) and type-theory subtyping.

Liskov Substitution Principle (LSP)

For the Strategy pattern, if \(S\) is a concrete strategy (SGD) and \(T\) is the abstract interface (Optimizer), then every property \(\phi\) that holds for objects of type \(T\) must hold for objects of type \(S\):

$$\forall\, s \in S,\; \phi(s) \text{ holds} \implies \phi(t) \text{ holds for all } t \in T$$

Concretely: any ConcreteStrategy must honour the signature step(params: List[Tensor], grads: List[Tensor]) -> None and must update params in-place. Breaking either guarantee breaks the substitution.

Decorator Composition is Function Composition

Given decorators \(D_1, D_2, D_3\) applied to base function \(f\), the decorated function is:

$$\hat{f} = D_1 \circ D_2 \circ D_3 \circ f$$

where \(\circ\) denotes function composition. Composition is associative but not commutative — order matters. \(@\text{no\_grad}\) then \(@\text{timer}\) profiles after disabling grad; \(@\text{timer}\) then \(@\text{no\_grad}\) disables grad after timing starts.

Observer: Publish-Subscribe as a Partial Order

Define events \(E = \{e_1, e_2, \ldots, e_k\}\) in causal order (e.g., on_train_begin < on_epoch_begin < on_batch_end < on_epoch_end < on_train_end). The Subject guarantees delivery in this partial order. Callbacks may modify shared state \(\sigma\) (e.g., set should_stop=True), which the Subject polls:

$$\sigma_{t+1} = \sigma_t \oplus \bigoplus_{cb \in \mathcal{C}} cb(e_t, \sigma_t)$$

where \(\oplus\) is state merge. This is the formal basis of PyTorch Lightning's callback state accumulation.

Factory: Type-Level Abstraction

A factory \(F\) is a function from configuration space \(\mathcal{C}\) to object space \(\mathcal{O}\):

$$F : \mathcal{C} \to \mathcal{O}, \quad F(\text{cfg}) = o \text{ where } \text{type}(o) \prec T$$

The client only knows the return type \(T\) (e.g., nn.Module). The factory hides the concrete subtype. This is parametric polymorphism at the value level.

Design Insight

All four patterns are mechanisms to honour the Open/Closed Principle: software entities should be open for extension, closed for modification. Strategy opens the algorithm slot. Factory opens the creation. Observer opens the event handler list. Decorator opens the behaviour stack. None require touching existing code.

Strategy — Optimizer & Loss

class Optimizer(ABC): # Abstract Strategy interface
@abstractmethod
def step(self, params, grads): ... # contract: update params in-place
class SGD(Optimizer): # ConcreteStrategy A
def __init__(self, lr=0.01, momentum=0.9):
self.lr, self.momentum, self.v = lr, momentum, {}
def step(self, params, grads): # velocity update rule
for i,(p,g) in enumerate(zip(params,grads)):
self.v[i] = self.momentum*self.v.get(i,0) + g
p -= self.lr * self.v[i] # θ ← θ − α·v
class Adam(Optimizer): # ConcreteStrategy B
def __init__(self, lr=1e-3, b1=0.9, b2=0.999):
self.lr,self.b1,self.b2,self.m,self.v,self.t=lr,b1,b2,{},{},0
def step(self, params, grads): # biased-corrected moments
self.t += 1
for i,(p,g) in enumerate(zip(params,grads)):
self.m[i] = self.b1*self.m.get(i,0) + (1-self.b1)*g
self.v[i] = self.b2*self.v.get(i,0) + (1-self.b2)*g**2
m_ = self.m[i]/(1-self.b1**self.t) # bias correction
v_ = self.v[i]/(1-self.b2**self.t)
p -= self.lr * m_/(v_**0.5 + 1e-8)
class Trainer: # Context
def __init__(self):
self.optimizer: Optimizer = SGD() # slot typed to interface
def set_optimizer(self, opt: Optimizer):
self.optimizer = opt # runtime swap — one line
def train_step(self, params, grads):
self.optimizer.step(params, grads) # delegation; no type check
# Usage: swap optimizer without touching Trainer
trainer = Trainer() # uses SGD by default
trainer.set_optimizer(Adam(lr=3e-4)) # swap → Adam mid-training

Factory — Model creation via registry

MODEL_REGISTRY = {} # name → builder function
def register(name): # registration decorator
def decorator(cls): # wraps builder class
MODEL_REGISTRY[name] = cls
return cls
return decorator
@register("resnet50") # add to registry
class ResNet50Builder:
def build(self, cfg) -> nn.Module: # returns abstract type
return torchvision.models.resnet50(pretrained=cfg.get("pretrained",False))
@register("vit_b16")
class ViTB16Builder:
def build(self, cfg) -> nn.Module:
return timm.create_model("vit_base_patch16_224", pretrained=cfg.get("pretrained",False))
class ModelFactory:
def build(self, cfg: dict) -> nn.Module: # client calls this only
name = cfg["arch"]
builder = MODEL_REGISTRY.get(name)
if builder is None: raise ValueError(f"Unknown arch: {name}")
return builder().build(cfg)
# Client code: only touches config
factory = ModelFactory()
model = factory.build({"arch": "resnet50", "pretrained": True})
# swap arch: change ONE key in config — zero code changes

Observer — Training callbacks

class Callback(ABC): # Observer interface
def on_train_begin(self, logs=None): pass
def on_epoch_end(self, epoch, logs=None): pass # event hook
def on_train_end(self, logs=None): pass
class TensorBoardLogger(Callback): # ConcreteObserver A
def __init__(self, log_dir="runs/"):
from torch.utils.tensorboard import SummaryWriter
self.writer = SummaryWriter(log_dir)
def on_epoch_end(self, epoch, logs=None): # react to event
for k,v in (logs or {}).items():
self.writer.add_scalar(k, v, epoch) # write to TB; Trainer unaware
class EarlyStopping(Callback): # ConcreteObserver B
def __init__(self, patience=5, monitor="val_loss"):
self.patience,self.monitor,self.best,self.wait=patience,monitor,float("inf"),0
self.should_stop = False
def on_epoch_end(self, epoch, logs=None):
val = (logs or {}).get(self.monitor, float("inf"))
if val < self.best: self.best,self.wait=val,0
else:
self.wait += 1
if self.wait >= self.patience: self.should_stop = True # signal
class Trainer: # Subject
def __init__(self): self.callbacks: list[Callback] = []
def add_callback(self, cb: Callback): self.callbacks.append(cb) # subscribe
def _fire(self, event, **kw): # notify all observers
for cb in self.callbacks: getattr(cb, event)(**kw)
def fit(self, epochs):
self._fire("on_train_begin")
for e in range(epochs):
logs = self._run_epoch() # returns {loss, val_loss}
self._fire("on_epoch_end", epoch=e, logs=logs)
if any(getattr(cb,"should_stop",False) for cb in self.callbacks): break

Decorator — @torch.no_grad, @timer, @lru_cache

import time, functools, torch
def timer(fn): # timing decorator
@functools.wraps(fn) # preserves __name__, __doc__
def wrapper(*args, **kwargs):
t0 = time.perf_counter()
result = fn(*args, **kwargs) # delegate to wrapped fn
print(f"{fn.__name__} took {(time.perf_counter()-t0)*1000:.2f}ms")
return result
return wrapper
def cache_shapes(fn): # shape-based caching decorator
_cache = {}
@functools.wraps(fn)
def wrapper(x):
key = x.shape # cache key = input shape
if key not in _cache:
_cache[key] = fn(x) # compute once per shape
return _cache[key]
return wrapper
class Predictor:
def __init__(self, model): self.model = model
@timer # outermost: runs first on call
@torch.no_grad() # middle: disables grad tracking
@cache_shapes # innermost: nearest to base fn
def predict(self, x: torch.Tensor):
return self.model(x).argmax(dim=-1) # base fn: untouched by decorators
# call sequence: timer→no_grad→cache_shapes→predict(x)
# decorator composition: predict = timer(no_grad()(cache_shapes(predict)))

Key Takeaways & When to Use
▼
Decision Guide

Strategy — when you have multiple algorithms for the same task and need to swap them at runtime (optimizers, losses, samplers, schedulers). Factory — when object creation is complex or config-driven (model architectures, data loaders, tokenizers). Observer — when multiple independent subsystems need to react to events (logging, checkpointing, early stopping, LR warmup). Decorator — when you want to add cross-cutting concerns (profiling, caching, grad control) without modifying the function.

In production ML: These four patterns together give you a plug-and-play experiment framework. Config-driven Factory selects the model. Strategy-based Trainer swaps optimisers and losses. Observer-based callback system logs and checkpoints. Decorator-wrapped inference handles caching and safety.

Related topics: Dependency Injection, Repository Pattern, Command Pattern, SOLID principles, PyTorch hooks, Lightning Fabric, HuggingFace Trainer API.

⚠ Anti-patterns to avoid

God Trainer: a Trainer that directly calls tensorboard.add_scalar(), does early stopping logic, and saves checkpoints internally — violates Observer, makes testing impossible. if-else factories: if arch == "resnet": model = ResNet50() — violates Open/Closed. Inheritance for behaviour extension: subclassing Trainer to add logging — violates composition-over-inheritance; use Decorator or Observer instead.
