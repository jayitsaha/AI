Apriori Algorithm

Level-wise frequent-itemset mining via the downward-closure (anti-monotone) property
Intermediate Association Rule Mining Classical ML Worst-case O(2|I|)
1
Understanding the Concept

What is this? Apriori is an algorithm for finding patterns in shopping baskets (or any transaction dataset). It discovers which groups of items tend to appear together, and then derives rules like "customers who buy bread and butter also buy milk."

Real-world analogy: Imagine a store manager who highlights products on the shelf that are often bought together. Instead of checking every possible product combination (there are millions), she uses a clever shortcut: if "bread + cheese" is already rare, then "bread + cheese + wine" will be even rarer — skip it entirely. That shortcut is the anti-monotone property, and Apriori exploits it systematically.

💡 If you remember one thing
Apriori's power is the downward-closure property: if an itemset is infrequent, every superset is also infrequent. This lets the algorithm prune exponentially many candidates before scanning the database.

Three numbers drive every rule: support (how often items appear together), confidence (how often the rule is correct when the antecedent appears), and lift (how much more often than by chance).

$$\text{support}(X) = \frac{|\{T \in \mathcal{D} : X \subseteq T\}|}{|\mathcal{D}|} \qquad \text{confidence}(X \Rightarrow Y) = \frac{\text{support}(X \cup Y)}{\text{support}(X)}$$

How It Works Internally — Level-wise Search

The Core Loop

Apriori proceeds in k-itemset rounds. In each round it does exactly two things:

  1. Generate candidates \(C_k\) — Join pairs of frequent \((k{-}1)\)-itemsets that share the same \((k{-}2)\)-prefix.
  2. Scan the database — Count the support of each candidate by scanning every transaction.
  3. Prune — Discard any \(C_k\) candidate whose any \((k{-}1)\)-subset is infrequent (they cannot be frequent by anti-monotonicity).
  4. Collect — Those that pass min-sup become \(L_k\), the frequent \(k\)-itemsets.

The algorithm terminates when no new frequent itemsets are found (or candidates are empty).

Why the Join Step Works

Two frequent \((k{-}1)\)-itemsets \(p\) and \(q\) (sorted lexicographically) are joined if they share the same first \(k{-}2\) items: \(\{p_1,\ldots,p_{k-2},p_{k-1}\}\) joins with \(\{p_1,\ldots,p_{k-2},q_{k-1}\}\) to form \(\{p_1,\ldots,p_{k-2},p_{k-1},q_{k-1}\}\). This generates exactly the right set of size-\(k\) candidates — no duplicates, no misses.

Key Invariant — Downward-Closure (Anti-Monotone) Property
For all itemsets \(X\) and \(Y\): if \(X \subseteq Y\) then \(\text{support}(Y) \leq \text{support}(X)\). Consequently, if \(X\) is infrequent, no superset of \(X\) can be frequent. Apriori uses this to prune the search space level by level.

Numerically Exact Example

Database: 4 transactions, items \(\{A,B,C,D,E\}\), min-sup threshold = 0.5 (i.e., ≥ 2/4 = 2 transactions).

T1: {A, B, C}
T2: {A, B, D}
T3: {A, C, D}
T4: {B, C, D}

k=1 scan: Count singles: A=3, B=3, C=3, D=3, E=0. With min-sup ≥ 2: \(L_1 = \{A,B,C,D\}\). E is pruned.

k=2 join & scan: Generate \(C_2\) by combining \(L_1\) pairs: {AB},{AC},{AD},{BC},{BD},{CD}. Count each:

{A,B}: T1,T2       → sup=2  ✓ frequent
{A,C}: T1,T3       → sup=2  ✓ frequent
{A,D}: T2,T3       → sup=2  ✓ frequent
{B,C}: T1,T4       → sup=2  ✓ frequent
{B,D}: T2,T4       → sup=2  ✓ frequent
{C,D}: T3,T4       → sup=2  ✓ frequent

All 6 pairs are frequent → \(L_2 = C_2\). No pruning at this level.

k=3 join: Pairs from \(L_2\) sharing prefix of length 1 (for k=3):

{A,B} ∪ {A,C} → {A,B,C} — check subsets: {A,B}✓ {A,C}✓ {B,C}✓ → keep
{A,B} ∪ {A,D} → {A,B,D} — check subsets: {A,B}✓ {A,D}✓ {B,D}✓ → keep
{A,C} ∪ {A,D} → {A,C,D} — check subsets: {A,C}✓ {A,D}✓ {C,D}✓ → keep
{B,C} ∪ {B,D} → {B,C,D} — check subsets: {B,C}✓ {B,D}✓ {C,D}✓ → keep

k=3 scan: Count each \(C_3\) candidate:

{A,B,C}: T1       → sup=1  ✗ pruned (below min-sup)
{A,B,D}: T2       → sup=1  ✗ pruned
{A,C,D}: T3       → sup=1  ✗ pruned
{B,C,D}: T4       → sup=1  ✗ pruned

\(L_3 = \emptyset\). Algorithm terminates. Final frequent itemsets: all of \(L_1\) and \(L_2\).

⚠ Design Decision — Why Multiple DB Scans?
Each level k requires one full database scan. For large datasets with many levels, this is the performance bottleneck. FP-Growth was invented to solve this by compressing the database into an FP-Tree and mining it without repeated scans.

Deriving Association Rules from Frequent Itemsets

Once we have all frequent itemsets, we generate rules \(X \Rightarrow Y\) where \(X \cap Y = \emptyset\) and \(X \cup Y\) is a frequent itemset. A rule passes if its confidence exceeds min-conf.

$$\text{lift}(X \Rightarrow Y) = \frac{\text{support}(X \cup Y)}{\text{support}(X) \cdot \text{support}(Y)}$$

Lift > 1 means the items appear together more than by chance; lift = 1 means independence; lift < 1 means negative correlation.

Example rules from our dataset (min-conf = 0.6):

RuleSupportConfidenceLift
{A} ⇒ {B}2/4 = 0.502/3 = 0.670.67/(0.75) = 0.89
{B} ⇒ {A}2/4 = 0.502/3 = 0.670.89
{A,B} ⇒ {C}not applicable (sup=1)——
{A} ⇒ {C}2/4 = 0.502/3 = 0.670.89
{C} ⇒ {A}2/4 = 0.502/3 = 0.670.89
{B} ⇒ {D}2/4 = 0.502/3 = 0.670.89
{D} ⇒ {C}2/4 = 0.502/3 = 0.670.89

All lift values <1 here because items are somewhat negatively correlated in this tiny dataset — each transaction is missing exactly one item.

Key Takeaways
Core Algorithm Summary
  1. Scan DB once for frequent 1-itemsets \(L_1\).
  2. Generate candidate \(k\)-itemsets by joining \(L_{k-1}\) with itself.
  3. Prune candidates with any infrequent subset (anti-monotone property).
  4. Scan DB to count survivors → keep those ≥ min_sup → \(L_k\).
  5. Repeat until \(L_k = \emptyset\). Generate rules from all \(L_k\).
  • Use when: Interpretable rules needed, small-medium datasets, offline mining
  • Avoid when: Very large datasets (prefer FP-Growth), high-dimensional item spaces, real-time requirements
  • Related topics: FP-Growth, Eclat, Market Basket Analysis, Collaborative Filtering, Sequential Pattern Mining
⚠ Common Pitfall — Correlation ≠ Causation
A high-lift rule beer ⇒ diapers (the famous example) describes co-occurrence, not causation. Use domain knowledge to interpret rules; mine for patterns, not mechanisms.
